1. 도입 — 버그를 찾는 시대에서, 없음을 증명하는 시대로

10월 22일, Anthropic Frontier Red Team이 형식 검증(formal verification) 스타트업 Theorem과 함께 낸 연구 글 하나가 이번 주 엔지니어링 담론을 삼켰습니다. 제목부터 도발적입니다 — "LLMs are making formal software verification feasible at a much larger scale". Hacker News에서 457포인트, 댓글 303개를 모으며 한 주 내내 상위권에 머물렀고, DevOps.com, Unite.AI 등이 연달아 보도했습니다.

발표 내용을 한 문장으로 줄이면 이렇습니다. Claude가 몇 주 만에 오픈소스 라이브러리 123개의 컴파일된 RISC-V 바이너리에 대해 약 1억 8천만 줄의 기계 검증 증명을 쓰고, "64MB 이하의 어떤 입력을 넣어도 crash하지 않는다"를 수학적으로 증명했다. 사람 손으로는 수십 년이 걸렸을 분량입니다. 그리고 증명을 시도하는 과정에서, 퍼저(fuzzer)가 수년간 돌면서도 놓친 버그 수백 개가 함께 드러났습니다.

타이밍이 절묘합니다. 지난주 이 블로그에서 다뤘듯 에이전트가 공격자이자 피해자가 된 주간이었습니다. AI가 버그를 찾고 악용하는 속도는 점점 빨라지는데, 방어 쪽은 여전히 "테스트 돌려보고 통과하면 배포"에 머물러 있습니다. Anthropic의 주장은 명확합니다 — 공격이 자동화되는 시대에는 버그를 더 많이 찾는 것만으로는 부족하고, 버그가 없다는 보장(guarantee)이 필요하다는 것. 그런데 그 보장을 만드는 형식 검증은 지금까지 너무 비싸서 극소수 안전-중요(safety-critical) 시스템의 사치품이었습니다.

이 글에서는 "LLM은 환각을 하는데 어떻게 증명을 믿지?"라는 당연한 의문부터 시작해서, 왜 이 조합이 오히려 LLM에게 가장 잘 맞는 일인지, 파이프라인이 실제로 어떻게 생겼는지, 그리고 "증명됐다"는 말을 어디까지 믿어야 하는지까지 차례로 뜯어봅니다.

2. 배경 — 테스트·퍼징·형식 검증은 각각 무엇을 보장하나

셋의 차이를 입력 공간(입력이 될 수 있는 모든 값의 집합) 관점에서 보면 명확합니다.

  • 테스트는 내가 고른 입력 몇 개에 대해 "이 입력에서는 맞게 동작한다"를 확인합니다. 입력 공간에 점 몇 개를 찍는 일입니다.
  • 퍼징(fuzzing)은 무작위(정확히는 커버리지 피드백 기반) 입력을 수백만 개 던져서 crash를 찾습니다. 점을 훨씬 많이, 더 교묘하게 찍지만 여전히 점입니다.
  • 형식 검증은 "모든 입력에 대해 이 성질이 성립한다"를 수학 증명으로 보입니다. 점이 아니라 영역 전체를 칠하는 일입니다.

그럼 왜 다들 형식 검증을 안 썼을까요? 비용이 터무니없었기 때문입니다. 가장 유명한 사례인 검증된 마이크로커널 seL4는 C 코드 약 8,700줄을 검증하는 데 손으로 쓴 Isabelle 증명 스크립트 20만 줄이 들었고, 설계부터 검증까지 전체 프로젝트에 20인년이 넘는 노력이 투입됐습니다. 코드 1줄에 증명 20~30줄, 그것도 박사급 증명 엔지니어의 손으로요. 이 비용 구조 때문에 형식 검증은 항공·우주·커널 같은 극단적 분야 밖으로 나오지 못했습니다.

비용의 정체는 두 가지입니다. 첫째, 스펙(specification) 작성 — "이 프로그램이 맞게 동작한다"에서 '맞게'를 수학 언어로 정의하는 일 자체가 어렵습니다. 둘째, 증명 작성 — 그 스펙이 성립함을 보이는 증명을 쓰는 노동이 코드 작성의 수십 배입니다. Anthropic×Theorem의 작업은 이 둘을 각각 다른 방법으로 격파합니다. 스펙은 이미 존재하는 fuzz target에서 자동 생성하고(4장), 증명 노동은 LLM에게 떠넘깁니다(3장).

3. 핵심 — 환각하는 모델에게 증명을 맡겨도 되는 이유

여기서 당연한 의문이 나옵니다. LLM은 그럴듯한 거짓말, 즉 환각(hallucination)을 하는데, 그런 모델이 쓴 "증명"을 어떻게 믿죠?

답은 믿지 않아도 된다입니다. 형식 검증의 세계에는 생성과 검사 사이에 근본적인 비대칭이 있습니다. 증명을 만드는 일은 창의성이 필요한 어려운 탐색이지만, 다 만들어진 증명이 올바른지 검사하는 일은 완전히 기계적입니다. Rocq(록크, 증명 보조기 Coq의 새 이름) 같은 증명 보조기(proof assistant)에는 작은 검사기(proof checker)가 붙어 있는데, 이 검사기는 증명의 모든 단계가 논리 규칙을 정확히 따르는지 한 줄씩 확인합니다. 단 한 단계라도 비약이 있으면 통과하지 못합니다.

그래서 구조가 이렇게 됩니다. LLM은 신뢰하지 않는 생성기(untrusted generator)로 두고, 신뢰는 전부 작은 검사기에 몰아줍니다. LLM이 환각으로 엉터리 증명을 100번 내놓아도, 검사기가 100번 다 거부하면 그만입니다. 통과한 증명 하나는 — 모델이 어떤 과정으로 만들었든 — 수학적으로 올바릅니다. 코드 리뷰처럼 "사람이 읽고 납득"할 필요가 없습니다. 실제로 이번 작업에서 증명 하나가 보통 60만 줄인데, 아무도 그걸 읽지 않습니다. 검사기가 읽습니다.

이 구조는 LLM 입장에서도 최고의 작업 환경입니다. 에이전트 루프에서 늘 문제가 되는 게 "결과가 맞는지 누가 확인하나"였는데(검증 병목, 검증기 엔지니어링 글에서 다뤘습니다), 여기서는 완벽한 채점기가 공짜로 주어집니다. 증명이 틀리면 검사기가 어디서 왜 틀렸는지 즉시 알려주고, 모델은 그 피드백으로 다시 시도합니다. 성공 신호에 거짓 양성이 없으니 몇 번을 돌려도 결과가 오염되지 않습니다. 보상 신호가 완벽한 RL 환경과 같은 꼴입니다.

Rocq가 뭔가요? 40년 역사의 증명 보조기 Coq가 2025년에 Rocq Prover로 이름을 바꿨습니다. 수학 정리와 프로그램 성질을 기계가 검사할 수 있는 형태로 쓰고 증명하는 도구로, 검증된 C 컴파일러 CompCert가 이걸로 만들어졌습니다. 비슷한 도구로 Lean, Isabelle, 그리고 Rust 코드 검증에 쓰는 Verus 등이 있습니다.

4. 파이프라인 해부 — fuzz target이 공짜 스펙이 되기까지

2장에서 형식 검증의 비용이 "스펙 작성 + 증명 작성"이라고 했습니다. 증명 작성은 LLM이 맡는다 치고, 스펙은 어떻게 할까요? "이 라이브러리가 맞게 동작한다"를 수학으로 쓰는 일은 여전히 사람 몫 아닌가요?

여기가 이 작업에서 가장 영리한 부분입니다. 세상에는 이미 수십만 개의 실행 가능한 스펙이 있습니다 — 바로 fuzz target입니다. Google의 OSS-Fuzz 프로그램에 등록된 오픈소스 프로젝트들은 이런 모양의 진입점을 갖고 있습니다.

{{< highlight c >}} // 전형적인 fuzz target: "어떤 data가 와도 crash하면 안 된다"는 뜻 int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) { my_image img; if (decode_image(data, size, &img) == OK) { // 임의 입력 파싱 encode_image(&img); // 파싱됐으면 재인코딩도 돼야 함 free_image(&img); } return 0; // 여기까지 crash 없이 도달하는 것 자체가 성질(property) } {{< /highlight >}}

이 함수의 의미를 뒤집어 읽으면 그대로 형식 스펙이 됩니다. "모든 입력 data에 대해, 이 함수는 crash(메모리 안전성 위반, assertion 실패)하지 않는다." OSS-Fuzz는 C/C++ 코드를 AddressSanitizer(ASan, 잘못된 메모리 접근 시 즉시 crash시키는 계측 도구)와 함께 컴파일하므로, out-of-bounds 읽기/쓰기 같은 메모리 버그가 crash라는 관측 가능한 사건으로 바뀝니다. 개발자가 스펙을 한 줄도 새로 쓸 필요가 없습니다.

전체 파이프라인은 이렇게 돌아갑니다.

왜 소스 코드가 아니라 RISC-V 바이너리를 증명 대상으로 삼았을까요? 소스 수준에서 증명하면 "컴파일러가 소스의 의미를 보존했다"는 가정이 추가로 필요합니다. 컴파일러 버그나 C의 미정의 동작(undefined behavior)이 끼어들 틈이 생기죠. 기계어 수준에서 증명하면 실제로 실행되는 그 바이트들에 대한 보장이 되고, 믿어야 할 대상 목록(6장)에서 컴파일러가 빠집니다. RISC-V를 고른 건 명령어 집합이 단순해서 형식 의미론(semantics, 각 명령이 기계 상태를 어떻게 바꾸는지의 수학적 정의)을 만들기 좋기 때문입니다. Theorem이 이 의미론을 만들었고, rocq-linux-process-semantics로 공개돼 있습니다 — RV64GC 바이너리를 실행하는 Linux 프로세스(v6.18 기준, 시스템 콜별 명세 포함)의 Rocq 모델입니다.

이렇게 해서 라이브러리 123개, fuzz 진입점 239개가 증명됐습니다. 바이너리 하나가 중앙값 1만 8천 개의 RISC-V 명령어이고, 증명 전체는 약 1억 8천만 줄. 성질은 "64MB 이하의 모든 입력에서 crash 없음"입니다. 64MB라는 한도가 아쉽게 들릴 수 있지만, 한도를 올리는 건 스펙의 파라미터 하나를 바꾸고 재증명을 돌리는 일이라 사람 노력이 거의 들지 않습니다. 참고로 퍼저들은 대부분 입력을 1MB 이하로 제한합니다.

5. 결과 — 퍼저가 수년간 놓친 버그들

증명이 안 되는 지점은 둘 중 하나입니다. 증명 전략이 나빴거나, 정말로 crash하는 입력이 존재하거나. 후자라면 그게 바로 버그입니다. 이번 작업에서 이렇게 찾은 버그가 수백 개인데, 몇 개를 보면 왜 퍼저가 못 찾았는지가 보입니다.

버그내용퍼저가 놓친 이유
압축 해제기 counter underflow카운터가 0 아래로 내려가며 out-of-bounds 쓰기 발생약 20MB짜리 입력 + 희귀한 내부 레이아웃이 필요 — 퍼저의 1MB 한도 밖

흥미로운 건 crash 버그만 나온 게 아니라는 점입니다. "애플리케이션이 로드할 수 있는 파일을 제한하는 기능이 항상 강제되지는 않는다"는 로직 버그도 증명 과정에서 드러났습니다. 그리고 fuzz target이 단순 no-crash 이상을 검사하는 경우 — 압축했다 풀면 원본이 나와야 한다(round-trip), 두 구현의 출력이 같아야 한다(differential) 같은 assertion — 그 성질까지 통째로 증명됩니다. "이 테스트 스위트는 영원히 통과한다"가 증명되는 셈이니까요.

난이도를 보여주는 사례 하나. HTTP 라이브러리 cpp-httplib의 증명에서는 std::set 소멸자의 재귀가 스택 오버플로를 일으키지 않음을 보여야 했는데, 그러려면 libc++ 레드-블랙 트리의 리밸런싱이 트리 깊이를 로그 수준으로 유지한다는 사실을 기계어 수준에서 증명해야 했습니다. 자료구조 교과서의 정리를 컴파일된 바이너리에 대고 다시 증명한 겁니다.

본편 밖의 사이드 실험들도 시사점이 큽니다. Claude가 RFC 1950 (zlib 포맷)의 형식 스펙을 직접 쓰고 Linux 커널의 zlib을 x86 바이너리 수준에서 증명했고(이때 x86 의미론도 Claude가 생성), 비슷한 과정을 널리 쓰이는 라이브러리 6개 정도에 반복해 "이미 거의 완전히 올바르다"는 결론을 얻었습니다. 한 PDF 리더에 간단한 보안 성질 증명을 시도하자 일주일 만에 보통 1년 치로 보고되는 수준의 보안 버그가 나왔고, 10년 넘게 잠복해 있던 로직 버그도 찾았습니다. 모두 Anthropic의 자체 보고 수치라는 점은 감안해야 합니다.

6. 그래서 무엇을 믿어야 하나 — TCB와 "증명됐다 ≠ 버그 없다"

"수학적으로 증명됐다"는 말은 강력하지만 공짜는 아닙니다. 모든 형식 검증에는 신뢰 컴퓨팅 기반(TCB, trusted computing base) — 증명 없이 그냥 믿어야 하는 최소한의 구성 요소 — 이 있습니다. 이번 작업의 TCB는 다음과 같습니다.

믿어야 하는 것왜
RISC-V·Linux 프로세스의 형식 모델모델이 실제 CPU·커널과 다르면 증명은 "다른 세계"에 대한 증명이 됨. Theorem 스스로 "증명은 모델만큼만 좋다"고 명시
증명된 정리 문장 그 자체스펙이 내 의도와 다르면, 올바른 증명도 엉뚱한 보장. 검사기는 "스펙이 현실과 맞는지"는 검사하지 못함
Rocq 검사기검사기 버그 가능성. 다만 수십 년 검증된 작은 코드이고, 검사기를 믿는다는 건 그 아래 하드웨어·OS·OCaml 컴파일러까지 믿는다는 뜻

반대로 목록에 없는 것들이 핵심입니다. Claude도, 1억 8천만 줄의 증명 자체도, 컴파일러도 믿을 필요가 없습니다. 전부 검사기 뒤에 있으니까요.

Hacker News 토론도 정확히 이 지점에 몰렸습니다. "검사기는 스펙이 현실과 일치하는지 알려주지 않는다"는 지적, 그리고 과거 LLM 증명 연구에서 논문 주장과 실제 증명 코드가 달랐던 사례를 들며 마케팅을 경계하는 목소리가 있었습니다. 타당한 경계입니다 — 그리고 Anthropic 글 자체도 한계를 길게 적어 뒀습니다.

"formally verified"가 보장하지 않는 것들. ① 증명 대상은 musl 정적 링크 RISC-V 단일 스레드 바이너리 — 실제 배포 환경(x86/ARM, glibc 동적 링크, 멀티스레드)은 모델 밖입니다. ② 모든 진입점이 검증된 게 아니고, 진입점 검증이 라이브러리 전체를 덮지도 않습니다. ③ ASan이 못 잡는 메모리 버그 유형이 있습니다. ④ 호출하는 쪽이 라이브러리를 잘못 쓰면(API 계약 위반) 여전히 메모리가 깨질 수 있습니다. 증명은 스펙에 적힌 것만, 모델이 맞는 만큼만 보장합니다.

7. 엔지니어링 디테일 — 토큰 비용, 증명 재사용, reward hacking

"그래서 얼마 드는데?"가 다음 질문입니다. 증명 하나에 수억 토큰이 들 수 있습니다. 싸지 않죠. 다만 비용 곡선이 가파르게 내려가고 있다는 게 Anthropic의 포인트입니다. OSS-Fuzz 코드에서 뽑은 작은 과제 36개 실험에서, Opus 5.5는 절반을 증명하면서 Opus 5보다 토큰을 약 40% 덜 썼습니다. 모델 세대가 바뀔 때마다 증명 가능 범위는 넓어지고 단가는 떨어지는 구조입니다.

구조적인 절감 장치도 있습니다. 증명 재사용입니다. 에이전트 여러 개가 증명을 공유하는 작업 공간(shared workspace)을 쓰자 혼자 일할 때보다 토큰이 17% 줄었고, 혼자서는 못 끝내던 증명 2개도 완료됐습니다. 123개 라이브러리는 C 런타임 초기화나 ASan 코드처럼 공통 부분이 많아서, 한 팀이 끝낸 증명을 다른 팀이 복사해 자기 프로그램에 맞게 고치는 식으로 일했습니다. 수학계의 Lean 라이브러리 Mathlib이 700명 넘는 기여자의 정리 30만 개를 쌓아 올린 것처럼, 증명은 쌓일수록 다음 증명이 싸집니다. 소프트웨어 의존성은 파워 로(power law)를 따르므로 glibc·OpenSSL·cURL 같은 공유 라이브러리 소수만 검증해도 스택의 큰 부분이 열립니다 — Theorem이 Nix 생태계 검증 로드맵을 내놓은 이유입니다.

마지막으로, 에이전트를 돌려 본 사람이라면 반드시 떠올릴 문제 — reward hacking은 어떻게 막았을까요? "어떤 입력에도 crash하지 않음을 증명하라 + 필요하면 패치해도 됨"이라는 과제에는 명백한 꼼수가 있습니다. 프로그램을 아무것도 안 하는 코드로 바꿔 버리면 증명이 쉬워지니까요. 대응은 세 겹입니다: 패치 자체에 페널티를 주고, "이 패치가 바꾸는 입력이 정확히 어떤 것들이고 얼마나 적은지"를 증명하면 가산점을 주고, 모든 패치를 로깅·감사했습니다. 완벽한 검증기가 있어도 목표 설계는 여전히 사람 몫이라는 좋은 사례입니다(에이전트 reward hacking 글 참고).

8. 실전 — 내 프로젝트 검증 대상으로 올려보기

직접 증명을 쓸 필요는 없습니다. Theorem이 파이프라인을 서비스로 돌려 주는 OSS Verify 프로그램을 공개했기 때문입니다. 오픈소스 메인테이너라면 프로젝트를 등록만 하면 됩니다. 조건은 네 가지 — OSI 승인 라이선스, 공개 git 저장소, fuzz target 1개 이상, 빌드 가능한 언어. 등록 절차는 PR 하나입니다.

{{< highlight bash >}} # 1) oss-verify를 포크하고 프로젝트 디렉터리를 만든다 git clone https://github.com/<내계정>/oss-verify && cd oss-verify mkdir projects/myproject # projects/myproject/ 안에 템플릿을 참고해 세 파일을 만든다: # project.yaml — 메타데이터 (버그를 비공개로 통보받을 primary_contact 필수) # Dockerfile — 빌드 환경 # build.sh — fuzz target 빌드 스크립트 # 2) 로컬 검증 — 빌드가 재현 가능한지(두 번 빌드해 바이트 단위 동일) 확인 python3 tools/validate.py tools/check --no-shell --twice myproject # 3) PR을 연다. 머지되면 Theorem이 타깃을 빌드해 SHA-256을 고정하고, # 바이너리에 대한 정리를 세워 증명한다. 발견된 버그는 primary_contact에게 # 비공개로 전달된다. {{< /highlight >}}

요구 사양은 Linux x86-64 + Docker buildx + Python 3, 디스크 약 10GB입니다. 저장소에는 Claude Code로 등록 작업을 자동화하는 skill(.claude/skills/add-project/)도 들어 있습니다. 한 가지 주의 — tools/check는 해당 프로젝트의 Dockerfile을 네트워크가 열린 상태로 빌드하므로, 신뢰할 수 있는 프로젝트에만 돌리라고 README가 명시하고 있습니다.

증명 쪽이 궁금하면 공개된 재료들을 직접 열어 볼 수 있습니다. rocq-linux-process-semantics(MIT)에는 RISC-V 명령 디코딩·의미론(theories/Riscv/)과 커널 소스 구조를 따라 배치한 시스템 콜별 명세(theories/LinuxProcessSem/Sys/), 그리고 작은 바이너리에 대한 예제 증명이 들어 있습니다. Rocq 9.2 이상과 opam 2로 빌드되고, 전체 빌드에 CPU 45분 정도 걸립니다. 완료된 증명의 일부는 oss-verify-proofs에 공개돼 있습니다(미패치 버그가 드러나는 증명은 보류).

9. 흔한 실수 · 팁

  • "증명됐으니 끝"이라고 믿기. 증명은 스펙과 모델의 범위 안에서만 유효합니다. 6장의 TCB 표를 체크리스트로 쓰세요. 특히 "스펙이 내 의도를 담고 있는가"는 기계가 검사해 주지 않는, 끝까지 사람 몫인 질문입니다.
  • LLM이 쓴 증명을 사람이 리뷰하려 들기. 방향이 반대입니다. 60만 줄짜리 증명은 읽는 게 아니라 검사기에 통과시키는 겁니다. 사람의 리뷰는 짧은 정리 문장(스펙)에 집중해야 합니다. 리뷰 대상을 "증명"에서 "명제"로 옮기는 것이 이 패러다임의 요점입니다.
  • 검증기가 없는 곳에서 같은 기대하기. 이 작업이 잘된 건 Rocq라는 완벽한 채점기가 있어서입니다. 일반 코드 생성에는 이런 채점기가 없으므로 "LLM이 알아서 맞게 했겠지"로 일반화하면 안 됩니다. 반대로, 여러분의 도메인에 기계적 검증기를 만들 수 있다면(타입 체커, 린터, 속성 기반 테스트, 시뮬레이터) LLM 산출물의 신뢰도를 같은 구조로 끌어올릴 수 있습니다.
  • fuzz target 없이 검증부터 바라기. 이 파이프라인의 입장권은 fuzz target입니다. 아직 없다면 형식 검증 이전에 퍼징부터 붙이세요. 잘 쓴 fuzz target은 오늘은 퍼징 자산, 내일은 공짜 스펙이 됩니다. assertion을 풍부하게 넣을수록(round-trip, 불변식) 증명되는 성질도 강해집니다.
  • 에이전트에게 패치 권한을 줄 때 목표를 그대로 두기. "통과하게 만들어라"는 목표에 수정 권한이 붙으면 반드시 꼼수 경로가 생깁니다. 패치 페널티·영향 범위 증명·감사 로그라는 3중 장치를 그대로 벤치마킹할 만합니다.

10. 마무리 (TL;DR)

  • Anthropic Frontier Red Team × Theorem이 Claude로 오픈소스 라이브러리 123개(fuzz 진입점 239개)의 RISC-V 바이너리에 대해 약 1억 8천만 줄의 Rocq 증명을 몇 주 만에 생성, "64MB 이하 어떤 입력에도 crash 없음"을 기계 검증했습니다. 이번 주 HN 457pt 토론의 주인공입니다.
  • 환각하는 LLM을 믿을 수 있는 이유는 생성과 검사의 비대칭: 증명 생성은 어렵지만 검사는 기계적이라, 신뢰는 전부 작은 Rocq 검사기에 몰리고 LLM·증명·컴파일러는 TCB에서 빠집니다.
  • 형식 검증의 두 비용 중 증명 노동은 LLM이, 스펙 작성은 기존 fuzz target의 재활용이 해결했습니다. 증명이 안 되는 지점이 곧 버그 후보라서, 퍼저가 수년간 놓친 버그 수백 개(20MB 입력 underflow, libexpat CVE 재발견 등)가 함께 나왔습니다.
  • 단, "증명됐다 ≠ 버그 없다": 보장은 스펙·모델(musl 정적 RISC-V 단일 스레드)의 범위 안에서만 유효하고, 스펙이 현실과 맞는지는 여전히 사람이 확인해야 합니다.
  • 비용은 증명당 수억 토큰 수준이지만 모델 세대마다 급감 중이고(Opus 5.5가 토큰 40% 절감), 증명 공유 작업 공간(−17%)과 재사용으로 더 내려갑니다. reward hacking은 패치 페널티 + 영향 범위 증명 + 감사로 눌렀습니다.
  • 메인테이너라면 oss-verify에 PR 하나로 내 프로젝트를 검증 큐에 올릴 수 있습니다. 입장권은 fuzz target — 오늘 퍼징 자산이 내일 공짜 스펙이 됩니다.
