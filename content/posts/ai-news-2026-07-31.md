# 🔥 오늘의 핵심

새 프런티어 모델 소식은 조용하다. 대신 신호는 **MCP 도구 견고성(robustness)** 한 축으로 모인다. (1) 도구 인터페이스가 진화하면 GPT-5.4·Claude-Sonnet-4-6 같은 프런티어도 성능이 **-13~14%** 무너진다(MCPEvol-Bench). (2) 실패는 대개 crash가 아니라 **"틀린 툴 출력을 확신에 차서 그대로 쓰는" 침묵형**이다(AgentCheck). 오늘 할 일: **툴 응답을 신뢰 대상이 아니라 테스트 대상으로 승격**하고, fault 종류마다 완화책이 다르니 **배포 전에 fault별 회귀 테스트**로 확인하라.

# 🤖 모델 & 릴리즈 레이더

- **큰 신규 프런티어 모델 소식은 오늘 조용.** 대신 오늘의 모델-관련 신호는 벤치마크에서 나왔다.
- **진화하는 도구 앞에서 프런티어도 취약.** MCPEvol-Bench 측정에서 도구가 바뀐 MCP 서버 위 성능이 **GPT-5.4 -13.7%, Claude-Sonnet-4-6 -14.4%** 하락했고, 계획·추론 오류가 함께 급증했다. → 에이전트 빌더에게: "모델을 최신으로 바꿨으니 됐다"가 아니라, **연결한 도구의 스키마·동작 변경 자체가 성능 회귀의 원인**이 된다. 출처: [arXiv 2607.14642](https://arxiv.org/abs/2607.14642)

# 📚 주목 논문

## 1) MCPEvol-Bench — "도구가 바뀌면 에이전트는 따라가지 못한다"

- **저자/소속**: Huanxi Liu 외 8인 (Dawei Feng·Bo Ding·Huaimin Wang 등 포함 — 저자 구성상 NUDT 계열로 추정)
- **arXiv**: [2607.14642](https://arxiv.org/abs/2607.14642) · category `cs.AI` · 2026-07-16
- **핵심 기여**: 기존 MCP 벤치는 "도구가 고정"이라 가정한다. 이 논문은 **도구가 계속 진화한다**는 현실을 벤치마크로 만들었다.
- **방법(2–3줄)**: 실제 MCP 서버 **123개**에 **11종 변형 연산자**(파라미터 추가/삭제, 이름 변경, 반환 스키마 변경 등)를 적용해 여러 버전을 생성. 동일 과제를 원본 vs 진화 버전에서 풀게 하고 **12개 최신 LLM**을 비교.
- **핵심 결과(검증)**: 진화 버전에서 **GPT-5.4 -13.7%, Claude-Sonnet-4-6 -14.4%**. 저하의 상당 부분이 계획·추론 오류.
- 🛠 **agent-builder 시사점**: MCP 서버 버전을 **평가 축**으로 넣어라. 벤더가 툴 스키마를 바꾸면 조용히 회귀한다 → 툴 정의 스냅샷을 고정하고 변경 시 자동 재평가.
- ⚠️ **한계**: 변형이 합성(mutation operator)이라 실제 벤더 변경 분포와 완전히 같지는 않다.

## 2) AgentCheck — "툴 실패를 재현하고, 고치고, 배포 전에 확인하라"

- **저자**: Aritra Mazumder, Nusrat jahan Lia 외
- **arXiv**: [2607.11098](https://arxiv.org/abs/2607.11098) · category `cs.SE` · 2026-07-13
- **핵심 기여**: MCP 서버를 **개입 표면(intervention surface)** 으로 바꾸는 오픈소스 워크벤치. "툴이 timeout, stale 값, 설명 오염"될 때를 **재현→개입→확인** 루프로 다룬다.
- **방법(2–3줄)**: 에이전트를 실제 툴에 붙여 모든 응답을 기록 → **fault 12종**을 주입해 재실행. 일치하는 툴콜은 캐시에서 replay, 이후는 라이브로 전환. 채점은 규칙 기반 + LLM 심판(인간 라벨로 검증).
- **핵심 결과(검증)**: 5개 에이전트 중 최고 **105/120**, 최약체 **77/120** 통과. 실패는 대개 crash가 아니라 **틀린 출력을 확신에 차서 쓰는 침묵형**. 최약체에서 **retry 완화**는 timeout fault 성공률을 **30%→100%**로 올렸지만, **stale-data는 완화책과 무관하게 ~3–4/10에 머문다.**
- 🛠 **agent-builder 시사점**: "재시도만 넣으면 된다"는 틀렸다. **fault 종류마다 완화책이 다르다** — timeout엔 retry, stale엔 캐시 무효화/재조회가 필요.
- ⚠️ **한계**: LLM 심판 채점의 해석 라벨은 판정 편향 가능성.

![AgentCheck 재현-개입-확인 루프 다이어그램. 1) 재현: 실제 툴 응답 기록 후 fault 12종 주입, 2) 개입: retry 등 완화책 토글 후 동일 fault로 재실행, 3) 확인: 배포 전 실패 소멸 여부를 규칙+LLM 심판으로 채점. 하단 막대: 최약체 에이전트에서 timeout fault 30%→100%(retry로 회복), stale-data ~35%→~35%(retry로도 안 나음).](/images/ai-news-2026-07-31/agentcheck-loop.svg)
*완화책은 fault 종류마다 효과가 다르다 — 수치는 arXiv 2607.11098 초록 기준. (자체 제작 SVG)*

# 🛠 오픈소스 스포트라이트

- **modelcontextprotocol/inspector** — MCP 서버 시각 테스트 도구(공식). 웹 UI + CLI로 툴/리소스/프롬프트를 직접 호출·검사. 오늘 논문들의 "툴을 눈으로 확인" 니즈의 1차 도구. 활용: MCP 서버를 에이전트에 붙이기 전에 **툴 스키마·응답을 수동 검증**. [github.com/modelcontextprotocol/inspector](https://github.com/modelcontextprotocol/inspector)
- **lastmile-ai/mcp-eval** — MCP 서버용 경량 eval 프레임워크. 구조 검사·성능 게이트로 툴 품질을 **자동 어서션**. 활용: MCPEvol이 지적한 "도구 진화 회귀"를 CI에서 잡는 회귀 스위트로. [github.com/lastmile-ai/mcp-eval](https://github.com/lastmile-ai/mcp-eval)

두 도구의 역할 구분: **Inspector = 수동·탐색적 검사**, **mcp-eval = 자동·회귀 게이트**. 오늘의 교훈("툴을 테스트 대상으로")을 이 둘로 각각 손·발처럼 나눠 쓰면 된다.

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — [Eval / Workflow] `codex exec`로 에이전트 시나리오를 CI 게이트로

- 출처: [developers.openai.com/codex/noninteractive](https://developers.openai.com/codex/noninteractive)
- 💡 **핵심**: 헤드리스 `codex exec`는 TUI 없이 한 세션을 끝까지 돌리고 종료 코드를 남긴다 → 툴 실패 시나리오를 **CI에서 자동 검증**할 수 있다.
- 📝 **how-to**:

```bash
# JSONL 이벤트 스트림으로 실행하고, 세션 파일은 남기지 않음
codex exec --json --ephemeral "MCP 툴 X가 timeout일 때 재시도 후 복구되는지 확인" \
  | jq -c 'select(.type=="agent_message")' > run.log
# 판정 로직: 실패 문자열이 있으면 파이프라인 실패
grep -q "recovered" run.log || exit 1
```

- 🎯 **언제**: MCP 서버/툴 업데이트 PR마다 회귀를 자동으로 돌리고 싶을 때.
- ⚠️ **주의**: 기본은 샌드박스. 파일 쓰기가 필요하면 `--full-auto`를 **의도적으로만** 열고, CI엔 `--ephemeral` 권장.
- ⭐ **추천**: MCPEvol이 경고한 "도구 진화 회귀"를 막는 가장 싼 방어선.

## 🟦 Claude Code — [MCP] `claude mcp add`로 붙이고 스코프를 분리하라

- 출처: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp)
- 💡 **핵심**: MCP 서버는 **local / project / user** 스코프로 붙일 수 있다. 팀 공유 툴은 `project`(체크인되는 `.mcp.json`), 개인 자격증명 툴은 `user`로 분리.
- 📝 **how-to**:

```bash
# 프로젝트 공유 스코프로 stdio 서버 등록 (팀이 함께 씀)
claude mcp add --scope project my-tools -- npx -y @acme/mcp-server

# 등록 상태 확인
claude mcp list
```

- 🎯 **언제**: 여러 명이 같은 MCP 툴셋으로 에이전트를 돌릴 때, 툴 정의를 **버전 관리 대상**으로 만들고 싶을 때.
- ⚠️ **주의**: `project` 스코프 `.mcp.json`엔 **토큰·비밀을 넣지 말 것**. 자격증명은 `user` 스코프나 환경변수 참조로.
- ⭐ **추천**: 툴 정의를 리포에 고정하면, MCPEvol이 말한 "스키마 변경 회귀"를 diff로 바로 본다.

## 🟪 공통 — [Eval] 툴 출력을 신뢰하지 말고 fault 12종을 회귀로 주입하라

- 출처: [AgentCheck (arXiv 2607.11098)](https://arxiv.org/abs/2607.11098)
- 💡 **핵심**: 실패의 대부분은 crash가 아니라 **"틀린 값을 확신하며 쓰기"**. 그래서 테스트는 "성공했나?"가 아니라 **"조용히 틀렸나?"**를 봐야 한다.
- 📝 **how-to (체크리스트)**:
  - [ ] timeout / 지연 → **retry** 완화가 실제로 회복시키는지
  - [ ] stale(오래된 값) → retry로는 안 낫는다. **캐시 무효화·재조회** 경로 확인
  - [ ] 스키마 드리프트(반환 필드 변경) → 파싱 실패가 침묵으로 넘어가지 않는지
  - [ ] 툴 설명 오염 → 지시가 아니라 **데이터**로 취급하는지
- 🎯 **언제**: 프로덕션 에이전트를 배포하기 전, 항상.
- ⚠️ **주의**: fault별로 완화책 효과가 다르다(위 차트). "retry 한 방"으로 뭉뚱그리지 말 것.
- ⭐ **추천**: 이 4가지를 최소 회귀 스위트로 고정해두면 대부분의 침묵형 실패를 잡는다.
