1. 도입 — 에이전트가 공격자이자 피해자가 된 주간

이번 주 보안 뉴스는 온통 에이전트였습니다. 10월 19일 TechCrunch 보도에 따르면 오픈소스 코딩 에이전트 OpenCode의 온라인 콘솔이 해킹당해, 공격자가 피해자의 AI 계정으로 요금을 쌓아 올렸습니다. 다음 날에는 자율 에이전트를 1,200개 넘는 사이트에 풀어 침투를 시도한 사건이, 이어서 랜섬웨어 조직이 침투 실행에 AI 에이전트 워크플로를 썼다는 분석까지 나왔습니다. 에이전트가 공격 도구가 된 사건과, 에이전트 인프라 자체가 뚫린 사건이 같은 주에 겹친 겁니다.

그리고 10월 21일, NVIDIA는 GTC Berlin에서 이 흐름에 정면으로 답하는 발표를 했습니다. 자율 에이전트 플릿(fleet, 여러 에이전트를 한꺼번에 운영하는 단위)을 위한 오픈소스 런타임 OpenShell을 전면에 내세우고, 그 위에 하드웨어까지 묶은 레퍼런스 아키텍처를 공개한 겁니다. 런타임은 Apache 2.0 라이선스로 GitHub에 있고, 발표 직후 Hacker News에서도 288포인트로 상위권에 올랐습니다.

OpenShell이 풀려는 문제는 한 문장으로 요약됩니다. 에이전트는 파일을 읽고, 패키지를 깔고, API를 부르고, credential을 써야 쓸모가 있는데 — 바로 그 권한들이 그대로 공격면이 된다는 것. 이 글에서는 OpenShell이 이 딜레마를 어떤 구조로 푸는지, 저장소와 공식 문서를 바탕으로 아키텍처부터 정책 문법, credential 주입, formal verification까지 차례로 뜯어봅니다.

2. 배경 — "컨테이너에 넣었으니 안전하다"는 착각

에이전트 격리라고 하면 대부분 Docker 컨테이너를 떠올립니다. 그런데 기본 설정의 컨테이너는 에이전트 보안 관점에서 구멍이 둘 있습니다.

  • 네트워크가 열려 있습니다. 컨테이너 안의 프로세스는 기본적으로 아무 곳에나 접속할 수 있습니다. 프롬프트 인젝션(prompt injection, 외부 데이터에 심긴 지시로 에이전트를 조종하는 공격)에 당한 에이전트가 수집한 데이터를 공격자 서버로 보내는 걸 막을 수단이 없습니다. 지난 글에서 다뤘듯, 격리의 성패는 들어오는 쪽이 아니라 나가는 쪽(egress)에서 갈립니다.
  • credential이 환경 변수에 그대로 있습니다. ANTHROPIC_API_KEY를 env로 넘기는 순간, 에이전트가 실행하는 모든 코드 — 에이전트가 설치한 npm 패키지까지 — 가 그 키를 읽을 수 있습니다. 키를 읽을 수 있으면 유출할 수 있습니다.

보안의 교과서적 처방은 최소 권한(least privilege)과 deny-by-default(명시적으로 허용하지 않은 것은 전부 거부)입니다. 문제는 에이전트가 쓰는 도구와 목적지가 작업마다 달라서, 이 원칙을 손으로 유지하기가 고통스럽다는 점입니다. 허용 목록을 빡빡하게 조이면 에이전트가 일을 못 하고, 느슨하게 풀면 격리가 무의미해집니다. OpenShell은 이 운영 고통까지 설계 범위에 넣은 시스템입니다.

3. 아키텍처 — 에이전트는 경계 안에, 결정은 경계 밖에

OpenShell의 구조는 세 가지 구성 요소로 이해하면 됩니다. 공식 아키텍처 문서의 용어를 그대로 쓰겠습니다.

구성 요소위치역할
gateway컨트롤 플레인샌드박스 생명주기 관리, 정책·credential 전달, 사용자 인증. 플릿 전체의 두뇌.
supervisor경계 밖(신뢰 영역)모든 요청을 정책과 대조하고, credential을 공급하고, DNS를 해석하고, 승인된 연결을 대신 열어 줌.
sandbox경계 안(비신뢰 영역)에이전트 프로세스를 자식으로 소유. 어떤 프로그램이 무슨 요청을 했는지 관찰해 supervisor에 보고만 하고, 결정은 하지 않음.

핵심 설계 원칙이 여기 있습니다. 에이전트와 같은 경계 안에 있는 코드는 언젠가 에이전트에게 장악당할 수 있다고 가정합니다. 그래서 경계 안쪽(sandbox)은 훔칠 가치가 있는 것을 아무것도 들고 있지 않습니다 — 서명 키도, gateway 토큰도, provider credential도 없습니다. 정책 판단은 전부 경계 밖 supervisor가 합니다.

그럼 에이전트의 네트워크 요청은 어떻게 밖으로 나갈까요? 못 나갑니다. 워크로드의 바깥 울타리(outer fence)가 supervisor로 가는 보호된 채널 하나만 남기고 모든 egress를 막기 때문입니다. Docker/Podman에서는 워크로드 컨테이너의 네트워킹 자체를 꺼 버리고, Kubernetes에서는 NetworkPolicy로 supervisor 서비스만 허용하며, VM에서는 게스트에 네트워크 장치를 아예 안 줍니다. 요청 하나의 여정은 이렇습니다.

디테일 몇 가지가 설계의 완성도를 보여 줍니다. sandbox와 supervisor는 상호 인증된 HTTP/2 연결 하나로 통신하는데(Docker는 Unix 소켓, K8s는 TCP, MicroVM은 vsock), TCP 연결마다 독립 스트림을 써서 느린 다운로드가 DNS나 프로세스 제어를 막지 못하게 합니다. 그리고 fail-closed: supervisor 연결이 끊기면 sandbox는 에이전트를 얼려(freeze) 버리고, 같은 supervisor 프로세스만 재접속해 재개할 수 있습니다. 통제가 확인되기 전에는 에이전트가 아예 시작되지 않습니다.

4. 정책 — YAML 한 장으로 deny-by-default

샌드박스가 무엇을 할 수 있는지는 YAML 정책 한 장이 정합니다. 최상위 섹션은 다섯 개로, filesystem_policy(Landlock LSM으로 커널에서 강제하는 파일 접근), landlock, process(실행 UID/GID), network_policies, network_middlewares입니다. 파일·프로세스 설정은 시작 시 고정되고, 네트워크 룰은 샌드박스가 도는 중에도 핫 리로드됩니다.

정책의 대부분을 차지하는 건 네트워크 룰입니다. 룰 하나는 "어떤 바이너리가(binaries) 어떤 목적지에(endpoints)"의 조합입니다.

{{< highlight yaml >}} version: 1 network_policies: github_api: endpoints: - host: api.github.com port: 443 protocol: rest # 요청 단위 검사 켜기 rules: - methods: [GET] # 읽기만 허용 — POST/DELETE는 차단 paths: ["/repos/**"] enforcement: enforce # 기본값은 audit(기록만) — 주의! binaries: - path: /usr/local/bin/opencode {{< /highlight >}}

눈여겨볼 장치가 셋 있습니다.

  • 바이너리 신원 고정. OpenShell은 프로세스를 커널이 보고하는 실행 파일의 실제 경로로 식별하고, 그 파일의 해시를 첫 연결 때 기록해 둡니다. 이후 파일이 바뀌면 연결을 거부합니다. 에이전트가 curl을 악성 바이너리로 바꿔치기해도 소용없습니다.
  • 요청 단위 검사. 목적지만이 아니라 요청 내용까지 봅니다. protocol 필드에 따라 REST(메서드·경로·쿼리), WebSocket, GraphQL, JSON-RPC, 심지어 MCP(메서드와 tool 이름)까지 검사합니다. "이 API는 읽기만"이 정책 한 줄로 됩니다.
  • audit 모드. enforcement: audit로 두면 차단 대신 위반을 기록만 합니다. 새 룰이 뭘 막을지 미리 보고 enforce로 올리는, 운영자를 위한 안전장치입니다.

정책이 없으면 어떻게 될까요? 기본 정책이 적용되는데, 네트워크 룰이 0개입니다. 즉 모든 outbound가 거부됩니다. deny-by-default가 문서의 구호가 아니라 기본값 그 자체입니다.

5. credential — 에이전트는 진짜 열쇠를 평생 못 본다

개인적으로 OpenShell에서 가장 배울 게 많다고 느낀 부분입니다. API 키 같은 credential은 provider라는 일급 객체로 gateway에 등록합니다.

{{< highlight bash >}} # 셸 환경의 ANTHROPIC_API_KEY를 읽어 credential 저장소에 보관 openshell provider create --name my-claude --type claude-code --from-existing {{< /highlight >}}

이 provider를 샌드박스에 붙이면, 에이전트의 환경 변수에는 진짜 키 대신 불투명한 placeholder 토큰이 들어갑니다. 에이전트는 평소처럼 $ANTHROPIC_API_KEY를 읽어 Authorization 헤더에 넣지만, 그 값은 openshell:resolve:env:... 같은 모양의 가짜입니다. 요청이 supervisor의 프록시를 지날 때, 정책이 허용한 endpoint로 가는 요청에 한해서만 placeholder가 진짜 값으로 치환됩니다.

치환에는 독립적인 관문이 둘입니다. 네트워크 정책이 그 바이너리와 목적지를 허용해야 하고(관문 1), credential binding이 그 호스트·포트·경로를 포함해야 합니다(관문 2). 둘 다 통과해야 진짜 값이 들어갑니다. 헤더뿐 아니라 쿼리 파라미터, URL 경로(/bot<토큰>/sendMessage 같은 패턴), 옵트인 시 요청 본문과 WebSocket 메시지, AWS SigV4 서명까지 지원합니다.

왜 이게 중요한가: 프롬프트 인젝션 방어의 상식은 "당한다고 가정하고 피해 범위를 설계하라"입니다. placeholder 구조에서는 에이전트가 완전히 장악당해 환경 변수를 통째로 외부에 불러 줘도, 공격자 손에 들어가는 건 OpenShell 프록시 밖에서는 아무 의미 없는 문자열입니다. 유출 '시도'는 막지 못해도 유출 '가치'를 0으로 만드는 접근입니다.

6. 정책은 누가 고치나 — advisor와 SMT 기반 prover

deny-by-default의 현실적 문제는 운영입니다. 에이전트가 새 작업을 받을 때마다 새 목적지가 필요한데, 매번 사람이 YAML을 고쳐야 한다면 아무도 안 씁니다. OpenShell의 답은 "에이전트가 제안하고, 기계가 심사하고, 사람이 승인한다"는 3단 루프입니다.

  • policy advisor — 요청이 차단되면 에이전트는 샌드박스 안에서만 보이는 http://policy.local API로 "이 바이너리가 이 호스트·포트·경로에 접근하게 해 달라"는 좁은 룰을 제안합니다. 차단 응답 자체에 제안 방법이 안내되고, /etc/openshell/skills/에 에이전트용 가이드(SKILL.md)까지 심어 줍니다. 제안은 네트워크 룰 추가만 가능하고, 룰 삭제나 파일 정책 변경은 못 합니다.
  • policy prover — 제안이 들어오면 SMT 솔버 기반 검증 엔진이 "이 룰이 추가하는 위험한 접근"을 형식적으로 따집니다. credential이 새 호스트로 나가게 되는지, 새 HTTP 메서드가 열리는지, 클라우드 메타데이터 주소(IMDS)에 닿는지 같은 것들이고, 하나라도 걸리면 자동 승인이 막히고 사람 리뷰 대기열로 갑니다.

prover는 독립 CLI로도 제공됩니다. 경계 정책(boundary, 이 환경에서 허용 가능한 최대 접근)을 정해 두고, 후보 정책이 그 안에 머무는지 검사합니다.

{{< highlight bash >}} openshell-prover check candidate.yaml --boundary boundary.yaml # result: exceeds_boundary # counterexample: filesystem write /tmp # 경계를 넘는 접근의 반례를 제시 {{< /highlight >}}

흥미로운 건 공식 문서가 이 CLI의 1차 사용자를 사람보다 에이전트로 상정한다는 점입니다. 부모 에이전트가 서브에이전트용 정책을 쓸 때, 자기 최대 권한 안에 들어오는지 스스로 증명하고 넘기라는 겁니다. "LLM이 쓴 것은 LLM 아닌 것으로 검증한다"는 검증기 엔지니어링의 원칙이 권한 관리에 그대로 적용된 사례입니다.

7. 실전 — 10분 만에 OpenCode를 가둬서 돌려보기

Linux, Apple Silicon macOS, 또는 WSL 2(실험적)에 Docker나 Podman이 있으면 됩니다. 공식 Run Your First Agent 흐름을 따라가 보겠습니다.

{{< highlight bash >}} # 1) CLI + 로컬 gateway 설치 curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh # 2) provider 프로필 가져오기 — opencode 바이너리가 openrouter.ai에만 # 접근하도록 endpoint·binary가 미리 정의돼 있음 openshell profile import \ --url https://raw.githubusercontent.com/NVIDIA/OpenShell/main/providers/openrouter.yaml # 3) OPENROUTER_API_KEY를 읽어 credential 저장소에 보관 openshell provider create --name openrouter --type openrouter --from-existing # 4) 샌드박스 생성: 이미지 + provider + 에이전트 명령 openshell sandbox create \ --name my-agent \ --from ghcr.io/anomalyco/opencode:latest \ --provider openrouter \ -- opencode -m openrouter/nvidia/nemotron-3.5-lightning:free {{< /highlight >}}

이제 에이전트가 일하다가 PyPI나 GitHub처럼 정책에 없는 곳이 필요해지면 차단과 함께 제안이 쌓입니다. 운영자는 이렇게 처리합니다.

{{< highlight bash >}} openshell rule get my-agent --status pending # 대기 중인 제안 확인 openshell rule approve my-agent --chunk-id # 승인 — 재시작 없이 반영 openshell rule reject my-agent --chunk-id \ --reason "쓰기 권한은 불필요 — GET만으로 다시 제안할 것" {{< /highlight >}}

거부 사유는 에이전트에게 그대로 전달되고, 에이전트는 더 좁은 제안을 다시 올립니다. 승인 루프 자체가 에이전트와의 대화인 셈입니다. 참고로 skills를 쓰는 코딩 에이전트라면 npx skills add NVIDIA/OpenShell로 OpenShell CLI 사용법·정책 작성법을 에이전트에게 가르치는 공식 스킬도 설치할 수 있습니다.

8. 한계와 논쟁 — 플릿의 거버넌스는 누가?

물론 OpenShell이 에이전트 보안을 끝내는 건 아닙니다. 공개 직후 나온 비판적 분석들이 공백을 잘 짚습니다.

  • 샌드박스 '하나'의 보안이지, 플릿의 거버넌스가 아닙니다. Tigera의 분석은 에이전트 신원(identity), 에이전트 간(agent-to-agent) 통신 거버넌스, 샌드박스 간 통신이 현재 범위 밖이라고 지적합니다. 에이전트 100개가 서로를 부르기 시작하면 OpenShell 바깥의 문제가 열립니다. 에이전트 신원과 권한 위임에서 다룬 과제가 그대로 남아 있는 셈입니다.
  • prover의 보증은 모델이 커버하는 범위까지입니다. 문서 스스로 명시합니다 — SMT 모델이 표현하는 정책 기능에 대해서만 보증하며, GraphQL이나 MCP 룰처럼 아직 모델 밖인 기능이 섞이면 "검사 불가"를 반환합니다(무시하고 통과시키지 않는 점은 올바른 설계입니다).
  • 아직 0.1.x입니다. 안정 릴리스 주기가 막 시작된 초기 프로젝트고, Kubernetes에서는 CNI가 NetworkPolicy를 실제로 강제해야 바깥 울타리가 성립하는 등 배포 전제 조건도 있습니다. Futurum의 논평처럼 "열린 표준인가, NVIDIA 생태계로의 초대장인가"라는 시선도 있습니다 — 런타임은 Apache 2.0이지만, 같은 주 발표된 레퍼런스 아키텍처는 NVIDIA 하드웨어와 한 묶음이기 때문입니다.

그래도 방향 자체에 대한 이견은 적습니다. "에이전트를 믿지 말고 경계를 믿어라, 권한은 경계 밖에서 요청 단위로 공급하라"는 패턴은 OpenShell이 없어도 베껴 갈 가치가 있습니다.

9. 흔한 실수 · 팁

  • pip용 룰에 /usr/bin/pip를 쓰기. 실제로 PyPI에 접속하는 프로세스는 Python 인터프리터입니다. 게다가 /usr/bin/python3는 보통 심볼릭 링크라서, 커널이 보고하는 실경로(readlink -f, 예: /usr/bin/python3.12)를 적어야 합니다. 차단 로그에 OpenShell이 식별한 경로가 찍히니 그걸 그대로 쓰세요.
  • 요청 검사 룰을 걸고 "차단되겠지" 하고 방심하기. 인스펙트 endpoint의 enforcement 기본값은 audit, 즉 기록만 하고 통과시킵니다. 의도한 위반만 로그에 남는 걸 확인한 뒤 반드시 enforce로 올려야 실제로 막힙니다.
  • placeholder가 어디서나 치환된다고 믿기. credential 치환은 프록시가 요청을 HTTP로 다룰 수 있을 때만 됩니다. tls: skip인 endpoint나 비HTTP 터널, 쿠키, WebSocket 바이너리 프레임에서는 치환이 안 됩니다. DB 접속 같은 네이티브 TCP에는 다른 credential 전략이 필요합니다.
  • 효과 정책을 안 보고 "네트워크 다 막았는데?" 하기. provider를 붙이면 그 profile이 네트워크 룰을 효과 정책(effective policy)에 보태 줍니다. 내 정책(base)에 룰이 없어도 provider 덕에 열린 길이 있을 수 있으니, 실제 허용 범위는 openshell policy get <sandbox> --full로 확인하세요.
  • 자동 승인을 켜 두고 승인 루프를 잊기. 자동 승인은 prover가 플래그를 못 찾은 제안만 통과시키지만, prover의 모델 밖 위험까지 보증하진 않습니다. 플릿 운영이라면 자동 승인된 룰 목록을 주기적으로 리뷰 대상에 올리는 게 안전합니다. 승인 피로 설계에서 다룬 원칙이 여기에도 적용됩니다.

10. 마무리 (TL;DR)

  • 에이전트발 보안 사건이 쏟아진 주간(OpenCode 콘솔 해킹, 1,200개 사이트 자율 에이전트 침투, 랜섬웨어의 에이전트 활용)에 NVIDIA가 GTC Berlin에서 에이전트 플릿용 오픈소스 런타임 OpenShell(Apache 2.0, v0.1.x)을 전면에 내세웠고, HN에서도 화제가 됐습니다.
  • 구조의 핵심은 "에이전트는 경계 안에, 결정은 경계 밖에": gateway(컨트롤 플레인) / supervisor(경계 밖, 정책 판단·credential 공급) / sandbox(경계 안, 관찰·보고만). 워크로드의 유일한 egress는 supervisor 채널이고, 연결이 끊기면 에이전트를 얼리는 fail-closed입니다.
  • 정책은 YAML 한 장: Landlock으로 파일을, seccomp 가로채기로 네트워크를 커널 수준에서 강제하고, 룰은 "바이너리(실경로+해시) × endpoint" 조합에 REST/GraphQL/MCP 요청 단위 검사까지 겁니다. 기본 정책은 네트워크 전면 거부.
  • credential placeholder가 백미: 에이전트 환경에는 가짜 토큰만 있고, 승인된 endpoint로 나가는 요청에서만 프록시가 진짜 값으로 치환합니다. 에이전트가 장악당해도 훔칠 키가 없습니다.
  • 운영 루프는 advisor(에이전트가 좁은 룰 제안) → prover(SMT 기반 리스크 체크) → 사람/자동 승인 → 핫 리로드. 정책 변경을 formal verification이 먼저 심사한다는 점이 차별점입니다.
  • 한계도 분명합니다: 에이전트 신원·에이전트 간 거버넌스는 범위 밖, prover 보증은 모델 커버리지까지, 아직 0.1.x. 그래도 "권한은 경계 밖에서 요청 단위로"라는 패턴은 어떤 에이전트 스택에든 가져갈 만합니다.
