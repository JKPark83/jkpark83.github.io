1. 도입 — 이번 주 화제가 된 차트 세 장

지난주 AI 엔지니어링 쪽 타임라인과 테크 미디어에 같은 차트가 반복해서 등장했습니다. a16z가 뉴스레터 Charts of the Week(8월 21일자, Moses Sternstein 작성)에서 공개한 OpenRouter 사용량 분석입니다. 요지는 세 개의 숫자로 요약됩니다.

  • 5배 — OpenRouter를 지나는 트래픽에서, 에이전트가 사람(사람이 직접 모델에 질문하는 사용)보다 토큰을 약 5배 소비합니다.
  • 14배 — 에이전트 사용량이 2026년 2월 이후 약 14배 늘었습니다.
  • 85%+ — 에이전트가 태우는 토큰의 85% 이상이 캐시된 프롬프트(cached prompt), 즉 이미 봤던 컨텍스트를 다시 읽는 데 쓰입니다.

eWeek, PPC Land, Computerworld 같은 매체가 일제히 받아썼고, 헤드라인은 대부분 "에이전트가 토큰을 5배 태운다"에 꽂혔습니다. 그런데 실무자 커뮤니티에서 더 회자된 건 세 번째 숫자였습니다. 한 분석이 지적했듯, 85%가 캐시 히트라면 — 캐시 히트는 단가가 정가의 10분의 1 수준이라 — "토큰 5배"의 청구서는 5배가 아니라 대략 1.18배로 계산됩니다. 토큰 수와 비용이 완전히 다른 얘기가 된 겁니다.

이 간극이 오늘의 주제입니다. 에이전트를 운영하는 순간, "토큰이 얼마나 드나"라는 질문은 요금표의 구조 — 입력·출력·캐시라는 세 가지 미터기 — 를 모르면 답할 수 없는 질문이 됩니다. 단가는 계속 내려가는데 에이전트 비용은 오히려 늘어난다는 Gartner의 "추론 역설(inference paradox)" 전망까지 겹치면서, 토큰 이코노믹스를 읽는 능력 자체가 AI 엔지니어링 스킬이 되고 있습니다.

이 글에서 얻어 갈 것. ① 요금표의 세 미터기(입력·출력·캐시)와 캐시 단가의 구조, ② 에이전트 루프가 토큰을 O(N²)로 태우는 이유와 "85% 캐시"가 필연인 이유, ③ 5배 → 1.18배 산수를 직접 재현하는 법과 그 계산의 함정, ④ 태스크당 비용을 계측하는 코드와 비용을 움직이는 네 가지 레버.

2. 배경 — 요금표에는 미터기가 세 개 있다

LLM API 요금은 "토큰당 얼마"라는 단일 단가처럼 보이지만, 실제로는 성격이 다른 미터기 세 개가 동시에 돌아갑니다.

미터기무엇을 재나단가 (입력 정가 = 1 기준)
입력(input)모델이 처음 읽는 토큰. 프롬프트, 히스토리, 도구 출력.1
출력(output)모델이 생성하는 토큰. 답변, 도구 호출 인자, 그리고 reasoning 모델의 사고 토큰도 출력으로 과금됩니다.보통 4~5 (입력보다 훨씬 비쌈)
캐시(cache)직전 요청과 앞부분(프리픽스)이 같아서 KV 캐시를 재사용한 토큰.읽기 ≈ 0.1 / 쓰기 ≈ 1.25 (Anthropic 기준)

캐시 미터기의 구조를 조금만 더 뜯어 보겠습니다. Anthropic의 프롬프트 캐싱은 명시적으로 캐시 지점을 표시하는 방식인데, 캐시에 쓸 때는 정가의 1.25배(1시간 TTL은 더 비쌈)를 내고, 캐시에서 읽을 때는 정가의 0.1배만 냅니다. OpenAI는 요청 프리픽스가 1,024토큰 이상 일치하면 자동으로 캐시가 적용되고, GPT-5 계열에서는 캐시된 입력이 정가 대비 90% 할인됩니다(과거 GPT-4o 시절엔 50%였습니다). OpenRouter 문서에 제공자별 정책이 정리되어 있습니다.

캐싱이 KV 캐시 수준에서 어떻게 동작하는지, 프리픽스를 어떻게 배치해야 캐시가 안 깨지는지는 프롬프트 캐싱 글에서 자세히 다뤘습니다. 오늘은 그 위에서 돈 계산을 합니다.

배경 지식 하나만 더. Gartner는 올해 3월 "1조 파라미터급 LLM의 추론 원가가 2030년까지 90% 이상 떨어진다"고 전망하면서, 동시에 에이전틱 워크플로의 추론 비용은 향후 2년간 5배 이상 늘어난다고 예측했습니다(AIwire 보도). 에이전트가 챗봇보다 태스크당 토큰을 5~30배 쓰기 때문에, 단가 하락보다 소비 증가가 빠르다는 겁니다. 단가가 내려가니 비용 걱정은 끝났다는 직관과 정반대의 전망이죠. 왜 이런 일이 생기는지, 루프의 산수부터 봅시다.

3. 에이전트는 왜 토큰을 5배 태우나 — 루프의 산수

에이전트 루프의 기본 구조를 떠올려 봅시다. 모델을 한 번 호출하고, 도구를 실행하고, 그 결과를 붙여서 다시 호출하고 — 태스크가 끝날 때까지 반복합니다. 여기서 핵심은, LLM API는 상태가 없다(stateless)는 점입니다. 모델은 지난 턴을 기억하지 않으므로, 매 턴 지금까지의 히스토리 전체를 처음부터 다시 보냅니다.

숫자를 넣어 보겠습니다. 시스템 프롬프트 + 도구 정의로 이루어진 고정 프리픽스가 8,000토큰, 매 턴 도구 출력과 모델 응답으로 히스토리가 평균 1,000토큰씩 자란다고 합시다. 턴 k의 입력 토큰은 대략 8,000 + (k−1) × 1,000입니다.

{{< highlight text >}} 턴 1 입력: 8,000 (프리픽스) 턴 2 입력: 9,000 (프리픽스 + 히스토리 1,000) 턴 3 입력: 10,000 ... 턴 20 입력: 27,000 20턴 누적 입력 = 20×8,000 + (0+1+...+19)×1,000 = 160,000 + 190,000 = 350,000 토큰 {{< /highlight >}}

스무 턴짜리 태스크 하나가 입력만 35만 토큰을 씁니다. 반면 이 태스크에서 "처음 보는" 토큰은 얼마일까요? 프리픽스 8,000 + 턴마다 새로 붙는 증분 19,000 = 약 27,000토큰뿐입니다. 나머지 32만여 토큰(약 92%)은 전부 이미 봤던 내용의 재전송입니다. 매 턴 증가분(등차수열)의 합이니, 총 토큰은 턴 수 N에 대해 O(N²)으로 자랍니다. 턴이 두 배 길어지면 토큰은 대략 네 배가 되는 구조입니다.

이제 a16z 차트의 세 번째 숫자가 필연이었다는 게 보입니다. 에이전트 토큰의 85% 이상이 캐시된 프롬프트라는 건, 에이전트가 낭비하고 있다는 뜻이 아니라 루프라는 구조의 산수적 귀결입니다. 사람의 채팅은 한 번 묻고 한 번 답하는 짧은 왕복이라 재독 비중이 낮고, 에이전트는 수십 턴을 돌며 같은 프리픽스를 수십 번 다시 읽습니다. 그래서 "에이전트 vs 사람"의 토큰 배율은 앞으로 루프가 길어질수록 더 벌어질 겁니다.

왜 재전송을 아예 없애지 않을까? 서버가 세션 상태를 들고 있으면 되지 않냐는 의문이 들 수 있습니다. 실제로 제공자들이 responses API류의 서버 측 대화 상태, KV 캐시 유지 같은 걸 제공하지만, 그 내부에서도 결국 어텐션 계산을 위한 KV 캐시를 누군가는 저장·재계산해야 하고 그 비용이 캐시 요금으로 청구됩니다. 재전송이 사라지는 게 아니라 재계산 비용이 "캐시 읽기 단가"라는 형태로 바뀌는 것에 가깝습니다.

4. 5배가 18%가 되는 계산 — 직접 해 보기

이제 이번 주 화제의 산수를 재현해 봅시다. 사람의 사용량을 1이라 두고, 다음 세 가지를 가정합니다.

  • 에이전트는 토큰을 5배 쓴다 (a16z/OpenRouter).
  • 그중 85%는 캐시 히트, 15%는 정가 토큰이다 (같은 출처).
  • 캐시 히트 단가는 정가의 0.1배다 (Anthropic 캐시 읽기, GPT-5 계열 캐시 입력 할인과 동일 수준).
{{< highlight text >}} 사람 비용 = 1 × 1 = 1.000 에이전트 비용 = 5 × (0.15×1 + 0.85×0.1) = 5 × (0.15 + 0.085) = 5 × 0.235 = 1.175 {{< /highlight >}}

토큰은 5배인데 비용은 약 1.18배, 즉 +18%. 헤드라인과 청구서 사이의 간극이 이 세 줄 산수에 다 들어 있습니다.

다만 이 계산은 봉투 뒷면 산수(back-of-the-envelope)라는 점을 분명히 해야 합니다. 실제 청구서와는 다음 지점에서 어긋날 수 있습니다.

  • 출력 토큰이 빠져 있습니다. 출력은 입력보다 4~5배 비싸고 캐시가 적용되지 않습니다. reasoning 모델이라면 보이지 않는 사고 토큰까지 출력 요금으로 나갑니다. 출력 비중이 큰 워크로드라면 +18%보다 훨씬 커집니다.
  • 캐시 쓰기 비용도 빠져 있습니다. Anthropic 방식은 캐시에 처음 쓸 때 1.25배를 내므로, 턴이 몇 번 안 도는 짧은 태스크는 캐시 손익분기점을 못 넘길 수 있습니다.
  • 85%는 "잘 돌아가는 평균"입니다. 프리픽스를 흔드는 실수 하나로(6장) 내 에이전트의 캐시 히트율은 0%가 될 수 있고, 그 순간 5배 토큰은 진짜 5배 비용이 됩니다.
그래서 결론은 "에이전트 비용은 괜찮다"가 아닙니다. 개별 태스크의 청구서가 +18%로 끝나더라도, 사용량 자체가 2월 이후 14배로 자라는 중이고 Gartner는 에이전틱 워크플로 비용이 2년간 5배 이상 늘어난다고 봅니다. 단가 하락(2030년까지 90%↓)보다 소비 증가가 빠르다는 게 추론 역설의 요지입니다. 개인 프로젝트의 청구서도, 회사의 인프라 계획도, "단가 × 토큰 구조"를 둘 다 봐야 맞게 예측됩니다.

5. 실전 — 태스크당 비용(cost per task) 계측하기

토큰 이코노믹스의 첫걸음은 거창한 게 아니라, 내 에이전트의 태스크당 비용을 숫자로 만드는 것입니다. 다행히 모든 주요 API가 응답마다 usage 필드로 미터기 눈금을 알려 줍니다. Anthropic API 기준으로, 루프에 몇 줄만 붙이면 됩니다.

{{< highlight python >}} # 1M 토큰당 단가(USD). 예시값 — 실제 값은 요금표에서 확인하세요. PRICE = { "input": 3.00, "output": 15.00, # 출력은 입력보다 5배 비쌈 "cache_write": 3.75, # 입력 × 1.25 "cache_read": 0.30, # 입력 × 0.10 } def turn_cost_usd(u) -> float: """한 턴의 usage에서 네 미터기를 모두 읽어 달러로 환산.""" return ( u.input_tokens * PRICE["input"] + u.output_tokens * PRICE["output"] + u.cache_creation_input_tokens * PRICE["cache_write"] + u.cache_read_input_tokens * PRICE["cache_read"] ) / 1_000_000 task = {"turns": 0, "usd": 0.0, "cache_read": 0, "uncached": 0} while not done: resp = client.messages.create(model=MODEL, messages=history, tools=tools) u = resp.usage task["turns"] += 1 task["usd"] += turn_cost_usd(u) task["cache_read"] += u.cache_read_input_tokens # input_tokens는 캐시를 못 탄 부분, cache_creation은 이번에 캐시에 쓴 부분 task["uncached"] += u.input_tokens + u.cache_creation_input_tokens # ... 도구 실행, history 갱신 ... hit_rate = task["cache_read"] / (task["cache_read"] + task["uncached"]) print(f"태스크 비용 ${task['usd']:.4f}, {task['turns']}턴, " f"캐시 히트율 {hit_rate:.0%}") {{< /highlight >}}

이 네 줄짜리 집계가 만들어 주는 지표가 두 개입니다. 태스크당 비용(cost per task)과 캐시 히트율. 전자는 "이 자동화가 사람 손보다 싼가"를 판단하는 단위이고 — 토큰당 비용은 이 판단에 아무 도움이 안 됩니다 — 후자는 4장의 +18% 산수가 내 시스템에서 실제로 성립하는지 알려 주는 건강 지표입니다. 히트율이 85% 밑으로 뚝 떨어져 있다면 어딘가에서 프리픽스가 흔들리고 있다는 신호입니다.

지표가 생기면 예산 가드를 걸 수 있습니다. 에이전트 비용 사고의 전형은 평균이 아니라 꼬리에서 납니다 — 같은 검색을 무한 반복하는 폭주 루프 하나가 하루 예산을 태우는 식이죠. 루프 조건에 두 줄이면 됩니다.

{{< highlight python >}} MAX_TURNS = 30 # 정상 태스크의 p95 턴 수보다 조금 크게 MAX_USD_PER_TASK = 0.50 while not done: if task["turns"] >= MAX_TURNS or task["usd"] >= MAX_USD_PER_TASK: # 그냥 죽이지 말고: 지금까지의 진행 상황을 요약해 사람에게 인계 raise BudgetExceeded(summary=summarize_progress(history)) ... {{< /highlight >}}

6. 비용을 움직이는 네 가지 레버

태스크당 비용은 결국 비용 = Σ(턴마다) 토큰 수 × 단가라는 곱셈입니다. 그래서 레버도 곱셈의 각 항에 하나씩 걸립니다: 단가를 낮추거나(캐시, 라우팅), 토큰 수를 줄이거나(컨텍스트 다이어트), 턴 수를 제한하거나(예산 가드).

레버어떻게함정
① 캐시 히트율 지키기고정 프리픽스(시스템 프롬프트·도구 정의)를 맨 앞에, 변하는 내용은 뒤에. 히스토리는 append-only로 유지. 자세한 설계는 캐싱 글 참고.프리픽스에 현재 시각을 넣거나, 턴 중간에 도구 정의를 바꾸거나, 히스토리 중간을 수정하면 그 지점 이후 캐시가 전부 무효. 컴팩션도 프리픽스를 갈아 끼우므로 캐시를 깹니다 — 컨텍스트를 줄이려는 조치가 단가를 10배로 되돌리는 트레이드오프가 있습니다.
② 컨텍스트 다이어트도구 출력을 통째로 붙이지 말고 필요한 부분만(적은 컨텍스트 글), 조사·검색 같은 소모성 작업은 서브에이전트로 격리해 본 루프의 히스토리 성장을 막기(N² 기울기 완화).과도한 요약·삭제는 정보 손실 → 모델이 같은 걸 다시 조회하느라 턴 수가 늘어 역효과. 무엇을 잃는지 모르는 압축은 비용 절감이 아니라 품질 저하입니다.
③ 모델 라우팅분류·추출·재작성 같은 서브스텝은 소형 모델로. 프런티어 모델과 소형 모델의 단가 차이는 보통 10배 이상이라, 서브스텝 몇 개만 옮겨도 체감이 큽니다(라우팅 글).능력 미달 모델로 라우팅하면 실패 → 재시도 → 오히려 비쌈. 라우팅 판단 자체도 평가로 검증해야 합니다. 모델을 바꾸면 캐시도 공유되지 않습니다.
④ 예산 가드태스크당 max_turns·비용 상한, 초과 시 진행 상황 요약과 함께 사람에게 인계(5장 코드).상한을 너무 낮게 잡으면 정상 태스크까지 잘려 실패율이 오릅니다. 정상 분포(p95)를 먼저 재고 상한을 정하세요.
우선순위 감각. 넷 중 가장 먼저 볼 것은 ①입니다. 이미 돌아가는 에이전트라면 코드 변경 거의 없이 단가를 최대 10분의 1로 만드는 레버인 데다, 잘못돼 있어도 기능은 멀쩡해서 계측하지 않으면 영원히 모르는 항목이기 때문입니다. 그다음이 ④(사고 방지), 그리고 ②·③(구조 개선) 순서가 실무에서 무난합니다.

7. 흔한 실수 · 팁

  • 토큰 수로 비용을 추정한다. 이 글의 요지 그대로입니다. 캐시 히트율과 입력/출력 비율에 따라 같은 토큰 수의 비용이 몇 배씩 달라집니다. 대시보드에 토큰 수만 있다면 절반만 보고 있는 겁니다.
  • 출력 토큰을 잊는다. 입력이 물량으로는 압도적이라 출력을 무시하기 쉽지만, 단가가 5배쯤 높고 reasoning 토큰도 출력으로 청구됩니다. 사고 예산을 넉넉히 준 reasoning 모델은 짧은 답변에도 수천 토큰의 출력 요금이 붙을 수 있습니다(사고 예산 글).
  • 캐시 쓰기 요금을 모르고 1시간 TTL을 남발한다. 쓰기 단가가 더 비싼 만큼, 다시 읽을 일이 별로 없는 짧은 태스크에선 캐싱이 손해일 수 있습니다. 히트율과 함께 손익을 계산하세요.
  • 평균만 보고 꼬리를 안 본다. 비용 사고는 p50이 아니라 p99에서 납니다. 태스크당 비용의 분포를 보고, 상위 몇 개 태스크의 트레이스를 열어 보는 습관이 폭주 루프를 가장 빨리 잡습니다.
  • "단가가 계속 내려가니 곧 해결된다"고 믿는다. Gartner 전망이 보여 주듯 단가 하락(90%↓/4년)보다 에이전트의 소비 증가(5배↑/2년)가 빠릅니다. 구조를 방치하면 청구서는 커집니다.
  • 팁: 비용 리그레션을 CI처럼 다루세요. 프롬프트나 도구 정의를 바꾸는 PR이 캐시 히트율을 떨어뜨리는 건 기능 테스트로는 안 잡힙니다. 대표 태스크 몇 개를 돌려 태스크당 비용과 히트율을 비교하는 스모크 체크를 배포 전에 끼워 넣으면, "기능은 그대로인데 비용만 4배"가 되는 조용한 회귀를 막을 수 있습니다.

8. 마무리 (TL;DR)

  • a16z의 OpenRouter 분석(8/21): 에이전트는 사람보다 토큰을 약 5배 소비하고, 사용량은 2월 이후 14배 성장, 토큰의 85% 이상이 캐시된 프롬프트입니다.
  • 85% 캐시는 낭비가 아니라 구조입니다. stateless API 위의 루프는 매 턴 히스토리를 재전송하므로 총 토큰이 O(N²)로 자라고, 재독 비중이 갈수록 커집니다.
  • 캐시 히트 단가는 정가의 ~0.1배. 그래서 5 × (0.15 + 0.85×0.1) ≈ 1.175 — 토큰 5배의 청구서는 약 +18%입니다. 단, 출력 토큰·캐시 쓰기·캐시 미스가 빠진 봉투 뒷면 산수임을 기억하세요.
  • 지표는 두 개면 시작할 수 있습니다: 태스크당 비용과 캐시 히트율. 응답의 usage 네 필드만 집계하면 됩니다.
  • 레버는 넷: 캐시 히트율 지키기 → 예산 가드 → 컨텍스트 다이어트 → 모델 라우팅. 컴팩션이 캐시를 깨는 트레이드오프처럼, 레버끼리 상충하는 지점을 아는 게 실력입니다.
  • 단가는 내려가지만(Gartner: 2030년까지 90%↓) 에이전트 소비가 더 빨리 늡니다(2년간 5배↑). 토큰 이코노믹스 리터러시는 이제 선택이 아니라 엔지니어링 기본기입니다.
