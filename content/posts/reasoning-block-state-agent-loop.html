1. 도입 — 같은 물건이 한 주에 두 번 화제가 됐다

리즈닝 모델(reasoning model, 답을 내기 전에 눈에 안 보이는 “생각”을 먼저 하는 모델)을 에이전트에 붙여 보면, API 응답에서 처음 보는 물건을 만납니다. 이런 겁니다.

{{< highlight json >}} { "content": [ { "type": "thinking", "thinking": "사용자가 파리 날씨를 묻고 있다. get_weather 함수가 있으니...", "signature": "BDaL4VrbR2Oj0hO4XpJxT28J5T...." }, { "type": "text", "text": "파리 날씨를 확인해 보겠습니다" }, { "type": "tool_use", "id": "toolu_01Cswd...", "name": "get_weather", "input": { "location": "Paris" } } ] } {{< /highlight >}}

여기서 signature가 문제의 그 덩어리입니다. 읽을 수도 없고, 길고, 로그를 지저분하게 만듭니다. 그래서 많은 사람이 두 가지 중 하나를 합니다. 아무 생각 없이 통과시키거나, 대화 기록을 예쁘게 만들려고 thinking 블록을 통째로 걸러 냅니다.

이번 주에 왜 화제였나. 이 덩어리가 8월 둘째 주에 서로 정반대 방향에서 두 번 조명을 받았습니다.

하나는 버리면 안 된다는 쪽입니다. OpenAI는 “How enabling two settings tripled our scores on the ARC-AGI-3 benchmark”에서, 공식 ARC-AGI-3 하네스가 매 수(手)마다 모델의 비공개 추론을 버리고 오래된 기록을 잘라 내고 있었다고 밝혔습니다. 모델을 새로 학습시키지도, 추론 예산을 늘리지도, 게임 전용 도구를 붙이지도 않고 추론을 버리지 않게 하는 것과 압축(compaction) 두 가지만 켰더니 GPT-5.6 Sol의 점수가 13.3%에서 38.3%로 올랐고, 출력 토큰은 오히려 약 6분의 1로 줄었습니다.

다른 하나는 아무 데나 두면 안 된다는 쪽입니다. 8월 10일 arXiv에 “Stealing Reasoning Traces from Proprietary LLM APIs”(arXiv:2608.09867)가 올라와 이튿날 널리 퍼졌습니다. 요지는 이 암호화 블록이 같은 공급자 생태계 안에서 세션·사용자·모델을 넘나들며 그대로 호환된다는 것입니다. 연구진은 공개된 에이전트 실행 기록에서 이 블록들을 모아 복원했고, 그 안에서 자격 증명과 개인 식별 정보가 나왔다고 보고했습니다. 즉, 개발자들이 “어차피 못 읽는 덩어리”라고 생각하고 그대로 공개 로그에 올려 둔 것들이었습니다.

정리하면 이렇습니다. 이 블록은 에이전트 루프에서 가장 값진 상태이면서 동시에 가장 잘못 다뤄지는 상태입니다. 이 글은 이게 정확히 뭐고, 어떻게 다뤄야 하는지를 다룹니다.

이 글에서 얻어 갈 것. ① thinking 블록·signature·reasoning item이 각각 무엇인지, ② 왜 “받은 그대로” 돌려줘야 하는지, ③ 떨궜을 때 망가지는 세 가지 방식과 그 증상, ④ 모델·공급자별 차이와 컨텍스트 비용, ⑤ 안 깨지는 루프 코드와 로그 위생.

2. 배경 — 리즈닝 모델의 응답은 “블록의 배열”이다

먼저 용어를 정리하겠습니다. 리즈닝 모델의 응답은 문자열 하나가 아니라 content 블록의 배열입니다. Claude의 Messages API 기준으로 에이전트가 자주 만나는 종류는 넷입니다.

블록안에 든 것돌려줄 때 규칙
thinking thinking(생각 텍스트, 요약본이거나 빈 문자열) + signature 도구를 쓰는 턴 안에서는 필수. 손대면 안 됨
redacted_thinking data(암호화된 내용, 읽을 수 있는 텍스트 없음) thinking과 똑같이 취급. 필터에서 빠지기 쉬움
text사용자에게 보여 줄 텍스트평범
tool_useid, name, inputtool_result의 tool_use_id로 짝을 맞춤

signature가 뭔가. Anthropic 문서의 설명은 짧고 분명합니다. 전체 thinking 내용이 암호화되어 각 thinking 블록의 signature 필드에 담겨 돌아오고, API는 이 값으로 그 블록을 정말 Claude가 생성했는지 검증합니다. 그러니까 서명이자 봉투입니다. 문서는 이 값을 불투명하게 취급하라고 못 박습니다. 해석하지도, 파싱하지도 말라는 뜻입니다. Claude API·Amazon Bedrock·Google Cloud 사이에서는 서로 호환됩니다.

redacted_thinking은 뭔가. 안전상의 이유로 추론 일부가 가려질 때 나오는 별도 블록입니다. 모양은 이렇습니다.

{{< highlight json >}} { "type": "redacted_thinking", "data": "..." } {{< /highlight >}}

여기서 첫 번째 함정이 나옵니다. 많은 코드가 이렇게 씁니다.

{{< highlight python >}} # ❌ redacted_thinking이 조용히 사라진다 blocks = [b for b in response.content if b.type == "thinking"] {{< /highlight >}}

이 한 줄이 나중에 400 에러로 돌아옵니다. Anthropic 문서가 이 실수를 콕 집어 경고할 만큼 흔합니다.

왜 빈 문자열이 오나. 최근 모델은 display 기본값이 "omitted"라서, thinking 블록은 오는데 thinking 필드가 빈 문자열이고 signature만 채워져 있는 경우가 많습니다. 생각 텍스트를 보고 싶으면 display: "summarized"를 주면 됩니다. 어느 쪽이든 돌려줄 때는 받은 배열을 그대로 넘기면 됩니다.

왜 텍스트가 아니라 봉투일까. 공급자는 원본 사고 흔적을 그대로 노출하지 않으려 합니다. 그렇다고 서버에 세션 상태를 들고 있으면 무상태(stateless) API가 아니게 되죠. 그래서 “암호화해서 클라이언트에 맡기고, 다음 요청에 다시 받는” 방식을 씁니다. 여러분의 애플리케이션이 모델의 단기 기억을 대신 보관하는 창고가 된다는 뜻입니다. 이 사실 하나만 이해하면 아래 내용이 전부 자연스럽게 따라옵니다.

3. 도구 호출 한 바퀴는 “턴 하나”다

이제 핵심 개념입니다. 우리 눈에 대화는 이렇게 보입니다. 사용자 → 어시스턴트 → 사용자 → 어시스턴트. 그런데 도구를 쓰면 tool_result가 user 역할로 들어갑니다. 그래서 코드만 보면 턴이 계속 바뀌는 것처럼 보이죠.

모델이 보는 그림은 다릅니다. Anthropic 문서의 표현을 그대로 옮기면, 도구 사용 루프 전체가 하나의 assistant 턴입니다. 모델은 답을 만들다가 외부 정보를 기다리려고 잠깐 멈춘 것이고, tool_result를 받으면 같은 응답을 이어서 만듭니다. 그러니 아까 하던 생각이 아직 거기 있어야 합니다.

그래서 규칙이 이렇게 갈립니다. Anthropic 문서의 세 줄 요약을 그대로 옮기면:

  • 필수 — 도구 사용 턴 안에서는 thinking 블록을 돌려준다.
  • 권장 — 턴을 넘어서도 전부 돌려준다.
  • 허용 — 도구를 안 쓰는 대화라면 이전 턴 thinking은 생략해도 된다.

그리고 한 가지 제약이 더 있습니다. 가장 최근 assistant 메시지 안에서 연속된 thinking 블록의 순서는 모델이 만든 그대로여야 합니다. 재배열도, 편집도, 일부만 빼는 것도 안 됩니다. redacted_thinking도 포함해서요.

좋은 소식. 오래된 thinking을 직접 잘라 낼 필요는 없습니다. 전부 그대로 돌려주면 API가 알아서 걸러 내고, 실제로 모델에게 보여 준 블록에 대해서만 input 토큰을 매깁니다. 즉 “그냥 다 돌려준다”가 기본값으로 옳습니다.

4. 떨구면 벌어지는 세 가지 일

이제 재미없는 부분입니다. 블록을 떨구거나 손댔을 때 나오는 증상은 셋인데, 난이도가 정반대입니다.

① 400 — 그나마 친절한 실패

도구 결과를 돌려주는 요청이 invalid_request_error로 실패하고 메시지에 이 문구가 들어 있습니다.

{{< highlight text >}} `thinking` or `redacted_thinking` blocks in the latest assistant message cannot be modified {{< /highlight >}}

원인은 거의 항상 둘 중 하나입니다. content 블록을 타입으로 걸러 redacted_thinking을 떨궜거나, assistant 메시지를 그대로 넘기지 않고 새로 조립했거나. 고치는 법도 하나입니다. 받은 배열을 그대로 실어 보내면 됩니다.

② 에러 없이 thinking이 꺼지는 경우

이쪽이 진짜 골칫거리입니다. 턴 중간에 — 예를 들어 도구를 호출한 뒤 결과를 돌려주는 사이에 — thinking 설정을 바꾸면 API는 에러를 내지 않습니다. 대신 그 요청에서 thinking을 조용히 끕니다. 문서가 “degrade gracefully”라고 부르는 동작인데, 실무에서는 “원인 모를 품질 저하”로 나타납니다.

턴 구조가 깨질 것 같으면 API가 thinking 블록을 알아서 벗겨 내기도 합니다. 그래서 thinking이 실제로 작동했는지 확인하는 방법은 하나뿐입니다. 응답에 thinking 블록이 있는지 직접 보는 것.

{{< highlight python >}} # thinking이 정말 켜져 있었는지 확인 — 200 OK만으로는 알 수 없다 thought = any(b.type in ("thinking", "redacted_thinking") for b in resp.content) if not thought: logger.warning("thinking이 꺼진 채로 응답함 — 턴 구조나 설정 변경을 확인하세요") {{< /highlight >}}

규칙은 간단합니다. thinking 설정은 턴과 턴 사이에서만 바꾸세요. 도구 루프 한가운데서는 절대 건드리지 않습니다.

③ 캐시가 통째로 다시 만들어지는 경우

프롬프트 캐싱(prompt caching, 같은 앞부분을 재사용해 입력 비용을 줄이는 기능)은 thinking 설정과 effort 값이 프롬프트 자체에 렌더링되기 때문에 이것들이 바뀌면 캐시 프리픽스가 새로 시작됩니다. Anthropic 문서에 실린 실측 결과가 이걸 그대로 보여 줍니다. 3번째 요청에서 예산을 4,000에서 8,000으로 바꿨을 뿐인데:

{{< highlight text >}} 1번째(캐시 생성): cache_creation=1370 cache_read=0 2번째(설정 동일): cache_creation=0 cache_read=1370 ← 히트 3번째(예산 변경): cache_creation=1370 cache_read=0 ← 통째로 다시 {{< /highlight >}}

반대로 좋은 소식도 있습니다. thinking 블록은 도구 결과와 함께 캐시됩니다. cache_control을 따로 안 붙여도 그렇습니다. 그러니 여러 단계짜리 도구 워크플로에서 블록을 그대로 유지하면 캐시 히트로 이득을 봅니다. 다만 캐시에서 읽힌 thinking 블록도 input 토큰으로 계산된다는 점은 기억하세요.

팁. 생각을 많이 시키는 작업은 기본 5분짜리 캐시 수명 안에 안 끝나는 경우가 많습니다. 여러 단계짜리 에이전트라면 1시간 캐시를 검토하세요.

5. 모델마다 다르다 — 다 남기기 vs 마지막 턴만

여기서 많이들 헷갈립니다. “이전 턴의 thinking 블록이 컨텍스트에 남는가”는 모델마다 다릅니다.

계열이전 턴을 전부 남김마지막 턴만 남김
OpusClaude Opus 4.5 이상Claude Opus 4.1 이하
SonnetClaude Sonnet 4.6 이상Claude Sonnet 4.5 이하
Haiku(없음)Claude Haiku 4.5까지 전부

Claude Fable 5, Mythos 5, Mythos Preview도 전부 남기는 쪽입니다.

전부 남기는 모델은 캐시 히트에 유리하고, 문서에 따르면 지능에 나쁜 영향은 없습니다. 대신 남은 thinking이 대화 기록과 똑같이 컨텍스트를 먹고 input 토큰으로 청구됩니다. 긴 에이전트 세션에서는 이게 쌓입니다.

마지막 턴만 남기는 모델은 tool_result가 아닌 일반 user 메시지가 오는 순간 이전 thinking 블록이 전부 사라집니다. 즉 thinking은 그 턴 한정 비용이고 다음 턴에는 창을 안 먹습니다. 여러분이 옛날 블록을 돌려보내도 API가 알아서 벗겨 냅니다.

기본값을 덮어쓰려면 context editing의 clear_thinking_20251015 전략을 씁니다. “최근 N개 턴의 thinking만 남기기” 또는 “전부 남기기”를 직접 고를 수 있습니다.

{{< highlight python >}} response = client.beta.messages.create( model="claude-opus-5", max_tokens=16000, messages=messages, betas=["context-management-2025-06-27"], context_management={ "edits": [ # 최근 2개 턴의 thinking만 남긴다. "all"을 주면 전부 유지(캐시 히트 최대). {"type": "clear_thinking_20251015", "keep": {"type": "thinking_turns", "value": 2}}, # 여러 전략을 함께 쓸 때 clear_thinking은 반드시 배열 맨 앞에 와야 한다. {"type": "clear_tool_uses_20250919", "trigger": {"type": "input_tokens", "value": 50000}, "keep": {"type": "tool_uses", "value": 5}}, ] }, ) {{< /highlight >}}

단, 지우는 순간 그 지점에서 캐시가 무효화됩니다. 컨텍스트 여유와 캐시 히트를 맞바꾸는 손잡이라고 생각하면 정확합니다.

모델을 바꿔 끼울 때. 대화 도중에 모델을 교체한다면(예: 폴백) 이전 턴의 thinking·redacted_thinking 블록을 벗겨 내고 보내세요. 이 블록들은 만든 모델에 묶여 있습니다. 다른 모델은 에러를 내지 않고 조용히 무시하는데, 무시된 블록도 input 토큰은 그대로 청구됩니다. 라우팅·폴백을 쓰는 팀이 청구서 보고 놀라는 전형적인 지점입니다.

6. OpenAI 쪽은 어떻게 다른가

OpenAI의 Responses API는 같은 문제를 다른 방식으로 풉니다. 이름은 thinking 블록이 아니라 reasoning item이고, 보관 위치를 고를 수 있습니다.

상태를 서버에 맡기는 방식. 응답은 기본적으로 저장되므로(store: true), 다음 요청에서 previous_response_id로 이전 응답을 가리키면 그 추론을 이어 쓸 수 있습니다. 코드가 단순해집니다. 다만 비용까지 공짜가 되지는 않습니다. previous_response_id를 써도 이어진 응답들의 이전 입력 토큰은 전부 input 토큰으로 청구됩니다.

상태를 클라이언트가 들고 있는 방식. 데이터 보관 정책상 서버 저장을 못 쓰는 조직(ZDR 등)을 위해, 암호화된 reasoning item을 받아 직접 들고 다닐 수 있습니다.

{{< highlight python >}} resp = client.responses.create( model="gpt-5.6-terra", input=history, tools=tools, store=False, # 서버에 저장하지 않음 include=["reasoning.encrypted_content"], # 대신 암호화된 추론을 돌려받음 ) # 다음 요청에서는 output 아이템을 그대로 이어 붙인다. # (Claude에서 content 배열을 통째로 echo하는 것과 같은 발상) history += resp.output {{< /highlight >}}

OpenAI 설명에 따르면 요청에 실려 온 encrypted_content는 메모리에서만 복호화되어 다음 응답 생성에 쓰이고 디스크에는 쓰이지 않습니다. 그리고 GPT-5.6 계열은 이전 턴의 reasoning을 재사용하는 all_turns를 기본으로 씁니다. 이전 응답 아이템에 접근할 수 있을 때만 효과가 있으니, 결국 “아이템을 이어 붙였는가”가 관건입니다.

1절의 ARC-AGI-3 이야기가 바로 이 지점입니다. 모델도 예산도 그대로였고, 하네스가 매 수마다 추론을 버리던 것을 안 버리게 바꾼 게 전부였습니다. 모델을 바꾸기 전에 하네스가 뭘 버리고 있는지부터 보라는 교훈으로 읽는 게 맞습니다.

7. 실전 — 안 깨지는 루프와 로그 위생

안 깨지는 에이전트 루프

규칙은 하나로 줄일 수 있습니다. 응답 content를 손대지 말고 통째로 넣는다. 블록 타입으로 걸러 내는 코드를 아예 쓰지 않는 게 요령입니다.

{{< highlight python >}} import anthropic client = anthropic.Anthropic() messages = [{"role": "user", "content": "파리 날씨 확인하고 우산이 필요한지 알려줘"}] while True: resp = client.messages.create( model="claude-opus-4-8", max_tokens=16000, thinking={"type": "adaptive"}, # 루프 도중에는 절대 바꾸지 않는다 tools=TOOLS, messages=messages, ) # ① 받은 배열을 통째로 넣는다. 필터링·재조립 금지. # thinking / redacted_thinking / text / tool_use가 원래 순서 그대로 들어간다. messages.append({"role": "assistant", "content": resp.content}) if resp.stop_reason != "tool_use": break # ② 도구를 돌리고 결과를 user 메시지로 붙인다. results = [] for block in resp.content: if block.type == "tool_use": results.append({ "type": "tool_result", "tool_use_id": block.id, "content": run_tool(block.name, block.input), }) messages.append({"role": "user", "content": results}) {{< /highlight >}}

짧죠. 요점은 resp.content를 가공하지 않는 것입니다. 화면에 보여 줄 텍스트가 필요하면 표시용으로만 따로 뽑아 쓰고, API에 보내는 배열은 원본을 유지하세요.

{{< highlight python >}} # 화면 표시용 — 여기서 뽑은 값을 다시 API로 보내면 안 된다 display_text = "".join(b.text for b in resp.content if b.type == "text") {{< /highlight >}}

로그 위생 — 덩어리를 그대로 남기지 않기

1절의 논문이 짚은 문제가 여기입니다. 연구진은 공개된 에이전트 실행 기록에서 이 블록들을 모아 복원했고, 그 안에서 자격 증명과 개인 정보를 찾아냈습니다. 이 추출 기법 자체는 2026년 8월 기준 더 이상 재현되지 않고, 실제 악용 사례도 문서화되지 않았습니다. 하지만 교훈은 남습니다.

암호화됐다는 말은 “안전하다”가 아니라 “내가 못 읽는다”입니다. 그 안에는 모델이 사용자 데이터를 보며 한 생각이 들어 있습니다. 그러니 실행 기록을 외부에 내보낼 때는 마스킹하세요.

{{< highlight python >}} OPAQUE_KEYS = {"signature", "data", "encrypted_content"} def redact_reasoning(obj): """추적/디버그 기록을 밖으로 내보내기 전에 불투명 필드를 마스킹한다. 주의: 이 결과물은 '보관·공유용'이다. API로 되돌려 보낼 원본은 반드시 손대지 않은 채로 따로 들고 있어야 한다. """ if isinstance(obj, dict): out = {} for k, v in obj.items(): if k in OPAQUE_KEYS and isinstance(v, str): out[k] = f"" # 길이만 남겨 디버깅에 쓴다 elif k == "thinking" and isinstance(v, str): out[k] = f"" # 생각 텍스트도 원문 저장은 피한다 else: out[k] = redact_reasoning(v) return out if isinstance(obj, list): return [redact_reasoning(x) for x in obj] return obj {{< /highlight >}}

운영 규칙으로 정리하면 이렇습니다.

  • 원본은 세션 메모리에만. API로 되돌려 보낼 배열은 손대지 않은 채로 들고 있되, 그 수명은 대화 수명까지로 한정합니다.
  • 내보내는 순간 마스킹. 이슈 첨부, 공개 저장소, 외부 로그 수집기, 재현용 덤프 — 프로세스 밖으로 나가는 모든 경로에 위 함수를 겁니다.
  • 추적 도구 설정을 확인. 요청·응답 본문을 통째로 저장하는 설정이면 이 필드도 같이 쌓입니다.

팁 하나 — 여러 모델을 돌린다면 기본값에 기대지 마세요. 같은 코드가 Haiku와 Opus에서 컨텍스트를 전혀 다르게 씁니다. clear_thinking_20251015의 keep을 명시하면 모델을 바꿔도 동작이 예측 가능해집니다.

팁 둘 — 회귀를 잡는 지표를 하나 두세요. 턴마다 cache_read_input_tokens와 “thinking 블록이 왔는지”를 같이 남기면, 앞서 본 ②와 ③이 배포 직후에 그래프로 드러납니다. 둘 다 에러를 안 내는 실패라서, 재는 것 말고는 알아챌 방법이 없습니다.

9. 마무리 (TL;DR)

  • 리즈닝 모델의 응답은 블록의 배열입니다. thinking의 signature, redacted_thinking의 data, OpenAI의 encrypted_content는 모델의 단기 기억을 담은 봉투입니다.
  • 도구 사용 루프 전체가 assistant 턴 하나입니다. 그 안에서는 thinking 블록을 받은 그대로 돌려주는 게 필수입니다.
  • 어겼을 때 증상은 셋입니다. ① 400 에러, ② 에러 없이 thinking이 꺼짐, ③ 캐시 프리픽스 재생성. 뒤로 갈수록 알아채기 어렵습니다.
  • 가장 흔한 원인은 b.type == "thinking" 필터링과 메시지 재조립입니다. 필터링을 없애면 대부분 해결됩니다.
  • 이전 턴 블록을 남기는지는 모델마다 다릅니다. Opus 4.5+·Sonnet 4.6+·Fable 5·Mythos 5는 전부 남기고, 그 이전 모델과 Haiku 계열은 마지막 턴만 남깁니다. 여러 티어를 쓰면 clear_thinking_20251015로 명시하세요.
  • 모델을 바꿔 끼울 때는 이전 thinking 블록을 벗겨 내세요. 무시되더라도 input 토큰은 청구됩니다.
  • 모델을 바꾸기 전에 하네스가 뭘 버리고 있는지 보세요. OpenAI는 추론 유지와 압축 두 가지만 켜서 ARC-AGI-3 점수를 13.3%에서 38.3%로 올렸습니다.
  • 불투명해 보이는 필드는 안전하다는 뜻이 아닙니다. 실행 기록을 밖으로 내보낼 때는 마스킹하고, 원본은 세션 안에만 두세요.
