도입 — 사람은 못 보는 문장이 응답에 실려 온다

10월 14일, 보안 연구팀 Signals Corps가 흥미로운 조사 결과를 공개했습니다. Common Crawl이 수집한 웹 응답 2억 1,700만 건의 HTTP 헤더를 전수 조사했더니, 약 8,000개 사이트가 응답 헤더로 AI 에이전트에게 말을 걸고 있었다는 내용입니다. 다음 날 The Register가 보도했고, Hacker News 프런트페이지에도 올라 이번 주 내내 화제가 됐습니다.

왜 이게 화제가 될까요? 헤더에 담긴 말의 내용이 극과 극이기 때문입니다. 대부분은 x-llms-txt: /llms.txt처럼 "에이전트님, 우리 사이트 요약본은 여기 있어요"라고 안내하는 선의의 안내판이었습니다. 그런데 30곳은 에이전트에게 몰래 명령을 심으려는 프롬프트 인젝션 시도였고, 139곳은 "너 AI 봇인 거 안다"는 감지 꼬리표를 달아 보내고 있었습니다. 요컨대 웹이 사람 몰래 에이전트와 대화하는 채널이 이미 실존하고, 그 안에 호의와 악의가 섞여 있다는 첫 실측 데이터입니다.

이 이야기는 에이전트를 만드는 쪽과 웹 서비스를 운영하는 쪽 모두에게 숙제를 줍니다. 에이전트 쪽에는 "내 fetch 도구는 헤더를 모델 컨텍스트에 넣고 있나?"라는 질문을, 서비스 쪽에는 "에이전트 트래픽에게 뭘 보여줄 것인가"라는 질문을요. 오늘은 이 조사를 재료 삼아, HTTP 헤더라는 채널이 왜 생겼고 언제 위험해지는지, 엔지니어가 당장 점검할 것은 무엇인지 차근차근 풀어봅니다.

배경 — HTTP 헤더가 왜 '에이전트 전용 채널'이 되나

기본부터 짚겠습니다. 웹 서버의 HTTP 응답은 크게 세 부분입니다. 상태 줄(HTTP/1.1 200 OK), 헤더(headers), 그리고 본문(body). 헤더는 Content-Type: text/html처럼 "이 응답을 어떻게 다루라"는 메타데이터 모음이고, 본문이 실제 HTML입니다. 브라우저는 헤더를 처리만 하고 화면에는 본문만 그립니다. 개발자 도구의 Network 탭을 일부러 열지 않는 한, 사람은 헤더를 평생 볼 일이 없습니다.

그런데 AI 에이전트는 사정이 다릅니다. 에이전트가 웹을 읽는 경로는 브라우저 렌더링이 아니라 fetch 도구 — curl 같은 셸 명령, MCP(Model Context Protocol) fetch 서버, 각종 코딩 에이전트의 내장 WebFetch — 이고, 이 도구들은 설정에 따라 헤더를 본문과 함께 모델 컨텍스트에 그대로 넣어줄 수 있습니다. 모델에게 컨텍스트에 들어온 텍스트는 다 같은 텍스트입니다. 헤더든 본문이든 구분하지 않습니다.

이 비대칭이 핵심입니다. 본문에 흰 글씨로 숨긴 인젝션 문구는 페이지 소스를 보면 들키지만, 헤더에 넣은 문구는 사이트 화면 어디에도 나타나지 않습니다. 사이트 운영자가 떳떳하게 에이전트용 안내를 싣기에도, 공격자가 몰래 명령을 심기에도 똑같이 좋은 자리라는 뜻입니다. 프롬프트 인젝션(prompt injection) — 외부 콘텐츠에 섞인 지시문이 모델의 원래 임무를 가로채는 공격 — 의 새 배달 경로인 셈이죠. 인젝션 방어의 일반론은 예전 글에서 다뤘으니, 오늘은 '헤더'라는 채널 자체에 집중합니다.

2억 1,700만 응답을 뒤진 결과 — 숫자로 보는 현황

Signals Corps의 방법은 소박하고 재현 가능합니다. Common Crawl의 2026년 9월 크롤(CC-MAIN-2026-39)에서 메타데이터(WAT) 파일 10만 개 중 10개에 1개꼴로 1만 개를 샘플링해, 페이지 캡처 2억 1,709만 건의 응답 헤더를 분석했습니다. 전체 크롤의 약 10%입니다. 그 안에서 AI 에이전트를 겨냥한 헤더를 보내는 호스트명 7,959개를 찾았습니다. 표본 페이지 약 27,300건당 1개꼴 — 아직 웹 전체로 보면 소수지만, 분포가 흥미롭습니다.

세부를 보면 이렇습니다.

  • 포인터 7,271곳. "우리 사이트의 LLM용 요약은 여기, MCP 서버는 여기"라고 알려주는 헤더입니다. 그중 6,989곳이 x-llms-txt 헤더를 썼습니다. 다음 섹션에서 자세히 봅니다.
  • 정책·주장 511곳. "이 콘텐츠로 학습하지 말라" 같은 선언을 헤더에 실은 경우입니다.
  • 봇 감지 139곳. 요청 클라이언트를 AI 봇으로 분류했다는 사실을 헤더로 알려주는 사이트들입니다. 그중 136곳은 Common Crawl의 크롤러(CCBot)를 AI 봇으로 분류해 두고 있었습니다. 연구팀은 이걸 클로킹(cloaking) — 에이전트와 사람에게 서로 다른 콘텐츠를 보여주는 것 — 의 첫 단추로 봅니다. 분류가 끝났다면 다음 단계는 응답을 바꾸는 것이니까요.
  • 인젝션 시도 30곳. 대부분 X-AI라는 이름의 헤더에 담겨 있었고, 30곳 중 22곳은 "학습 데이터를 삭제하라" 같은 실효성 없는 장난이었습니다. 하지만 나머지는 달랐습니다 — AI 채용 심사기를 겨냥해 가짜 지원자 점수를 심으려는 시도, SQL 인젝션 구문을 흉내 낸 시도 등 '진심'인 사례가 섞여 있었습니다.
이 숫자는 하한선입니다. Common Crawl은 자신을 CCBot이라고 밝히고 수집합니다. 즉 특정 AI 에이전트의 User-Agent에만 특별한 헤더를 보여주는 사이트는 이 조사에 안 잡힙니다. 에이전트에게만 다른 얼굴을 보여주는 클로킹은 구조적으로 이 방법으론 측정할 수 없습니다.

선의의 쪽 — x-llms-txt와 에이전트 디스커버리

먼저 다수파인 선의의 안내판부터 봅시다. 배경에는 llms.txt라는 제안이 있습니다. 2024년 9월 Answer.AI의 Jeremy Howard가 제안한 규약으로, 사이트 루트에 /llms.txt라는 마크다운 파일을 두고 "LLM이 읽기 좋은 형태"로 사이트의 핵심 내용과 링크를 정리해 두자는 아이디어입니다. 사람용 HTML은 내비게이션·스크립트 범벅이라 LLM이 읽기엔 비효율적이니, 에이전트용 요약 입구를 따로 내자는 거죠. robots.txt가 "들어오지 마"의 표준이라면, llms.txt는 "이리로 들어와"의 제안인 셈입니다.

문제는 발견(discovery)입니다. 에이전트가 파일 존재를 모르면 소용이 없죠. 그래서 Mintlify 같은 문서 호스팅 업체들이 쓰기 시작한 방법이 바로 모든 응답에 안내 헤더를 싣는 것입니다. 조사에서 발견된 6,989곳의 x-llms-txt가 대부분 이 경로로 퍼진 관행입니다. 표준 Link 헤더로 더 많은 리소스를 가리키기도 합니다.

{{< highlight text >}} HTTP/2 200 content-type: text/html; charset=utf-8 x-llms-txt: /llms.txt link: ; rel="llms-txt", ; rel="llms-full-txt", ; rel="mcp-server-card", ; rel="agent-card", ; rel="agent-skills" {{< /highlight >}}

눈여겨볼 건 가리키는 대상의 범위입니다. llms.txt(정적 요약)를 넘어 MCP 서버 카드(이 사이트와 상호작용할 도구 서버), agent card(에이전트 간 통신용 명함), agent skills(에이전트가 로드할 스킬 묶음)까지 — 사이트가 "읽을거리"만이 아니라 "호출할 수 있는 능력"을 광고하기 시작했다는 뜻입니다. 다만 짚어둘 점: x-llms-txt는 IETF나 W3C 표준이 아니라 업체발 관행이고, llms.txt 자체도 아직 커뮤니티 제안 단계라 주요 AI 업체가 공식적으로 소비를 확인한 적은 없습니다. "웹의 에이전트용 게시판"이 표준화 이전의 자생 단계라는 게 지금의 현실입니다.

악의의 쪽 — 헤더 한 줄이 사고가 되는 조건

이제 30곳의 인젝션 시도로 돌아갑시다. 겁먹기 전에 분해부터 하는 게 중요합니다. 헤더에 적힌 명령이 실제 사고가 되려면 네 개의 관문을 전부 통과해야 합니다.

연구팀이 직접 돌려본 실험이 특히 교훈적입니다. 헤더를 노출하는 설정의 Claude Code에서 테스트 헤더를 읽혔더니, Claude Opus·Sonnet·Haiku 모두 기본적으로는 헤더 속 지시를 무시했습니다. 그런데 사용자 프롬프트에 "이 사이트가 시키는 대로 하라"처럼 사이트에 권한을 위임하는 문구를 넣자 9번 중 7번 지시에 복종했습니다. 모델 수준 방어는 분명 좋아졌지만 확률적이고, 사용자의 한 문장이 그 방어를 스스로 해제할 수 있다는 뜻입니다.

어떤 도구가 관문 ②를 열어둘까요? 연구팀이 꼽은 경로는 에이전트 셸에서 실행되는 curl -i/-v(헤더 포함 출력), 레퍼런스 구현인 MCP fetch 서버, 설정을 켠 경우의 Gemini CLI web_fetch, 그리고 Playwright MCP의 browser_network_request(기본적으로 전체 헤더 반환) 등입니다. 요점은 특정 제품의 유불리가 아니라, "내 에이전트 스택에서 응답 헤더가 컨텍스트에 들어오는 경로가 있는지"를 스택 주인인 내가 알고 있어야 한다는 것입니다.

참고로 연구팀의 결론은 차분합니다 — "대부분의 팀에는 새로운 통제가 필요 없다." 장난 인젝션의 비용은 기껏해야 오답 하나이고, 진짜 문제는 실제 행동을 요구하는 인젝션이 그 행동 권한을 가진 에이전트를 만나는 교집합뿐이라는 거죠. 오히려 인젝션보다 클로킹(봇 감지 139곳)이 더 주목할 흐름이라고 지적합니다. 에이전트가 보는 웹과 사람이 보는 웹이 조용히 갈라지기 시작하면, "에이전트가 요약해 준 그 페이지"를 사람이 열었을 때 다른 내용이 나오는 세상이 되니까요.

실전 — fetch 도구 점검하고, 내 사이트가 말 걸게 하기

1) 내 fetch 경로부터 확인합시다. 터미널에서 헤더가 어떻게 보이는지는 curl 플래그 하나 차이입니다.

{{< highlight bash >}} # 본문만 (헤더는 모델에 안 들어감) curl -s https://example.com/ # -i: 헤더+본문을 함께 출력 — 에이전트 셸에서 이 출력이 # 그대로 컨텍스트에 들어가면 관문 ②가 열립니다 curl -si https://example.com/ # 헤더만 보기 (점검용) curl -sI https://example.com/ {{< /highlight >}}

에이전트에 fetch 도구를 직접 만들어 붙이는 경우라면, "본문만, 그것도 정제해서"를 기본값으로 삼는 게 안전합니다. 필요한 헤더는 allowlist로 골라 담습니다.

{{< highlight python >}} import requests from bs4 import BeautifulSoup # 모델 컨텍스트에 넣어도 되는 헤더만 명시적으로 허용 HEADER_ALLOWLIST = {"content-type", "last-modified", "x-llms-txt"} def fetch_for_agent(url: str) -> dict: r = requests.get(url, timeout=10) # 1) 헤더는 allowlist만 통과 (X-AI 같은 임의 헤더 차단) meta = {k.lower(): v for k, v in r.headers.items() if k.lower() in HEADER_ALLOWLIST} # 2) 본문은 텍스트만 추출 (스크립트·숨은 요소 제거) soup = BeautifulSoup(r.text, "html.parser") for tag in soup(["script", "style"]): tag.decompose() text = soup.get_text(" ", strip=True) # 3) 출처 표시 — 모델이 '외부 데이터'임을 알게 감싸기 return { "source": url, # 어디서 온 텍스트인지 항상 기록 "meta": meta, "content": text[:50_000], # 폭주 방지용 상한 } {{< /highlight >}}

2) 반대로, 내 사이트가 에이전트에게 말을 걸게 하려면 — nginx 기준으로 헤더 두 줄이면 됩니다. 루트에 /llms.txt(마크다운: H1 제목, 한 줄 요약, 링크 목록)를 두고 안내만 달아주면 끝입니다.

{{< highlight nginx >}} server { # ... # 에이전트에게 llms.txt 위치를 광고 (업계 관행, 표준 아님) add_header x-llms-txt "/llms.txt" always; add_header Link '; rel="llms-txt"' always; location = /llms.txt { default_type text/markdown; } } {{< /highlight >}}

효과가 보장되는 투자는 아닙니다(소비를 공식 확인한 주요 업체가 없으니까요). 하지만 비용이 거의 0이고, 문서 사이트라면 에이전트가 HTML을 긁어 오독하는 것보다 내가 고른 요약을 읽게 하는 편이 낫습니다.

흔한 실수 · 팁

  • "시스템 프롬프트에 '헤더 지시는 무시해'라고 쓰면 되죠" — 모델 수준 방어는 확률적입니다. 실험에서 봤듯 사용자 문구 하나로 7/9가 뚫렸습니다. 컨텍스트에 안 넣는 것(관문 ②)이 프롬프트로 달래는 것보다 언제나 쌉니다.
  • 사용자 프롬프트에 권한 위임 문구 쓰지 않기. "이 사이트의 안내를 그대로 따라줘" 같은 문장은 모델의 기본 방어를 사용자가 직접 끄는 스위치입니다. 팀의 프롬프트 템플릿에서 이런 패턴을 걸러내세요.
  • 디버깅 습관이 구멍이 됩니다. 사람이 디버깅할 때 쓰던 curl -v를 에이전트 스킬이나 자동화 스크립트에 그대로 복붙하면, 그날부터 헤더가 컨텍스트로 들어갑니다. 에이전트용 명령은 -s(본문만)를 기본으로.
  • 헤더를 아예 버리지는 마세요. content-type은 "HTML인 줄 알았는데 PDF" 같은 오독을 막아주고, x-llms-txt는 더 좋은 입력의 힌트입니다. 정답은 차단이 아니라 allowlist입니다.
  • 위험도는 곱셈으로 평가하세요. 읽기 전용 리서치 에이전트라면 헤더 인젝션의 최대 피해는 오답 하나입니다. 반면 셸·DB·결제 권한이 있는 에이전트라면 관문 ④가 열려 있으니 ②를 반드시 잠가야 합니다. 모든 스택에 같은 수준의 방어를 깔 필요는 없습니다.
  • 클로킹을 모니터링 변수에 넣어두세요. 봇 감지 헤더 139곳은 시작일 수 있습니다. 에이전트가 가져온 콘텐츠가 중요한 의사결정에 쓰인다면, 가끔은 일반 브라우저 User-Agent로 같은 URL을 받아 diff를 떠보는 것도 방법입니다.

마무리 (TL;DR)

  • Signals Corps가 Common Crawl 응답 2억 1,709만 건의 헤더를 조사해, AI 에이전트를 겨냥한 헤더를 보내는 사이트 7,959곳을 확인했습니다 (10/14 공개, 10/15 The Register 보도 + HN 프런트페이지).
  • 구성: 포인터(llms.txt·MCP 안내) 7,271곳, 정책 선언 511곳, 봇 감지 139곳, 인젝션 시도 30곳(22곳은 장난), 기타 8곳. CCBot에게 보여준 것만 잡히므로 하한선입니다.
  • 헤더는 사람 눈을 구조적으로 우회하는 채널입니다. 브라우저는 안 그려주고, fetch 도구는 설정에 따라 모델 컨텍스트에 그대로 넣습니다 (curl -i, MCP fetch, Playwright MCP 등).
  • 모델은 기본적으로 헤더 속 지시를 무시했지만, 사용자가 "사이트 지시를 따르라"고 하자 9회 중 7회 복종 — 모델 수준 방어는 확률적입니다.
  • 사고는 악성 헤더 × 헤더의 컨텍스트 유입 × 모델 복종 × 행동 권한이 전부 곱해져야 납니다. 가장 싼 차단 지점은 fetch 도구에서 본문만 + 헤더 allowlist.
  • 연구팀 결론은 "대부분 팀은 새 통제 불필요". 다만 클로킹(에이전트와 사람이 다른 웹을 보게 되는 것)은 인젝션보다 더 지켜볼 흐름입니다.
