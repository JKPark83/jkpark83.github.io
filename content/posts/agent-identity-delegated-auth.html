1. 도입 — API 키 한 장으로 시작해서 어디서 무너지나

에이전트에 처음 툴을 붙일 때 우리는 거의 다 같은 길을 갑니다. GitHub 토큰 하나 발급받아 GITHUB_TOKEN에 넣고, Slack 토큰 하나 더 넣고, 사내 API 키까지 .env에 채웁니다. 잘 돌아갑니다. 내 노트북에서 내가 쓰는 동안은요.

그런데 이 구조를 회사 동료 30명이 쓰는 서비스로 옮기는 순간, 답할 수 없는 질문이 하나 생깁니다. “방금 그 API 호출은 누구의 자격으로 나갔나요?”

서버 로그를 열어 보면 전부 같은 얼굴입니다. 모든 요청이 agent-service-account 한 명의 이름으로 나갔고, 그 계정은 30명 누구의 권한이든 다 갖고 있습니다. A가 볼 수 없어야 할 저장소를 에이전트에게 부탁하면? 에이전트는 아무 저항 없이 읽어 줍니다. 에이전트가 실수로 데이터를 지웠을 때 누가 시킨 일인지 추적하려면? 로그에는 서비스 계정 이름만 남아 있습니다.

이건 보안 담당자만의 고민이 아니라 설계 문제입니다. 에이전트가 사람 대신 시스템을 만지는 순간, “권한”은 코드 한 줄이 아니라 아키텍처의 일부가 되니까요.

이번 주에 이 주제가 유난히 시끄러웠던 데는 이유가 있습니다.

  • MCP 2026-07-28 규격이 인가(authorization)를 통째로 다시 썼습니다. 세션과 초기화 핸드셰이크를 걷어낸 이 대규모 개정판은 7월 28일에 확정됐고, Tier 1 SDK 네 개(TypeScript·Python·Go·C#)가 같은 날 대응을 내놨습니다. 이전 규격에 맞춰 짜 둔 MCP 서버를 8월부터 옮기라는 이야기라, 실무자들이 지금 막 인가 부분을 다시 읽고 있는 참입니다.
  • Black Hat USA 2026에서 “에이전트 신원”이 하나의 제품 카테고리가 됐습니다. 48시간 사이에 15개 넘는 업체가 에이전트 인프라 보안 제품을 냈고, 그중 상당수가 “정적 자격 증명(static credential)에 기댄 기존 신원 모델은 자율 에이전트에 맞지 않는다”는 같은 문장을 출발점으로 삼았습니다.
  • 표준은 아직 미완성입니다. 사람 → 에이전트 → 서브 에이전트 → API로 이어지는 다단계 위임을 어떻게 검증 가능하게 남길지를 두고 IETF에서 새 초안(actor chain)이 논의되고 있습니다. 즉, 지금 당장은 각자 설계해야 하는 영역이 남아 있다는 뜻입니다.
이 글에서 얻어갈 것. ① 왜 토큰을 “그대로 넘기면” 안 되는지 ② MCP 규격이 요구하는 최소한이 정확히 무엇인지 ③ 사람의 신원을 여러 홉의 에이전트에 어떻게 실어 나르는지 ④ 오늘 코드에 바로 넣을 수 있는 검증 로직. OAuth를 잘 몰라도 따라올 수 있게 필요한 만큼만 짚고 갑니다.

2. 배경 — OAuth를 5분 만에 (에이전트에 필요한 부분만)

먼저 등장인물 넷만 외우면 됩니다. 비유하자면 호텔입니다.

역할OAuth 용어호텔 비유에이전트 세계에선
권한의 주인resource owner투숙객 본인에이전트에게 일을 시킨 사람
대신 요청하는 쪽client심부름을 부탁받은 벨보이MCP 클라이언트(에이전트)
열쇠를 발급하는 곳authorization server (AS)프런트 데스크사내 IdP, Okta, Entra 등
열쇠로 여는 문resource server (RS)객실 문MCP 서버, 외부 API

프런트에서 받는 카드키가 액세스 토큰(access token)입니다. 여기서 초보자가 가장 자주 놓치는 두 속성이 있는데, 이 글의 나머지 전부가 사실 이 둘 이야기입니다.

  • 스코프(scope) — “무엇을 할 수 있는가”. 카드키로 헬스장은 되고 와인 창고는 안 되는 것과 같습니다.
  • 오디언스(audience) — “어느 문에 쓰라고 준 것인가”. 1204호 카드키는 1204호에서만 통해야 합니다. 토큰의 aud 클레임에 들어갑니다.

API 키는 이 둘이 사실상 없는 물건입니다. 대체로 만료도 없고, 누구를 대신하는지도 안 적혀 있고, 어디에 쓰라는 표시도 없습니다. 그래서 혼자 쓸 땐 편하지만 여럿이 쓰는 순간 “구분”이라는 기능 자체가 없어집니다. 마스터키를 30명에게 복사해 준 셈이니까요.

정리. 에이전트 인증의 목표는 “토큰이 유효한가”를 확인하는 게 아닙니다. 이 토큰은 누구를 대신해, 무엇을, 어디에 하라고 준 것인가를 시스템이 스스로 답할 수 있게 만드는 것입니다.

3. 함정 ① 토큰 패스스루 — 가장 흔하고 가장 조용한 실수

MCP 서버를 만들다 보면 자연스럽게 이런 코드를 쓰게 됩니다. 클라이언트가 Authorization 헤더에 실어 보낸 토큰을 받아서, 외부 API를 부를 때 그대로 다시 붙이는 겁니다.

{{< highlight python >}} # ❌ 하지 마세요 — 이게 바로 '토큰 패스스루'입니다 @app.post("/mcp") async def handle(request: Request): token = request.headers["Authorization"] # 클라이언트가 준 토큰 # 검증 없이 그대로 상류 API에 재사용 r = await httpx.get("https://api.github.com/user/repos", headers={"Authorization": token}) return r.json() {{< /highlight >}}

동작은 잘 합니다. 그리고 바로 그 점이 이 실수가 오래 살아남는 이유입니다. MCP 규격은 이 패턴을 안티패턴(anti-pattern)이라고 이름 붙이고 MUST NOT으로 금지합니다. 규격이 드는 근거를 실무 언어로 옮기면 이렇습니다.

  • 보안 통제를 건너뜁니다. 레이트 리밋이나 요청 검증처럼 “토큰의 audience에 기대는” 통제들이 전부 무력해집니다. 클라이언트가 서버를 거치지 않고 직접 상류 API를 불러도 똑같이 통하니까요.
  • 감사 추적이 사라집니다. 상류 API 로그에는 실제로 요청을 전달한 MCP 서버가 아니라 다른 신원이 찍힙니다. 사고가 났을 때 경로를 되짚을 수가 없습니다.
  • 신뢰 경계가 무너집니다. 여러 서비스가 검증 없이 같은 토큰을 받아 주면, 한 곳만 뚫려도 연결된 전부가 뚫립니다.

여기에 하나 더. 서버가 audience를 검증하지 않으면 남의 서비스용으로 발급된 토큰까지 받아 주게 됩니다. 1204호 카드키를 프런트에 보여 주며 “저 금고 열어 주세요”라고 했는데 열어 주는 상황입니다.

4. 2026-07-28 MCP 규격이 못 박은 것

새 규격의 인가 부분은 “각자 알아서 하세요”를 최대한 줄이는 방향으로 정리됐습니다. 핵심만 뽑으면 다섯 줄입니다. (규격 원문의 MUST/SHOULD를 그대로 살렸습니다.)

누가무엇을강도
MCP 서버OAuth 2.0 Protected Resource Metadata(RFC 9728) 구현 — 즉 /.well-known/oauth-protected-resource로 “내 인가 서버는 여기다”를 알림MUST
MCP 클라이언트Resource Indicators(RFC 8707)의 resource 파라미터를 인가 요청과 토큰 요청 양쪽에 포함. 인가 서버가 지원하든 말든 무조건 보냄MUST
MCP 서버들어온 토큰이 자기 자신을 대상으로 발급된 것인지 검증. 아니면 401MUST
MCP 서버클라이언트에게 받은 토큰을 상류 API로 그대로 전달하지 않기MUST NOT
MCP 클라이언트PKCE 사용(가능하면 S256), 그리고 인가 서버 메타데이터에 code_challenge_methods_supported가 없으면 진행 자체를 거부MUST

용어를 하나씩 풀면 이렇습니다.

PKCE(Proof Key for Code Exchange, “픽시”라고 읽습니다)는 인가 코드를 중간에서 가로채도 못 쓰게 만드는 장치입니다. 클라이언트가 무작위 값(verifier)을 만들어 그 해시(challenge)를 먼저 보내고, 나중에 원본을 함께 제시해야만 토큰을 받습니다. 택배 수령할 때 미리 정한 암호를 대는 것과 같습니다.

resource 파라미터는 “이 토큰을 어디에 쓸 건지”를 발급 요청 단계에서 명시하는 값입니다. 인가 서버는 이걸 보고 토큰의 aud를 좁혀서 발급합니다. 앞서 말한 카드키의 호수를 새겨 넣는 단계라고 보면 됩니다.

그리고 새 규격에서 눈에 띄는 변화가 하나 더 있습니다. 클라이언트 등록 방식으로 Client ID Metadata Documents가 들어왔습니다. 클라이언트가 자기 정보를 담은 JSON을 HTTPS URL에 올려 두고, 그 URL 자체를 client_id로 쓰는 방식입니다. 반대로 기존의 동적 클라이언트 등록(DCR)은 deprecated가 됐습니다. 처음 보는 서버와 클라이언트가 사전 관계 없이 만나는 MCP 특성상, 매번 등록 API를 두드리는 것보다 이 편이 깔끔하다는 판단입니다.

{{< highlight json >}} // https://app.example.com/oauth/client-metadata.json // ↑ 이 URL 문자열이 그대로 client_id가 됩니다 { "client_id": "https://app.example.com/oauth/client-metadata.json", "client_name": "Example MCP Client", "redirect_uris": ["http://127.0.0.1:3000/callback"], "grant_types": ["authorization_code"], "response_types": ["code"], "token_endpoint_auth_method": "none" } {{< /highlight >}}

5. 함정 ② confused deputy — 동의 화면을 건너뛰는 공격

confused deputy(혼란한 대리인)는 오래된 보안 개념인데, 한 문장으로는 이렇습니다 — 권한 있는 중개자가, 권한 없는 요청자를 대신해, 요청자 스스로는 할 수 없었을 일을 해 주는 것. 문 열 권한이 있는 경비원에게 “저기 좀 열어 주세요”라고 부탁해서 여는 상황입니다.

MCP에서 이게 어떻게 터지는지가 규격 문서에 아주 구체적으로 적혀 있습니다. 무대는 MCP 프록시 서버입니다. 여러 MCP 클라이언트를 받아서, 자기는 외부 API에 대해 하나의 OAuth 클라이언트로 행동하는 서버죠. 다음 네 조건이 모두 겹치면 공격이 성립합니다.

  1. 프록시가 외부 인가 서버에 대해 정적 client_id를 씁니다(누가 요청하든 같은 값).
  2. 프록시가 MCP 클라이언트들에게 동적 등록을 허용합니다(각자 다른 client_id를 받아 감).
  3. 외부 인가 서버가 첫 승인 후 브라우저에 동의 쿠키를 심습니다.
  4. 프록시가 외부로 넘기기 전에 클라이언트별 동의를 따로 받지 않습니다.

공격은 이렇게 흘러갑니다. 사용자가 한 번 정상적으로 승인합니다 → 브라우저에 동의 쿠키가 남습니다 → 공격자가 악성 redirect_uri로 클라이언트를 동적 등록하고, 조작된 인가 링크를 사용자에게 보냅니다 → 사용자가 클릭하면 쿠키가 있으니 동의 화면이 안 뜹니다 → 인가 코드가 공격자 서버로 리다이렉트됩니다 → 공격자가 그 코드를 토큰으로 바꿔 사용자 행세를 합니다.

무서운 점은 사용자가 “허용”을 누른 적이 없다는 겁니다. 예전에 한 번 눌렀던 동의가 재사용됐을 뿐입니다.

처방. 규격은 정적 client_id를 쓰는 MCP 프록시라면 외부 인가 서버로 넘기기 전에, 동적 등록된 클라이언트마다 사용자 동의를 직접 받으라고 MUST로 요구합니다. “[클라이언트 이름]이 [외부 API]에 접근하도록 허용할까요?”라는 내 서버가 소유한 동의 페이지를 한 장 두는 것입니다. 남의 쿠키에 기대지 말고 내 동의를 저장하세요.

6. 진짜 어려운 문제 — 여러 홉을 건너는 위임

여기까지는 “클라이언트 하나 ↔ 서버 하나”였습니다. 그런데 실제 에이전트는 이렇게 생겼습니다.

사람 → 오케스트레이터 에이전트 → 서브 에이전트 → MCP 서버 → 외부 API

홉이 넷입니다. 마지막 API 입장에서 알아야 할 게 두 가지인데, 서로 다릅니다.

  • 누구의 권한으로 하는 일인가 — 사람 A의 데이터에 접근하는 것이므로 A의 권한 범위를 넘으면 안 됩니다.
  • 지금 실제로 두드리고 있는 게 누구인가 — 사람이 직접 누른 게 아니라 서브 에이전트가 자동으로 부른 것입니다. 로그에도 그렇게 남아야 하고, “에이전트에게는 금지”인 동작도 있을 수 있습니다.

OAuth에는 이걸 위한 물건이 이미 있습니다. 토큰 교환(token exchange, RFC 8693)입니다. 이름 그대로 “토큰을 주고 다른 토큰을 받는” 문법이고, 전용 grant type이 하나 정의돼 있습니다.

{{< highlight http >}} POST /token HTTP/1.1 Host: auth.example.com Content-Type: application/x-www-form-urlencoded grant_type=urn:ietf:params:oauth:grant-type:token-exchange &subject_token=<사람 A를 나타내는 토큰> # 누구를 대신하는가 &subject_token_type=urn:ietf:params:oauth:token-type:access_token &actor_token=<에이전트 자신의 토큰> # 지금 실제로 행동하는 주체 &actor_token_type=urn:ietf:params:oauth:token-type:access_token &resource=https://api.example.com # 이 토큰을 쓸 곳 (aud를 좁힘) &scope=invoices:read # 필요한 만큼만 {{< /highlight >}}

두 파라미터의 역할이 정확히 나뉩니다. subject_token은 누구를 대신해, actor_token은 누가 실제로 행동하는지를 나타냅니다. 그리고 여기서 갈리는 두 모드를 구분해야 합니다.

임퍼소네이션(impersonation)위임(delegation)
토큰 모양sub = 사람 A. 끝.sub = 사람 A + act = 에이전트
받는 쪽이 보는 것“사람 A가 직접 했다”“에이전트가 사람 A를 대신했다”
에이전트에 권할까?❌ — 로그에서 사람과 봇이 구분되지 않습니다✅ — 기본값으로 삼으세요

위임을 요청하려면 subject_token과 actor_token을 둘 다 보내야 합니다. 하나만 보내면 위임이 아니라 임퍼소네이션이 됩니다. 결과로 받는 JWT에는 act(actor) 클레임이 붙는데, 여기에 “지금 행동하는 주체”가 들어갑니다. 대략 이런 모양입니다.

{{< highlight json >}} { "iss": "https://auth.example.com", "aud": "https://api.example.com", // 이 토큰을 쓸 곳 하나 "sub": "user:a@example.com", // 권한의 주인 = 사람 A "scope": "invoices:read", // 이 홉에 필요한 만큼만 "exp": 1786000000, // 짧게 // 지금 실제로 행동하는 주체. 중첩하면 위임 경로가 됩니다. "act": { "sub": "agent:invoice-bot", "act": { "sub": "agent:orchestrator" } } } {{< /highlight >}}

act 안에 act를 중첩해서 “오케스트레이터가 시켰고, 청구서 봇이 실행했고, 원래 주인은 A”라는 경로를 표현합니다. 여기서 초보자가 반드시 알아야 할 함정이 하나 있습니다.

중첩된 act는 “참고용”입니다. RFC 8693은 토큰을 받는 쪽이 최상위 클레임과 현재 행위자만 판단 근거로 삼도록 규정합니다. 그 안쪽의 이전 행위자들은 정보 제공용일 뿐이라 접근 제어 판단에 쓸 수 없습니다. 게다가 act 체인은 각 홉의 신원만 담을 뿐, 홉마다 어떤 제약이 걸렸는지는 담지 않습니다. “act 체인만 보면 되겠네”라고 생각했다면 지금 고쳐 두세요.

바로 이 빈틈 때문에 IETF에서 actor chain 초안이 논의되고 있습니다. 위임 경로를 홉을 넘어가며 암호학적으로 검증 가능하게 유지하는 프로파일을 정의하는 작업이고, 서비스 메시·API 게이트웨이·CI/CD 파이프라인처럼 “누가, 어떤 순서로, 누구의 권한으로 행동했는가”가 정확성 요건인 곳을 함께 겨냥합니다. 표준이 아직 굳지 않았다는 뜻이기도 하니, 지금 만드는 시스템에서는 감사 로그를 별도로 남기는 쪽이 안전합니다.

7. 실전 — 오늘 붙일 수 있는 코드와 체크리스트

7-1. MCP 서버: 토큰 검증 미들웨어

가장 먼저 넣어야 할 코드입니다. 규격이 요구하는 “내 것으로 발급된 토큰인가”를 확인합니다. 라이브러리 없이 뼈대만 보면 이렇습니다.

{{< highlight python >}} import time, jwt # PyJWT from fastapi import Request, HTTPException MY_RESOURCE = "https://mcp.example.com/mcp" # 이 서버의 canonical URI ISSUER = "https://auth.example.com" def verify(request: Request) -> dict: auth = request.headers.get("Authorization", "") if not auth.startswith("Bearer "): # 401에 '어디서 인가 정보를 찾을지'와 '필요한 스코프'를 같이 알려 줍니다 raise HTTPException(401, headers={ "WWW-Authenticate": f'Bearer resource_metadata=' f'"{MY_RESOURCE}/.well-known/oauth-protected-resource", ' f'scope="files:read"' }) claims = jwt.decode( auth[7:], key=jwks_key_for(auth[7:]), # 인가 서버 JWKS에서 서명 키 조회 algorithms=["RS256"], issuer=ISSUER, audience=MY_RESOURCE, # ★ 핵심: aud가 '나'인지 검증 (MUST) ) # 스코프는 별도로 확인해야 합니다. 토큰이 유효한 것과 # 이 작업을 할 권한이 있는 것은 다른 이야기입니다. if "files:read" not in claims.get("scope", "").split(): raise HTTPException(403, "insufficient_scope") return claims {{< /highlight >}}
왜 audience=를 꼭 넘겨야 하나요? 대부분의 JWT 라이브러리는 audience 인자를 주지 않으면 aud 검증을 아예 건너뜁니다. 서명도 맞고 만료도 안 됐으니 jwt.decode()는 조용히 성공합니다. 남의 서비스용 토큰이 통과하는 사고 대부분이 이 한 줄 누락에서 나옵니다.

7-2. 상류 API를 부를 때: 토큰을 넘기지 말고 바꾸기

앞서 금지된 패스스루 대신 이렇게 씁니다. 받은 토큰을 재료로만 쓰고, 실제로 나가는 건 새 토큰입니다.

{{< highlight python >}} TOKEN_EXCHANGE = "urn:ietf:params:oauth:grant-type:token-exchange" ACCESS_TOKEN = "urn:ietf:params:oauth:token-type:access_token" async def exchange_for_upstream(user_token: str, upstream: str, scope: str) -> str: """사용자 토큰 → 상류 API 전용 토큰. 이 서버가 actor로 기록됩니다.""" r = await http.post(f"{ISSUER}/token", data={ "grant_type": TOKEN_EXCHANGE, "subject_token": user_token, # 누구를 대신하는가 "subject_token_type": ACCESS_TOKEN, "actor_token": await my_own_token(),# 지금 행동하는 주체 = 이 MCP 서버 "actor_token_type": ACCESS_TOKEN, "resource": upstream, # aud를 상류 API 하나로 좁힘 "scope": scope, # 이 호출에 필요한 만큼만 }) r.raise_for_status() return r.json()["access_token"] # 사용 claims = verify(request) # ① 내 것인지 먼저 검증 up_tok = await exchange_for_upstream( # ② 상류용으로 교환 raw_token, "https://api.github.com", "repo:read") await http.get("https://api.github.com/user/repos", headers={"Authorization": f"Bearer {up_tok}"}) # ③ 새 토큰으로 호출 {{< /highlight >}}
인가 서버가 token exchange를 지원하지 않는다면? 흔한 상황입니다. 그럴 땐 MCP 서버가 상류 API에 대해 독립된 OAuth 클라이언트로서 별도 인가 플로를 돌려 토큰을 따로 받아 두면 됩니다. 규격이 요구하는 건 “교환을 쓰라”가 아니라 “받은 토큰을 그대로 재사용하지 마라”입니다. 방법은 둘 중 아무거나 좋습니다.

7-3. 에이전트 자신의 신원 만들기

여기까지 오면 자연스럽게 질문이 생깁니다. “actor_token, 그러니까 에이전트 자신의 토큰은 어디서 나오나요?”

여기가 바로 표준이 아직 덜 채운 자리입니다. 실제로 MCP 인가 규격 전문을 훑어보면 “agent”라는 단어는 user-agent(브라우저) 말고는 나오지 않고, token exchange 이야기도 없습니다. 규격이 답하는 질문은 “이 토큰은 어느 리소스용인가”까지고, “지금 행동하는 에이전트는 누구인가”는 각자 구현할 몫으로 남아 있습니다.

실무에서 자리 잡아 가는 답은 “에이전트를 사람 계정도, 공용 서비스 계정도 아닌 별도의 1급 신원으로 만든다”입니다. Microsoft Entra Agent ID가 대표적인데(2026년 상반기 GA), 에이전트마다 고유한 디렉터리 신원을 부여하고 OAuth on-behalf-of 흐름을 확장해 사용자를 sub로 유지한 채 에이전트를 별도 클레임으로 얹는 방식입니다. 방금 본 sub + act 구조와 정확히 같은 그림입니다.

직접 만든다면 최소 요건은 이렇습니다.

  • 인스턴스 단위로 발급하세요. “배포 하나 = 신원 하나”가 아니라 “역할 하나 = 신원 하나”가 좋습니다. 코드 리뷰 봇과 배포 봇이 같은 신원을 쓰면 구분할 수 없습니다.
  • 수명을 짧게 하세요. 오래 사는 비밀은 언젠가 로그·프롬프트·이슈 코멘트로 샙니다. 규격도 “인가 서버는 짧은 수명의 액세스 토큰을 발급해야 한다(SHOULD)”고 권합니다.
  • 사람의 권한을 상한으로 두세요. 에이전트의 실효 권한 = (사람의 권한) ∩ (에이전트에게 허용된 범위). 교집합이지 합집합이 아닙니다.

7-4. 체크리스트

단계확인할 것
서버 진입aud가 내 canonical URI인지 검증했는가 (라이브러리에 audience 인자를 넘겼는가)
서버 진입iss가 기대한 인가 서버인지, 서명 키를 JWKS에서 가져오는지

8. 흔한 실수 · 팁

실수 1 — aud 검증을 “나중에” 미룬다. 개발 초기엔 토큰이 하나뿐이라 아무 문제가 없습니다. 문제는 두 번째 MCP 서버를 붙이는 날 생기는데, 그때는 이미 여러 서비스가 서로의 토큰을 받아 주는 상태입니다. 서버가 하나일 때 넣어 두는 게 제일 쌉니다.

실수 2 — 스코프를 “일단 넉넉히” 받아 둔다. 나중에 401이 뜨는 게 귀찮아서 repo 전체를 받아 놓는 식입니다. 새 규격은 반대 방향을 권합니다 — 서버가 401의 WWW-Authenticate에 필요한 스코프를 적어 주고, 클라이언트는 부족할 때마다 단계적으로 올려 받는(step-up) 구조입니다. 프롬프트 인젝션이 성공했을 때 피해 범위를 결정하는 건 결국 토큰에 붙은 스코프입니다.

실수 3 — 위임 대신 임퍼소네이션을 쓴다. actor_token 없이 subject_token만 보내면 “사람 A가 직접 한 일”로 기록됩니다. 편하지만 그 순간 로그에서 사람과 봇을 영영 구분할 수 없게 됩니다. 기본값은 위임으로 두세요.

실수 4 — 중첩된 act로 접근 제어를 한다. “오케스트레이터가 부른 거니까 허용” 같은 판단은 규격상 하면 안 됩니다. 최상위 클레임과 현재 행위자만 판단 근거입니다. 체인 전체를 판단에 쓰고 싶다면 별도 설계(또는 진행 중인 actor chain 프로파일)가 필요합니다.

실수 5 — 메타데이터 URL을 검증 없이 따라간다. 401의 resource_metadata는 서버가 준 값입니다. 악의적인 MCP 서버가 http://169.254.169.254/(클라우드 메타데이터 엔드포인트) 같은 주소를 넣어 두면 클라이언트가 대신 찔러 주는 SSRF가 됩니다. 규격이 이 위험을 따로 다루는 이유입니다 — HTTPS 강제, 사설 IP 차단, 리다이렉트 제한을 걸어 두세요.

팁 — 감사 로그에 두 개의 ID를 남기세요. actor=agent:invoice-bot과 on_behalf_of=user:a@example.com을 같은 줄에 남기면, 나중에 “누가 시켰나”와 “무엇이 실행했나”를 각각 필터링할 수 있습니다. 토큰 클레임에만 의존하지 말고 애플리케이션 로그에 직접 남기는 편이 낫습니다. 토큰은 만료되지만 로그는 남으니까요.

팁 — 로컬(stdio) MCP 서버는 이 규격을 따르지 않습니다. 규격은 stdio 전송을 쓰는 구현이라면 이 인가 흐름을 따르지 말고(SHOULD NOT) 환경에서 자격 증명을 가져오라고 명시합니다. 내 노트북에서 도는 서버에 OAuth를 붙이느라 시간을 쓸 필요는 없습니다. 이 글의 내용은 HTTP로 노출되는 순간부터 필요한 이야기입니다.

9. 마무리 (TL;DR)

  • 에이전트 인증의 질문은 “토큰이 유효한가”가 아니라 “이 토큰은 어디에 쓰라고 준 것인가”입니다. 답을 담는 자리가 aud(오디언스)이고, 좁히는 도구가 resource 파라미터(RFC 8707)입니다.
  • 토큰 패스스루는 MCP 규격이 MUST NOT으로 금지합니다. 받은 토큰을 상류로 그대로 넘기면 보안 통제가 무력해지고, 감사 추적이 끊기고, 한 곳 유출이 전부 유출이 됩니다.
  • 2026-07-28 규격의 최소선 다섯 줄 — 서버는 RFC 9728 메타데이터 제공(MUST), 클라이언트는 resource 항상 전송(MUST), 서버는 aud 검증(MUST), 토큰 패스스루 금지(MUST NOT), PKCE 미지원이면 진행 거부(MUST). 클라이언트 등록은 Client ID Metadata Documents 중심으로 옮겨 갔고 DCR은 deprecated입니다.
  • 정적 client_id를 쓰는 MCP 프록시는 클라이언트별 동의를 직접 받으세요. 안 그러면 예전 동의 쿠키를 재사용해 동의 화면을 건너뛰는 confused deputy 공격이 성립합니다.
  • 여러 홉을 건널 땐 토큰을 넘기지 말고 교환하세요. RFC 8693 token exchange에서 subject_token(누구를 대신해)과 actor_token(누가 행동하는지)을 둘 다 보내면 sub + act 구조의 위임 토큰을 받습니다. 임퍼소네이션은 기본값으로 삼지 마세요.
  • 단, 중첩된 act는 정보 제공용입니다. 접근 제어에 쓸 수 있는 건 최상위 클레임과 현재 행위자까지입니다. 검증 가능한 위임 체인은 IETF에서 지금 만들고 있는 중이니, 그전까지는 감사 로그를 따로 남기는 게 답입니다.
  • 권한은 내려갈수록 좁아지고, 책임 표시는 내려갈수록 쌓여야 합니다. 이 두 방향이 반대라는 점만 기억해도 설계의 절반은 맞습니다.
