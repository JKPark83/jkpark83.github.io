1. 도입 — 재난 대비 앱이 AI 엔지니어링 교과서였다

정전이 됐습니다. 와이파이도, 모바일 데이터도 없습니다. 냉장고 속 음식은 언제까지 안전할까요? 화상은 어떻게 처치해야 할까요? 평소라면 ChatGPT에 물어보면 그만이지만, 클라우드 AI는 인터넷과 함께 사라집니다. 지난주 Hacker News 프런트 페이지에 오른 Survival LLM은 정확히 이 상황을 위해 만들어진 앱입니다. 로컬 AI 모델과 약 150만 건의 오프라인 문서(의료·응급처치·생존 매뉴얼·위키백과)를 내 컴퓨터에 전부 담아 두고, 인터넷 없이 질문에 답합니다.

개발자가 X에 올린 소개가 퍼지고, 10월 28일 Hacker News 토론이 500포인트 가까이 오르고, GIGAZINE과 Tom's Guide까지 보도가 이어졌습니다. 10월 24일에 공개된 GitHub 저장소는 일주일 만에 별 1,200개를 넘겼습니다.

그런데 이 글은 재난 대비 이야기가 아닙니다. Survival LLM이 흥미로운 진짜 이유는, AI 엔지니어링의 거의 모든 주제가 극한 제약 아래에서 작게 압축돼 있고 그 코드와 평가 결과가 전부 공개돼 있기 때문입니다. 외부 API 없음, GPU 클러스터 없음, 벡터 DB 없음, 그런데도 검색 증강 생성(RAG), 에이전틱 도구 호출, 하드웨어별 모델 선택, LLM 저지 평가, 인용 검증까지 다 들어 있습니다. 클라우드라는 안전망을 빼면 RAG 시스템에서 무엇이 본질인지가 선명하게 드러납니다. 하나씩 뜯어 보겠습니다.

2. 배경 — 로컬 LLM과 RAG 3분 요약

따라오는 데 필요한 개념은 두 가지뿐입니다.

① 로컬 LLM. 모델 가중치를 내 컴퓨터에 내려받아 CPU/GPU로 직접 돌리는 방식입니다. 가장 널리 쓰이는 실행기가 Ollama인데, ollama run llama3 한 줄로 모델을 받고 실행하며, OpenAI API와 비슷한 로컬 HTTP API를 열어 줍니다. 핵심 제약은 메모리입니다. 모델이 통째로 RAM(또는 VRAM)에 들어가야 하므로, 양자화(quantization, 가중치를 4비트 등 저정밀로 압축)와 MoE(mixture-of-experts, 토큰마다 일부 파라미터만 활성화) 같은 기법이 로컬 실행의 열쇠가 됩니다.

② RAG(retrieval-augmented generation, 검색 증강 생성). 모델이 기억에 의존해 답을 지어내는 대신, 먼저 문서를 검색해서 찾아 읽고, 읽은 내용을 근거로 답하게 하는 패턴입니다. 도서관 사서에 비유하면, 사서가 아무리 박식해도 의학 질문에는 기억 대신 의학 서가에서 책을 꺼내 확인하고 답하는 쪽이 안전합니다. 많은 RAG 입문 자료가 "문서를 임베딩(embedding, 텍스트를 의미 벡터로 변환)해서 벡터 DB에 넣는다"부터 시작하지만, 곧 보듯 임베딩은 RAG의 필수 요소가 아닙니다.

3. 해부 ① — 전체 아키텍처: 모델이 검색을 '도구'로 쥔다

Survival LLM의 구조는 README의 다이어그램 한 줄로 요약됩니다. 질문이 들어오면 로컬 모델(Ollama)이 search_library, read_article, show_article 세 개의 도구를 호출하면서 SQLite 전문(全文) 인덱스를 검색하고, 찾은 passage를 읽고, 출처를 달아 답합니다. 서버는 127.0.0.1에만 바인딩되어 바깥으로 아무것도 나가지 않습니다.

주목할 설계 선택이 세 가지 있습니다.

첫째, 파이프라인 RAG가 아니라 에이전틱 RAG입니다. 고전적인 RAG는 "질문 → 검색 1회 → 상위 k개를 프롬프트에 붙임 → 생성"의 고정 파이프라인입니다. Survival LLM은 검색을 도구로 노출해서 모델이 몇 번, 어떤 질의로 검색할지 스스로 결정하게 합니다. "발전기를 집 안에서 돌려도 되나요?" 같은 질문이면 모델이 '발전기 환기', '일산화탄소'처럼 질의를 바꿔 가며 여러 번 검색하고, 모자라면 read_article로 원문 전체를 읽습니다.

둘째, 하드웨어에 맞춰 모델을 고릅니다. 설치할 때 앱이 메모리를 보고 모델을 제안합니다. 128GB 이상 Mac이면 NVIDIA Nemotron 3.5 Super(120B-A12B, NVFP4 양자화, 80GB), 32~96GB Mac이면 Qwen3.8 27B, 32GB 이상 Windows면 Nemotron 3.5 Lightning(30B-A3B), 16GB대면 IBM Granite 4.2 8B. 재미있는 건 8GB 컴퓨터에는 어떤 모델도 제안하지 않는다는 점입니다. 테스트해 보니 그 크기에서 안전 기준을 통과한 모델이 없었기 때문인데, 대신 라이브러리 검색 기능은 그대로 쓸 수 있습니다. "모델이 못 미더우면 검색만 남긴다"는 우아한 강등(graceful degradation)입니다.

셋째, 의존성이 거의 없습니다. Ollama(추론), pywebview(창), pypdf(PDF 읽기) 정도를 빼면 전부 Python 표준 라이브러리입니다. LangChain도, 벡터 DB도, 임베딩 모델도 없습니다. 재난 대비용이라는 특성상 "10년 뒤에도 돌아가야 한다"는 요구가 의존성 다이어트를 강제한 셈인데, 결과적으로 일반적인 RAG 시스템에도 좋은 질문을 던집니다. 그 의존성, 정말 필요한가요?

4. 해부 ② — 벡터 DB 없는 검색: SQLite FTS5 + BM25

검색 레이어가 이 앱에서 가장 교육적인 부분입니다. 임베딩 기반 벡터 검색 대신 SQLite의 FTS5(full-text search, 전문 검색 확장)를 씁니다. 문서를 약 1,500자 단위 passage로 잘라 인덱싱하고, 질의가 오면 BM25(단어 빈도 기반의 고전 랭킹 알고리즘)로 순위를 매기고, Ready.gov나 CDC 같은 공식 소스에는 가중치를 더 줍니다.

왜 임베딩을 안 썼을까요? 오프라인 제약에서 따져 보면 합리적입니다.

  • 임베딩도 모델입니다. 150만 문서를 임베딩하려면 임베딩 모델을 함께 배포하고, 질의 때마다 돌려야 합니다. 디스크·메모리·복잡도가 전부 늘어납니다.
  • 이 도메인에서는 키워드가 강합니다. "일산화탄소", "지혈대", "보툴리눔" 같은 질문은 용어가 명확해서 BM25가 이미 잘 맞춥니다. 의미 검색의 이득이 큰 건 표현이 다양하고 모호한 질의인데, 그 간극은 모델이 질의를 바꿔 가며 재검색하는 것으로 상당 부분 메워집니다. 에이전틱 루프가 임베딩의 대체재 역할을 하는 겁니다.
  • SQLite는 어디에나 있습니다. 파일 하나, 서버 없음, Python 표준 라이브러리로 접근 가능. 운영할 것이 없습니다.
벡터 검색이 틀렸다는 말이 아닙니다. 이 블로그의 2단계 검색(리랭킹) 글에서 다뤘듯 대규모 시맨틱 검색에는 임베딩+리랭커가 정석입니다. 교훈은 "검색 품질 요구와 운영 제약을 먼저 따지고, 가장 단순한 도구부터 검토하라"는 순서입니다. BM25는 여전히 많은 도메인에서 깜짝 놀랄 만큼 강한 베이스라인입니다.

FTS5 인덱스는 이렇게 만듭니다. 외부 패키지가 하나도 필요 없습니다.

{{< highlight python >}} import sqlite3 db = sqlite3.connect("index.sqlite") # porter: 영어 어간 처리. unicode61이 기본 토크나이저로 함께 동작 db.execute(""" CREATE VIRTUAL TABLE passages USING fts5( title, body, source, -- 검색 대상 컬럼 tokenize = 'porter unicode61' )""") db.executemany( "INSERT INTO passages VALUES (?, ?, ?)", [("Food safety in a power outage", "A refrigerator keeps food safe for about 4 hours if unopened...", "ready.gov"), # ... 문서를 ~1,500자 passage로 잘라 전부 삽입 ... ]) # bm25()는 점수가 낮을수록 관련성이 높음 → ORDER BY rank가 곧 BM25 순 rows = db.execute(""" SELECT title, source, snippet(passages, 1, '[', ']', '…', 20) FROM passages WHERE passages MATCH ? ORDER BY rank LIMIT 5 """, ("refrigerator power outage",)).fetchall() {{< /highlight >}}

실제 코드(library/search.py)는 여기에 공식 소스 가중치를 더한 정도입니다. 150만 문서 규모에서도 FTS5는 수십 밀리초 안에 응답합니다. 참고로 FTS5는 한국어처럼 띄어쓰기만으로 단어 경계를 못 가르는 언어에는 기본 토크나이저가 약하므로, 한국어 문서를 다룬다면 형태소 분석 기반 커스텀 토크나이저나 n-gram(trigram) 토크나이저를 검토해야 합니다.

5. 해부 ③ — 평가가 제품을 만들었다: 블라인드 LLM 저지

이 앱의 README에서 가장 긴 섹션은 기능 소개가 아니라 평가 결과입니다. 그리고 그 평가가 제품의 모양을 직접 바꿨습니다.

방법은 이렇습니다. 정전·응급처치 관련 22개 질문(음식 안전, 발전기, 일산화탄소, 저체온증, 출혈, 화상, 인슐린 보관, 끊어진 전선, 보툴리눔 등)을 실제 앱 환경 그대로 — 프롬프트, 도구, 라이브러리 검색 포함 — 각 모델에게 풀게 합니다. 그다음 LLM 저지(LLM-as-a-judge, AI가 답안을 채점) 셋이 모델 이름을 가리고 순서를 섞은 블라인드 상태에서, USDA·CDC·FEMA·EPA·NHS·WHO·적십자의 공식 지침과 대조해 채점합니다. 저지 하나는 정확성, 하나는 안전성을 보고, 세 번째 '회의론자' 저지가 유해 판정을 받은 답을 전부 재검증합니다. 채점 스크립트와 답안이 저장소의 evals/에 그대로 들어 있어 재현할 수 있습니다.

이 평가에서 배울 점은 수치보다 평가 결과가 제품 결정으로 이어진 경로입니다.

  • 탈락 기준은 평균이 아니라 최악의 답. Granite 4.2 3B는 8GB 컴퓨터용으로 계획됐지만, "팔에는 지혈대를 쓰지 말라", "끊어진 전선에서 3피트(약 1m)만 떨어지라"(공식 지침은 35피트)라고 답해 제외됐습니다. 정확도 44%여서가 아니라, 따라 하면 사람이 죽을 수 있는 답이 5개여서입니다.
  • 평가가 기능을 낳았습니다. Qwen 3.6이 한 질문에서 94분 동안 같은 말을 반복하다 멈추지 않았고, 그래서 앱에 답변 길이 제한 기능이 생겼습니다. 여러 모델이 검색만 반복하다 답을 못 내는 패턴을 보여서, "읽은 것으로 답하라"는 규칙이 프롬프트에 추가됐습니다. "차나 발전기를 집 근처에서 돌려야만 한다면…" 식의 위험한 예외 조항을 모델들이 덧붙이는 걸 보고, 프롬프트에서 그 예외를 금지했습니다.
  • 풀 시스템 평가. 모델 단독 벤치마크가 아니라 앱의 프롬프트·도구·라이브러리를 전부 태운 상태로 측정했습니다. 사용자가 겪는 건 모델이 아니라 시스템이니까요. 이 관점은 허메틱 에이전트 평가 글에서 다룬 것과 같은 결입니다.
README는 평가의 한계도 명시합니다. 테스트가 이전 버전 라이브러리에서 돌았고, 일부 답안은 공개 다운로드에 없는 자료를 읽었으며, 그 후 프롬프트에 규칙이 추가됐다는 것까지요. "이 표는 모델 간 비교이지, 당신이 받을 버전의 보증이 아니다"라고 직접 적어 뒀습니다. 평가 수치를 공개할 때는 측정 조건과 한계를 함께 공개해야 한다는 모범 사례입니다.

6. 해부 ④ — 모델이 지어낸 인용을 앱이 잡는다

이 앱의 간판 기능은 "모든 답에 출처를 단다"입니다. 그런데 출처 표기를 모델에게 맡기면 어떻게 될까요? 개발자가 14개 질문으로 따로 측정(evals/citation_check.py, 2026-10-24)해 보니, 모든 모델이 자기가 읽지도 않은 소스를 인용했습니다. 가장 똑똑한 Nemotron Super가 오히려 최다인 6건이었는데, 패턴이 흥미롭습니다. 똑똑한 모델일수록 검색 없이 기억으로 답할 수 있고, 그럴듯한 기관명(Ready.gov, CDC)을 출처 칸에 채워 넣는 겁니다. 답은 맞는데 출처가 조작된 상태죠.

해결책이 교과서적입니다. 앱은 모델이 이번 턴에 어떤 문서를 검색 결과로 봤고 어떤 문서를 열어 읽었는지를 어차피 전부 알고 있습니다(도구 호출을 앱이 실행하니까요). 그래서 답변 끝의 "Sources:" 라인을 이 기록과 대조해서, 목록에 없는 소스가 적혀 있으면 그 라인을 실제로 읽은 문서 목록으로 교체합니다. 모델의 주장(확률적)을 하네스의 기록(결정적)으로 덮어쓰는 구조입니다.

이 패턴은 범용입니다. LLM 시스템에서 "모델이 보고하는 자기 행동"은 신뢰할 수 있는 데이터가 아닙니다. 어떤 파일을 읽었는지, 어떤 API를 호출했는지, 어떤 근거를 참조했는지는 하네스가 이미 알고 있는 사실이므로, 사용자에게 보여 줄 때는 모델의 말이 아니라 하네스의 로그에서 가져와야 합니다. 이 블로그의 검증기 엔지니어링 글에서 다룬 "생성과 검증의 분리"가 인용이라는 작은 영역에 적용된 사례입니다.

7. 실전 — 미니 오프라인 RAG를 직접 만들어 보기

Survival LLM의 뼈대를 60줄짜리 장난감으로 재현해 보겠습니다. 필요한 건 ollama(앱 + pip install ollama)와 Python뿐입니다. 4절에서 만든 index.sqlite를 그대로 쓴다고 가정합니다.

{{< highlight python >}} import json, sqlite3, ollama db = sqlite3.connect("index.sqlite") opened = [] # 하네스가 기록하는 '실제 열람' 로그 def search_library(query: str) -> str: rows = db.execute(""" SELECT rowid, title, source, snippet(passages, 1, '', '', '…', 40) FROM passages WHERE passages MATCH ? ORDER BY rank LIMIT 5""", (query,)).fetchall() opened.extend((r[1], r[2]) for r in rows) # 검색 결과도 '본 것'으로 기록 return json.dumps([ {"id": r[0], "title": r[1], "source": r[2], "snippet": r[3]} for r in rows], ensure_ascii=False) TOOLS = [{ "type": "function", "function": { "name": "search_library", "description": "오프라인 라이브러리를 전문 검색한다. 영어 키워드로 질의.", "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}, }, }] SYSTEM = ("You answer ONLY from library passages you retrieved this turn. " "Search before answering; if results are thin, search again with " "different keywords, then answer from what you read. " "End with a 'Sources:' line.") messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": "정전 때 냉장고 음식은 몇 시간 안전해?"}] for _ in range(6): # 루프 가드: 최대 6턴 (94분 반복 방지!) r = ollama.chat(model="granite4.2:8b", messages=messages, tools=TOOLS) messages.append(r.message) if not r.message.tool_calls: break # 도구 호출이 없으면 최종 답변 for tc in r.message.tool_calls: # 모델이 요청한 검색을 하네스가 실행 result = search_library(**tc.function.arguments) messages.append({"role": "tool", "content": result, "tool_name": tc.function.name}) answer = r.message.content # 인용 검증: 모델의 Sources 라인을 하네스 기록으로 교체 seen = ", ".join(sorted({f"{t} ({s})" for t, s in opened})) or "(없음)" body = answer.split("Sources:")[0].rstrip() print(f"{body}\n\nSources: {seen}") {{< /highlight >}}

장난감이지만 Survival LLM의 핵심 요소가 전부 들어 있습니다. 도구로서의 검색, "읽은 것으로만 답하라"는 프롬프트 규칙, 루프 상한(runaway 방지), 그리고 마지막의 인용 교체. 여기서 라이브러리를 키우고(앱은 Kiwix의 ZIM 아카이브와 정부 매뉴얼 PDF를 플레인 텍스트로 변환해 씁니다), 평가 하네스를 붙이면 구조적으로는 같은 시스템이 됩니다.

8. 흔한 실수 · 팁

  • RAG = 벡터 DB라고 단정하기. 요구사항을 보기 전에 임베딩 파이프라인부터 세우는 경우가 많습니다. 용어가 명확한 도메인 + 에이전틱 재검색 조합이면 BM25(FTS5)로 충분할 수 있고, 운영 부담은 몇 분의 일입니다. 벡터 검색은 "BM25로 안 되는 질의가 실제로 얼마나 되는지" 측정한 뒤에 추가해도 늦지 않습니다.
  • 모델이 쓴 "Sources:"를 그대로 내보내기. 위에서 봤듯 최상위 모델도 14문항 중 6문항에서 안 읽은 소스를 인용했습니다. 출처·행동 보고는 반드시 하네스의 도구 호출 로그와 대조하세요. 대조가 어렵다면 최소한 "모델이 주장한 출처"라고 표시해야 합니다.
  • 작은 모델의 실패를 '품질 저하'로만 생각하기. 작은 모델은 조금 덜 정확한 게 아니라, 치명적으로 틀린 답을 자신 있게 냅니다(지혈대 금지, 전선 1m 거리). 안전이 걸린 도메인이라면 정확도 평균이 아니라 유해 답변 수를 채택 기준으로 삼고, 기준 미달이면 Survival LLM처럼 생성 기능을 아예 빼는 것도 설계입니다.
  • 루프 가드 없이 에이전틱 루프 돌리기. 검색만 반복하며 답을 안 내는 모델, 94분간 같은 말을 반복하는 모델은 평가에서 실제로 관찰된 사건입니다. 턴 수 상한, 출력 길이 상한, "지금까지 읽은 것으로 답하라" 폴백은 로컬이든 클라우드든 에이전트 루프의 기본 안전장치입니다.
  • 평가를 모델 단독으로 돌리기. 프롬프트·도구·데이터를 뺀 벤치마크 점수는 사용자 경험을 예측하지 못합니다. 시스템 전체를 태운 평가 + 블라인드 채점 + 유해 판정 재검증(회의론자 저지)이라는 이 앱의 3단 구성은 규모와 무관하게 베낄 가치가 있습니다.

9. 마무리 (TL;DR)

  • 지난주 HN을 달군 Survival LLM은 재난 대비용 오프라인 AI 비서입니다. 로컬 모델(Ollama) + 약 150만 문서 라이브러리 + 출처 표시를 전부 내 컴퓨터 안에서 해결하고, 코드(MIT)와 평가가 공개돼 있습니다.
  • 검색은 임베딩·벡터 DB 없이 SQLite FTS5 + BM25(~1,500자 passage, 공식 소스 가중치)로 해결했습니다. 모델이 질의를 바꿔 가며 재검색하는 에이전틱 루프가 의미 검색의 간극을 메웁니다.
  • 모델은 RAM에 맞춰 선택합니다(128GB Mac → Nemotron 3.5 Super부터 16GB → Granite 4.2 8B까지). 안전 기준을 통과한 모델이 없는 8GB에는 생성 기능을 아예 주지 않습니다.
  • 22문항 블라인드 LLM 저지 평가(정확성·안전성·회의론자)가 모델 채택을 갈랐고, 기능(길이 제한)과 프롬프트 규칙("읽은 것으로 답하라")을 낳았습니다. 탈락 기준은 평균 정확도가 아니라 치명적 답변 수였습니다.
  • 모든 모델이 읽지 않은 소스를 인용했기 때문에(최상위 모델이 14문항 중 6문항으로 최다), 앱이 Sources 라인을 실제 도구 호출 기록과 대조해 교체합니다. 모델의 자기 보고는 하네스의 로그로 검증한다 — 이 글의 가장 범용적인 교훈입니다.
  • 극한 제약(오프라인·무의존성)은 RAG의 본질을 드러냅니다. 검색은 요구에 맞는 가장 단순한 도구로, 신뢰는 검증 레이어로, 품질은 시스템 전체 평가로.
