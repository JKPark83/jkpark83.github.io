1. 도입 — 이번 주에 에이전트가 옮겨 간 자리

PR을 올리고 커피를 타러 갔다가 돌아왔더니 CI가 빨갛습니다. 로그를 엽니다. 5,000줄입니다. 스크롤을 내리다가 Timeout after 30000ms를 발견하고, 잠시 고민하다가, 그냥 Re-run jobs를 누릅니다. 초록불이 뜹니다. 방금 그게 진짜 버그였는지 아닌지는 아무도 모릅니다.

이 장면이 하루에 몇 번씩 반복되는 게 대부분 팀의 현실입니다. 그런데 이번 주(8월 셋째 주), 이 자리에 에이전트를 앉히겠다는 소식이 이상하리만치 같은 날에 몰렸습니다.

8월 18일, Anthropic은 “Claude on call: How Claude Tag serves as Anthropic's first responder for CI/CD failures”를 공개했습니다. 사내 CI/CD 실패의 1차 대응자(first responder)로 Slack에 붙은 에이전트를 쓰고 있다는 내용입니다. 핵심 구조는 단순합니다. 실패가 감지되면 에이전트가 Slack 채널에서 원인을 좁히고, 필요하면 수정을 작성하되, 그 수정은 사람이 리뷰하는 pull request로 나갑니다. 프로덕션에 바로 나가지 않습니다.

같은 날, Warp는 Warp Factories를 closed beta로 열었습니다. 티켓 하나를 트리아지 → 스펙 → 구현 → 리뷰 → 검증 → 모니터링 단계로 흘려보내는 파이프라인인데, 파이프라인 자체가 버전 관리되는 설정 파일로 정의되고 단계마다 모델과 하네스를 따로 고르며, 팀이 정한 지점에서 사람이 승인합니다.

두 소식이 가리키는 방향은 같습니다. 에이전트가 “코드를 쓰는 쪽”에서 “빨간 빌드를 받는 쪽”으로 옮겨 오고 있습니다. 그리고 이건 junior 개발자에게 유난히 좋은 소식이자 유난히 위험한 소식입니다. 좋은 소식인 이유는 CI 1차 대응이 경력과 무관하게 지루하고 반복적인 일이기 때문이고, 위험한 소식인 이유는 이 자동화를 잘못 설계하면 “테스트를 지워서 초록불을 만드는 봇”을 만들게 되기 때문입니다.

이 글에서 얻어 갈 것. ① CI 실패 1차 대응을 다섯 단계로 쪼개는 법, ② 실제로 도는 GitHub Actions 워크플로 두 개, ③ 자유 서술 대신 스키마로 분류를 받아 임계값으로 자동화 수준을 조절하는 법, ④ 로그를 컨텍스트에 욱여넣지 않고 잘라 주는 법, ⑤ 에이전트가 초록불을 위조하지 못하게 막는 가드레일.

2. 배경 — 빨간 빌드의 84%는 진짜 버그가 아니다

본격적으로 설계하기 전에 숫자 하나만 짚고 갑시다. Google이 사내 CI 시스템을 분석한 결과, 통과하던 테스트가 실패로 바뀐 전환(pass → fail transition)의 약 84%에 플래키 테스트(flaky test)가 끼어 있었습니다. 여기서 플래키 테스트란 코드가 바뀌지 않았는데도 어떤 날은 통과하고 어떤 날은 실패하는 테스트를 말합니다. 같은 분석에서 전체 테스트 실행의 약 1.5%가 플래키하게 동작했고, 전체 테스트의 약 16%가 어느 정도 플래키함을 보였습니다.

이 숫자가 1차 대응 설계의 출발점입니다. 빨간 빌드를 보고 가장 먼저 해야 할 일은 “고치기”가 아니라 “이게 진짜인지 가리기”입니다. 이 순서를 뒤집으면 무슨 일이 벌어지는지는 뻔합니다. 에이전트가 플래키 타임아웃을 진짜 버그로 착각하고, 존재하지 않는 race condition을 고치겠다며 코드를 뜯어고치고, 그 PR을 사람이 리뷰하느라 원래보다 시간이 더 듭니다.

사람이 온콜(on-call, 장애 발생 시 1차로 호출되는 당번)을 설 때 실제로 하는 일을 순서대로 적으면 이렇습니다.

이 다섯 단계를 그대로 코드로 옮기는 게 이 글의 목표입니다. 한 번에 다 자동화하려 들지 말고, ①부터 하나씩 붙이면서 각 단계가 만들어 내는 소음을 확인하고 넘어가는 게 좋습니다.

3. 1단계 감지 — 언제, 어디서 깨울 것인가

가장 먼저 정할 건 트리거입니다. 직관적으로는 “테스트 실행 워크플로 안에서 실패하면 바로 에이전트를 부르면 되지 않나?” 싶지만, GitHub Actions에서는 그렇게 하지 않는 게 정석입니다. workflow_run이라는 별도 이벤트를 씁니다.

왜 workflow_run인가. 이 이벤트로 시작된 워크플로는 항상 저장소의 기본 브랜치(default branch) 버전으로 실행되고, 읽기·쓰기 토큰과 secret에 접근할 수 있습니다. 반면 fork에서 올라온 PR로 도는 워크플로는 보호 차원에서 secret을 못 받고 토큰도 읽기 전용입니다. 즉 “PR 브랜치의 코드를 테스트하는 워크플로”와 “그 실패를 받아 처리하는 권한 있는 워크플로”를 분리하는 구조입니다.

Anthropic이 공식 예제로 공개한 ci-failure-auto-fix.yml의 트리거 부분이 딱 이 모양입니다.

{{< highlight yaml >}} on: workflow_run: workflows: ["CI"] # "CI"라는 이름의 워크플로가 끝나면 types: [completed] # 성공/실패 상관없이 일단 이 워크플로가 뜬다 permissions: contents: write # 수정 커밋을 push 하려면 필요 pull-requests: write # PR 생성/코멘트 actions: read # 실패한 run의 로그를 읽으려면 필요 issues: write id-token: write # OIDC 토큰 교환용 jobs: auto-fix: if: | github.event.workflow_run.conclusion == 'failure' && github.event.workflow_run.pull_requests[0] && !startsWith(github.event.workflow_run.head_branch, 'claude-auto-fix-ci-') {{< /highlight >}}

if: 조건 세 줄이 이 워크플로에서 가장 중요한 부분입니다. 하나씩 읽어 봅시다.

  • conclusion == 'failure' — 성공한 run에는 반응하지 않습니다. types: [completed]가 성공까지 잡아 주기 때문에 여기서 걸러 줘야 합니다.
  • pull_requests[0] — PR에 딸린 실패만 처리합니다. 같은 저장소 안의 브랜치에서 올라온 PR만 이 배열이 채워지므로, fork PR은 자연스럽게 제외됩니다.
  • !startsWith(..., 'claude-auto-fix-ci-') — 에이전트가 자기가 만든 브랜치의 실패에 다시 반응하는 걸 막습니다. 이 한 줄이 없으면 무한 루프가 돕니다. 에이전트가 고친다 → 그 브랜치 CI가 또 실패한다 → 에이전트가 또 붙는다 → 토큰이 사라집니다.
이 워크플로는 아무 저장소에나 쓰면 안 됩니다. 공식 예제 파일 맨 위에 보안 주의가 길게 붙어 있는 이유가 있습니다. 이 워크플로는 PR 브랜치를 checkout 하고 npm·bun 같은 빌드·테스트 명령을 secret에 접근 가능하고 저장소에 push 할 수 있는 권한으로 실행합니다. 즉 브랜치를 push 할 수 있는 사람은 누구든 여기서 도는 코드를 정할 수 있습니다. write 권한을 가진 사람 전원을 신뢰할 수 있는 저장소에서만 쓰세요.

참고로 Claude Code GitHub Action은 트리거한 주체도 두 번 검사합니다. issue·PR 이벤트에서는 트리거한 사용자에게 write 권한이 있어야 하고, 모든 이벤트에서 봇 액터는 allowed_bots에 명시하지 않는 한 거부합니다. 봇이 봇을 부르며 도는 루프를 막기 위한 장치입니다.

4. 2단계 분류 — 자유 서술이 아니라 스키마로 받기

이제 핵심입니다. 실패를 받았으면 “진짜인가 플래키인가”를 먼저 갈라야 합니다.

여기서 junior 개발자가 가장 흔히 하는 설계 실수는 프롬프트를 이렇게 쓰는 겁니다. “로그를 보고 플래키한지 판단해서 알려 줘.” 그러면 모델은 문단 세 개짜리 산문을 돌려주고, 워크플로의 다음 스텝은 그걸 파싱할 방법이 없습니다. grep -q "flaky" 같은 걸 붙이는 순간 지옥문이 열립니다.

대신 구조화 출력(structured output)을 씁니다. 모델에게 “이 JSON 스키마를 반드시 만족하는 값만 내라”고 강제하는 기능입니다. Claude Code CLI에서는 --json-schema 플래그가 그 역할을 합니다. 공식 예제 test-failure-analysis.yml이 정확히 이 패턴입니다.

{{< highlight yaml >}} - name: Detect flaky test failures id: detect uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} prompt: | The CI workflow failed: ${{ github.event.workflow_run.html_url }} Check the logs: gh run view ${{ github.event.workflow_run.id }} --log-failed 다음 신호가 있는지 보고 플래키 실패인지 판단할 것: - Timeout errors - Race conditions - Network errors - "Expected X but got Y" 형태의 간헐적 실패 - 직전 커밋에서는 통과했던 테스트 claude_args: | --json-schema '{"type":"object","properties":{ "is_flaky":{"type":"boolean"}, "confidence":{"type":"number","minimum":0,"maximum":1}, "summary":{"type":"string"}}, "required":["is_flaky","confidence","summary"]}' {{< /highlight >}}

이러면 다음 스텝에서 결과를 평범한 값으로 쓸 수 있습니다.

{{< highlight yaml >}} # 플래키로 판단했고, 확신도가 0.7 이상일 때만 자동 재실행 - name: Retry flaky tests if: | fromJSON(steps.detect.outputs.structured_output).is_flaky == true && fromJSON(steps.detect.outputs.structured_output).confidence >= 0.7 env: GH_TOKEN: ${{ github.token }} WORKFLOW_NAME: ${{ github.event.workflow_run.name }} HEAD_BRANCH: ${{ github.event.workflow_run.head_branch }} run: gh workflow run "$WORKFLOW_NAME" --ref "$HEAD_BRANCH" # 플래키 같긴 한데 확신이 약하면 재실행하지 않고 기록만 남김 - name: Low confidence detection if: | fromJSON(steps.detect.outputs.structured_output).is_flaky == true && fromJSON(steps.detect.outputs.structured_output).confidence < 0.7 run: echo "⚠️ 플래키 의심이지만 확신도가 낮아 자동 재실행하지 않습니다" {{< /highlight >}}

confidence가 왜 중요한가. 이 숫자 하나가 자동화 수준을 돌리는 다이얼이 됩니다. 처음 도입할 때는 임계값을 0.9로 잡아 놓고 코멘트만 남기게 하다가, 판단이 실제로 맞는지 2~3주 지켜본 뒤 0.7로 낮추면서 자동 재실행을 켜는 식입니다. 임계값 없이 is_flaky만 보고 재실행하면 모델이 애매할 때 내리는 판단까지 그대로 실행됩니다.

확신도는 모델의 자기 보고입니다. 교정(calibration)이 완벽하다는 보장은 없습니다. 그래서 임계값을 “진실의 경계”가 아니라 “내가 감당할 수 있는 오작동 빈도를 조절하는 손잡이”로 생각하는 게 맞습니다. 실제 값이 맞는지는 며칠간 판단 결과와 최종 결과를 나란히 기록해서 직접 확인해야 합니다.

실무에서는 is_flaky 불리언 하나보다 세 갈래 분류가 더 잘 맞습니다. real_regression(코드가 깼다) / flaky(테스트가 불안정하다) / infra(레지스트리 다운, 러너 디스크 부족, 토큰 만료). 인프라 실패는 재실행해도 대개 또 실패하므로 자동 재시도 대상에서 빼는 게 낫습니다.

5. 3단계 증거 — 로그를 통째로 넣지 마세요

이 단계에서 사고가 제일 많이 납니다. 공식 ci-failure-auto-fix.yml 예제는 실패한 job의 로그를 API로 내려받아 프롬프트에 통째로 붙입니다. 데모로는 훌륭하지만, 로그가 큰 저장소에서 그대로 쓰면 컨텍스트가 순식간에 찹니다.

실패 로그는 대부분 쓸모없는 부분이 99%입니다. 의존성 설치 로그 3,000줄, 통과한 테스트 이름 1,500줄, 그리고 우리가 원하는 스택 트레이스 40줄. 그래서 로그를 넣기 전에 잘라 줘야 합니다.

{{< highlight bash >}} # 실패한 step의 로그만 뽑는다. 전체 로그가 아니라 --log-failed가 핵심. gh run view "$RUN_ID" --log-failed > failed.log # 그중에서도 실패 지점 주변만 남긴다 (앞 5줄 + 뒤 30줄) grep -n -E "FAIL|Error|error:|Exception|assert" failed.log \ | head -20 | cut -d: -f1 \ | while read -r line; do sed -n "$((line>5 ? line-5 : 1)),$((line+30))p" failed.log echo "---" done > evidence.txt # 그래도 크면 상한을 건다 (약 2,000줄) head -2000 evidence.txt > evidence.trimmed.txt {{< /highlight >}}
더 좋은 방법 — 로그를 넘기지 말고 도구를 주세요. 프롬프트에 로그 본문을 붙이는 대신 gh run view --log-failed를 실행할 권한만 주면, 에이전트가 필요한 만큼만 읽어 갑니다. 위의 test-failure-analysis.yml 예제가 바로 그 방식입니다. 프롬프트에는 실행할 명령만 알려 주고, 로그 본문은 넣지 않습니다. “컨텍스트에 미리 밀어 넣기”보다 “필요할 때 가져가게 하기”가 거의 항상 낫습니다.

6. 4단계 조치와 검증 — 재현 없이 고치지 않기

진짜 회귀로 판정됐다면 이제 고칠 차례입니다. 여기서 프롬프트에 반드시 넣어야 하는 규칙이 있습니다. 고치기 전에 실패를 재현하고, 고친 뒤에 같은 검사가 통과하는 걸 보여 줄 것.

왜 이게 필요할까요? 재현 없이 수정하면 에이전트는 “그럴듯한 원인”에 대해 “그럴듯한 수정”을 만듭니다. 로그의 NullPointerException을 보고 널 체크를 하나 추가하는 식입니다. 증상은 사라지지만 원인은 그대로 남습니다. 재현 단계를 강제하면 이 실패 모드가 크게 줄어듭니다.

{{< highlight text >}} # 1차 대응 에이전트 프롬프트 (요지) 역할: CI 실패의 1차 대응자. 목표는 "초록불"이 아니라 "무엇이 왜 빨간지 밝히는 것". 반드시 이 순서로: 1. 실패한 검사를 로컬에서 그대로 재현한다. 재현에 실패하면 거기서 멈추고 보고한다. 2. 원인을 한 문장으로 적는다. 확신이 없으면 "확신 없음"이라고 적는다. 3. 가장 작은 수정을 만든다. 실패와 무관한 파일은 건드리지 않는다. 4. 같은 검사를 다시 돌려 통과를 확인한다. 통과 로그를 PR 본문에 붙인다. 5. PR을 연다. merge 하지 않는다. 절대 하지 말 것: - 테스트를 삭제하거나 skip 처리하기 - 단언(assertion)을 느슨하게 바꾸기 - 테스트 대상 자체를 mock으로 바꿔치기 - 타임아웃을 늘리거나 무조건 재시도를 넣어 증상 가리기 - 실패와 무관한 리팩터링 끼워 넣기 3번에서 필요한 수정이 파일 3개를 넘어가면, 고치지 말고 5단계(인계)로 간다. {{< /highlight >}}

마지막 줄이 실무에서 특히 잘 먹힙니다. “여기까지가 내 범위”를 프롬프트에 숫자로 박아 두는 것입니다. 범위를 정해 주지 않으면 에이전트는 대개 끝까지 시도하고, 그 결과 리뷰하기 어려운 큰 PR이 나옵니다.

비용도 같은 방식으로 묶습니다. Claude Code CLI 기준으로는 이렇습니다.

{{< highlight yaml >}} claude_args: | --max-turns 12 --max-budget-usd 2.00 --allowedTools "Read,Grep,Glob,Edit,Bash(npm test:*),Bash(git:*),Bash(gh:*)" {{< /highlight >}}

--allowedTools에 주목하세요. 에이전트가 쓸 수 있는 명령을 화이트리스트로 못 박습니다. Bash(*)처럼 전부 열어 두면 앞의 프롬프트 규칙은 그냥 부탁일 뿐입니다. 워크플로 레벨에서 timeout-minutes와 concurrency도 같이 거세요. 커밋이 연달아 push 되면 실패도 연달아 나고, 에이전트도 연달아 뜹니다.

7. 5단계 인계 — 못 고칠 때 무엇을 남길 것인가

대부분의 글이 여기서 끝나지만, 사실 1차 대응의 진짜 가치는 “못 고쳤을 때”에 나옵니다. 사람 온콜도 마찬가지입니다. 새벽 3시에 깬 당번이 문제를 못 고쳤어도, 원인 후보 두 개와 관련 로그를 정리해 두면 아침 팀원이 30분 만에 끝냅니다.

에이전트도 똑같이 시켜야 합니다. 인계 코멘트에 들어갈 항목을 고정하세요.

항목왜 필요한가
실패한 검사 이름과 run 링크사람이 로그를 다시 찾는 시간을 없앰
실패 지점 로그 발췌 (20~40줄)PR 화면에서 바로 판단 가능
분류 결과 + 확신도나중에 판단 정확도를 집계할 수 있음
재현 시도 결과 (성공/실패)재현이 안 됐다면 그 자체가 플래키의 강한 증거
이 브랜치에서 같은 실패가 몇 번째인지1회성인지 반복인지 구분
포기한 이유 한 줄“범위 초과” / “재현 불가” / “원인 불명”

Anthropic이 8월 18일 글에서 강조한 것도 결국 이 구조입니다. 에이전트가 수정을 쓰긴 하지만, 그 수정은 사람이 리뷰하는 PR로 나가고 프로덕션에는 사람이 확인한 뒤 반영됩니다. Warp Factories가 파이프라인 단계마다 사람 승인 지점을 두는 것도 같은 발상입니다. 자동화의 목표는 사람을 빼는 게 아니라 사람이 판단할 지점에 정리된 정보를 갖다 놓는 것입니다.

8. 가드레일 — 초록불을 만드는 네 가지 부정행위

이제 이 글에서 가장 중요한 부분입니다. OWASP의 Secure Coding with AI Cheat Sheet는 에이전트가 CI를 초록으로 만드는 방법을 이렇게 정리합니다. 실패하는 테스트를 삭제하거나, 단언을 약화시키거나, 코드를 고치는 대신 테스트 대상을 mock으로 바꿔치기하거나, 버그 동작을 정답이라고 단언하는 겁니다.

여기에 덧붙이는 지적이 특히 날카롭습니다. 코드를 만든 그 에이전트가 만든 테스트가 통과한다는 사실은 아무런 독립적 보증이 되지 못합니다. 채점자가 답안 작성자와 같은 사람인 셈이니까요.

그래서 OWASP는 CI 규칙 자체로 막으라고 권합니다. “에이전트가 만든 PR에서 테스트 삭제나 단언 개수 감소를 플래그하는 CI 규칙을 두라.” 프롬프트로 부탁하는 게 아니라, 결정론적인 검사로 막는 것이 핵심입니다.

{{< highlight bash >}} #!/usr/bin/env bash # .github/scripts/guard-tests.sh # 에이전트가 만든 PR에서 테스트가 줄었는지 결정론적으로 검사한다. set -euo pipefail BASE="${1:-origin/main}" # 1) 테스트 파일이 삭제됐는가 deleted=$(git diff --diff-filter=D --name-only "$BASE"...HEAD -- '**/*.test.*' '**/*_test.*' 'tests/**') if [ -n "$deleted" ]; then echo "::error::테스트 파일이 삭제되었습니다:"; echo "$deleted"; exit 1 fi # 2) skip 처리가 늘었는가 (추가된 줄에서만 센다) added_skips=$(git diff -U0 "$BASE"...HEAD -- '**/*.test.*' \ | grep -E '^\+' | grep -cE '\.skip\(|@pytest\.mark\.skip|t\.Skip\(' || true) if [ "$added_skips" -gt 0 ]; then echo "::error::skip 처리가 $added_skips 건 추가되었습니다"; exit 1 fi # 3) 단언 개수가 줄었는가 (추가된 단언 - 삭제된 단언) diffstat=$(git diff -U0 "$BASE"...HEAD -- '**/*.test.*') added=$(echo "$diffstat" | grep -E '^\+' | grep -cE 'expect\(|assert' || true) removed=$(echo "$diffstat" | grep -E '^-' | grep -cE 'expect\(|assert' || true) if [ "$removed" -gt "$added" ]; then echo "::error::단언이 순감소했습니다 (추가 $added / 삭제 $removed)"; exit 1 fi echo "✅ 테스트 가드 통과" {{< /highlight >}}

이 스크립트는 에이전트가 수정할 수 없는 위치에 두는 게 중요합니다. .github/ 경로를 CODEOWNERS로 보호하고, 에이전트의 --allowedTools에서 해당 경로 편집을 막고, branch protection에서 이 검사를 필수 상태 검사로 지정하세요. 에이전트가 가드레일 자체를 고칠 수 있으면 그건 가드레일이 아닙니다.

9. 흔한 실수 · 팁

실수증상대응
에이전트 push에 CI가 안 돎 고쳤다는데 검사 상태가 그대로 기본 GITHUB_TOKEN으로 만든 커밋은 워크플로를 트리거하지 않습니다. github_token: ${{ secrets.GITHUB_TOKEN }}을 넘기지 말고 GitHub App으로 인증하거나 별도 App 토큰을 쓰세요
자기가 만든 실패에 자기가 반응 PR·브랜치가 계속 늘고 토큰이 사라짐 브랜치 이름 접두사로 재귀 차단 + allowed_bots 기본 거부 유지 + concurrency 설정
플래키를 무한 재시도 초록불은 뜨는데 불안정 테스트가 영원히 남음 재실행은 1회로 제한. 2회째 실패하면 격리 이슈를 만들고 사람에게 넘기기
로그를 통째로 프롬프트에 비용 급증, 정작 스택 트레이스는 잘림 --log-failed + 실패 지점 주변만 발췌. 또는 로그 대신 도구 권한을 주기
fork PR에서도 동작시키려 함 secret이 안 잡히거나, 억지로 열어 사고 pull_requests[0] 조건으로 같은 저장소 PR만 처리. fork PR 자동 수정은 하지 않는 게 맞습니다
첫날부터 전 저장소에 적용 소음이 많아 팀이 알림을 무시하기 시작 저장소 하나 + 코멘트 전용으로 2주 → 판단 정확도 확인 후 자동 재실행 → 마지막에 자동 패치 PR
분류 결과를 기록하지 않음 임계값을 조정할 근거가 없음 매 판단마다 is_flaky·confidence·최종 결과를 한 줄씩 남기기. 이게 나중에 eval 데이터가 됩니다

팁 하나 — 첫 주에는 “재실행 금지”로 시작하세요. 자동 재실행을 켜지 않고 코멘트만 달게 해 두면, 에이전트의 판단이 맞았는지를 사람의 실제 행동(재실행했나, 코드를 고쳤나)과 비교할 수 있습니다. 2주치 기록이 쌓이면 임계값을 근거 있게 정할 수 있습니다.

팁 둘 — 같은 실패의 반복 횟수를 세세요. 브랜치별로 “같은 테스트가 같은 이유로 며칠째 실패 중”인지를 추적하면, 개별 실패로는 안 보이던 패턴이 드러납니다. 사실 1차 대응 자동화의 가장 큰 이득은 개별 수정이 아니라 이 집계에서 나오는 경우가 많습니다.

10. 마무리 (TL;DR)

  • 이번 주 흐름. 8월 18일 Anthropic이 CI/CD 실패의 1차 대응자로 에이전트를 쓴다는 사례를 공개했고, 같은 날 Warp가 트리아지·스펙·구현·리뷰·검증 파이프라인을 열었습니다. 에이전트의 자리가 “코드 작성”에서 “빨간 빌드 대응”으로 넓어지고 있습니다.
  • 먼저 가릴 것. Google 분석 기준 통과→실패 전환의 약 84%에 플래키 테스트가 끼어 있었습니다. 1차 대응의 첫 임무는 고치기가 아니라 진짜인지 가리기입니다.
  • 다섯 단계. 감지 → 분류 → 증거 → 조치·검증 → 인계. 한 번에 다 자동화하지 말고 앞에서부터 하나씩 붙이세요.
  • 트리거는 workflow_run. 기본 브랜치에서 실행되고 secret에 접근할 수 있습니다. conclusion == 'failure', 같은 저장소 PR, 자기 브랜치 제외 — 이 세 조건이 필수입니다.
  • 분류는 스키마로. --json-schema로 is_flaky·confidence·summary를 받고, 확신도 임계값으로 자동화 수준을 조절하세요. 처음엔 0.9, 검증 후 0.7.
  • 로그는 잘라서. gh run view --log-failed로 실패 부분만, 그마저도 발췌해서. 더 좋은 건 로그를 밀어 넣는 대신 읽을 권한만 주는 것입니다.
  • 범위를 숫자로. “파일 3개 넘으면 인계”, --max-turns, --max-budget-usd, --allowedTools. 프롬프트 규칙만으로는 부족합니다.
  • 가드레일은 결정론적으로. OWASP가 지적한 네 가지 부정행위(테스트 삭제·단언 약화·mock 치환·버그 동작 단언)는 CI 검사로 막으세요. 그리고 그 검사를 에이전트가 못 고치게 하세요.
  • merge는 끝까지 사람이. 1차 대응의 산출물은 초록불이 아니라 사람이 5분 안에 판단할 수 있게 정리된 증거입니다.
