1. 도입 — 해킹이 아니라 편의 기능이었다

코딩 에이전트를 쓰다 보면 하루에도 수십 번 만나는 화면이 있습니다. "이 명령을 실행해도 될까요?"라는 권한 프롬프트입니다. 매번 누르기 귀찮으니 자연스럽게 '네, 다시 묻지 마세요(Yes, and don't ask again)'에 손이 갑니다. 이번 주 사건은 바로 그 버튼에서 시작됐습니다.

11월 5일, 보안 업체 Apiiro가 조사 결과를 공개했습니다. 공개 GitHub에 올라와 있는 Claude Code의 프로젝트 설정 파일 .claude/settings.local.json 104,185개를 수집해 분석했더니, 그중 1,122개 파일에서 실제로 동작하는 시크릿 1,379개가 나왔다는 내용입니다. 데이터베이스 비밀번호, 클라우드 키, SSH 접속 정보가 설정 파일 안에 평문으로 들어 있었습니다. 이 소식은 The Hacker News를 시작으로 보안 매체 전반에 보도됐고, Hacker News에서는 댓글이 400개 가까이 달리며 이번 주 내내 논쟁이 이어졌습니다. 나흘 뒤인 11월 9일에는 GitGuardian이 git 히스토리까지 포함한 후속 조사로 판을 더 키웠습니다. 같은 파일 경로에서 누적 3만 개가 넘는 시크릿을 찾아냈고, Docker Hub 이미지 안에서도 같은 파일이 나왔습니다.

중요한 건 이게 해킹 사건이 아니라는 점입니다. 취약점 익스플로잇도, 악성코드도 없습니다. 권한 승인 결과를 설정 파일에 저장하는 평범한 편의 기능과, 개발자의 평범한 습관(비밀번호를 명령어에 그대로 타이핑하기), 그리고 .gitignore 보호장치의 구멍 몇 개가 겹쳐서 생긴 구조적인 유출입니다. 그래서 오늘 글의 주제는 "Claude Code 조심하세요"가 아닙니다. 에이전트가 디스크에 쓰는 모든 파일은 잠재적인 시크릿 유출 벡터라는 일반 원리와, 그걸 막는 secrets hygiene(시크릿 위생)을 다룹니다. 어떤 코딩 에이전트를 쓰든 똑같이 적용되는 이야기입니다.

2. 배경 — Claude Code 권한 시스템 3분 정리

유출 경로를 이해하려면 Claude Code가 권한과 설정을 어디에 저장하는지만 알면 됩니다. 공식 문서 기준으로 설정 파일은 크게 네 곳입니다.

파일적용 범위git에 올라가나?
~/.claude/settings.json내 머신의 모든 프로젝트아니오 (홈 디렉터리)
.claude/settings.json이 프로젝트의 모든 팀원예 — 커밋해서 공유하라고 만든 파일
.claude/settings.local.json이 프로젝트에서 나만아니오 (gitignore 대상) — 이번 사건의 주인공
managed settings조직이 배포한 전 머신아니오 (조직이 관리)

권한 규칙은 이 파일들의 permissions 키 아래에 들어갑니다. 형태는 간단합니다. 도구 이름과 허용할 패턴을 적으면 됩니다.

{{< highlight json >}} { "permissions": { "allow": [ "Bash(npm run lint)", // 이 명령은 묻지 않고 실행 "Bash(npm run test *)" // npm run test로 시작하는 모든 명령 허용 ], "deny": [ "Read(./.env)", // .env 파일은 읽기 자체를 차단 "Read(./.env.*)" ] } } {{< /highlight >}}

여기까지는 문제가 없습니다. 문제는 이 규칙이 만들어지는 또 하나의 경로입니다. 에이전트가 명령 실행 허락을 구할 때 '네, 다시 묻지 마세요'를 고르면, Claude Code는 그 승인을 기억하려고 방금 승인한 명령을 allow 규칙으로 .claude/settings.local.json에 자동 저장합니다. 다음부터 같은 명령은 묻지 않기 위해서입니다. 합리적인 설계입니다 — 승인 피로(approval fatigue)를 줄이는 장치이고, 승인 피로가 왜 위험한지는 예전 글에서 다룬 적이 있습니다.

그런데 이 "방금 승인한 명령"이 어떤 모양일지 생각해 봅시다. 에이전트에게 "프로덕션 DB에서 스키마 좀 확인해 줘"라고 시켰고, 에이전트가 만든 명령에 비밀번호가 들어 있었다면? 혹은 급한 마음에 내가 직접 비밀번호를 포함한 명령을 에이전트에게 붙여넣었다면? 그 비밀번호는 명령 문자열의 일부이므로, allow 규칙에도 그대로 들어갑니다.

{{< highlight json >}} { "permissions": { "allow": [ "Bash(PGPASSWORD=pr0d-s3cret! psql -h db.example.com -U admin -c \"\\dt\")" ] } } {{< /highlight >}}

이 시점에서 비밀번호는 코드도 아니고 .env도 아닌, 설정 파일이라는 제3의 장소에 복사됐습니다. 남은 질문은 하나입니다. 이 파일이 git 바깥에 안전하게 머무느냐.

3. 유출 경로 해부 — 비밀번호는 어떻게 공개 저장소까지 갔나

Anthropic도 이 파일이 저장소에 올라가면 안 된다는 건 알고 있었습니다. 공식 문서에 따르면, Claude Code가 git 저장소 안에서 이 파일을 처음 직접 생성할 때 **/.claude/settings.local.json 패턴을 전역 git excludes(보통 ~/.config/git/ignore)에 추가합니다. 내 머신의 모든 저장소에서 이 파일이 커밋되지 않도록 하는 장치입니다. 그런데 Apiiro와 GitGuardian의 조사 결과가 보여주듯, 현실에서는 이 보호가 여러 갈래로 뚫렸습니다.

구멍을 하나씩 보면 각각은 사소합니다. 전역 excludes는 머신 단위 설정이라 저장소를 새 노트북에 클론하거나 CI에서 돌리면 보호가 따라오지 않습니다. 파일을 손으로 먼저 만들면(블로그 글 따라하다가, dotfiles 템플릿으로) excludes 등록 로직이 아예 발동하지 않습니다. git은 이미 추적 중인 파일을 ignore하지 않으므로 한 번이라도 커밋된 뒤에는 excludes가 소용없습니다. 승인 규칙이 공유용 .claude/settings.json에 기록된다는 버그 리포트(#77530)도 있었습니다 — 2026년 7월에 올라왔다가 방치 끝에 자동으로 닫혔는데, 이 파일은 애초에 커밋하라고 만든 파일이라 excludes 보호 대상도 아닙니다. 마지막으로 docker build는 .gitignore가 아니라 .dockerignore를 보기 때문에, 프로젝트 폴더를 통째로 COPY하는 Dockerfile은 git이 무시하던 파일까지 이미지에 넣습니다. GitGuardian이 Docker Hub에서 같은 파일을 찾아낸 경로가 바로 이겁니다.

일반화하면 이렇습니다. "비밀이 파일에 쓰이는 시점"과 "그 파일이 공유되는 시점"이 다르면, 그 사이의 모든 보호장치는 조건부입니다. 조건부 보호가 n개 겹쳐 있어도, 각 조건이 깨지는 경우의 수는 곱이 아니라 합으로 늘어납니다. 그래서 뒤에서 볼 방어 전략의 1원칙은 "애초에 비밀이 파일에 쓰이지 않게 한다"입니다.

4. 숫자로 보는 규모 — 무엇이 얼마나 샜나

두 조사의 수치를 정리합니다. 집계 방식이 달라서 숫자가 크게 다른데, 이 차이 자체가 배울 점입니다.

Apiiro (11/5)GitGuardian (11/9)
대상공개 GitHub의 settings.local.json 사본 104,185개 (11/1~3 수집)같은 경로, git 히스토리와 삭제된 버전 포함 + Docker Hub
발견1,122개 파일에서 시크릿 1,379개, 63개 조직 연루23,276개 저장소에서 시크릿 31,088개
유효성실제 동작하는 시크릿 기준탐지 시점에 약 5,343개가 아직 유효
기타추적 가능한 1,105개 저장소 중 539개는 Claude가 공동 작성한 커밋이 파일을 변경Docker Hub 이미지에서 613개 (99개 유효)

유형별로는 뭐가 샜을까요. Apiiro가 공개한 분류를 보면 화려한 클라우드 키보다 수수한 데이터베이스 비밀번호가 압도적입니다.

왜 DB 비밀번호가 1위일까요? 에이전트에게 시키는 작업을 생각해 보면 자연스럽습니다. "마이그레이션 돌려 줘", "프로덕션 데이터 좀 확인해 줘" 같은 요청은 전부 psql, mysql, mongosh 명령으로 이어지고, 이런 CLI는 비밀번호를 환경 변수나 인자로 받는 관행이 오래됐기 때문입니다. 즉 에이전트와 대화하며 일하는 워크플로우 자체가 비밀번호를 명령 문자열에 태워 보내는 빈도를 높입니다.

5. 시크릿 스캐너는 왜 놓쳤나

"우린 gitleaks 돌리는데?"라고 생각했다면, 이번 조사에서 제일 아픈 대목이 여기입니다. Apiiro가 시크릿이 든 1,122개 파일을 대표적인 오픈소스 스캐너에 넣어 봤더니 — gitleaks는 564개, TruffleHog는 643개 파일만 잡아냈고, 215개는 둘 다 통과시켰습니다.

이유는 스캐너의 동작 원리에 있습니다. 시크릿 스캐너는 크게 두 가지 신호로 탐지합니다.

  • 패턴 매칭 — ghp_로 시작하는 GitHub 토큰, AKIA로 시작하는 AWS 키처럼 발급자가 박아 둔 식별 가능한 접두사·형식
  • 컨텍스트 + 엔트로피 — password = "..." 같은 변수 할당 주변에서 무작위성 높은 문자열 찾기

그런데 이번에 샌 시크릿의 최대 그룹은 접두사 없는 일반 비밀번호가, 변수 할당도 아닌 셸 명령 문자열 한복판에 박힌 형태였습니다. "Bash(PGPASSWORD=pr0d-s3cret! psql ...)" 같은 JSON 문자열에서 pr0d-s3cret!만 비밀이라는 걸 패턴으로 알아내긴 어렵습니다. 사람 눈에는 뻔한데 정규식에는 안 보이는 전형적인 사각지대입니다. 보도에 따르면 탐지를 빠져나간 215개 파일의 내용물 대부분이 이런 '명령어 속 비밀번호'였습니다.

교훈: 시크릿 스캐너의 룰셋은 "시크릿이 나타나던 기존 장소"(코드, .env, CI 설정)에 맞춰 진화해 왔습니다. 에이전트 설정 파일은 새로 생긴 장소라 룰셋의 가정 바깥에 있습니다. 새 도구가 디스크에 뭔가를 쓰기 시작하면, 스캐너가 그 경로를 아는지부터 확인해야 합니다. 실제로 이번 사건 이후 Apiiro는 .claude/ 같은 에이전트 폴더를 pre-commit과 CI 스캔 범위에 명시적으로 추가하라고 권고했습니다.

6. 실전 — 오늘 할 일: 점검 한 번, 방어 4겹

이제 손을 움직일 차례입니다. 먼저 내가 이미 당했는지 점검하고, 그다음 재발을 막는 방어를 겹겹이 깝니다.

6-0. 점검 — 내 저장소에 이미 들어 있나

{{< highlight bash >}} # 1) 지금 작업 트리와 '히스토리 전체'에서 에이전트 설정 파일 흔적 찾기 git log --all --oneline -- '.claude/settings.local.json' '.claude/settings.json' # 2) 흔적이 있다면 내용에 비밀이 있었는지 확인 git log --all -p -- '.claude/settings.local.json' | grep -inE 'password|passwd|token|secret|key' # 3) 조직 전체 점검 — GitHub 코드 검색 (조직 이름을 바꿔서) # org:my-org path:.claude/settings.local.json {{< /highlight >}}

하나라도 걸렸고 그 안에 진짜 시크릿이 있었다면, 순서는 "파일 삭제"가 아니라 시크릿 로테이션(재발급)이 먼저입니다. 이유는 7장에서 다시 강조합니다.

6-1. 1겹 — 비밀을 명령 문자열에 태우지 않는다 (원천 차단)

allow 규칙은 명령 문자열을 그대로 저장할 뿐입니다. 그러니 문자열에 비밀이 없으면 규칙에도 비밀이 없습니다. 핵심 요령은 간접 참조입니다. 셸 변수는 따옴표 규칙상 확장되지 않은 리터럴로 저장되므로, 비밀을 변수 뒤로 숨기면 규칙에는 변수 이름만 남습니다.

{{< highlight bash >}} # 나쁨 — 비밀번호가 명령 문자열에 그대로 (allow 규칙에도 그대로 들어감) PGPASSWORD=pr0d-s3cret! psql -h db.example.com -U admin # 좋음 — 비밀은 환경에 미리 두고, 명령에는 참조만 export PGPASSWORD="$(cat ~/.secrets/prod-db)" # 셸 설정 등에서 한 번만 psql -h db.example.com -U admin # 규칙에는 이 줄만 남음 # 더 좋음 — 시크릿 매니저가 실행 시점에 주입 (디스크에 평문이 아예 없음) op run --env-file=.env.tpl -- psql -h db.example.com -U admin # 1Password CLI doppler run -- psql -h db.example.com -U admin # Doppler {{< /highlight >}}

에이전트에게 일을 시킬 때도 마찬가지입니다. "비밀번호는 PGPASSWORD 환경 변수에 이미 있어"라고 알려 주고 명령에는 넣지 않게 하는 습관이, 설정 파일·세션 로그·트랜스크립트 등 모든 파생 파일을 한 번에 깨끗하게 만듭니다.

6-2. 2겹 — 저장소 차원의 .gitignore (머신 말고 repo에)

전역 excludes는 내 머신만 지킵니다. 팀원 전체를 지키려면 저장소의 .gitignore에 명시하는 게 맞습니다. 커밋되는 파일이니 모든 클론과 CI에 따라갑니다.

{{< highlight bash >}} # .gitignore에 추가 (에이전트 로컬 파일 일반 패턴) .claude/settings.local.json .claude/*.local.json # 이미 커밋돼 버린 경우: 추적만 중단 (파일은 로컬에 유지) git rm --cached .claude/settings.local.json git commit -m "chore: stop tracking agent local settings" # 주의 — 히스토리에는 남아 있으므로, 비밀이 있었다면 로테이션 필수 {{< /highlight >}}

Docker 쪽 구멍도 같은 원리로 막습니다. .dockerignore에 .claude/와 .git/을 넣으면 이미지에 설정 파일이 복사되는 경로가 닫힙니다.

6-3. 3겹 — pre-commit 스캐너와 push protection (그물)

1·2겹을 뚫고 나온 비밀을 커밋/푸시 직전에 걸러내는 층입니다. 단, 5장에서 봤듯 스캐너는 만능이 아니므로 "있으면 안전"이 아니라 "없으면 위험"으로 생각해야 합니다.

{{< highlight yaml >}} # .pre-commit-config.yaml — 커밋 전에 gitleaks 실행 repos: - repo: https://github.com/gitleaks/gitleaks rev: v8.24.3 hooks: - id: gitleaks {{< /highlight >}} {{< highlight toml >}} # .gitleaks.toml — 에이전트 설정 파일 경로를 명시적으로 커스텀 룰에 추가 [[rules]] id = "agent-settings-inline-secret" description = "agent settings 파일의 allow 규칙 안 인라인 시크릿 의심 패턴" path = '''\.claude/settings.*\.json''' regex = '''(PASSWORD|PASSWD|TOKEN|SECRET|API_KEY)=\S+''' {{< /highlight >}}

GitHub을 쓴다면 저장소 설정에서 secret scanning과 push protection을 켜 두세요. 알려진 형식의 토큰이 푸시에 포함되면 서버가 푸시 자체를 거부합니다. 공개 저장소에서는 무료입니다. 다만 이것도 '알려진 형식' 기반이라 일반 DB 비밀번호는 못 잡는다는 한계를 같이 기억해야 합니다.

6-4. 4겹 — 권한 규칙을 손으로 설계한다 (근본 처방)

'다시 묻지 마세요'로 쌓이는 규칙은 "방금 그 명령 통째"라서 조잡합니다. 자주 쓰는 명령이라면 처음부터 공유 설정 파일에 prefix 패턴으로 직접 써 두는 편이 보안과 편의 양쪽에 낫습니다. 규칙에 들어갈 내용을 사람이 통제하게 되기 때문입니다.

{{< highlight json >}} { "permissions": { "allow": [ "Bash(npm run lint)", "Bash(npm run test *)", "Bash(psql -h localhost *)" // 로컬 DB만 — 호스트를 패턴에 박아 제한 ], "deny": [ "Read(./.env)", // 에이전트가 비밀 파일을 읽는 것 자체를 차단 "Read(./.env.*)", "Read(./secrets/**)" ] } } {{< /highlight >}}

7. 흔한 실수 · 팁

  • "파일 지웠으니 끝" — 아닙니다. git 히스토리, 포크, 그리고 이미 긁어 간 크롤러에는 비밀이 남아 있습니다. GitGuardian 집계(31,088개)가 Apiiro(1,379개)의 20배가 넘는 이유가 바로 삭제된 버전까지 포함했기 때문입니다. 공개 저장소에 한 번이라도 올라간 시크릿은 유출된 것으로 간주하고 즉시 로테이션하는 게 원칙입니다. 히스토리 세탁(git filter-repo)은 로테이션 다음에 하는 정리 작업입니다.
  • '다시 묻지 마세요'를 악당 취급하지 마세요. 승인 피로에 지쳐 아무 데나 Yes를 누르는 것보다, 자주 쓰는 안전한 명령을 넓게 허용하고 위험한 건 deny로 못 박는 쪽이 전체적으로 안전합니다. 문제는 버튼이 아니라 버튼이 저장하는 내용(비밀이 든 명령 문자열)입니다.
  • 벤더의 대응은 '진행 중'으로 읽어야 합니다. Claude Code를 이끄는 Boris Cherny는 Hacker News에서 "역사적으로 Claude Code는 secret scrubbing을 하지 않았다(좋은 전용 도구가 많으므로). 하지만 막을 방법을 찾고 있다"고 답했고, 기본 시크릿 스캐닝 내장 등을 프로토타이핑 중이라고 밝혔습니다. 방향은 맞지만, 배포 전까지 내 저장소를 지키는 건 6장의 4겹입니다.
  • 이건 Claude Code만의 문제가 아닙니다. 세션 트랜스크립트, 에이전트 메모리 파일, MCP 서버 설정(mcp.json에 API 키를 넣는 패턴!), 셸 히스토리 — 에이전트 워크플로우가 만들어 내는 파일은 전부 "런타임 데이터가 디스크에 적히는 장소"입니다. 같은 주에 화제가 된 User-Agent 헤더에 사용자 이메일이 실려 나간 이슈도 본질은 같습니다. 에이전트 하네스가 다루는 데이터가 의도하지 않은 채널(설정 파일, HTTP 헤더)로 복사되는 문제입니다. 도구 공급망 전반의 위험은 예전 글에서 다뤘습니다.
  • 에이전트에게 읽기 권한부터 제한하세요. deny: Read(./.env)는 유출 이전에, 에이전트가 비밀을 컨텍스트에 넣는 것 자체를 줄입니다. 컨텍스트에 들어간 비밀은 로그·트랜스크립트·외부 요청 등 더 많은 경로로 번질 수 있습니다. 샌드박스와 egress 제한까지 더하면 좋고, 그 주제는 샌드박스 격리 글에 정리돼 있습니다.

8. 마무리 (TL;DR)

  • Claude Code의 '네, 다시 묻지 마세요'는 승인한 명령 전체를 .claude/settings.local.json에 allow 규칙으로 저장합니다. 명령에 비밀번호가 있었다면 비밀번호도 함께 저장됩니다.
  • Apiiro 조사(11/5): 공개 GitHub의 사본 104,185개 중 1,122개 파일에서 시크릿 1,379개 발견. DB 비밀번호가 379건으로 최다. GitGuardian(11/9)은 히스토리 포함 31,088개(약 5,343개 유효), Docker Hub 이미지에서도 613개를 확인했습니다.
  • 전역 git excludes 보호는 '내 머신 + Claude Code가 만든 파일'이라는 조건부였고, 다른 머신·수동 생성·기존 커밋·버그·Docker 이미지라는 다섯 구멍으로 샜습니다.
  • gitleaks·TruffleHog도 215개 파일을 놓쳤습니다. 접두사 없는 비밀번호가 명령 문자열 안에 있으면 패턴 기반 탐지는 약합니다. 스캐너는 그물이지 보증이 아닙니다.
  • 방어는 4겹: ① 비밀을 명령 문자열에 태우지 않기(env 간접 참조·시크릿 매니저) ② repo .gitignore와 .dockerignore에 에이전트 파일 명시 ③ pre-commit 스캐너 + push protection + CI에 .claude/ 포함 ④ allow 규칙은 손으로 prefix 패턴 설계, .env는 deny.
  • 이미 올라간 시크릿은 삭제가 아니라 로테이션이 먼저입니다. 히스토리와 포크는 지워지지 않습니다.
  • 일반 원리: 에이전트가 디스크에 쓰는 모든 파일은 잠재적 유출 벡터입니다. 새 도구를 들이면 "이 도구가 어떤 파일에 뭘 적는가"부터 목록화하세요.
