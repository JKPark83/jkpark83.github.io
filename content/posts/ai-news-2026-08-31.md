# 📚 주목 논문

**Safety Does Not Compose: Non-Decaying Loop State for Autonomous LLM Agents**

- 저자: Chenhao Wu, Haoxuan Jia, Yang Liu 외 5인 (소속은 arXiv 초록 페이지에 미표기)
- arXiv: [2608.27141](https://arxiv.org/abs/2608.27141) (cs.CR, 8/27)
- 핵심: 자율 루프(발견→계획→실행→검증→상태 저장 반복)에서 안전장치 대부분은 트래젝터리 단위로 정의되고, 다음 반복이 시작되면 안전 상태가 초기화된다. 이건 구현 디테일이 아니라 **조합(composition)의 실패**라는 진단.
- 방법: 증거가 여러 반복에 조각나 있는 공격에 대해, 트래젝터리 범위 모니터는 아무리 정교해도 탐지율 = 오탐율이 됨을 증명(볼 증거가 창 안에 없기 때문). 반복을 가로질러 상태를 유지하면 완전 분리가 가능. 감쇠(decay)형 리스크 점수는 인내심 있는 공격자가 상수 시간만 기다리면 뚫려서 불충분하다는 것도 증명.
- 제안: 루프 레벨에 감쇠 없는 지속 안전 상태를 복원하는 LoopHarness.
- 🛠 시사점: cron이나 스케줄러로 도는 에이전트에 세션 단위 가드레일만 있다면 구조적 구멍이 있는 셈. 리스크 신호를 반복 밖의 저장소에 누적하고, 리셋 없이 읽게 하라.
- 한계: 초록 기준 오버헤드·오탐 누적 관리 방식은 본문 확인 필요.

![루프 레벨 안전 상태 다이어그램](/images/ai-news-2026-08-31/loop-state.svg)

*반복마다 리셋되는 모니터(위)는 조각난 공격을 원리적으로 못 본다 — 감쇠 없는 루프 상태(아래)가 논문의 답. (제작: 본 블로그, 출처: arXiv:2608.27141 초록)*

**Calibrated Enough to Know, Not Calibrated to Act**

- 저자: Pranav Aggarwal (단독 저자, 소속은 arXiv 초록 페이지에 미표기)
- arXiv: [2608.27167](https://arxiv.org/abs/2608.27167) (cs.AI, 8/27)
- 핵심: 증명 가능하게 예측 불가능한 질문이라도, 그럴듯한 "시장 데이터 패널"을 붙이면 에이전트가 방향성 베팅을 한다. 12개 프런티어 모델에서 커밋 비율이 6.5% → 54.0%로 상승.
- 방법: 같은 질문에 증거의 "포장 수준"만 바꿔 제시. 패널의 숫자를 전부 조작해도 커밋률 36.8%로, 진짜 데이터(37.6%)와 통계적으로 구분 불가.
- 결과: 모델은 질문의 답 불가능성을 물어보면 90% 정확히 분류하고, 분류 후에는 0.4%만 커밋한다. 즉 지식도 판단력도 아닌 **행동 게이트**가 고장.
- 🛠 시사점: 도구가 물어온 외부 데이터를 근거로 에이전트가 액션(거래, 배포, 삭제)을 결정한다면, 액션 직전에 "이 질문이 현재 증거로 답해질 수 있는가"를 별도 단계로 강제 분류시키는 것만으로 커밋 오류가 크게 줄어든다는 실험적 근거.
- 한계: 시장 예측 도메인 중심 실험 — 다른 액션 유형으로의 일반화는 본문 확인 필요.

![증거 포장에 따른 커밋 비율](/images/ai-news-2026-08-31/evidence-commitment.svg)

*정보가 아니라 포장이 행동을 잠금 해제한다 — 조작 패널과 진짜 패널의 차이가 없다는 게 핵심. (제작: 본 블로그, 출처: arXiv:2608.27167 초록)*

# 🛠 오픈소스 스포트라이트

**huangruiteng/LoopX** — [github.com/huangruiteng/loopx](https://github.com/huangruiteng/loopx)

- 언어: Python 3.11+, Apache-2.0 (클론으로 확인, 스타 수는 API 제한으로 미확인 — GitHub 주간 트렌딩에 올라 있다)
- Codex·Claude Code·Cursor·dsh 등 하니스 **위에** 얹는 provider 중립 상태 커널. 목표(goal)·게이트·투두·증거·쿼터·핸드오프를 하니스 밖에 두고, 하니스는 유한한 턴만 실행한다. `loopx dashboard`로 로컬 웹 대시보드를 띄워 무엇이 돌고 있고 무엇이 사람을 기다리는지 본다. 마지막 커밋 8/31로 매우 활발.
- 활용: 위 LoopHarness 논문이 요구하는 "반복을 가로지르는 상태"를 직접 구현하지 않고 얻는 실용적 선택지. 며칠짜리 목표를 여러 하니스 세션에 나눠 돌리는 팀에 맞다.

**TencentCloud/TencentDB-Agent-Memory** — [github.com/TencentCloud/TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory)

- 언어: TypeScript (Node 22.16+), MIT (클론으로 확인, 스타 수는 API 제한으로 미확인)
- 대화·문서·코드를 재사용 가능한 메모리 자산으로 바꿔 **여러 에이전트가 같은 메모리 서버를 공유**하게 하는 팀 메모리 허브. memory-core + memory-hub + proxy 3개 서비스 구성이고, Claude Code·CodeBuddy·Pi 어댑터(8/27 추가)까지 지원.
- 활용: 개인 세션 메모리를 넘어 "1인 회사식" 에이전트 팀이 축적한 지식을 한곳에 모으고 싶을 때. LoopX가 목표·거버넌스 상태를 담당한다면 이쪽은 지식 상태 담당 — 같은 문제의 다른 층이다.

**🟩 Codex — 0.151.0의 MCP 결과 미들웨어와 시작 grace** (카테고리: MCP)

- 출처: [Codex CLI rust-v0.151.0 릴리즈](https://github.com/openai/codex/releases/tag/rust-v0.151.0)
- 💡 확장이 MCP 도구 결과를 모델이 보기 전에 검사·치환할 수 있는 지점이 생겼다. 도구 출력에서 시크릿 마스킹, 거대 JSON 요약, 의심 패턴 태깅 같은 "관측 후처리"를 프롬프트가 아니라 코드로 걸 수 있다는 뜻.
- 📝 방법:

```bash
codex --version        # 0.151.0 이상인지 확인
npm i -g @openai/codex # 업그레이드
```

  업그레이드 후 릴리즈 노트의 #41202(결과 후처리), #41199(옵션 MCP 서버 시작 grace 설정)를 확인하고, 자주 타임아웃 나던 느린 MCP 서버에는 grace를 늘려 주자.
- 🎯 MCP 도구가 많고 출력이 크거나 신뢰 수준이 제각각인 에이전트 셋업.
- ⚠️ 결과를 치환하는 미들웨어는 그 자체가 공격면이다. 어제 다룬 스킬 스캔 게이트처럼 확장도 출처 확인 후 설치할 것.
- ⭐ 추천도: MCP 헤비 유저라면 ★★★★☆

**🟦 Claude Code — Anthropic이 자기 저장소에서 쓰는 슬래시 커맨드 훔쳐보기** (카테고리: Slash Command)

- 출처: [anthropics/claude-code의 .claude/commands](https://github.com/anthropics/claude-code/tree/main/.claude/commands)
- 💡 Claude Code 저장소 자체에 Anthropic 팀이 실제로 쓰는 커맨드 3개(`/dedupe`, `/triage-issue`, `/commit-push-pr`)가 들어 있다. 잘 쓴 커맨드의 교과서다: ① frontmatter `allowed-tools`로 래퍼 스크립트만 허용(최소 권한), ② `!`백틱 명령으로 git 상태를 컨텍스트에 주입, ③ 병렬 서브에이전트 5개로 검색 후 별도 에이전트가 오탐 필터링.
- 📝 방법: 내 프로젝트의 `.claude/commands/my-review.md`에 같은 패턴을 적용해 보자.

```markdown
---
allowed-tools: Bash(git diff:*), Bash(git log:*)
description: 리뷰 대상 diff 요약
---
## Context
- 현재 diff: !`git diff HEAD`
## Task
위 diff에서 위험 변경 3개를 골라 근거와 함께 보고.
```

- 🎯 팀 공용 커맨드를 처음 설계할 때, 특히 권한 범위를 어디까지 열지 고민될 때.
- ⚠️ `allowed-tools`에 `Bash(*)`처럼 넓게 열면 최소 권한 패턴의 의미가 없어진다. 래퍼 스크립트로 좁히는 게 원본의 핵심.
- ⭐ 추천도: 커맨드 만드는 모든 팀에 ★★★★★

**🟪 공통 — 루프 레벨 리스크 상태를 만들자** (카테고리: Workflow)

- 출처: [arXiv:2608.27141 (LoopHarness)](https://arxiv.org/abs/2608.27141)
- 💡 스케줄러로 반복 실행되는 에이전트라면, 반복마다 컨텍스트가 리셋되므로 "지난 반복의 의심 신호"가 사라진다. 리스크 신호를 파일·DB 등 반복 밖 저장소에 누적하고 매 반복 시작 시 읽게 하는 것만으로 논문이 지적한 구조적 구멍을 좁힐 수 있다.
- 📝 방법: 반복 시작 시 `risk-log.jsonl`을 읽고, 이상 신호(권한 상승 요청, 예상 밖 네트워크 접근, 실패한 검증)를 발견할 때마다 append. 임계 누적치에 도달하면 자동 실행을 멈추고 사람 확인을 요구하는 규칙을 프롬프트가 아니라 하니스/훅 레벨에 둔다.
- 🎯 cron·CI에서 무인 반복되는 에이전트 전부. 이 블로그의 발행 봇도 해당된다.
- ⚠️ 감쇠형 점수(오래된 신호 자동 삭제)는 논문이 이론적으로 불충분함을 보였다. 삭제는 사람이 리뷰한 뒤에만.
- ⭐ 추천도: 무인 루프 운영자라면 ★★★★★
