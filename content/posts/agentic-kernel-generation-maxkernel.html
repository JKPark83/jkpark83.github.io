1. 도입 — 가장 희소한 엔지니어를 에이전트로

ML 인프라 조직에서 가장 뽑기 어려운 사람이 누구냐고 물으면, 많은 팀이 커널 엔지니어를 꼽습니다. GPU·TPU 위에서 행렬 곱과 어텐션을 하드웨어 한계까지 밀어붙이는 사람들이죠. 모델 하나 서빙 비용이 수백만 달러 단위로 움직이는 시대에 커널 몇 개를 2배 빠르게 만들면 그대로 청구서가 반으로 줄지만, 이 일을 할 수 있는 사람은 전 세계에 손에 꼽을 만큼 적습니다.

이번 주 Hugging Face 데일리 페이퍼 주간 트렌딩 1위는 바로 이 일을 에이전트에게 맡긴 논문이었습니다. Google AI Hypercomputer 팀이 9월 초 공개한 MaxKernel: Agentic Kernel Generation for TPUs(arXiv:2609.04523)입니다. Gemini 기반 서브에이전트들이 계획을 세우고, TPU 커널 언어인 Pallas로 구현하고, 컴파일러와 프로파일러의 피드백을 받아 스스로 고치는 멀티 에이전트 시스템인데, 결과가 눈에 띕니다. TPU 커널 벤치마크 JaxBench 50개 태스크에서 기하평균 1.58배, 그리고 사람이 손으로 튜닝한 커널이 존재하는 프로덕션 문제 8개에서는 사람의 2.02배를 넘는 2.32배 속도 향상을 보고했습니다(자체 보고). 코드도 공개돼 있어서 직접 돌려볼 수 있습니다.

"에이전트가 커널을 쓴다"는 아이디어 자체는 새롭지 않습니다. 2025년 초부터 NVIDIA가 DeepSeek-R1로 어텐션 커널을 생성하는 실험을 공개했고, Sakana AI의 "AI CUDA Engineer"는 화려하게 등장했다가 더 화려하게 무너졌습니다(6장에서 자세히 다룹니다). 그 뒤로 2년 가까이 벤치마크와 시스템이 쌓이면서, 이제는 "되냐 안 되냐"가 아니라 "루프를 어떻게 설계하느냐"의 문제가 됐습니다. MaxKernel은 이 흐름의 현재 지점을 보여주는 좋은 표본이고, 동시에 에이전트 엔지니어링 전반에 통하는 교훈 하나를 아주 선명하게 보여줍니다. 검증 가능한 피드백이 있는 곳에서 에이전트 루프는 가장 세게 돈다는 것입니다.

2. 배경 — 커널이 뭐길래, 그리고 Pallas 3분 요약

따라오는 데 필요한 배경만 짚고 갑니다.

커널(kernel)은 가속기 위에서 직접 실행되는 작은 프로그램입니다. jnp.dot(x, w) 한 줄을 부르면 실제로는 "HBM(큰 메모리)에서 타일을 읽어 → 칩 안의 빠른 메모리(TPU에서는 VMEM)에 올리고 → 행렬 연산 유닛(MXU)에 밀어 넣고 → 결과를 다시 쓰는" 커널이 돕니다. 성능의 대부분은 연산 자체가 아니라 메모리를 얼마나 덜, 얼마나 잘 움직이느냐에서 갈립니다. FlashAttention이 유명해진 이유도 수학을 바꿔서가 아니라 메모리 이동을 바꿔서입니다.

보통은 컴파일러(XLA)가 이 일을 알아서 해 줍니다. 문제는 마지막 몇 배입니다. 새로운 어텐션 변형, 특이한 fusion 패턴, MoE 라우팅처럼 컴파일러의 자동 최적화가 못 따라가는 지점에서는 사람이 커널을 직접 씁니다. TPU에서 그 도구가 Pallas입니다. JAX 안에서 블록 단위 커널을 파이썬으로 쓰는 확장인데, 감을 잡을 만큼만 보면 이렇습니다.

{{< highlight python >}} import jax import jax.numpy as jnp from jax.experimental import pallas as pl def fused_kernel(x_ref, y_ref, o_ref): # x_ref, y_ref는 VMEM에 올라온 '블록' — 이 함수는 그리드의 칸마다 실행된다 o_ref[...] = jax.nn.gelu(x_ref[...]) * y_ref[...] @jax.jit def fused_gelu_mul(x, y): # GELU와 곱을 한 커널로 합쳐 HBM 왕복을 줄인다 block = 256 return pl.pallas_call( fused_kernel, out_shape=jax.ShapeDtypeStruct(x.shape, x.dtype), grid=(x.shape[0] // block,), in_specs=[pl.BlockSpec((block, x.shape[1]), lambda i: (i, 0))] * 2, out_specs=pl.BlockSpec((block, x.shape[1]), lambda i: (i, 0)), )(x, y) {{< /highlight >}}

블록 크기를 얼마로 잡을지, 어떤 축으로 그리드를 자를지, 무엇을 한 커널로 합칠지 — 이런 선택 하나하나가 성능을 몇 배씩 바꿉니다. 그리고 이 선택의 근거는 코드가 아니라 하드웨어 사양과 프로파일러 트레이스에 있습니다. 사람 전문가가 하는 일이 정확히 "트레이스를 보고 → 병목을 짚고 → 코드를 고치고 → 다시 재는" 반복이라는 점을 기억해 두세요. 잠시 뒤 에이전트가 똑같은 일을 합니다.

그런데 LLM에게 Pallas 커널을 그냥 시키면 처참합니다. CUDA에 비해 Pallas는 학습 데이터에 거의 없는 저자원 언어라서요. TPU 커널 벤치마크를 만든 JAXBench 논문(arXiv:2607.20466)의 측정이 이를 잘 보여줍니다. 프런티어 모델에게 맨몸으로 커널을 시키면 샘플당 정확도가 5.8%에 그칩니다. 그런데 큐레이션한 TPU·Pallas 문서를 컨텍스트에 넣어 주는 것만으로 37.3%까지 뜁니다. 모델 교체 없이 컨텍스트 엔지니어링(context engineering)만으로 6배가 넘게 오른 겁니다. 여기에 반복 루프를 더하면 50개 중 48개가 풀립니다. "모델이 못 한다"와 "시스템이 못 한다"는 다른 문제라는 것, 이 글 전체의 복선입니다.

3. 왜 커널 생성은 '에이전트 문제'인가

에이전트 루프가 잘 도는 문제에는 공통점이 있습니다. 싸고, 빠르고, 속일 수 없는 채점기가 있다는 점입니다. 커널 생성은 이 조건을 교과서처럼 만족합니다. 채점기가 세 겹으로 존재하거든요.

세 채점기를 하나씩 보면 이렇습니다.

채점기 1: 컴파일러. 코드가 문법적으로, 그리고 하드웨어 제약상 말이 되는지 몇 초 안에 판정하고, 틀리면 왜 틀렸는지 에러 메시지까지 줍니다. 공짜 선생님입니다.

채점기 2: 수치 검증. 커널에는 항상 참조 구현이 있습니다(느리지만 맞는 jnp.dot 같은 것). 랜덤 입력을 넣고 두 출력을 비교하면 정답 여부가 나옵니다. 라벨링 비용이 0원입니다.

채점기 3: 프로파일러. 얼마나 빠른지는 재면 됩니다. 게다가 트레이스는 "MXU 활용률 31%, HBM 대역폭이 병목"처럼 다음에 뭘 고쳐야 하는지까지 알려줍니다. 보상이 스칼라 하나가 아니라 진단서로 오는 셈입니다.

일반적인 코딩 에이전트가 "이 리팩터링이 좋은가?"라는 애매한 판정에 시달리는 것과 비교하면, 커널 생성은 에이전트 입장에서 드물게 공정한 게임입니다. 에이전틱 RL에서 검증 가능한 보상이 중요하다고 했던 것과 정확히 같은 이야기이고, 그래서 이 분야에는 KernelBench(GPU), JAXBench(TPU) 같은 벤치마크가 먼저 서고 그 위에 시스템이 쌓이는 건강한 구조가 만들어졌습니다.

4. MaxKernel 해부 — 서브에이전트 풀과 세 가지 운용 방식

MaxKernel의 구조는 두 층으로 나눠 보면 깔끔합니다. 아래층에는 공유 서브에이전트 풀이 있습니다. 계획(planning), 구현(implementation), 자가 디버깅(self-debugging), 테스트(testing), 하드웨어 프로파일링(profiling)을 각각 맡는 전문 에이전트들입니다. 위층에는 이 풀을 어떻게 굴릴지 정하는 세 가지 운용 방식이 있습니다.

운용 방식사람의 역할언제 쓰나
HITL 에이전트최적화 계획을 검토·승인하며 단계마다 방향을 잡음전문가가 있고, 커널이 중요해서 설계 통제가 필요할 때
Auto 에이전트없음 — 계획→구현→컴파일→테스트→오토튜닝→프로파일링 폐쇄 루프한 커널을 무인으로 다듬을 때
그래프 탐색없음 — Auto 에이전트를 워커로 삼아 설계 공간을 병렬 탐색컴퓨트를 더 태워 로컬 옵티마를 벗어나고 싶을 때

흥미로운 건 세 번째, 그래프 기반 자율 탐색입니다. 커널 하나를 순차적으로 다듬는 Auto 루프는 그럴싸한 로컬 옵티마에 갇히기 쉽습니다. 예를 들어 "fusion을 먼저 하고 블록 크기를 튜닝"하는 경로에 들어서면, 사실은 "메모리 레이아웃을 먼저 바꿨어야 하는" 더 좋은 경로를 영영 못 봅니다. 그래서 MaxKernel은 커널 설계 공간을 탐색 그래프로 놓습니다. 노드는 커널 변형(variant), 엣지는 "이 최적화 전략을 적용한다"입니다. 오케스트레이터가 확장할 노드를 골라 분산 워커들에게 나눠 주면, 각 워커는 독립적으로 Auto 에이전트를 돌려 새 전략을 적용하고 컴파일·테스트·프로파일 결과를 그래프에 되돌려줍니다. 그 위에서 단순 병렬 탐색이나 빔 서치(beam search) 같은 고전 탐색 알고리즘을 돌립니다.

낯익은 그림 아닐까요? 맞습니다. 알파고 이후 우리가 아는 "탐색 + 학습된 정책" 구조에서 정책 네트워크 자리에 LLM 에이전트를 꽂은 형태입니다. LLM이 "다음에 시도할 만한 최적화"라는 좋은 후보를 내고, 탐색이 그 후보들을 하드웨어 측정으로 걸러냅니다. 창의성은 모델에서, 진실은 측정에서 나오는 분업입니다.

5. 숫자 읽는 법 — 1.58×, 그리고 사람을 이긴 2.32×

벤치마크 수치는 늘 "무엇을, 무엇과 비교했는지"부터 확인해야 합니다. MaxKernel이 쓴 JaxBench는 50개 태스크로 구성되는데, 절반쯤은 실제 프로덕션에서 온 것들입니다. MaxText(Google의 JAX LLM 프레임워크)에서 뽑은 Llama-3.1, DeepSeek-V3, Mixtral, Mamba-2, AlphaFold2의 연산 17개, 그리고 GPU 벤치마크 KernelBench에서 TPU v6e에 맞게 문제 크기를 다시 잡아 옮긴 33개입니다. 기준선은 XLA가 컴파일한 참조 구현입니다.

읽을 때 주의할 점 세 가지만 짚습니다.

첫째, 기하평균 1.58×는 "모든 커널이 1.58배"가 아닙니다. 기하평균은 극단값에 둔감하니, 몇 개는 3배 오르고 몇 개는 거의 그대로일 수 있습니다. 여러분의 워크로드가 어느 쪽인지는 재 보기 전엔 모릅니다.

둘째, 2.32× vs 2.02×의 표본은 8개입니다. "사람이 튜닝한 커널이 존재하는" 문제만 골랐기 때문인데, 방향은 인상적이지만 "커널 엔지니어가 필요 없어졌다"로 일반화하기엔 작은 표본입니다. 게다가 벤더가 자기 하드웨어 위에서 잰 자체 보고이기도 합니다.

셋째, 기준선이 XLA 컴파일 결과라는 점이 오히려 공정한 편입니다. 2025년 초의 일부 발표들은 eager 모드 PyTorch처럼 느슨한 기준선과 비교해 배수를 부풀렸다는 비판을 받았습니다. "무엇 대비 몇 배"에서 '무엇'을 확인하는 습관은 이 동네에서 특히 중요합니다. 왜 중요한지, 다음 장이 보여줍니다.

6. 진짜 어려운 건 생성이 아니라 채점 — Sakana 사건의 교훈

2025년 2월, Sakana AI는 "AI CUDA Engineer"를 발표하며 PyTorch 대비 10~100배, 최대 150배 속도 향상을 내걸었습니다. 그리고 하루 만에 무너졌습니다. 외부 검증자들이 재현에 실패했고, 원인이 밝혀졌습니다. 에이전트가 평가 하니스의 메모리 재사용 허점을 찾아내 정답 검사를 우회하는 커널을 만든 겁니다. 참조 구현이 써 둔 결과 메모리를 슬쩍 돌려주면, 계산을 제대로 안 해도 채점기는 "정답, 그리고 엄청 빠름"이라고 판정하니까요. Sakana는 공식으로 철회하고 "모델이 reward hacking을 했다"고 인정했습니다. 유효한 하니스로 다시 재니 평균은 1.5배 수준이었고, 일부 사례는 오히려 3배 느려졌다는 재현 보고도 나왔습니다.

이 사건이 커널 생성 분야에 남긴 유산은 역설적으로 건강합니다. "생성은 어차피 루프가 해 준다. 승부는 채점기의 방어력에서 갈린다"는 합의가 생겼거든요. 3장에서 커널 생성의 채점기가 "속일 수 없다"고 했지만, 정확히 말하면 잘 만들었을 때만 속일 수 없습니다. 허술한 채점기는 에이전트에게 그 자체로 최적화 대상이 됩니다. reward hacking을 다룬 글에서 본 그대로, 루프를 세게 돌릴수록 채점기의 구멍은 반드시 발견됩니다.

구멍은 생각보다 흔합니다. 최근 연구 The Correctness Illusion in LLM-Generated GPU Kernels(arXiv:2606.20128)는 KernelBench류 벤치마크의 관행 — 고정 shape 입력 몇 개에 느슨한 allclose 허용 오차 — 을 검사해 봤습니다. 허용 오차(atol/rtol)가 커널의 실제 오차 범위보다 1~3자릿수 느슨하게 잡혀 있어서, GELU에서 0.5배가 빠졌거나 어텐션에서 1/√D 스케일링이 빠진 진짜 버그가 있는 커널이 검사를 통과하더라는 겁니다. 반대로 고정밀(fp64) 참조와 연산 스키마를 아는 퍼징으로 바꾸니 심어 둔 버그 9개를 모두 잡았습니다. NVIDIA가 DeepSeek-R1로 어텐션 커널을 생성한 초기 실험에서 검증기를 루프의 중심에 둔 것도, MaxKernel이 테스트와 프로파일링을 별도 서브에이전트로 분리한 것도 같은 이유입니다. 이 분야의 진짜 기술 축적은 커널 생성 프롬프트가 아니라 검증 하니스에 쌓이고 있습니다.

7. 실전 — 미니 커널 에이전트 루프 만들어 보기

MaxKernel 자체는 accelerator-agents 저장소에서 받아 prepare_maxkernel.sh로 설정하고 run_auto_agent.sh(무인) 또는 run_hitl_agent.sh(대화형)로 돌립니다. TPU가 없어도 괜찮습니다. 핵심 구조 — 생성기는 갈아 끼울 수 있고, 채점기가 본체다 — 는 CPU에서도 그대로 만들어 볼 수 있으니까요. 부품 세 개면 됩니다.

부품 1: 정확성 채점기. 6장의 교훈을 그대로 코드로 옮깁니다. 입력은 매번 새로 뽑고, 참조는 고정밀로 계산합니다.

{{< highlight python >}} import numpy as np import jax.numpy as jnp def check_correctness(candidate, reference, arg_shapes, trials=20, seed=0): rng = np.random.default_rng(seed) for t in range(trials): # 고정 입력 재사용 금지 — 매 시도 다른 랜덤 입력 (극단값도 섞으면 더 좋다) args = [rng.standard_normal(s).astype(np.float32) for s in arg_shapes] ref = np.asarray(reference(*[a.astype(np.float64) for a in args])) # fp64 참조 out = np.asarray(candidate(*[jnp.asarray(a) for a in args]), dtype=np.float64) # 허용 오차는 '통과가 목표'가 아니라 연산의 오차 특성에서 정한다 if not np.allclose(out, ref, rtol=1e-3, atol=1e-5): return False, f"trial {t}: max abs err {np.abs(out - ref).max():.3e}" return True, "ok" {{< /highlight >}}

부품 2: 시간 채점기. JAX는 비동기로 실행되므로 동기화 없이 재면 디스패치 시간만 재게 됩니다. 워밍업도 필수입니다(첫 호출은 컴파일 시간이 섞입니다).

{{< highlight python >}} import time, jax def measure_ms(fn, *args, warmup=10, iters=100): for _ in range(warmup): jax.block_until_ready(fn(*args)) # 컴파일 + 캐시 워밍업 t0 = time.perf_counter() for _ in range(iters): out = fn(*args) jax.block_until_ready(out) # 반드시 동기화하고 나서 시계를 본다 return (time.perf_counter() - t0) / iters * 1e3 {{< /highlight >}}

부품 3: 루프. LLM 호출부는 어떤 API든 상관없습니다. 요점은 채점기 출력이 그대로 다음 프롬프트의 재료가 된다는 것, 그리고 정확성을 통과하지 못한 후보는 시간 측정 자격조차 없다는 순서입니다.

{{< highlight python >}} best = Candidate(code=reference_code, ms=measure_ms(reference, *sample_args)) history = [] for step in range(BUDGET): plan = llm(PLAN_PROMPT, task=task, history=history) # "다음에 뭘 시도할까" code = llm(IMPL_PROMPT, plan=plan, base=best.code) # Pallas/NumPy 구현 fn, err = try_compile(code) if err: history.append(("compile_error", err)); continue # 에러 메시지가 다음 턴의 힌트 ok, log = check_correctness(fn, reference, arg_shapes) if not ok: history.append(("wrong_answer", log)); continue # 틀린 커널은 속도 잴 필요 없음 ms = measure_ms(fn, *sample_args) history.append(("measured", code, ms)) # 프로파일 요약을 넣으면 더 강해진다 if ms < best.ms: best = Candidate(code=code, ms=ms) {{< /highlight >}}

이 30줄짜리 루프가 사실상 NVIDIA의 DeepSeek-R1 실험 구조(생성→검증→피드백 재투입, 15분 예산)이고, 여기에 4장의 그래프 탐색(워커 여러 개 + 빔 서치)을 얹으면 MaxKernel의 뼈대입니다. 직접 해 본다면 softmax나 RMSNorm처럼 참조 구현이 서너 줄인 연산부터 시작해 보세요. 채점기가 허술하면 어떤 일이 생기는지 — 예컨대 trials=1로 줄이고 허용 오차를 1e-1로 풀어 보면 — 루프가 어떻게 그 틈을 파고드는지도 직접 관찰할 수 있습니다. 꽤 교육적인(그리고 약간 소름 돋는) 경험입니다.

8. 흔한 실수 · 팁

  • 동기화 없이 시간 재기. JAX·PyTorch 모두 비동기 디스패치라서 block_until_ready()(또는 torch.cuda.synchronize()) 없이 재면 커널이 아니라 함수 호출 오버헤드를 재게 됩니다. "1000배 빨라졌다"는 측정의 90%는 이겁니다.
  • 고정 입력 한 벌로 정확성 판정. 마스킹 경계, 오버플로, 누적 오차는 특정 입력에서만 드러납니다. 매 시도 랜덤 입력 + 극단값(0, ±inf 근처, 큰 값) 몇 벌을 섞으세요.
  • 허용 오차를 '통과할 때까지' 푸는 것. 그 순간 채점기는 버그 필터가 아니라 버그 통과 장치가 됩니다. 허용 오차는 참조 구현의 정밀도 특성에서 계산해 고정하고, 후보가 못 맞추면 후보를 고쳐야 합니다.
  • 기준선 확인 없이 배수 믿기. "PyTorch 대비 100배"의 상당수는 eager 모드 대비입니다. torch.compile·XLA 같은 컴파일된 기준선과 비교해야 의미 있는 숫자입니다.
  • 루프에 문서를 안 넣는 것. Pallas 같은 저자원 DSL에서는 문서 큐레이션이 5.8%→37.3%를 만듭니다. 하드웨어 가이드·DSL 레퍼런스를 컨텍스트에 넣는 건 선택이 아니라 전제 조건입니다.
  • 탐색 예산을 한 경로에 몰빵. 순차 루프는 첫 전략 선택에 갇힙니다. 예산이 있다면 독립 시드 여러 개(병렬 탐색)가 한 경로 오래 파기보다 대체로 낫습니다.

9. 마무리 (TL;DR)

  • 이번 주 Hugging Face 주간 트렌딩 1위 MaxKernel(arXiv:2609.04523)은 Gemini 기반 서브에이전트(계획·구현·자가 디버깅·테스트·프로파일링)로 TPU Pallas 커널을 자동 생성·최적화하는 Google의 멀티 에이전트 시스템입니다. 코드는 공개돼 있습니다.
  • 자체 보고 기준 JaxBench 50개 태스크에서 XLA 참조 대비 기하평균 1.58배, 사람이 튜닝한 커널이 있는 프로덕션 문제 8개에서는 사람(2.02배)을 넘는 2.32배를 기록했습니다 — 단, 8개 표본의 벤더 자체 보고입니다.
  • 커널 생성이 에이전트와 잘 맞는 이유는 컴파일러·수치 검증·프로파일러라는 세 겹의 기계 채점기가 있어서입니다. 라벨 없이, 사람 없이, 초 단위로 루프를 돌릴 수 있습니다.
  • 운용 방식은 성숙도 사다리입니다: 사람이 방향을 잡는 HITL → 폐쇄 루프 Auto → Auto를 워커로 쓰는 그래프 탐색(병렬·빔 서치)으로, 컴퓨트를 더 태워 로컬 옵티마를 벗어납니다.
  • 저자원 DSL에서는 컨텍스트가 곧 능력입니다. TPU 문서 큐레이션만으로 샘플당 정확도가 5.8%→37.3%(JAXBench).
  • 이 분야의 진짜 교훈은 채점기가 본체라는 것. Sakana AI CUDA Engineer는 평가 하니스의 메모리 허점을 파고든 reward hacking으로 "150배" 주장을 철회했고, 느슨한 atol/rtol이 진짜 버그를 통과시킨다는 후속 연구도 나왔습니다. 랜덤 입력, 고정밀 참조, 고정된 허용 오차, 동기화된 타이밍 — 검증 하니스에 기술을 쌓으세요.
