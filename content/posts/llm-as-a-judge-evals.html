프롬프트를 한 줄 고쳤습니다. 더 좋아진 걸까요, 나빠진 걸까요? 답을 하나씩 눈으로 읽어 채점하면 스무 개는 하겠지만, 이천 개는 못 합니다.

— 그래서 LLM에게 채점을 맡깁니다. 단, 이 채점관에게도 편애가 있다는 걸 알고 써야 합니다.

LLM으로 무언가를 만들어 본 사람은 금방 벽에 부딪힙니다. 코드는 테스트를 돌리면 통과·실패가 딱 나오는데, LLM의 출력은 "요약이 잘 됐나?", "말투가 적절한가?", "질문에 제대로 답했나?"처럼 정답이 하나로 딱 떨어지지 않습니다. 프롬프트를 조금 바꾸거나 모델을 갈아탈 때마다 "이게 나아진 게 맞아?"를 확인해야 하는데, 매번 수백~수천 개의 답을 사람이 눈으로 읽어 채점할 수는 없습니다.

그래서 나온 방법이 LLM을 채점관으로 쓰는 것입니다. 사람 대신 또 다른 LLM에게 "이 답이 이 기준을 만족하니?"라고 물어 점수를 매기게 하는 방식이죠. 영어로는 LLM-as-a-judge라고 부르고, 이 글에서는 그 LLM을 채점관(judge)이라고 하겠습니다. 빠르고, 싸고, 밤새 수만 건도 돌립니다.

그런데 여기엔 함정이 있습니다. 이 채점관은 사람처럼 편향을 갖습니다. 앞에 놓인 답을 괜히 더 좋게 보고(위치 편향), 길고 장황한 답에 후한 점수를 주고(장황함 편향), 심지어 자기가 쓴 답을 편애합니다(자기 선호 편향). 편향을 모르고 채점 결과를 그대로 믿으면, "프롬프트가 좋아졌다"는 결론 자체가 착각일 수 있습니다.

이 주제가 2026년 내내, 특히 이번 주에 다시 화제가 된 이유가 있습니다. LLM 채점관을 프로덕션 평가 파이프라인에 넣는 팀이 급격히 늘면서, "그 채점관을 우리가 믿어도 되나?"를 대규모로 검증한 '채점관을 감사하다(auditing the judge)' 계열 연구가 쏟아졌습니다. 결론이 제법 뼈아픕니다 — 채점관을 다른 모델로 바꾸기만 해도 순위가 뒤집힌다는 겁니다. 이 글은 LLM 채점관이 어떻게 동작하고, 어디서 무너지며, 어떻게 하면 믿을 만하게 만드는지를 처음부터 끝까지 짚습니다.

1. 왜 채점이 어려운가 — 생성 태스크에는 정답이 없다

먼저 문제부터 봅시다. 전통적인 소프트웨어는 정답을 미리 알기 때문에 테스트가 쉽습니다. add(2, 3)은 5가 나와야 하고, 아니면 실패입니다. 그런데 "이 이메일을 정중하게 요약해줘"의 정답은 하나가 아닙니다. 표현이 조금 다른 좋은 답이 수십 가지죠.

이런 생성 태스크(generation task)를 자동으로 채점하려고 예전에는 BLEU·ROUGE 같은 글자 겹침(n-gram overlap) 지표를 썼습니다. "모범 답안과 단어가 얼마나 겹치나"를 세는 방식인데, 뜻은 같아도 단어가 다르면 점수가 낮게 나옵니다. "환불해 드리겠습니다"와 "환불 처리하겠습니다"는 사실상 같은 답인데 겹침 지표는 이걸 다르다고 봅니다. 의미를 못 읽는 거죠.

그렇다고 사람이 다 채점하면 느리고 비쌉니다. 프롬프트 한 줄 바꿀 때마다 평가셋 2,000건을 사람이 읽으면, 실험 한 번에 며칠이 걸립니다. 개발 속도가 여기서 다 죽습니다.

LLM 채점관은 이 두 문제를 동시에 풉니다. 의미를 읽을 줄 알고(겹침 지표의 한계를 넘고), 사람보다 훨씬 빠르고 쌉니다. 그래서 요즘 LLM 앱의 평가 루프는 대개 아래 그림처럼 돌아갑니다.

여기서 채점관은 단순한 도구가 아니라 개선 방향을 정하는 계기판입니다. 계기판이 편향돼 있으면 "좋아졌다"는 신호를 보고 엉뚱한 방향으로 최적화하게 됩니다. 그래서 채점관을 믿을 수 있게 만드는 일이 이렇게 중요합니다.

2. LLM-as-a-judge란 무엇인가

정의는 간단합니다. LLM-as-a-judge는 어떤 출력의 품질을 평가하기 위해 LLM에게 채점을 시키는 방법입니다. 채점관에게 주는 프롬프트에는 보통 세 가지가 들어갑니다 — (1) 원래 질문/맥락, (2) 채점할 답변(들), (3) 채점 기준표(rubric). 그러면 채점관이 "점수는 4점, 이유는 …"처럼 판정과 근거를 돌려줍니다.

이 아이디어를 널리 퍼뜨린 건 2023년의 MT-Bench 논문입니다. 이 연구에서 GPT-4를 채점관으로 썼더니 사람의 선호와 80% 넘게 일치했는데, 이는 사람 평가자끼리의 일치율과 맞먹는 수준이었습니다. "LLM이 사람만큼 채점할 수 있다"는 게 숫자로 증명된 순간이고, 이후 거의 모든 평가 프레임워크가 이 방식을 기본으로 채택합니다.

비유: LLM 채점관은 신입 조교에게 채점을 맡기는 것과 같습니다. 명확한 채점 기준표를 주면 꽤 잘합니다. 하지만 "알아서 좋은 답 골라줘"라고 기준을 안 주면, 그 조교의 취향(길고 자신감 있는 답을 선호하는 등)이 그대로 점수에 새어 나옵니다. 채점관의 품질은 8할이 기준표에서 나옵니다.

3. 채점 방식 3가지 — pointwise · pairwise · listwise

채점관에게 일을 시키는 방식은 크게 셋으로 나뉩니다. 뭘 고르느냐에 따라 비용과 신뢰도가 달라집니다.

  • pointwise(절대 점수) — 답변 하나를 놓고 "1~5점 중 몇 점"처럼 절대 점수를 매깁니다. 답변 개수만큼만 채점하면 되니 비용이 O(n)으로 싸고, 대시보드에 "평균 4.2점"처럼 찍기 좋습니다. 다만 절대 점수는 그날그날, 표현에 따라 미묘하게 흔들려서 모델끼리 순위 매기기엔 약합니다. 비슷한 답들에 다 3~4점을 줘 버리거든요.
  • pairwise(둘 비교) — 두 답변을 나란히 놓고 "A가 나은가, B가 나은가"를 고릅니다. 사람도 "이거 몇 점?"보다 "둘 중 뭐가 나아?"를 훨씬 일관되게 답하듯, 채점관도 비교가 더 안정적입니다. 프롬프트 A안 vs B안을 비교할 때 최적이죠. 대신 모든 쌍을 비교하면 O(n²)이라 개수가 많아지면 비쌉니다.
  • listwise(순위) — 여러 답변을 한꺼번에 주고 순위를 매깁니다. 호출 수는 줄지만 맥락이 길어지고, 뒤쪽 답변일수록 대충 보는 경향이 있어 신중히 써야 합니다.

실무 감각으로 정리하면: "이 답이 합격이야?"처럼 절대 판정이 필요하면 pointwise(기준표를 아주 구체적으로), "A안과 B안 중 뭐가 나아?"처럼 두 버전을 겨루게 할 땐 pairwise를 씁니다. pointwise를 더 똑똑하게 만든 대표 기법이 G-Eval인데, 채점관에게 먼저 "채점 단계"를 스스로 적게 한 뒤(chain-of-thought) 그 단계에 따라 점수를 매기게 해서 사람과의 일치도를 끌어올립니다.

4. 채점관의 편향 3형제

이제 핵심입니다. LLM 채점관은 사람처럼 체계적인 편향을 갖습니다. "가끔 틀린다"가 아니라 "특정 방향으로 꾸준히 치우친다"는 게 무섭습니다. 랜덤 오류는 평균 내면 사라지지만, 편향은 아무리 많이 돌려도 그대로 남거든요. MT-Bench 논문이 처음 정리한 이후 수많은 연구가 재확인한 3형제를 봅시다.

  • 위치 편향(position bias) — pairwise에서 두 답을 A, B 순으로 보여 주면, 내용과 상관없이 특정 위치(주로 앞)를 더 자주 고릅니다. 심한 경우 완전히 똑같은 두 답을 줘도 앞을 고릅니다. 연구에 따라 대략 5~15%p 수준의 체계적 쏠림이 보고됩니다.
  • 장황함 편향(verbosity bias) — 더 길고 자세해 보이는 답에 높은 점수를 줍니다. 실제로 더 정확한지와는 별개로요. 채점관이 "열심히 썼네"를 "잘 썼네"로 착각하는 셈입니다.
  • 자기 선호 편향(self-preference bias) — 채점관이 자기와 같은 모델군이 생성한 답을 더 좋게 봅니다. 그래서 A사 모델로 답을 만들고 같은 A사 모델로 채점하면, 그 답에 은근히 후한 점수가 나옵니다.

여기에 하나 더 — 채점관은 자기 답에 대한 확신이 매번 조금씩 달라서, 같은 답을 두 번 채점하면 점수가 다르게 나오기도 합니다(일관성 문제). 편향은 방향이 있는 오류, 이건 흔들림이라 성격이 다릅니다. 둘 다 잡아야 합니다.

5. 믿을 수 있는 채점관 만들기 — 5가지 원칙

다행히 편향은 설계로 상당 부분 눌러낼 수 있습니다. 프로덕션에서 통하는 5가지 원칙입니다.

  1. 기준표를 구체적으로, 한 번에 하나씩. "좋은 답인가?"처럼 뭉뚱그리면 채점관 취향이 새어 나옵니다. "① 질문에 실제로 답했는가 ② 사실이 정확한가 ③ 요청한 형식(JSON)을 지켰는가"처럼 기준을 쪼개고, 각 기준을 따로 채점하세요. 여러 축을 한 점수에 뭉치면 뭐 때문에 낮은 점수인지 알 수 없습니다.
  2. 순서를 뒤집어 두 번 물어라(위치 편향). pairwise에서 A→B로 한 번, B→A로 한 번 물어서 두 번 다 같은 답이 이길 때만 승리로 인정합니다. 엇갈리면 무승부로 처리하세요. 위치 편향을 잡는 가장 강력한 한 방입니다.
  3. 생성 모델과 채점 모델을 다른 계열로(자기 선호). 답을 만든 모델과 채점하는 모델을 같은 계열로 쓰지 마세요. 가능하면 채점관은 별도 모델로 고정합니다.
  4. 사람 라벨과 주기적으로 대조하라(calibration). 사람이 채점한 소규모 '골든셋'(예: 100~200건)을 만들어 두고, 채점관 점수가 사람과 얼마나 일치하는지 Cohen's kappa 같은 지표로 정기적으로 확인합니다. 카파는 "우연히 맞을 확률을 뺀 진짜 일치도"라서, 단순 일치율보다 정직합니다. 일치도가 낮으면 채점관 프롬프트나 기준표를 고쳐야 한다는 신호입니다.
  5. 판정과 근거를 로그로 남겨라(observability). 점수만 저장하지 말고 채점관이 왜 그렇게 판정했는지 이유도 함께 남기세요. 나중에 "이 채점 왜 이래?"를 추적할 수 있고, 채점관이 헛다리를 짚는 패턴을 발견하게 됩니다.
가장 흔한 착각: "더 똑똑한 채점관 모델을 쓰면 편향이 사라지겠지?" 아닙니다. 최신 프런티어 모델도 어려운 편향 테스트에서 절반 넘게 틀린다는 2026년 보고가 있습니다. 편향은 모델을 키운다고 없어지는 게 아니라, 위 설계로 걸러 내는 것입니다.

6. 직접 해보기 (1) — 기준표 기반 pointwise 채점관

말로만 하면 감이 안 오니 코드로 봅시다. 먼저 기준을 쪼갠 pointwise 채점관입니다. 핵심은 (1) 기준을 명확히 적고, (2) 근거를 먼저 쓰게 한 뒤 점수를 내게 하고, (3) 파싱하기 쉽게 JSON으로 받는 것입니다. (예시는 Anthropic Python SDK 스타일이지만, 어떤 LLM 클라이언트로도 똑같이 됩니다.)

{{< highlight python >}} import json from anthropic import Anthropic client = Anthropic() # 기준을 '쪼개서' 각각 따로 채점하게 한다. 한 점수에 여러 축을 뭉치지 않는다. JUDGE_PROMPT = """당신은 고객지원 답변을 채점하는 엄격한 채점관입니다. 아래 [질문]에 대한 [답변]을 다음 세 기준으로 각각 0 또는 1점으로 채점하세요. 1. answered: 질문에 실제로 답했는가 (인사만 하고 안 답하면 0) 2. correct: 내용이 사실에 맞는가 (근거 없는 추측이면 0) 3. format: 요청한 형식(3문장 이내)을 지켰는가 먼저 각 기준마다 한 문장으로 '이유'를 적고, 그 다음에 점수를 정하세요. 길이나 말투에 현혹되지 마세요. 근거가 부족하면 망설이지 말고 0을 주세요. 반드시 아래 JSON만 출력하세요: {"reason": {"answered": "...", "correct": "...", "format": "..."}, "score": {"answered": 0, "correct": 0, "format": 0}} [질문] %s [답변] %s""" def judge_pointwise(question: str, answer: str) -> dict: msg = client.messages.create( model="claude-sonnet-4-5", # 채점관은 생성 모델과 '다른' 것으로 고정 max_tokens=500, temperature=0, # 채점은 재현성이 생명 → 온도 0 messages=[{"role": "user", "content": JUDGE_PROMPT % (question, answer)}], ) return json.loads(msg.content[0].text) result = judge_pointwise( question="환불은 며칠 걸리나요? 3문장 이내로.", answer="안녕하세요! 문의 주셔서 감사합니다. 좋은 하루 되세요!", # 정작 답을 안 함 ) print(result["score"]) # → {'answered': 0, 'correct': 0, 'format': 1} {{< /highlight >}}

포인트가 몇 개 있습니다. temperature=0으로 흔들림을 줄이고, 기준을 answered / correct / format으로 쪼개서 각각 채점하게 했습니다. 그래야 "왜 낮은 점수인지"가 분명해집니다. 또 "근거를 먼저 쓰고 점수를 내라"고 시켜서, 채점관이 대충 숫자부터 던지지 못하게 합니다(이유를 쓰다 보면 판단이 정교해집니다).

팁: 점수를 1~5점 같은 넓은 척도로 받으면 채점관이 애매하게 다 3~4점을 줍니다. 위처럼 0/1의 명확한 기준으로 쪼개면 훨씬 일관됩니다. "5점 만점에 4.2"보다 "세 기준 중 몇 개 통과"가 실무에선 더 쓸모 있습니다.

7. 직접 해보기 (2) — 순서를 뒤집는 pairwise 채점관

이번엔 프롬프트 A안과 B안 중 어느 쪽이 나은지 겨루게 하는 pairwise 채점관입니다. 핵심은 순서를 뒤집어 두 번 물어 위치 편향을 걸러 내는 것입니다.

{{< highlight python >}} PAIR_PROMPT = """두 답변 중 [질문]에 더 잘 답한 쪽을 고르세요. 길이가 길다고 더 좋은 게 아닙니다. 사실 정확성과 질문 적합성만 보세요. "1" 또는 "2"만, 그 이유 한 문장과 함께 JSON으로 출력하세요. {"winner": 1, "reason": "..."} [질문] %s [답변 1] %s [답변 2] %s""" def _ask(question, first, second) -> int: msg = client.messages.create( model="claude-sonnet-4-5", max_tokens=200, temperature=0, messages=[{"role": "user", "content": PAIR_PROMPT % (question, first, second)}], ) return json.loads(msg.content[0].text)["winner"] # 1 또는 2 def judge_pairwise(question: str, a: str, b: str) -> str: # ① A를 앞에, B를 뒤에 두고 판정 w1 = _ask(question, a, b) # 1이면 A, 2면 B # ② 순서를 뒤집어 B를 앞에, A를 뒤에 두고 다시 판정 w2 = _ask(question, b, a) # 1이면 B, 2면 A first_says = "A" if w1 == 1 else "B" second_says = "B" if w2 == 1 else "A" # 두 번 다 같은 답이 이겨야 진짜 승리. 엇갈리면 무승부(위치 편향 의심). if first_says == second_says: return first_says return "tie" print(judge_pairwise("환불 절차를 알려줘", a="환불은 영업일 3일 내 처리됩니다. 마이페이지에서 신청하세요.", b="네, 환불 도와드리겠습니다! 저희는 항상 최선을 다합니다!")) # → "A" (순서를 바꿔도 A가 이기면 진짜 A 우세) {{< /highlight >}}

이 짧은 함수가 하는 일이 바로 5번 원칙의 2번, 순서 뒤집기입니다. LLM을 두 번 부르니 비용은 두 배지만, 위치 편향에 속아 잘못된 결론을 내는 것보단 훨씬 쌉니다. 아래 그림이 흐름입니다.

8. 이번 주의 화제 — '채점관을 감사하다'

2026년 들어 LLM 채점관이 진지한 프로덕션 평가의 표준이 되면서, "그 채점관 자체를 얼마나 믿을 수 있나"를 대규모로 감사하는 연구가 줄줄이 나왔습니다. 이번 주에도 관련 논문이 arXiv에 올라오며 실무자 사이에서 다시 화제가 됐습니다.

대표적인 대규모 감사 연구 하나는 9개 제공사의 채점관 21종을 MT-Bench·JudgeBench·RewardBench 등에서 118회에 걸쳐 약 54만 건을 판정하게 하고 뜯어봤습니다. 결과가 인상적입니다 — 채점관을 어느 모델로 쓰느냐에 따라 같은 대상의 순위가 최대 14계단까지 뒤집혔고, "같은 답을 다시 채점하면 같은 점수가 나오는" 재현성(test-retest)이 높은 채점관조차 심한 위치 편향을 함께 갖고 있었습니다. 즉 일관되게 채점하는 것과 올바르게 채점하는 것은 별개라는 뜻입니다("Reliability without Validity").

실무자에게 이게 주는 교훈은 분명합니다. 채점관을 바꾸는 건 설정 하나 바꾸는 게 아니라, 평가셋을 통째로 이사하는 일과 같습니다. 어제까지 잘 나오던 점수가 채점관 모델 업그레이드 한 번에 달라질 수 있으니, 채점관 버전을 고정하고, 바꿀 땐 사람 골든셋으로 다시 대조해야 합니다. "우리 앱이 좋아졌다"는 결론의 신뢰도는 결국 채점관의 신뢰도를 넘지 못합니다.

9. 흔한 실수 · 팁

흔한 실수왜 문제인가어떻게
"좋은 답인지 채점해줘"처럼 기준 없이 맡김채점관 취향(길이·자신감)이 그대로 점수가 됨기준을 쪼개 명시하고 각각 채점
pairwise에서 순서 고정위치 편향에 속아 잘못된 승자A→B, B→A 두 번 물어 둘 다 같아야 승
생성=채점 같은 모델자기 선호 편향으로 후한 점수채점관은 다른 계열로 고정
사람 라벨과 한 번도 안 맞춰봄채점관이 엉뚱해도 눈치 못 챔골든셋으로 kappa 정기 점검
점수만 저장, 이유는 버림이상 채점을 추적 불가판정 근거도 함께 로그
temperature를 높게 둠같은 답에 점수가 매번 달라짐채점은 temperature=0
1~10점 같은 넓은 척도다 5~7점에 몰려 변별 안 됨0/1 또는 좁은 척도 + 명확한 기준
실전 팁: 처음부터 완벽한 채점관을 만들려 하지 말고, 사람 골든셋 100건부터 만드세요. 그걸로 채점관과 사람의 일치도를 재고, 안 맞는 케이스를 보며 기준표를 고치는 겁니다. 채점관 개발도 결국 하나의 반복(iteration) 루프입니다 — 채점관을 채점하는 셈이죠.

10. 마무리 (TL;DR)

  • LLM-as-a-judge는 정답이 하나로 안 떨어지는 생성 태스크를, 사람 대신 LLM에게 채점시켜 빠르고 싸게 평가하는 방법입니다. 잘 만든 채점관은 사람과 80% 넘게 일치합니다.
  • 채점 방식은 pointwise(절대 점수) · pairwise(둘 비교) · listwise(순위). 합격/불합격엔 pointwise, 두 버전 비교엔 pairwise가 안정적입니다.
  • 채점관에겐 편향 3형제가 있습니다 — 위치 편향, 장황함 편향, 자기 선호 편향. 모델을 키운다고 사라지지 않습니다.
  • 믿을 수 있게 만드는 5원칙: 기준 쪼개기 · 순서 뒤집기 · 다른 모델로 채점 · 사람 골든셋과 대조(kappa) · 근거 로깅.
  • 2026년 감사 연구의 교훈: 채점관을 바꾸면 순위가 바뀐다. 일관성과 정확성은 별개이니, 채점관 버전을 고정하고 사람과 주기적으로 맞춰 보세요.
