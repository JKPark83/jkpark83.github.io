1. 도입 — 데모의 저주: 한 번은 되는데, 매일 돌리면 무너진다

에이전트를 만들어 본 분이라면 이 장면이 낯설지 않을 겁니다. 시연에서는 환불 처리도, 예약 변경도 매끄럽게 해내던 에이전트가, 실제 운영에 들어가면 이틀에 한 번꼴로 이상한 짓을 합니다. 환불은 했는데 재고를 안 돌려놓거나, 예약을 바꾸랬더니 새 예약을 하나 더 만들어 놓거나. 그런데 로그를 열어 보면 에이전트는 매번 자신 있게 "처리 완료했습니다!"라고 말하고 깔끔하게 종료했습니다. 뭐가 문제였을까요?

이번 주(8월 셋째~넷째 주) AI 엔지니어링 판에서 가장 화제가 된 결과물이 정확히 이 문제를 겨냥합니다. Microsoft가 8월 19일 블로그와 함께 공개하고 이튿날 arXiv에 올린 ThinkingBox(arXiv:2608.19741)는 에이전트를 업무 시나리오 샌드박스에서 반복 실행하고, 에이전트의 응답이 아니라 백엔드 데이터베이스의 최종 상태로 채점하는 오픈소스 프레임워크입니다. 함께 공개된 벤치마크 ThinkingBox-Bench는 Hugging Face 데일리 페이퍼 트렌딩 상위권에 올랐고, "신뢰성(reliability)이 이제 에이전트 도입의 구매 기준이 됐다"는 논평이 여러 매체와 커뮤니티에서 이어졌습니다.

결과는 뼈아픕니다. 12개 모델을 507개 태스크에서 각 20번씩 돌렸더니, 가장 강한 모델도 첫 시도 성공률(pass@1)은 65.36%였지만 20번 전부 성공한 태스크는 25.25%뿐이었습니다. 그리고 실패한 시도의 80.88%는 에러 없이 깨끗하게 종료했고, 상태를 바꾸는 툴콜까지 성공적으로 날렸습니다. 즉 겉보기 신호만 보면 성공과 구분이 안 되는 "그럴듯한 실패"가 대부분이었다는 뜻입니다.

이 글에서 얻어 갈 것. ① 응답 평가·궤적 평가·상태 평가의 차이, ② pass@k와 pass^k가 왜 완전히 다른 질문인지, ③ ThinkingBox 샌드박스의 6가지 구성 요소와 검증 방식, ④ 65.36% → 25.25% 숫자를 해석하는 법(그리고 왜 이 숫자가 수학적으로 흥미로운지), ⑤ 내 에이전트에 바로 붙일 수 있는 sqlite 기반 미니 상태 검증 하니스 코드.

2. 배경 — 에이전트 평가의 세 층위와 pass@k vs pass^k

에이전트 평가는 "무엇을 보고 채점하느냐"에 따라 세 층위로 나눌 수 있습니다.

① 응답 평가는 에이전트의 최종 답변 텍스트를 사람이나 LLM 심판(LLM-as-a-judge)이 채점합니다. 만들기 가장 쉽지만, 에이전트가 "처리 완료했습니다"라고 말만 잘하면 통과해 버립니다. ② 궤적 평가는 툴 호출 로그를 봅니다. 올바른 툴을 올바른 순서로 불렀는지 확인할 수 있지만, "올바른 순서"가 여러 개인 태스크에서는 채점 기준을 정하기 어렵고, 툴콜이 성공했다고 태스크가 끝난 것도 아닙니다. ③ 상태 평가는 실행이 끝난 뒤 환경 — 대개 데이터베이스 — 을 열어 보고, 기대한 변화가 실제로 일어났는지(그리고 일어나면 안 될 변화가 없는지) 확인합니다. 이 방식을 대중화한 것이 2024년 Sierra의 τ-bench입니다. 대화가 끝난 시점의 DB 상태를 정답 상태와 비교하고, 신뢰성을 재는 지표로 pass^k를 제안했습니다.

여기서 pass@k와 pass^k를 확실히 구분하고 넘어가야 합니다. 생김새는 비슷하지만 완전히 다른 질문입니다.

  • pass@k — k번 시도해서 적어도 한 번 성공할 확률. "이 모델이 이 태스크를 풀 수 있는가?"라는 능력(capability)의 질문입니다.
  • pass^k — k번 시도해서 전부 성공할 확률. "이 모델에게 이 태스크를 맡겨도 되는가?"라는 신뢰성(reliability)의 질문입니다.

시도가 독립이고 시도당 성공률이 p라면 pass^k는 pk로 떨어집니다. p=0.7인 에이전트도 세 번 연속 성공할 확률은 0.7³ = 34.3%뿐입니다. 데모(한 번 성공 = pass@1)와 운영(매일 성공 = pass^k)의 간극이 바로 이 지수 함수 안에 있습니다. 자동화의 가치는 대개 "같은 일을 반복해서 맡기는 것"에서 나오므로, 실무에서 의미 있는 지표는 pass^k 쪽입니다.

3. ThinkingBox 해부 — 말이 아니라 DB 상태를 검증하는 샌드박스

ThinkingBox는 이 상태 평가를 "업무 워크플로" 규모로 확장한 도구-에이전트-유저 상호작용(tool-agent-user interaction) 샌드박스입니다. 태스크 하나가 어떻게 구성되는지 뜯어 보면 구조가 명확해집니다.

구성 요소는 여섯 가지입니다.

  1. 리셋 가능한 백엔드 DB — 태스크마다 정해진 초기 상태(시드)로 되돌릴 수 있는 데이터베이스. 반복 실행의 전제 조건입니다.
  2. 격리된 MCP 호환 툴 세션 — 에이전트는 MCP(Model Context Protocol) 방식으로 노출된 도메인 툴로만 DB를 조작합니다. 세션이 격리되어 있어 시도끼리 상태가 새지 않고, 실행 트레이스가 전부 기록됩니다.
  3. 도메인 정책 문서 + 지식 베이스 — "30일 이내 구매 건만 환불 가능" 같은 업무 규칙. 태스크 대부분이 이 정책을 조건으로 겁니다(policy-conditioned).
  4. 시뮬레이션 유저 — LLM이 연기하는 고객/직원. 중요한 설계가 하나 있는데, 유저는 태스크 해결에 필요한 사실을 처음부터 다 말해주지 않습니다. 에이전트가 물어봐야 나옵니다. 정보 수집 능력까지 시험하는 장치입니다.
  5. 평가 대상 에이전트 — 우리가 시험하려는 모델/시스템.
  6. 검증기 — 대화가 끝나면 DB의 최종 상태를 태스크별 기대 상태와 비교합니다. 여기에 더해 부수 효과(collateral effect), 즉 일어나면 안 될 변화가 없는지도 검사합니다. 환불은 제대로 했지만 엉뚱한 주문을 하나 취소했다면 실패입니다.

벤치마크인 ThinkingBox-Bench는 이런 태스크 507개를 다섯 도메인 — 리테일/이커머스, 여행·호스피탈리티, 자동차 보험, 네오뱅크 사내 IT 지원, 컨설팅사 IT/HR 지원 — 에 걸쳐 담았습니다. 다중 단계 트랜잭션, 정책 조건부 갱신, 유저 재질문, 레코드 조회, 그리고 되돌릴 수 없는 고위험 부수 효과처럼 실제 업무 지원에서 반복되는 패턴을 일부러 밟게 설계했습니다. τ-bench가 항공·리테일 2개 도메인으로 증명한 방법론을 도메인 다양성과 태스크 수 면에서 크게 확장한 셈입니다.

왜 "말"을 채점하면 안 될까? 상태를 바꾸는 태스크에서는 응답 텍스트가 성공의 증거가 아니기 때문입니다. 에이전트는 자기가 실패했다는 사실을 모른 채 성공 보고를 하는 경우가 많습니다. 반대로 정답 상태에 도달하는 경로는 여러 개일 수 있으므로, 궤적(툴 호출 순서)을 정답과 비교하는 방식은 멀쩡한 성공을 실패로 채점하기도 합니다. 최종 상태 비교는 두 문제를 동시에 피합니다.

4. 숫자 읽기 — 65.36% vs 25.25%, 그리고 '그럴듯한 실패' 80.88%

Microsoft는 독점 모델과 오픈 웨이트 모델 12개를 507개 태스크 × 20회 반복으로 평가했습니다. 헤드라인 숫자 세 개만 기억하면 됩니다.

첫째, 65.36% → 25.25%. 논문이 discovery–reliability gap이라 부르는 간극입니다. 성공 궤적을 한 번 "발견"하는 능력과 그 궤적을 매번 재현하는 능력은 다르며, 현재 최강 모델도 업무 태스크 4개 중 1개에서만 20연속 성공을 해냈습니다.

둘째, 25.25%라는 값 자체가 시사하는 구조. 잠깐 계산해 보면 재미있는 게 보입니다. 만약 모든 태스크의 시도당 성공률이 균일하게 65.36%라면 pass^20은 0.6536²⁰ ≈ 0.02%여야 합니다. 실제로는 25.25%가 나왔다는 것은, 태스크 성공률이 평균 근처에 모여 있는 게 아니라 "거의 항상 되는 태스크"와 "가끔만 되는 태스크"로 양극화되어 있다는 뜻입니다(이 문단의 해석은 필자의 계산입니다). 실무적 함의는 분명합니다. 평균 성공률은 자동화 범위를 정하는 데 거의 쓸모가 없고, 태스크 단위로 pass^k를 재서 "항상 되는 부류"만 골라 자동화해야 합니다.

셋째, 실패의 80.88%가 그럴듯한 실패. 실패한 시도의 대다수가 에러 없이 종료했고 유효한 상태 변경 툴콜까지 날렸습니다. 응답 수준·툴콜 수준의 신호는 태스크 완수의 프록시(대리 지표)가 못 된다는 뜻입니다. 여러분의 대시보드에 "툴콜 성공률 99%"가 찍혀 있어도, DB를 열어 보기 전까지는 에이전트가 일을 제대로 했는지 알 수 없습니다.

도메인별 성적 변동도 컸고, 실패 유형에는 오류 후 복구 실패와 잘못된 상태 변경이 두드러졌습니다. 즉 모델이 "툴을 못 써서"가 아니라, 여러 턴에 걸친 상태 관리와 회복에서 무너집니다.

5. 실전 — 내 에이전트에 상태 검증 하니스 붙이기

ThinkingBox-Bench 자체는 벤치마크지만, 방법론은 그대로 훔쳐 올 수 있습니다. 필요한 건 세 가지입니다: 리셋 가능한 시드 상태, 상태로 정의된 성공 기준, k회 반복 루프. sqlite로 만드는 최소 골격을 보겠습니다.

먼저 태스크를 "기대 상태 + 금지 부수 효과"로 정의합니다. 자연어 채점 기준이 아니라 실행 가능한 assertion이라는 점이 핵심입니다.

{{< highlight python >}} # task_refund.py — 태스크를 '상태'로 정의한다 TASK = { "task_id": "refund-1042", "prompt": "주문 1042번 환불해 주세요.", # 시뮬레이션 유저의 첫 발화 "hidden_facts": { # 물어봐야 알려주는 정보 "reason": "defective", "customer_id": "C-77", }, # 성공 조건: 실행 후 DB가 만족해야 할 상태 "expected": [ ("SELECT status FROM orders WHERE id=1042", [("refunded",)]), ("SELECT amount FROM refunds WHERE order_id=1042", [(39000,)]), ("SELECT qty FROM inventory WHERE sku='A-1'", [(13,)]), # 재고 복구 12→13 ], # 금지 부수 효과: 건드리면 안 되는 것들 "forbidden": [ ("SELECT COUNT(*) FROM orders WHERE status='cancelled'", [(0,)]), # 다른 주문 취소 금지 ("SELECT COUNT(*) FROM refunds", [(1,)]), # 환불은 정확히 1건 ], } {{< /highlight >}}

다음은 하니스입니다. 시드 리셋 → 에이전트 실행 → 상태 검증을 k번 반복해 pass^k를 계산합니다.

{{< highlight python >}} # harness.py — 시드 리셋 → 실행 → 상태 검증 → k회 반복 import shutil, sqlite3 SEED_DB, RUN_DB = "seed.db", "run.db" def reset(): shutil.copy(SEED_DB, RUN_DB) # 매 시도 전, 반드시 시드 상태로 복원 def verify(task) -> tuple[bool, list[str]]: con = sqlite3.connect(RUN_DB) errors = [] for sql, want in task["expected"] + task["forbidden"]: got = con.execute(sql).fetchall() if got != want: errors.append(f"{sql} → {got} (기대: {want})") con.close() return (not errors), errors def pass_hat_k(task, run_agent, k=10): ok = 0 for i in range(k): reset() run_agent(task, db_path=RUN_DB) # 에이전트의 '말'은 여기서 안 본다 passed, errors = verify(task) # DB 최종 상태만 본다 ok += passed if not passed: print(f"[trial {i}] 실패: {errors[:2]}") print(f"pass@1≈{ok/k:.0%}, pass^{k}={'성공' if ok == k else '실패'}") return ok == k {{< /highlight >}}

여기서 run_agent는 여러분의 에이전트 루프입니다. 반환값(응답 텍스트)을 채점에 쓰지 않는다는 점, 그리고 verify가 기대 상태와 금지 부수 효과를 함께 검사한다는 점만 지키면, 이 30줄이 응답 채점 하니스보다 훨씬 정직한 신호를 줍니다. 유저와의 멀티턴이 필요하면 run_agent 안에서 hidden_facts를 가진 작은 유저 시뮬레이터 LLM을 붙이면 됩니다 — "묻기 전엔 답하지 말 것"이라는 시스템 프롬프트가 포인트입니다.

실제 서비스 DB가 sqlite가 아니어도 원리는 같습니다. Postgres라면 템플릿 DB 복제나 트랜잭션 롤백으로 시드 리셋을 구현하고, 외부 SaaS 툴이라면 스테이징 테넌트를 하나 잡아 태스크 전후 스냅샷을 비교하면 됩니다. 더 크게 가고 싶다면 ThinkingBox 공개 저장소의 도메인 정의를 참고해 자기 도메인의 태스크를 작성하는 방법이 있습니다.

CI에 거는 법. 핵심 태스크 10~20개를 골라 pass^k(k=5~10)를 CI 게이트로 겁니다. 프롬프트나 툴 정의를 바꿨을 때 "평균 점수 1%p 하락"은 눈에 안 띄지만, "환불 태스크가 pass^5에서 탈락"은 바로 잡힙니다. 반복 비용이 부담되면, 항상 통과하던 태스크는 k를 줄이고 경계선 태스크에 k를 몰아주는 식으로 예산을 배분합니다.

6. 흔한 실수 · 팁

  • 응답 텍스트로 채점하기. "처리 완료했습니다"는 증거가 아닙니다. 실패의 80.88%는 겉보기에 멀쩡했습니다. 상태를 바꾸는 태스크는 반드시 상태로 채점하세요.
  • LLM 심판에게 DB를 안 보여주고 판정 맡기기. 심판 모델에게 대화 로그만 주면 에이전트와 같은 것에 속습니다. LLM 심판은 어조·정책 위반 같은 정성 평가에 쓰고, 상태 판정은 결정론적 쿼리로 하세요.
  • 1회 실행으로 결론 내리기. pass@1은 능력의 하한 증명일 뿐입니다. 자동화 여부를 정할 때는 태스크당 최소 5~10회 돌려 pass^k를 보세요. 온도를 0으로 내려도 툴 결과·유저 발화가 달라지면 궤적은 갈라집니다.
  • 시드 리셋을 빼먹기. 이전 시도가 남긴 상태 위에서 다음 시도를 돌리면 성공도 실패도 오염됩니다. "리셋 가능한 백엔드"가 ThinkingBox 설계의 출발점인 이유입니다. 리셋이 안 되는 실환경 테스트는 반복 평가가 아니라 도박입니다.
  • 부수 효과를 안 보기. 기대 상태 assertion만 있으면 "환불 성공 + 엉뚱한 주문 취소"가 통과합니다. 건드리면 안 되는 테이블의 불변 조건을 forbidden 목록으로 함께 거세요. 되돌릴 수 없는 고위험 액션일수록 중요합니다.
  • 과잉 친절한 유저 시뮬레이터. 시뮬레이터가 첫 턴에 정보를 다 쏟아내면 에이전트의 정보 수집 능력이 평가에서 빠집니다. 실제 유저는 그렇게 말해주지 않습니다. 사실을 숨겨 두고 물어야 답하게 만드세요.
  • 반복 비용 과소평가. 507개 태스크 × 20회 × 12개 모델이면 12만 회가 넘는 롤아웃입니다. 자체 평가에서는 태스크 수를 좁히고 k를 차등 배분해 비용을 통제하세요. 전수 × 고반복은 벤치마크 제작자의 사치입니다.

7. 마무리 (TL;DR)

  • Microsoft가 8월 19일 공개한 ThinkingBox는 에이전트를 업무 시나리오 샌드박스에서 반복 실행하고, 응답이 아니라 백엔드 DB의 최종 상태로 채점하는 오픈소스 프레임워크입니다. 벤치마크 ThinkingBox-Bench는 5개 도메인 507개 태스크로 구성됩니다.
  • 구성 요소는 여섯 가지: 리셋 가능한 DB, 격리된 MCP 호환 툴 세션, 정책 문서+지식 베이스, 정보를 숨기는 유저 시뮬레이터, 평가 대상 에이전트, 그리고 기대 상태와 부수 효과를 함께 검사하는 검증기.
  • 핵심 결과: 최강 모델도 pass@1 65.36% vs pass^20 25.25% — 한 번 성공하는 능력과 매번 성공하는 신뢰성 사이의 discovery–reliability gap이 큽니다.
  • 실패의 80.88%는 깨끗하게 종료하고 유효한 상태 변경 툴콜까지 성공한 "그럴듯한 실패"였습니다. 툴콜 성공률·응답 품질은 태스크 완수의 프록시가 아닙니다.
  • 방법론은 오늘 훔칠 수 있습니다: 시드 리셋 → 에이전트 실행 → 상태 assertion(기대 + 금지) → k회 반복. 핵심 태스크의 pass^k를 CI 게이트로 걸면 회귀를 즉시 잡습니다.
  • 평균 성공률 말고 태스크 단위 pass^k를 보세요. 자동화할 태스크를 고르는 기준은 "가끔 되는 것"이 아니라 "항상 되는 것"입니다.
