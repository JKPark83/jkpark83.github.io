1. 왜 벡터 검색이 비싸지는가

RAG(retrieval-augmented generation, 검색으로 문서를 찾아 LLM에 붙여 주는 방식)를 처음 붙일 때는 대개 문제가 없습니다. 문서 몇천 개를 임베딩해 벡터 DB에 넣고, 질문이 오면 가까운 벡터를 찾아 LLM에 넘기면 끝이니까요. 그런데 서비스가 커져 문서가 수백만 개, 수천만 개로 늘면 이야기가 달라집니다.

가장 먼저 아파 오는 곳은 메모리입니다. 벡터 검색이 빠른 이유는 벡터를 디스크가 아니라 RAM에 올려 두고 비교하기 때문인데, 임베딩이 float32(32비트 부동소수점)라면 이 RAM 요구량이 문서 수에 정비례해 커집니다. 1024차원 벡터 하나가 1024 × 4바이트 = 4KB, 100만 개면 약 4GB, 1억 개면 약 400GB. 인덱스 오버헤드까지 더하면 실제로는 더 나갑니다. 여기서부터는 “더 큰 인스턴스”가 곧 “더 큰 청구서”입니다.

그래서 이번 주 검색·RAG 실무자들 사이에서 다시 화제가 된 게 임베딩 양자화(embedding quantization)입니다. Vespa가 Matryoshka 임베딩과 바이너리 양자화를 한데 묶어 벡터 검색 비용을 크게 줄이는 방법을 정리해 올렸고, “양자화와 Matryoshka로 벡터 검색 비용을 80% 줄였다”는 사례 글이 커뮤니티에서 널리 공유됐습니다. 핵심 아이디어는 놀랄 만큼 단순합니다 — 벡터를 굳이 float32로 저장할 필요가 없다는 겁니다.

한 줄 요약. 임베딩 양자화는 float32 벡터를 int8(1바이트)이나 1비트로 압축해 메모리·속도를 4~32배 벌고, 그렇게 잃은 정확도는 원본 벡터로 상위 후보만 다시 채점(rescore)해 되찾는 기법입니다.

2. 배경 — 임베딩과 float32의 무게

임베딩(embedding)은 텍스트를 숫자 벡터로 바꾼 것입니다. “고양이”와 “강아지”는 벡터 공간에서 가깝고, “고양이”와 “주식”은 멀죠. 벡터 검색은 이 거리를 재서 질문과 가까운 문서를 찾습니다. 대표적인 임베딩 모델은 벡터 차원이 768(e5-base), 1024(mxbai·Cohere), 1536(OpenAI text-embedding-3-small)쯤 됩니다.

문제는 각 차원의 값을 float32, 즉 4바이트로 저장한다는 데 있습니다. 아래 계산을 보면 무게가 실감 납니다.

“그러면 값을 대충 줄여도 검색이 될까?”가 자연스러운 의문입니다. 놀랍게도 됩니다. 임베딩이 담고 있는 건 정확한 좌표값이 아니라 방향과 상대적 위치에 가깝기 때문입니다. 소수점 아래를 조금 뭉개도 “고양이는 강아지 쪽, 주식은 반대쪽”이라는 큰 구도는 잘 살아남습니다. 이 여유를 활용하는 게 양자화입니다.

3. 스칼라 양자화(int8) — 4배 줄이기

가장 온건한 방법은 스칼라 양자화(scalar quantization)입니다. float32 값을 int8, 즉 −128부터 127까지 256단계 정수로 옮겨 담습니다. 4바이트가 1바이트가 되니 저장 공간이 딱 4배 줄죠.

원리는 자를 하나 만드는 것과 같습니다. 어떤 차원의 값이 대체로 −0.2에서 0.2 사이에 분포한다면, 그 구간을 256칸으로 잘게 나눠 각 값을 가장 가까운 칸 번호(정수)로 바꿉니다. 검색할 때는 이 정수를 다시 대략의 실수로 되돌려 거리(내적)를 계산합니다.

여기서 중요한 게 보정(calibration)입니다. 각 차원의 최소·최대 범위를 알아야 자를 만들 수 있는데, 이 범위는 실제 데이터에서 뽑아야 합니다. 그래서 대표 문서 임베딩 수천 개를 calibration_embeddings로 넘겨 “이 차원은 −0.2~0.2, 저 차원은 −0.5~0.5” 하는 범위를 계산하게 합니다. 이 보정을 건너뛰거나 표본이 너무 적으면 자의 눈금이 엉터리가 되어 정확도가 크게 떨어집니다.

대신 int8은 손실이 아주 작습니다. 공개된 벤치마크에서 스칼라 양자화는 원본 float32 대비 검색 성능의 약 99%를 유지합니다. 예를 들어 mxbai-embed-large-v1(1024차원)의 MTEB 검색 점수(NDCG@10)는 float32에서 54.39, int8에서 52.79로 약 97% 수준입니다. 저장 공간을 4분의 1로 줄이면서 정확도는 거의 그대로 — 사실상 공짜 점심에 가깝습니다.

4. 바이너리 양자화 — 32배 줄이기

더 과감한 방법이 바이너리 양자화(binary quantization)입니다. 각 차원을 딱 1비트로 만듭니다. 규칙도 단순합니다 — 값이 0보다 크면 1, 아니면 0. 그게 전부입니다. 32비트가 1비트가 되니 저장 공간은 32배, 1024차원 벡터 하나가 4KB에서 128바이트로 쪼그라듭니다.

이렇게 극단적으로 뭉개도 검색이 되는 이유는, 고차원에서 벡터의 부호 패턴만으로도 방향 정보의 상당 부분이 남기 때문입니다. 게다가 비트열끼리의 거리는 Hamming distance로 잽니다. 두 비트열을 XOR한 뒤 1이 몇 개인지 세는 건데, 현대 CPU에서는 명령어 두어 개면 끝납니다. 그래서 바이너리 검색은 float32 대비 최대 40배 이상(평균 약 25배) 빨라집니다.

공짜는 아닙니다. 그냥 바이너리로만 검색하면 성능 유지율이 약 92.5%로, int8보다 눈에 띄게 떨어집니다. 상위권 후보의 미세한 순위가 흔들리기 때문입니다. 바로 이 손실을 메우는 게 다음 절의 rescore입니다.

5. 잃은 정확도를 되찾는 열쇠: rescore

핵심 아이디어는 이렇습니다. 빠르고 거친 검색으로 후보를 넉넉히 뽑은 뒤, 정확한 원본 벡터로 그 후보만 다시 채점한다. 리랭킹(reranking)의 2단계 검색과 정확히 같은 발상인데, 여기서는 “다시 채점”을 무거운 cross-encoder가 아니라 원본 float32 벡터 내적으로 합니다.

왜 이게 통할까요? 바이너리 검색은 정답을 상위 몇 개에 정확히 세우는 데는 약하지만, 정답을 후보 40개 안에 포함시키는 건 꽤 잘합니다(recall이 높습니다). 그러니 후보를 넉넉히 뽑아 정답을 그물 안에 넣어 두고, 최종 순위만 원본 벡터로 정확히 매기면 됩니다. 후보가 40개뿐이라 원본을 써도 계산량이 미미합니다.

실제 구현에서는 rescore_multiplier라는 값으로 후보를 얼마나 넉넉히 뽑을지 정합니다. 최종 10개가 필요하고 배수가 4면 1단계에서 40개를 뽑아 rescore하는 식입니다. 이 rescore를 붙이면 바이너리의 성능 유지율이 약 92.5%에서 약 96%로 올라갑니다. int8은 rescore까지 더하면 원본과 거의 구분되지 않는 수준(약 99%)이 됩니다.

기억할 그림. 저장은 작게(바이너리·int8), 최종 채점은 정확하게(float32). 메모리는 압축된 벡터가, 정확도는 소수의 후보에만 쓰는 원본이 책임집니다. 이 역할 분담이 임베딩 양자화의 전부라고 해도 됩니다.

6. Matryoshka 임베딩과 조합하기

양자화가 “각 숫자를 더 적은 비트로” 줄이는 축이라면, Matryoshka 임베딩(matryoshka representation learning, MRL)은 “숫자 개수(차원)를 줄이는” 다른 축입니다. 이름은 러시아 인형에서 왔습니다 — 큰 인형 안에 작은 인형이 들어 있듯, 하나의 임베딩 안에 저차원 버전이 겹겹이 들어 있습니다.

보통 임베딩은 앞부분을 잘라 내면 정보가 망가집니다. 하지만 MRL로 학습한 모델은 앞쪽 차원에 중요한 정보를 몰아넣도록 훈련돼서, 1536차원을 256차원으로 잘라 써도 성능이 거의 유지됩니다. 즉 임베딩 하나를 만들어 두고 상황에 따라 “앞 256개만”, “앞 512개만” 하고 잘라 쓸 수 있습니다.

두 축은 곱해집니다. Vespa의 정리에 따르면 바이너리 양자화로 32배, 거기에 MRL로 차원을 잘라 추가로 몇 배를 더 벌 수 있습니다. 1536차원을 256차원으로 줄이면 저장 공간이 원본의 약 16%로 떨어지는데도 정확도 손실은 미미합니다. 양자화와 MRL을 함께 쓰면 저장 비용을 훨씬 극적으로 낮출 수 있는 셈입니다.

어떤 모델이 MRL을 지원하나요? OpenAI text-embedding-3 계열, Nomic, mxbai, Voyage 등 최근 임베딩 모델 상당수가 MRL로 학습돼 차원 자르기를 공식 지원합니다. 모델 카드에 “Matryoshka” 또는 “truncate dimensions”가 있으면 앞부분을 잘라 써도 됩니다. 그렇지 않은 모델을 함부로 자르면 성능이 무너지니 주의하세요.

7. 실전 — 코드로 돌려 보기

말보다 코드가 빠릅니다. 오픈소스 sentence-transformers가 버전 2.6.0부터 양자화를 기본 지원합니다. 핵심 함수는 quantize_embeddings 하나입니다.

{{< highlight python >}} from sentence_transformers import SentenceTransformer from sentence_transformers.quantization import quantize_embeddings model = SentenceTransformer("mixedbread-ai/mxbai-embed-large-v1") docs = [ "고양이는 대표적인 반려동물이다.", "강아지는 사람을 잘 따른다.", "오늘 코스피 지수가 하락했다.", ] # 1) 평소처럼 float32 임베딩을 만든다 emb = model.encode(docs) # shape: (3, 1024), dtype float32 # 2) 바이너리로 양자화 — 0보다 크면 1, 아니면 0 → 1비트씩 8개를 1바이트로 묶음 bin_emb = quantize_embeddings(emb, precision="binary") # shape: (3, 128), int8(비트팩) # 3) int8로 양자화하려면 보정용 임베딩을 함께 넘긴다 (범위 계산용) int8_emb = quantize_embeddings( emb, precision="int8", calibration_embeddings=emb, # 실제로는 수천 개의 대표 임베딩을 쓴다 ) print(emb.nbytes, bin_emb.nbytes, int8_emb.nbytes) # 12288 384 3072 (byte) {{< /highlight >}}

출력에서 보이듯 같은 문서 3개의 임베딩이 float32에서는 12288바이트, 바이너리에서는 384바이트로 정확히 32분의 1이 됩니다. 이제 이걸 검색에 쓰려면 rescore를 붙여야 합니다. sentence-transformers의 semantic_search_faiss가 이 2단계를 대신 해 줍니다.

{{< highlight python >}} from sentence_transformers.quantization import semantic_search_faiss # 코퍼스: 바이너리로 저장(메모리 절약) + 원본 float32는 rescore용으로 보관 corpus_emb = model.encode(corpus_docs) # float32 원본 corpus_bin = quantize_embeddings(corpus_emb, precision="binary") # 인덱스는 바이너리 # 질문은 float32 그대로 인코딩 (rescore에 원본 정밀도가 필요하다) q_emb = model.encode(["사람을 잘 따르는 동물은?"]) results, search_time, _ = semantic_search_faiss( q_emb, corpus_index=None, corpus_embeddings=corpus_bin, # 1단계: 바이너리로 빠르게 후보 검색 corpus_precision="binary", top_k=10, # 최종 10개 rescore=True, # 2단계 rescore 켜기 rescore_embeddings=corpus_emb, # 후보를 원본 float32로 다시 채점 rescore_multiplier=4, # 1단계에서 40개(10×4) 뽑아 rescore exact=True, ) # results[0]: corpus_id와 score가 정밀 재정렬된 상위 10개 {{< /highlight >}}

패턴을 한 번 익히면 어디서든 똑같습니다. 인덱스는 압축본으로 가볍게, rescore는 원본으로 정확하게. Qdrant·Milvus·Weaviate·Elasticsearch·Vespa 같은 실무 벡터 DB도 대부분 이 “양자화 인덱스 + 원본 rescore”를 옵션 하나로 지원합니다. 직접 FAISS를 만지지 않아도, DB 설정에서 quantization: binary와 rescore: true를 켜는 것으로 같은 효과를 얻습니다.

8. 흔한 실수 · 팁

  • 모델마다 견디는 정도가 다릅니다. 바이너리 양자화가 mxbai·Cohere에서는 성능을 96% 안팎 지키지만, e5-base-v2 같은 모델은 바이너리에서 유지율이 약 75%까지 무너집니다. “양자화 친화적”으로 학습됐는지가 중요합니다. 반드시 내 데이터로 양자화 전후 검색 품질을 재보고 도입하세요.
  • int8 보정(calibration)을 건너뛰지 마세요. 범위를 표본 몇 개로만 잡으면 자의 눈금이 틀어져 정확도가 크게 떨어집니다. 실제 분포를 대표하는 임베딩 수천 개로 보정하는 게 안전합니다. 바이너리는 임계값이 0으로 고정이라 이 함정은 없습니다.
  • 질문은 양자화하지 마세요(rescore를 쓸 때). rescore가 동작하려면 질문(query) 임베딩은 float32, 코퍼스만 양자화돼 있어야 합니다. 질문까지 바이너리로 만들면 다시 채점할 정밀도가 사라져 rescore가 무의미해집니다.
  • 차원을 자를 땐 MRL 모델인지 확인하세요. Matryoshka로 학습되지 않은 모델의 임베딩을 앞부분만 잘라 쓰면 정보가 골고루 흩어져 있어 성능이 급락합니다. 모델 카드에서 지원 여부를 먼저 보세요.
  • rescore 배수는 튜닝 대상입니다. rescore_multiplier가 너무 작으면 정답이 후보 그물을 빠져나가 정확도가 떨어지고, 너무 크면 rescore 비용이 커집니다. 보통 3~5에서 시작해 리콜을 보며 조정합니다.
  • 원본을 버리지 마세요. rescore에는 float32 원본이 필요합니다. RAM에서 내려 디스크(또는 오브젝트 스토리지)에 두더라도 보관은 해야 합니다. 원본을 지우면 바이너리만으로 검색해야 해서 정확도를 되찾을 길이 없어집니다.

9. 마무리 (TL;DR)

  • 문제: float32 임베딩은 무겁다. 1024차원 100만 개면 약 4GB가 RAM에 올라가고, 문서가 늘수록 비용이 정비례로 폭발한다.
  • 스칼라 양자화(int8): 4바이트 → 1바이트로 4배 절감, 성능 유지율 약 99%. 대신 보정(calibration)이 필수.
  • 바이너리 양자화: 부호만 남겨 1비트로 32배 절감, Hamming distance로 검색은 최대 40배 빠름. 단독 유지율은 약 92.5%.
  • rescore가 핵심: 바이너리로 후보를 넉넉히 뽑고 원본 float32로 상위만 다시 채점하면 유지율이 약 96%로 오른다. 저장은 작게, 채점은 정확하게.
  • Matryoshka(MRL): 차원 자르기라는 또 다른 절감 축. 양자화와 곱해져 저장 비용을 더 크게 낮춘다. 단, MRL로 학습된 모델에서만.
  • 실무: sentence-transformers의 quantize_embeddings로 바로 실험 가능. Qdrant·Milvus·Weaviate·Elasticsearch·Vespa도 옵션으로 지원. 도입 전 반드시 내 데이터로 품질을 재볼 것.
