# 🔥 오늘의 핵심

Nvidia의 Hugging Face 인수 발표와 같은 주, MBZUAI 산하 IFM이 **가중치·코드·학습 데이터·중간 체크포인트까지 전부 Apache 2.0으로 공개한 K2 Horizon 6종**을 냈다 — "완전 개방" 진영의 가장 큰 응수다. 논문 쪽에선 Salesforce의 Random Attention이 눈에 띈다. 긴 추론의 KV 캐시는 **프롬프트만 지키면 나머지는 무작위로 버려도 된다**는 결과로, 자체 서빙하는 팀이라면 오늘 바로 실험해 볼 수 있다.

# 📚 주목 논문

## Random Attention — KV 캐시 축출, 점수가 필요 없었다

- **저자**: Heng Wang, Jielin Qiu 외 (Salesforce AI Research·UIUC — Jiawei Han, Heng Ji, Silvio Savarese 포함)
- **arXiv**: [2609.03430](https://arxiv.org/abs/2609.03430) (cs.CL) — 9/3 공개, HF Daily Papers 상위권
- **핵심 기여**: 기존 KV 캐시 압축은 전부 "이 토큰이 나중에 얼마나 중요할지" 점수를 매겨 top-k를 남기는 패러다임이었다. 이 논문은 **그 선택 신호가 거의 아무 기여도 하지 않음**을 보인다. 프롬프트는 전부 보존하고, 추론 트레이스는 헤드별로 균등 무작위 축출 — 점수 계산 0회.
- **왜 되나**: (1) 캐시에서 깨지기 쉬운 건 프롬프트뿐이고, 기존 방법 간 격차는 대부분 "우연히 프롬프트를 지켰는가"의 차이였다. (2) 추론 트레이스는 텍스트 차원(모델이 필요한 걸 재진술)과 헤드 차원(헤드마다 사본 보유)의 이중 중복으로 스스로를 보호한다.
- **결과**: 4개 모델 × 6개 추론 태스크에서 최강 기존 축출법과 동급 정확도, vLLM 서빙 처리량은 **32~43% 더 높음**(자체 보고).
- 🛠 **에이전트 빌더 시사점**: 긴 CoT를 뿜는 추론 모델을 자체 서빙 중이라면 메모리 병목의 해법이 공짜로 단순해진다. 복잡한 중요도 추정 로직을 걷어낼 근거.
- **한계**: 자체 호스팅 스택 전용이고, "프롬프트 보존"이 전제라 프롬프트 자체가 초장문이면 이득이 줄어든다.
- **코드**: [SalesforceAIResearch/Random-Attention](https://github.com/SalesforceAIResearch/Random-Attention) (클론으로 확인, 최근 커밋 9/4)

![Random Attention 동작 원리](/images/ai-news-2026-09-07/random-attention.svg)

*프롬프트는 지키고 트레이스는 랜덤으로. 점수 계산이 사라진 만큼 처리량이 올라간다.*

## BCIT — 과거의 성공 레시피, 언제 재사용하면 안 되나

- **저자**: Tingyun Li, Wenfeng Feng 외 6인 (arXiv 초록에 소속 미표기)
- **arXiv**: [2608.26730](https://arxiv.org/abs/2608.26730) (cs.AI) — HF Daily Papers 150+ 추천
- **핵심 기여**: 모델을 반복 포스트트레이닝하는 자율 시스템에서, **과거에 통했던 업데이트 증거가 부모 모델이 바뀐 뒤에도 유효한지**를 따지는 "conditional experience transfer" 문제를 정식화했다.
- **방법**: Boundary-Calibrated Intervention Transfer(BCIT). 관찰된 효과를 원래 문맥에 묶어 두고, 적용 조건을 검사하고, 명시적 충돌은 거부하며, 필요하면 소규모 시험 학습으로 현재 상태 증거를 얻은 뒤에만 재사용을 허가한다.
- **결과**: 4B 모델을 금융 추론·text-to-SQL·함수 호출에 적응시키는 실험에서, 동일 예산 대비 해로운 업데이트 승인이 줄고 성능이 더 높았다(자체 보고).
- 🛠 **에이전트 빌더 시사점**: 파인튜닝만의 얘기가 아니다. "지난번에 통한 프롬프트/스킬 패치"를 맥락 확인 없이 재적용하는 에이전트 개선 루프 전반에 같은 함정이 있다 — 성공 이력에 조건을 달아 저장하자.
- **한계**: 4B 단일 모델 실험이라 스케일 일반화는 미검증.

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — 팀 전체 훅을 requirements.toml로 강제하기

- **분류**: Hook / 거버넌스 · **출처**: [openai/codex docs/config.md](https://github.com/openai/codex/blob/main/docs/config.md) (클론으로 확인)
- 💡 관리자가 `requirements.toml`에 `allow_managed_hooks_only = true`를 설정하면, 사용자·프로젝트·세션 레벨 훅 설정은 무시되고 관리 레이어의 훅만 실행된다.
- 📝 조직 표준 로깅·가드레일 훅을 배포할 때:

```toml
# requirements.toml (관리자 배포 레이어)
allow_managed_hooks_only = true
```

- 🎯 팀원 각자의 `config.toml` 훅이 감사 로깅을 우회하거나 충돌을 일으키는 조직에서.
- ⚠️ `config.toml`에 넣으면 동작하지 않는다 — `requirements.toml` 전용이다.
- ⭐ 에이전트를 여러 명이 쓰는 팀이라면 훅을 "개인 설정"에서 "관리 대상"으로 승격시킬 시점.

## 🟦 Claude Code — 출력 잘림 한도를 128K까지 올리기

- **분류**: Debugging / Context · **출처**: [공식 changelog](https://code.claude.com/docs/en/changelog) (2.1.261, CHANGELOG 클론으로 확인)
- 💡 `bashOutputMaxChars`·`taskOutputMaxChars` 설정으로, 명령·백그라운드 태스크 출력이 파일로 밀려나기 전에 인라인으로 받는 분량을 최대 128K자까지 키울 수 있다.
- 📝 `settings.json`에:

```json
{
  "bashOutputMaxChars": 100000,
  "taskOutputMaxChars": 100000
}
```

- 🎯 긴 테스트 로그·스택트레이스를 Claude가 파일 재읽기 없이 한 번에 보고 진단해야 하는 디버깅 세션.
- ⚠️ 인라인 출력은 곧 컨텍스트 소비다. 로그가 큰 리포에서 상시로 올려 두면 토큰 비용이 뛴다 — 디버깅 때만 켜자.
- ⭐ "출력이 잘려서 Claude가 두 번 읽는" 패턴이 잦다면 즉효.

## 🟪 공통 — 추론 모델 자체 서빙, 캐시 축출부터 단순하게

- **분류**: Workflow / 인프라 · **출처**: [Random-Attention 리포](https://github.com/SalesforceAIResearch/Random-Attention)
- 💡 오늘 논문의 실전 버전: 자체 서빙 스택에서 KV 캐시가 병목이면, 정교한 중요도 추정기 대신 "프롬프트 보존 + 무작위 축출"을 베이스라인으로 먼저 깔아라.
- 📝 리포의 vLLM 통합 코드로 자기 워크로드(모델 × 태스크)에서 정확도·처리량을 재현 측정한 뒤, 기존 축출법과 비교한다.
- 🎯 긴 CoT를 쓰는 에이전트를 GPU 메모리 한계에서 돌리는 팀.
- ⚠️ 논문 결과는 추론 태스크 6종 기준. 초장문 프롬프트(RAG 대량 주입) 워크로드는 별도 검증 필요.
- ⭐ "복잡한 최적화를 지우는 최적화"는 흔치 않다. 벤치마크할 가치 충분.
