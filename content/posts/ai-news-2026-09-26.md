# 🔥 오늘의 핵심

Hugging Face 트렌딩 상위에 오른 **Agensh**가 중앙 오케스트레이터를 없애고 에이전트들이 공유 게시판으로 자기조직화하는 구조로, 에이전트 1개 → 1,024개 스케일링에서 태스크 통과율을 33.89% → 55.06%까지 끌어올렸다. 흥미로운 건 같은 "게시판(message board)" 패턴이 openai/codex 코드베이스에 기능 플래그로 착륙하는 중이라는 것 — 논문과 프로덕션 툴이 같은 방향을 보고 있다. 오늘 해볼 것: Claude Code 2.1.283의 새 명령 `/doctor prompt-audit`로 내 CLAUDE.md·스킬·에이전트 정의 감사하기.

# 📚 주목 논문

## Agensh: 1,024개 에이전트의 자기조직화

- **저자**: Zhihao Zhan, Ting Song, Li Dong, Shaohan Huang, Jianxun Lian, Yan Xia, Furu Wei (arXiv에 소속 미표기)
- **arXiv**: [2609.26781](https://arxiv.org/abs/2609.26781) (cs.CL·cs.MA, 9/22)
- **핵심 기여**: 멀티에이전트의 정석이던 중앙 오케스트레이터를 제거했다. 대신 공유 워크스페이스 + 메시지 인터페이스 + 컨텍스트 보존 인프라 위에서, 각 에이전트가 "컨텍스트 수집 → 하위 태스크 클레임(자기 할당) → 실행 → 발견 사항 공유" 루프를 돈다.
- **결과**: ProgramBench 최고 난도 5개 태스크(GPT-5.6-sol 기반)에서 1 → 128 에이전트로 평균 test-pass 19.31% → 28.78%(상대 +49%). pandoc 태스크는 1 → 1,024 에이전트에서 33.89% → 55.06%.
- 🛠 **시사점**: "더 좋은 모델"만이 아니라 **"더 많은 에이전트"가 독립적인 스케일링 축**이 될 수 있다는 실증. 오케스트레이터가 병목인 파이프라인이라면 게시판 구조를 검토할 가치가 있다.
- **한계**: 코드 미공개. 1,024개 병렬 실행의 토큰 비용은 초록에 보고되지 않아, 비용 대비 효율은 본문 확인이 필요하다.

![Agensh 에이전트 수 스케일링에 따른 테스트 통과율 변화 차트](/images/ai-news-2026-09-26/agensh-scaling.svg)

*에이전트 수를 늘리는 것만으로 통과율이 오른다 — 난도 상위 5개 평균과 pandoc 태스크. (자체 제작, 데이터: 논문 초록)*

## AEWM: 에이전트 히스토리의 '오염'을 편집으로 지우기

- **저자**: Shuang Sun, Guoxin Chen, Wayne Xin Zhao, Ji-Rong Wen 외 (arXiv에 소속 미표기)
- **arXiv**: [2609.28416](https://arxiv.org/abs/2609.28416) (cs.CL, 9/23)
- **핵심 기여**: 긴 에이전트 실행에서 틀린 가정과 낡은 계획이 히스토리에 남아 이후 판단을 계속 왜곡하는 **태스크 상태 오염(task-state contamination)** 을 정의하고, 히스토리를 '추가만' 하지 말고 '편집'하자고 제안.
- **방법**: 행동을 Critical/Exploratory/Noisy로 분류하는 Action Judge + 문제 있는 추론-행동 구간을 고쳐 쓰는 State Revision, 이 둘을 실제 실행과 통합한 EditAct.
- **결과**: Action Judge 분류 macro-F1 70.5%(최강 베이스라인 +10.6p), EditAct가 검색·터미널·SWE 6개 벤치마크에서 +3.2~6.7p (논문 보고치).
- 🛠 **시사점**: 컴팩션을 "오래된 것 요약"이 아니라 "틀린 것 정정"으로 설계하는 관점. 실패한 시도 후 에이전트가 같은 함정에 반복해 빠진다면 이 프레임이 진단 틀이 된다.
- **한계**: 코드 공개 여부는 초록·abs 페이지에서 확인되지 않았다.

- README 기준 Google Flights 왕복 검색을 **7.1초**에 완료(로딩 대기 포함). 조작·대상을 speculative하게 한 네트워크 왕복으로 묶은 설계가 포인트.
- **용례**: "매 클릭마다 프론티어 모델 호출"이 비용·지연 병목인 웹 자동화. 결정 레이어와 생성 레이어를 분리하는 실전 예제 코드로도 좋다.

**2. [browser-use/browser-harness](https://github.com/browser-use/browser-harness)** — Python · 같은 팀의 하부 레이어

- jev-ultrafast가 Chrome 연결에 쓰는 CDP(웹소켓) 하니스. 로그인된 실제 브라우저에 에이전트를 붙이고, 없는 헬퍼 함수는 에이전트가 작업 중 직접 작성해 `agent_helpers.py`에 쌓는다 — 쓸수록 하니스가 자라는 구조.
- **용례**: Claude Code/Codex에 README의 셋업 프롬프트를 붙여넣으면 스킬로 등록된다. 사내 웹툴처럼 로그인 세션이 필요한 자동화에.

### 🟦 Claude Code — /doctor prompt-audit: 낡은 프롬프트 패턴 감사

- **분류**: Context / Review · **출처**: [CHANGELOG 2.1.283](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- 💡 **핵심**: CLAUDE.md, 스킬, 에이전트, 커맨드 파일에는 예전 모델 세대에 맞춰 쓴 프롬프트 패턴("반드시", 과잉 강조, 낡은 우회책)이 쌓인다. 새 명령이 이를 자동 감사한다.
- 📝 **방법**:

```bash
# 2.1.283 이상
/doctor prompt-audit
# 또는
/checkup prompt-audit
```

- 🎯 **언제**: 모델 버전을 올린 직후. 구세대 모델용 강한 지시가 신모델에서는 오히려 과잉 행동을 유발하는 경우가 많다.
- ⚠️ **주의**: 감사 결과는 제안이지 정답이 아니다. 팀 컨벤션으로 의도한 강조까지 지우지 말 것.
- ⭐ **추천도**: ★★★★★ — CLAUDE.md는 쌓이기만 하고 리팩터링되지 않는 대표적 자산이다.

### 🟩 Codex — 기능 플래그 목록에서 로드맵 읽기

- **분류**: Workflow · **출처**: [openai/codex codex-rs/features](https://github.com/openai/codex/tree/main/codex-rs/features)
- 💡 **핵심**: Codex의 실험 기능은 전부 `codex-rs/features/src/lib.rs`의 `FeatureSpec` 목록에 stage(UnderDevelopment/Stable/Removed)와 함께 선언된다. 이 파일 하나가 사실상 공개 로드맵이다.
- 📝 **방법**:

```bash
git clone --depth 1 --filter=blob:none https://github.com/openai/codex.git
grep -B2 -A3 "UnderDevelopment" codex/codex-rs/features/src/lib.rs
# 오늘 기준 눈에 띄는 항목: agent_message_board, defer_mailbox_preemption 등
```

- 🎯 **언제**: Codex 기반 워크플로를 운영하며 다음 분기 무엇이 올지 미리 대비하고 싶을 때. 문서화 전 기능의 정확한 설정 키 이름도 여기서 확인된다.
- ⚠️ **주의**: UnderDevelopment 플래그는 기본 꺼짐이고 예고 없이 바뀐다. 프로덕션 의존 금지, "방향 읽기" 용도로만.
- ⭐ **추천도**: ★★★★☆

### 🟪 공통 — 내 오케스트레이터에 게시판 패턴 들이기

- **분류**: Workflow / Subagent · **출처**: [arXiv 2609.26781 (Agensh)](https://arxiv.org/abs/2609.26781)
- 💡 **핵심**: 오케스트레이터가 모든 하위 태스크를 지정 할당하면 워커를 늘려도 병목은 그대로다. 태스크를 게시판에 올리고 워커가 스스로 클레임하게 바꾸는 게 첫 걸음.
- 📝 **방법**: 미니 체크리스트 —
  - 태스크 큐를 "할당 목록"에서 "클레임 가능한 게시판"(파일·DB 한 장이면 충분)으로 전환
  - 워커 루프에 "실행 전 게시판 재독 → 겹치는 클레임 회피" 단계 추가
  - 발견 사항(막힌 지점, 부분 결과)을 결과물과 별도로 게시판에 기록해 다른 워커가 재활용
- 🎯 **언제**: 병렬 서브에이전트가 4개를 넘어가며 오케스트레이터 컨텍스트가 포화될 때.
- ⚠️ **주의**: 클레임 경합과 중복 작업 방지를 위해 클레임에 원자적 쓰기(파일 잠금, DB 트랜잭션)가 필요하다.
- ⭐ **추천도**: ★★★★☆
