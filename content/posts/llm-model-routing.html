"안녕"이라는 인사에도, 복잡한 코드 리팩터링에도 똑같이 가장 비싼 모델을 부르고 있다면 — 요금의 상당 부분은 그냥 새고 있는 겁니다.

— 쉬운 질문은 싼 모델로 충분합니다. 문제는 "쉬운지 어려운지"를 미리 가려내는 일입니다.

LLM으로 서비스를 만들어 본 사람이라면 월말 API 청구서를 보고 한 번쯤 놀랐을 겁니다. 그리고 로그를 뒤져 보면 꽤 허무한 사실을 발견합니다. 사용자가 던진 질문의 상당수는 "환불 어떻게 해요?", "이거 요약해줘" 같은 쉬운 것인데, 이것마저 전부 제일 크고 제일 비싼 모델로 처리하고 있었던 겁니다.

쉬운 질문은 작고 싼 모델로도 답이 똑같이 나옵니다. 진짜 큰 모델이 필요한 건 전체의 일부, 어려운 질문뿐입니다. 그러니 질문이 들어오는 순간 "이건 싼 모델, 저건 비싼 모델" 하고 갈라 보내면 품질은 거의 그대로 두면서 비용을 크게 줄일 수 있습니다. 이렇게 질문마다 알맞은 모델을 고르는 일을 LLM 라우팅(LLM routing), 그 갈라 보내는 장치를 라우터(router)라고 합니다.

이 주제가 이번 주에 다시 화제가 된 데는 이유가 있습니다. 2026년 7월 중순, Supra-Router-51M이라는 5,170만 파라미터짜리 초경량 라우터 모델이 Hugging Face 트렌딩에 올랐습니다. "질문을 로컬 작은 모델에서 처리할지, 클라우드의 큰 모델로 넘길지"만 빠르게 판단하는 아주 작은 전용 모델입니다. 비슷한 시기에 라우팅·캐스케이딩을 정리한 서베이 논문과, 코딩 작업용 Agent-as-a-Router 논문도 arXiv에 올라오면서, 모델 여러 개를 섞어 쓰는 팀이라면 "라우팅을 어떻게 할 것인가"가 피할 수 없는 질문이 됐습니다.

이 글은 라우팅이 왜 필요한지부터, 라우터를 언제·무엇으로·어떻게 만드는지(설계의 3축), 유명한 오픈소스인 RouteLLM과 캐스케이드 방식인 FrugalGPT가 실제로 얼마나 아끼는지, 그리고 직접 만들 수 있는 코드까지 차근차근 짚습니다.

먼저 구분: 이 글의 라우팅은 장애 대비 폴백(fallback)과 다릅니다. 폴백은 "A 모델이 죽으면 B로 넘긴다"는 가용성 이야기고(예전 글 모델-애그노스틱 LLM 레이어에서 다뤘습니다), 오늘의 라우팅은 "이 질문엔 어느 모델이 가성비가 좋은가"라는 비용·품질 최적화 이야기입니다. 둘은 같은 게이트웨이 안에서 함께 살지만 목적이 다릅니다.

1. 왜 라우팅인가 — 모델 하나로는 답이 안 나온다

2026년의 현실은 "모델이 하나가 아니라 여럿"이라는 겁니다. 같은 회사 안에서도 크기별로 여러 모델이 있고(가벼운 것 ↔ 무거운 것), 회사를 넘나들면 선택지는 더 많아집니다. 중요한 건 이들의 가격과 품질이 제각각이라는 점입니다. 작은 모델은 토큰당 값이 몇 배에서 수십 배까지 쌉니다. 그리고 대부분의 실제 트래픽에서 어려운 질문은 소수입니다.

여기서 한 가지 오해를 짚고 갑시다. "그럼 제일 똑똑한 모델 하나에 다 맡기면 품질은 최고 아닌가?" 품질은 그럴 수 있지만, 두 가지를 잃습니다. 첫째, 돈입니다. 쉬운 질문 열 개를 비싼 모델로 처리하면, 같은 답을 싼 모델로 냈을 때보다 몇 배를 더 냅니다. 둘째, 속도입니다. 큰 모델은 보통 응답이 느립니다. "안녕"이라는 인사에 2초씩 기다리게 만들 이유가 없습니다.

반대로 "그럼 다 싼 모델에 맡기자"도 답이 아닙니다. 어려운 질문에서 싼 모델은 틀리거나 헛소리를 합니다. 그러니 정답은 가운데에 있습니다 — 질문의 난이도를 보고 알맞은 모델로 나눠 보내기. 이게 라우팅입니다.

비유: 병원 응급실의 트리아지(triage)를 떠올리면 쉽습니다. 접수대에서 간호사가 환자를 쓱 보고 "경상은 일반 진료, 위급은 바로 수술실"로 보냅니다. 모든 환자를 다짜고짜 수술실로 밀어 넣지 않습니다. 라우터가 바로 그 접수대 간호사입니다.

2. 라우터 설계의 3축 — 언제·무엇으로·어떻게

2026년에 나온 라우팅·캐스케이딩 서베이는 라우터의 설계 공간을 세 개의 축으로 깔끔하게 정리합니다. 새 라우터를 고민할 때 이 세 질문만 던지면 됩니다.

  • 언제(WHEN) 결정하나? — 요청을 보내기 전에(pre-request) 정하나, 응답을 만들어 보며(at-inference) 정하나, 한 번 답을 받아 본 뒤에(post-response) 정하나.
  • 무엇을(WHAT) 보고 정하나? — 질문 자체의 특징(길이·주제·난이도), 모델들의 메타데이터(가격·강점), 과거 성능 기록.
  • 어떻게(HOW) 계산하나? — 사람이 짠 규칙(rule), 학습된 분류기(classifier), 강화학습(RL), 아니면 값싼 모델부터 순서대로 밟는 캐스케이드(cascade).

이 중 언제 축이 특히 실무 감각을 잘 보여 줍니다. 셋은 비용·정확도가 반대로 움직입니다.

3. 라우터 유형 4가지와 캐스케이드

"어떻게 계산하나" 축을 조금 더 구체적으로 풀어 봅시다. 현장에서 쓰는 방식은 대략 네 갈래입니다.

방식동작장점단점
규칙 기반
(rule)		 사람이 짠 조건: "코드가 들어오면 큰 모델", "100자 미만이면 작은 모델" 구현이 제일 쉽고 예측 가능. 비용 0에 가까움 세상 모든 경우를 규칙으로 못 덮음. 금방 지저분해짐
임베딩 + 분류기
(classifier)		 질문을 임베딩으로 바꿔, "이건 큰 모델감/작은 모델감"을 예측하는 작은 분류기를 학습 빠르고(수 ms) 싸다. 데이터로 계속 개선 가능 학습 데이터가 필요. 새로운 유형엔 약함
라우터-LLM
(LLM-as-router)		 작은 LLM에게 "이 질문 어렵니?"를 직접 물어 판단 낯선 표현·맥락에 강함. 규칙 없이도 유연 판단에도 LLM 호출 비용·지연이 든다
캐스케이드
(cascade)		 싼 모델부터 답을 내 보고, 자신 없어 하면 다음 큰 모델로 순서대로 올림 사전 판단이 필요 없음. 정확도가 가장 안정적 어려운 질문은 여러 번 호출 → 지연·비용 겹침

앞의 셋(규칙·분류기·라우터-LLM)은 "보내기 전에 어느 모델인지 딱 찍는" 방식이라 묶어서 사전 라우팅이라 부를 수 있습니다. 마지막 캐스케이드는 결이 다릅니다. 미리 찍지 않고, 일단 싼 모델로 답해 보고 마음에 안 들면 위로 올리는 방식입니다.

핵심은 "자신감 점수": 캐스케이드의 성패는 "이 답을 믿어도 되나?"를 재는 점수 함수에 달려 있습니다. 모델의 확률(logprob), 답의 형식이 맞는지, 별도의 작은 검증 모델(verifier)의 판정 등을 씁니다. 이 점수가 엉터리면 쉬운 질문도 자꾸 위로 올라가 라우팅의 이득이 사라집니다.

4. 숫자로 보기 — RouteLLM과 FrugalGPT

"정말 효과가 있나?"를 숫자로 확인해 봅시다. 이 분야에서 가장 많이 인용되는 두 연구가 있습니다.

RouteLLM(LMSYS·UC Berkeley, arXiv:2406.18665, ICLR 2025)은 사전 라우팅 쪽의 대표작입니다. 사람들의 선호 데이터(어느 답이 더 나은지)를 학습해, "이 질문은 큰 모델이 필요할까?"를 예측하는 라우터를 만듭니다. 논문 결과가 인상적입니다. MT-Bench에서 강한 모델 호출을 14%로 줄이면서도 GPT-4 품질의 95%를 유지했고, 비용은 약 85% 절감했습니다. 또 다른 벤치마크인 MMLU에서는 같은 품질을 유지하며 45%를 아꼈습니다.

RouteLLM은 네 종류의 라우터를 오픈소스(lm-sys/RouteLLM, GitHub 별 약 4.5k)로 함께 공개했는데, 이게 라우터 구현을 이해하는 좋은 카탈로그입니다.

FrugalGPT(arXiv:2305.05176)는 캐스케이드 쪽의 고전입니다. 값싼 모델부터 순서대로 물어보고, 자신감 점수가 낮을 때만 위로 올립니다. 논문은 최고 단일 모델(GPT-4) 수준의 정확도를 최대 98%까지 싸게 내거나, 같은 비용으로 정확도를 4%p 더 끌어올릴 수 있다고 보고합니다.

숫자를 그대로 믿지 마세요: 위 85%·98% 같은 수치는 특정 벤치마크 + 특정 모델 조합에서 나온 값입니다(예: RouteLLM은 GPT-4-Turbo 대 Mixtral 8x7B). "이 기법이 통한다"는 증거로 받아들이되, "우리 서비스에서도 딱 85% 나온다"는 약속으로 읽으면 안 됩니다. 실제 기업 사례에서는 대체로 40~70% 절감을 봅니다. 당신의 트래픽·모델 쌍으로 직접 측정해야 합니다.

5. 직접 해보기 (1) — 분류기 라우터

말로만 하면 감이 안 오니 가장 실용적인 임베딩 + 분류기 라우터를 손으로 만들어 봅시다. 아이디어는 간단합니다. 과거 로그에서 "작은 모델로도 충분했던 질문"과 "큰 모델이 필요했던 질문"에 라벨을 붙여 두고, 질문 임베딩으로 둘을 가르는 작은 분류기를 학습합니다. 실전에서는 로지스틱 회귀 한 줄이면 충분할 때가 많습니다.

{{< highlight python >}} # pip install sentence-transformers scikit-learn from sentence_transformers import SentenceTransformer from sklearn.linear_model import LogisticRegression import numpy as np # 1) 라벨 데이터: (질문, 큰 모델이 필요했나?) — 실제로는 로그에서 수천 건을 모은다. # label=0 → 작은 모델로 충분, label=1 → 큰 모델 필요 train = [ ("영업시간 언제까지예요?", 0), ("이 문장 맞춤법만 고쳐줘", 0), ("환불 정책 요약해줘", 0), ("이 500줄짜리 결제 로직 리팩터링하고 버그도 찾아줘", 1), ("아래 논문 3편을 비교해서 한계와 후속 연구를 제안해줘", 1), ("멀티스레드 데드락 원인을 코드에서 추적해줘", 1), ] texts = [t for t, _ in train] labels = np.array([y for _, y in train]) # 2) 질문을 임베딩(의미 벡터)으로 변환 — 작고 빠른 임베딩 모델이면 충분하다. embedder = SentenceTransformer("all-MiniLM-L6-v2") X = embedder.encode(texts) # 3) "큰 모델이 필요할 확률"을 예측하는 아주 작은 분류기를 학습한다. clf = LogisticRegression(max_iter=1000).fit(X, labels) SMALL, BIG = "small-cheap-model", "big-expensive-model" def route(question: str, threshold: float = 0.5) -> str: v = embedder.encode([question]) p_big = clf.predict_proba(v)[0][1] # 큰 모델이 필요할 확률(0~1) # 임계값(threshold)이 라우팅의 '핸들'이다: # 높이면 → 큰 모델로 덜 감(더 아끼지만 품질 위험 ↑) # 낮추면 → 큰 모델로 자주 감(품질 안전하지만 비용 ↑) return BIG if p_big >= threshold else SMALL print(route("포인트 적립은 어떻게 하나요?")) # → small-cheap-model print(route("이 마이크로서비스 아키텍처를 검토해줘")) # → big-expensive-model {{< /highlight >}}

여기서 진짜 중요한 손잡이는 threshold입니다. 이 값 하나로 비용과 품질 사이 어디에 설지를 정합니다. 서비스 초반엔 보수적으로(임계값 낮게, 큰 모델로 자주) 시작해 품질을 확인하고, 안정되면 조금씩 올려 비용을 짜내는 식으로 운영합니다. 오프라인 평가 셋으로 임계값을 바꿔 가며 "품질 곡선"을 그려 보고 허용 가능한 지점을 고르면 됩니다.

팁: 라우팅 결과를 반드시 로그에 남기세요 — 질문, 고른 모델, 확률, 실제 만족도(사용자 피드백·후속 재질문 여부). 이 로그가 다음 학습 데이터가 되고, 라우터는 시간이 갈수록 좋아집니다. 라우터는 "한 번 만들고 끝"이 아니라 계속 재학습하는 부품입니다.

6. 직접 해보기 (2) — 캐스케이드

사전 학습 데이터가 없다면 캐스케이드가 더 쉽게 출발할 수 있습니다. 라벨도, 분류기도 필요 없이 "싼 모델 → 검사 → 부족하면 큰 모델"만 있으면 됩니다. 핵심은 역시 답을 믿어도 되는지 재는 함수입니다.

{{< highlight python >}} # 개념 코드: 실제 클라이언트/모델 이름은 환경에 맞게 바꾸세요. def call_model(name: str, question: str) -> str: ... # 해당 모델을 호출해 답 문자열을 반환 def confidence(question: str, answer: str) -> float: """이 답을 믿어도 되는지 0~1로 점수. 여기서는 아주 단순한 규칙 예시.""" if not answer or "잘 모르겠" in answer or "확실하지 않" in answer: return 0.0 # 모델이 스스로 자신 없어 하면 0점 if len(answer) < 15: # 너무 짧으면 대충 답했을 가능성 return 0.4 return 0.9 # 실전에선: logprob 기반 점수, 형식 검증(JSON 스키마), 별도 verifier 모델 등을 조합 # 싼 → 비싼 순서. 각 단계의 '통과 기준'을 다르게 줄 수도 있다. CASCADE = [("small-cheap-model", 0.7), ("big-expensive-model", 0.0)] def answer_with_cascade(question: str) -> tuple[str, str]: for name, threshold in CASCADE: ans = call_model(name, question) if confidence(question, ans) >= threshold: return ans, name # 기준 통과 → 여기서 멈춘다(더 안 올라감) return ans, name # 끝까지 왔으면 마지막(큰 모델) 답을 쓴다 ans, used = answer_with_cascade("포인트 적립은 어떻게 하나요?") print(used) # 대개 → small-cheap-model 에서 끝남 {{< /highlight >}}

마지막 단계의 임계값을 0.0으로 둔 게 포인트입니다. 큰 모델까지 올라왔다면 더 갈 곳이 없으니 무조건 그 답을 채택합니다. 큰 모델이 "최종 보루" 역할을 하는 거죠. 쉬운 질문 대부분은 첫 줄에서 끝나므로, 평균적으로 보면 대부분의 트래픽이 싼 모델에서 처리됩니다.

직접 다 만들기 부담스럽다면 이미 잘 만들어진 도구를 붙여도 됩니다. 오픈소스 RouteLLM은 위 분류기 라우터를 학습된 형태로 제공하고, OpenRouter의 자동 라우팅, NotDiamond 같은 호스티드 라우터, 서빙 계층에 붙는 vLLM Semantic Router 등 선택지가 다양합니다. 처음엔 규칙 몇 개로 시작해, 로그가 쌓이면 분류기나 캐스케이드로 넘어가는 순서를 추천합니다.

7. 이번 주의 화제 — 초경량 라우터 모델

서두에서 말한 Supra-Router-51M이 왜 흥미로운지 이제 이해가 될 겁니다. 이건 "라우팅 자체를 아주 작은 전용 모델로 빠르게 하자"는 방향입니다. 파라미터가 5,170만 개뿐이라, 라우터가 소비하는 비용·지연을 거의 무시할 수준으로 낮춥니다. 학습은 라우팅 전용 데이터셋(SupraLabs/Prompt-Routing-Dataset, 약 992행)으로 작은 베이스 모델을 미세조정해 만들었고, 단순 이진 분류가 아니라 질문의 성질을 먼저 서술한 뒤 라우팅 토큰을 예측하는 방식(multi-task sequence generation)을 씁니다.

특히 엣지(edge) 대 클라우드 구도가 눈에 띕니다. "이 질문은 기기 안의 작은 모델(SLM)로 처리할까, 아니면 클라우드의 큰 모델로 넘길까"를 게이트키퍼처럼 판단합니다. 온디바이스 AI가 늘면서 이 "로컬이냐 클라우드냐" 라우팅은 앞으로 더 중요해질 축입니다.

같은 흐름에서 코딩 작업에 특화한 Agent-as-a-Router(arXiv:2606.22902)처럼 에이전트가 매 단계마다 알맞은 모델을 고르는 연구도 나오고 있습니다. 에이전트는 한 작업 안에서 계획·검색·코드 생성처럼 성격이 다른 단계를 오가는데, 단계마다 필요한 지능이 다릅니다. 계획엔 큰 모델, 단순 도구 호출엔 작은 모델 — 이렇게 한 세션 안에서도 라우팅하는 게 자연스러운 다음 걸음입니다. 추론 예산 조절과도 맞닿아 있는 주제입니다.

8. 흔한 실수 · 팁

  • 라우터의 비용·지연을 잊는다. 라우터도 공짜가 아닙니다. 판단에 큰 LLM을 쓰면, 아끼려다 배보다 배꼽이 커집니다. 라우터는 싸고 빨라야 의미가 있습니다(그래서 51M 같은 초경량이 화제인 겁니다).
  • 자신감 점수를 대충 만든다. 캐스케이드의 성패는 점수 함수입니다. 점수가 부정확하면 쉬운 질문도 자꾸 큰 모델로 올라가 이득이 사라지거나, 반대로 나쁜 답을 통과시킵니다. 점수 자체도 평가 대상입니다.
  • 분포 변화(distribution shift)를 방치한다. 라우터는 과거 트래픽으로 학습합니다. 신규 기능·신규 사용자로 질문 분포가 바뀌면 라우터가 옛날 감으로 오판합니다. 정기적으로 재학습·재평가하세요.
  • "품질은 어차피 비슷하겠지"라고 넘긴다. 라우팅은 품질을 조금 희생해 비용을 많이 줄이는 거래입니다. 얼마나 희생하는지 반드시 오프라인 평가 셋으로 측정하세요. 평가(evals) 없이 라우팅을 켜는 건 눈 감고 운전하는 것과 같습니다.
  • 임계값을 하나로 박아 둔다. 서비스마다, 심지어 기능마다 허용 가능한 품질이 다릅니다. 결제 관련 질문은 보수적으로(큰 모델로 자주), 잡담은 공격적으로 — 세그먼트별로 임계값을 다르게 두면 훨씬 알뜰합니다.
  • 폴백과 헷갈린다. 라우팅은 "가성비 선택", 폴백은 "장애 대비"입니다. 둘 다 필요하지만 목적이 다르니 코드에서도 분리해 두는 편이 유지보수에 좋습니다.

9. 마무리 (TL;DR)

핵심 요약
  • 문제: 쉬운 질문까지 전부 최고 모델로 보내면 요금이 샌다. 어려운 질문은 소수다.
  • 해법: 질문마다 알맞은 모델로 나눠 보내는 LLM 라우팅. 라우터는 응급실 트리아지 간호사다.
  • 설계 3축: 언제(요청 전/추론 중/응답 후) · 무엇으로(질문·모델·성능) · 어떻게(규칙·분류기·RL·캐스케이드) 결정하나.
  • 두 큰 갈래: 미리 찍는 사전 라우팅(RouteLLM류) vs 싼 모델부터 올리는 캐스케이드(FrugalGPT류).
  • 효과: 논문 기준 최대 85~98% 절감 사례가 있으나 벤치마크 한정. 실무는 보통 40~70%. 반드시 직접 측정.
  • 손잡이: 분류기의 threshold, 캐스케이드의 자신감 점수가 비용·품질을 가른다.
  • 흐름: 규칙 → 분류기/캐스케이드 → 초경량 라우터 모델·에이전트별 라우팅으로. 라우터는 계속 재학습하는 부품이다.
  • 주의: 라우터 자신의 비용, 자신감 점수 품질, 분포 변화, 평가 없이 켜기 — 이 넷을 조심.

라우팅은 화려한 신기술이라기보다, 모델이 여러 개가 된 시대에 돈을 덜 쓰면서 품질을 지키는 가장 실용적인 레버입니다. 규칙 몇 줄로 오늘 당장 시작할 수 있고, 로그가 쌓이면 분류기와 캐스케이드로 키워 가면 됩니다. 다음에 API 청구서를 볼 때, "이 질문들, 정말 다 큰 모델이어야 했나?"를 한 번 물어보세요. 대부분은 아닐 겁니다.
