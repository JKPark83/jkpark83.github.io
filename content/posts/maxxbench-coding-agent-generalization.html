1. 도입 — 리더보드의 74%는 얼마나 단단한 숫자일까

모델을 고를 때 누구나 벤치마크 리더보드를 봅니다. "coding agent 성능은 A 모델이 74%, B 모델도 74%, 비슷하네" — 여기까지는 자연스러운 독해입니다. 그런데 그 74%가 같은 종류의 74%가 아니라면 어떨까요.

지난 금요일(11월 7일) 공개된 MaxxBench가 정확히 이 질문을 던졌습니다. 방법은 단순합니다. 기존 coding agent 벤치마크인 DeepSWE의 태스크 89개를 가져와서, 요구사항이나 시작 코드를 조금만 바꿉니다. 참조 정답 기준으로 중앙값 17줄, 약 3.5% 분량입니다. 실무에서 흔한 "아, 그리고 파일명은 소문자로 통일해 주세요" 수준의 후속 요청과 비슷한 크기입니다.

결과는 단순하지 않았습니다. 원본 DeepSWE에서 74% 부근에 나란히 서 있던 모델들이, 변형판에서는 76.4%부터 53.4%까지 갈라졌습니다. 전체 구성(모델×설정) 기준으로 최고-최저 격차는 20.9%p에서 48.3%p로 두 배 넘게 벌어졌습니다. 이 발표는 11월 9일 Hacker News에 올라 380점 안팎, 댓글 100여 개가 달리며 이번 주 평가(evals) 담론의 중심이 됐고, 공개 사흘 만에 저장소 이슈로 외부 통계 재분석이 달리는 보기 드문 광경까지 벌어졌습니다.

이 글은 MaxxBench를 뉴스로 소비하고 끝내지 않습니다. 설계를 뜯어보면서 벤치마크 점수를 읽는 법, 그리고 같은 기법(perturbation, 섭동 평가)을 내 에이전트 평가에 적용하는 법까지 다룹니다. 에이전트 평가의 기초 어휘가 낯설다면 에이전트 평가 — 역량 vs 신뢰성 글을 먼저 읽고 와도 좋습니다.

2. 배경 — 벤치마크가 수명을 다하는 두 가지 방식

벤치마크는 두 가지 방식으로 망가집니다. 첫째는 포화(saturation)입니다. 모델들이 다 90점을 넘기면 변별력이 사라집니다. 둘째는 오염(contamination)입니다. 벤치마크의 문제와 정답이 공개돼 있으면, 이후에 학습된 모델의 훈련 데이터에 스며듭니다. 그 모델의 점수는 "문제를 풀 수 있다"가 아니라 "문제를 본 적이 있다"를 측정하게 됩니다. 공개 벤치마크의 오염 문제는 프라이빗 코드 벤치마크 글에서 자세히 다룬 적이 있습니다.

오염을 의심하는 고전적인 진단법이 바로 섭동(perturbation)입니다. 문제의 본질은 유지하면서 표면만 바꿔 보는 겁니다. 2024년 Apple의 GSM-Symbolic 논문이 대표적입니다. 초등 수학 벤치마크 GSM8K의 문제에서 숫자와 이름만 바꿨더니 여러 LLM의 점수가 떨어졌고, 저자들은 데이터 오염을 유력한 설명으로 지목했습니다. MaxxBench는 같은 아이디어를 coding agent 영역으로 가져온 셈입니다. 다만 뒤에서 보겠지만, "점수가 떨어졌다 = 암기했다"로 바로 건너뛰면 안 되는 이유도 있습니다.

DeepSWE 3분 정리

변형의 대상이 된 DeepSWE는 Datacurve가 2026년 5월 20일 공개한 coding agent 벤치마크입니다. SWE-bench처럼 과거 이슈를 재활용하지 않고, 실제 오픈소스 저장소(FastAPI, Helm, Prometheus, vitest, LangChain 등) 위에 새로 작성한 장기(long-horizon) feature 구현 태스크 113개로 구성됩니다. 에이전트는 태스크 명세(instruction.md)와 저장소를 받고, 네트워크가 차단된 컨테이너 안에서 기능을 구현합니다. 채점은 별도 컨테이너에서 feature 테스트와 regression 테스트를 전부 통과해야 성공으로 치는 방식이고, 실행 하네스로는 Harbor를 포크한 Pier를 씁니다.

요컨대 DeepSWE는 "오염에 강하게 설계된 최신 벤치마크"였습니다. 그런데 공개된 지 6개월이 되기도 전에, 이걸 다시 비트는 벤치마크가 나온 겁니다. 왜일까요? 공개된 순간부터 모든 벤치마크는 늙기 시작하기 때문입니다. 지금 나오는 모델들의 post-training(사후 학습)은 전부 DeepSWE 공개 이후에 이뤄졌습니다.

3. MaxxBench 설계 해부 — 17줄짜리 변형의 과학

MaxxBench 저장소는 DeepSWE의 113개 태스크 중 89개를 가져와 변형했습니다. 핵심 설계 원칙은 세 가지입니다.

  • 변형은 작게 — 요구사항(프롬프트), 파일명, 출력 포맷, 인터페이스 수준의 변경. 참조 정답 patch가 중앙값 17줄(약 3.5%)만 커지는 크기입니다. 태스크를 새로 내는 게 아니라, 실무의 "요구사항이 살짝 바뀌었어요"를 재현합니다.
  • 채점 방식은 유지 — 원본과 같은 구조(feature + regression 테스트 전부 통과)로 채점합니다. 변형된 요구에 맞는 테스트와 참조 정답(oracle)을 다시 만들었습니다.
  • 원본과 쌍(pair)으로 비교 — 같은 태스크의 원본 점수와 변형 점수를 비교해, "문제가 낯설어지면 얼마나 무너지는가"를 봅니다.

변형이 어떤 느낌인지 실제 태스크 하나를 보겠습니다. JavaScript 테스트 러너 testem의 testem-per-launcher-reports 태스크는 "브라우저(launcher)별로 테스트 리포트 파일을 분리하라"는 feature 구현 과제인데, MaxxBench판 명세에는 이런 요구가 들어 있습니다.

{{< highlight text >}} Launcher names in filenames must be filesystem-safe for Windows (each /\:*?"<>|() becomes one underscore, consecutive whitespace becomes one underscore, and letters become lowercase). {{< /highlight >}}

공식 해설이 예로 드는 변형이 바로 이 "파일명은 소문자로" 규칙입니다. FastAPI 태스크에서는 타임스탬프를 UTC 기준 + 뒤에 Z를 붙이는 포맷으로 바꿨습니다. 사람이 보기엔 사소한 디테일이지만, 정답을 "기억"하고 있는 에이전트에게는 함정이 됩니다. 기억 속 정답은 소문자 변환을 하지 않으니까요.

태스크 구조 엿보기 — 저장소를 clone하면 태스크마다 instruction.md(에이전트에게 주는 명세), task.toml(저장소·실행 설정), environment/(시작 코드와 Dockerfile), tests/(채점용 테스트), solution/(참조 patch)가 들어 있습니다. 에이전트 환경과 검증기 모두 network_mode = "no-network"로 못 박혀 있어서, 평가 중에 웹을 검색해 정답을 찾아오는 길은 차단돼 있습니다.

4. 결과 읽기 — 74% 클러스터가 48점 스프레드로

헤드라인 숫자부터 보겠습니다. 원본 DeepSWE에서 74% 부근에 몰려 있던 대표 모델 네 개가 MaxxBench에서 이렇게 갈라졌습니다.

여기서 junior가 놓치기 쉬운 포인트를 세 개 짚겠습니다.

첫째, 하락 폭은 모델마다 다릅니다 — 이게 핵심입니다. 변형 때문에 태스크가 일괄적으로 어려워진 거라면 모든 모델이 비슷하게 떨어져야 합니다. 그런데 공개 데이터를 재분석한 이슈 #1의 통계 검정은 "모든 구성이 같은 폭으로 떨어졌다"는 가설을 기각합니다(p=0.003). 같은 89개 태스크 기준으로 Gemini 3.8 Flash와 GPT-6 Astra는 원본 점수가 79점대로 같은데, 하락 폭은 18.9%p나 차이 납니다. 변형판은 원본에서 똑같아 보이던 모델들을 실제로 갈라냅니다.

둘째, 하락은 소수 태스크에 집중돼 있습니다. 같은 재분석에 따르면 89개 중 15개 태스크가 전체 하락의 62%를 만듭니다. 극단적인 예로 bandit-incremental-cache-control은 원본에서 통과율 77.5%였는데 변형판에서는 0%, scriggo-method-declarations는 85%에서 5%로 떨어졌습니다. 반대로 더 쉬워진 태스크도 21개 있습니다. "평균 몇 점 하락"이라는 요약 뒤에는 늘 이런 분포가 숨어 있습니다.

셋째, 표본이 작습니다. MaxxBench는 구성당 89개 태스크 × 2회 시도입니다. 이슈 #3의 부호 검정(sign test) 분석에 따르면, 이 표본에서 통계적으로 확실하게 버티는 모델 간 격차는 Opus 5.5 vs Gemini 3.8 Flash(23.0%p) 같은 큰 것들뿐이고, 10%p 안팎의 격차는 노이즈와 구분되지 않습니다. 리더보드에서 2~3점 차이로 모델을 고르는 건 대부분 의미가 없다는 일반 교훈이 여기서도 확인됩니다.

5. 실패 모드 — 기억이 명세를 이길 때

점수보다 흥미로운 건 어떻게 틀렸는지입니다. 시도 2,848건의 trajectory(에이전트의 작업 기록)가 전부 공개돼 있는데, 공식 발표와 외부 분석이 공통으로 지목하는 패턴은 이렇습니다.

일부 모델에서는 실패의 약 4분의 1이 "새 요구사항을 읽고 이해까지 했는데, 결국 원래 DeepSWE 정답의 동작으로 회귀"한 사례였습니다. 보고된 testem 사례에서는 에이전트가 바뀐 명세대로 올바르게 구현해 놓고, 나중에 기억 속 정답과 다르다는 이유로 자기 손으로 옳은 코드를 되돌려서 feature 테스트 33개를 떨어뜨렸습니다. 프롬프트에 적힌 명세보다 학습 때 각인된 패턴이 더 센 겁니다.

이 패턴이 낯설지 않다면, 리워드 해킹 글에서 다룬 "프록시(테스트 통과)와 진짜 목표(명세)의 어긋남"의 변형이기 때문입니다. 학습 과정에서 "이런 모양의 문제에는 이런 모양의 답"이라는 지름길이 보상을 받아 왔다면, 명세가 살짝 바뀐 문제는 그 지름길이 함정으로 바뀌는 지점입니다.

6. 그런데 정말 '암기 때문'일까 — 통제군이 없다

여기까지 읽으면 "결국 모델들이 DeepSWE를 외운 거네"라고 결론 내리고 싶어집니다. 그런데 공개 데이터를 재분석한 이슈 #1은 중요한 반론을 제기합니다. 그 결론을 내리기에는 통제군(control group)이 없다는 겁니다.

점수 하락의 가설은 최소 두 개입니다.

  • 가설 A: 친숙함(암기) — 모델이 DeepSWE 원본(또는 그 유사 데이터)을 학습해서, 원본 점수에 거품이 있었다.
  • 가설 B: 일반적인 적응력 부족 — 어떤 모델은 애초에 "요구사항이 수정된 문제"를 잘 못 다룬다. DeepSWE를 본 적이 없어도 똑같이 떨어졌을 것이다.

두 가설을 가르려면 DeepSWE가 공개된 2026년 5월 20일 이전에 가중치가 고정된 모델을 같은 조건으로 돌려 봐야 합니다. 그런 모델이 변형판에서 비슷하게 떨어진다면 가설 B(원래 어려운 변형), 거의 안 떨어진다면 가설 A(친숙함)의 증거가 됩니다. 그런데 MaxxBench가 평가한 16개 구성은 전부 2026년 6월 이후 출시 모델입니다. 통제군이 없습니다.

"knowledge cutoff가 5월 이전이면 되는 거 아냐?" — 안 됩니다. 이게 이 논쟁에서 junior가 얻어 갈 가장 중요한 디테일입니다. 공개된 cutoff 날짜는 사전학습(pretraining) 데이터 기준입니다. 벤치마크 정답 같은 데이터는 그 뒤의 post-training 단계에서도 얼마든지 들어갈 수 있고, 지금 평가된 모델들의 post-training은 전부 DeepSWE 공개 이후에 이뤄졌습니다. 실제로 재분석 결과, cutoff 날짜와 하락 폭 사이에는 양의 상관이 전혀 없었습니다. "cutoff가 벤치마크 공개 전이니 오염은 없다"는 흔한 주장은 그 자체로는 성립하지 않습니다.

그 밖에도 커뮤니티 이슈에는 평가 엔지니어링 관점에서 배울 거리가 많습니다. 이슈 #2는 원본/변형 비교에 모델 시드(seed)가 통제되지 않아 개별 태스크 비교가 흔들린다는 점을, 이슈 #4는 로컬 Docker 재현 시 89개 중 19개 태스크의 채점이 하네스 버그로 아예 실패한다는 점을 지적합니다. 공개 사흘 만에 이 수준의 외부 검증이 붙은 건 시도별 원자료와 trajectory를 전부 공개한 덕분입니다. 점수만 공개하는 벤치마크와의 결정적 차이입니다.

7. 실전 — 내 에이전트 평가에 perturbation 넣기

MaxxBench의 기법은 프런티어 모델 평가에만 쓰이는 게 아닙니다. 사내 에이전트든 사이드 프로젝트든, "우리 평가 셋에서 92% 나왔어요"라는 숫자가 있다면 똑같이 물어볼 수 있습니다. 태스크를 살짝 바꿔도 92%가 유지되나요? 에이전트가 태스크를 "풀고" 있는지, 평가 셋에 "적응"해 버렸는지(프롬프트와 few-shot 예시를 평가 셋에 맞춰 튜닝하다 보면 반드시 생깁니다)를 가르는 가장 싼 방법입니다.

절차는 세 단계입니다. 먼저 기존 평가 태스크에서 본질은 유지하고 표면만 바꾼 변형판을 만듭니다.

{{< highlight yaml >}} # eval/tasks/invoice-parser/variants.yaml # 원본 태스크: 업로드된 인보이스에서 금액·날짜·거래처를 추출 variants: - id: rename # 필드 이름만 변경 — 스키마 암기 여부 확인 change: "출력 필드명을 total_amount → amount_total 로" - id: format # 출력 포맷 변경 — 포맷 암기 여부 확인 change: "날짜를 YYYY-MM-DD 대신 UNIX timestamp로" - id: constraint # 제약 추가 — 명세 주의력 확인 change: "통화가 KRW가 아니면 converted: false 필드를 추가" # 채점기(verifier)도 변형에 맞게 같이 수정해야 한다 — 이걸 빼먹으면 # '변형판 점수 하락'이 사실은 채점기 버그인 경우가 생긴다 {{< /highlight >}}

다음으로 원본과 변형을 같은 설정으로 쌍을 지어 돌립니다. MaxxBench 이슈 #2의 교훈대로, 비교 대상끼리는 모델·버전·temperature·시드(지원된다면)를 통일하고 그 설정을 결과에 같이 저장합니다.

{{< highlight python >}} import json, statistics def run_paired_eval(tasks, agent, n_attempts=4): results = [] for task in tasks: for variant in [task.original, *task.variants]: for i in range(n_attempts): out = agent.run(variant, seed=i) # 쌍마다 같은 시드 사용 results.append({ "task": task.id, "variant": variant.id, # "original" 포함 "attempt": i, "passed": variant.verify(out), # 변형에 맞게 수정된 채점기 "config": agent.config_dict(), # 모델·버전·설정 스냅샷 저장 }) return results def paired_drop(results): """태스크별로 (원본 통과율 - 변형 통과율)을 계산한다. 평균 하나로 뭉개지 말고 태스크별 분포를 봐야 한다 — MaxxBench에서는 15/89개 태스크가 전체 하락의 62%를 만들었다.""" drops = {} for task_id in {r["task"] for r in results}: orig = [r["passed"] for r in results if r["task"] == task_id and r["variant"] == "original"] mut = [r["passed"] for r in results if r["task"] == task_id and r["variant"] != "original"] drops[task_id] = statistics.mean(orig) - statistics.mean(mut) return dict(sorted(drops.items(), key=lambda kv: -kv[1])) {{< /highlight >}}

마지막으로 결과를 읽을 때는 평균이 아니라 하락 상위 태스크의 trajectory부터 엽니다. 거기서 "명세를 읽고도 원래 패턴으로 회귀"가 보이면, 프롬프트에 명세 재확인 단계를 넣거나 변형 태스크를 few-shot에 추가하는 식으로 고칠 지점이 구체적으로 나옵니다. 점수는 증상이고, trajectory가 진단입니다.

그리고 공개 벤치마크를 직접 돌려 보고 싶다면, 에이전트를 붙이기 전에 oracle(참조 정답)부터 돌려서 채점기가 내 환경에서 멀쩡한지 확인하세요. MaxxBench도 그 용도의 명령을 제공합니다.

{{< highlight bash >}} # 참조 정답으로 채점기 자체를 검증 — 이게 실패하면 모델 평가는 무의미 uv run run.py run -p tasks/testem-per-launcher-reports --agent oracle --force-build {{< /highlight >}}

실제로 이 확인을 건너뛰고 로컬에서 돌렸다면, 이슈 #4의 하네스 버그(19개 태스크 채점 불가) 때문에 어떤 에이전트든 최대 70/89점으로 측정되는 함정에 빠졌을 겁니다.

8. 흔한 실수 · 팁

실수왜 문제인가 / 어떻게 하나
리더보드 2~3점 차이로 모델 선택 89개 × 2회 규모에서는 10%p 안팎 격차도 노이즈와 구분이 안 됩니다(이슈 #3의 부호 검정). 작은 격차는 "동급"으로 읽고, 내 워크로드로 직접 비교하세요.
"cutoff가 공개일 이전이니 오염 없음" cutoff는 사전학습 기준입니다. post-training은 그 뒤에도 계속되므로, 오염을 배제하려면 가중치 고정 시점이 벤치마크 공개 이전인 통제군이 필요합니다.
변형판 점수 하락 = 암기라고 단정 "수정된 요구사항에 원래 약한 모델"일 수도 있습니다(가설 B). 두 가설은 결론이 다릅니다 — 전자는 원본 점수를 깎아 읽어야 하고, 후자는 실무 능력 자체의 경고입니다.
태스크 변형만 하고 채점기는 그대로 변형판 실패가 사실은 채점기-명세 불일치인 경우가 생깁니다. MaxxBench 재분석에서도 채점기 수리 때문에 오히려 쉬워진 태스크가 21개 발견됐습니다.
평균 점수만 보고 끝내기 하락은 소수 태스크에 집중됩니다(15개가 62%). 하락 상위 태스크의 trajectory를 읽어야 고칠 지점이 나옵니다.
서로 다른 태스크 셋의 점수를 직접 비교 MaxxBench 헤드라인도 "DeepSWE 113개 vs MaxxBench 89개" 비교라서, 같은 89개로 맞추면 하락 폭이 더 커집니다(이슈 #1). 비교는 반드시 같은 태스크 집합·같은 설정으로.

9. 마무리 (TL;DR)

  • MaxxBench(11/7 공개)는 DeepSWE 태스크 89개의 요구사항을 중앙값 17줄(~3.5%)만 바꾼 변형 벤치마크입니다. 원본에서 74% 부근에 몰려 있던 모델들이 76.4%(Claude Opus 5.5)부터 53.4%(Gemini 3.8 Flash)까지 갈라졌고, 전체 스프레드는 20.9%p → 48.3%p로 벌어졌습니다.
  • 하락 폭은 모델별로 유의하게 다릅니다 — 변형이 일괄적으로 어려워서가 아니라, 원본 점수가 같아도 "낯선 문제를 다루는 능력"은 모델마다 다르기 때문입니다.
  • 대표 실패 모드는 "바뀐 명세대로 올바르게 구현 → 기억 속 정답과 다르다며 스스로 되돌림"입니다. 명세보다 기억이 이기는 순간이 있습니다.
  • 다만 하락의 원인이 암기(오염)인지 적응력 부족인지는 벤치마크 공개 전에 가중치가 고정된 통제군 없이는 단정할 수 없고, cutoff 날짜는 post-training 때문에 통제군 증명이 되지 못합니다.
  • 내 에이전트 평가에도 적용하세요: 태스크의 표면(이름·포맷·제약)만 바꾼 변형판을 만들고, 같은 설정으로 쌍을 지어 돌리고, 평균 대신 태스크별 하락 분포와 trajectory를 읽습니다. 공개 벤치마크를 돌릴 땐 oracle로 채점기부터 검증합니다.
  • 원자료·trajectory 전체 공개 덕분에 사흘 만에 외부 재분석과 반론이 붙었습니다 — 좋은 평가 인프라는 점수가 아니라 검증 가능성을 공개하는 것입니다.
