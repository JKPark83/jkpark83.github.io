1. 왜 지금 '에이전트의 눈'이 다시 화제인가

이번 주 AI 엔지니어링 타임라인을 흔든 소식 하나. 2026년 8월 9일, OpenAI가 자체 AI 브라우저 ChatGPT Atlas를 출시 9개월 만에 접었습니다. 흥미로운 건 그 뒤 처리 방식입니다. 페이지 요약은 크롬 확장으로, 로그인·다운로드는 데스크톱 앱으로 흩어졌지만, 대신 일을 처리하는 에이전트는 OpenAI 서버의 '원격 클라우드 브라우저'로 옮겨 갔습니다. "사용자에게 새 브라우저로 갈아타라고 하는 것보다, 이미 쓰는 도구에 AI 브라우징을 심는 게 낫다"는 결론이었죠.

비슷한 시기 Microsoft는 코딩 에이전트(Claude Code, Cursor, Copilot 등) 전용으로 Playwright CLI(@playwright/cli)를 밀고 있습니다. 핵심 세일즈 포인트가 딱 하나입니다. 기존 Playwright MCP보다 같은 작업에 토큰을 약 4배 덜 쓴다는 것. 어떻게? 페이지를 통째로 넘기는 대신, 요소마다 e21·e35 같은 짧은 참조(reference)만 오가게 만들어서요.

두 소식은 방향이 같습니다. 브라우저 에이전트 경쟁의 무게중심이 "어떤 모델이 똑똑한가"에서 "페이지를 무엇으로, 얼마나 싸게 읽고 정확히 누를 것인가"로 옮겨 가고 있다는 것. 이 글은 바로 그 지각(perception) 계층을 다룹니다. 결론부터 말하면, 같은 페이지라도 무엇으로 읽느냐에 따라 토큰이 100배, 지연이 10배까지 벌어지고, 에이전트가 엉뚱한 버튼을 누르는 사고의 상당수도 여기서 시작됩니다.

용어 정리. 이 글의 '브라우저 에이전트(browser agent)'는 웹 페이지를 스스로 읽고 클릭·입력해 일을 끝내는 에이전트를, '컴퓨터 유즈(computer use)'는 브라우저를 넘어 운영체제 화면 전체를 조작하는 더 넓은 개념을 뜻합니다. 화면을 읽는 원리는 둘이 거의 같아서, 여기서는 웹을 예로 설명합니다.

2. 배경 — 브라우저 에이전트의 perceive→decide→act 루프

브라우저 에이전트는 사실 단순한 반복문입니다. 본다(perceive) → 정한다(decide) → 누른다(act), 그리고 다시 봅니다. 목표를 이룰 때까지 이 루프를 돕니다.

  • perceive: 지금 페이지 상태를 모델이 이해할 수 있는 형태로 만든다. ← 이 글의 주제
  • decide: "로그인 버튼을 누르자" 같은 다음 행동을 LLM이 고른다.
  • act: 실제로 클릭·타이핑·스크롤을 실행하고, 페이지가 바뀌면 다시 perceive로.

여기서 초보가 놓치기 쉬운 사실. 이 루프는 매 스텝마다 페이지를 다시 읽습니다. 로그인 폼 하나 채우는 데도 대여섯 번은 돌죠. 그러니 perceive 한 번의 비용이 곧 전체 비용에 그 횟수만큼 곱해집니다. "한 번 읽는 데 얼마냐"가 사소해 보여도, 전체 작업에서는 결정적입니다.

3. 세 가지 눈: 스크린샷 · 전체 DOM · 접근성 트리

페이지를 모델에게 넘기는 방법은 크게 셋입니다. 각각 장단이 뚜렷합니다.

① 스크린샷(screenshot) — 픽셀을 본다

렌더링된 화면을 이미지로 캡처해 멀티모달 모델에게 넘깁니다. Anthropic Computer Use, OpenAI Operator(현재는 ChatGPT 에이전트 모드), Google Project Mariner 같은 소비자용 제품이 이 방식입니다. 사람이 보는 것과 똑같은 화면을 보니 범용성이 최고입니다. 캔버스로 그린 UI든, 게임 화면이든, 운영체제 창이든 가리지 않죠. 대신 이미지 한 장이 수천 토큰을 먹고, "저 버튼이 화면 어디 좌표에 있나"를 모델이 눈대중으로 맞혀야 합니다(뒤에서 다룰 그라운딩 문제).

② 전체 DOM(full DOM) — HTML을 통째로 넘긴다

브라우저가 들고 있는 원본 HTML 트리를 문자열로 직렬화해 넘깁니다. 정확한 구조가 다 담기지만, 광고·추적 스크립트·인라인 스타일·난독화된 클래스명까지 전부 딸려 옵니다. 콘텐츠가 많은 페이지는 필터를 안 하면 직렬화 결과가 10만 토큰을 넘기기 일쑤라, 실무에서 날것 그대로 쓰긴 어렵습니다. 신호 대 잡음비가 나쁩니다.

③ 접근성 트리(accessibility tree) — 의미만 추린다

브라우저가 스크린리더(시각장애인용 화면 읽기 도구)를 위해 원래부터 만들어 두는 의미 중심의 요약 트리입니다. 버튼·입력창·링크 같은 상호작용 요소의 역할(role)·이름(name)·상태(state)만 남기고 시각적 잡음은 버립니다. 그래서 같은 페이지가 보통 수백 토큰으로 줄고, "이건 로그인 버튼"이라는 의미가 이미 붙어 있어 모델이 좌표를 눈대중할 필요도 없습니다. 최근 업계가 브라우저 에이전트의 1차 인터페이스로 수렴하는 방식이 바로 이겁니다.

왜 셋 다 안 죽고 공존할까? 스크린샷은 접근성 트리에 안 잡히는 화면(캔버스로 그린 차트, 이미지 버튼)까지 볼 수 있어 최후의 보루입니다. 그래서 요즘 잘 만든 에이전트는 하나만 고르지 않고 기본은 접근성 트리, 막히면 스크린샷 폴백으로 섞습니다(6절 하이브리드).

4. 접근성 트리가 대체 뭔데

접근성 트리는 새로 만드는 게 아닙니다. 브라우저가 이미 스크린리더를 위해 DOM에서 뽑아 두는 병렬 구조입니다. 원리는 이렇습니다. DOM을 훑으면서 "사람이 상호작용할 의미가 있는" 노드만 남기고, 각 노드에 세 가지를 붙입니다.

  • role(역할): button, textbox, link, checkbox, dialog… "이게 무엇인가"
  • name(이름): "로그인", "이메일 주소"… 보이는 라벨이나 aria-label에서 온다
  • state(상태): checked, disabled, expanded, hidden… "지금 어떤 상태인가"

그래서 어지러운 <div class="x9f2"> 더미가 button "로그인" 한 줄로 정리됩니다. 아래는 같은 로그인 폼을 전체 DOM과 접근성 트리로 봤을 때의 차이입니다.

전체 DOM (잡음 포함, 일부):

{{< highlight html >}}
이메일
{{< /highlight >}}

접근성 트리 (의미만, 요소 참조 부여):

{{< highlight text >}} textbox "이메일" [ref=e22] autocomplete=username button "로그인" [ref=e21] # 광고 슬롯·svg 아이콘·script는 상호작용 의미가 없어 빠짐 {{< /highlight >}}

차이가 보이시나요? 잡음이 사라졌을 뿐 아니라, 각 요소에 e21 같은 안정적인 참조(ref)가 붙습니다. 이게 Playwright CLI가 토큰을 아끼는 비결입니다. 페이지 전체를 매번 다시 넘기는 대신, "그 폼의 e21을 눌러"처럼 짧은 참조만 주고받으면 되니까요. 브라우저 상태는 바깥(CLI 프로세스)에 두고, 모델 컨텍스트로는 최소한의 구조화된 정보만 오갑니다.

5. 스크린샷 에이전트가 무너지는 지점: 그라운딩

스크린샷 방식의 진짜 난관은 "화면을 이해하는 것"이 아니라 "이해한 걸 정확한 좌표로 옮기는 것"입니다. 이걸 그라운딩(grounding, 시각적 지시-대상 연결)이라고 부릅니다. 모델이 "로그인 버튼을 눌러야지"까지는 알아도, 그 버튼이 화면의 (x=612, y=289)에 있다는 걸 픽셀만 보고 정확히 찍어야 합니다. 몇 픽셀만 빗나가도 옆 링크를 누르거나 허공을 클릭합니다.

이게 왜 어렵냐면, 실제 웹은 밀도가 높고(작은 아이콘이 다닥다닥), 스크롤·확대·반응형 레이아웃 때문에 같은 버튼도 좌표가 계속 바뀌기 때문입니다. 그래서 컴퓨터 유즈 에이전트의 표준 벤치마크인 OSWorld(실제 데스크톱 앱 작업을 시키는 테스트) 초기 점수는 처참했습니다. 최신 프런티어 모델과 2026년 나온 더 어려운 후속 벤치마크에서 성적이 올라오고는 있지만, 여전히 사람과의 격차가 큽니다. 이 격차의 큰 부분이 바로 그라운딩입니다.

그라운딩이 왜 실무에서 무서운가. 좌표가 5px 빗나가 '삭제' 대신 '보관'을 누르는 실수는, 텍스트 오답과 달리 돌이킬 수 없는 부작용을 냅니다. 그래서 스크린샷 에이전트는 반드시 실행 전 확인 단계나 되돌리기 안전장치를 함께 설계해야 합니다.

접근성 트리 방식엔 이 문제가 아예 없습니다. "이거 로그인 버튼"이라는 의미와 참조가 이미 붙어 있으니, 좌표를 눈대중할 필요 없이 click e21이면 끝입니다. Playwright 같은 도구가 그 참조를 실제 DOM 요소로 정확히 되짚어 클릭해 줍니다. 스크린샷 대비 지연이 초 단위에서 밀리초 단위로 떨어지는 이유도 여기 있습니다 — 매번 이미지를 만들고 추론할 필요가 없으니까요.

6. 실전 — 접근성 트리로 클릭 루프 돌리기

개념은 충분히 봤으니, 실제 루프가 어떻게 생겼는지 봅시다. Playwright의 접근성 스냅샷을 써서 "스냅샷 → 참조 고르기 → 클릭 → 다시 스냅샷"을 도는 최소 예제입니다(Node.js).

{{< highlight javascript >}} import { chromium } from "playwright"; const browser = await chromium.launch(); const page = await browser.newPage(); await page.goto("https://example.com/login"); // 1) perceive: 접근성 트리 스냅샷 — 전체 HTML이 아니라 의미만 담긴 트리 const tree = await page.accessibility.snapshot(); // tree는 { role, name, children[...] } 형태. 이걸 LLM에 넘길 땐 // 아래처럼 한 줄짜리 텍스트로 평탄화해 토큰을 더 줄인다. const lines = []; (function walk(node, depth = 0) { if (!node) return; if (node.role !== "generic" && node.name) // 잡음 role은 건너뛴다 lines.push(`${" ".repeat(depth)}${node.role} "${node.name}"`); (node.children ?? []).forEach((c) => walk(c, depth + 1)); })(tree); const observation = lines.join("\n"); // ← 이 짧은 문자열이 모델의 '눈' // 예: textbox "이메일" / textbox "비밀번호" / button "로그인" {{< /highlight >}}

이 observation을 프롬프트에 넣고 "다음에 어떤 요소를 어떻게 조작할지" 한 스텝만 고르게 합니다. 모델은 좌표가 아니라 역할+이름으로 대상을 지목하고, 우리는 Playwright의 역할 기반 로케이터로 그걸 실제 클릭으로 바꿉니다.

{{< highlight javascript >}} // 2) decide: LLM이 { role, name, action, text } 형태로 다음 행동을 반환한다고 하자 const step = await askLLM(observation, goal); // 예: { role: "textbox", name: "이메일", action: "fill", text: "me@x.com" } // 3) act: 좌표가 아니라 '역할+이름'으로 요소를 집는다 — 그라운딩 문제가 없다 const target = page.getByRole(step.role, { name: step.name }); if (step.action === "fill") await target.fill(step.text); else if (step.action === "click") await target.click(); // 4) 페이지가 안정될 때까지 기다린 뒤 루프를 다시 돈다 await page.waitForLoadState("networkidle"); // → 다시 accessibility.snapshot() 부터 반복 {{< /highlight >}}

Playwright CLI를 쓰면 이 흐름이 셸 명령으로 더 얇아집니다. 코딩 에이전트가 playwright-cli snapshot으로 참조가 달린 트리를 받고, playwright-cli click e21로 누릅니다. 브라우저 세션은 CLI가 들고 있으니 에이전트 컨텍스트엔 짧은 참조만 남습니다 — MCP 대비 토큰을 크게 아끼는 지점입니다.

{{< highlight bash >}} # 접근성 트리 스냅샷 — 요소마다 [ref] 부여 $ playwright-cli snapshot textbox "이메일" [ref=e22] textbox "비밀번호" [ref=e23] button "로그인" [ref=e21] # 참조로 조작 — 페이지 전체를 다시 넘기지 않는다 $ playwright-cli type e22 "me@x.com" $ playwright-cli type e23 "••••••" $ playwright-cli click e21 {{< /highlight >}}

현실은 하이브리드

가장 신뢰성 높은 브라우저 에이전트는 한 방식만 고집하지 않습니다. 실무의 정석은 이렇게 계층을 둡니다.

7. 흔한 실수 · 팁

함정 1 — 오래된 참조(stale ref). e21은 그 스냅샷 시점의 페이지에서만 유효합니다. 클릭 뒤 페이지가 바뀌면 참조가 무효화됩니다. 행동 한 번 → 스냅샷 다시를 원칙으로 하세요. 오래된 참조를 재사용하면 엉뚱한 요소를 누릅니다.

함정 2 — 동적 DOM과 늦게 뜨는 요소. SPA는 클릭 직후 요소가 아직 안 붙어 있을 수 있습니다. waitForLoadState나 요소 대기 없이 바로 스냅샷을 뜨면 '텅 빈 화면'을 보고 헤맵니다. 항상 안정될 때까지 기다린 뒤 읽으세요.

함정 3 — 접근성 트리에 안 보이는 UI. <div onclick>로 만든 가짜 버튼, canvas로 그린 차트, 라벨 없는 아이콘 버튼은 트리에서 이름이 비거나 아예 안 잡힙니다. 이럴 때만 스크린샷 폴백으로 넘기세요. 접근성 트리는 시맨틱 HTML을 잘 지킨 사이트에서 가장 강력합니다.

팁 1 — iframe·shadow DOM을 잊지 마세요. 결제창·로그인 위젯은 iframe 안에 있는 경우가 많습니다. 트리를 뜰 때 프레임을 함께 훑지 않으면 "버튼이 없다"고 착각합니다.

팁 2 — 성공 경로는 결정론적으로 굳히세요. 매번 LLM으로 같은 로그인을 반복하는 건 낭비이자 불안정의 원천입니다. 한 번 성공한 경로는 참조/로케이터 스크립트로 저장해 다음엔 LLM 없이 재생하고, 실패할 때만 다시 에이전트를 부르세요. 비용·속도·재현성이 한꺼번에 좋아집니다.

팁 3 — 되돌릴 수 없는 행동엔 확인 게이트를. 결제·삭제·전송처럼 부작용이 큰 클릭 앞에는 사람 확인이나 드라이런을 두세요. 특히 스크린샷 그라운딩이 개입하는 경로일수록 필수입니다.

8. 마무리 (TL;DR)

  • 브라우저 에이전트의 성패는 지각 계층에서 먼저 갈린다. perceive→decide→act 루프는 매 스텝 다시 읽으므로, '한 번 읽는 비용'이 반복 횟수만큼 곱해진다.
  • 읽는 방법은 셋. 스크린샷(범용·비쌈·좌표 그라운딩 취약), 전체 DOM(정확하지만 10만+ 토큰 잡음), 접근성 트리(역할·이름·상태만 추려 수백 토큰).
  • 업계는 접근성 트리로 수렴 중. 의미와 참조가 이미 붙어 있어 좌표 추측이 필요 없고, 지연이 초 단위에서 밀리초로 떨어진다.
  • 이번 주 신호. OpenAI가 ChatGPT Atlas를 접고 에이전트를 원격 클라우드 브라우저로 옮겼고(8/9), Microsoft의 Playwright CLI는 참조 기반으로 MCP 대비 토큰을 약 4배 아낀다.
  • 스크린샷의 아킬레스건은 그라운딩. "무엇을 누를지"가 아니라 "정확한 좌표"가 문제다. OSWorld류 벤치마크의 낮은 점수 상당수가 여기서 나온다.
  • 정석은 하이브리드. 싼 접근성 트리 우선 → 안 잡히면 스크린샷 폴백 → 성공 경로는 결정론적으로 재생.
  • 초보가 밟는 지뢰: 오래된 참조 재사용, 동적 DOM 대기 누락, iframe/shadow DOM 누락, 되돌릴 수 없는 행동에 확인 게이트 부재.
