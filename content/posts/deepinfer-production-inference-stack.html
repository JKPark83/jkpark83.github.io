1. 도입 — 프런티어 랩의 '진짜 서빙 코드'가 열렸다

10월 20일, DeepSeek이 DeepInfer를 Apache 2.0 라이선스로 공개했습니다. 데모용 레퍼런스 구현이 아니라, DeepSeek V4.1 Flash의 실제 프로덕션 서비스를 돌리고 있는 추론 프레임워크 그 자체입니다. Hacker News에서는 2,000점이 넘는 대형 스레드가 섰고, SiliconANGLE, The New Stack 등이 바로 보도했습니다. 사흘 전인 10월 17일에 나온 V4.1-Flash-1017 모델 업데이트에 이어, 이번엔 모델이 아니라 모델을 '돌리는 쪽'을 연 겁니다.

함께 공개된 배포 Q&A 문서에는 평소 어디서도 보기 힘든 숫자가 그대로 적혀 있습니다. 단일 클러스터가 하루 155조(trillion) 토큰을 서빙하고 있으며, 비수기(밸리) 단가 기준으로 GPU-시간당 38달러의 수익을 낸다고 합니다(모두 DeepSeek 자체 공개 수치입니다). KV 캐시를 위해 SSD 100 PiB를 쓰고, 캐시 TTL을 줄이면 히트율이 몇 %p 떨어지는지까지 공개했습니다.

junior 입장에서 이 공개가 특별한 이유가 있습니다. vLLM 튜토리얼로 LLM 서빙의 기초 — PagedAttention, continuous batching — 는 배울 수 있지만, 그 위에 있는 시스템 층(로드밸런서, KV 캐시 스토리지, 장애 대응, 오토스케일링)은 각 회사의 내부 인프라라 볼 기회가 없었습니다. DeepInfer와 Q&A 문서는 그 층을 구체적인 수치와 함께 보여 주는, 사실상 공짜 교과서입니다. 이 글에서는 코드와 문서를 직접 뜯어 보며 전체 구조를 따라가고, 마지막에 "일부러 공개하지 않은 것"이 무엇인지도 짚어 봅니다.

2. 배경 — 추론 프레임워크가 푸는 문제

Q&A 문서의 첫 문장이 문제 정의를 깔끔하게 해 줍니다. "모델은 가능성의 경계를 정한다. 그 가능성을 거대한 사용자 기반에 감당 가능한 비용으로 서빙하는 것이 추론 프레임워크(inference framework)가 풀어야 할 핵심 문제다." 핵심 지표는 두 가지입니다. 첫 토큰이 나오기까지 걸리는 TTFT(time to first token)와 그 뒤 토큰 사이 간격인 TBT(time between tokens), 그리고 이 둘을 지키면서 뽑아내는 전체 처리량입니다.

LLM 추론은 성격이 다른 두 단계로 나뉩니다. 입력 전체를 한 번에 처리해 KV 캐시를 만드는 프리필(prefill)은 연산량이 많은 compute-bound 작업이고, 토큰을 하나씩 뽑는 디코드(decode)는 매 스텝 가중치와 KV 캐시를 통째로 읽어야 하는 memory-bound 작업입니다. 성격이 다르니 같은 GPU에 섞어 두면 서로 방해합니다. 그래서 두 단계를 아예 다른 머신에 배치하는 P/D 분리(disaggregation)가 대규모 서빙의 표준이 됐습니다.

또 하나의 배경은 MoE(Mixture-of-Experts)입니다. DeepSeek 계열 모델은 토큰마다 일부 전문가(expert)만 활성화되는 MoE 구조라, 전문가들을 여러 GPU에 나눠 두는 expert parallelism(EP)이 서빙의 중심 축입니다. DeepInfer 자체의 계보도 흥미롭습니다. README에 "원래 vLLM 위에서 만들어졌고 SGLang과 TensorRT-LLM에서 영감을 받았다"라고 명시돼 있습니다. 범용 프레임워크에서 출발해, 자사 모델 하나를 극한까지 서빙하는 전용 엔진으로 진화한 사례입니다.

3. 전체 그림 — VE/Prefill/Decode 분리와 4개의 로드밸런서

DeepInfer가 서빙하는 V4.1 Flash는 이미지 입력을 받는 멀티모달 모델입니다. 그래서 P/D 분리에 한 단계가 더 붙습니다. 이미지를 임베딩으로 바꾸는 비전 인코더(Vision Encoder, VE)까지 분리한 EPD(Encoder/Prefill/Decode) 아키텍처입니다.

숫자가 보여 주는 설계 철학이 분명합니다. 프리필은 일반 8-GPU 머신에서 HBM이 허용하는 한 가장 작은 EP2–8로 돌리고, 디코드는 반대로 64~128 GPU 슈퍼노드에서 가능한 가장 큰 EP64–128(Wide-EP)로 돌립니다. 디코드에서 EP를 넓히면 GPU 하나가 담당하는 전문가 수가 줄어 스텝당 메모리 트래픽이 크게 떨어지고, 그만큼 토큰 생성 속도가 올라갑니다. TP(tensor parallelism)와 CP(context parallelism)는 현재 쓰지 않습니다. 참고로 "1P + 1D"로도 배포는 되지만, 효율이 나오는 최소 단위는 프리필 64 GPU + 디코드 64 GPU라고 못 박습니다. 여담으로, P와 D를 다른 데이터센터에 두는 것도 기술적으로 가능한데(8 GPU당 400 Gbps 예산), 실제로는 "공사하다 광케이블이 끊기는" 리스크 때문에 인접한 데이터센터에 둔다고 합니다.

로드밸런서는 네 종류가 각자 다른 문제를 풉니다. 특히 Prefill Load Balancer가 재미있습니다. 요청을 컨텍스트 길이로 4개 버킷(16K 미만 / 16–64K / 64–256K / 256K 이상)에 나눠 버킷별로 엔진을 동적으로 배정하고, GPU 안에서는 chunk 크기를 고정하지 않습니다. 대신 스텝마다 시간 예산을 주고, "토큰 q개를 처리하면 얼마나 걸릴까"를 예측하는 2차 비용 모델을 풀어 예산에 꼭 맞는 q를 역산합니다. Decode Load Balancer는 요청 수(배치 크기 결정)와 총 KV 길이(attention 비용 결정)라는 두 차원을 동시에 맞춥니다. 이렇게 해서 "완벽히 균형 잡힌 오프라인 벤치마크의 약 80%"까지 도달한다고 공개했습니다. 로드밸런싱의 품질을 이런 식으로 정량화한 공개 자료는 드뭅니다.

4. KV 캐시는 스토리지 제품이다 — 100 PiB와 TTL의 경제학

이번 공개에서 가장 교육적인 부분은 KV 캐시를 다루는 태도입니다. 흔히 KV 캐시를 "GPU 메모리 안의 자료구조"로 배우지만, DeepSeek은 처음부터 "KV 캐시를 72시간 이상 보존한다"를 시스템 설계 목표로 걸었습니다. 어제 나눈 대화를 오늘 이어가도 프리필을 다시 하지 않겠다는 뜻입니다. 그 결과 KV 캐시는 사실상 하나의 스토리지 제품이 됐습니다.

전용 스토리지 클러스터를 쓰는 이유가 명쾌합니다. 각 프리필 머신의 로컬 디스크에 캐시를 두면 "이 prefix는 저 머신에 있으니 저기로 보내야 한다"는 prefix 친화 라우팅이 생겨 로드밸런싱과 충돌합니다. 전용 클러스터에 두면 어느 머신이든 어떤 prefix든 히트할 수 있어 라우팅이 자유로워지고, 컴퓨트 노드(장애율이 스토리지 노드의 10배 이상)가 죽어도 캐시는 무사합니다.

TTL 숫자에는 트래픽 성격이 그대로 반영돼 있습니다. 에이전트 트래픽은 3일, 챗봇 트래픽은 7일. 챗봇 대화는 소수의 KV가 아주 여러 번 읽히는 롱테일이 두터워서, TTL을 3일로 줄이면 히트율이 0.5~1%p 떨어진다고 합니다. "디스크 비용 vs 프리필 재계산 비용"의 손익분기점을 데이터로 잡는, 캐시 설계의 좋은 본보기입니다.

5. 속도의 기술 — DSpark · SWA bounded replay · zero-overhead 스케줄러

DSpark — 검증 예산을 '수익률 순'으로 배분하는 speculative decoding

Speculative decoding은 작은 draft 모델이 여러 토큰을 미리 뽑고 본 모델이 한 번에 검증하는 기법입니다. 보통은 draft 길이를 고정합니다(예: 5개 전부 검증). 문제는 수락 확률이 요청마다, 위치마다 다르다는 점입니다. 수락될 가망이 없는 draft까지 검증하면 그만큼 계산이 낭비됩니다.

DeepInfer의 DSpark는 Confidence Head가 draft 토큰별 수락 확률을 예측하고, 하드웨어 처리량 곡선과 함께 고려해 "한 스텝의 검증 예산을 한계 수익이 높은 토큰부터" 배분합니다. 공개된 벤치마크(EP64/DP64)를 보면, 스텝당 검증하는 draft 토큰이 5.00개에서 3.2~4.4개로 약 30% 줄었는데 평균 수락 길이는 3.29 → 3.20으로 거의 그대로입니다. 프로덕션 운영점(rank당 동시 60 시퀀스)에서 처리량 +5.4%, 동시 96에서는 +11%입니다.

SWA bounded replay — 프리필 계산을 절반으로

V4.1 Flash는 디코더 레이어의 KV를 마지막 인코더 레이어의 hidden state에서 투영해 내는, YOCO(You Only Cache Once) 계열 구조를 씁니다. 여기에 sliding window attention(SWA, 최근 토큰만 보는 어텐션)이 결합돼 있는데, 디코더 쪽 SWA KV 캐시를 정확히 복원하려면 마지막 2,560토큰을 20개 디코더 레이어에 다시 돌려야 합니다. DeepInfer는 대신 마지막 128토큰만 재계산하고 어텐션 창을 그 구간 안으로 잘라 근사 SWA 캐시를 만듭니다. 재계산 비용이 컨텍스트 길이와 무관한 상수가 되고, 전체 프리필 계산이 거의 절반으로 줄었다고 합니다. 캐시 히트 판정도 이 원칙을 따릅니다. 히트 길이는 block KV가 정하고, SWA KV가 없으면 한 블록(128토큰) 물러나서 그만큼만 재계산합니다.

zero-overhead 스케줄러와 EPLB

디코드 한 스텝은 schedule → forward → sample → post-process로 이뤄지는데, schedule과 post-process는 순수 CPU 작업입니다. 순서대로 돌리면 그동안 GPU가 놉니다. DeepInfer는 GPU가 스텝 N의 forward를 도는 동안 CPU가 스텝 N+1의 스케줄링과 스텝 N−1의 후처리를 미리 해 두는 비동기 파이프라인으로 GPU 공백을 없앴습니다. 문서는 이 설계가 SGLang과 NanoFlow의 기존 구현을 따른 것이라고 출처를 밝힙니다.

MoE 쪽에는 EPLB(Expert-Parallel Load Balancer)가 붙습니다. 각 GPU가 담당 전문가 외에 핫한 전문가의 복제본(redundant expert)을 몇 개 더 들고, 최근 N스텝의 부하 통계로 M스텝마다 전문가를 GPU에 재배치합니다. 프리필은 GPU당 복제 4개·1,000스텝마다 재배치, 디코드는 1,000스텝 통계·10,000스텝마다 재배치. 그 결과 가장 느린 rank와 평균의 비율(moe_lb)이 1.045~1.090 — 즉 불균형 손실이 10% 이내로 잡힙니다.

직접 돌려 볼 하드웨어가 있다면(아래 7절의 조건을 보세요) 실행은 이렇게 시작합니다.

6. 재현 가능한 추론 — batch-invariant 모드

작년 Thinking Machines의 Defeating Nondeterminism in LLM Inference가 화제가 된 뒤로, "같은 입력인데 왜 결과가 다르지?"의 주범이 배치 구성이라는 사실이 널리 알려졌습니다. 부동소수점 덧셈은 결합 순서에 따라 결과가 달라지는데, 내 요청이 어떤 요청들과 같은 배치에 묶이느냐에 따라 커널의 reduction 순서가 바뀌기 때문입니다. DeepInfer는 이를 프로덕션 엔진 차원에서 지원합니다. batch-invariant inference를 켜면 배치 구성이 달라져도 모델 결과가 동일하게 유지됩니다(NVIDIA 전용).

{{< highlight python >}} # 1) 배치 불변: 배치가 어떻게 묶여도 같은 입력 → 같은 logits # 환경 변수 DEEPINFER_BATCH_INVARIANT=1 # 2) 결정론 샘플링: 여기에 draft 가변 길이를 끄고(seq_seed가 고정돼야 하므로) # DEEPINFER_ENABLE_MTP_VARLEN=0 + 요청마다 고정 시드 params = SamplingParams( temperature=0.6, max_tokens=512, seq_seed=42, # 같은 토큰 입력 + 같은 파라미터 → 항상 같은 출력 ) {{< /highlight >}}

이게 왜 중요할까요? 평가(eval)를 돌릴 때 결과가 재현되지 않으면 "모델이 나빠진 건지, 배치 운이 나빴던 건지" 구분할 수 없습니다. 회귀 테스트는 플레이크가 되고, 디버깅은 미궁에 빠집니다. 실제로 DeepInfer의 예제 코드는 NVIDIA에서 기본으로 DEEPINFER_BATCH_INVARIANT=1을 켜고, PPL(perplexity) 골든 값을 샘플 단위로 정확히 비교하는 회귀 테스트를 돌립니다. 결정론이 테스트 인프라의 토대인 셈입니다.

7. 공개된 것과 공개되지 않은 것

흥분을 가라앉히고 README의 작은 글씨를 읽어 보면, 이 공개는 "서비스 전체"가 아닙니다. 완전한 추론 서비스를 만들려면 다음이 더 필요한데, 이번 릴리스에는 포함되지 않았습니다.

공개됨 (Apache 2.0)공개 안 됨 (내부 인프라에 강결합)
추론 엔진 본체: 커널·모델 런타임·샘플러, EP + EPLB, DSpark, SWA bounded replay, zero-overhead 스케줄러, batch-invariant 모드, structured outputs KV 캐시 시스템(3FS 기반 kvcache-store)
deepseek-recipe: Rust로 만든 API 프로토콜 ↔ 토큰 변환 컴포넌트 VE/Prefill/Decode 분리 배포의 배선 (엔진 쪽 기능은 대부분 구현돼 있음)
배포 Q&A 문서: 숫자가 들어간 운영 노하우 DP 복제본 간 로드밸런서 (Prefill/Decode/VE LB)

하드웨어 장벽도 분명합니다. 지원 대상이 NVIDIA SM100 GPU와 Huawei Ascend 950 NPU뿐이고, CUDA 13·Python 3.12·GCC 13 이상을 요구합니다. H100이나 RTX 4090에서는 돌아가지 않습니다. 지원 모델도 V4.1-Flash 하나입니다. 그러니 대부분의 독자에게 DeepInfer는 "돌리는 오픈소스"가 아니라 "읽는 오픈소스"에 가깝습니다. 그래도 가치가 줄지 않는 이유는, 코드와 Q&A 문서가 다른 곳에서는 돈 주고도 못 보는 프로덕션 설계 결정을 담고 있기 때문입니다. The New Stack이 짚었듯 Huawei 칩이 NVIDIA와 동급으로 지원 목록에 올라 있다는 점 자체도 신호입니다. 멀티 벤더 지원이 처음부터 설계 목표였다는 뜻이고, 추론 스택의 하드웨어 다변화가 더는 가정이 아니라는 뜻이기도 합니다.

deepseek-recipe의 보안 디테일 하나. 사용자 입력에 <｜User｜> 같은 특수 토큰 문자열이 섞여 들어와도, recipe는 이를 제어 토큰이 아니라 일반 토큰 시퀀스로 인코딩합니다. 텍스트가 제어 토큰을 주입해 모델 행동을 바꾸는 걸 토크나이즈 단계에서 차단하는 겁니다. 프롬프트 인젝션 방어가 프롬프트 층이 아니라 토큰 인코딩 층에서도 이뤄진다는 좋은 사례입니다.

8. 실전 — junior가 여기서 가져갈 것

SM100 슈퍼노드가 없어도 가져갈 설계 패턴은 분명합니다. 규모를 줄이면 여러분의 서빙 코드에도 그대로 적용됩니다.

① 라우팅은 버킷 + 비용 모델로. "요청을 빈 서버로"가 아니라, 요청을 비용 특성(컨텍스트 길이)으로 버킷에 나누고, 처리 시간을 예측하는 비용 모델로 예산을 채우는 방식입니다. 개념만 뽑으면 이렇습니다.

{{< highlight python >}} # 개념 의사코드 — DeepInfer Prefill LB의 chunk 크기 역산 아이디어 # cost(q, c) ≈ a*q^2 + b*q*c + ... : q = 이번에 처리할 토큰 수, # c = 이미 계산된 prefix 길이. 계수는 실측으로 피팅합니다. def solve_chunk_size(budget_ns: float, prefix_len: int) -> int: # 시간 예산을 정확히 소진하는 가장 큰 q를 2차방정식으로 역산 q = largest_q_with(lambda q: cost(q, prefix_len) <= budget_ns) return min(q, 32_768) # 토큰 상한도 함께 적용 {{< /highlight >}}

② KV 캐시는 히트율-비용 곡선으로 결정하라. "캐시를 며칠 보관할까"는 감이 아니라 측정의 문제입니다. DeepSeek은 TTL을 하루 단위로 바꿔 보며 히트율 손실(3일 TTL → 챗봇 히트율 0.5~1%p 하락)을 쟀습니다. 여러분의 prompt caching 설정에도 같은 사고방식이 통합니다.

③ 고정 예산 대신 한계 수익 배분. DSpark의 교훈은 speculative decoding을 넘어섭니다. 재시도 횟수, 검증 샘플 수, draft 길이 같은 "고정 N" 파라미터가 있다면, N을 고정하는 대신 성공 확률 추정치로 예산을 배분할 수 없는지 의심해 보세요.

④ 결정론을 테스트 인프라의 기본값으로. 서빙 코드를 만들 때 배치 불변·고정 시드 모드를 처음부터 설계에 넣으면, 골든 값 비교 테스트가 가능해지고 "가끔 다르게 나오는" 플레이크와 싸울 일이 줄어듭니다.

9. 흔한 실수 · 팁

  • "오픈소스 됐으니 바로 self-host 가능"이 아닙니다. 로드밸런서와 KV 캐시 스토어가 빠져 있고, 효율이 나오는 최소 단위가 128 GPU(64P+64D)입니다. 이번 릴리스의 1차 용도는 오프라인 추론과 학습용 레퍼런스입니다.
  • vLLM의 대체재가 아닙니다. vLLM에서 출발했지만 V4.1-Flash 전용으로 특화됐고, OpenAI 호환 서버를 띄워 주는 범용 서빙 프레임워크가 아닙니다. 범용 서빙이 필요하면 여전히 vLLM/SGLang이 답입니다.
  • batch-invariant는 NVIDIA 전용이고, 완전한 결정론 샘플링을 원하면 DEEPINFER_ENABLE_MTP_VARLEN=0으로 draft 가변 길이를 꺼야 합니다. 켜 둔 채로 "시드를 고정했는데 왜 달라지지?"라고 헤매기 쉽습니다.
  • 155조 토큰/일, GPU-시간당 38달러는 DeepSeek의 자체 공개 수치입니다. 외부 검증된 숫자가 아니니 인용할 때 출처를 밝히는 게 안전합니다.
  • 모델과 엔진의 라이선스가 다릅니다. V4.1-Flash 가중치는 MIT, DeepInfer 코드는 Apache 2.0입니다. 섞어 쓸 때 각자의 조건을 확인하세요.

10. 마무리 (TL;DR)

  • 10/20 DeepSeek이 프로덕션 추론 프레임워크 DeepInfer를 Apache 2.0으로 공개 — HN 2,000점+ 스레드. vLLM에서 출발해 V4.1-Flash 전용 엔진으로 진화했고, 단일 클러스터 하루 155조 토큰 서빙(자체 공개 수치).
  • 구조는 VE/Prefill/Decode 분리: 프리필은 8-GPU 머신에서 최소 EP, 디코드는 64–128 GPU 슈퍼노드에서 Wide-EP. 네 종류 로드밸런서가 각자 다른 균형 문제를 풀어 이상적 균형의 약 80% 도달.
  • KV 캐시는 스토리지 제품: 3FS SSD 100 PiB에 TTL 3~7일 보관, 어떤 머신이든 어떤 prefix든 히트. 전송은 비동기 fetch + GDR swap-in으로 계산과 겹쳐 숨김.
  • 속도 기술 3종: confidence로 검증 예산을 배분하는 DSpark(+4~11%), 마지막 128토큰만 재계산하는 SWA bounded replay(프리필 계산 거의 절반), GPU 공백을 없애는 zero-overhead 스케줄러.
  • batch-invariant 추론을 프로덕션 엔진이 기본 지원 — 평가 재현성과 회귀 테스트의 토대.
  • 단, 로드밸런서·KV 스토어는 미공개이고 하드웨어는 SM100/Ascend 950뿐 — 대부분에게는 "읽는 오픈소스". 그래도 버킷 라우팅, TTL 경제학, 한계 수익 배분, 결정론 기본값이라는 설계 패턴은 작은 시스템에도 그대로 가져갈 수 있습니다.
