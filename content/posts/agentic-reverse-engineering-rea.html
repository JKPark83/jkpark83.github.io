도입 — 이번 주 GitHub을 집어삼킨 리포

이번 주 GitHub Trending을 지켜봤다면 한 리포가 차트를 부수는 장면을 보셨을 겁니다. morluto/rea — 이름은 REA, "Reverse Engineer Anything"의 약자입니다. 트렌딩 집계 기준으로 10월 6일경 5천여 개였던 별이 9일 2만 7천, 11일 4만 6천을 넘더니, 이 글을 쓰는 10월 12일 아침 리포 페이지에는 10만 1천 개가 찍혀 있습니다. 집계 사이트마다 숫자에 편차는 있지만, 어느 쪽을 보더라도 일주일 만에 스무 배라는 성장입니다. 10월 8일에는 유튜버 Matthew Berman이 소개하며 X에서도 크게 돌았고, 며칠 사이 GitHub Trending 1위 보도가 이어졌습니다.

한 줄 요약은 이렇습니다. "MCP 서버 하나로, 에이전트가 소스 코드 없는 소프트웨어를 분석한다." 네이티브 바이너리의 디스어셈블리부터 Electron 앱의 IPC 추적, APK, 웹사이트, 네트워크 캡처까지를 Claude Code·Codex·Cursor 같은 코딩 에이전트의 도구로 밀어 넣는 물건입니다. 리버스 엔지니어링(reverse engineering)이라는, 전통적으로 소수 전문가의 영역이던 작업이 "에이전트에게 시키는 일"의 목록에 들어온 셈이죠.

그런데 리포를 실제로 뜯어보면, junior AI 엔지니어에게 가장 배울 거리가 많은 부분은 리버스 엔지니어링 그 자체가 아닙니다. 수 기가바이트짜리 분석 대상을 컨텍스트 윈도우가 유한한 에이전트에게 어떻게 먹일 것인가 — 이 문제를 REA가 꽤 교과서적으로 풀어놨다는 점입니다. Evidence 레코드, 핸들 참조, 응답 바이트 예산, fail-closed 무결성 정책 같은 설계는 바이너리 분석이 아니라 어떤 도메인의 MCP 도구를 만들더라도 그대로 쓸 수 있는 패턴입니다. 오늘은 REA를 안내자 삼아 이 패턴들을 하나씩 살펴보겠습니다.

배경 — 리버스 엔지니어링과 LLM은 왜 잘 맞나

리버스 엔지니어링은 소스 코드 없이 완성된 소프트웨어를 분석해 동작 원리를 알아내는 작업입니다. 호환 구현을 만들기 위한 상호운용성 분석, 멀웨어 분석, 사라진 소스의 레거시 시스템 이해, 보안 취약점 연구가 대표적인 용도죠. 도구는 이미 훌륭합니다. NSA가 공개한 Ghidra, 상용 디스어셈블러 IDA와 Hopper 같은 도구가 기계어를 사람이 읽을 만한 의사코드(pseudocode)로 복원해 줍니다.

문제는 그다음입니다. 디컴파일러가 뱉는 건 sub_401a20 같은 이름 없는 함수 수천 개와 수십만 줄의 의사코드입니다. 이걸 읽고 "아, 이 함수가 공의 x좌표를 스테레오 팬 값으로 바꾸는 헬퍼구나"라고 알아내는 건 여전히 사람 몫이었고, 그래서 리버스 엔지니어링은 학습 곡선이 가파른 전문 기술로 남아 있었습니다.

그런데 이 "이름 없는 코드 덩어리에서 의도를 읽어내는 일"은 LLM이 유난히 잘하는 일입니다. 변수 이름 복원, 함수 요약, 호출 관계에서 기능 추론 — 전부 패턴 인식과 언어화 작업이니까요. 그래서 MCP(Model Context Protocol)가 자리 잡자마자 디스어셈블러를 LLM에 연결하는 시도가 나왔습니다. 2025년의 GhidraMCP가 대표적입니다. Ghidra 플러그인으로 HTTP 서버를 띄우고, LLM이 디컴파일·심볼 조회·이름 변경을 호출하게 한 물건이죠.

REA가 이번 주에 터진 건 이 흐름의 다음 단계이기 때문입니다. GhidraMCP가 "Ghidra 한 개를 LLM에 연결"했다면, REA는 디스어셈블러 셋(Hopper·Ghidra·IDA)에 JADX(APK), WABT(WASM), 브라우저, 프로세스 캡처, 네트워크 캡처까지를 MCP 서버 하나로 통합하고, 처음부터 에이전트가 쓰기 좋은 응답 형태로 설계했습니다. npx 명령 하나로 Claude Code·Codex·Cursor·Gemini CLI에 붙는 설치 경험도 한몫했고요. 도구를 연결하는 것과 에이전트용으로 설계하는 것의 차이 — 이게 오늘 본론의 주제입니다.

REA 한 바퀴 — MCP 서버 하나, 분석 대상 전부

먼저 전체 그림입니다. REA는 MIT 라이선스의 CLI 겸 MCP 서버입니다. README의 표현을 빌리면 "One MCP for reverse engineering across binaries, applications, and runtime behavior" — 바이너리, 애플리케이션, 런타임 동작을 아우르는 리버스 엔지니어링 MCP 하나입니다. 에이전트가 MCP로 질문하면 REA가 대상을 검사·추적하고, 결론마다 근거와 한계를 붙인 결과를 돌려줍니다. 분석은 전부 로컬에서 돌아갑니다(단, 결과를 읽는 모델 쪽의 데이터 정책은 별개라고 README가 명시합니다).

구조도 짚고 갈 포인트가 있습니다. 네이티브 분석에서 REA는 Hopper·Ghidra·IDA를 프로바이더(provider)로 추상화합니다. 에이전트는 open_binary로 대상을 열면서 프로바이더를 auto로 두면 되고, 어느 디스어셈블러가 뒤에서 도는지는 몰라도 됩니다. 분석 세션은 open_binary → 분석 도구들 → close_binary라는 수명 주기로 묶이고, 닫는 순간 세션에 쌓인 분석 결과도 함께 정리됩니다. 데이터베이스 커넥션 풀을 다뤄 봤다면 익숙한 모양새일 겁니다.

핵심 설계 ① Evidence — 주장에 증거를 묶는다

리버스 엔지니어링에 LLM을 붙일 때 가장 무서운 실패는 그럴듯한 헛소리입니다. "이 함수는 라이선스 키를 검증합니다"라는 답이 디컴파일 결과에 근거한 건지, 함수 이름 보고 지어낸 건지 구분이 안 되면 분석 결과 전체를 신뢰할 수 없게 됩니다.

REA의 답은 모든 분석 결과를 Evidence 레코드라는 구조로 돌려주는 겁니다. 도구 계약 문서(docs/mcp-contracts.md)에 따르면, 분석을 수행하는 도구는 항상 다음 요소를 포함한 레코드를 반환합니다.

{{< highlight json >}} { "evidence_id": "ev_01…", // 이 분석 결과의 고유 핸들 "normalized_result": { … }, // 정규화된 분석 결과 (의사코드, 블록, 호출 관계 …) "raw_result": { … }, // 원본 도구 출력 (없으면 null — 출처 추적용) "analysis_profile": { … } // 어떤 도구·설정으로 분석했는지 (항상 포함) } {{< /highlight >}}

주의: 위 JSON은 계약 문서가 설명하는 필드를 간추린 개념 예시입니다. 실제 레코드에는 대상·도구별 필드가 더 붙습니다.

포인트는 두 가지입니다. 첫째, analysis_profile이 항상 붙기 때문에 "이 결론이 어느 도구의 어떤 분석에서 나왔는지"가 결과에 내장됩니다. 호출 그래프 도구는 프로바이더가 못 푼 노드를 limitations로, 경로 추적 도구는 residual_unknowns(남은 미지)와 truncated(잘림 여부)를 함께 돌려줍니다. 모델이 한계를 지어내서 숨길 여지를 스키마 수준에서 줄인 겁니다.

둘째가 진짜 컨텍스트 엔지니어링입니다. 한 번 만들어진 Evidence는 세션에 보관되고, 이후 도구들은 결과 전체 대신 핸들만 받아도 됩니다. 두 함수를 비교하는 compare_functions를 부를 때 의사코드 덩어리 두 개를 도구 인자로 다시 밀어 넣는 게 아니라, 이렇게 참조만 넘깁니다.

{{< highlight json >}} { "left": { "kind": "retained-evidence", "evidence_id": "ev_01HX…" }, "right": { "kind": "retained-evidence", "evidence_id": "ev_01HY…" } } {{< /highlight >}}

참조는 현재 연결(세션)에 묶여 있고 close_binary가 정리합니다. 왜 이게 중요할까요? 에이전트의 대화 기록에서 도구 호출의 인자와 결과는 전부 컨텍스트 토큰입니다. 의사코드 500줄짜리 함수 둘을 "분석 → 비교 → 재분석" 하는 동안 매번 본문을 주고받으면, 같은 내용이 컨텍스트에 서너 번씩 복제됩니다. 핸들 방식이면 큰 덩어리는 서버에 한 번만 머물고, 대화에는 ID만 오가죠. 이 블로그에서 다룬 MCP 코드 실행이나 컨텍스트를 덜 쓰는 에이전트와 정확히 같은 문제의식을, "서버 쪽 상태 + 핸들"로 푼 사례입니다.

핵심 설계 ② 응답 예산 — 컨텍스트에 바이너리를 들이붓지 않는 법

핸들로 저장해 둔 결과라도, 결국 모델이 읽으려면 컨텍스트로 들어와야 합니다. 여기서 두 번째 설계가 나옵니다. 응답에 바이트 예산을 걸고, 큰 결과는 "뷰"로 잘라 읽게 하는 것입니다.

  • 하드 예산 — MCP 응답은 기본 10MiB로 캡이 걸려 있습니다(REA_MCP_MAX_RESPONSE_BYTES로 조정). 한도를 넘는 결과는 데이터 대신 resource_constraint 오류가 돌아오고, 이때는 export_evidence_bundle로 파일에 통째로 내보낸 뒤 필요한 부분만 다시 읽는 게 공식 우회로입니다.
  • 페이지네이션 뷰 — inspect_analysis_view는 보관된 Evidence에서 요약·섹션·모듈·의사코드 페이지 같은 "뷰"를 투영해 줍니다. offset/limit(기본 64)으로 끊어 읽고, 결과의 coverage.next_offset이 다음 위치를 알려 줍니다. 프로바이더를 다시 띄우지 않고 저장된 결과에서만 읽기 때문에 싸고 빠릅니다.
  • 이어 읽기 안내 — 함수 하나가 너무 커서 잘리면, 결과에 그대로 복사해 부르면 되는 다음 호출(continuation)이 포함됩니다. 모델이 "어디까지 읽었더라"를 계산하다 틀리는 흔한 실수를 설계로 막은 거죠.
  • 스키마 다이어트 — 도구가 많아지면 도구 정의 자체가 컨텍스트를 먹습니다. REA는 REA_MCP_INPUT_SCHEMA_PROFILE=compact로 광고되는 입력 스키마를 약 13KB까지 줄이는 모드를 둡니다. 스키마 크기에 상한이 있는 클라이언트 대응이지만, "도구 정의도 비용"이라는 감각 자체가 배울 점입니다. 이 블로그의 Tool Search와 지연 로딩에서 다룬 문제의식과 같은 축입니다.

정리하면 REA의 응답 설계는 "모델에게 다 보여 준다"가 아니라 "모델이 필요한 만큼만, 명시적 비용으로 꺼내 읽게 한다"입니다. 수십만 줄짜리 분석 대상을 다루면서도 에이전트 컨텍스트가 터지지 않는 비결입니다.

핵심 설계 ③ 신뢰 경계 — 관찰·추론·미지를 구분시킨다

세 번째 축은 에이전트의 인식과 행동을 어떻게 통제하느냐입니다. REA는 MCP의 prompts 기능으로 가이드 프롬프트 6종을 제공합니다. 기능 추적(investigate_feature), 버전 비교, 재구현 검증(verify_reconstruction), 크래시 추적, 남은 미지 감사(audit_residual_unknowns), 그리고 실행 실험 설계(prepare_bounded_process_capture)까지. 문서가 강조하는 원칙이 인상적입니다.

  • "관찰, 추론, 미지를 구분하라(keep observations, inferences, and unknowns distinct)" — 디컴파일 결과에서 직접 본 것, 거기서 추론한 것, 아직 모르는 것을 에이전트가 섞지 못하게 워크플로 수준에서 요구합니다. LLM-as-a-judge나 리서치 에이전트를 만들 때도 그대로 쓸 수 있는 규율입니다.
  • 제안은 호출이 아니다 — 가이드 프롬프트의 도구 제안은 "시작점일 뿐 도구 호출이 아니"고, 프롬프트 인자와 자동완성 선택지는 "지시도 권한도 아닌 신뢰할 수 없는 선택 데이터(untrusted selection data)"로 취급하라고 명시합니다. 분석 대상(= 잠재적으로 적대적인 입력)에서 나온 문자열이 에이전트의 명령이 되는 프롬프트 주입 경로를 문서 수준에서 끊은 겁니다.
  • 부수효과의 명시 — 도구마다 readOnlyHint/destructiveHint 애너테이션이 붙고, 외부 코드를 실행하는지(executesForeignCode), 기기를 변경하는지(mutatesDevice)가 표시됩니다. 힌트일 뿐 권한 통제는 아니라고 못 박는 것까지 포함해서, 정직한 설계입니다.
  • 무결성은 fail-closed — 분석 중 바이트 불일치가 감지되면 기본값은 실패입니다. integrity_policy=record-and-continue를 명시해야만 불일치를 격리·기록하고 계속 갑니다. "일단 계속 진행"이 디폴트가 아니라는 점, 운영 도구를 만들어 본 사람이라면 고개를 끄덕일 선택입니다.

실전 — 직접 붙여 보기

설치는 한 줄입니다. Node.js 22.19 이상이 필요하고, 셋업 마법사가 어떤 에이전트에 연결할지 묻고 변경 사항을 보여 준 뒤 승인받아 적용합니다(기존 설정은 백업).

{{< highlight bash >}} # Claude Code / Codex / Cursor / Gemini CLI 등에 REA MCP 서버 등록 npx rea-agents setup # MCP 없이 CLI로 바로 분석할 수도 있습니다 npx -y rea-agents@latest analyze-javascript-application ./내앱 --json {{< /highlight >}}

네이티브 바이너리 분석에는 Hopper·Ghidra·IDA 중 하나가 필요합니다(Ghidra는 무료, Hopper는 데모 모드로도 동작). 감을 잡기 좋은 건 리포의 쇼케이스입니다.

  • Electron 앱 추적 (Notion) — 렌더러의 클립보드 API에서 출발해 preload 스크립트와 IPC를 거쳐 메인 프로세스까지, 클립보드 브리지의 전체 경로를 추적합니다. "이 기능이 어느 프로세스의 어느 모듈을 지나가는가"를 소스 없이 그려내는 전형적인 사용례입니다. Electron 분석은 파일만 읽는 정적 분석이라 앱을 실행하지 않습니다.
  • 검증되는 재구현 (DX-Ball) — 고전 게임의 사운드 호출을 따라가 "공의 x좌표 → 스테레오 팬" 헬퍼 함수를 찾고, 불완전한 의사코드를 C 코드로 복원합니다. 재미있는 건 검증 방식입니다. 복원한 C가 원본 x86 테스트 케이스 3,205개를 통과하고, 컴파일하면 원본 함수의 63바이트를 그대로 재현하는지까지 확인합니다. "그럴듯한 복원"이 아니라 "기계적으로 검증된 복원"이죠. verify_reconstruction 프롬프트가 바로 이 워크플로입니다.

junior 개발자에게 현실적인 출발점은 바이너리보다 자기 회사 제품의 Electron/JS 번들입니다. "빌드 산출물에 소스맵이 새고 있지 않나", "번들에 포함된 모듈 그래프가 의도와 같나", "두 릴리스 사이에 뭐가 달라졌나"(compare_application_versions) 같은 질문은 전부 합법적이고 당장 유용한 분석입니다.

법과 윤리 — "할 수 있다"와 "해도 된다"는 다릅니다

힘이 센 도구라 경계도 분명히 해야 합니다. REA 스스로 면책 조항에 "REA는 합법적인 리버스 엔지니어링 연구·분석·재구성을 위한 도구를 제공한다", "필요한 승인 획득과 법규 준수는 사용자 책임"이라고 못 박고 있습니다. 리버스 엔지니어링의 적법성은 나라·목적·라이선스 약관에 따라 크게 달라집니다. 상호운용성 분석이나 자사 제품 점검, 허가받은 보안 연구는 널리 인정되는 용도지만, 타사 앱의 보호 장치 우회나 기능 무단 복제는 다른 문제입니다. 실제로 이번 주 화제 속에서도 "결국 남의 앱 베끼기 도구 아니냐"는 비판과 "상호운용성·분석의 민주화"라는 반론이 같이 돌았습니다. 도구가 에이전트로 쉬워질수록, "해도 되는 일인가"를 묻는 habit은 엔지니어 본인 몫으로 남습니다.

흔한 실수 · 팁

  • 에이전트의 결론을 그대로 믿지 마세요 — Evidence 구조는 검증 가능성을 주는 것이지 정답을 보장하지 않습니다. 중요한 결론일수록 analysis_profile과 근거 의사코드를 직접 열어 보고, residual_unknowns가 남아 있는 결론은 "미확정"으로 다루세요. audit_residual_unknowns 프롬프트가 이 점검용입니다.
  • 분석 대상은 적대적 입력입니다 — 바이너리 속 문자열, 웹페이지의 스크립트가 에이전트에게 지시를 내리려 들 수 있습니다(프롬프트 주입). REA가 선택 데이터를 비신뢰로 취급하듯, 여러분의 에이전트 설정에서도 분석 결과를 근거 자료로만 쓰게 하고, 특히 capture_process_scenario처럼 실제 실행이 걸린 도구는 자동 승인 목록에 넣지 마세요. 실행 캡처는 여러분의 사용자 권한으로 대상을 돌립니다 — 모르는 바이너리라면 일회용 VM이 기본입니다.
  • 큰 바이너리는 타임아웃부터 — 대형 바이너리 임포트는 분 단위로 걸릴 수 있습니다. 프로바이더 기동이 실패하면 REA_GHIDRA_STARTUP_TIMEOUT_MS/REA_HOPPER_STARTUP_TIMEOUT_MS를 먼저 올려 보세요.
  • 로컬 분석 ≠ 데이터가 안 나간다 — 분석 자체는 로컬이지만, 결과를 읽는 건 모델입니다. 의사코드·문자열이 모델 프로바이더로 전송된다는 뜻이니, 사내 독점 코드가 섞인 대상이라면 데이터 정책을 먼저 확인하세요. README의 FAQ도 이 구분을 명시합니다.
  • 패턴은 가져가되 규모는 가늠하세요 — 여러분이 만들 MCP 도구가 응답 수 KB짜리라면 Evidence 저장소까지는 과합니다. 반대로 응답이 수백 KB를 넘나들고 여러 도구가 같은 결과를 돌려 쓴다면, 오늘 본 핸들 + 뷰 + 예산 3종 세트가 교과서입니다.
  • 별 수는 품질 지표가 아닙니다 — 일주일에 별 10만 개는 관심의 증거지 성숙의 증거가 아닙니다. 같은 기간 릴리스가 매일 나왔다는 건 API가 아직 빠르게 움직인다는 뜻이기도 합니다. 도입한다면 버전을 고정하고 체인지로그를 따라가세요.

마무리 (TL;DR)

  • REA(morluto/rea)가 이번 주 GitHub을 휩쓸었습니다 — 10/6 약 5.4K였던 별이 10/12 작성 시점 101.7K. MCP 서버 하나로 네이티브 바이너리·WASM·Electron·.NET·APK·웹사이트를 에이전트가 분석하게 해 주는 MIT 라이선스 도구입니다.
  • 진짜 배울 점은 RE가 아니라 도구 설계입니다: ① 모든 결과를 Evidence 레코드(evidence_id + 정규화 결과 + 원본 + 분석 프로필)로 반환하고 후속 도구는 핸들만 참조 → 컨텍스트 복제 제거, ② 10MiB 응답 예산 + 페이지네이션 뷰 + 이어 읽기 continuation → 거대 결과를 필요한 만큼만 열람, ③ 관찰·추론·미지 구분, fail-closed 무결성, 비신뢰 선택 데이터 → 환각과 프롬프트 주입을 구조로 방어.
  • 시작은 npx rea-agents setup 한 줄. 바이너리 분석엔 Ghidra(무료) 등이 필요하고, 첫 연습 대상으론 자사 Electron/JS 번들 점검이 적당합니다.
  • 합법적 용도(상호운용성, 자사 제품 점검, 허가된 보안 연구)와 아닌 것의 경계는 사용자 책임입니다. 실행이 걸린 도구는 자동 승인 금지, 모르는 바이너리는 VM에서.
