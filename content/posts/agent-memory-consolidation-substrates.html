1. 도입 — 메모리를 붙였더니 에이전트가 더 헷갈려한다?

에이전트에 장기 기억을 붙여 본 분이라면 한 번쯤 겪는 시나리오입니다. Mem0 같은 메모리 라이브러리를 연결하고, 대화가 끝날 때마다 기억을 차곡차곡 저장했습니다. 처음 며칠은 훌륭합니다. 사용자 이름도 기억하고, 지난주에 정한 규칙도 지킵니다. 그런데 한 달쯤 지나자 이상해집니다. 석 달 전에 바뀐 옛날 설정을 꺼내 오고, 비슷한 기억 다섯 개를 한꺼번에 검색해 와서는 컨텍스트만 부풀리고, 정작 지금 하던 작업의 핵심은 놓칩니다. 기억이 늘었는데 왜 더 멍청해질까요?

8월의 AI 엔지니어링 커뮤니티가 정확히 이 질문을 붙들고 있습니다. 8월 중순 공개된 Harness the Memory(arXiv:2608.15008)는 7가지 메모리 substrate를 하나의 통제된 하네스에서 비교해 지난주까지 Hugging Face 데일리 페이퍼에서 화제가 됐고, 같은 시기 공개된 LycheeMemory V2(arXiv:2608.12990)는 기억을 '정리'하는 통합 파이프라인으로 토큰을 약 71% 줄이면서 정확도를 올려 트렌딩 상위권에 올랐습니다. 여기에 Mem0의 State of AI Agent Memory 2026 리포트까지 겹치면서, "메모리는 이제 저장 문제가 아니라 라이프사이클 문제"라는 논의가 주간 뉴스레터마다 이어졌습니다.

결론부터 말하면 이렇습니다. 기억은 쌓는 게 아니라 정리하는 것입니다. 무엇을 남기고(추출), 겹치는 것을 어떻게 합치고(융합), 낡은 것을 언제 버릴지(퇴역)를 설계하지 않으면, 메모리 저장소는 필요한 바늘 하나를 찾기 위해 전체를 뒤져야 하는 건초더미(haystack)가 됩니다. 이 글에서는 그 정리의 원리를 이번 달 화제가 된 연구들의 숫자와 함께 뜯어봅니다.

이 글에서 얻어 갈 것. ① 메모리 substrate 7가지 분류와 "만능 저장 방식은 없다"는 벤치마크 결론, ② 통합(consolidation) 라이프사이클 — 추출·융합·승격·퇴역의 설계법, ③ LycheeMemory의 71% 토큰 절감이 어디서 나오는지, ④ 기억이 많을수록 학습이 망가지는 '메모리-보상 함정', ⑤ sqlite만으로 만들어 보는 미니 통합 파이프라인 코드.

2. 배경 — 기억 파이프라인 복습: 병목은 '저장'이 아니라 '정리'

이 블로그에서 에이전트 메모리 기초를 다룬 적이 있습니다. 짧게 복습하면, LLM은 상태가 없어서(stateless) 컨텍스트 윈도우 밖의 일은 전부 잊습니다. 그래서 기억을 모델 바깥에 두고, 세 단계 파이프라인으로 관리합니다. 대화에서 기억할 가치가 있는 것을 뽑아 저장하는 쓰기(write), 저장된 기억을 정리하는 통합(consolidation), 필요할 때 골라 꺼내는 읽기(read)입니다.

주니어 시절에는 대부분 쓰기와 읽기만 만들고 끝냅니다. "저장하고 검색하면 되지, 정리가 왜 필요해?"라고 생각하기 쉽습니다. 사람으로 비유하면 이렇습니다. 매일 겪은 일을 전부 일기장에 적기만 하고 한 번도 정리하지 않는 사람과, 주말마다 중요한 것만 노트에 옮기고 낡은 메모를 버리는 사람이 있습니다. 1년 뒤 "내가 작년에 정한 원칙이 뭐였지?"라는 질문에 누가 빨리 정확히 답할까요? 뇌과학에서도 자는 동안 해마의 단기 기억을 장기 기억으로 옮겨 정리하는 과정을 consolidation이라고 부릅니다. 에이전트도 똑같은 단계가 필요합니다.

정리를 건너뛰면 세 가지 문제가 누적됩니다. 첫째, 중복 — "사용자는 Python을 선호한다"는 기억이 표현만 다르게 열 개 쌓입니다. 둘째, 모순 — "배포는 금요일에 한다"와 "배포는 금요일에 하지 않기로 했다"가 공존하고, 검색 순위에 따라 아무거나 걸립니다. 셋째, 희석 — 저장소가 커질수록 검색 결과에 잡동사니가 섞여 들어와, 정작 필요한 기억의 신호가 흐려집니다. Vektor Memory의 2026년 연구 동향 정리는 "기억이 통합되고, 승격되고, 강등되고, 퇴역하는 라이프사이클이야말로 현재 메모리 도구들이 가장 덜 다룬 차원이며, 이것이 없으면 저장소는 건초더미가 된다"고 지적합니다.

3. substrate 지형도 — 기억을 '어디에, 어떤 모양으로' 둘 것인가

정리 이야기를 하기 전에, 먼저 기억을 담는 그릇부터 봅시다. 메모리 substrate는 기억을 저장하고 꺼내는 물리적 방식, 쉽게 말해 기억의 그릇입니다. 위에 어떤 메모리 프레임워크를 얹든, 바닥에서는 결국 이 그릇 중 하나(또는 조합)를 씁니다. Harness the Memory 논문은 이 그릇들을 7가지로 나눠 같은 조건에서 비교했습니다.

이 논문이 흥미로운 이유는 규모입니다. 백본 모델 3종, 사용자 중심 QA부터 에이전트 중심 의사결정까지 벤치마크 스위트 4종, 성능·효율 지표 26개를 하나의 통제된 하네스에서 돌렸습니다. 그동안 메모리 시스템들은 저마다 다른 벤치마크에서 자기가 최고라고 주장해 왔는데, 같은 링에 올려 본 겁니다. 결과는 세 문장으로 요약됩니다.

  • 모든 상황을 이기는 substrate는 없습니다. 태스크 종류, 히스토리 길이, 운영 조건에 따라 승자가 바뀝니다.
  • 폭넓은 검색은 양날의 검입니다. 장문 컨텍스트에서 사실을 찾는 QA에는 기억을 많이 꺼내 올수록 유리하지만, 순차적 의사결정 태스크에서는 과도한 검색이 행동에 필요한 핵심 컨텍스트에서 주의를 빼앗아 성능을 떨어뜨립니다.
  • 규모가 또 하나의 축입니다. 중간 길이 히스토리에서 잘 동작하던 substrate가 히스토리가 길어지면 비용이 폭증하거나 취약해집니다. 그래서 논문은 상황에 따라 그릇을 바꿔 끼우는 substrate 라우팅(routing)을 다음 과제로 제시합니다.

주니어 입장에서 실용적인 해석은 이렇습니다. 벡터 DB 하나 붙여 놓고 "메모리 완성"이라고 부르는 순간, 밀집 인덱스라는 그릇 하나에 모든 태스크를 밀어 넣은 셈입니다. 챗봇처럼 "지난번에 뭐라고 했더라?"를 찾는 서비스라면 그걸로 충분할 수 있습니다. 하지만 여러 단계 작업을 이어 가는 에이전트라면, 검색을 늘리는 것보다 꺼내 오는 양을 통제하고 저장소를 정리하는 쪽이 성능을 올립니다. 그 정리가 다음 섹션의 주제입니다.

4. 통합(consolidation) — 기억의 라이프사이클을 설계한다

통합은 저장된 기억을 배경에서 정리하는 모든 작업을 묶어 부르는 말입니다. 구체적으로는 네 단계 라이프사이클로 나눌 수 있습니다. 이 라이프사이클을 실제 오픈소스로 구현해 이번에 화제가 된 것이 LycheeMemory(GitHub 1.2k 스타, Apache-2.0)입니다. 구조를 보면서 단계를 따라가 봅시다.

각 단계를 뜯어보면 이렇습니다.

① 추출(extraction). 대화 원문을 통째로 저장하지 않고, 기억할 가치가 있는 조각만 뽑아 타입을 붙여 저장합니다. LycheeMemory는 레코드를 fact(사실), preference(선호), event(사건), constraint(제약), procedure(절차), failure_pattern(실패 패턴), tool_affordance(툴 사용법) 7가지 타입으로 나눕니다. 타입이 있으면 나중에 "제약 조건만 전부", "이 툴 관련 실패 패턴만" 같은 선별 검색이 가능해집니다.

② 탈맥락화(decontextualization). "그거 어제 말한 대로 바꿔 줘"에서 추출한 기억이 "그거"와 "어제"를 그대로 담고 있으면, 석 달 뒤에 꺼냈을 때 아무 의미가 없습니다. 대명사와 상대적 시간 표현을 풀어서, 기억 혼자 읽혀도 이해되는 문장으로 고쳐 씁니다. "사용자는 2026-08-26에 배포 스크립트의 타임아웃을 30초에서 120초로 늘리기로 결정했다"처럼요.

③ 융합(fusion). 새 기억을 넣기 전에 비슷한 기존 기억을 찾아, 중복이면 합치고 모순이면 최신 정보로 갱신합니다. 갱신하되 이전 값을 이력으로 남기면, "원래는 30초였는데 언제 바뀌었지?" 같은 질문에도 답할 수 있습니다. 이 충돌 처리는 벤치마크에서도 별도 역량으로 잴 만큼 중요합니다. ICLR 2026의 MemoryAgentBench는 메모리 시스템의 역량을 정확한 검색(accurate retrieval), 테스트 시점 학습(test-time learning), 장거리 이해(long-range understanding), 충돌 해소(conflict resolution) 4가지로 나눠 평가하는데, 나중에 들어온 정보가 이전 정보를 이기는지를 반사실(counterfactual) 편집으로 직접 테스트합니다.

④ 승격과 퇴역(promotion & retirement). 반복해서 확인되는 기억은 신뢰 점수를 올려 검색에서 우대하고, 반복 등장하는 절차는 아예 스킬 문서로 승격합니다. 반대로 오래 안 쓰이는 기억은 점수를 낮추다가 결국 내립니다. LycheeMemory는 시각 기억에 에빙하우스 망각 곡선을 본뜬 7~30일 반감기를 적용합니다. 사람이 안 쓰는 기억을 잊는 것처럼, 에이전트도 잊는 능력이 있어야 저장소가 건초더미가 되지 않습니다.

어디서 많이 본 구조 아닌가요? 맞습니다. 컨텍스트 엔지니어링의 압축(compaction)과 원리가 같습니다. 컨텍스트 압축이 세션 '안'에서 창이 넘치지 않게 정리하는 일이라면, 메모리 통합은 세션 '밖' 저장소를 정리하는 일입니다. LycheeMemory의 워킹 메모리가 예산 70%에서 배경 압축을 시작하고 90%에서 오래된 턴을 요약으로 방출하는 이중 임계값 설계는, 두 세계가 같은 문제의식으로 수렴하고 있다는 좋은 증거입니다.

5. 숫자 읽기 — 71% 토큰 절감, 그리고 메모리-보상 함정

RoMeRL
(arXiv:2608.02508)		 스스로 기억을 쌓는 에이전트의 메모리를 고정된 의미 좌표로 묶어, 무한히 자라는 대신 갱신·교체하게 제한 ALFWorld·LifelongAgentBench에서 성능 향상, 유지 메모리 크기 −84.4%, LLM 호출 −21.1%, 피드백 밀도 약 6배

첫 줄부터 봅시다. 토큰 71% 절감이 어떻게 정확도 상승과 동시에 나올 수 있을까요? 비결은 마법이 아니라 그림 2에서 본 원리입니다. 정리된 저장소에서 예산 안에서만 골라 꺼내면, 컨텍스트에 들어가는 기억의 양은 줄고 밀도는 올라갑니다. 모델 입장에서는 읽을 것이 줄어드니 비용이 내려가고, 잡동사니가 빠지니 답은 좋아집니다. 적은 컨텍스트가 더 나은 에이전트를 만든다에서 다룬 원리가 메모리에서도 그대로 통하는 셈입니다.

셋째 줄 RoMeRL은 다른 각도에서 같은 교훈을 줍니다. 이 논문이 메모리-보상 함정(memory-reward trap)이라 부르는 현상은, 경험에서 배우며 스스로 기억을 늘려 가는 에이전트에서 생깁니다. 기억 항목이 무한정 늘어나면 각 항목이 실제로 쓰이고 피드백을 받는 빈도가 점점 희박해져서, 검증도 정리도 안 된 기억이 산처럼 쌓입니다. RoMeRL의 처방은 통합의 극단형입니다. 기억 슬롯을 고정된 의미 좌표 집합으로 묶고, 새 경험은 새 슬롯을 만드는 대신 기존 슬롯의 내용을 갱신·교체합니다. 그 결과 유지하는 메모리가 84.4% 줄었는데 성능은 올랐습니다. 기억의 가치는 개수가 아니라, 각 기억이 얼마나 자주 검증되고 쓰이느냐에서 나온다는 뜻입니다.

주의해서 읽을 부분. LycheeMemory의 71%·55% 숫자는 저장소가 자체 벤치마크 환경에서 보고한 값입니다. 방향은 다른 연구들과 일치하지만, 정확한 크기는 여러분의 워크로드에서 다시 재야 합니다. 그리고 Harness the Memory의 결론이 말해 주듯, 어떤 메모리 구성이든 "우리 태스크 믹스에서" 측정하기 전까지는 남의 벤치마크 순위표를 그대로 믿지 않는 게 안전합니다.

6. 실전 — sqlite로 만드는 미니 통합 파이프라인

원리를 확인했으니 최소 구현을 만들어 봅시다. 외부 라이브러리 없이 Python 표준 라이브러리의 sqlite3만으로, ① 타입 있는 레코드 저장, ② 융합(중복 병합·모순 갱신), ③ 사용 기반 승격·퇴역, ④ 예산 안 읽기까지 넣습니다. 실제 서비스에서는 임베딩 검색을 더하겠지만, 라이프사이클의 뼈대는 이 코드 그대로입니다.

{{< highlight python >}} import sqlite3, time, json DB = sqlite3.connect("memory.db") DB.executescript(""" CREATE TABLE IF NOT EXISTS mem( id INTEGER PRIMARY KEY, type TEXT NOT NULL, -- fact/preference/constraint/procedure/... text TEXT NOT NULL, -- 탈맥락화된 문장 status TEXT DEFAULT 'candidate', -- candidate/active/retired confirms INTEGER DEFAULT 1, -- 재확인 횟수 (승격 근거) uses INTEGER DEFAULT 0, -- 검색돼 쓰인 횟수 updated REAL, -- 마지막 갱신 시각 history TEXT DEFAULT '[]' -- 갱신 전 이전 값들 ); -- 데모용 standalone FTS 테이블 (content= 외부 참조 방식은 직접 UPDATE 불가) CREATE VIRTUAL TABLE IF NOT EXISTS mem_fts USING fts5(text); """) def write(mtype: str, text: str): """쓰기 경로: 저장 전에 반드시 융합을 시도한다.""" now = time.time() # 1) 비슷한 기존 기억 검색 (실전에서는 임베딩 유사도 병용) dup = DB.execute( "SELECT rowid, * FROM mem WHERE id IN " "(SELECT rowid FROM mem_fts WHERE mem_fts MATCH ?) AND type=? " "AND status != 'retired' LIMIT 1", (' OR '.join(text.split()[:5]), mtype)).fetchone() if dup is None: # 신규 → 후보로 입장 cur = DB.execute( "INSERT INTO mem(type,text,updated) VALUES(?,?,?)", (mtype, text, now)) DB.execute("INSERT INTO mem_fts(rowid,text) VALUES(?,?)", (cur.lastrowid, text)) else: # 융합: 갱신 + 이전 값은 이력으로 mid, _, old_text = dup[0], dup[1], dup[3] hist = json.loads(dup[8]) + [old_text] DB.execute( "UPDATE mem SET text=?, confirms=confirms+1, updated=?, " "history=?, status=CASE WHEN confirms+1>=3 " "THEN 'active' ELSE status END WHERE id=?", (text, now, json.dumps(hist, ensure_ascii=False), mid)) DB.execute("UPDATE mem_fts SET text=? WHERE rowid=?", (text, mid)) DB.commit() {{< /highlight >}}

포인트는 write()가 저장 전에 반드시 융합을 시도한다는 것, 그리고 세 번 이상 재확인된 기억만 active로 승격한다는 것입니다. 이제 읽기와 퇴역입니다.

{{< highlight python >}} def read(query: str, token_budget: int = 800) -> list[str]: """읽기 경로: 관련도 순으로 훑되, 예산이 차면 즉시 멈춘다.""" rows = DB.execute( "SELECT m.id, m.text FROM mem m " "JOIN mem_fts ON mem_fts.rowid=m.id " "WHERE mem_fts MATCH ? AND m.status='active' " "ORDER BY bm25(mem_fts), m.uses DESC LIMIT 20", (' OR '.join(query.split()),)).fetchall() picked, spent = [], 0 for mid, text in rows: cost = len(text) // 3 # 대략적 토큰 추정 if spent + cost > token_budget: # 예산 초과 → 더 안 꺼낸다 break picked.append(text); spent += cost DB.execute("UPDATE mem SET uses=uses+1 WHERE id=?", (mid,)) DB.commit() return picked def retire(days: int = 30): """배경 통합 작업: 오래 안 쓰인 후보·저사용 기억을 퇴역시킨다.""" cutoff = time.time() - days * 86400 DB.execute( "UPDATE mem SET status='retired' " "WHERE updated < ? AND uses < 2 AND status != 'retired'", (cutoff,)) DB.commit() {{< /highlight >}}

read()의 token_budget이 그림 2의 '적정 검색량'을 코드로 옮긴 것입니다. 관련도가 높아도 예산이 차면 더 꺼내지 않습니다. retire()는 cron이나 세션 종료 훅에서 주기적으로 돌리면 됩니다. 여기에 LLM을 이용한 추출·탈맥락화 단계(대화 턴을 넣고 타입 있는 JSON 레코드를 받는 프롬프트)를 앞단에 붙이면, 그림 3의 파이프라인이 완성됩니다. 완성형이 궁금하다면 LycheeMemory를 pip install "lycheemem[rerank]"로 설치해 구조를 뜯어보는 것도 좋은 공부입니다.

7. 흔한 실수 · 팁

  • 대화 원문을 통째로 저장한다. 가장 흔한 첫 실수입니다. 원문은 검색 노이즈 덩어리입니다. 추출·탈맥락화를 거친 레코드만 장기 저장소에 넣고, 원문이 정말 필요하면 별도 아카이브에 두고 링크만 남기세요.
  • 지우는 기능을 안 만든다. 쓰기·읽기만 있고 퇴역이 없는 메모리는 시간문제일 뿐 반드시 건초더미가 됩니다. 첫날부터 retire()에 해당하는 경로를 만들고, 지표(저장소 크기, 검색 정밀도)를 함께 보세요.
  • 모순 처리 정책 없이 융합한다. "최신이 이긴다"는 기본값일 뿐 만능이 아닙니다. constraint 타입처럼 안전에 관련된 기억은 자동 갱신 대신 사람 확인을 거치게 하고, 이전 값을 이력으로 보존하세요. 반사실 편집 테스트(MemoryAgentBench 방식)를 자체 평가에 한두 개 넣어 두면 회귀를 빨리 잡습니다.
  • 검색량을 늘려서 품질 문제를 풀려고 한다. top-k를 5에서 20으로 올리면 QA는 좋아질 수 있지만 에이전트 태스크는 나빠질 수 있습니다. 검색량을 늘리기 전에 저장소 정리가 먼저입니다. top-k 대신 토큰 예산으로 상한을 거는 것도 좋은 습관입니다.
  • 메모리 평가를 "잘 기억하나?"로만 한다. 4역량(정확한 검색·테스트 시점 학습·장거리 이해·충돌 해소)을 나눠 재야 어디가 병목인지 보입니다. 특히 충돌 해소는 통합 로직의 버그가 그대로 드러나는 지점입니다.
  • 남의 벤치마크 순위표로 substrate를 고른다. 만능 substrate는 없다는 게 이번 달의 결론입니다. 여러분의 태스크 믹스(QA 비중, 의사결정 비중, 히스토리 길이)로 두세 가지 구성을 직접 비교한 뒤 고르세요.

8. 마무리 (TL;DR)

  • 에이전트 메모리의 병목은 저장이 아니라 정리(consolidation)입니다. 통합 없는 저장소는 중복·모순·희석이 쌓여 건초더미가 됩니다.
  • Harness the Memory는 substrate 7종을 통제 비교해 만능 그릇은 없다는 결론을 냈습니다. 특히 과도한 검색은 순차적 의사결정 성능을 오히려 떨어뜨립니다.
  • 통합은 추출 → 탈맥락화 → 융합 → 승격/퇴역의 라이프사이클입니다. LycheeMemory는 이 파이프라인으로 토큰 약 71%, 비용 약 55%를 줄이며 정확도를 올렸다고 보고합니다.
  • RoMeRL의 메모리-보상 함정은 기억이 무한정 자라면 각 기억이 받는 피드백이 희석돼 학습이 망가진다는 것을 보여 줍니다. 유지 메모리를 84.4% 줄이고도 성능이 올랐습니다.
  • 실전 원칙 세 가지: 타입 붙여 추출하고, 저장 전에 융합하고, 읽을 때는 토큰 예산으로 상한을 거세요. sqlite 하나로도 뼈대는 만들 수 있습니다.
