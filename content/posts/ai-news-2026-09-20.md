# 🔥 오늘의 핵심

# 📚 주목 논문

오늘 두 편은 모두 저장(Zhejiang)대 ZJU-REAL 계열 — 공저자(Yongliang Shen, Weiming Lu, Zhengxi Lu)가 겹치는 자매 논문이다. 하나는 "학습 없이", 하나는 "학습으로" 에이전트 지식을 갱신한다.

## EvoSkill-GUI: 학습 없이 스킬을 진화시키기 (arXiv 2609.17653, cs.LG)

- **저자**: Bofan Chen, Boxuan Zhang(공동 1저자), Fei Tang, Yongliang Shen(교신) 외 — ZJU-REAL, Zhejiang University (9/15 공개)
- **핵심 기여**: 스킬을 배포 전에 완성하는 정적 산출물이 아니라, **실행 피드백으로 배포 중에 고쳐 쓰는 "살아있는 절차 지식"**으로 재정의했다. 파인튜닝 없이 동작한다.
- **방법**: 스킬 1개를 retrieval 메타데이터·실행 플랜·백업 로컬라이제이션·실패 복구 규칙·접근성 유틸·실패 사례로 구성된 멀티 파일 패키지로 만들고, 실행자(즉석 수정) → 정보 격리된 비평자(실패 진단) → 제한된 툴 인터페이스로 해당 파일만 수정하는 reflect-revise-reuse 루프를 돌린다.
- **검증된 결과(초록 기준)**: MobileWorld **+16.2%p**, AndroidWorld **+6.0%p**, OSWorld **+10.5%p** 최대 개선 — 범용·GUI 특화 백본 모두에서.
- 🛠 **에이전트 빌더 시사점**: "스킬이 실전에서 깨지면 사람이 고친다"를 "에이전트가 고치되, 고칠 수 있는 파일을 제한한다"로 바꾼 설계. 아래 공통 팁에서 그대로 옮겨 심는 법을 다룬다.
- **한계**: GUI 벤치마크 3종에서의 검증 — 코딩 에이전트 스킬로의 일반화는 아직 미측정.
- [arXiv 링크](https://arxiv.org/abs/2609.17653) · [코드](https://github.com/ZJU-REAL/EvoSkill-GUI)

![EvoSkill-GUI 루프](/images/ai-news-2026-09-20/evoskill-loop.svg)

*스킬 패키지 구조와 reflect-revise-reuse 루프, 벤치마크 개선 폭.*

## RetireOPD: 스스로 은퇴하는 교사 모델 (arXiv 2609.20784, cs.CL)

- **저자**: Yan Yu, Zhengxi Lu, Yizhou Liu, Yongliang Shen 외 11명 (9/17 공개, 초록 메타데이터에 소속 미표기 — EvoSkill-GUI와 공저자 다수 중복)
- **핵심 기여**: 멀티턴 에이전트 RL의 희소 보상 문제를 자기 증류(self on-policy distillation)로 보완하되, 두 가지 실측 — **특권 정보를 가진 교사가 항상 믿을 만하지는 않다**, **교사의 효용은 학습 단계에 따라 달라진다** — 을 반영했다.
- **방법**: 스킬 조건부 교사를 환경 보상으로 먼저 최적화한 뒤, 학생을 RL+OPD로 공동 학습. 핵심은 Adaptive Retirement — 교사와의 격차가 더 줄지 않고 학생이 교사 성공률의 목표 비율에 도달하면 **학생이 알아서 교사를 떼어내고** 이후 RL만으로 진행한다.
- **검증된 결과(초록 기준)**: Qwen2.5 1.5B~7B에서 ALFWorld 성공률 **+14.1~18.8%**, WebShop 정확도 **+11.8~19.0%** (RL 베이스라인 대비), 모든 설정에서 자기 교사까지 추월.
- 🛠 **에이전트 빌더 시사점**: 소형 모델을 에이전트 태스크에 RL로 튜닝 중이라면, "증류 스케줄을 언제 끊을까"를 하이퍼파라미터가 아니라 격차 수렴 조건으로 정하는 아이디어는 바로 차용 가능하다.
- **한계**: ALFWorld·WebShop 2개 환경, Qwen2.5 계열에서의 검증.
- [arXiv 링크](https://arxiv.org/abs/2609.20784)

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — 백그라운드 메모리 파이프라인 해부 (Context)

- 소스: [codex-rs/memories README](https://github.com/openai/codex/blob/main/codex-rs/memories/README.md)
- 💡 Codex는 루트 세션이 시작될 때 **백그라운드에서 2단계 메모리 파이프라인**을 돌린다: Phase 1이 최근 롤아웃(대화 기록)에서 구조화된 `raw_memory`를 뽑고(시크릿 자동 마스킹 포함), Phase 2가 이를 전역 통합한다. 충분히 idle한 롤아웃만 대상이고, 서브에이전트·ephemeral 세션에서는 돌지 않는다.
- 📝 `config.toml`의 `[memories]` 섹션에서 제어할 수 있다(소스 코드로 확인):

```toml
[memories]
use_memories = true          # 읽기 경로 (기본 true, 기능 플래그 활성 시)
generate_memories = true     # 쓰기 경로 (기본 true)
disable_on_external_context = false
# extract_model / consolidation_model 로 파이프라인용 모델 지정 가능
```

- 🎯 "Codex가 왜 내 예전 세션 내용을 아는지 / 왜 모르는지" 디버깅할 때, 그리고 추출·통합에 쓰는 모델을 저렴한 것으로 바꿔 백그라운드 비용을 낮추고 싶을 때.
- ⚠️ 기능 플래그(MemoryTool)가 켜진 빌드에서만 동작하며, 내부 구조라 필드명은 버전에 따라 바뀔 수 있다.
- ⭐ 프롬프트 템플릿(`read_path.md`, `consolidation.md`)이 저장소에 평문으로 있다 — 자작 에이전트에 메모리 파이프라인을 넣을 때 그대로 벤치마킹할 것.

## 🟦 Claude Code — /new-sdk-app으로 Agent SDK 스캐폴딩 (Workflow)

- 소스: [agent-sdk-dev 플러그인 README](https://github.com/anthropics/claude-code/blob/main/plugins/agent-sdk-dev/README.md)
- 💡 공식 플러그인 `agent-sdk-dev`의 `/new-sdk-app`은 Claude Agent SDK 프로젝트를 대화형으로 스캐폴딩하고, 생성 직후 **검증 전용 서브에이전트**(`agent-sdk-verifier-py`/TS)가 공식 문서 패턴과 대조해 셋업을 점검한다.
- 📝 시작은 한 줄:

```bash
/new-sdk-app customer-support-agent
# 언어(TS/Python) → 에이전트 유형 → 시작점 → 패키지 매니저 순으로 질문
# 최신 SDK 설치 + .env.example/.gitignore 생성 + 타입 체크까지 자동
```

- 🎯 Agent SDK 프로젝트를 처음 만들 때, 또는 팀원 온보딩용 표준 시작점이 필요할 때.
- ⚠️ 대화형 질문이 여러 번 끼어든다 — CI에서 무인으로 돌릴 용도는 아니다.
- ⭐ "생성 → 검증 서브에이전트로 즉시 점검" 패턴은 스캐폴딩 자동화 전반에 옮겨 쓸 만하다.

## 🟪 공통 — 통짜 SKILL.md를 멀티 파일 패키지로 (Context)

- 소스: [arXiv 2609.17653](https://arxiv.org/abs/2609.17653)
- 💡 EvoSkill-GUI의 핵심 실측: 스킬 하나에 플래닝·로컬라이제이션·복구 지식을 통짜 문서로 넣으면 **실패를 정밀하게 고칠 수 없다**. 파일로 쪼개면 에이전트가 깨진 부분만 수정할 수 있다.
- 📝 Claude Code·Codex 스킬에 바로 적용하는 체크리스트:
  1. SKILL.md에는 트리거 조건과 개요만 남기고, 절차는 `plan.md`, 복구 규칙은 `recovery.md`로 분리.
  2. `failures.md`를 만들어 실패 사례를 누적 — 다음 실행 때 컨텍스트로 주입.
  3. 스킬을 고치는 에이전트에게는 **해당 스킬 디렉터리 쓰기 권한만** 준다(정보 격리된 비평자 역할).
  4. 수정 전후 성공률을 기록해 "진화가 실제로 개선인지" 확인.
- 🎯 같은 스킬이 같은 이유로 반복해서 깨지는데, 매번 사람이 프롬프트를 고치고 있을 때.
- ⚠️ 자동 수정 루프는 스킬 오염 위험이 있다 — 3번의 권한 제한과 4번의 측정 없이 켜지 말 것.
- ⭐ 스킬 파일 수를 늘리는 게 아니라 **수정 단위를 좁히는 것**이 목적이라는 걸 잊지 말자.
