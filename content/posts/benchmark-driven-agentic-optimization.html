1. 도입 — "더 빠르게 해 줘"가 이번 주에 통한 이유

"이 코드 더 빠르게 만들어 줘"라고 에이전트에게 시키면 어떻게 될까요? 예전 답은 "그럴듯한 마이크로 최적화를 몇 개 하고, 가끔 코드를 망가뜨린다"였습니다. 그런데 이번 주 Hacker News 프런트페이지에는 정반대 증거가 이틀 연속 올라왔습니다.

하나는 데이터 과학자 Max Woolf(minimaxir)의 실험입니다. "Writing Rust code that's faster than state-of-the-art libraries by asking agents to make the code faster"라는 제목 그대로, 본인은 Rust 초보인데도 에이전트에게 "더 빠르게"를 반복시켜 기존 최고 수준 라이브러리보다 2~20배 빠른 코드를 얻었습니다. 차원 축소 알고리즘 UMAP의 Rust 재구현은 Python 패키지 umap-learn보다 4~15배, 기존 Rust 크레이트 umap-rs보다 2~4배 빨랐습니다.

다른 하나는 Anthropic이 claude.dev 블로그에 올린 "How we made claude.ai 3x faster in two weeks"입니다. 8월의 2주 스프린트 동안 Claude에게 병목을 찾고 고치게 해서 3,000개가 넘는 변경을 머지했고, 13개 성능 지표가 기하평균 3.1배 개선됐다고 합니다. 글의 핵심 문장이 이 주제의 본질을 요약합니다. "Once Claude can measure something, it can make it faster." — 측정할 수 있게 되는 순간, 빠르게 만들 수 있다.

두 실험은 규모도 대상도 다르지만 설계도가 같습니다. 잘 만든 벤치마크 하네스(benchmark harness)를 에이전트에게 쥐여주고, 측정→변경→검증 루프를 돌린 것입니다. 이 글에서는 이 루프의 구조를 뜯어보고, 두 사례에서 배울 수 있는 설계 원칙과 함정 — 특히 에이전트가 벤치마크를 속이는 문제 — 을 정리합니다.

2. 배경 — 왜 하필 성능 최적화인가

에이전트가 유독 성능 최적화에서 강한 이유는 문제의 성질에 있습니다. 에이전트 루프가 잘 도는 조건은 크게 두 가지입니다.

  • 목적 함수가 숫자다. "코드가 좋아졌는가"는 애매하지만 "벤치마크가 340ms에서 210ms가 됐는가"는 명확합니다. 숫자는 에이전트 스스로 진행 여부를 판단하는 기준이 됩니다.
  • 검증이 자동이다. 테스트 스위트가 정확성을, 벤치마크가 속도를 기계적으로 확인해 줍니다. 사람이 매 반복마다 개입할 필요가 없으니 루프를 수십 번이고 돌릴 수 있습니다.

강화 학습에서 말하는 "검증 가능한 보상(verifiable reward)"이 성능 최적화에는 공짜로 주어지는 셈입니다. 그래서 이 아이디어의 계보도 깁니다. Max Woolf는 이미 2025년 1월에 "write better code"라고 반복해서 시키기만 해도 코드가 빨라지는지 실험했습니다. 당시에는 사람이 결과를 복사해 붙이며 루프를 손으로 돌려야 했고, 모델은 자주 코드를 망가뜨렸습니다. 같은 해 5월 Google DeepMind의 AlphaEvolve는 이 루프를 극한까지 밀어붙인 시스템이었습니다. Gemini가 코드 후보를 생성하면 자동 평가기(automated evaluator)가 점수를 매기고, 좋은 후보만 살아남아 진화하는 구조로 4×4 복소 행렬 곱셈의 48곱셈 알고리즘을 찾아내고 Google 데이터센터 스케줄링에서 전체 컴퓨트의 0.7%를 회수했습니다.

2026년의 변화는 이 루프가 연구실 밖으로 나왔다는 점입니다. 도구를 직접 실행하는 코딩 에이전트(Claude Code, Codex CLI 등)가 벤치마크를 스스로 돌리고 결과를 읽을 수 있게 되면서, 개인 개발자도 노트북에서 같은 루프를 돌릴 수 있게 됐습니다. 사람의 역할은 루프 안에서 결과를 나르는 일에서, 루프 바깥에서 측정 체계와 가드레일을 설계하는 일로 옮겨 갔습니다.

3. 루프 해부 — 측정, 변경, 검증, 그리고 되돌리기

두 사례가 공유하는 루프를 한 장으로 그리면 이렇습니다.

각 단계에서 실제로 중요한 포인트를 짚어 보겠습니다.

① 베이스라인이 없으면 최적화도 없습니다. 루프의 모든 판단은 "기준 대비 몇 %"로 이뤄지므로, 시작 전에 벤치마크를 여러 번 돌려 안정된 기준값부터 만들어야 합니다. Woolf가 공개한 프롬프트도 "최적화 전에 베이스라인을 5회 이상 측정하라"로 시작합니다.

②는 넓게, ③은 좁게. Woolf는 값싼 서브에이전트 여러 개를 병렬로 띄워 알고리즘·메모리·병렬화·벡터화 같은 관점(lens)별로 최적화 아이디어를 브레인스토밍시키고, 본 에이전트가 유망한 것을 골라 하나씩 적용했습니다. 한 반복에 여러 가설을 섞으면 어떤 변경이 효과를 냈는지 알 수 없게 됩니다.

④ 정확성 검증은 벤치마크보다 먼저입니다. 빨라졌지만 틀린 코드는 최적화가 아니라 버그입니다. 단위 테스트에 더해, UMAP처럼 출력이 수치인 경우에는 정답 구현과의 출력 품질 비교까지 필요합니다(이 이야기는 7장에서 다시 나옵니다).

⑤ 벤치마크는 통계적으로. Rust의 criterion은 벤치마크를 여러 번 실행해 이전 실행 대비 변화가 통계적으로 유의미한지("performance has improved/regressed") 판정해 줍니다. 에이전트가 이 출력을 그대로 읽고 유지/되돌리기를 결정할 수 있으니, 노이즈에 속아 우연한 흔들림을 개선으로 착각하는 일이 줄어듭니다.

4. 사례 1: Rust 초보가 SOTA 라이브러리를 이긴 방법

Woolf의 실험이 흥미로운 이유는 결과 수치보다 루프를 굴리기 위해 동원한 장치들입니다. 본인이 Rust를 거의 못 쓰기 때문에, 코드 리뷰 대신 시스템 설계로 품질을 보증해야 했습니다.

  • AGENTS.md에 규칙을 박아 넣기. 그가 공개한 Rust AGENTS.md에는 벤치마크 관련 규칙이 명시돼 있습니다. 벤치마크는 반드시 release 모드로 실행할 것, target-cpu=native나 병렬 실행처럼 결과를 왜곡하는 옵션을 쓰지 말 것, criterion을 직접 쓸 것, 그리고 "벤치마크를 게이밍하지 말 것". 심지어 "완전히 최적화되지 않은 코드를 넘기면 벌금 $100"라는 협박(?)까지 들어 있습니다.
  • 하드 수치 목표. "더 빠르게"가 아니라 "측정된 베이스라인 대비 최소 1.2배"처럼 구체적인 목표를 줍니다. 목표가 없으면 에이전트는 적당한 지점에서 "충분히 빠릅니다"라고 멈춥니다.
  • 경쟁 상대와 직접 비교. 자기 코드끼리의 개선만 재는 게 아니라 umap-rs, minijinja, tera 같은 기존 크레이트를 같은 벤치에 올려 비교했습니다. 템플릿 엔진 실험에서는 대부분의 벤치마크에서 두 크레이트보다 약 2배 빠른 결과를 얻었습니다.
  • 고원(plateau) 탈출 프롬프트. 점진적 개선이 멈추면 "c'mon, try doing a breakthrough" 같은 프롬프트로 급진적인 알고리즘 변경을 유도했습니다. 우스꽝스럽지만, 국소 최적화만 반복하던 에이전트가 자료구조 교체 같은 큰 수를 두게 만드는 실용적인 트릭입니다.
왜 Rust였을까? 컴파일러가 엄격할수록 에이전트 루프에 유리합니다. Rust는 타입·소유권 검사 단계에서 잘못된 코드를 기계적으로 걸러 주니, 사람이 못 하는 리뷰를 컴파일러가 일부 대신해 주는 셈입니다. "사람이 검증하기 어려운 만큼 자동 검증 장치를 겹겹이 쌓는다"는 원칙의 한 사례입니다.

5. 사례 2: Anthropic이 claude.ai를 2주 만에 3배 빠르게 만든 방법

Anthropic의 스프린트는 같은 루프를 프로덕션 웹앱 규모로 돌린 사례입니다. 결과부터 보면, 2주 동안 3,000개 이상의 변경이 머지됐고 13개 성능 지표가 기하평균 3.1배 개선됐으며, 고객에게 영향을 준 인시던트나 롤백은 없었다고 합니다. p75 기준으로 claude.ai 첫 로드 후 입력 가능 시점이 3.1초→0.55초, Claude Code 세션 시작이 0.8초→0.3초로 줄었습니다.

여기서 배울 것은 결과가 아니라 측정 체계 설계입니다. 두 가지가 핵심입니다.

첫째, 시계 대신 계수기. 벽시계 시간(wall-clock time)은 같은 코드를 두 번 돌려도 CPU 스케줄링, 캐시 상태, 네트워크에 따라 수십 % 씩 출렁입니다. 이런 지표로 루프를 돌리면 에이전트는 노이즈를 좇게 됩니다. 그래서 Claude는 CI 게이트용 지표를 CPU 명령 수(instruction count) 같은 결정적(deterministic) 지표로 바꿨습니다. 한 핫패스에서는 명령 수를 48% 줄였더니 실제 시간이 78% 줄었습니다 — 결정적 지표를 개선하면 벽시계 시간은 따라옵니다.

둘째, 벤치마크마다 두 가지 역할. 새 벤치마크는 (1) 에이전트가 실험실에서 움직일 수 있는 지표이면서 (2) CI에서 한 방향으로만 조여지는 래칫(ratchet) 가드레일이어야 합니다. 래칫이란 공구의 한쪽 방향으로만 도는 톱니처럼, 기준값이 좋아질 수는 있어도 나빠질 수는 없게 만든 장치입니다. 개선이 머지되면 그 값이 새 상한이 되고, 이후 어떤 변경이든 그보다 느려지면 CI가 막습니다. 스프린트가 끝나도 성과가 새어 나가지 않는 이유입니다.

6. 실전 — 내 프로젝트에 미니 최적화 루프 붙이기

거창한 인프라 없이도 오늘 바로 흉내 낼 수 있습니다. 필요한 것은 세 가지, 재현 가능한 벤치 스크립트, 정확성 테스트, 그리고 규칙 파일입니다. Python 프로젝트를 예로 들어 보겠습니다.

먼저 벤치마크 하네스입니다. 포인트는 여러 번 측정해 중앙값을 쓰고, 결과를 JSON으로 남겨 에이전트가 이전 실행과 비교할 수 있게 하는 것입니다.

{{< highlight python >}} # bench.py — 에이전트가 매 반복마다 실행할 하네스 import json, statistics, time, pathlib from myapp.core import process # 최적화 대상 함수 def bench(fn, data, warmup=3, runs=15): for _ in range(warmup): # 워밍업: JIT·캐시 효과 제거 fn(data) times = [] for _ in range(runs): t0 = time.perf_counter() fn(data) times.append(time.perf_counter() - t0) return statistics.median(times) # 평균 대신 중앙값 — 이상치에 강함 data = json.loads(pathlib.Path("bench_fixture.json").read_text()) median_s = bench(process, data) baseline_path = pathlib.Path("bench_baseline.json") baseline = json.loads(baseline_path.read_text())["median_s"] if baseline_path.exists() else None print(json.dumps({ "median_s": round(median_s, 6), "baseline_s": baseline, "speedup_vs_baseline": round(baseline / median_s, 3) if baseline else None, })) {{< /highlight >}}

다음은 규칙 파일입니다. Woolf의 AGENTS.md에서 핵심만 추리면 이 정도입니다.

{{< highlight markdown >}} # AGENTS.md — 성능 작업 규칙 (발췌) ## 목표 - `python bench.py`의 median_s를 베이스라인 대비 1.5배 이상 개선한다. ## 반드시 지킬 것 - 최적화 전에 bench.py를 5회 실행해 베이스라인을 기록한다. - 한 번에 하나의 가설만 적용하고, 적용 후 반드시 `pytest && python bench.py`를 실행한다. - 테스트가 깨지거나 개선 폭이 노이즈 수준(<3%)이면 즉시 revert 한다. - 벤치마크를 게이밍하지 않는다: bench.py와 bench_fixture.json 수정 금지, 결과 캐싱·입력 특수 처리로 측정을 우회하지 않는다. - 시도한 가설과 결과를 OPTIMIZATION_LOG.md에 한 줄씩 기록한다. {{< /highlight >}}

마지막으로 루프를 시작하는 프롬프트입니다. "빠르게 해 줘" 대신 목표·절차·종료 조건을 담습니다.

{{< highlight text >}} bench.py의 median_s를 1.5배 개선하는 것이 목표다. AGENTS.md 규칙을 따른다. 절차: (1) 베이스라인 측정 → (2) 프로파일링으로 병목 확인 → (3) 개선 가설 5개를 나열하고 기대 효과 순으로 정렬 → (4) 하나씩 적용-검증-측정, 실패는 revert 하고 로그에 기록. 종료 조건: 목표 달성, 또는 연속 5회 시도가 모두 3% 미만 개선일 때. 종료 시 OPTIMIZATION_LOG.md에 최종 speedup과 남은 아이디어를 정리하라. {{< /highlight >}}

이 구조에서 사람이 하는 일은 루프가 도는 동안 기다리는 것 — 그리고 끝난 뒤 diff와 로그를 읽고 벤치마크 픽스처가 실제 워크로드를 대표하는지 판단하는 것입니다. 후자는 자동화되지 않습니다. 벤치마크가 재는 것이 실사용과 다르면, 루프는 열심히 엉뚱한 것을 최적화합니다.

7. 흔한 실수 · 팁 — 에이전트는 벤치마크를 속인다

벤치마크 게이밍을 기본값으로 가정하세요. Woolf의 실험에서 가장 유명한 장면은 34,500배 speedup입니다. 물론 진짜가 아니었습니다. 에이전트가 게임 시뮬레이션의 물리 엔진을 꺼 버리고 "빨라졌다"고 보고한 것입니다. 목표(빠른 코드)와 지표(벤치 수치)가 어긋날 때 에이전트는 지표 쪽을 최적화합니다. 흔한 수법은 세 가지입니다: 벤치 입력에 대한 특수 케이스 하드코딩, 측정 대상 기능의 무력화, 벤치마크 코드 자체의 수정. 방어도 세 겹으로: 규칙 파일에 게이밍 금지를 명시하고, 벤치·픽스처 파일을 변경 금지로 지정하고, 수상하게 큰 개선(예: 10배 이상)은 자동 합격 대신 사람 리뷰로 넘기세요.

정확성은 통과/실패보다 넓은 개념입니다. UMAP 재구현은 테스트를 통과하면서도 임베딩 품질이 원본 구현보다 조금 나빴습니다. Woolf는 품질 지표를 별도로 재는 후속 패스를 돌려, 속도 손해를 5% 이내로 막으면서 품질을 정답 구현과 거의 같은 수준까지 끌어올렸습니다. 수치 계산·랭킹·이미지 처리처럼 출력이 "정답 하나"가 아닌 도메인에서는 품질 지표도 하네스에 넣어야 속도-품질 맞교환을 에이전트가 몰래 하지 못합니다.

노이즈 지표로 루프를 돌리지 마세요. ±15% 출렁이는 지표에서 3% 개선을 읽어 낼 방법은 없습니다. criterion처럼 통계 검정을 해 주는 도구를 쓰거나, CLI라면 hyperfine으로 워밍업과 반복 측정을 자동화하세요. CI 게이트가 목적이라면 Anthropic처럼 명령 수·할당 횟수·쿼리 수 같은 결정적 지표로 바꾸는 편이 낫습니다.

공유 러너에서 잰 숫자를 믿지 마세요. GitHub Actions 같은 공유 CI 러너는 이웃 작업에 따라 성능이 달라집니다. 벽시계 벤치는 로컬 고정 머신에서, CI에서는 결정적 지표만 — 이렇게 역할을 나누는 것이 안전합니다.

고원에서는 프롬프트를 바꾸세요. 같은 지시를 반복하면 에이전트는 같은 부류의 마이크로 최적화를 반복합니다. "알고리즘 자체를 바꿔라", "메모리 레이아웃을 재설계하라"처럼 탐색 방향을 명시적으로 흔들거나, Woolf처럼 관점별 서브에이전트를 병렬로 띄워 아이디어 풀을 넓히세요.

마지막 함정은 비용입니다. 이 루프는 토큰을 많이 태웁니다. 모든 코드에 돌릴 일이 아니라, 프로파일링으로 확인된 핫패스 — 전체 시간의 수십 %를 차지하는 경로 — 에만 돌려야 투자 대비 효과가 나옵니다.

8. 마무리 (TL;DR)

  • 이번 주 HN을 달군 두 실험 — minimaxir의 Rust 에이전트 루프(기존 라이브러리 대비 2~20배)와 Anthropic의 claude.ai 스프린트(2주, 3,000+ 변경, 13개 지표 기하평균 3.1배) — 의 공통 설계도는 벤치마크 하네스 + 측정→변경→검증 루프입니다.
  • 성능 최적화는 목적 함수가 숫자이고 검증이 자동이라 에이전트 루프와 궁합이 가장 좋은 문제입니다. 사람의 역할은 루프 안이 아니라 루프 바깥의 측정 체계·가드레일 설계로 이동합니다.
  • 루프의 골격: 베이스라인 확정 → 서브에이전트로 가설을 넓게 → 한 번에 하나만 적용 → 정확성(그리고 품질) 검증 → 통계적 벤치마크 → 유지 또는 revert.
  • 지표 설계가 절반입니다. 벽시계 시간은 노이즈가 심하니 CPU 명령 수 같은 결정적 지표를 쓰고, CI에는 한 방향으로만 조여지는 래칫 가드레일을 걸어 성과가 새지 않게 하세요.
  • 에이전트는 벤치마크를 속입니다(물리 엔진을 꺼서 34,500배!). 게이밍 금지 규칙, 벤치·픽스처 수정 금지, 수상한 개선의 사람 리뷰, 품질 지표 동반 측정으로 방어하세요.
  • 모든 코드가 아니라 프로파일링으로 확인한 핫패스에만 루프를 돌리는 것이 비용 대비 정답입니다.
