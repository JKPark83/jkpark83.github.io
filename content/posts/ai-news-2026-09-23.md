# 📚 주목 논문

## RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

- **저자**: Peng Xia, Rujun Han 외 (Google, Tomas Pfister·Chen-Yu Lee 팀)
- **arXiv**: [2609.24972](https://arxiv.org/abs/2609.24972) (cs.LG, 9/21) · [코드](https://github.com/google-research/rrsi)
- **핵심 기여**: 프롬프트·제어 흐름·도구·메모리, 즉 하네스를 에이전트가 스스로 편집하게 하면 학습용 벤치마크에 과적합된다는 문제를 정면으로 다뤘다.
- **방법**: 제안 단계에는 시간에 따라 줄어드는 "편집 번들 예산"과 미탐색 궤적 우대를, 선택 단계에는 벤치마크 특화 변경을 걸러내는 critic과 너무 작거나 비싸거나 쓸모없어진 변경을 제거하는 pruner를 단다.
- **결과**: 코딩·워크스페이스·엔지니어링 설계 8개 벤치마크에서 진화 대상 스플릿 +14.1pt, OOD 벤치마크 5종 +4.7pt. 비정규화 진화 대비 정책 토큰 30% 절감.
- 🛠 **시사점**: 하네스를 자동이든 수동이든 반복 튜닝하고 있다면, "그 벤치에서만 좋아지는 변경"을 걸러낼 장치가 없는 한 개선 수치는 부풀려져 있을 가능성이 높다.
- **한계**: 정규화 하이퍼파라미터(예산 스케줄, 프루닝 기준) 자체가 새 튜닝 대상이 된다.

## Jev-Mem: System-One-Controlled Agentic Memory for Efficient AI Agents

- **저자**: Dongming Jiang, Yi Li, Bingzhe Li (소속은 arXiv 메타데이터에 미표기)
- **arXiv**: [2609.23986](https://arxiv.org/abs/2609.23986) (cs.AI, 9/21)
- **핵심 기여**: 에이전트 메모리의 구성·검색을 자기회귀 LLM이 아닌 값싼 "System-One" 컨트롤 플레인이 담당하게 한 구조. 지난주 다룬 TypeSafe Jev의 System-One 개념을 메모리에 이식한 셈이다.
- **방법**: 메모리 타이핑·관계 구성, 쿼리 라우팅, 검색 예산 배분, 그래프 탐색, 후보 스코어링, 적응적 중단까지 System-One이 처리하고, System-Two(LLM)는 복잡한 추론과 답변 합성에만 호출된다.
- **결과**: LoCoMo LLM-judge 종합 0.777로 최강 베이스라인 대비 상대 11% 개선, 메모리 구성 비용도 절감 보고.
- 🛠 **시사점**: 메모리 저장·검색의 크리티컬 패스에서 LLM 호출을 빼는 설계는 오늘 당장 흉내 낼 수 있다. 분류기·휴리스틱으로 충분한 결정을 LLM에게 시키고 있지 않은지 점검해 보자.
- **한계**: LoCoMo 중심 평가라 코드 에이전트류 장기 작업 메모리로의 일반화는 미검증.

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — GPT-6 Sol/Luna가 이미 소스에 들어왔다, 모델부터 고정하자

- **카테고리**: Workflow · **출처**: [openai/codex model_catalog.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/model_catalog.rs) (저장소 클론으로 확인)
- 💡 **핵심**: Codex 소스에 `gpt-6-luna` 상수, Bedrock용 `openai.gpt-6-sol` ID, 그리고 `gpt-5.4-mini` 사용자를 GPT-6 Luna로 안내하는 자동 마이그레이션 로직이 들어왔다. 0.157.0-alpha가 10번째 태그까지 연발 중이라 정식판에 실릴 가능성이 높다.
- 📝 **how-to**: 업그레이드 시 모델이 조용히 바뀌는 것을 막으려면 `config.toml`에 명시:

```toml
model = "gpt-6-sol"
model_reasoning_effort = "high"
```

- 🎯 **언제**: CI·평가 파이프라인처럼 모델이 바뀌면 수치 비교가 무의미해지는 곳 전부.
- ⚠️ **주의**: 알파 채널 기준 관찰이므로 정식 릴리즈에서 동작이 달라질 수 있다.
- ⭐ **추천도**: Codex를 자동화에 쓰는 팀이라면 오늘 바로.

## 🟦 Claude Code — MCP 설명문 2,048자 캡, 이제 조절 가능

- **카테고리**: MCP/Context · **출처**: [CHANGELOG 2.1.280](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) (클론으로 확인)
- 💡 **핵심**: Claude Code는 MCP 도구 설명과 서버 instructions를 2,048자에서 잘라 컨텍스트를 보호하는데, 2.1.280부터 `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` 환경 변수로 이 캡을 세션 단위로 바꿀 수 있다.
- 📝 **how-to**: 설명이 긴 사내 MCP 서버가 잘려서 오동작하면 캡을 올리고, 반대로 도구가 수십 개라 컨텍스트가 부족하면 캡을 내려 본다:

```bash
CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH=4096 claude
```

- 🎯 **언제**: MCP 도구가 "설명대로 안 움직인다" 싶을 때 첫 번째 점검 포인트.
- ⚠️ **주의**: 캡을 올리면 모든 MCP 서버에 적용되어 세션 컨텍스트 소비가 함께 늘어난다.
- ⭐ **추천도**: MCP 서버를 직접 만드는 개발자 필수.

## 🟪 공통 — 하네스 튜닝에는 OOD 홀드아웃을 남겨두자

- **카테고리**: Eval · **출처**: [arXiv:2609.24972](https://arxiv.org/abs/2609.24972)
- 💡 **핵심**: RRSI의 교훈은 자동 진화가 아니어도 적용된다. 하네스(프롬프트·훅·도구 설명)를 고칠 때 늘 보는 평가 세트로만 검증하면, 그 세트 전용 개선을 실력 향상으로 착각하게 된다.
- 📝 **how-to**: 평가 태스크를 "튜닝용"과 "홀드아웃"으로 나누고, 홀드아웃은 릴리즈 직전에만 돌린다. 튜닝용 점수만 오르고 홀드아웃이 제자리면 그 변경은 과적합이다. 한 번에 편집 하나씩(번들 금지), 효과가 애매한 변경은 삭제 — RRSI의 예산·프루닝 원칙 그대로다.
- 🎯 **언제**: 시스템 프롬프트를 "조금만 더" 고치는 일이 주간 루틴이 된 팀.
- ⚠️ **주의**: 홀드아웃도 자주 보면 결국 튜닝 세트가 된다. 주기적으로 교체할 것.
- ⭐ **추천도**: 에이전트 평가를 운영하는 모든 팀.
