# 🔥 오늘의 핵심

오늘의 키워드는 **속도와 기억**이다. Inception의 **Mercury 3**는 토큰을 한 개씩이 아니라 블록 단위로 병렬 정제하는 디퓨전 방식으로 1,068 tok/s(벤더 보고)를 찍었고, MemTensor의 **MemT-1.0**은 외부 RAG가 아니라 **모델 연산 안에 메모리를 내장**한 오픈 웨이트를 공개했다. 에이전트의 보조 루프에 초고속 모델을 끼워 넣을지, 기억을 도구 계층에서 모델 계층으로 내릴지 — 둘 다 오늘 바로 만져볼 수 있는 실물이 나왔다.

# 🤖 모델 & 릴리즈 레이더

- **Inception Mercury 3** (10/19) — 상용 디퓨전 LLM(dLLM) 4번째 릴리즈. 벤더 보고로 NVIDIA GPU에서 **1,068 tok/s**, 컨텍스트 260K → **1M**, Mercury 1 대비 40배 이상 파라미터. 자체 벤치마크에선 GPT-6 Luna·Claude Haiku 5.5를 12개 중 8개 테스트에서 앞선다고 주장(벤더 수치). 가격은 입력/출력 $0.20/$0.70 per 1M tok, 런칭 기간 50% 할인. OpenAI 호환 API로 Inception 플랫폼·OpenRouter·Baseten·Vercel에서 제공, **오픈 웨이트는 없음**. [공식 발표](https://www.inceptionlabs.ai/blog/introducing-mercury-3) · [MarkTechPost](https://www.marktechpost.com/2026/10/19/inception-mercury-3-diffusion-llm/)
- **MemT-1.0-Nano / Flash 오픈 웨이트** (MemTensor, 10/15·10/17, MIT) — 아래 논문 섹션의 그 모델. Nano는 Qwen3.6-35B-A3B, Flash는 DeepSeek-V4-Flash 백본 위에 메모리 블록을 얹었다. HF에서 바로 받을 수 있다. [HF 컬렉션](https://huggingface.co/MemTensor/MemT-1.0-Flash)

![Mercury 3 스펙 카드 — 속도 1068 tok/s, 컨텍스트 1M, 가격, Bito 독립 테스트에서 Claude Opus 5.5와의 점수 비교](/images/ai-news-2026-10-21/mercury3-card.svg)

*Mercury 3 숫자 요약. 속도·가격 수치는 벤더 보고, 하단 막대는 [Bito의 독립 장시간 코딩 테스트](https://bito.ai/blog/inception-mercury-3-diffusion-model-coding-benchmark/) 결과.*

독립 검증이 벌써 나온 점이 흥미롭다. Bito의 장시간 멀티턴 코딩 테스트에서 Mercury 3는 세션을 5.8분 만에 끝내 **가장 빨랐지만** 점수는 65%로 Claude Opus 5.5(87%)에 크게 못 미쳤다. 결론은 명확하다: 메인 코딩 루프 대체재가 아니라, **초안 생성·분류·대량 서브태스크** 같은 속도 민감 구간용.

# 📚 주목 논문

## MemT-1.0: Towards Memory-Native Evolution

- **저자**: MemTensor 연구진 (74명)
- **arXiv**: [2610.26825](https://arxiv.org/abs/2610.26825) (cs.CL, 10/19) · HF 데일리 109 업보트
- **핵심 기여**: 메모리를 외부 저장소가 아니라 **모델 연산의 일부로 내장**한 "메모리 파운데이션 모델" 패밀리를 공개했다.
- **방법**: 백본 어텐션 옆에 Native Memory Block을 나란히 두고, Gated DeltaNet-2로 턴 안에서 토큰 단위 메모리를 갱신한다. Mixture-of-Storage로 메모리 용량을 확장하고, 34B 토큰으로 2단계(계속 사전학습 → 사후학습) 훈련.
- **결과**: 파라메트릭 메모리 베이스라인 평균을 상회, RAG 계열과는 경쟁 수준. 128K 히스토리 기준 Nano가 풀 컨텍스트 KV 캐시 대비 **추론 1.86배 가속, 영구 저장 공간 66배 절감**.
- 🛠 **Agent Builder 시사점**: 지금은 세션 간 기억을 전부 프롬프트/도구 계층에서 관리하지만, 이 방향이 성숙하면 "히스토리 재주입" 비용 자체가 사라진다. 절차적 경험(procedural experience)을 내재화해 에이전틱 과제 성공률이 올라간다는 결과도 주목.
- **한계**: RAG를 이기는 게 아니라 "경쟁 수준"이고, custom architecture라 전용 추론 코드가 필요하다.

## Self-Evolving Coding Agents via Harness-Policy Optimization

- **저자**: Zhepei Wei, Jianfeng Gao 등 8명 (Microsoft Research 소속 저자 포함)
- **arXiv**: [2610.22791](https://arxiv.org/abs/2610.22791) (cs.CL, 10/16)
- **핵심 기여**: 코딩 에이전트의 성능은 정책(모델)과 하네스가 함께 결정하는데, 한쪽만 고치면 서로 어긋난다. **둘을 번갈아 최적화**하는 Self-HPO를 제안.
- **방법**: H-step에서 현재 정책이 자기 실패를 분석해 하네스 후보를 제안하고, P-step에서 선택된 하네스 아래 RL로 정책을 갱신한다. 훈련 중 발견된 난제가 다음 하네스 탐색 셋이 된다.
- **결과**: 코딩 벤치마크 3종에서 Qwen3.5-35B-A3B 평균 해결률 **57.8% → 64.8%**. 최적화된 하네스·정책은 각각 단독으로도 이득을 유지하고, 합동 이득이 개별 합을 넘는다. 더 강한 외부 모델(Opus 4.8)을 제안자로 쓰면 추가 상승.
- 🛠 **Agent Builder 시사점**: 하네스(시스템 프롬프트, 도구 설계, 스캐폴드)를 고정 상수가 아니라 **최적화 변수**로 다루라는 정량 근거. 아래 공통 팁 참고.
- **한계**: 코딩 도메인 한정 검증이고, P-step은 RL 인프라가 필요하다.

![Self-HPO의 H-step과 P-step 순환 구조와 결과 요약 다이어그램](/images/ai-news-2026-10-21/self-hpo-loop.svg)

*Self-HPO 루프. 실패 분석 → 하네스 제안 → RL 갱신 → 난제 적재가 한 라운드다.*

# 🛠 오픈소스 스포트라이트

- **[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory)** (Rust, MIT, v3.1.2 10/20) — 코딩 에이전트용 **교차 하네스 장기 기억**. Claude Code로 작업하다 중단하고 같은 디렉터리에서 Codex를 열면, 아키텍처·실패한 접근·열린 질문이 담긴 핸드오프를 이어받는다. Claude Code, Codex, Cursor, Gemini CLI 등 20개 이상 하네스가 하나의 기억을 공유하고, 핸드오프는 소유자가 있는 타입드 프로토콜이다. 멀티 툴을 오가며 작업하는 개발자라면 오늘 설치해볼 가치가 있다.
- **[yetone/magpie](https://github.com/yetone/magpie)** (Go, MIT, 10/21에도 활발 커밋) — 모든 코딩 CLI를 임의의 모델/계정에 연결하는 **로컬 게이트웨이**. Claude Code를 Kimi로, Codex를 DeepSeek으로, Gemini CLI를 GLM으로 돌리고, 쿼터가 소진되면 다음 계정으로 자동 전환한다. macOS/Windows/Linux/Docker/Termux 지원. Mercury 3 같은 신모델을 기존 CLI 워크플로에 끼워 시험할 때 유용하다.

두 저장소 모두 클론으로 실존·활동을 확인했고, 스타 수는 API 권한 제약으로 미확인. 같은 "기억" 문제를 ai-memory는 **도구 계층**에서, MemT-1.0은 **모델 계층**에서 푼다는 대비가 오늘의 관전 포인트다.

- ⚠️ 체인지로그가 명시하듯 중첩 네임스페이스는 **샌드박스의 파일 보호를 우회할 수 있다**. 신뢰하는 워크플로에만 켤 것. 덤: 같은 버전에서 Vertex/Bedrock의 전 요청 실패(2.1.304 회귀)도 고쳐졌으니 게이트웨이 사용자는 업데이트 권장.
- ⭐ 필요한 프로젝트에만 좁게 적용.

**🟪 공통 / Harness** — [Self-HPO, arXiv 2610.22791](https://arxiv.org/abs/2610.22791)

- 💡 RL 없이도 Self-HPO의 H-step은 수동으로 흉내 낼 수 있다: 하네스를 "모델이 제안하고 평가로 채택하는" 대상으로 다루는 것.
- 📝 실패한 세션 트래젝터리를 모아 가장 강한 모델에게 "이 실패들을 줄일 시스템 프롬프트/도구 설명 수정안 3개"를 제안시키고, 홀드아웃 과제 셋에서 통과율이 오를 때만 채택한다.
- 🎯 에이전트 성공률이 정체됐는데 모델 교체는 선택지가 아닐 때.
- ⚠️ 제안을 만든 바로 그 과제들로 평가하면 과적합된다 — 채택 판정은 반드시 새 과제로.
- ⭐ 논문 수치(+7.0%p)는 RL 포함 결과지만, 하네스 최적화 단독으로도 이득이 유지됐다는 분석이 근거다.
