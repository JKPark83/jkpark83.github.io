에이전트에 툴을 붙일 때 우리는 거의 반사적으로 같은 안전장치를 답니다. “위험한 일을 하기 전에 사람에게 물어보자.” 그리고 한 시간쯤 지나면, 그 사람은 창이 뜨는 위치를 외워서 그냥 클릭하고 있습니다.

1. 왜 지금 '승인'이 화제인가

2026년 8월 14일, Anthropic이 코딩 에이전트 Claude Code의 기본 동작을 바꿨습니다. 그동안은 파일을 고치거나 명령을 실행할 때마다 사용자에게 “허용할까요?”를 묻는 방식이 기본이었는데, 이제 Pro·Max·Team 플랜에서는 auto mode가 기본값입니다. 사람 대신 별도의 분류기(classifier) 모델이 툴 호출 하나하나를 실행 직전에 검사하고, 위험해 보이는 것만 막습니다.

업계가 술렁인 건 “기능이 하나 바뀌었다” 때문이 아닙니다. 그 변경을 뒷받침하려고 공개된 숫자들이 우리가 지난 2년간 당연하게 달아 온 안전장치를 정면으로 반박했기 때문입니다. 핵심만 추리면 이렇습니다.

  • 사용자는 Claude Code 권한 요청의 97%를 승인했습니다. 거부는 3%뿐이었습니다.
  • 반면 에이전트가 제안한 계획(plan)은 39%나 거부했습니다. 같은 사람이 계획은 따져 보고, 개별 명령은 그냥 통과시킨 겁니다.
  • 유료 전문 테스터 1,053명을 대상으로 한 통제 실험에서, 작업 흐름에 몰래 섞어 넣은 위험 명령을 사람은 13.6%(143건)만 잡아냈습니다. 같은 명령을 auto mode의 분류기는 89%(937건) 막았습니다.
  • 정면 대결로 보면 더 극적입니다. 사람이 승인했지만 분류기가 막은 명령이 800건, 그 반대는 6건이었습니다.

여기서 오해하면 안 되는 게 있습니다. 이 글은 “Claude Code 설정을 이렇게 바꾸세요”라는 안내가 아닙니다. 우리가 볼 건 그 아래 깔린 설계 문제입니다 — 에이전트를 직접 만드는 사람 입장에서, 사람에게 무엇을 묻고 무엇을 묻지 말아야 하는가. 이 질문에 답하는 계층을 흔히 승인 계층(approval layer) 혹은 권한 계층이라고 부릅니다.

한 줄 요약. “매번 묻기”는 안전해 보이지만, 사람의 주의력이 반복 앞에서 무너지기 때문에 실제로는 거의 아무것도 막지 못합니다. 답은 덜 묻는 것도, 더 묻는 것도 아니라 묻는 대상을 바꾸는 것입니다.

2. 배경 — 승인 프롬프트는 원래 무엇을 하려던 장치인가

먼저 용어를 정리합니다. 에이전트가 셸을 치고 파일을 지우고 API를 부르는 구조에서, 툴 호출을 실행 직전에 가로채 “실행할지 말지”를 정하는 지점을 권한 게이트(permission gate)라고 합니다. 여기서 사람에게 판단을 넘기는 방식이 human-in-the-loop(사람을 루프 안에 두기, 줄여서 HITL)입니다.

이 설계는 두 가지를 기대하고 만들어졌습니다.

  • 판단의 이양. 모델은 사용자의 진짜 의도나 조직의 규칙을 다 모릅니다. 그러니 애매한 순간엔 사람이 결정하게 하자.
  • 책임의 소재. 사고가 나도 “사람이 승인했다”는 기록이 남습니다. 감사(audit) 관점에서 편합니다.

둘 다 합리적입니다. 문제는 빈도입니다. 코딩 에이전트 한 세션은 툴 호출을 수십에서 수백 번 합니다. 파일 읽기, grep, 테스트 실행, 파일 쓰기, git diff… 이 중 압도적 다수는 지루할 만큼 안전합니다. 그런데 게이트는 그 지루한 호출들 사이에 위험한 것 하나를 섞어 넣고 사람에게 매번 같은 모양의 창을 보여 줍니다.

인간 요소(human factors) 연구에서는 이 상황의 결말이 오래전에 정리돼 있습니다. Parasuraman과 Manzey가 2010년에 정리한 자동화 안주(automation complacency)와 자동화 편향(automation bias)이 그것입니다. 요지는 이렇습니다 — 자동 시스템이 대체로 잘 맞으면 사람은 감시에 쓰던 주의를 다른 일로 재배분합니다. 이건 게으름이나 훈련 부족이 아니라 주의 자원이 유한한 데서 오는 구조적 결과여서, 초보든 전문가든 똑같이 나타나고 “주의하세요”라는 교육으로 없어지지 않습니다.

비유로. 자동차 경보음이 온 동네에 하루 열 번 울리면, 어느 순간 아무도 창밖을 보지 않습니다. 경보가 고장 난 게 아니라 경보의 정보량이 0에 수렴한 겁니다. 승인 프롬프트도 똑같습니다. 100번 중 99번이 “안전한데 그냥 묻는 것”이면, 101번째의 진짜 경고는 앞선 100번에 묻혀 버립니다.

3. 데이터가 말하는 것 — 승인 피로는 취향이 아니라 구조

이론은 그렇다 치고, 실제 숫자는 어떨까요. 앞서 소개한 실험 결과를 조금 더 뜯어보면 승인 피로(approval fatigue)의 모양이 뚜렷하게 보입니다.

여기서 가장 중요한 한 줄은 “계획은 39% 거부, 개별 명령은 3% 거부”입니다. 같은 사람의 주의력이 어디로 갔는지 정확히 보여 주기 때문입니다. 사람은 맥락이 있고, 한 번뿐이고, 결정처럼 느껴지는 질문에는 답을 합니다. 반대로 맥락 없고, 반복되고, 진행을 가로막는 질문에는 반사적으로 “예”를 누릅니다.

그러니 설계 원칙이 하나 나옵니다.

원칙 1. 사람에게 묻는 횟수는 예산(budget)입니다. 한 세션에 사람이 진지하게 판단할 수 있는 횟수는 많아야 손에 꼽습니다. 그 예산을 ls나 테스트 실행에 써 버리면, 정작 프로덕션 DB 마이그레이션 차례에는 남는 게 없습니다.

4. 대안은 '덜 묻기'가 아니라 '세 겹으로 나누기'

“그럼 그냥 다 자동으로 돌리면 되나요?”라고 물으면 답은 당연히 아니오입니다. 실제로 auto mode의 분류기도 실험에서 11%는 놓쳤습니다. 자동 판정 하나에 전부를 맡기는 건 사람 하나에 전부를 맡기는 것만큼이나 순진한 설계입니다.

제대로 된 답은 역할을 세 겹으로 쪼개는 겁니다. 각 층이 다른 방식으로 실패하기 때문에, 겹쳐 놓으면 서로의 구멍을 메웁니다.

층별로 무엇을 맡는지 한 문장씩 정리합니다.

층하는 일강점실패하는 방식
① 컨테인먼트 샌드박스·파일시스템 경계·네트워크 허용 목록·최소 권한 토큰으로 애초에 할 수 있는 일을 줄임 모델이 무엇을 하든 경계 밖으로 못 나감. 판단이 필요 없음 경계 안에서 벌어지는 사고는 못 막음(예: 저장소 안 파일 날리기)
② 결정론적 규칙 deny/allow 목록으로 확실한 것을 즉시 판정 빠르고, 로그가 명확하고, 테스트가 됨 문자열 매칭은 우회에 약함. 예상 못 한 조합엔 무력
③ 분류기 판정 남은 애매한 호출을 문맥과 함께 판단(부작용·되돌림 가능성·인젝션 흔적) 지치지 않고, 세션 길이와 무관하게 일정 확률적. 오탐으로 진행을 막고, 미탐으로 통과시킴
④ 사람 게이트 되돌릴 수 없는 행동, 조직 정책·의도 판단이 필요한 결정 맥락과 책임을 가진 유일한 층 반복되면 무너짐(승인 피로). 그래서 드물어야 함

Claude Code의 auto mode도 딱 이 모양입니다. 분류기가 배포·마이그레이션·권한 부여·대량 삭제·force push 같은 행동을 잡아내고, 막힌 호출은 모델에게 돌려보내 다른 방법을 찾게 하거나 사람에게 물어봅니다. 그리고 차단이 연속 3회 또는 세션 누적 20회에 이르면 아예 수동 승인 모드로 되돌립니다. 자동 판정이 이상해졌을 때를 대비한 회로 차단기인 셈이죠.

왜 이게 프롬프트 인젝션에도 먹히나요? 분류기는 “이 툴 호출이 사용자가 시킨 일과 이어지는가”를 함께 봅니다. 에이전트가 방금 읽은 웹페이지나 이슈 코멘트에 숨은 지시를 따라 갑자기 크레덴셜을 외부로 보내려 하면, 그 호출은 문맥과 어긋나 보입니다. 실제로 Trajectory Labs가 수행한 독립 평가에서 간접 프롬프트 인젝션 시나리오 72종을 각 10회씩, 총 720회 시도했지만 auto mode는 모두 막았다고 보고됐습니다. 물론 “현재 알려진 시나리오에서”라는 단서가 붙습니다.

5. 무엇을 물을지 고르는 기준 — 되돌림 등급 × 영향 범위

이제 실제 설계로 내려갑니다. 툴 호출 하나를 앞에 두고 “이건 물어야 하나?”를 판단하는 기준이 필요합니다. 가장 쓸 만한 축은 두 개입니다.

  1. 되돌림 등급(reversibility) — 잘못됐을 때 되돌릴 수 있나, 얼마나 싸게?
  2. 영향 범위(blast radius) — 잘못되면 어디까지 번지나? 내 작업 디렉터리? 팀 저장소? 프로덕션? 고객?

이 그림에서 얻을 규칙은 짧습니다.

원칙 2. 되돌릴 수 있으면 확인 창 대신 되돌리기를 주세요. 확인 창은 사용자의 주의를 미리 당겨 쓰는 비용이고, 되돌리기는 사고가 났을 때만 지불하는 비용입니다. 사고 확률이 낮을수록 후자가 압도적으로 쌉니다.

“되돌릴 수 있다”를 판단할 때는 등급을 나눠 두면 편합니다. 실무에서는 대략 세 단계로 갈립니다.

  • 싸게 되돌릴 수 있음 — 작업 트리의 파일 변경. git 체크포인트나 세션 스냅샷으로 원복됩니다.
  • 비싸게 되돌릴 수 있음 — DB 쓰기. 트랜잭션 롤백이나 보상 트랜잭션(compensating transaction)이 필요하고, 그사이 다른 사람이 읽어 갔을 수도 있습니다.
  • 되돌릴 수 없음 — 이미 나간 메일, 결제, 외부 API 호출, 공개 저장소로의 force push. 사과는 되지만 취소는 안 됩니다.
함정. “DB는 롤백되니까 되돌릴 수 있음”이라고 단순히 분류하면 안 됩니다. 부작용은 롤백되지 않습니다. 트랜잭션 안에서 웹훅을 쐈다면 롤백해도 웹훅은 이미 나갔습니다. 되돌림 등급은 “가장 되돌리기 어려운 부작용” 기준으로 매기세요.

6. 실전 — 내 에이전트에 승인 계층 붙이기

이제 코드로 내려갑니다. 프레임워크가 무엇이든, 툴 호출을 실행하기 직전에 끼어드는 함수 하나가 승인 계층의 전부입니다. 먼저 판정 타입과 되돌림 등급을 정의합니다.

{{< highlight python >}} from dataclasses import dataclass from enum import IntEnum class Reversibility(IntEnum): READ_ONLY = 0 # 아무것도 바꾸지 않음 CHEAP_UNDO = 1 # 체크포인트로 원복 가능 (작업 트리 파일 등) COSTLY_UNDO = 2 # 보상 트랜잭션이 필요 (DB 쓰기 등) IRREVERSIBLE = 3 # 되돌릴 수 없음 (메일·결제·배포·force push) class Scope(IntEnum): LOCAL = 0 # 내 작업 공간 SHARED = 1 # 팀 저장소·스테이징 PROD = 2 # 프로덕션·고객에게 보이는 것 @dataclass class ToolCall: name: str args: dict # 신뢰할 수 없는 콘텐츠(웹페이지·이슈 코멘트·메일)를 읽은 뒤인가? # 인젝션 위험 구간을 표시해 두면 판정을 더 보수적으로 할 수 있습니다. tainted: bool = False {{< /highlight >}}

다음은 판정 함수입니다. 핵심은 순서입니다 — 값싼 규칙을 먼저 태우고, 분류기는 남은 것에만 부릅니다. 규칙이 확실히 아는 걸 굳이 모델에게 물으면 돈과 지연만 늘어납니다.

{{< highlight python >}} DENY = {"aws iam", "kubectl delete ns", "git push --force"} # 절대 금지 AUTO = {"read_file", "grep", "run_tests", "list_dir"} # 항상 허용 def decide(call: ToolCall, rev: Reversibility, scope: Scope) -> str: """ALLOW | ASK | DENY 중 하나를 돌려줍니다.""" # ① 결정론적 규칙 — 가장 싸고 가장 예측 가능 if any(p in call.args.get("command", "") for p in DENY): return "DENY" if call.name in AUTO and not call.tainted: return "ALLOW" # ② 되돌릴 수 없는 일은 규칙만으로 통과시키지 않습니다 if rev == Reversibility.IRREVERSIBLE: return "ASK" if rev == Reversibility.COSTLY_UNDO and scope >= Scope.SHARED: return "ASK" # ③ 남은 애매한 구간만 분류기에게 — 특히 인젝션 위험 구간 if call.tainted or scope >= Scope.SHARED: verdict = classify(call) # 별도 모델 호출 return "ASK" if verdict.risky else "ALLOW" # ④ 로컬에서 싸게 되돌릴 수 있는 일은 그냥 실행하고 되돌리기를 남깁니다 checkpoint() # 예: git stash create / 세션 스냅샷 return "ALLOW" {{< /highlight >}}

이 골격에서 눈여겨볼 점이 셋 있습니다.

  • tainted 플래그. 에이전트가 신뢰할 수 없는 콘텐츠를 읽은 뒤라면 같은 툴 호출도 더 의심해야 합니다. 프롬프트 인젝션은 “읽은 것”이 “하는 것”으로 번지는 경로를 타니까요.
  • checkpoint()가 ALLOW보다 먼저. 되돌리기를 약속하려면 되돌릴 지점이 실제로 있어야 합니다. 순서를 바꾸면 “되돌리기 버튼이 있는데 되돌릴 게 없는” 상태가 됩니다.
  • 분류기는 마지막. 확률적 판정은 비싸고 느립니다. 전체 호출의 5~10%만 여기까지 오도록 앞단을 설계하세요.

그리고 회로 차단기를 답니다. 자동 판정이 이상해졌을 때 조용히 계속 굴러가는 게 최악입니다.

{{< highlight python >}} class Circuit: def __init__(self, streak_limit=3, session_limit=20): self.streak = 0 self.total = 0 self.streak_limit, self.session_limit = streak_limit, session_limit def record(self, verdict: str) -> bool: """True를 돌려주면 '전면 수동 승인으로 전환'하라는 뜻입니다.""" if verdict == "DENY": self.streak += 1 self.total += 1 else: self.streak = 0 # 통과하면 연속 카운트는 초기화 return self.streak >= self.streak_limit or self.total >= self.session_limit {{< /highlight >}}

차단이 연속으로 쌓인다는 건 보통 둘 중 하나입니다. 에이전트가 잘못된 경로에 갇혔거나, 누군가 밀어붙이고 있거나. 어느 쪽이든 사람이 볼 때입니다. Claude Code가 연속 3회·누적 20회를 임계값으로 쓰는 이유도 같습니다.

마지막으로 컨테인먼트입니다. 코드로 짜는 게 아니라 설정으로 정하는 층인데, 사실 가장 효과가 큽니다. Claude Code를 쓴다면 저장소의 .claude/settings.json에 규칙을 박아 둘 수 있습니다.

{{< highlight json >}} { "permissions": { "allow": [ "Bash(npm run test:*)", "Bash(git status)", "Read(./src/**)" ], "ask": [ "Bash(git push:*)" ], "deny": [ "Bash(rm -rf /*)", "Read(./.env)", "Read(./secrets/**)" ] } } {{< /highlight >}}

deny는 auto mode에서도 그대로 유효합니다. 자동 판정을 켜더라도 “이건 절대 안 된다”는 조직의 결정은 규칙으로 남겨 두세요. 확률적 판정보다 결정론적 금지가 언제나 우선입니다. 네트워크 경계도 마찬가지입니다 — 허용 목록에 없는 호스트로 나가려는 명령은 자동 통과되지 않고 원래의 승인 흐름으로 되돌아옵니다.

직접 해 보기. 지금 굴리는 에이전트의 로그에서 최근 100건의 툴 호출을 뽑아 되돌림 등급으로 분류해 보세요. 대개 80% 이상이 READ_ONLY나 CHEAP_UNDO입니다. 그 80%에 승인 창을 띄우고 있었다면, 사람의 주의력 예산을 거기에 다 태우고 있었다는 뜻입니다.

7. 흔한 실수 · 팁

실수 1 — 분류기를 새로운 만능 안전장치로 믿는다. auto mode도 실험에서 11%는 놓쳤습니다. 확률적 판정은 “사람보다 낫다”이지 “안전하다”가 아닙니다. 그래서 컨테인먼트가 먼저입니다 — 분류기가 뚫려도 샌드박스 밖으로는 못 나가게 해 두세요.

실수 2 — 되돌릴 수 있는 일에 확인 창을 띄운다. 파일 하나 고치는 데 매번 묻는 설정이 대표적입니다. 사용자를 훈련시켜 “예”를 누르는 손가락만 만들고, 정작 배포 승인 차례엔 같은 손가락이 그대로 움직입니다.

실수 3 — 되돌리기를 약속하고 체크포인트를 안 남긴다. “언제든 되돌릴 수 있어요”라고 UI에 적어 놓고, 정작 에이전트가 파일 40개를 고친 뒤에는 원복 지점이 없는 경우입니다. 자동 실행을 늘릴 거라면 체크포인트가 먼저 늘어야 합니다.

실수 4 — 개별 명령만 묻고 계획은 안 묻는다. 데이터가 정확히 반대를 가리킵니다. 사람은 계획은 39% 거부하고 개별 명령은 3%만 거부했습니다. 사람의 판단력이 살아 있는 지점은 계획 단위입니다. 승인을 받을 거면 “이 20단계를 이렇게 진행하겠습니다”를 한 번 보여 주고 받으세요.

실수 5 — 감사 로그를 안 남긴다. 사람이 덜 개입할수록 “무슨 일이 있었는지”를 나중에 재구성할 수 있어야 합니다. 판정 결과(ALLOW/ASK/DENY), 근거, 분류기 버전, 실행 결과를 남기세요. 자동화의 대가는 관측 가능성입니다.

팁 — 승인 요청에 '무엇이 되돌릴 수 없는지'를 적으세요. “이 명령을 실행할까요?”보다 “이 명령은 프로덕션 DB의 컬럼을 삭제하며 되돌릴 수 없습니다”가 훨씬 낫습니다. 사람은 맥락이 있을 때만 진짜로 판단합니다.

8. 마무리 (TL;DR)

  • 매번 묻는 승인은 안전장치처럼 보이지만 무너집니다. Claude Code 사용자는 권한 요청의 97%를 승인했고, 몰래 섞은 위험 명령을 13.6%만 잡았습니다. 같은 명령을 자동 분류기는 89% 막았습니다.
  • 이건 개인의 부주의가 아니라 자동화 안주라는 구조적 현상입니다. 세션이 길어질수록 사람의 차단율은 17% → 5%로 떨어졌고, 분류기는 평평했습니다.
  • 그렇다고 자동 판정만 믿는 것도 순진합니다(같은 실험에서 11% 미탐). 답은 컨테인먼트 → 결정론적 규칙 → 분류기 → 사람 게이트의 네 겹으로 나누는 설계입니다.
  • 무엇을 물을지는 되돌림 등급 × 영향 범위로 고르세요. 되돌릴 수 있으면 확인 창 대신 되돌리기를, 되돌릴 수 없을 때만 사람을.
  • 사람에게 묻는 횟수는 예산입니다. ls에 쓰지 말고 배포·마이그레이션·권한 부여에 쓰세요. 그리고 물을 거면 개별 명령이 아니라 계획 단위로 묻는 편이 실제로 검토됩니다.
  • 자동화를 늘릴 때 함께 늘려야 하는 것: 체크포인트, 회로 차단기(연속 차단 시 수동 전환), 감사 로그.
