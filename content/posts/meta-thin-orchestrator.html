1. 도입 — '모든 걸 아는 에이전트'가 거짓말을 시작했다

10월 19일, Meta 엔지니어링 블로그에 The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do라는 글이 올라왔습니다. 제목을 직역하면 "라우터에게 일을 덜 시켰더니 에이전트가 더 믿을 만해졌다"입니다. 하루 만에 PPC Land, DEV Community, daily.dev 등 여러 매체가 받아썼고, "Meta가 환각 때문에 에이전트 하나를 14명의 전문가로 쪼갰다"라는 자극적인 제목으로 돌았습니다.

이야기의 출발점은 단순합니다. Meta는 추천 시스템에 새 데이터 컬럼을 온보딩하는 작업 — 스키마 정의, 검증, 데이터 적재(population), 테스트까지 — 을 자동화하려고 에이전트를 만들었습니다. 첫 버전은 요즘 누구나 먼저 떠올리는 형태였습니다. 모든 도메인 지식을 집어넣은 똑똑한 에이전트 하나. 그리고 그 에이전트는 프로덕션에서 환각(hallucination)을 시작했습니다.

흥미로운 건 Meta의 처방입니다. 더 좋은 모델로 바꾸지도, 프롬프트를 더 정교하게 다듬지도 않았습니다. 대신 에이전트가 생각할 일 자체를 구조적으로 줄였습니다. 도메인 지식이 전혀 없는 약 1,300줄짜리 결정론적(deterministic) 오케스트레이터가 20개 이상의 워크플로를 14개 전문가 서브에이전트에게 배분하고, LLM의 추론은 격리된 전문가 안에서만 일어나게 한 겁니다. 이번 주 AI 엔지니어링 담론이 온통 "에이전트가 만든 결과물을 누가 검증하나"(하버드의 코딩 에이전트 생산성 연구, 에이전트 트레이스 검증 모델 출시 등)로 쏠린 가운데, "애초에 틀릴 공간을 줄이는 설계"를 보여준 보기 드문 실전 사례라 더 주목받았습니다.

이 글에서는 Meta가 공개한 구조를 하나씩 뜯어보고, 같은 패턴을 흉내 낸 미니 구현을 만들어 본 다음, "그래서 오케스트레이터는 LLM이어야 하나, 코드여야 하나"라는 더 큰 논쟁 안에 이 설계를 놓아 봅니다.

2. 배경 — 워크플로와 에이전트, 그 사이의 라우터

먼저 용어부터 정리하겠습니다. Anthropic은 Building effective agents에서 에이전틱 시스템을 둘로 나눕니다.

  • 워크플로(workflow): LLM과 도구를 미리 정해 둔 코드 경로로 엮은 시스템. 순서는 개발자가 코드로 결정합니다.
  • 에이전트(agent): LLM이 스스로 다음 행동과 도구 사용을 결정하며 진행하는 시스템.

같은 글의 조언은 "가능한 한 단순한 쪽을 먼저 쓰라"였습니다. 하지만 지난 2년간 실무의 기본값은 반대로 움직였습니다. 오케스트레이터 역할까지 LLM에게 맡기는 구조 — 리드 에이전트가 과제를 읽고, 계획을 세우고, 서브에이전트를 띄우는 패턴 — 가 유행했고, 이 블로그에서도 멀티 에이전트 오케스트레이션 편에서 그 구조를 다뤘습니다.

LLM 오케스트레이터는 유연합니다. 처음 보는 요청도 어떻게든 분해해 냅니다. 문제는 그 유연함의 값입니다. 라우팅·필드 수집·순서 결정처럼 정답이 명확한 판단까지 확률적인 모델에게 맡기면, 그 판단 하나하나가 실패 확률을 가진 지점이 됩니다. 열 단계짜리 작업에서 단계마다 95% 정확하면 전체 성공률은 60% 아래로 떨어집니다. 게다가 오케스트레이터가 중간에 길을 잘못 들면, 그 아래에서 아무리 성실하게 일해도 결과물은 틀립니다.

Meta의 글이 겨냥하는 지점이 정확히 여기입니다. 한 문장으로 요약하면 이렇습니다. "라우팅은 추론 과제가 아니다(routing is not a reasoning task)." 요청이 어떤 종류인지 분류하고, 필요한 입력값이 다 모였는지 확인하고, 다음 단계로 넘길지 결정하는 일은 — 적어도 도메인이 정해진 사내 시스템에서는 — 평범한 코드로 충분하다는 겁니다.

3. 사건 해부 — 교차 오염이라는 환각의 뿌리

Meta의 1세대 에이전트가 왜 무너졌는지부터 봅시다. 데이터 컬럼 온보딩에는 여러 종류의 지식이 필요합니다. 스키마 규칙, 검증 규칙, 소스별 데이터 적재 패턴, 테스트 작성법…. 1세대는 이걸 전부 한 에이전트의 컨텍스트에 실었습니다. 그중 데이터 적재 지식만 해도 10개 이상의 데이터 소스별 패턴이 함께 들어 있었습니다.

그러자 교차 오염(cross-contamination)이 일어났습니다. A 소스의 컬럼을 작업하는데 B 소스의 적재 패턴이 섞여 나오는 식입니다. 모델 입장에서는 당연한 일입니다. 컨텍스트에 비슷하게 생긴 패턴이 10개 놓여 있으면, 그중 무엇을 집을지는 결국 확률의 문제가 됩니다. 비유하자면 서랍 10칸의 내용물을 책상 하나에 전부 쏟아 놓고 "알아서 맞는 걸 집어 써"라고 시킨 셈입니다. 사람도 이러면 틀립니다.

daily.dev에 전재된 본문 수치에 따르면, 이 단일 에이전트는 과제마다 수작업으로 프롬프트를 손봐 줘야 70~80% 성공률이 나왔고, 그 손질이 없으면 10~20%까지 떨어졌습니다. 자동화하려고 만든 시스템이 과제별 수작업 없이는 돌아가지 않는, 자기모순에 빠진 겁니다.

2세대의 핵심 아이디어가 그림 1 오른쪽입니다. 적재 전문가는 담당 소스의 패턴만 로드한 채 실행됩니다. Meta의 표현을 빌리면, 한 데이터 소스의 population agent는 다른 소스의 패턴을 본 적이 없으므로 그것을 잘못 끌어올 수 없습니다. 환각을 "모델이 가끔 틀리는 현상"으로 받아들이고 검증으로 걸러내는 대신, 틀릴 재료 자체를 컨텍스트에서 치운 겁니다. 결과는 분명했습니다. 컬럼 하나 준비에 수작업으로 3~4일, 이전의 설정 기반 시스템으로 약 하루 걸리던 작업이 1시간 이내로 줄었고, 변경의 약 3분의 2는 사람의 유의미한 수정 없이 그대로 반영됩니다.

컨텍스트 격리가 왜 효과적일까요? 이 블로그에서 다룬 컨텍스트가 적을수록 에이전트가 나아지는 이유와 같은 원리입니다. LLM의 주의(attention)는 컨텍스트에 있는 모든 토큰에 분산됩니다. 지금 과제와 무관한 "비슷하게 생긴" 지식은 단순한 낭비가 아니라, 잘못된 답을 그럴듯하게 만들어 주는 적극적인 방해물입니다.

4. Thin Orchestrator ① — 7단계 중 LLM은 한 단계뿐

그럼 그 "얇은" 오케스트레이터는 실제로 무슨 일을 할까요? Meta의 오케스트레이터는 약 1,300줄의 코드로, 요청 하나를 7단계 프로토콜로 처리합니다. 핵심은 7단계 중 LLM 추론이 개입하는 단계가 6번 하나뿐이라는 점입니다. 나머지는 전부 결정론적 코드, 즉 같은 입력에 항상 같은 출력을 내는 평범한 프로그램입니다.

각 단계를 junior 눈높이로 다시 읽어 보면 이렇습니다.

  • ① 지시문 읽기 — 해당 워크플로를 맡을 서브에이전트의 지시 파일을 읽어 옵니다. 전문가의 지식 파일은 오케스트레이터에 내장되지 않고, 실행 시점에 필요한 것만 로드됩니다.
  • ② 중복 확인 — 같은 컬럼에 대한 작업이 이미 돌고 있으면 새로 만들지 않습니다. 에이전트가 중복 산출물을 만드는 흔한 사고를 코드 한 줄짜리 검사로 막습니다.
  • ③ 필드 수집 / ④ 값 자동 추론 — 작업에 필요한 필수 입력값을 점검하고, 기존 시스템에서 유추할 수 있는 값은 질문 없이 채웁니다. "필요한 값이 빠졌는데 에이전트가 지어내는" 사고는 대부분 여기서 걸러집니다.
  • ⑤ 안정성 게이트(reliability gate) — 대상 시스템에 활성 경보가 떠 있는지, 필수 리뷰어 지정이 필요한지 등을 확인합니다. 통과하지 못하면 LLM은 아예 호출되지 않습니다.
  • ⑥ 위임 — 여기서 처음으로 LLM이 등장합니다. 선택된 전문가 서브에이전트가 자기 도메인 지식만 들고 실제 추론과 생성을 수행합니다.
  • ⑦ 결과 처리 — 산출물을 받아 검수하고 다음 단계로 넘깁니다.

이 설계의 멋진 점은 실패의 성격이 단계마다 달라진다는 겁니다. ①~⑤에서 생기는 문제는 버그입니다. 재현되고, 디버거로 잡히고, 테스트로 막을 수 있습니다. 확률적이고 재현이 어려운 LLM의 실패는 ⑥ 안에, 그것도 좁은 도메인 컨텍스트 안에 갇힙니다. 장애가 났을 때 "어디부터 봐야 하나"가 구조적으로 정해져 있는 셈입니다.

5. Thin Orchestrator ② — 워크플로 템플릿이라는 상태 기계

남은 질문이 하나 있습니다. 단계 순서는 누가 정할까요? "스키마부터 만들고, 검증하고, 데이터를 채우고, 테스트한다" 같은 진행 계획 말입니다. LLM 오케스트레이터 구조에서는 이걸 모델이 매번 새로 "계획"합니다. Meta는 이것도 모델에게서 뺏었습니다. 워크플로 템플릿(workflow template), Meta의 표현으로는 "LLM의 결정 공간을 제약하는 결정론적 상태 기계(deterministic state machines that constrain the LLM's decision space)"가 순서를 정합니다.

예를 들어 컬럼 온보딩 템플릿은 Schema → Validation → Population → Testing이라는 고정된 phase 순서를 가집니다. 상태 기계(state machine)란 "현재 상태에서 갈 수 있는 다음 상태가 미리 정의된 그래프"입니다. 게임 캐릭터가 '서기 → 걷기 → 달리기'로만 전이하고 '서기 → 공중제비'로는 못 가는 것과 같은 구조입니다. 에이전트는 Validation 단계에서 갑자기 Testing으로 건너뛰자고 "판단"할 수 없습니다. 그런 선택지가 애초에 존재하지 않기 때문입니다.

이 구조는 이 블로그에서 다룬 멀티에이전트 핸드오프의 제약 약화 문제의 해법이기도 합니다. 그 글의 요지는 "에이전트끼리 자유 서술로 작업을 넘기면, 실행을 구속해야 할 조건이 '참고 사항'으로 약화되어 무시된다"였습니다. Meta의 템플릿에서는 핸드오프가 자유 서술이 아니라 구조화된 상태 전이이고, 전제 조건은 ⑤ 안정성 게이트가 코드로 강제합니다. 조건이 약화될 통로가 없습니다.

6. 실전 — 미니 thin orchestrator 만들어 보기

패턴을 몸에 붙이는 가장 좋은 방법은 작게 만들어 보는 것입니다. Meta 시스템의 뼈대를 100줄 이하 Python으로 흉내 내 보겠습니다. 먼저 전문가 서브에이전트의 정의입니다. 포인트는 전문가마다 지시문·지식 파일·필수 필드를 선언적으로 들고 있고, 지식은 실행 시점에만 로드된다는 것입니다.

{{< highlight python >}} from dataclasses import dataclass from pathlib import Path @dataclass class Specialist: name: str knowledge_file: str # 이 전문가"만" 보는 도메인 지식 required_fields: list[str] def run(self, task: dict) -> str: # 실행 시점에 자기 지식만 로드 — 다른 전문가의 지식은 못 본다 knowledge = Path(self.knowledge_file).read_text() prompt = ( f"당신은 {self.name} 전문가입니다.\n" f"--- 도메인 지식 ---\n{knowledge}\n" f"--- 작업 ---\n{task}" ) return call_llm(prompt) # 유일한 LLM 호출 지점 (⑥ 위임) SPECIALISTS = { "schema": Specialist("스키마", "knowledge/schema.md", ["column", "dtype"]), "validation": Specialist("검증", "knowledge/validation.md", ["column"]), "population": Specialist("적재", "knowledge/pop_source_a.md", ["column", "source"]), "testing": Specialist("테스트", "knowledge/testing.md", ["column"]), } {{< /highlight >}}

다음은 오케스트레이터입니다. 의도 분류, 필드 점검, 안정성 게이트, 그리고 상태 기계로 고정된 phase 진행 — 전부 평범한 코드입니다. LLM은 어디에도 없습니다.

{{< highlight python >}} # 워크플로 템플릿: phase 순서가 고정된 상태 기계 TEMPLATES = { "column_onboarding": ["schema", "validation", "population", "testing"], } # 의도 분류: 사내 시스템이라면 요청 유형이 유한하므로 코드 매핑으로 충분 INTENT_MAP = {"새 컬럼": "column_onboarding", "컬럼 추가": "column_onboarding"} def classify_intent(request: str) -> str: for keyword, workflow in INTENT_MAP.items(): if keyword in request: return workflow raise ValueError(f"미지원 요청: {request!r}") # 모르면 지어내지 않고 거절 def reliability_gate(task: dict) -> None: if has_active_alerts(task["column"]): # ⑤ 활성 경보 확인 raise RuntimeError("대상 시스템에 활성 경보 — LLM 호출 전에 차단") def orchestrate(request: str, fields: dict) -> dict: workflow = classify_intent(request) # ① 분류 (결정론) if is_duplicate(workflow, fields): # ② 중복 확인 return {"status": "skipped", "reason": "이미 진행 중"} results = {} for phase in TEMPLATES[workflow]: # 상태 기계가 순서 결정 spec = SPECIALISTS[phase] missing = [f for f in spec.required_fields if f not in fields] for f in missing: # ③④ 필드 수집·자동 추론 fields[f] = auto_discover(f, fields) # 못 찾으면 여기서 예외 reliability_gate(fields) # ⑤ 게이트 results[phase] = spec.run(fields) # ⑥ 유일한 LLM 단계 return {"status": "done", "results": results} # ⑦ 결과 처리 {{< /highlight >}}

장난감 수준이지만 Meta 설계의 성질이 그대로 드러납니다. orchestrate()는 단위 테스트를 쓸 수 있습니다. 의도 분류가 틀리면 그건 INTENT_MAP의 버그이지 "모델이 이상한 날"이 아닙니다. 적재 전문가에게 B 소스 패턴이 섞여 들어갈 방법은 코드 어디에도 없습니다. 그리고 새 워크플로를 추가할 때 건드리는 것은 템플릿 딕셔너리 한 줄과 전문가 정의뿐입니다. Meta가 이 구조로 20개 이상의 워크플로를 돌리는 이유입니다.

의도 분류에 LLM을 쓰면 안 되나요? 됩니다. 요청이 자유로운 자연어라면 분류기 자리에 작은 LLM 호출을 둘 수도 있습니다. 중요한 건 그 경우에도 출력을 TEMPLATES의 키 중 하나로 강제(constrained output)하고, 분류 결과가 이후 단계를 "제안"하는 게 아니라 고정된 템플릿을 "선택"만 하게 하는 것입니다. 결정 공간을 좁힌다는 원칙은 그대로입니다.

7. 논쟁 — 그래서 LLM 플래너는 버려야 하나

여기까지 읽으면 "오케스트레이터는 무조건 코드로 짜야겠다"는 결론으로 기울기 쉽습니다. 하지만 반대편 증거도 만만치 않습니다. Anthropic의 멀티 에이전트 리서치 시스템은 리드 LLM이 서브에이전트를 동적으로 설계·지휘하는 구조로 리서치 품질을 크게 끌어올렸고, Cognition은 Don't Build Multi-Agents에서 아예 "컨텍스트를 쪼개지 말라"고 주장했다가, 올해 4월 후속 글 Multi-Agents: What's Actually Working에서 "읽기는 병렬로, 쓰기는 단일 스레드로"라는 절충으로 입장을 다듬었습니다.

모순처럼 보이지만, 과제의 성격을 기준으로 놓으면 깔끔하게 정리됩니다.

얇은 오케스트레이터가 맞는 과제LLM 플래너가 맞는 과제
과제 구조유형이 유한하고 반복적 (온보딩, 설정 변경, 티켓 처리)열린 질문, 매번 분해 방식이 다름 (리서치, 탐색적 디버깅)
올바른 순서미리 알 수 있고 거의 변하지 않음진행하면서 발견됨
도메인 지식영역별로 깔끔하게 쪼개짐 → 격리가 이득서로 얽혀 있음 → 격리하면 Cognition이 지적한 맥락 단절 발생
실패 비용프로덕션 변경이라 틀리면 비쌈 → 결정론·게이트 필수탐색 중 오답은 싸고 회복 가능
대표 사례Meta Thin OrchestratorAnthropic 리서치 시스템, 코딩 에이전트의 계획 수립

Meta의 과제는 왼쪽 열의 교과서적 사례였습니다. 워크플로 유형이 20여 개로 유한하고, 순서는 도메인이 이미 정해 놨고, 지식은 소스별로 쪼개지고, 틀리면 추천 시스템의 데이터가 오염됩니다. Meta 스스로도 이 설계가 일반성(generality)을 포기하고 깊이를 산 의도적 선택이라고 못 박습니다 — "오케스트레이터는 일반적이고, 서브에이전트는 전문가다(The orchestrator is general; the subagents are specialists)." 처음 보는 유형의 요청은 이 시스템이 처리하지 못합니다. 그건 버그가 아니라 설계의 대가입니다.

junior 입장에서 가져갈 질문은 "어느 진영이 옳은가"가 아니라 "내 시스템에서 LLM 추론이 꼭 필요한 단계는 정확히 어디인가"입니다. Anthropic의 원칙("가장 단순한 구성을 먼저")을 오케스트레이션에 적용하면 이렇게 됩니다. 모든 단계를 LLM에게 주고 시작하는 게 아니라, 코드로 되는 단계를 전부 코드로 깎아낸 뒤 남는 자리에만 LLM을 놓는 것. Meta는 그 깎아내기를 끝까지 밀어붙이면 7단계 중 1단계만 남더라는 실측 사례를 보여준 겁니다.

8. 흔한 실수 · 팁

  • "얇게"의 기준을 코드 줄 수로 착각하기. 1,300줄이라서 얇은 게 아니라, 도메인 지식과 추론이 0이라서 얇은 겁니다. 오케스트레이터에 "이 소스는 보통 이렇게 처리하니까…" 같은 지식이 한 줄이라도 스며들면, 전문가와 라우터 두 곳에서 같은 지식을 관리하게 되고 교차 오염이 돌아옵니다.
  • 전문가를 쪼개 놓고 지식 파일을 공유하기. 서브에이전트를 14개로 나눠도 모두가 같은 거대 지식 베이스를 로드하면 1세대와 똑같습니다. 격리의 단위는 프로세스가 아니라 컨텍스트입니다.
  • 게이트를 LLM 뒤에 두기. 안정성 게이트가 ⑥ 뒤에 있으면 이미 생성된 그럴듯한 산출물을 사람이 심사하는 구조가 됩니다. 게이트는 LLM 앞에 둬야 비용(토큰)과 위험(그럴듯한 오답)을 동시에 줄입니다.
  • 필수 필드가 비었을 때 LLM이 채우게 두기. 1세대 환각의 단골 경로입니다. 유추 가능한 값은 결정론적 조회(④)로 채우고, 못 채우면 지어내는 대신 사람에게 묻거나 실패해야 합니다.
  • 모든 것을 템플릿화하려다 멈추기. 템플릿은 반복되는 워크플로에만 효과가 있습니다. 유형이 아직 안 잡힌 신규 업무까지 억지로 상태 기계에 밀어 넣으면 템플릿이 수십 갈래로 분기하며 썩습니다. 처음엔 LLM 플래너로 풀어 보고, 패턴이 보이면 템플릿으로 "굳히는" 순서가 현실적입니다.
  • 성공 지표를 데모 기준으로 잡기. Meta가 보고한 건 "3분의 2가 사람의 유의미한 수정 없이 반영"이라는 운영 지표입니다. 내 시스템에도 "사람 개입 없이 끝난 비율" 같은 지표를 처음부터 심어 두면, 아키텍처 변경의 효과를 숫자로 비교할 수 있습니다.

9. 마무리 (TL;DR)

  • Meta는 추천 시스템의 데이터 컬럼 온보딩을 "모든 도메인 지식을 아는 에이전트 하나"로 자동화하려다 프로덕션 환각(교차 오염)을 겪었고, 10/19 엔지니어링 블로그에 그 전환기를 공개했습니다.
  • 2세대는 도메인 지식이 0인 약 1,300줄짜리 결정론적 오케스트레이터가 20개 이상의 워크플로를 14개 전문가 서브에이전트에게 배분하는 구조입니다. 7단계 프로토콜 중 LLM 추론은 ⑥ 위임 단계 하나뿐입니다.
  • 전문가는 자기 도메인 지식만 실행 시점에 로드합니다. 다른 소스의 패턴을 본 적이 없으면 잘못 집을 수도 없다 — 환각을 검증으로 거르는 대신 틀릴 재료를 컨텍스트에서 치우는 접근입니다.
  • phase 순서는 워크플로 템플릿, 즉 LLM의 결정 공간을 제약하는 상태 기계가 고정합니다. 모델의 고민은 "다음에 뭘 할까"에서 "이 단계를 어떻게 잘할까"로 좁아집니다.
  • 성과: 컬럼 준비 3~4일(수작업)·약 1일(기존 설정 시스템) → 1시간 이내, 변경의 약 3분의 2는 사람의 유의미한 수정 없이 반영. 대가는 일반성 — 정해진 유형 밖의 요청은 처리하지 못합니다.
  • 교훈은 "LLM 플래너를 버려라"가 아닙니다. 코드로 되는 단계를 전부 코드로 깎아낸 뒤, 남는 자리에만 LLM을 두라는 것 — 반복적이고 실패가 비싼 과제일수록 그 남는 자리는 생각보다 작습니다.
