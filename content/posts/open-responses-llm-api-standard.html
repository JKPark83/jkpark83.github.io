1. 도입 — 사설 API가 공개 표준이 된 날

vLLM, Ollama, LM Studio… 로컬에서 모델을 서빙해 본 적이 있다면 이상한 공통점을 눈치챘을 겁니다. 전부 자기를 "OpenAI 호환(OpenAI-compatible) 서버"라고 소개합니다. 경쟁사의 모델을 돌리는 도구조차 한 회사의 API 모양을 그대로 흉내 냅니다. HTTP에 W3C가 있고 언어에 ISO가 있는 것과 달리, LLM API의 표준은 지금까지 어느 날 한 회사가 정한 JSON 모양이었습니다. 스펙 문서도, 중립적인 관리 주체도, 준수 여부를 검사할 테스트도 없이요.

이 어색한 상태가 지난주에 한 단계 정리됐습니다. 10월 22일(현지 시각), San Jose에서 열린 AGNTCon + MCPCon에서 Linux Foundation 산하 Agentic AI Foundation(AAIF)이 신규 프로젝트 4개를 발표했습니다. Anthropic의 Agent Skills, Hugging Face의 OpenEnv, Alibaba의 OpenSandbox, 그리고 OpenAI의 Open Responses — Responses API를 벤더 중립 스펙으로 정리한 프로젝트입니다. 전날인 10월 21일에는 Open Responses의 기술 헌장(technical charter)이 채택됐고, 운영위원회(TSC)에는 OpenAI뿐 아니라 Amazon, Databricks, Hugging Face, Ollama, OpenRouter, Ramp의 엔지니어가 이름을 올렸습니다.

"재단에 기부했다"는 뉴스 자체는 거버넌스 이야기지만, 그 밑에 깔린 질문은 순수하게 엔지니어링입니다. 에이전트 시대의 LLM API는 어떤 모양이어야 하는가? Open Responses 스펙은 이 질문에 대한 현재 업계의 합의안이고, 분량도 핵심만 보면 하루에 다 읽을 수 있는 수준입니다. 이번 글에서는 이 스펙을 처음부터 끝까지 뜯어봅니다. 다 읽고 나면 "왜 다들 Chat Completions를 버리고 이쪽으로 가는지"가 구조적으로 이해될 겁니다.

2. 배경 — 'OpenAI 호환'의 역사

먼저 어쩌다 한 회사의 API가 사실상 표준이 됐는지 짚고 갑시다. 2023년 3월, OpenAI가 gpt-3.5-turbo와 함께 Chat Completions API(POST /v1/chat/completions)를 공개했습니다. messages 배열에 role과 content를 담아 보내면 응답이 오는 단순한 구조였고, ChatGPT 붐과 함께 순식간에 생태계의 공용어가 됐습니다. 이후 등장한 거의 모든 서빙 도구와 라우터가 이 모양을 복제했습니다. 클라이언트 입장에서 base_url만 바꾸면 어디든 붙을 수 있다는 건 강력한 네트워크 효과였으니까요.

그런데 2025년 3월 11일, 정작 OpenAI가 후속작을 내놓습니다. Responses API(POST /v1/responses)입니다. 에이전트와 리즈닝 모델(reasoning model, 답을 내기 전에 내부 추론 토큰을 생성하는 모델)을 위해 처음부터 다시 설계한 API였고, OpenAI는 기존의 Assistants API를 단계적으로 폐기하고 이쪽으로 통합하겠다고 예고했습니다. 문제는 이게 다시 한 회사의 사설 API라는 점이었습니다. 생태계가 또 한 번 그대로 복제하기 시작하면, "버전 관리도 안 되는 비공식 표준"이라는 상황이 반복됩니다.

그래서 나온 게 Open Responses입니다. 2026년 1월 15일 첫 스펙 릴리스로 공개됐고, Responses API에서 출발하되 특정 벤더 종속 없이 요청/응답 모델·스트리밍 의미론·도구 호출 패턴을 정의합니다. TypeSpec 소스에서 OpenAPI 문서를 생성하고, 날짜 버전(2026-01-15, 2026-04-24)으로 릴리스하며, 한번 릴리스된 버전은 불변(immutable)입니다. 라이선스는 Apache 2.0, 스펙 준수 여부를 검사하는 compliance 테스트(웹 UI와 CLI)까지 함께 제공합니다. 프로젝트 사이트에는 OpenAI 외에 AWS, NVIDIA, Hugging Face, Databricks, Red Hat, Vercel(AI SDK), OpenRouter, Ollama, LM Studio, vLLM, Llama Stack이 참여사로 올라 있습니다. 그리고 지난주, 이 스펙의 소유권이 AAIF로 넘어가면서 '한 회사의 제안'이 아니라 '공동 관리 표준'이 된 것입니다.

AAIF가 뭔가요? 2025년 12월 9일 Linux Foundation이 설립한 에이전트 기술 전용 재단입니다. 창립 프로젝트가 MCP(Anthropic), goose(Block), AGENTS.md(OpenAI)였고, 이번 4개가 합류하며 호스팅 프로젝트는 총 10개가 됐습니다. 플래티넘 멤버는 AWS·Anthropic·Block·Bloomberg·Cloudflare·Google·Microsoft·OpenAI. 에이전트 스택의 '표준 기구' 역할이 이 재단으로 모이는 중입니다.

3. Chat Completions가 에이전트 시대에 삐걱대는 세 곳

새 스펙을 이해하는 가장 빠른 길은 옛 스펙이 깨지는 지점을 보는 겁니다. Chat Completions는 "메시지를 보내면 메시지가 온다"는 챗봇 시대의 모델입니다. 에이전트 시대에는 세 군데서 삐걱댑니다.

첫째, 응답이 '메시지 하나'가 아닙니다. 요즘 모델의 한 턴은 내부 추론 → 도구 호출 → 도구 결과 반영 → 또 추론 → 최종 답변처럼 여러 종류의 산출물이 섞인 시퀀스입니다. Chat Completions는 이걸 choices[0].message 하나에 욱여넣느라 tool_calls 필드를 덧대고, 추론은 벤더마다 제각각의 비표준 필드로 노출했습니다.

둘째, 리즈닝 상태가 턴 사이에 유실됩니다. 리즈닝 모델은 도구 호출 전에 쌓은 추론을 도구 결과가 돌아온 뒤에도 이어 가야 하는데, Chat Completions에는 추론 상태를 다음 요청으로 돌려보낼 표준 통로가 없습니다. 모델 입장에서는 도구 결과가 돌아올 때마다 기억 상실에 걸리는 셈입니다. OpenAI는 같은 GPT-5를 Responses API로 돌리면 추론 보존 덕에 TAU-Bench 점수가 5% 오르고, 내부 벤치마크 기준 캐시 활용률이 40~80% 개선됐다고 보고합니다(자사 수치이니 참고용으로만).

셋째, 스트리밍이 '텍스트 조각'입니다. Chat Completions의 스트림은 사실상 content 문자열의 델타 나열이라, 도구 호출 인자와 추론과 본문이 섞이기 시작하면 클라이언트가 "지금 내가 받는 조각이 뭐의 일부인지"를 추측해야 합니다. 벤더마다 추측 규칙이 달라서, 멀티 프로바이더 클라이언트는 스트리밍 파서를 프로바이더 수만큼 들고 다니게 됩니다.

Open Responses는 이 세 문제에 각각 답을 내놓습니다 — item, reasoning item, 시맨틱 이벤트입니다. 하나씩 봅시다.

4. 해부 ① — item: 컨텍스트의 원자 단위

스펙의 중심 개념은 item(아이템)입니다. 메시지의 자리를 item이 대신합니다. item은 모델 출력·도구 호출·추론 상태를 담는 원자 단위이고, 양방향입니다 — 모델의 출력으로 받을 수도 있고, 다음 요청의 입력으로 그대로 돌려보낼 수도 있습니다. 대화 컨텍스트란 결국 item의 목록입니다.

item에는 네 가지 성질이 있습니다.

다형적(polymorphic)입니다. type 필드로 구분되는 여러 모양이 있습니다. 공통 타입으로 message, function_call, function_call_output, reasoning 등이 정의돼 있고, 각 타입은 자기 목적에 맞는 스키마를 가집니다.

{{< highlight json >}} // 한 응답(response)의 output — 서로 다른 타입의 item이 순서대로 쌓인다 [ { "type": "reasoning", "status": "completed", "summary": [{ "type": "summary_text", "text": "환율 조회가 필요하다고 판단" }], "content": [], // 원문 추론: 프로바이더가 숨길 수 있음 "encrypted_content": "gAAAA..." // 암호화 추론: 클라이언트는 불투명하게 취급 }, { "type": "function_call", "id": "fc_001", "call_id": "call_123", "name": "get_exchange_rate", "arguments": "{\"base\":\"USD\",\"quote\":\"KRW\"}" } ] {{< /highlight >}}

상태 머신(state machine)입니다. 모든 item은 in_progress(모델이 토큰을 뱉는 중) → completed(완료) 또는 incomplete(토큰 예산 소진)라는 생명주기를 가집니다. incomplete은 종료 상태라서, 어떤 item이 이 상태로 끝나면 그 item이 마지막이어야 하고 응답 전체도 incomplete이어야 한다 — 이런 규칙까지 스펙에 못 박혀 있습니다. "응답이 중간에 잘렸는지 어떻게 아나요?" 같은, 지금까지 벤더마다 답이 다르던 질문에 표준 답이 생긴 겁니다.

스트리밍 가능(streamable)합니다. item이 생기고 자라고 완료되는 과정이 모두 이벤트로 중계됩니다(다음 절에서 자세히).

확장 가능(extensible)합니다. 프로바이더는 스펙에 없는 자기만의 item 타입을 추가할 수 있는데, 반드시 openai:web_search_call처럼 프로바이더 슬러그를 접두사로 붙여야 합니다. 핵심 스키마를 깨지 않으면서 벤더 고유 기능이 공존하는 통로입니다. 클라이언트는 모르는 타입의 item을 만나도 죽지 않고 통과시키도록 작성하면 됩니다.

세 번째 문제였던 리즈닝 유실은 reasoning item이 해결합니다. 필드가 세 개인데 전부 선택(optional)입니다 — content(원문 추론, 공개 여부는 프로바이더 재량), encrypted_content(원문을 숨기면서도 다음 요청에 왕복시킬 수 있는 암호화 페이로드), summary(사용자에게 보여줘도 안전한 요약). 프로바이더는 자기 정책에 맞는 조합을 고르면 되고, 클라이언트는 받은 reasoning item을 다음 요청에 그대로 돌려보내기만 하면 모델이 추론을 이어 갑니다. 추론 상태의 보존을 '벤더 내부 구현'에서 '스펙의 계약'으로 끌어올린 설계입니다.

5. 해부 ② — 시맨틱 스트리밍과 상태 머신

스트리밍도 다시 설계됐습니다. 원칙은 한 문장입니다. 스트림은 텍스트 델타의 나열이 아니라, 의미 있는 사건(semantic event)의 나열이다. 모든 이벤트는 두 종류 중 하나입니다.

  • 델타 이벤트 — 객체에 생긴 변화: response.output_item.added(새 item 추가), response.output_text.delta(본문 텍스트 추가), response.function_call_arguments.delta(도구 인자 추가), response.content_part.done(한 콘텐츠 조각 완결)…
  • 상태 머신 이벤트 — 객체의 상태 전이: response.in_progress, response.completed, response.failed, response.incomplete…

전송은 평범한 SSE(Server-Sent Events)지만 규칙이 명확합니다. 스트림은 반드시 종결 이벤트(response.completed/failed/incomplete)로 끝나야 하고, 그 뒤의 [DONE] 문자열은 보내도 되고 안 보내도 됩니다(클라이언트는 둘 다 수용해야 합니다). 각 이벤트에는 sequence_number가 붙어 순서 검증과 재연결 복구에 쓸 수 있습니다. item이 처음 등장할 때는 반드시 response.output_item.added가 먼저 오고, 그 시점에 알 수 있는 필드(메시지면 최소 role, 도구 호출이면 최소 name)가 채워져 있어야 합니다.

이 설계의 수혜자는 UI를 만드는 사람입니다. "추론 중입니다" 스피너, 도구 호출 카드, 본문 타이핑 효과를 이벤트 타입별 분기로 깔끔하게 구현할 수 있고, 그 코드가 OpenAI든 vLLM이든 Ollama든 동일하게 동작합니다. 참고로 2026-04-24 릴리스에서는 같은 이벤트 모델을 그대로 쓰는 WebSocket 전송도 추가됐습니다. 연결당 동시 응답은 1개, 연결 수명은 최대 60분, 턴 시작은 response.create 메시지로 — 장시간 에이전트 세션을 위한 저지연 통로입니다.

6. 해부 ③ — 에이전트를 위한 손잡이들

스펙 후반부에는 에이전트 루프 운영에 필요한 손잡이들이 모여 있습니다. 네 가지만 추리면 이렇습니다.

previous_response_id — 대화를 서버에 이어 붙이기. 매 턴 전체 히스토리를 재전송하는 대신, 직전 응답의 ID와 새 입력만 보내면 서버가 이전 입력 → 이전 출력 → 새 입력 순서로 컨텍스트를 이어 붙입니다. 이 순서 보존은 MUST 규칙입니다. 도구 호출 루프라면 function_call_output item과 다음 사용자 메시지만 보내면 되니 페이로드가 확 줄고, 서버는 캐시를 그대로 재사용할 수 있습니다. 단, 서버 저장을 끈 store=false에서는 영속 폴백이 없다는 점을 기억하세요(8절에서 다시).

allowed_tools — 캐시를 깨지 않는 도구 제한. 도구 목록(tools)을 요청마다 고치면 시스템 프롬프트와 도구 스키마의 프롬프트 캐시가 통째로 무효화됩니다. 대신 tools는 고정해 두고 allowed_tools로 "이번 턴에 실제 호출 가능한 부분집합"만 좁히는 설계입니다. 서버는 이걸 강제 규칙(hard constraint)으로 집행해야 합니다 — 목록 밖 도구 호출은 거부되거나 억제됩니다. 테넌트별 권한, 사용자 역할, 기능 플래그 같은 요청 단위 도구 거버넌스를 캐시 손실 없이 구현하는 통로입니다.

truncation — 컨텍스트 초과 시의 계약. "auto"면 서버가 오래된 턴부터 알아서 잘라 창에 맞추고, "disabled"면 자르는 대신 요청을 실패시켜야 합니다. "조용히 앞부분이 잘려 나갔는데 아무도 몰랐다"는 사고를 계약 수준에서 막을 수 있습니다.

POST /v1/responses/compact — 압축의 표준화. 2026-04-24 릴리스에 추가된 엔드포인트로, 긴 대화를 압축한 입력 윈도우로 바꿔 돌려줍니다. 이 블로그에서 여러 번 다룬 컨텍스트 압축(compaction)이 벤더 공통 API 표면으로 올라온 셈입니다. 압축 후에는 previous_response_id 없이 압축 결과를 새 input의 바탕으로 깔고 새 응답을 시작합니다.

7. 실전 — 같은 코드로 여러 프로바이더 호출하기

스펙의 약속이 실감 나는 건 역시 코드를 볼 때입니다. 아래는 도구 호출 루프 한 바퀴를 도는 최소 클라이언트입니다. 포인트는 딱 하나 — BASE_URL만 바꾸면 OpenAI, vLLM(0.10 이상이 /v1/responses를 지원합니다), Ollama 어디에든 붙습니다.

{{< highlight python >}} import json, requests BASE_URL = "http://localhost:8000/v1" # vLLM이든 OpenAI든 여기만 교체 HEADERS = {"Authorization": "Bearer sk-...", "Content-Type": "application/json"} tools = [{ "type": "function", "name": "get_exchange_rate", "description": "기준 통화 대비 환율을 조회한다", "parameters": { "type": "object", "properties": {"base": {"type": "string"}, "quote": {"type": "string"}}, "required": ["base", "quote"], }, }] # ① 첫 턴: 질문과 도구 목록을 보낸다 r1 = requests.post(f"{BASE_URL}/responses", headers=HEADERS, json={ "model": "gpt-openresponses-1", "input": [{"type": "message", "role": "user", "content": "지금 1달러가 몇 원이야?"}], "tools": tools, }).json() # ② 출력은 '메시지 하나'가 아니라 item 목록 — 타입으로 분기한다 outputs = {} for item in r1["output"]: if item["type"] == "function_call": args = json.loads(item["arguments"]) outputs[item["call_id"]] = my_get_exchange_rate(**args) # 직접 실행 # reasoning 등 모르는 타입은 그냥 통과 (전방 호환) # ③ 둘째 턴: 전체 히스토리 대신 previous_response_id + 도구 결과만 r2 = requests.post(f"{BASE_URL}/responses", headers=HEADERS, json={ "model": "gpt-openresponses-1", "previous_response_id": r1["id"], # 서버가 이전 입력+출력을 이어 붙인다 "input": [{"type": "function_call_output", "call_id": cid, "output": str(out)} for cid, out in outputs.items()], "tools": tools, # 도구 목록은 고정 (캐시 보존) }).json() print(r2["output_text"]) # 최종 답변 텍스트 헬퍼 {{< /highlight >}}

내 서버(혹은 내가 만든 프록시)가 스펙을 제대로 지키는지는 공식 compliance 테스트로 확인할 수 있습니다. 스펙 저장소를 받아 CLI로 돌리면 됩니다.

{{< highlight bash >}} git clone https://github.com/openresponses/openresponses cd openresponses && bun install # 내 엔드포인트에 스펙 준수 테스트 실행 (요청당 30초 데드라인) bun run test:compliance --base-url http://localhost:8000/v1 --api-key $API_KEY # 특정 테스트만 골라서 bun run test:compliance --base-url http://localhost:8000/v1 \ --api-key $API_KEY --filter basic-response,streaming-response {{< /highlight >}}

웹 UI 버전도 openresponses.org/compliance에 있습니다. "우리 게이트웨이는 OpenAI 호환입니다"라는 말이 이제 돌려서 검증 가능한 주장이 된 겁니다 — 이게 공개 스펙과 비공식 호환의 결정적 차이입니다.

8. 흔한 실수 · 팁

  • output[0]이 메시지라고 가정하지 마세요. Chat Completions에서 넘어올 때 가장 흔한 버그입니다. 출력의 첫 item은 reasoning일 수도, function_call일 수도 있습니다. 반드시 type으로 분기하고, 최종 텍스트만 필요하면 output_text 헬퍼를 쓰세요.
  • 모르는 item·이벤트 타입에서 죽지 않게. 프로바이더 확장은 벤더슬러그:타입 형태로 언제든 끼어듭니다. 파서의 기본 동작은 '무시하고 통과'여야 전방 호환이 됩니다.
  • store=false와 previous_response_id의 조합을 조심하세요. 서버 저장을 끄면 이전 응답을 복원할 영속 상태가 없습니다. WebSocket에서는 연결-로컬 메모리로 직전 응답에 한해 이어 갈 수 있지만, 연결이 끊기거나 60분 한도에 걸리면 previous_response_not_found를 받습니다. 이때는 전체 컨텍스트를 다시 보내거나 /responses/compact 결과로 새 응답을 시작하는 복구 경로를 미리 코드에 넣어 두세요.
  • reasoning item은 버리지 말고 되돌려 보내세요. 도구 호출 루프에서 encrypted_content가 달린 reasoning item을 다음 요청 입력에 포함하지 않으면, 모델은 도구 결과가 올 때마다 추론을 처음부터 다시 합니다. 내용이 안 보여도(암호화) 왕복은 됩니다.
  • 도구를 끄고 싶으면 tools를 고치지 말고 allowed_tools를 쓰세요. tools 배열을 수정하면 프롬프트 캐시가 깨집니다. 전체 목록은 고정하고 호출 가능 부분집합만 좁히는 게 스펙이 의도한 사용법입니다.
  • 컨텍스트가 길어질 서비스라면 truncation을 명시하세요. 기본 동작에 기대면 "언제부턴가 모델이 앞부분을 모른다"는 미스터리 버그로 돌아옵니다. 자를 거면 auto를 의식적으로, 못 자르게 할 거면 disabled로 실패를 받으세요.
  • 버전은 날짜로 고정하세요. 릴리스(2026-01-15, 2026-04-24)는 불변입니다. 게이트웨이나 SDK를 만든다면 "우리는 2026-04-24 스펙 준수"처럼 날짜를 박고, compliance 테스트를 CI에 넣어 두면 스펙 업데이트 때 깨지는 지점이 바로 보입니다.

9. 마무리 (TL;DR)

  • 10월 22일, OpenAI가 Open Responses를 Linux Foundation 산하 AAIF에 기부했습니다. Agent Skills(Anthropic)·OpenEnv(Hugging Face)·OpenSandbox(Alibaba)와 함께였고, 이로써 'OpenAI 호환'이라는 비공식 관행이 Amazon·Databricks·Hugging Face·Ollama·OpenRouter가 함께 관리하는 공개 표준이 됐습니다.
  • 왜 새 API인가: Chat Completions는 응답이 '메시지 하나'라는 챗봇 시대 가정 위에 서 있습니다. 에이전트 시대의 한 턴은 추론·도구 호출·답변이 섞인 시퀀스라 item 목록이 맞는 모양이고, 리즈닝 상태는 reasoning item(원문/암호화/요약)으로 턴 사이를 왕복합니다.
  • 스트리밍은 시맨틱 이벤트(델타 + 상태 전이) 두 종류로 통일됐습니다. 이벤트 type으로 분기하는 파서 하나로 모든 준수 프로바이더를 처리할 수 있습니다.
  • 에이전트용 손잡이: previous_response_id(히스토리 재전송 없는 연속), allowed_tools(캐시를 안 깨는 도구 제한), truncation(자를지 실패할지의 계약), /responses/compact(압축의 표준화), WebSocket 전송(60분, 턴당 response.create).
  • 검증 가능성이 핵심 차이: 날짜 버전 릴리스는 불변이고, compliance 테스트(웹/CLI)로 "호환"이라는 주장을 실제로 돌려 확인할 수 있습니다. 내 게이트웨이를 만들면 CI에 넣으세요.
  • 수치는 출처를 가려 읽으세요 — "TAU-Bench +5%, 캐시 활용률 40~80% 개선"은 OpenAI 자사 벤치마크 수치입니다.
