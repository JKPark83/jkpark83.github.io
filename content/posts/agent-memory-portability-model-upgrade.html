1. 도입 — 업그레이드는 한 줄, 기억은 한 줄이 아니다

9월 들어 모델 릴리스가 쏟아지고 있습니다. Anthropic은 9월 1일 Fable 5.1을 내놓으면서 1M 토큰 컨텍스트에 캐시 읽기 요금을 $1에서 $0.25로 75% 내렸고, OpenAI도 같은 주에 제품 라인을 갈아엎었습니다. 장기 실행 에이전트의 운영 비용이 뚝 떨어지니, 지금 돌고 있는 에이전트의 모델 ID를 바꾸고 싶은 유혹이 큽니다. 실제로 바꾸는 건 코드 한 줄입니다.

그런데 오래 굴린 에이전트에는 코드 한 줄로 안 옮겨지는 것이 있습니다. 지금까지 쌓아 온 기억입니다. 유저 선호, 과거 결정, 프로젝트 맥락 — 몇 달치 대화에서 추출해 DB에 쌓아 둔 그 상태 말입니다. "메모리는 모델 밖 DB에 있으니 모델을 바꿔도 안전하다"고 생각하기 쉽습니다. 이번 주 실무자들 사이에서 화제가 된 Does Your Agent's Memory Survive a Model Upgrade?(arXiv:2609.05339, 9월 4일 공개)는 바로 그 가정을 통제 실험으로 검증했습니다.

결론부터 말하면, 저장 형태에 따라 운명이 극단적으로 갈립니다. 고정 스키마 지식 그래프에 넣은 기억은 모델을 바꿔도 정확도 변화가 사실상 0이었습니다. 반면 모델이 자연어로 압축해 둔 노트는 새 모델이 읽는 순간 정확도가 +9.91%p 오르거나 −13.28%p 떨어지는, 방향조차 예측할 수 없는 요동을 보였습니다. 임베딩을 절반만 새로 갈아 끼운 혼합 인덱스는 업그레이드로 얻을 수 있던 이득의 60%를 날렸습니다. 같은 DB, 같은 데이터인데도요.

이 글은 이 결과를 발판 삼아 한 단계 위의 질문을 다룹니다. 에이전트 밑에서 모델을 갈아 끼우는 일은 어떤 엔지니어링 이벤트이고, 무엇을 준비해야 하는가. 메모리 이식성(memory portability)이라는 렌즈로 보면, 업그레이드는 버전 숫자 바꾸기가 아니라 데이터 마이그레이션입니다.

2. 배경 — 기억을 쓴 모델, 읽을 모델, 찾아줄 모델

따라오는 데 필요한 최소한만 짚겠습니다. 에이전트 메모리 시스템에는 서로 다른 역할의 모델이 최소 셋 얽혀 있습니다.

  • writer — 대화·이벤트에서 기억할 내용을 뽑아 쓰는 모델. 요약하고, 노트로 압축하고, 그래프 노드로 정규화합니다.
  • reader — 나중에 그 기억을 읽고 답을 만드는 모델. 보통 writer와 같은 모델이지만, 업그레이드하는 순간 달라집니다.
  • 임베딩 모델 — 기억을 벡터로 바꿔 찾아주는 모델. 검색 기반 메모리라면 반드시 끼어 있습니다.

업그레이드란 이 셋 중 하나 이상을 갈아 끼우는 일입니다. 문제는 기억이 중립적인 데이터가 아니라는 점입니다. "요약 노트"는 writer 모델이 무엇이 중요한지 판단하고 자기 언어 습관으로 눌러 담은 결과물입니다. 사람으로 치면, 전임자가 자기만 알아보게 갈겨 쓴 인수인계 노트를 후임자가 물려받는 셈입니다. 전임자에게는 완벽한 기록이 후임자에게는 수수께끼일 수 있습니다.

논문은 같은 히스토리를 네 가지 형태로 저장해 비교합니다. 실무 프레임워크와 대응시켜 보면 감이 빠릅니다.

형태저장 방식모델 개입 정도실무에서 비슷한 것
LC-RAW원본 히스토리를 통째로 보존, 긴 컨텍스트로 읽기없음 (무손실)대화 로그 전체 재주입
RAG원본을 청크로 잘라 임베딩 검색임베딩 모델만벡터 DB 기반 검색 메모리

여기서 핵심 축이 보입니다. 모델의 해석이 데이터에 얼마나 스며들어 있는가. LC-RAW는 해석이 0이고, NOTES는 해석 그 자체이고, KG-fixed는 해석을 스키마라는 틀에 가둡니다. 이 축이 이식성을 결정합니다.

3. 실험 — 네 가지 저장 형태, 갈리는 운명

실험 설계는 검소하지만 통제가 좋습니다. 정답 코드를 랜덤화한 합성 히스토리 48개를 만들고(사전 지식으로 답을 맞힐 수 없게), 각 히스토리를 위 네 형태로 저장한 뒤, 정확 일치(exact match)로 채점합니다. 모델은 10B 미만 오픈웨이트 2종을 써서 writer와 reader를 서로 갈아 끼웁니다. 핵심 조작은 두 가지입니다.

  • writer swap — 기억은 구모델이 썼는데, 신모델이 읽는 상황. 우리가 겪는 "업그레이드 직후"입니다.
  • 임베딩 swap — 기억 본문은 그대로인데, 임베딩 모델 버전이 갈리는 상황. 다음 섹션에서 다룹니다.

writer swap 결과가 이 논문의 첫 번째 펀치라인입니다.

  • KG-fixed: 정확도 변화 +0.0004 ± 0.0020. 사실상 0입니다. 스키마가 강제하는 (주어, 관계, 값) 형식은 어느 모델이 읽어도 같은 뜻이기 때문입니다.
  • NOTES: 모델 조합에 따라 +9.91%p 또는 −13.28%p. 크기도 문제지만 진짜 문제는 비대칭입니다. 어떤 조합에서는 오르고 어떤 조합에서는 떨어지는데, 미리 예측할 방법이 없습니다.

NOTES가 왜 흔들리는지는 앞의 인수인계 비유로 설명됩니다. 압축 노트는 writer가 "무엇을 남기고 무엇을 버릴지" 판단한 결과이고, 그 판단은 writer 자신의 독해 습관에 최적화되어 있습니다. reader가 바뀌면 같은 문장을 다르게 해석하거나, writer가 "당연해서 생략한" 부분을 복원하지 못합니다. 더 좋은 모델로 바꿔도 마찬가지입니다 — 신모델이 더 똑똑한 것과, 구모델의 축약을 잘 알아듣는 것은 다른 능력이기 때문입니다.

실무로 번역하면 이렇습니다. Letta처럼 모델이 직접 관리하는 자연어 메모리 블록, Mem0처럼 LLM이 추출한 사실 노트를 쓰는 시스템은 모두 NOTES 계열의 결합을 안고 있습니다. 반면 Zep류의 스키마 있는 그래프 메모리, 또는 직접 설계한 고정 스키마 프로필({"선호_언어": "한국어", "타임존": "KST"} 같은)은 KG-fixed 쪽에 가깝습니다. 지난 글 메모리 통합(consolidation) 편에서 "무엇으로 굳힐 것인가"를 다뤘다면, 이번 결과는 그 선택에 이식성이라는 새 평가 기준을 추가합니다.

4. 임베딩 축 — 같은 1024차원인데 왜 어긋나나

두 번째 펀치라인은 RAG 쪽에서 나옵니다. 임베딩 모델을 v1.0에서 v1.5로 올리면서 인덱스 전체를 새로 임베딩하면 정확도가 +11.90%p 오릅니다. 여기까지는 예상대로입니다. 문제는 중간 상태입니다. 운영 중인 시스템에서 흔히 하듯 새 문서만 새 모델로, 옛 문서는 그대로 두는 50/50 혼합 인덱스를 만들면, 이득이 +4.96%p로 쪼그라듭니다. 잠재 이득의 60%가 증발한 겁니다.

왜 이럴까요? 두 임베딩 모델이 같은 1024차원 벡터를 내놓아도, 벡터가 사는 공간의 기하가 다릅니다. v1.0이 만든 벡터와 v1.5가 만든 질의 벡터 사이의 코사인 유사도는 의미적 유사성을 반영하지 않는 그냥 숫자입니다. 혼합 인덱스에서는 옛 벡터로 저장된 기억이 검색에서 체계적으로 밀려나고, 에이전트는 그 시기의 경험을 사실상 잊습니다. 데이터는 DB에 멀쩡히 있는데도요.

낯선 얘기가 아닙니다. OpenAI가 text-embedding-3 시리즈를 내놨을 때도 같았습니다. text-embedding-3-small은 ada-002와 같은 1536차원으로 설정할 수 있지만 두 공간은 호환되지 않아서, 갈아타려면 코퍼스 전체를 다시 임베딩해야 했습니다. 덤으로 유사도 점수의 분포 자체가 달라지므로, ada-002 기준으로 잡아 둔 컷오프 0.85 같은 임계값도 다시 캘리브레이션해야 합니다.

재임베딩이 부담스러운 규모라면 선택지는 세 가지입니다.

전략방법트레이드오프
전체 재임베딩백그라운드 잡으로 전 레코드를 새 모델로 다시 임베딩 후 컷오버가장 깔끔. 대신 코퍼스가 크면 비용·시간이 큼
이중 인덱스 (dual-index)마이그레이션 동안 v1·v2 필드를 병행, 질의도 두 모델로 각각 임베딩해 양쪽 검색 후 병합다운타임 없음. 질의 비용 2배, 병합 랭킹 필요
어댑터 (Drift-Adapter류)새 질의 벡터를 구공간으로 사상하는 가벼운 변환층 학습 (arXiv:2509.23471)재임베딩 회피. 근사이므로 품질 상한이 낮고, 변환층 관리가 늘어남

혼합 인덱스를 "일단 두고 천천히" 방치하는 것만은 피해야 합니다. 위 숫자가 보여 주듯, 그 상태는 과도기가 아니라 조용한 성능 저하가 상시화된 상태입니다.

5. 복구 — 원본이 없으면 고칠 수도 없다

업그레이드로 기억이 흐려졌다면 고치면 되지 않을까요? 논문은 복구를 두 종류로 나눕니다. 이 구분이 실무적으로 가장 값집니다.

  • raw-retained repair — 원본 대화·이벤트 히스토리가 남아 있어, 신모델이 원본에서 기억을 다시 뽑는 복구. 구노트가 빠뜨리거나 왜곡한 사실까지 되살릴 수 있습니다.
  • store-only repair — 원본은 지웠고 스토어만 남은 상태에서, 기존 노트를 신모델이 고쳐 쓰는 복구. 이미 노트에 없는 증거는 어떤 모델도 되살릴 수 없습니다. 흐린 사진을 다시 찍을 수는 없는 것과 같습니다.

당연한 얘기 같지만, 많은 메모리 시스템이 토큰 비용을 아끼려고 압축본만 남기고 원본을 버리는 설계를 택합니다. 이 결과는 그 설계의 숨은 비용을 보여 줍니다. 원본 히스토리는 스토리지 낭비가 아니라 다음 업그레이드 때 기억을 다시 구울 수 있는 원판입니다. 스토리지는 싸고, 잃어버린 맥락은 비쌉니다. Scroll 편에서 다룬 append-only 이벤트 로그 설계가 여기서도 빛을 발합니다 — 로그를 진실의 원천으로 두고 압축본을 파생물로 취급하면, 모델이 몇 번 바뀌어도 기억을 재생성할 수 있습니다.

6. 실전 — 안전한 모델 업그레이드 runbook

이제 종합해서, 메모리 있는 에이전트의 모델을 갈아 끼울 때의 절차를 만들어 봅시다. 핵심 원칙은 두 가지입니다. ① 기억 레코드마다 "누가 언제 무엇으로 썼는지"를 남긴다. ② 컷오버 전에 같은 기억을 새 모델로 읽혀 회귀를 측정한다.

먼저 메모리 레코드에 provenance(출처 정보) 메타데이터를 심습니다. 나중에 마이그레이션 대상을 골라내고, 문제가 생겼을 때 원인을 추적하는 기반입니다.

{{< highlight python >}} from dataclasses import dataclass, field from datetime import datetime, timezone @dataclass class MemoryRecord: content: str # 기억 본문 (노트/그래프 트리플 직렬화) kind: str # "note" | "kg_triple" | "raw_chunk" # ── provenance: 이게 없으면 마이그레이션 대상 선별이 불가능해진다 ── writer_model: str # 예: "claude-opus-4-8" embedding_model: str # 예: "text-embedding-3-small@1536" schema_version: str # 고정 스키마라면 그 버전 source_ref: str # 원본 이벤트 로그의 위치 (raw-retained repair의 생명줄) created_at: datetime = field( default_factory=lambda: datetime.now(timezone.utc)) def needs_reembedding(rec: MemoryRecord, current: str) -> bool: # 임베딩 버전이 다른 레코드 = 검색에서 밀려나는 중인 레코드 return rec.embedding_model != current {{< /highlight >}}

다음은 컷오버 게이트입니다. 배포 전에, 운영 스토어의 스냅샷을 새 reader로 읽혀 구 reader와 나란히 채점합니다. 논문의 교훈대로 벤치마크 점수가 아니라 내 스토어, 내 질의로 재야 합니다 — NOTES의 요동은 모델 조합마다 다르므로 남의 숫자는 참고가 안 됩니다.

{{< highlight python >}} def upgrade_gate(memory_snapshot, eval_queries, old_reader, new_reader, max_regression: float = 0.02): """같은 메모리 스토어를 두 모델로 읽혀 회귀를 측정하는 게이트. eval_queries: (질의, 기대 답) 쌍 — 실제 트래픽과 과거 장애에서 수집한 것. """ def score(reader): hits = sum( grade(reader.answer(q, memory_snapshot), expected) # exact/rubric 채점 for q, expected in eval_queries) return hits / len(eval_queries) old_acc, new_acc = score(old_reader), score(new_reader) if new_acc < old_acc - max_regression: # 컷오버 중단 → raw-retained repair(원본에서 재추출) 후 재시도 raise BlockUpgrade(f"memory regression: {old_acc:.3f} → {new_acc:.3f}") return {"old": old_acc, "new": new_acc} {{< /highlight >}}

7. 흔한 실수 · 팁

  • "메모리는 DB에 있으니 모델과 무관하다"는 착각. 이 글의 출발점입니다. 데이터가 모델 밖에 있어도, 그 데이터를 만든 것도 해석하는 것도 모델입니다. 결합은 저장 위치가 아니라 형식에 있습니다.
  • 업그레이드 게이트를 벤치마크 점수로 대신하기. 공개 벤치마크가 오른 모델도 내 구노트는 못 읽을 수 있습니다. NOTES의 요동이 조합마다 다르다는 게 논문의 요지입니다. 게이트는 내 스토어 스냅샷 + 실트래픽에서 수집한 질의로 돌리세요. 이런 회귀 스위트 만드는 법은 Promptfoo의 업그레이드 회귀 글과 에이전트 평가 편을 참고하세요.
  • 임베딩 버전 혼합을 "과도기"로 방치. 50/50 혼합 인덱스는 이득의 60%를 버리는 상태입니다. 마이그레이션 잡에 종료 기한을 박고, embedding_model 메타데이터로 잔여 구버전 레코드 수를 대시보드에 올리세요. 0이 되기 전까지는 끝난 게 아닙니다.
  • 유사도 임계값 재사용. 임베딩 모델이 바뀌면 점수 분포가 통째로 이동합니다. 구모델에서 튜닝한 컷오프 0.85는 새 모델에서 너무 빡빡하거나 너무 헐거울 수 있습니다. 검증 세트로 임계값을 다시 잡으세요.
  • 압축본만 남기고 원본 로그 삭제. raw-retained repair의 길을 스스로 닫는 결정입니다. 원본은 콜드 스토리지에라도 남기세요. 토큰 예산이 문제라면 컨텍스트에 안 올리면 될 뿐, 지울 이유는 없습니다.
  • reader와 judge를 동시에 업그레이드. 평가 채점용 judge 모델까지 같이 바꾸면 회귀가 모델 탓인지 잣대 탓인지 알 수 없게 됩니다. 모델-애그노스틱 레이어 편에서 다룬 judge pinning 그대로 — 게이트를 돌리는 동안 judge는 고정하세요.
  • 이 논문을 과신하는 것도 금물. 히스토리 48개, 10B 미만 모델 2종의 통제 실험입니다. 방향(형식별 이식성 차이, 혼합 인덱스의 손실)은 설득력 있지만, 숫자 자체를 프런티어 모델 조합에 그대로 이식할 수는 없습니다. 그래서 더더욱, 내 시스템의 숫자는 내 게이트로 재야 합니다.

8. 마무리 (TL;DR)

  • 모델 업그레이드는 코드 한 줄이 아니라 데이터 마이그레이션이다. 기억은 모델 밖에 있어도 모델의 언어로 쓰여 있다.
  • arXiv:2609.05339의 통제 실험: 고정 스키마 그래프(KG-fixed)는 writer swap에도 정확도 변화 ≈ 0, 모델이 압축한 노트(NOTES)는 +9.91/−13.28%p로 방향조차 예측 불가하게 요동.
  • 임베딩은 차원이 같아도 공간이 다르다. 전체 재임베딩은 +11.90%p, 50/50 혼합 인덱스는 +4.96%p — 혼합 방치는 이득의 60%를 버리는 것.
  • 복구는 원본이 있어야 가능하다(raw-retained repair). 압축본만 남기고 원본 로그를 지우면 어떤 신모델도 잃은 증거를 되살리지 못한다.
  • runbook: 레코드마다 writer_model·embedding_model·source_ref provenance를 남기고 → 내 스토어 스냅샷으로 섀도 평가 게이트 → 임베딩 백필(기한 있는) → 컷오버 + 임계값 재캘리브레이션 → 회귀 시 원본에서 재추출.
  • 이식성과 압축률은 트레이드오프다. 오래 살아남아야 하는 기억일수록 스키마 있는 형식으로, 원본과 함께 보관하라.
