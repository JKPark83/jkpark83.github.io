도입 — 같은 주에 정반대로 달린 두 흐름

이번 주 Hacker News에서 가장 뜨거웠던 에이전트 설계 논쟁은 모델 발표가 아니라 짧은 에세이 한 편에서 터졌습니다. Kevin Liao가 쓴 "Agents Don't Need Memory. They Need Documentation."(에이전트에게 필요한 건 기억이 아니라 문서다)는 약 350포인트와 200개가 넘는 댓글을 모으며 일주일 내내 회자됐습니다. 주장을 한 문장으로 줄이면 이렇습니다. "코딩 에이전트용 메모리 플러그인은 결국 옛 대화에 대한 RAG일 뿐이고, 에이전트가 정말 잘 쓰는 건 작업 전에 읽고 작업 후에 고쳐 두는 평범한 마크다운 문서 폴더다."

타이밍이 절묘했습니다. 같은 주 GitHub 트렌딩에서는 정반대 진영이 축포를 터뜨리고 있었거든요. 세션 활동을 통째로 기록해 다음 세션에 주입해 주는 메모리 레이어 claude-mem이 하루 600개가 넘는 스타를 쓸어 담았고(누적 약 9.6만 개), 에이전트 메모리 플랫폼 cognee(약 3.1만 개)와 메모리 인프라의 대표 주자 mem0(약 6.7만 개)도 나란히 주간 트렌딩에 올랐습니다. 2주 전 이 블로그에서 다룬 Hindsight 같은 '배우는 메모리'까지 포함하면, 생태계는 분명히 "에이전트에 기억을 달아 주자" 쪽으로 돈과 스타를 몰아 주고 있습니다. 그 한복판에서 "그 기억, 사실 필요 없다"는 글이 350포인트를 받은 겁니다.

흥미로운 건 댓글 창의 전선입니다. 문서 쪽 손을 든 사람들은 감사 가능성(auditability)과 디버깅 용이성을 들었고, 메모리 쪽은 문서만으로는 안 되는 장기 작업 사례를 들고 나왔습니다. 그리고 긴 논쟁 끝에 흐릿하게나마 "둘 다 쓰는 하이브리드가 답 아니냐"는 쪽으로 수렴했습니다. 오늘은 이 논쟁을 안주 삼아, 두 진영이 각각 무엇을 어떻게 저장하고 꺼내는지 기술적으로 뜯어 보고, 주니어 개발자가 당장 자기 에이전트에 적용할 수 있는 선택 기준까지 정리해 보겠습니다.

배경 — 에이전트는 왜 잊는가

논쟁을 따라가려면 먼저 "에이전트의 기억 상실"이 왜 구조적인 문제인지 알아야 합니다. LLM API는 상태가 없습니다(stateless). 모델이 무언가를 "기억"하는 유일한 공간은 이번 호출에 함께 보낸 컨텍스트 윈도우뿐입니다. 세션이 끝나면 그 컨텍스트는 통째로 증발합니다. 어제 세 시간 동안 에이전트와 함께 파고든 버그의 원인, 리팩터링하면서 내린 결정, "이 모듈은 건드리지 말자"던 합의 — 다음 세션의 모델은 아무것도 모릅니다.

그래서 "세션을 넘어 지식을 잇는" 해법이 필요한데, 계보가 크게 둘로 갈립니다.

  • 메모리 레이어(memory layer) — 대화와 작업 기록에서 중요한 내용을 추출하고, 임베딩(embedding, 텍스트를 의미 공간의 좌표로 바꾼 벡터)으로 저장해 뒀다가, 새 세션에서 유사도 검색으로 관련 조각을 찾아 컨텍스트에 주입합니다. mem0, claude-mem, cognee가 이 계열입니다.
  • 문서/컨텍스트 파일(docs-as-context) — 프로젝트 규칙과 결정 사항을 사람이 읽는 것과 같은 문서(AGENTS.md, CLAUDE.md, 스펙, 결정 기록)로 저장소에 넣어 두고, 에이전트가 작업 전에 읽고 작업 후에 직접 갱신하게 합니다. 예전에 다룬 AGENTS.md 컨벤션이 이 계열의 표준화 시도입니다.

비유하면 이렇습니다. 메모리 레이어는 회의 녹취록 전체를 검색 엔진에 넣어 두는 것이고, 문서는 회의가 끝날 때마다 위키의 결정 사항 페이지를 고쳐 두는 것입니다. 녹취록 검색은 자동이고 빠뜨리는 게 없어 보이지만, "그때 그렇게 말했다"와 "지금도 그게 맞다"는 다른 문제입니다. 위키는 손이 가지만, 열어 보면 지금 유효한 결론만 깔끔하게 남아 있습니다. 이 차이가 논쟁의 뿌리입니다.

문서 진영 — "메모리 플러그인은 옛 대화에 대한 RAG다"

Liao의 에세이가 겨냥하는 과녁은 명확합니다. 코딩 에이전트에 붙이는 메모리 플러그인의 실체는 지난 대화에 대한 RAG(Retrieval-Augmented Generation, 검색으로 찾은 자료를 컨텍스트에 붙여 주는 기법)라는 겁니다. 과거 세션을 조각내 임베딩하고, 새 작업이 시작되면 유사한 조각을 찾아 주입하는 구조 말이죠. 그는 이 구조의 문제를 다섯 가지로 정리합니다.

  1. 유사도 ≠ 정확성. 유사도 검색이 알려 주는 건 두 텍스트가 임베딩 공간에서 가깝다는 사실뿐입니다. 꺼내 온 스니펫이 맞는지, 아직도 유효한지, 정작 필요한 게 빠진 건 아닌지는 말해 주지 않습니다.
  2. 맥락 상실. 조각난 스니펫은 "왜 그렇게 결정했는지"라는 동기와 전후 사정을 잃어버립니다.
  3. 낡은 대화가 진실 행세. 코드는 계속 바뀌는데, 석 달 전 대화 조각이 현재의 사실처럼 주입됩니다.
  4. 모르는 건 검색할 수 없다. 에이전트는 자기가 뭘 놓치고 있는지 모르는 것에 대해서는 질의 자체를 만들 수 없습니다.
  5. 감사 불가. 수천 개의 임베딩이 쌓인 저장소는 사람이 열어서 검토할 수 없습니다. 무엇이 들어 있고 무엇이 잘못됐는지 아무도 모릅니다.

그가 내놓는 대안은 거창한 시스템이 아니라 루프의 교체입니다. 기존 에이전트 루프가 prompt → build → forget(시키고, 만들고, 잊는다)이라면, 이를 prompt → consult → build → update(시키면, 먼저 문서를 읽고, 만들고, 문서를 고친다)로 바꾸자는 겁니다. 에이전트는 지침·스펙·결정 기록·조사 노트·색인을 구조화된 폴더에 평문 마크다운으로 유지합니다. 벡터 저장소와 달리 이 문서들은 팀원이 읽을 수 있고, 고칠 수 있고, 커밋할 수 있고, 코드 리뷰처럼 diff로 감사할 수 있습니다.

어디서 많이 본 구조 아닌가요? 맞습니다. 좋은 시니어 개발자가 일하는 방식 그대로입니다. 작업 전에 설계 문서와 ADR(Architecture Decision Record, 아키텍처 결정 기록)을 읽고, 작업 후에 문서를 갱신합니다. Liao의 주장은 "에이전트에게 초능력(기억)을 달아 주려 하지 말고, 좋은 엔지니어의 습관(문서화)을 시켜라"로 요약할 수 있습니다.

HN 댓글에서 문서 진영이 특히 호응을 받은 지점도 5번, 감사 가능성이었습니다. 에이전트가 이상한 행동을 할 때 원인이 코드인지, 프롬프트인지, 석 달 묵은 메모리 조각인지 추적해 본 사람이라면 "저장소에 뭐가 들었는지 열어 볼 수 있어야 한다"는 말의 무게를 압니다. 반면 메모리 진영은 실전 반례를 들었습니다. 수 주에 걸친 장기 작업에서는 문서에 적기 애매한 세부 맥락(시도했다 실패한 접근, 사용자별 선호)이 산더미처럼 쌓이는데, 이걸 전부 문서로 관리하는 건 비현실적이라는 겁니다. 그래서 스레드의 잠정 결론은 하이브리드였습니다. 뒤에서 보겠지만, 이 하이브리드의 모양이 생각보다 구체적입니다.

메모리 진영 — claude-mem과 mem0는 실제로 뭘 하나

비판을 제대로 평가하려면 비판받는 쪽이 실제로 뭘 하는지 알아야 합니다. 이번 주 스타를 쓸어 담은 claude-mem부터 보겠습니다.

claude-mem은 Claude Code 등 에이전트 하네스의 라이프사이클 훅(hook)에 끼어듭니다. SessionStart, UserPromptSubmit, PostToolUse, Stop, SessionEnd 다섯 지점에서 세션 활동을 관찰로 기록하고, LLM으로 압축 요약을 만들어 SQLite(FTS5 전문 검색)와 Chroma 벡터 DB에 저장합니다. 새 세션이 시작되면 관련 컨텍스트를 자동 주입하고, mem-search 스킬로 "색인 → 타임라인 → 상세"의 점진적 탐색(progressive disclosure)도 지원합니다. 설치는 npx claude-mem install 한 줄이고 Claude Code 외에 Codex, Gemini, Copilot 등도 지원합니다. 설계만 보면 Liao가 비판한 "옛 대화에 대한 RAG"의 교과서적 구현이 맞습니다. 다만 하이브리드 검색(키워드+시맨틱)과 점진적 탐색으로 "유사도 상위 k개를 무지성 주입"보다는 한결 정교해졌습니다.

한편 mem0는 범용 메모리 인프라에 가깝습니다. 대화에서 기억할 가치가 있는 정보를 추출하고, 사용자/세션/에이전트 세 수준으로 저장하고, 시맨틱 검색·BM25 키워드 매칭·엔티티 연결을 조합해 검색하며, 엔티티를 그래프로 이어 회상 품질을 올립니다. 자사 측정 기준으로 장기 대화 벤치마크 LoCoMo에서 정확도 92.5, p50 지연 0.88초, 토큰 사용 7.0K를 보고했습니다(2026년 4월 알고리즘 기준, 이전 버전 대비 정확도 +21점).

여기서 공정하게 짚을 점이 있습니다. mem0가 내세우는 대표 사용처는 고객 지원 챗봇, 헬스케어 어시스턴트, 개인화가 필요한 대화형 제품입니다. "사용자가 이메일 후속 연락을 선호한다" 같은 사실은 문서 폴더에 적어 둘 성격의 정보가 아니라, 사용자별로 쌓이고 검색돼야 하는 정보입니다. 즉 Liao의 비판이 가장 아프게 꽂히는 영역은 코드베이스라는 '이미 구조화된 진실'이 존재하는 코딩 에이전트이고, 대화형 개인화 제품에서는 메모리 레이어가 여전히 자연스러운 답입니다. 논쟁을 "메모리는 항상 틀렸다"로 읽으면 과격한 오독이 됩니다.

수렴점 — Anthropic의 memory tool은 '파일'이다

그런데 이 논쟁에는 뜻밖의 제3자가 있습니다. Anthropic이 Claude API에 제공하는 공식 memory tool입니다. 이름은 "메모리"인데, 열어 보면 벡터 저장소가 아니라 파일 디렉터리입니다.

동작은 이렇습니다. 요청의 tools에 {"type": "memory_20250818", "name": "memory"}를 넣으면, Claude는 작업을 시작하기 전에 /memories 디렉터리를 먼저 확인하고, 작업하면서 배운 것을 파일로 기록하고, 다음 세션에서 그 파일들을 다시 읽어 이어 갑니다. 명령은 view, create, str_replace, insert, delete, rename — 파일 편집기와 같습니다. 저장은 클라이언트 쪽에서 여러분 애플리케이션이 수행하므로 저장 위치와 방식도 여러분이 통제합니다. 임베딩도, 유사도 검색도 없습니다. 모델이 자기 손으로 읽고, 쓰고, 고치는 평문 파일 묶음입니다.

심지어 memory tool을 켜면 API가 시스템 프롬프트에 자동으로 넣어 주는 지침은 이렇게 시작합니다. "항상 다른 일보다 먼저 메모리 디렉터리를 확인하라 … 컨텍스트가 언제든 리셋될 수 있다고 가정하고, 기록하지 않은 진행 상황은 잃는다고 생각하라." 어디서 본 루프죠? Liao의 consult → build → update와 사실상 같습니다. 공식 문서가 권하는 멀티세션 개발 패턴도 마찬가지입니다. 첫 세션(initializer)이 진행 로그와 기능 체크리스트 파일을 깔아 두고, 이후 세션은 그 파일을 읽으며 시작하고, 끝날 때 갱신합니다. 기능은 한 번에 하나씩, 끝까지 검증된 뒤에야 완료 표시를 합니다.

그래서 논쟁의 진짜 축은 "기억이 필요한가"가 아닙니다. 세션을 넘는 지식 이전은 모두가 필요하다고 동의합니다. 진짜 갈림길은 저장 형태와 꺼내는 방식입니다. ① 대화 로그를 자동으로 쌓고 임베딩 유사도로 꺼내는 검색형 기억이냐, ② 에이전트가 의도를 갖고 읽고 고치는 문서형 기억이냐. Liao의 에세이, Anthropic의 memory tool, HN의 하이브리드 합의는 코딩 에이전트에 한해 ②를 기본값으로 두는 쪽으로 수렴하고 있습니다.

이 수렴이 우연이 아닌 이유도 생각해 볼 만합니다. 코딩 에이전트의 "기억할 가치가 있는 것"은 대부분 이미 이름이 있습니다. 규칙은 AGENTS.md로, 결정은 ADR로, 진행 상황은 진행 로그로. 구조화할 그릇이 존재하는 도메인에서는 구조화된 문서가 이깁니다. 반대로 그릇이 없는 비정형 정보(사용자 취향, 수개월치 대화 뉘앙스)가 주인 도메인에서는 검색형 기억이 이깁니다. 도구 선택은 이 한 줄로 거의 정리됩니다.

실전 — 오늘부터 시작하는 docs-first 기억 설계

그럼 주니어 개발자가 당장 할 수 있는 것부터 해 봅시다. 거창한 플러그인 없이, 저장소에 문서 폴더 하나 만드는 것으로 시작합니다.

{{< highlight text >}} my-project/ ├── AGENTS.md # 에이전트용 README: 빌드·테스트 방법, 규칙, 금기 ├── docs/ │ ├── decisions/ # 결정 기록 (ADR): 왜 그렇게 했는지 한 건당 한 파일 │ │ ├── 0001-use-postgres.md │ │ └── 0002-no-orm.md │ ├── specs/ # 기능 스펙: 무엇을 만드는 중인지 │ └── notes/ # 조사 노트: 삽질 기록, 시도했다 버린 접근 └── PROGRESS.md # 진행 로그: 어디까지 했고 다음이 뭔지 {{< /highlight >}}

AGENTS.md는 공개 컨벤션(저장소 스타 약 2.5만 개)이 있어서 여러 하네스가 똑같이 읽어 갑니다. 핵심은 사람용 README에 쓰기엔 시시콜콜한, 그러나 에이전트가 매번 틀리는 것들을 적는 겁니다.

{{< highlight markdown >}} # AGENTS.md ## 빌드 & 테스트 - 패키지 매니저는 pnpm만 사용 (npm 금지 — lockfile이 깨진다) - 테스트: `pnpm test` / 단일 파일: `pnpm vitest run ` ## 작업 규칙 - 작업 전 `PROGRESS.md`와 `docs/decisions/`를 먼저 읽을 것 - DB 스키마 변경은 반드시 마이그레이션 파일로 (직접 ALTER 금지) ## 작업 후 - 새로 내린 결정은 `docs/decisions/`에 ADR로 기록 - `PROGRESS.md`의 '다음 할 일'을 갱신하고 끝낼 것 {{< /highlight >}}

포인트는 마지막 섹션입니다. 읽기(consult)만 시키고 끝내면 반쪽짜리입니다. "작업 후 문서를 갱신하라"를 명시해야 update 단계가 생기고, 그래야 다음 세션이 더 똑똑해지는 선순환이 돕니다. 문서가 갱신되는지는 리뷰에서 코드와 함께 diff로 확인하면 됩니다. 이것이 벡터 저장소에서는 불가능했던, 문서형 기억의 감사 가능성입니다.

API로 직접 에이전트를 만들고 있다면 Anthropic memory tool로 같은 패턴을 구현할 수 있습니다. Python SDK에는 로컬 파일시스템 구현체가 들어 있어서 몇 줄이면 됩니다.

{{< highlight python >}} import anthropic from anthropic.tools import BetaLocalFilesystemMemoryTool client = anthropic.Anthropic() # ./memory 디렉터리가 세션을 넘어 살아남는 '문서형 기억'이 된다 memory = BetaLocalFilesystemMemoryTool(base_path="./memory") runner = client.beta.messages.tool_runner( model="claude-opus-5-5", max_tokens=2048, messages=[{"role": "user", "content": "어제 하던 결제 모듈 리팩터링 이어서 진행해 줘."}], tools=[memory], # Claude가 먼저 /memories를 확인하고 시작한다 ) print(runner.until_done().content) {{< /highlight >}}

모델은 view로 메모리 디렉터리를 확인하고, 진행하면서 create/str_replace로 파일을 고칩니다. 핸들러가 클라이언트 쪽에서 돌기 때문에 경로 검증은 여러분 책임입니다. /memories/../../secrets.env 같은 경로 탈출(path traversal)을 반드시 막아야 합니다(SDK 제공 구현체를 쓰면 기본 처리됩니다).

마지막으로 선택 기준을 결정 트리로 정리합니다.

흔한 실수 · 팁

  • consult만 있고 update가 없는 루프. 문서를 읽게만 하고 고치게 하지 않으면, 문서는 한 달 만에 Liao가 비판한 "낡은 대화"와 똑같은 거짓말쟁이가 됩니다. "작업 후 문서 갱신"을 지침에 명시하고, 리뷰에서 문서 diff를 코드와 함께 보세요.
  • 문서 비대화. 모든 것을 적으면 문서도 컨텍스트 로트를 일으킵니다. AGENTS.md는 "에이전트가 자주 틀리는 것"만, 결정 기록은 "번복 비용이 큰 결정"만. 지난 주 다룬 것처럼 컨텍스트는 유한 자원입니다.
  • 메모리 레이어를 측정 없이 켜기. 자동 주입되는 컨텍스트는 토큰 비용이자 품질 변수입니다. 켜기 전후로 세션당 토큰과 작업 성공률을 비교하고, 무엇이 주입되는지 샘플링해서 열어 보세요.
  • 기억을 신뢰 경계 안에 두기. 자동으로 쌓이는 기억은 오염 공격(memory poisoning)의 표적이 됩니다. 외부 입력(이슈, 웹 검색 결과)이 섞여 들어간 기억이 다음 세션의 "사실"로 주입되는 경로를 점검하세요. 문서형 기억도 PR 리뷰 없이 자동 커밋하면 같은 문제가 생깁니다.
  • memory tool 핸들러의 경로 검증 생략. 클라이언트 사이드 파일 조작이므로 ../ 탈출, URL 인코딩된 탈출(%2e%2e%2f)을 막아야 합니다. 직접 구현하지 말고 SDK 제공 구현체부터 쓰세요.
  • "문서 vs 메모리"를 종교 전쟁으로 읽기. 결론은 용도 분리입니다. 구조화 가능한 프로젝트 지식은 문서로, 장기 작업 상태는 파일형 메모리로, 비정형 개인화는 검색형 레이어로. HN 스레드의 하이브리드 합의도 이 모양이었습니다.

마무리 (TL;DR)

  • 이번 주 HN 350포인트 에세이의 주장: 코딩 에이전트용 메모리 플러그인은 옛 대화에 대한 RAG이고, 유사도 검색은 "가깝다"만 보장할 뿐 맞는지·최신인지·빠졌는지는 모른다. 대안은 prompt → consult → build → update 루프와 평문 문서 폴더.
  • 같은 주 메모리 진영은 전성기였습니다. claude-mem(약 9.6만★)은 훅 5지점에서 세션을 기록해 SQLite FTS5 + Chroma로 쌓고, mem0(약 6.7만★)는 추출·저장·하이브리드 검색·그래프로 LoCoMo 92.5를 보고합니다. 개인화가 핵심인 대화형 제품에서는 여전히 검색형 메모리가 자연스러운 답입니다.
  • 뜻밖의 수렴점: Anthropic의 공식 memory tool은 벡터 저장소가 아니라 /memories 디렉터리의 평문 파일이고, 자동 주입되는 프로토콜도 "먼저 읽고, 기록하며 일하라"는 Liao의 루프와 같습니다.
  • 논쟁의 진짜 축은 "기억이 필요한가"가 아니라 저장 형태와 꺼내는 방식: 검색형(자동 축적 + 유사도 주입) vs 문서형(의도적 읽기 + 직접 갱신). 코딩 에이전트처럼 지식을 구조화할 그릇이 있는 도메인에서는 문서형이 기본값이 되어 가고 있습니다.
  • 오늘 시작할 것: 저장소에 AGENTS.md + docs/decisions/ + PROGRESS.md를 만들고, "작업 전 읽기 · 작업 후 갱신"을 지침에 박아 넣고, 문서 diff를 코드 리뷰에 포함하기. 무엇이 주입되는지 볼 수 없는 기억은 쓰지 않기.
