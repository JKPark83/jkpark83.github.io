1. 도입 — 연습 문제집과 시험지가 다르다

고전 ML 엔지니어링에는 유명한 함정이 하나 있습니다. train-serve skew — 학습 파이프라인에서 만든 피처와 서빙 파이프라인에서 만든 피처가 미묘하게 달라서, 오프라인 지표는 좋은데 실전에서는 모델이 무너지는 현상입니다. 원인은 늘 같습니다. 학습 환경과 배포 환경을 따로 만들었기 때문입니다.

2026년의 에이전트 RL에서 이 문제가 그대로 재현되고 있습니다. RL로 에이전트를 훈련하려면 에이전트를 트레이닝 프레임워크 안에서 돌려야 하는데, 실제 배포용 에이전트는 하네스(harness) — 컨텍스트 관리, 도구 실행, 서브에이전트, 컴팩션까지 얹힌 복잡한 실행 껍데기 — 위에서 돕니다. 이걸 트레이너 안에 통째로 이식하기는 어려우니, 다들 학습용으로 단순화한 '간이 에이전트'를 새로 만듭니다. 그리고 그 간이 에이전트로 훈련한 가중치를, 전혀 다르게 생긴 진짜 하네스에 얹어 배포합니다. 연습은 문제집으로 하고 시험은 다른 시험지로 보는 셈입니다.

이번 주(8월 마지막 주) 이 문제가 제대로 화두에 올랐습니다. Microsoft가 arXiv에 올린 Agent Lightning v1.0: Towards Harnessed Agentic RL이 "학습은 에이전트의 실제 운영 환경 안에서 일어나야 한다 — 아니면 배포할 것과 다른 무언가를 훈련하게 된다"는 메시지로 X에서 널리 회자됐고(Rohan Paul의 정리 스레드), The New Stack이 플랫폼 엔지니어 관점에서 받아썼습니다. 같은 주에 vLLM 블로그에는 SkyRL의 트레이너–추론 엔진 불일치를 없애는 IsoExec 글(2026-08-21)이 올라왔습니다. 결이 같은 이야기입니다. 학습에 쓰는 것과 배포에 쓰는 것을 일치시켜라.

이 글은 Agent Lightning v1.0을 재료 삼아, "하네스째 학습시킨다"는 게 정확히 무슨 뜻이고, 그게 왜 공짜가 아닌지 — retokenization drift부터 엔진 간 확률 불일치까지 — 를 뜯어봅니다.

이 글에서 얻어 갈 것. ① 전통 agentic RL과 harnessed agentic RL의 구도 차이, ② 프록시 하나로 기존 에이전트를 코드 수정 없이 훈련 루프에 넣는 방법, ③ 문자열로 학습 데이터를 만들면 안 되는 이유(retokenization drift), ④ 같은 가중치인데 트레이너와 vLLM이 다른 확률을 내놓는 문제와 처방, ⑤ 6K 샘플로 SWE-bench Verified를 14.6%p 올린 숫자를 읽는 법.

2. 배경 — agentic RL과 하네스, 딱 필요한 만큼만

따라오는 데 필요한 최소한만 정리합니다.

agentic RL은 에이전트를 강화학습으로 개선하는 것입니다. 에이전트가 과제를 하나 받아 여러 턴에 걸쳐 도구를 부르고 최종 결과를 내면 — 이 한 판을 롤아웃(rollout)이라 합니다 — 채점기가 보상(reward)을 매깁니다. 코딩이라면 "패치가 테스트를 통과했는가"처럼 기계적으로 검증 가능한 보상(RLVR)을 주로 씁니다. 같은 과제로 롤아웃을 여러 개 만들어 잘한 판의 행동은 확률을 올리고 못한 판은 내리는 식으로 가중치를 갱신합니다(GRPO가 대표적입니다). 환경이 왜 병목인지는 예전 글에서 다뤘으니, 여기서는 "롤아웃을 만들고 → 보상을 매기고 → 가중치를 갱신하는 루프"라는 것만 기억하면 됩니다.

하네스(harness)는 모델을 감싸고 실행을 굴리는 껍데기입니다. 시스템 프롬프트, 도구 목록과 실행기, 컨텍스트 압축, 재시도, 서브에이전트 — Claude Code 같은 코딩 에이전트에서 모델 밖의 전부입니다. 지난주 글에서 봤듯 하네스는 성능을 좌우하는 변수이고, 최근 담론은 "하네스도 설계·학습의 대상"으로 옮겨 가고 있습니다.

문제는 이 둘을 합칠 때 생깁니다. 전통적인 agentic RL 프레임워크에서는 트레이너가 환경 상호작용 루프를 소유합니다. 롤아웃 생성부터 가중치 갱신까지 트레이너가 지휘하므로, 에이전트 로직을 트레이너가 이해하는 형태로 다시 구현해야 합니다. 그 결과가 두 가지 비용입니다.

  • 이식 비용. LangChain이든 직접 짠 루프든, 기존 에이전트를 트레이닝 프레임워크의 인터페이스에 맞춰 다시 짜야 합니다. 도구 하나, 프롬프트 한 줄 바뀔 때마다 두 벌을 관리합니다.
  • 불일치 비용. 이식본은 필연적으로 단순해집니다. 진짜 하네스에 있는 컨텍스트 압축, 멀티 에이전트 협업, 에러 복구가 빠진 채 훈련되면, 모델이 배운 분포와 배포 시 마주칠 분포가 어긋납니다. 훈련 지표는 오르는데 실전 체감은 그대로인 이유가 여기 있는 경우가 많습니다.

3. harnessed agentic RL — 루프의 주인을 바꾸다

Agent Lightning의 답은 구도를 뒤집는 것입니다. 에이전트를 트레이너 안으로 이식하는 게 아니라, 배포 하네스가 평소처럼 루프를 소유한 채 그대로 돌고, 트레이너는 그 뒤에서 관찰만 합니다. 논문은 이 패러다임을 harnessed agentic RL — 배포 시점 하네스가 포스트 트레이닝에 직접 참여하는 방식 — 이라 부릅니다.

동작을 순서대로 풀면 이렇습니다.

  1. 하네스(에이전트)는 평소처럼 OpenAI 호환 API로 모델을 부릅니다. 다른 점은 단 하나, base_url이 Agent Lightning의 프록시(Gateway, LLMProxy)를 가리킨다는 것뿐입니다.
  2. 프록시는 요청을 실제 추론 엔진(vLLM 등)에 전달하면서, 오가는 모든 것 — 프롬프트, 응답, 토큰 ID, logprob — 을 가로채 기록하고, 어떤 롤아웃의 몇 번째 시도인지 ID를 붙여 저장소에 쌓습니다.
  3. 롤아웃이 끝나면 채점기가 보상을 매기고, 트레이너는 쌓인 요청–응답 쌍 시퀀스를 학습 샘플로 바꿔 GRPO 같은 알고리즘으로 가중치를 갱신합니다.
  4. 갱신된 가중치가 추론 엔진에 반영되고, 다음 롤아웃부터 새 모델이 응답합니다. 루프 반복.

에이전트 입장에서 보면 자기가 훈련 중인지도 모릅니다. 그냥 평소처럼 일하고 있을 뿐이고, 훈련은 그 뒤에서 일어납니다. 원조 Agent Lightning 논문(2025)이 이 분리를 Training-Agent Disaggregation이라 불렀는데 — 무거운 LLM 생성·학습과 가볍고 다양한 애플리케이션 로직을 떼어 놓는 설계 — v1.0은 여기서 한 발 더 나가 "간이 에이전트조차 만들지 말고 진짜 하네스로 훈련하라"를 기본값으로 삼았습니다. GitHub 저장소(스타 약 1.7만 개)의 표현을 빌리면 코어는 약 3,500줄의 Python이고, LangChain·OpenAI Agents SDK·AutoGen 등 어떤 프레임워크로 짠 에이전트든 거의 코드 수정 없이 붙습니다.

4. 공짜가 아니다 — 다섯 가지 엔지니어링 함정

여기까지 들으면 "프록시 하나 끼우면 끝이네"싶지만, 트레이너가 루프의 통제권을 내려놓는 순간 학습 데이터 만들기가 갑자기 어려워집니다. v1.0 논문이 정면으로 다루는 다섯 가지를 하나씩 봅니다. 이 목록은 그대로 "내가 직접 만든다면 어디서 데일까"의 체크리스트이기도 합니다.

4-1. Retokenization drift — 같은 문자열, 다른 토큰

가장 유명한 함정이라 먼저 자세히 봅니다. RL 학습은 문자열이 아니라 토큰 ID 시퀀스 위에서 일어납니다. "이 토큰을 뽑을 확률을 올려라/내려라"가 갱신의 단위이기 때문입니다. 그런데 하네스는 OpenAI 호환 API로 모델을 부르고, 이 API는 전통적으로 문자열만 돌려줬습니다. 모델이 생성한 토큰들은 문자열로 풀어서(detokenize) 전달되고, 학습하려면 그 문자열을 다시 토큰으로 쪼개야(retokenize) 합니다.

문제는 같은 문자열을 만드는 토큰 분할이 하나가 아니라는 것입니다. 한국어로 비유하면 "아버지가방에들어가신다"를 어디서 끊어 읽느냐의 문제입니다. BPE 토크나이저에서 예컨대 self-improving이라는 출력은 생성 시 [self][-impro][ving]이었는데 재토크나이즈하면 [self][-][improving]이 될 수 있습니다. 문자열은 동일하니 눈으로는 못 잡습니다. 하지만 학습은 이제 모델이 실제로 뽑은 적 없는 토큰열에 대해 확률을 갱신합니다. 이 어긋남이 retokenization drift이고, 멀티턴 에이전트에서는 턴마다 누적되며 학습을 조용히 오염시킵니다.

처방은 명확합니다. 문자열이 아니라 토큰 ID를 왕복시키는 것입니다. Agent Lightning 팀과 vLLM이 함께 만든 확장이 그것으로, vLLM의 OpenAI 호환 엔드포인트에 "return_token_ids": true를 넘기면 응답에 프롬프트와 출력의 실제 토큰 ID(prompt_token_ids, token_ids)가 함께 옵니다(vLLM 블로그: No More Retokenization Drift). 프록시는 이 값을 트레이스에 남기고, 트레이너는 재토크나이즈 없이 그 토큰열을 그대로 씁니다.

4-2. 샘플 병합(sample merging) — 롤아웃 하나에 LLM 호출은 여러 번

에이전트 롤아웃 하나는 LLM 호출 한 번이 아닙니다. 계획 세우기, 도구 호출 10번, 요약 한 번 — 수십 번의 요청–응답 쌍이 쌓입니다. 게다가 멀티턴 대화는 이전 턴 전체를 프롬프트로 다시 포함하므로, 호출들끼리 앞부분(prefix)이 겹칩니다. 이걸 호출 단위로 흩어 별개 샘플로 취급하면 겹치는 프리픽스가 중복 학습되고, 하나의 시퀀스로 합치려면 어디까지가 모델이 만든 토큰이고 어디가 하네스가 끼워 넣은 토큰(도구 결과, 시스템 프롬프트)인지 정확히 가려 loss 마스크를 씌워야 합니다. 하네스가 중간에 컨텍스트를 압축하거나 메시지를 재배열했다면 단순 이어붙이기로는 안 되는, v1.0이 공들여 다루는 지점입니다.

4-3. Advantage 배분 — 보상은 하나, 행동은 수십 개

보상은 대개 롤아웃이 다 끝난 뒤에 하나 옵니다("패치가 테스트를 통과했다"). 그런데 갱신해야 할 LLM 호출은 수십 개입니다. 성공한 롤아웃의 모든 호출이 잘한 걸까요? 초반에 삽질하다 마지막에 만회했다면요? 이 신용 배분(credit assignment) 문제를 원조 논문은 LightningRL이라는 계층적 알고리즘으로 다뤘고 — 임의 에이전트가 만든 궤적을 학습 가능한 전이(transition)들로 분해합니다 — v1.0은 이를 하네스가 만든 지저분한 실제 궤적에서도 안정적으로 계산하는 문제로 확장합니다.

4-4. Loss 정규화 — 길이가 제각각인 샘플들

호출마다 출력 길이가 다르고 롤아웃마다 호출 수가 다릅니다. 이대로 평균 내면 긴 응답·긴 롤아웃이 gradient를 지배하거나, 반대로 토큰 단위 정규화가 짧은 응답을 과대평가합니다. 배치 안에서 무엇으로 나눌지(토큰 수, 시퀀스 수, 롤아웃 수)는 사소해 보여도 학습 안정성을 좌우하는 선택이고, 논문이 명시적으로 짚는 네 번째 함정입니다.

4-5. 백엔드 스케줄링 — 롤아웃은 길고, 가중치는 계속 바뀐다

에이전트 롤아웃은 몇 분씩 걸리고 병렬로 수십 개가 돕니다. 그 사이 트레이너는 가중치를 갱신하고 싶어 합니다. 어떤 롤아웃이 어떤 버전의 가중치로 생성됐는지 추적하지 않으면, 옛 정책이 만든 데이터를 새 정책의 것인 양 학습하는 의도치 않은 off-policy(뒤에서 다시 나옵니다)가 생깁니다. 생성용 GPU와 학습용 GPU 사이에서 가중치를 언제 어떻게 동기화할지 — 백엔드 스케줄링 — 까지가 프레임워크의 몫입니다.

5. 또 하나의 불일치 — 트레이너와 추론 엔진은 다른 확률을 말한다

하네스와 트레이너를 일치시켜도 불일치가 하나 더 남습니다. 이번엔 시스템 계층입니다. 롤아웃은 추론에 최적화된 엔진(vLLM, SGLang)이 만들고, gradient 계산은 학습 엔진(FSDP, Megatron)이 합니다. 같은 체크포인트, 같은 입력인데도 두 엔진이 내놓는 다음 토큰 확률분포가 미묘하게 다릅니다. 커널 구현, 연산 순서, 정밀도 처리가 다르기 때문입니다.

이게 왜 문제일까요? GRPO류 알고리즘은 "지금 정책이 뽑은 샘플"이라는 전제(on-policy) 위에 서 있습니다. 그런데 샘플은 vLLM의 분포에서 나왔고 갱신은 FSDP의 분포 기준으로 하니, 전제가 조용히 깨집니다 — 문헌에서 말하는 암묵적 off-policy입니다(On the Rollout-Training Mismatch in Modern RL Systems). 티끌 같은 확률 차이가 긴 시퀀스와 수천 스텝에 걸쳐 누적되면 학습이 불안정해지거나 붕괴합니다. 처방은 두 갈래입니다.

처방아이디어예시
알고리즘으로 보정두 분포의 확률 비율로 gradient를 재가중하는 중요도 샘플링(importance sampling). 극단값은 잘라내거나(TIS) 마스킹(MIS)해 분산을 통제TIS/MIS — 최근 RL 프레임워크 다수가 옵션으로 내장 (ms-swift 문서)
시스템으로 제거두 엔진의 연산을 정렬해 애초에 같은 확률이 나오게 만들기(truly on-policy)SkyRL의 IsoExec — 트레이너·추론의 실행을 통일해 불일치를 제거 (vLLM 블로그, 2026-08-21)

junior 입장에서 기억할 것은 하나입니다. 불일치는 진단부터. 같은 시퀀스에 대해 추론 엔진이 기록한 logprob과 학습 엔진이 다시 계산한 logprob의 차이를 학습 내내 지표로 찍으세요. 이 차이가 커지는데 loss만 보고 있으면, 원인 모를 학습 붕괴를 "하이퍼파라미터 탓"으로 돌리며 며칠을 태우게 됩니다. 프록시가 logprob을 트레이스에 남기는 이유가 바로 이것입니다.

6. 숫자 읽기 — 6K 샘플로 SWE-bench +14.6%p

이제 결과입니다. 논문의 대표 실험은 코딩 에이전트입니다. Qwen3.5-9B를 실제 하네스째 RL로 훈련했더니 SWE-bench Verified 점수가 41.8%에서 56.4%로, 14.6%p 올랐습니다. 눈여겨볼 건 비용입니다. 학습 샘플 6천 개와 "modest compute"로 얻은 수치이고, 데이터 정제 파이프라인과 학습 스크립트를 오픈소스 데이터·모델 기반으로 전부 공개해 재현 가능하게 했습니다. 명령 수행·검색·코딩 세 종류의 에이전트로 평가했습니다.

읽을 때 걸러야 할 것도 있습니다. 첫째, 이 수치는 "그 하네스에서 훈련하고 그 하네스에서 평가한" 결과입니다. harnessed RL의 주장 자체가 "훈련·배포 환경을 일치시키면 이만큼 나온다"이므로 당연한 설계지만, 다른 하네스로 옮기면 이득이 얼마나 보존되는지는 별개 질문입니다. 둘째, 9B라는 작은 모델의 결과입니다. 작은 모델일수록 도메인 특화 RL의 개선 폭이 크게 나오는 경향이 있으니, 프론티어급에서 같은 폭을 기대하긴 어렵습니다. 그럼에도 "간이 에이전트로 훈련해 배포에서 잃어버리던 이득을, 하네스 일치로 회수한다"는 방향성의 증거로는 충분히 인상적입니다.

7. 실전 — 내 에이전트에 적용한다면

전체 그림을 코드 감각으로 잡아 봅니다. 먼저 에이전트 쪽 — 바꿀 것은 정말 base_url뿐입니다.

{{< highlight python >}} # 기존 에이전트 코드 (개념 예시) — 하네스 로직은 그대로 둡니다 import os from openai import OpenAI client = OpenAI( base_url=os.environ["AGL_PROXY_URL"], # 훈련 시: Agent Lightning 프록시 api_key="dummy", # 배포 시: 실제 엔드포인트 ) # 이하 평소의 에이전트 루프 그대로. # 프록시가 요청-응답·토큰 ID·logprob을 가로채 롤아웃 ID와 함께 기록합니다. resp = client.chat.completions.create(model="policy", messages=messages, tools=tools) {{< /highlight >}}

다음은 프록시 뒤에서 일어나는 일의 핵심, 토큰 ID 직접 반환입니다. vLLM 엔드포인트를 직접 때려 보면 감이 옵니다.

{{< highlight python >}} import requests resp = requests.post("http://localhost:8000/v1/chat/completions", json={ "model": "Qwen/Qwen3.5-9B", "messages": [{"role": "user", "content": "버그 원인을 찾아 줘"}], "logprobs": True, "return_token_ids": True, # vLLM 확장 — 실제 생성 토큰 ID를 함께 반환 }) data = resp.json() # 문자열을 재토크나이즈하지 않고, '엔진이 실제로 만든' 토큰열을 그대로 확보 # (필드 위치는 vLLM 버전에 따라 응답 최상위 또는 choice 안에 있습니다) prompt_ids = data.get("prompt_token_ids") output_ids = data["choices"][0].get("token_ids") {{< /highlight >}}

마지막으로 트레이너가 보는 세상입니다. 하네스가 뭘 하든, 트레이너에게 도착하는 건 롤아웃별로 묶인 요청–응답 쌍의 시퀀스와 보상 하나입니다.

{{< highlight python >}} # 트레이너 관점의 롤아웃 (의사코드) rollout = { "rollout_id": "swe-1042/attempt-3", "reward": 1.0, # 패치가 테스트 통과 "calls": [ # 하네스가 만든 LLM 호출들 (시간순) {"prompt_ids": [...], "output_ids": [...], "logprobs": [...]}, {"prompt_ids": [...], "output_ids": [...], "logprobs": [...]}, # ... 도구 결과·시스템 프롬프트 토큰은 loss 마스크로 제외 ], } # 이후: 샘플 병합 → advantage 배분 → loss 정규화 → 가중치 갱신 → 엔진에 반영 {{< /highlight >}}

직접 굴려 보고 싶다면 공식 문서의 튜토리얼부터 시작하면 됩니다. RL만이 아니라 자동 프롬프트 최적화, SFT 같은 다른 알고리즘도 같은 트레이스 위에서 지원하므로, "일단 트레이스 수집부터 붙여 두는" 것만으로도 가치가 있습니다. 무엇을 관찰할 수 있어야 하는지의 감각은 에이전트 관측성 글과 이어집니다.

8. 흔한 실수 · 팁

  • 학습용 간이 에이전트를 새로 만드는 것. 이 글의 요지 그대로입니다. "훈련용으로 간단한 버전을 하나 만들자"는 그 결정이 train-serve skew의 시작입니다. 훈련이 필요해질 것 같으면, 하네스의 LLM 호출을 처음부터 base_url 주입이 가능하게 짜 두세요.
  • 문자열만 로깅하고 토큰 ID·logprob을 버리는 것. 트레이스에 문자열만 남기면 나중에 학습 데이터로 쓸 때 재토크나이즈를 피할 수 없습니다. 지금 학습 계획이 없어도, 수집 시점에 토큰 ID와 logprob을 함께 남기는 건 비용이 거의 안 듭니다.
  • 프록시를 우회하는 호출을 놓치는 것. 하네스 구석의 요약 호출, 서브에이전트, 임베딩 호출이 프록시를 안 거치면 트레이스에 구멍이 납니다. 구멍 난 롤아웃은 샘플 병합 단계에서 조용히 어긋납니다. 모든 LLM 트래픽이 한 곳을 지나가게 만드세요.
  • 롤아웃을 temperature=0으로 만드는 것. RL은 잘한 판과 못한 판의 차이에서 배웁니다. 탐색 없이 같은 행동만 반복하면 배울 신호가 없습니다. 반대로 훈련 때의 샘플링 설정과 배포 때의 설정이 크게 다르면 그것도 또 하나의 skew입니다.
  • logprob 차이를 안 찍는 것. 5장의 결론 반복입니다. 추론 엔진의 logprob과 학습 엔진의 재계산 logprob 차이는 가장 싼 조기 경보입니다. 학습이 이유 없이 불안정하면 하이퍼파라미터보다 이 지표를 먼저 보세요.
  • 평가만 옛날 방식으로 하는 것. 훈련을 하네스째 했다면 평가도 같은 하네스로 해야 비교가 성립합니다. 에이전트 평가의 함정은 evals 글에서 다뤘습니다.

9. 마무리 (TL;DR)

  • agentic RL의 고질병: 학습은 트레이너 안의 간이 에이전트로, 배포는 진짜 하네스로 — ML의 고전 문제 train-serve skew의 에이전트판입니다.
  • harnessed agentic RL은 구도를 뒤집습니다. 배포 하네스가 상호작용 루프를 소유한 채 평소처럼 돌고, 트레이너는 프록시 뒤에서 요청–응답 쌍만 관찰해 학습합니다. Microsoft의 Agent Lightning v1.0(arXiv:2608.17528)이 이번 주 이 개념을 밀어 올렸습니다.
  • 에이전트 쪽 수정은 사실상 base_url 교체뿐. 프록시가 토큰 ID·logprob·롤아웃 ID를 기록해 학습 데이터를 만듭니다.
  • 공짜는 아닙니다. retokenization drift(문자열 왕복이 토큰열을 바꿈 — vLLM return_token_ids로 차단), 샘플 병합, advantage 배분, loss 정규화, 백엔드 스케줄링이 프레임워크가 풀어야 할 다섯 함정입니다.
  • 남는 불일치 하나 더: 같은 가중치라도 추론 엔진과 학습 엔진의 확률이 달라 암묵적 off-policy가 됩니다. 중요도 샘플링(TIS/MIS)으로 보정하거나 IsoExec처럼 실행을 정렬해 제거하고, 무엇보다 logprob 차이를 상시 모니터링하세요.
  • 결과: Qwen3.5-9B가 6K 샘플의 RL만으로 SWE-bench Verified 41.8% → 56.4%(+14.6%p). 작은 모델·동일 하네스 평가라는 조건은 감안해 읽되, "훈련한 그 에이전트를 그대로 배포한다"는 방향의 증거로는 충분합니다.
