에이전트에게 "이 레포 정리해 줘"라고 했더니, 정말로 rm -rf를 쳤습니다. 이번엔 맞는 디렉터리였을까요?

— 에이전트가 말만 하던 시절은 끝났습니다. 이제 에이전트는 행동합니다. 문제는 그 행동을 무엇으로 막느냐는 것.

1. 왜 지금 '툴 호출 가드레일'이 화제인가

요즘 에이전트는 답만 내놓지 않습니다. 셸 명령을 치고, 파일을 지우고, DB에 쿼리를 날리고, 결제 API를 부르고, 메일을 보냅니다. 이런 "행동"을 하는 통로가 바로 툴 호출(tool call)입니다. 모델이 "이 도구를 이런 인자로 부르고 싶다"고 JSON을 뱉으면, 우리 코드가 그걸 받아 실제 함수를 실행하죠. 편리합니다. 그런데 여기엔 조용한 전제가 하나 있습니다 — 그 인자를 정하는 게 실제로는 누구인가.

2026년 6월 30일, 보안 업체 Adversa AI가 공개한 GuardFall 연구가 이 불안을 정확히 찔렀습니다. 널리 쓰이는 오픈소스 코딩·컴퓨터 사용 에이전트 11개 중 10개가, 위험한 셸 명령을 막겠다고 붙여 둔 차단 장치를 그대로 우회당했습니다. Aider, Cline, Goose, Open Interpreter, OpenHands, opencode, Plandex, Roo-Code, SWE-agent, NousResearch Hermes — 이름만 대면 아는 도구들이 줄줄이 뚫렸고, 방어에 성공한 건 오직 하나(Continue)뿐이었습니다.

더 뼈아픈 건 공격 기법이 전혀 새롭지 않았다는 점입니다. $IFS로 공백을 대신 넣고, 따옴표를 없애고, 명령 치환(command substitution)이나 base64 디코딩으로 문자열을 비틀면, "차단 목록"에 걸리지 않고 셸에 도달합니다. 전부 수십 년 된 셸 트릭이죠. 요점은 분명합니다. "위험한 문자열을 목록에서 찾아 막는다"는 접근 자체가 구조적으로 틀렸다는 것입니다.

그래서 이번 주 실무 담론의 초점은 "더 좋은 블록리스트"가 아니라, 에이전트의 모든 행동을 한 곳에서 결정론적으로 판정하는 계층 — 흔히 컨트롤 플레인(control plane) 또는 행동 가드레일(action guardrail)이라 부르는 것 — 으로 옮겨 갔습니다. Microsoft·OpenAI·Anthropic·LangChain이 약속이라도 한 듯 "툴 호출 승인/정책" 기능을 앞다퉈 정식화한 것도 같은 맥락이고요. 이 글은 그 밑바닥, 즉 에이전트가 '무엇을 하는가'를 어떻게 통제하는가를 junior 개발자 눈높이에서 코드로 풀어 봅니다.

2. 배경: 두 종류의 가드레일 — 입력 vs 행동

먼저 용어를 정리하겠습니다. "가드레일(guardrail)"은 에이전트가 궤도를 벗어나지 않게 막는 안전장치를 통칭하는데, 크게 두 자리에 놓입니다. 자리를 헷갈리면 엉뚱한 곳을 지키게 됩니다.

  • 입력 가드레일(input guardrail) — 모델에게 들어가는 것을 검사합니다. 프롬프트 인젝션(prompt injection) 탐지, 개인정보 마스킹, 유해 입력 필터 같은 것들이죠. "나쁜 지시가 모델을 조종하지 못하게" 막는 자리입니다.
  • 행동 가드레일(action guardrail) — 모델이 내놓은 툴 호출이 실제로 실행되기 직전을 검사합니다. "이 delete_user 호출을 정말 실행해도 되나?"를 판정하는 자리입니다.

이 글의 주제는 후자입니다. 왜 후자가 더 중요할까요? 입력 필터는 아무리 잘 만들어도 완벽할 수 없기 때문입니다. 새로운 인젝션 기법은 계속 나오고, 모델은 확률적으로 움직입니다. 그러니 "나쁜 지시가 언젠가는 새어 들어온다"를 전제로 깔고, 마지막 관문 — 부작용이 실제로 일어나는 지점 — 에 결정론적 방어선을 두는 게 안전합니다. 아무리 교묘한 프롬프트도, 결국 rm -rf /라는 툴 호출로 귀결되지 않으면 피해를 못 줍니다. 그 툴 호출을 잡으면 됩니다.

핵심 관점: 에이전트 보안의 무게중심을 "모델이 나쁜 말을 못 하게"에서 "모델이 나쁜 짓을 못 하게"로 옮기세요. 전자는 확률적이라 언젠가 새지만, 후자는 코드로 결정론적으로 막을 수 있습니다.

3. 왜 블록리스트는 구조적으로 실패하나 (GuardFall)

많은 에이전트가 처음엔 이렇게 방어합니다. "위험한 명령 패턴 목록을 만들어 두고, 모델이 뱉은 명령 문자열이 거기 걸리면 막자." 직관적이죠. 그런데 GuardFall이 보여 준 건, 이 방식이 고칠 수 없는 종류의 실패라는 겁니다. 패턴을 아무리 추가해도 소용없습니다. 왜일까요?

핵심은 가드가 검사하는 텍스트와, 셸이 실제로 실행하는 텍스트가 다르다는 데 있습니다. 가드는 모델이 준 날문자열(raw string)을 그대로 봅니다. 하지만 bash는 그 문자열을 실행하기 전에 변수 확장, 따옴표 제거, 명령 치환 같은 재작성을 거칩니다. 둘이 보는 게 애초에 다른 물건인 거죠.

여기서 배울 원칙이 두 가지입니다. 첫째, 차단 목록(denylist)이 아니라 허용 목록(allowlist)이 기본이어야 합니다. "이런 나쁜 것만 막자"는 무한한 우회로에 지고, "이런 안전한 것만 허용하자"는 이길 수 있습니다. 둘째, 정책은 문자열이 아니라 의미(semantics)를 봐야 합니다. 셸 명령을 문자열로 검사하지 말고, 애초에 셸을 주지 말거나 — 주더라도 파싱해서 실행 파일과 인자를 구조적으로 확인하거나 — 능력을 좁게 쪼갠 전용 툴(예: list_files(path))만 노출하는 식으로요.

구조적 실패란: 버그를 하나 고쳐서 없어지는 게 아니라, 설계 방식 자체가 틀려서 같은 방식으로는 아무리 고쳐도 뚫리는 걸 말합니다. "에이전트 → 문자열 매칭 게이트 → bash"라는 구조는, 패턴을 몇 개 넣든 GuardFall에 집니다.

4. 컨트롤 플레인: 네 가지 결정

그럼 제대로 된 방어선은 어떻게 생겼을까요? 핵심 아이디어는 단순합니다. 모든 툴 호출이 반드시 지나가는 하나의 좁은 통로(choke point)를 만들고, 거기서 정책을 판정합니다. 이 통로가 컨트롤 플레인입니다. 그리고 판정 결과는 예/아니오 둘이 아니라, 실무에서는 대개 네 가지로 나뉩니다.

  • ALLOW — 안전한 호출은 그대로 통과. read_file, 검색, 조회처럼 부작용이 없는 것들.
  • DENY — 절대 허용하지 않음. 실행 자체가 일어나지 않고, "이건 정책상 막혔다"는 에러 메시지를 모델에게 돌려줍니다. 그러면 모델이 다른 방법을 찾거나 사용자에게 물어보게 됩니다.
  • ASK (REQUIRE_APPROVAL) — 위험하지만 필요할 수 있는 것. 실행을 멈추고 사람의 승인을 기다립니다. 결제, 대량 삭제, 외부로 데이터 전송 같은 것들이죠.
  • DEGRADE (안전 모드) — 요청의 위험한 부분만 빼고 안전한 형태로 대체해 실행합니다. 예: "파일에 쓰기" 대신 "무엇을 쓸지 미리보기만 반환", "프로덕션 DB 대신 읽기 전용 복제본 조회".

여기서 가장 중요한 설계 원칙 하나. 이 판정을 모델에게 맡기지 마세요. "위험하면 알아서 사람한테 물어봐"라고 프롬프트에 적는 건 방어가 아닙니다. 모델은 확률적이라 언젠가 안 물어봅니다. 판정은 반드시 모델 바깥의, 우리가 짠 일반 코드가 내려야 합니다. 그래야 "결정론적"이라 부를 수 있습니다.

5. 실전 ①: 툴 호출 인터셉터 직접 만들기

개념을 코드로 만져 보겠습니다. 프레임워크 없이도 컨트롤 플레인의 뼈대는 아주 단순합니다. 모든 툴 호출이 지나가는 함수 하나를 두고, 실제 실행 전에 정책을 물어보면 됩니다.

{{< highlight python >}} from enum import Enum from dataclasses import dataclass class Decision(Enum): ALLOW = "allow" DENY = "deny" ASK = "ask" # 사람 승인 필요 DEGRADE = "degrade" # 안전 모드로 대체 @dataclass class ToolCall: name: str # 예: "delete_file" args: dict # 예: {"path": "/data/report.csv"} # ── 정책: 모델 바깥의 '일반 코드'. 여기서 결정론적으로 판정한다 ── def policy(call: ToolCall) -> Decision: # 1) 조회성 툴은 허용 목록으로 통과 (allowlist 우선!) if call.name in {"read_file", "list_files", "web_search"}: return Decision.ALLOW # 2) 파일 삭제는 경로에 따라 다르게 if call.name == "delete_file": path = call.args.get("path", "") if path.startswith("/data/tmp/"): # 임시 폴더면 OK return Decision.ASK # 그래도 사람에게 한 번 확인 return Decision.DENY # 그 밖의 경로는 아예 차단 # 3) 외부로 나가는 행동(메일·결제 등)은 무조건 사람 승인 if call.name in {"send_email", "charge_card"}: return Decision.ASK # 4) 목록에 없는 툴은 기본 차단 (default-deny) return Decision.DENY {{< /highlight >}}

포인트는 마지막 줄, return Decision.DENY입니다. 모르는 건 일단 막는(default-deny) 게 기본값이어야 합니다. GuardFall에서 배웠듯, "나쁜 것만 막기"가 아니라 "좋은 것만 허용하기"로 뒤집는 것이죠. 이제 이 정책을 실제 실행 경로에 끼웁니다.

{{< highlight python >}} def run_tool(call: ToolCall): decision = policy(call) audit_log(call, decision) # 모든 판정을 반드시 기록 (감사 로그) if decision is Decision.DENY: # 실행하지 않고, 왜 막혔는지 '모델에게' 알려 준다 return {"error": f"'{call.name}' 호출은 정책상 차단되었습니다."} if decision is Decision.ASK: if not request_human_approval(call): # 사람이 거절하면 return {"error": "사용자가 이 작업을 승인하지 않았습니다."} if decision is Decision.DEGRADE: call = to_safe_mode(call) # 예: write → preview 로 바꿔치기 # 여기까지 왔다면 ALLOW 이거나, 승인/대체를 통과한 것 return EXECUTORS[call.name](**call.args) {{< /highlight >}}

단 몇 줄이지만, 이 구조가 주는 보장이 큽니다. 어떤 프롬프트 인젝션이 들어와도, 모델이 charge_card를 부르는 순간 무조건 사람 승인 앞에 멈춥니다. 모델의 선의에 기대지 않죠. 그리고 audit_log가 모든 판정을 남기므로, 나중에 "왜 이게 실행됐지?"를 추적할 수 있습니다. 이 세 가지 — 단일 통로, default-deny, 감사 로그 — 가 컨트롤 플레인의 최소 골격입니다.

실전 팁: 정책 함수는 순수 함수로 유지하세요. 입력은 ToolCall, 출력은 Decision뿐 — 네트워크도 안 부르고 부작용도 없게요. 그래야 정책 자체를 단위 테스트로 촘촘히 검증할 수 있고, "이 인자면 이 결정"을 회귀 테스트로 고정할 수 있습니다.

6. 실전 ②: 프레임워크는 뭘 주나

직접 만들 수도 있지만, 주요 에이전트 프레임워크는 이 컨트롤 플레인을 이미 1급 기능으로 제공합니다. 이름과 모양은 조금씩 다르지만 개념은 위와 똑같습니다. 대표 셋을 봅시다.

Claude Agent SDK는 툴 호출을 여러 겹으로 심사합니다. 공식 문서가 밝히는 평가 순서가 이 글의 주제를 거의 그대로 보여 줍니다.

PreToolUse 훅 → Deny 규칙 → Allow 규칙 → Ask 규칙 → 권한 모드 → canUseTool 콜백 → PostToolUse 훅

맨 앞의 PreToolUse 훅은 툴이 실행되기 전에 우리 코드를 끼워 넣는 자리입니다. 훅은 permissionDecision을 "allow"·"deny"·"ask" 중 하나로 정하고, 이유(permissionDecisionReason)와 수정된 인자(updatedInput)까지 돌려줄 수 있습니다. 그다음 선언적 Deny/Allow/Ask 규칙이 순서대로 걸리고, 어디에도 안 걸린 나머지는 런타임 canUseTool 콜백이 처리합니다. 중요한 점: Deny 규칙은 다른 무엇보다 세서, bypassPermissions 모드에서도 차단이 유지됩니다. "절대 안 되는 것"을 확실히 못 박을 수 있다는 뜻이죠.

LangChain — HumanInTheLoopMiddleware

LangChain(1.2+)은 HumanInTheLoopMiddleware라는 미들웨어로 승인 게이트를 붙입니다. 어떤 툴에 어떤 결정을 허용할지 interrupt_on 딕셔너리로 툴별로 지정합니다.

{{< highlight python >}} from langchain.agents.middleware import HumanInTheLoopMiddleware middleware = HumanInTheLoopMiddleware( interrupt_on={ # 파일 쓰기는 승인/수정/거절 모두 허용 "write_file": {"allowed_decisions": ["approve", "edit", "reject"]}, # 메일 전송은 승인 아니면 거절만 "send_email": {"allowed_decisions": ["approve", "reject"]}, # 여기 없는 툴(read_file 등)은 승인 없이 그냥 실행 } ) {{< /highlight >}}

결정 종류가 네 가지인 점이 눈에 띕니다 — approve(그대로 실행), edit(인자를 사람이 고쳐서 실행), reject(거절하고 모델에 피드백), respond("사용자에게 물어보기" 툴에 사람이 직접 답). 실행을 멈추는 건 내부적으로 interrupt()가, 재개는 Command(resume=...)가 담당합니다. (인자 값에 따라 멈출지 말지를 동적으로 정하는 조건부 인터럽트는 langchain>=1.3.3에서 지원합니다.)

OpenAI Agents SDK — needsApproval

OpenAI Agents SDK는 툴에 needsApproval을 걸어 둡니다. 승인이 필요한데 아직 결정이 없으면, 그 툴 호출은 실행되지 않고 런의 interruptions에 ToolApprovalItem으로 쌓입니다. 각 항목엔 에이전트 이름·툴 이름·인자가 담겨 있어, 사람에게 보여 주고 판단을 받을 수 있죠. 승인/거절 후 저장한 상태(state)를 다시 run()에 넘기면 멈췄던 지점부터 이어집니다.

프레임워크정책을 거는 자리결정 종류멈춤 · 재개
Claude Agent SDKPreToolUse 훅 + Deny/Allow/Ask 규칙 + canUseToolallow · deny · ask규칙·모드·콜백 계층 평가
LangChainHumanInTheLoopMiddleware의 interrupt_onapprove · edit · reject · respondinterrupt() / Command(resume=)
OpenAI Agents SDK툴의 needsApprovalapprove · rejectinterruptions → state.approve() → run()

이름은 제각각이지만 공통 뼈대가 보이시나요? ①모든 툴 호출을 가로채는 자리, ②실행 전에 내리는 판정(허용/차단/승인), ③사람이 개입할 땐 멈췄다 재개하는 상태 처리. 5장에서 손으로 만든 것과 정확히 같은 구조입니다.

7. 사람 승인은 '멈췄다 재개하는' 상태 기계다

ASK(사람 승인)를 얕보면 크게 헤맵니다. 웹 서버에서 에이전트를 돌린다고 해 봅시다. 사용자가 "이 인보이스 결제해 줘"라고 하면, 에이전트는 charge_card 앞에서 멈춰 승인을 기다려야 합니다. 그런데 사람이 승인 버튼을 누르는 데 30초가 걸릴지, 3시간이 걸릴지 모릅니다. 그동안 프로세스를 붙잡고 while로 기다릴 순 없죠. 서버는 재시작될 수도 있고요.

그래서 제대로 된 승인은 상태를 저장하고 멈췄다가, 나중에 그 상태에서 재개하는 구조여야 합니다. 위 프레임워크들이 하나같이 "인터럽트 → 상태 저장 → 재개"로 설계된 이유가 이것입니다.

이 패턴은 이전에 이 블로그에서 다룬 지속 실행(durable execution)과도 맞닿아 있습니다. 승인 대기는 결국 "오래 걸리는 중단점"이고, 그 지점을 견고하게 저장·복원하는 게 프로덕션 에이전트의 핵심 역량입니다. OpenAI Agents SDK가 result.to_state()로 상태를 떠서 다시 run()에 넣고, LangChain이 체크포인터에 상태를 남기는 것도 다 이 때문입니다.

8. 흔한 실수 · 팁

  • 블록리스트에 의존하기 — 가장 흔하고 가장 치명적인 실수입니다. "위험한 명령 목록"은 GuardFall처럼 반드시 우회당합니다. 허용 목록 + default-deny로 뒤집으세요. 셸이 꼭 필요하면 문자열을 매칭하지 말고, 좁은 전용 툴로 능력을 쪼개 노출하는 편이 훨씬 안전합니다.
  • 판정을 모델에게 맡기기 — "위험하면 사람한테 물어봐"를 프롬프트에 적는 건 가드레일이 아닙니다. 모델은 확률적이라 언젠가 건너뜁니다. 판정은 모델 바깥의 결정론적 코드가 내려야 합니다.
  • 승인 피로(approval fatigue) — 사소한 것까지 다 물어보면, 사용자는 내용을 안 읽고 "승인"만 연타합니다. 그러면 승인 게이트는 있으나 마나죠. 정말 위험한 것만 ASK로 올리고, 안전한 다수는 ALLOW로 흘려보내세요. 위험을 등급으로 나눠 임계값을 정하는 게 핵심입니다.
  • 승인 ≠ 인가(authorization) — 사용자에게 승인 버튼을 보여 준다고 해서, 그 사용자가 그 작업을 할 권한이 있는 건 아닙니다. 승인 UI는 사람의 확인일 뿐, 실제 권한 검사(누가 무엇에 접근 가능한가)는 별도로 서버에서 강제해야 합니다. 둘을 헷갈리면 권한 상승 취약점이 생깁니다.
  • DENY를 조용히 삼키기 — 차단했으면 그 사실을 모델에게 에러로 돌려주세요. 아무 말 없이 무시하면 모델은 같은 호출을 반복하거나 엉뚱하게 진행합니다. "정책상 막혔다"를 알려 주면 다른 경로를 찾거나 사용자에게 물어봅니다.
  • 감사 로그 빼먹기 — 모든 판정(무엇을, 어떤 인자로, 어떤 결정으로)을 남기세요. 사고가 났을 때 타임라인을 복원하고, "왜 이게 실행됐지?"에 답하는 유일한 근거입니다. 판정 자체와 로깅은 한 세트입니다.

9. 마무리 (TL;DR)

  • 에이전트가 행동하기 시작하면, 방어의 무게중심을 "무엇을 말하는가"에서 "무엇을 하는가"로 옮겨야 합니다.
  • 2026년 6월 GuardFall은 인기 코딩 에이전트 11개 중 10개의 셸 차단 장치가 수십 년 된 셸 트릭에 뚫린다는 걸 보여 줬습니다. 문자열 블록리스트는 구조적으로 실패합니다 — 가드가 본 텍스트와 셸이 실행한 텍스트가 다르기 때문입니다.
  • 답은 컨트롤 플레인: 모든 툴 호출이 지나가는 단일 통로에서, 모델 바깥의 결정론적 코드가 ALLOW · DENY · ASK · DEGRADE 넷 중 하나로 판정합니다.
  • 최소 골격은 ①단일 통로 ②default-deny(허용 목록) ③감사 로그. 정책은 순수 함수로 만들어 단위 테스트로 고정하세요.
  • Claude Agent SDK(PreToolUse 훅·Deny/Allow/Ask 규칙·canUseTool), LangChain(HumanInTheLoopMiddleware), OpenAI Agents SDK(needsApproval)가 같은 뼈대를 1급 기능으로 제공합니다.
  • 사람 승인은 while로 기다리는 게 아니라, 인터럽트 → 상태 저장 → 재개하는 상태 기계로 만드세요. 그래야 오래 걸리는 승인과 서버 재시작을 견딥니다.
  • 실수 체크리스트: 블록리스트 의존 금지, 판정을 모델에 맡기지 말 것, 승인 피로 관리, 승인 ≠ 인가, DENY는 에러로 돌려주기, 모든 판정 로깅.
