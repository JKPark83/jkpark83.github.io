1. 도입 — 공식 확장 ID로 배포된 백도어

2026년 10월 29일 새벽(태평양 시간 2시 27분경), Cursor의 확장 마켓플레이스에 anthropic.claude-code 확장의 새 버전이 올라왔습니다. 가짜 이름을 흉내 낸 짝퉁이 아니라, Anthropic의 정식 extension ID 그대로였습니다. 자동 업데이트가 켜져 있던 사용자라면 아무것도 누르지 않아도 받았고, 받은 뒤 에디터를 켜는 것만으로 악성 코드가 실행됐습니다. Claude 채팅을 열 필요도 없었습니다.

이 변조 버전(2.1.313, 이후 2.1.312도 추가 확인)은 약 11시간 뒤인 오후 1시 35분경 제거될 때까지 최대 5,000명의 개발자에게 노출됐습니다. 페이로드는 광고 사기나 코인 채굴 같은 "값싼" 악성코드가 아니었습니다. 피해자의 ~/.ssh/authorized_keys에 공격자의 공개키를 심고, 역방향 SSH 터널로 개발 머신에 지속적으로 들어올 수 있는 백도어를 만들려 했습니다. Cursor는 보안 공지를 내고 마켓플레이스 전체를 일시 폐쇄했으며, Microsoft 위협 인텔리전스 팀과 여러 보안 업체가 다음 날 바로 분석을 공개했습니다. Hacker News에서는 관련 스레드가 700포인트 넘게 오르며 한 주 내내 화제였습니다.

왜 이 사건이 'AI 뉴스'가 아니라 'AI 엔지니어링' 이야기일까요? AI 코딩 도구는 지금 개발 생태계에서 가장 빨리 설치되고, 가장 자주 업데이트되고, 가장 깊은 권한으로 도는 소프트웨어이기 때문입니다. 에이전트가 제대로 일하려면 git 자격 증명, 클라우드 토큰, API 키에 접근해야 하고, 우리는 그걸 기꺼이 내어줍니다. 공격자 입장에서 AI 도구의 공급망은 개발자 머신 수천 대의 자격 증명으로 직행하는 고속도로입니다. 이번 사건을 한 단계씩 해부하면서, 이 고속도로에 어떤 검문소를 세워야 하는지 정리해 보겠습니다.

2. 배경 — 에디터 확장이라는 공격면 3분 요약

사건을 이해하는 데 필요한 배경은 세 가지입니다.

① 확장은 곧 임의 코드 실행입니다. VS Code 계열 에디터의 확장은 에디터와 같은 권한의 Node.js 프로세스에서 돕니다. 브라우저 탭 같은 샌드박스(sandbox, 격리된 실행 환경)가 없습니다. 파일 시스템 전체를 읽고, 네트워크에 접속하고, 자식 프로세스를 띄울 수 있습니다. 즉 확장을 설치한다는 건 그 배포 채널을 운영하는 모든 주체에게 내 머신의 셸을 맡기는 일과 같습니다.

② 마켓플레이스는 하나가 아닙니다. Microsoft의 Visual Studio Marketplace는 약관상 공식 VS Code 제품만 쓸 수 있습니다. 그래서 Cursor, Windsurf 같은 포크(fork)들은 Eclipse 재단이 운영하는 Open VSX를 쓰거나 자체 마켓플레이스를 운영합니다. 같은 이름의 확장이 채널마다 다른 바이너리일 수 있다는 뜻입니다. 이번 사건에서도 Microsoft 마켓플레이스와 npm의 Claude Code는 멀쩡했고, 변조본은 Cursor 마켓플레이스에서만 배포됐습니다.

③ 자동 업데이트는 신뢰를 자동으로 연장합니다. 확장은 기본적으로 자동 업데이트됩니다. "설치할 때 한 번 검토했으니 괜찮다"는 가정은 성립하지 않습니다. 어제의 깨끗한 확장 2.1.311과 오늘의 변조된 2.1.313 사이에서 사용자가 개입할 지점은 없습니다. 공급망 공격이 노리는 게 정확히 이 지점입니다. 잘 알려진 이름의 배포 경로를 한 번만 장악하면, 신뢰가 쌓아 놓은 설치 기반 전체가 공격 표면이 됩니다.

공개된 사실관계를 먼저 정리합니다. Cursor 공지와 Microsoft·보안 업체들의 분석을 종합하면 이렇습니다.

주목할 점 두 가지입니다. 첫째, 짝퉁 확장이 아니라 정식 ID의 변조였습니다. 4. 해부 ② — extension.js 맨 앞의 66줄: 로더는 무슨 일을 했나

공급망 공격 기법 관점에서 이 사건의 교과서적인 부분입니다. StepSecurity의 바이너리 분석에 따르면, 변조본은 정상 확장 번들의 extension.js 맨 앞에 약 7,386바이트, 66줄짜리 즉시실행함수(IIFE)를 붙인 것이 전부였습니다. 나머지는 정상 빌드와 바이트 단위로 동일했고, 설치 스크립트(install/postinstall)도 없었습니다. 확장이 정상 동작하니 사용자는 아무 이상을 못 느낍니다. 악성 코드는 에디터가 확장을 로드할 때 조용히 먼저 실행될 뿐입니다.

로더가 시도한 일은 네 단계입니다.

  1. 정찰 비컨(beacon). 호스트 정보를 수집해 공격자 서버(134.209.82.225:8099의 /beacon)로 HTTP POST를 보냅니다. 흥미로운 디테일: 환경변수는 값이 아니라 이름만 보냈습니다. KEY, TOKEN, SECRET, PASS, AWS, GCP 같은 패턴에 걸리는 변수명 목록으로, "이 머신에 어떤 자격 증명이 있는지" 지도를 먼저 그린 겁니다.
  2. SSH 키 주입. 공격자의 공개키를 ~/.ssh/authorized_keys에 추가합니다. 이 파일에 등록된 키의 소유자는 SSH 서비스가 열려 있는 한 비밀번호 없이 로그인할 수 있습니다.
  3. 역방향 SSH 터널. 피해 머신이 방화벽·NAT 뒤에 있어도 공격자가 들어올 수 있도록, 피해 머신 쪽에서 공격자 서버로 먼저 터널을 뚫으려 시도합니다.
  4. 지속화(persistence). 자동 시작 스크립트를 확장 폴더 바깥에 심습니다. 이게 운영상 가장 악질적인 부분입니다. 확장을 삭제하거나 깨끗한 2.1.314로 업데이트해도 백도어 설치 스크립트는 그대로 남아서 계속 돕니다.
핵심 교훈: 이 공격에서 "확장 삭제"는 치료가 아닙니다. 지속화 스크립트가 확장 폴더 밖에 있으므로 authorized_keys의 수상한 키, 자동 시작 항목, 생성된 스크립트를 각각 찾아 제거해야 합니다. Cursor와 Microsoft 모두 이 점을 명시적으로 경고했고, Cursor는 플랫폼별 점검·정리 스크립트를 공지에 첨부했습니다.

5. 해부 ③ — 왜 피해가 제한됐고, 무엇이 아직 미궁인가

다행히 실제 피해는 설계된 것보다 작았을 가능성이 높습니다. 역방향 터널이 성립하려면 피해 머신의 로컬 SSH 서비스를 켜야 하는데, 여기에 관리자 권한이 필요합니다. 에디터를 관리자 권한으로 띄우는 특이한 경우가 아니라면 이 단계는 실패합니다. Cursor 공지도 악성 코드 자체의 오류와 권한 문제로 터널 단계가 대부분 실패했을 것으로 봤습니다. 공격자가 한 끗 더 정교했다면 — 예컨대 SSH 서비스에 의존하지 않는 사용자 권한 역방향 셸을 썼다면 — 이야기가 훨씬 어두웠을 겁니다. 이번에 살아남은 건 방어가 훌륭해서가 아니라 공격자가 서툴렀기 때문이라는 게 여러 분석의 공통된 평가입니다.

반면 아직 공개되지 않은 핵심 질문이 있습니다. 공격자가 어떻게 공식 extension ID로 게시할 수 있었는가입니다. 게시용 토큰 탈취인지, 마켓플레이스 인프라의 다른 구멍인지, 이 글을 쓰는 시점까지 Cursor는 침투 경로를 공개하지 않았습니다. Cursor가 사고 대응에서 마켓플레이스 전체를 내리고 모든 접근 키를 로테이션한 것은, 게시 경로의 자격 증명 오염 가능성을 심각하게 봤다는 간접 신호로 읽을 수 있습니다. 다만 이건 추정이 아니라 "아직 모른다"로 남겨 두는 게 정확합니다.

참고 — 신뢰 인프라는 양방향으로 흔들립니다. 공교롭게도 2025년 8월에는 정반대 사고가 있었습니다. Open VSX가 진짜 Claude Code 확장을 악성으로 오탐해서, Open VSX를 쓰는 에디터들이 정상 확장을 자동 삭제한 일입니다. 마켓플레이스의 "악성/정상" 판정은 생각보다 수작업에 가깝고, 가짜를 통과시키는 실수와 진짜를 차단하는 실수가 모두 일어납니다. 판정 결과를 맹신하기보다 아래 7절의 방어 계층을 직접 갖추는 편이 안전합니다.

6. 더 큰 그림 — GlassWorm, Shai-Hulud, 그리고 AI 코딩 시대의 표적 이동

이번 사건은 단발이 아니라 뚜렷한 흐름의 한 장면입니다. 최근 1년여 사이 개발자 도구 공급망에서 벌어진 일들을 나란히 놓으면 패턴이 보입니다.

2025년 9월npm Shai-Hulud 웜탈취한 npm 토큰으로 패키지 187개에 자기 복제. 피해자 머신에서 TruffleHog로 시크릿을 긁어 다음 감염에 사용

2026년 10월Claude Code 변조 (이번 사건)공식 extension ID의 배포 경로를 직접 장악해 트로이 버전 게시. 목표는 개발 머신 자체의 원격 접근

흐름이 보이시나요? 공격자들의 표적이 "인기 패키지"에서 "개발자 머신의 자격 증명과 접근 권한" 그 자체로 이동하고 있습니다. 그리고 AI 코딩 도구는 그 교차점의 한가운데에 있습니다. 이유는 구조적입니다.

  • 자격 증명이 모입니다. 코딩 에이전트가 쓸모 있으려면 git push 권한, 클라우드 CLI 토큰, 각종 API 키가 손에 닿아야 합니다. 에이전트를 잘 쓰는 개발자일수록 머신에 더 많은 권한이 모여 있습니다.
  • 교체 주기가 빠릅니다. AI 도구는 몇 주 단위로 갈아타는 게 일상입니다. "새로 나온 확장·CLI·MCP 서버를 일단 깔아 보는" 문화는 검증 없는 설치를 정상 행동으로 만들었습니다.
  • 이상 행동이 가려집니다. AI 도구는 원래 네트워크를 많이 쓰고, 파일을 많이 읽고, 프로세스를 많이 띄웁니다. 악성 행위가 정상 동작의 소음에 묻히기 좋은 환경입니다.

즉 "AI 엔지니어링을 한다"는 것은 이제 "공급망 공격의 고가치 표적이 된다"와 같은 말입니다. 그래서 방어도 엔지니어링 관점으로 접근해야 합니다.

7. 실전 — 내 머신 점검과 팀 방어 계층 세우기

먼저 급한 것부터. Cursor에서 Claude Code 확장을 쓰고 있었다면(특히 10월 29일 전후), 공식 공지의 플랫폼별 스크립트를 따르는 게 정석입니다. 그와 별개로 아래 점검은 어떤 머신에서든 몇 분이면 끝납니다.

{{< highlight bash >}} # 1) 문제 버전이 설치됐었는지 확인 (Cursor 확장 폴더) ls ~/.cursor/extensions | grep -i "anthropic.claude-code-2.1.31[23]" # 2) authorized_keys에 내가 모르는 공개키가 있는지 — 가장 중요한 점검 # (한 줄 = 키 하나. 끝의 주석(label)까지 전부 눈으로 확인하세요) cat ~/.ssh/authorized_keys # 3) 자동 시작 항목에 수상한 것이 있는지 # macOS: LaunchAgents / Linux: crontab과 systemd user unit ls -la ~/Library/LaunchAgents/ # macOS crontab -l; ls -la ~/.config/systemd/user # Linux # 4) 원격 SSH 서비스가 불필요하게 켜져 있지 않은지 sudo systemsetup -getremotelogin # macOS systemctl status ssh # Linux {{< /highlight >}}

개인 점검은 응급 처치일 뿐입니다. 구조적인 방어는 계층으로 세워야 합니다. 어느 한 층이 뚫려도 다음 층이 피해를 줄이도록요.

이 중 당장 효과가 큰 두 가지만 구체적으로 보겠습니다.

실행 격리 — 에이전트는 컨테이너 안에서. 코딩 에이전트와 그 확장을 devcontainer(개발 환경을 컨테이너로 정의하는 표준) 안에서 돌리면, 이번 같은 공격이 성공해도 피해 범위가 컨테이너로 제한됩니다. 핵심은 호스트의 민감한 경로를 마운트하지 않는 것입니다.

{{< highlight json >}} // .devcontainer/devcontainer.json — 에이전트 전용 격리 환경의 뼈대 { "name": "agent-sandbox", "image": "mcr.microsoft.com/devcontainers/typescript-node:22", // 워크스페이스 '폴더만' 마운트합니다. 홈 디렉터리 전체(~/.ssh, // ~/.aws 등)를 마운트하는 순간 격리는 의미가 없어집니다. "mounts": [], "containerEnv": { // 시크릿은 상주 환경변수가 아니라 필요한 순간에만 주입 }, "customizations": { "vscode": { // 이 환경에서 쓸 확장을 '명시적으로' 나열 = 사실상의 허용 목록 "extensions": ["anthropic.claude-code"] } } } {{< /highlight >}}

설치 게이트 — 확장 허용 목록. VS Code는 조직 정책으로 설치 가능한 확장을 제한하는 extensions.allowed 설정을 지원합니다. 게시자 단위·확장 단위·버전 단위까지 지정할 수 있어서, 팀 전체에 "검토된 확장의 검토된 버전만" 강제할 수 있습니다. 개인이라면 최소한 자동 업데이트를 끄고 릴리스 후 며칠 지난 버전을 설치하는 것만으로도, 이번처럼 수 시간~수일 안에 발각되는 변조본의 노출창을 대부분 피할 수 있습니다. npm 생태계에서 lockfile과 --ignore-scripts로 하던 일을 확장 생태계에도 똑같이 적용하는 셈입니다.

트레이드오프도 정직하게: 자동 업데이트 지연은 보안 패치도 늦게 받는다는 뜻이고, 격리 환경은 처음 세팅이 귀찮습니다. 공짜 방어는 없습니다. 다만 "AI 도구에 머신의 모든 권한을 주고 최신 버전을 즉시 받는" 현재의 기본값이 공격자에게 최적화된 설정이라는 점은 분명합니다. 기본값을 의식적으로 선택한 값으로 바꾸는 것이 이 글의 요지입니다.

8. 흔한 실수 · 팁

  • "공식 확장이니까 안전하다"고 믿기. 이번 변조본은 정식 extension ID로 배포됐습니다. 신뢰할 것은 이름이 아니라 배포 경로와 무결성 검증입니다. 같은 이름이라도 Microsoft 마켓플레이스, Open VSX, Cursor 마켓플레이스의 패키지는 서로 다른 빌드일 수 있습니다.
  • 사고 소식에 확장만 지우고 끝내기. 지속화가 확장 폴더 밖에 있으면 삭제는 치료가 아닙니다. 벤더의 공식 정리 절차를 따르고, authorized_keys·자동 시작 항목을 직접 확인하고, 그 머신에서 접근 가능했던 자격 증명을 다른(깨끗한) 머신에서 로테이션하세요.
  • 시크릿을 셸 rc 파일에 export 해두기. .zshrc에 박힌 AWS_SECRET_ACCESS_KEY는 모든 프로세스의 것입니다. 이번 로더의 1단계가 정확히 그 환경변수 스캔이었습니다. 단기 토큰 발급(예: 클라우드 CLI의 SSO 로그인)이나 OS 키체인으로 옮기세요.
  • 에이전트 편의를 위해 격리를 먼저 포기하기. "컨테이너 안에서는 에이전트가 내 dotfiles를 못 봐서 불편하다"며 홈 디렉터리 전체를 마운트하는 순간, 격리층은 장식이 됩니다. 필요한 파일만 골라서 넣으세요.
  • 탐지를 남의 일로 두기. 이번 사건의 탐지도 외부 보안 연구자의 신고였습니다. authorized_keys는 자주 바뀌는 파일이 아니므로, 변경 시 알림을 걸어 두는 것만으로 훌륭한 개인용 침입 탐지가 됩니다. macOS라면 fswatch, Linux라면 inotifywait 한 줄로 충분합니다.
  • MCP 서버·CLI 도구는 예외라고 생각하기. 이 글은 에디터 확장 사건을 다뤘지만, 같은 논리가 npm으로 설치하는 MCP 서버, curl로 받는 설치 스크립트, 에이전트가 제안하는 의존성 추가에 모두 적용됩니다. "임의 코드를 내 권한으로 실행하는 모든 것"이 같은 공격면입니다.

9. 마무리 (TL;DR)

  • 10월 29일, Cursor 마켓플레이스에서 정식 ID의 Claude Code 확장 변조본(2.1.312·2.1.313)이 약 11시간 배포돼 최대 5,000명이 노출됐습니다. Anthropic 공식 채널·MS 마켓플레이스·npm은 영향이 없었습니다.
  • 수법은 extension.js 맨 앞에 66줄 로더를 붙인 것. 에디터가 확장을 로드하면 시크릿 환경변수 이름 수집 → authorized_keys 키 주입 → 역방향 SSH 터널 → 확장 폴더 밖 지속화를 시도했습니다. 터널은 관리자 권한 요구와 코드 오류로 대부분 실패했습니다 — 방어의 승리가 아니라 공격자의 실수였습니다.
  • 확장 삭제는 치료가 아닙니다. 지속화 스크립트·주입된 키·자동 시작 항목을 별도로 제거하고, 노출된 자격 증명은 깨끗한 머신에서 로테이션해야 합니다.
  • Shai-Hulud(npm) → GlassWorm(Open VSX) → 이번 사건으로 이어지는 흐름의 공통점: 표적은 패키지가 아니라 개발자 머신의 자격 증명과 접근 권한입니다. 자격 증명이 모이는 AI 코딩 도구가 1순위 표적입니다.
  • 방어는 계층으로: 설치 게이트(허용 목록·업데이트 지연) → 실행 격리(devcontainer) → 시크릿 다이어트(단기 토큰) → 이그레스 제어 → 탐지(authorized_keys 모니터링). 한 층이 뚫려도 다음 층이 '침해'를 '소동'으로 줄입니다.
  • 오늘 할 일: 위 7절의 4가지 점검 명령 실행, 셸 rc 파일의 장수 시크릿 정리, 에이전트 작업용 격리 환경 하나 만들기.
