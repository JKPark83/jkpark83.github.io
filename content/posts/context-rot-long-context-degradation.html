1. 왜 지금 '컨텍스트 로트'가 화제인가

2024~2025년은 컨텍스트 창(context window) 경쟁의 시대였습니다. 8K에서 시작해 128K, 200K를 지나 100만(1M), 심지어 1천만(10M) 토큰까지 벌어졌죠. 그래서 많은 사람이 이렇게 생각했습니다. "이제 컨텍스트 문제는 하드웨어로 밀어붙여 끝났다. 그냥 다 집어넣으면 된다."

그런데 2026년 들어 실무 담론의 결론은 정반대로 굳어졌습니다. 창을 키운다고 로트(rot·부패)가 사라지지 않는다. 오히려 창이 커질수록 "넣을 수 있는 양"과 "모델이 실제로 제대로 쓰는 양" 사이의 간극이 더 도드라졌습니다. 이 현상을 요즘은 컨텍스트 로트(context rot)라고 부릅니다 — 입력이 길어질수록, 창 한계에 닿기 한참 전부터 모델의 정확도가 조용히 무너지는 현상입니다.

이 말을 데이터로 못 박은 게 벡터 DB 회사 Chroma의 "Context Rot" 연구입니다. GPT-4.1, Claude 4 계열, Gemini 2.5, Qwen3 등 프런티어 모델 18종을 "건초 더미에서 바늘 찾기(needle-in-a-haystack)" 같은 단순 검색·복제 과제로 시험했더니, 예외 없이 전부 입력이 길어질수록 성능이 떨어졌습니다. 그것도 매끄럽게 떨어지는 게 아니라, 특정 지점에서 뚝 꺾이는 절벽에 가까웠고요.

Databricks Mosaic 팀의 장문 RAG 실험은 숫자로도 아프게 보여 줍니다. 13개 모델·2,000회 넘는 실험에서, 문서를 더 넣을수록 처음엔 좋아지다가 어느 지점부터 꺾였습니다. Llama-3.1-405B는 32K 토큰부터, GPT-4는 64K부터 성능이 내려갔고, 어떤 모델은 길이가 늘자 지시를 아예 안 따르기 시작했습니다(예: DBRX의 지시 위반이 8K에서 5.2%였는데 32K에서 50.4%로 폭증). 창은 훨씬 큰데도요.

그래서 이번 주에도 X(옛 트위터)와 엔지니어링 블로그에서 "1M 컨텍스트의 거짓말", "유효 컨텍스트는 광고치의 절반"이라는 이야기가 반복해서 돌았습니다. 에이전트가 툴 출력·검색 결과·버려진 추론 흔적을 계속 쌓아 가며 일하는 구조라, 이 로트는 프로덕션 에이전트의 1순위 실패 모드이기도 합니다. 이 글에서는 로트가 왜 생기는지, 어떻게 측정하고 어떻게 설계로 피하는지를 코드까지 함께 풀어 봅니다.

2. 배경: 창 오버플로 ≠ 컨텍스트 로트

먼저 헷갈리기 쉬운 두 개념을 갈라 놓겠습니다. 이걸 섞으면 "토큰만 안 넘치게 자르면 되겠지"라는 잘못된 안심을 하게 됩니다.

  • 창 오버플로(context overflow) — 모델의 최대 토큰 한계를 넘겨서 나는 에러입니다. 200K 창에 210K를 넣으면 잘리거나 거부됩니다. 이건 명확한 하드 리밋이고, 세면 알 수 있습니다.
  • 컨텍스트 로트(context rot) — 한계를 넘지 않았는데도 성능이 떨어지는 현상입니다. 200K 창에 50K만 넣어도 심하게 나빠질 수 있습니다. 에러가 안 나서 조용하다는 게 더 무섭습니다.

비유하자면, 컨텍스트 창은 책상 크기입니다. 책상이 넓다고 서류 300장을 다 펼쳐 놓으면, 정작 필요한 한 장을 찾느라 헤매죠. 책상이 넘치진 않았지만(오버플로 아님), 일의 질은 떨어집니다(로트). 모델도 똑같습니다. 창에 들어가는 것과, 그 안에서 주의(attention)를 제대로 배분하는 것은 다른 문제입니다.

3. 현상 ①: lost in the middle (가운데서 길을 잃다)

로트의 가장 유명한 얼굴은 lost in the middle입니다. 2023년 Nelson Liu 등이 발표하고 TACL 2024에 실린 논문(arXiv:2307.03172)에서 나온 말인데, 지금도 장문 설계의 기본 상식으로 통합니다.

실험은 단순합니다. 여러 문서를 컨텍스트에 넣고 그중 딱 하나에만 정답이 있게 한 뒤, 그 정답 문서의 위치만 바꿔 가며 정확도를 잽니다. 결과는 U자 곡선이었습니다. 정답이 맨 앞이나 맨 뒤에 있으면 잘 찾는데, 가운데로 갈수록 뚝 떨어졌습니다. 어떤 세팅에선 위치를 바꾸는 것만으로 정확도가 30%포인트 넘게 출렁였고, 이건 "장문 전용"이라는 모델에서도 나타났습니다.

실무 관점에서 함의는 분명합니다. 검색해 온 20개 청크를 그냥 이어 붙여 넣으면, 정말 중요한 근거가 가운데 8~15번째 자리에 묻혀 무시될 수 있습니다. 그래서 뒤에서 볼 리랭킹(reranking)과 위치 배치가 중요해집니다. 좋은 근거를 찾아 오는 것만큼, 어디에 놓느냐도 성능을 좌우합니다.

4. 현상 ②: 디스트랙터와 '비슷한 오답'

로트를 부추기는 두 번째 요인은 디스트랙터(distractor)입니다. 정답은 아니지만 정답과 주제가 비슷한 방해 문서를 말합니다. Chroma 연구의 핵심 발견 중 하나가 이겁니다 — 질문과 정답(needle)의 의미적 유사도가 낮을수록, 그리고 비슷한 오답이 함께 있을수록, 입력이 길어질 때 성능이 더 급격히 무너집니다.

직관적으로 이해됩니다. "2023년 매출은?"이라고 물었는데 컨텍스트에 2021·2022·2024년 매출이 잔뜩 섞여 있으면, 모델은 헷갈립니다. 사람도 표를 잘못 읽죠. 게다가 질문과 정답이 다른 단어로 쓰여 있으면(예: 질문은 "수익", 문서는 "순이익") 유사도가 낮아 더 어렵습니다. 노이즈는 그냥 무시되는 게 아니라, 길이가 늘수록 적극적으로 오답을 끌어당깁니다.

핵심 관점: 컨텍스트에 "관련 있어 보이지만 답이 아닌 것"을 많이 넣는 건 도움이 아니라 해입니다. RAG에서 top-k를 무작정 늘리면 리콜은 올라가도, 디스트랙터가 함께 늘어 로트를 키웁니다. "많이"가 아니라 "깨끗하게"가 목표입니다.

에이전트에서는 이게 더 고약합니다. 에이전트는 한 스텝씩 진행하며 이전 툴 출력·검색 결과·실패한 시도를 컨텍스트에 계속 쌓습니다. 그 축적된 잡동사니가 전부 잠재적 디스트랙터죠. 그래서 매 스텝마다 컨텍스트가 조금씩 더 오염되고, 후반 스텝일수록 판단이 나빠지는 누적 열화가 생깁니다. 뒤에서 볼 compaction이 필요한 이유입니다.

5. 실전 ①: 내 모델의 '유효 컨텍스트' 측정하기

남의 벤치마크만 믿지 말고, 내가 쓰는 모델·내 데이터로 직접 재 보는 것이 첫걸음입니다. 방법은 lost-in-the-middle 실험을 축소한 버전입니다: 길이를 바꿔 가며 "바늘"을 심고, 얼마나 찾는지 봅니다. 아래는 개념을 보여 주는 최소 코드입니다.

{{< highlight python >}} import random # 1) '바늘(needle)': 이 문장에만 정답이 있다. 실제 문서에 없을 법한 고유 사실로 만든다. NEEDLE = "그날 창고 B-7 선반의 비밀 코드는 QX-4471 이었다." QUESTION = "창고 B-7 선반의 비밀 코드는 무엇이었나?" ANSWER = "QX-4471" # 2) '건초(haystack)': 주제가 비슷하지만 답이 아닌 디스트랙터 문장 풀 FILLER = [ "창고 A-2 선반은 정기 점검 대상이었다.", "B-7 구역은 지난달 재고 실사를 마쳤다.", "비밀 코드는 분기마다 갱신하도록 규정돼 있다.", # ... 실제로는 수백~수천 문장을 준비한다 ] def build_context(target_tokens, needle_depth): """needle_depth: 0.0=맨 앞, 0.5=한가운데, 1.0=맨 뒤""" # 대략적인 토큰 수를 맞추려고 필러 문장을 반복해 채운다(개념 예시) lines, approx = [], 0 while approx < target_tokens: s = random.choice(FILLER) lines.append(s) approx += len(s) # 실제로는 tokenizer로 정확히 세는 게 좋다 # 원하는 깊이 위치에 바늘을 끼워 넣는다 pos = int(len(lines) * needle_depth) lines.insert(pos, NEEDLE) return "\n".join(lines) def hit(model_answer): return ANSWER.lower() in model_answer.lower() # 3) 길이 × 위치를 격자로 훑으며 정확도 표를 만든다 for tokens in [2_000, 8_000, 32_000, 128_000]: for depth in [0.0, 0.25, 0.5, 0.75, 1.0]: ctx = build_context(tokens, depth) prompt = f"다음 자료만 근거로 답하라.\n\n{ctx}\n\n질문: {QUESTION}" ans = call_model(prompt) # 쓰는 LLM API로 교체 print(tokens, depth, hit(ans)) # 여러 번 반복해 정확도 평균을 낸다 {{< /highlight >}}

이 표를 그려 보면 내 모델의 유효 컨텍스트(effective context) — 성능이 무너지기 시작하는 실제 길이 — 가 보입니다. 업계 분석들은 대체로 공칭 창의 50~65% 부근부터 열화가 두드러진다고 말하지만, 이건 모델·과제·디스트랙터 밀도에 따라 크게 달라집니다. 그러니 숫자 하나를 외우지 말고, 내 파이프라인으로 곡선을 직접 그려 운영 상한을 정하세요.

주의: 바늘을 "일반 상식"으로 만들면 안 됩니다. 모델이 컨텍스트를 안 읽고 사전지식으로 맞혀 버려서, 로트가 없는 것처럼 착시가 생깁니다. 바늘은 반드시 컨텍스트를 봐야만 알 수 있는 고유한 사실(가짜 코드·가짜 날짜 등)로 만드세요.

6. 실전 ②: 로트를 피하는 4가지 설계

진단을 했으니 처방입니다. 핵심 철학은 하나입니다 — "다 넣기"가 아니라 "고신호 토큰만 최소로 넣기". 이것이 요즘 말하는 컨텍스트 엔지니어링(context engineering)의 목표입니다. 네 가지 실전 기법을 봅니다.

① 리랭킹으로 top-k를 줄인다

벡터 검색이 뽑아 온 수십 개 후보를 그대로 넣지 마세요. 리랭커(reranker)로 질문과의 실제 관련도를 다시 매겨 상위 소수(예: 3~5개)만 남깁니다. 리콜을 위해 넓게 검색하되, 컨텍스트에는 좁게 넣는 겁니다. "많이 넣어 리콜을 올리자"는 유혹이 곧 디스트랙터를 늘려 로트를 부른다는 걸 기억하세요.

② 디스트랙터를 능동적으로 쳐낸다

관련도 점수에 하한선(threshold)을 두고, 그 밑은 버립니다. "6개 채우기"가 목표가 아니라 "확실한 근거만"이 목표입니다. 근거가 2개뿐이면 2개만 넣으세요. 아래는 리랭킹 + 임계값 컷을 합친 최소 예시입니다.

{{< highlight python >}} def build_clean_context(question, candidates, reranker, max_docs=5, min_score=0.35): # 1) 리랭커로 (문서, 관련도점수) 리스트를 받아 내림차순 정렬 scored = reranker.rank(question, candidates) # [(doc, score), ...] scored.sort(key=lambda x: x[1], reverse=True) # 2) 임계값 미달 디스트랙터는 버리고, 상위 max_docs만 남긴다 kept = [doc for doc, score in scored[:max_docs] if score >= min_score] # 3) lost-in-the-middle 대비: 가장 강한 근거를 '맨 뒤'(질문 직전)에 배치 # 끝자리 회상률이 높으므로, 1등 근거를 질문에 가장 가깝게 둔다 kept = kept[::-1] # 약→강 순으로 뒤집기 body = "\n\n".join(f"[근거 {i+1}] {d}" for i, d in enumerate(kept)) return f"{body}\n\n질문: {question}" # 질문을 맨 뒤에 {{< /highlight >}}

③ 중요한 것을 앞·뒤 끝에 놓는다

lost in the middle을 역이용합니다. 시스템 지시·가장 강한 근거·질문처럼 꼭 반영돼야 하는 것은 컨텍스트의 처음이나 끝에 둡니다. 위 코드에서 질문을 맨 뒤에 붙이고 1등 근거를 그 바로 앞에 둔 게 이 원칙입니다. 반대로, 배경 설명처럼 덜 중요한 건 가운데로 보내도 됩니다.

④ 에이전트는 compaction으로 접는다

에이전트는 스텝이 쌓일수록 히스토리가 부풀어 로트가 누적됩니다. 그래서 일정 길이를 넘으면 지난 대화·툴 출력을 요약(compaction)해 핵심만 남기고 원본은 버립니다. "무엇을 했고, 무엇을 알아냈고, 지금 목표는 무엇인가"만 남기면, 컨텍스트를 좁게 유지하면서도 맥락을 잃지 않습니다. (자세한 기법은 이 블로그의 컨텍스트 compaction 편을 참고하세요.)

정리: 네 기법의 공통 목표는 하나입니다 — 토큰을 아끼는 게 아니라 '신호 대 잡음비'를 지키는 것. 창이 남아돌아도, 잡음이 많으면 성능은 떨어집니다.

7. 흔한 실수 · 팁

흔한 실수왜 문제인가대신 이렇게
창이 크니 문서를 다 넣는다 디스트랙터가 늘어 로트가 심해진다. 비용·지연도 커진다 리랭킹 후 상위 소수만. 근거가 적으면 적게 넣는다
needle 테스트를 상식 문장으로 함 모델이 사전지식으로 맞혀서 로트가 안 보인다 컨텍스트를 봐야만 아는 고유 사실로 바늘을 만든다
공칭 창 크기를 운영 상한으로 씀 200K 창이라도 유효는 그 절반 안팎일 수 있다 직접 측정해 유효 컨텍스트로 상한을 잡는다
중요한 근거를 가운데 묻음 lost in the middle으로 무시된다 핵심은 앞·뒤 끝에 배치, 질문은 맨 뒤에
에이전트 히스토리를 계속 쌓기만 함 스텝마다 잡음이 누적돼 후반부 판단이 나빠진다 주기적 compaction으로 핵심만 남기고 접는다
top-k만 늘려 리콜을 챙김 리콜은 올라도 정밀도가 떨어져 정답이 묻힌다 넓게 검색·좁게 주입. 임계값 컷을 둔다

한 가지 더. 로트는 과제에 따라 다르게 나타납니다. 단순 사실 검색은 비교적 잘 버티지만, "여러 문서를 종합해 추론"하는 과제(multi-hop)는 훨씬 빨리 무너집니다. 그러니 "우리 모델은 128K까지 괜찮더라"를 모든 과제에 일반화하지 마세요. 실제 프로덕션 과제와 최대한 닮은 형태로 측정해야 합니다.

8. 마무리 (TL;DR)

  • 컨텍스트 로트 = 창 한계에 닿기 전부터 입력이 길어질수록 정확도가 조용히 떨어지는 현상. 오버플로(에러)와 달리 에러가 안 나서 놓치기 쉽다.
  • Chroma "Context Rot"는 프런티어 모델 18종 전부에서 이 열화를 확인했고, Databricks 실험에선 Llama-3.1-405B가 32K부터 꺾였다. 창 크기 ≠ 제대로 쓰는 양.
  • lost in the middle: 정답이 가운데 있으면 놓친다(U자 곡선). → 중요한 건 앞·뒤 끝에 배치.
  • 디스트랙터(비슷한 오답)는 길이가 늘수록 적극적으로 오답을 끌어당긴다. → 많이가 아니라 깨끗하게.
  • 실전 처방: ① 리랭킹으로 top-k 축소 ② 임계값으로 디스트랙터 컷 ③ 핵심을 앞·뒤에 배치 ④ 에이전트는 compaction으로 접기.
  • 남의 벤치마크 말고 내 모델·내 데이터로 유효 컨텍스트를 직접 측정해 운영 상한을 잡자. 바늘은 반드시 고유 사실로.
