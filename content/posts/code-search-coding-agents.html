1. 도입 — 에이전트 작업의 절반은 “찾기”다

코딩 에이전트에게 “로그인 실패할 때 세션이 안 지워지는 버그 좀 고쳐 줘”라고 시켜 보면, 실제로 코드를 쓰는 시간은 얼마 안 됩니다. 대부분의 턴은 파일을 뒤지는 데 씁니다. 후보 파일을 찾고, 열어 보고, 아니면 다시 찾고. 이 탐색 단계가 길어질수록 컨텍스트는 쓸모없는 코드로 채워지고, 토큰 비용은 올라가고, 정작 중요한 파일이 컨텍스트 뒤쪽으로 밀려납니다.

그래서 “에이전트가 코드를 어떻게 찾느냐”는 취향 문제가 아니라 성능과 비용을 동시에 결정하는 아키텍처 선택입니다. 그런데 업계를 대표하는 두 도구가 정반대 답을 내놓고 있습니다.

  • Claude Code는 인덱스를 아예 안 만듭니다. 초기 버전엔 RAG와 로컬 vector DB가 있었지만 걷어냈습니다. 지금은 Glob으로 파일을 찾고, Grep으로 내용을 뒤지고, Read로 읽는 게 전부입니다.
  • Cursor는 반대로 갔습니다. 코드 검색 전용 임베딩 모델을 직접 학습시켰고, 이걸 붙였더니 질의 응답 정확도가 모델 평균 12.5% 올랐다고 공개했습니다.

여기에 2026년 8월 13일, MongoDB 산하 Voyage AI가 voyage-code-4를 공개하면서 이 논쟁이 다시 뜨거워졌습니다. 기존 코드 임베딩 모델과 다른 점이 하나 있는데, 실제 이슈를 고친 pull request의 검색 패턴으로 학습시켜서 “코딩 에이전트가 코드를 찾는 방식”에 맞췄다고 못 박은 겁니다. 같은 주에 “grep의 대체재는 도구 하나가 아니라 셋이다” 같은 실무자 글이 여럿 돌았고, 코드 그래프를 MCP 서버로 붙이는 도구들도 계속 쏟아졌습니다.

이 글에서는 세 가지 방식이 각각 어떤 질문에 강하고 어디서 무너지는지를 정리하고, 벤치마크 숫자가 실제로 무슨 뜻인지 읽어 본 다음, 셋을 하나의 도구 세트로 묶는 실전 설계까지 갑니다.

미리 말하는 결론. 셋 중 하나를 고르는 문제가 아닙니다. 질의의 모양이 답을 정하고, 에이전트에게 세 가지를 도구로 쥐어 준 다음 스스로 고르게 하는 게 2026년의 실무 합의입니다. 대신 각 도구가 언제 거짓말을 하는지는 만드는 사람이 알고 있어야 합니다.

2. 배경 — 문서 RAG 지식이 코드에서 깨지는 지점

RAG(retrieval-augmented generation, 검색으로 가져온 내용을 프롬프트에 붙여 답하게 하는 방식)를 사내 문서로 한 번쯤 만들어 봤다면 절차는 익숙할 겁니다. 문서를 청크(chunk, 검색 단위로 잘라 놓은 조각)로 자르고, 임베딩 모델로 벡터를 만들고, 벡터 DB에 넣고, 질문이 오면 가장 가까운 청크를 꺼내 붙입니다.

이 파이프라인을 코드에 그대로 가져오면 문서에는 없던 문제가 셋 생깁니다.

① 코드의 의미는 청크 밖에 있습니다. 함수 하나의 뜻은 시그니처, 본문, import 목록, 그리고 저 멀리 있는 호출자까지 합쳐져야 완성됩니다. 청킹은 이 실을 끊습니다. refund() 함수 본문만 떼어 놓으면 “이게 결제 취소랑 무슨 관계지?”를 알 수 없습니다. 문서라면 문단 하나로도 뜻이 서지만, 코드는 잘 안 그렇습니다.

② 인덱스는 커밋하는 순간 낡습니다. 사내 위키는 하루에 몇 번 바뀌지만 저장소는 매 커밋마다 바뀝니다. 게다가 브랜치를 갈아타면 파일 내용이 통째로 달라집니다. 인덱스는 원본의 사본이라, 사본을 계속 따라붙게 만드는 일 자체가 하나의 시스템이 됩니다. 재인덱싱 파이프라인, 캐시 무효화, 브랜치별 인덱스… 운영해야 할 것이 늘어납니다.

③ 코드에는 “정확히 이 이름”이 존재합니다. 문서 검색에선 “환불”로 “결제 취소”를 찾아내는 게 미덕이지만, 코드에서 SessionStore를 찾을 때는 정확히 그 문자열이 답입니다. 이럴 때 의미 유사도는 오히려 비슷하지만 다른 것들을 잔뜩 데려옵니다.

한 줄 요약. 문서 RAG는 “뜻이 비슷한 걸 찾아 줘”가 기본값이고, 코드 검색은 “이름이 정확한 것 + 구조로 이어진 것”이 기본값입니다. 출발점이 다르니 도구도 달라집니다.

3. 세 갈래 — 어휘·구조, 의미, 그래프

2026년 현재 코드 검색은 세 갈래로 정리됩니다. 각각을 “어떤 질문을 잘 받는가”로 이해하면 헷갈리지 않습니다.

① 어휘·구조 검색 — 인덱스 없는 쪽

가장 단순하고, 놀랍게도 가장 널리 쓰입니다. ripgrep은 문자열과 정규식으로 저장소를 훑습니다. ast-grep은 한 걸음 더 나아가 파일을 tree-sitter로 파싱한 구문 트리에서 코드처럼 생긴 패턴을 찾습니다. $METAVAR 자리에 아무 표현식이나 들어갈 수 있게 해 두는 식입니다.

{{< highlight bash >}} # ripgrep: 문자열/정규식 — 이름을 정확히 알 때 rg -n --type py 'class SessionStore\b' # ast-grep: 구문 구조 — "await 없이 호출된 fetch"처럼 형태로 찾을 때 # $ARG 는 아무 표현식이나 매칭되는 메타 변수입니다 ast-grep --pattern 'fetch($ARG)' --lang ts # 정의로 점프하고 싶다면 LSP (에디터가 쓰는 그 기능) # textDocument/definition, textDocument/references {{< /highlight >}}

Claude Code가 택한 길이 이쪽입니다. 개발자 Boris Cherny는 초기 버전의 RAG와 로컬 vector DB를 걷어낸 이유로 “대체로 agentic search가 더 낫고, 더 단순하며, 보안·프라이버시·최신성·신뢰성 문제가 없다”를 들었습니다. 여기서 agentic search는 미리 만들어 둔 인덱스에서 꺼내 오는 대신, 모델이 검색 도구를 루프 안에서 여러 번 직접 호출하며 좁혀 가는 방식을 말합니다. 사람이 낯선 저장소를 뒤지는 방식과 거의 같습니다.

이 방식의 진짜 장점은 정확도보다 운영 부담이 0에 가깝다는 데 있습니다. 임베딩 모델 교체, 인덱스 동기화 지연, 청킹 전략 튜닝, 인덱스 유출 대응이 통째로 사라집니다. 코드를 외부로 보내지 않아도 되니 보안 심사도 훨씬 가볍습니다.

② 의미 검색 — 이름을 모를 때

반대편의 논리는 이렇습니다. grep은 이미 답을 알 때만 쓸모가 있다는 겁니다. “세션 만료를 어디서 처리하지?”라는 질문에 grep으로 접근하면 session, expire, ttl, timeout을 차례로 던져 보며 매번 수십 개의 매칭을 읽어야 합니다. 그 읽기 하나하나가 토큰입니다.

Cursor는 이 지점을 데이터로 반박했습니다. 자체 임베딩 모델을 붙였을 때 질의 응답 정확도가 모델 평균 12.5% 올랐고(모델에 따라 6.5%~23.5%), 에이전트가 작성한 코드가 살아남는 비율도 올랐다고 밝혔습니다. 특히 파일 1,000개가 넘는 대형 저장소에서 효과가 컸습니다. 학습 방법이 재밌는데, 에이전트의 실제 세션 기록을 데이터로 씁니다. 에이전트가 헤매다 결국 정답 파일에 도달한 궤적을 놓고 “어느 시점에 무엇이 먼저 나왔어야 했나”를 LLM으로 순위 매긴 뒤, 그 순위에 임베딩 유사도를 맞추도록 학습시킵니다.

8월 13일 공개된 voyage-code-4도 같은 발상입니다. 실제 이슈 해결 pull request의 검색 패턴으로 학습했고, 컨텍스트 길이 32,000 토큰에 2048·1024·512·256차원을 골라 쓸 수 있는 Matryoshka 임베딩(하나의 벡터에서 앞부분만 잘라 써도 성능이 유지되도록 학습한 방식)을 지원합니다. 자체 발표 기준으로 에이전트형 코드 검색 벤치마크에서 Cohere Embed v4 대비 평균 28.25%, Gemini Embedding 2 대비 31.03% 앞섰다고 합니다.

벤더 숫자를 읽는 법. 위 수치는 모델을 만든 쪽이 자기 벤치마크에서 잰 값입니다. 방향(에이전트 워크로드에 맞춘 학습이 도움이 된다)은 믿을 만하지만, 절대값을 그대로 우리 저장소에 옮겨 적으면 안 됩니다. 이런 발표를 볼 때는 항상 “어떤 질의 분포에서 쟀나”를 먼저 확인하세요.

③ 코드 그래프 — 관계를 묻는 질문

세 번째 갈래는 검색이라기보다 구조를 미리 계산해 두는 쪽입니다. tree-sitter로 모든 파일을 파싱해서 “어떤 함수가 어디 정의됐고, 누가 누구를 호출하고, 어떤 심볼이 어디서 참조되는지”를 그래프로 만들어 둡니다. 그리고 이 그래프를 MCP 서버로 노출해 에이전트가 질의하게 합니다.

이 방식이 압도적으로 강한 질문이 있습니다. “이 함수 시그니처를 바꾸면 어디가 깨지나?” grep으로 하면 동명이인 함수까지 다 걸리고, 임베딩으로 하면 애초에 답할 수 있는 질문이 아닙니다. 그래프에서는 엣지를 따라가면 끝입니다.

4. 숫자로 보는 트레이드오프

공개된 연구 중 트레이드오프를 가장 정직하게 보여 주는 건 Codebase-Memory(arXiv:2603.27277)입니다. tree-sitter 기반 코드 지식 그래프를 MCP로 붙인 뒤, 파일을 직접 탐색하는 에이전트와 실제 저장소 31곳에서 비교했습니다.

결과가 재밌습니다. 답변 품질은 파일을 직접 뒤지는 에이전트가 92%, 그래프 쪽이 83%로 그래프가 졌습니다. 대신 토큰은 10분의 1, 도구 호출은 2.1분의 1만 썼습니다. 즉 품질 9%p를 내주고 비용을 한 자릿수 배수로 줄인 겁니다. 호출 관계처럼 그래프에 딱 맞는 질문에서는 파일 탐색 쪽을 따라잡거나 앞섰습니다.

“정확도가 곧 정답”이 아니라는 게 핵심입니다. 하루에 수천 번 도는 자동화 파이프라인이라면 10배 저렴한 83%가 이깁니다. 사람이 지켜보며 한 번 돌리는 어려운 리팩터링이라면 92%가 이깁니다.

임베딩 쪽에도 비슷하게 냉정한 결과가 있습니다. CORE-Bench(arXiv:2606.11864)는 코드 검색 능력을 코드 이해, 이슈-수정 위치 찾기, 넓은 맥락 검색의 세 층위로 나눠 18만 건 이상의 질의로 측정했는데, 전통적인 코드 검색 과제에서 에이전트형 코드 검색으로 넘어가는 순간 임베딩 모델의 성능이 크게 떨어졌습니다. 기존 임베딩 모델을 그대로 코딩 에이전트에 붙이면 기대만큼 안 나온다는 뜻이고, 동시에 Cursor와 Voyage가 왜 굳이 전용 모델을 학습시켰는지를 설명해 줍니다.

또 하나. ContextBench(arXiv:2602.05892)는 저장소 66곳, 8개 언어에서 1,136개의 이슈 해결 과제에 사람이 직접 정답 맥락을 달아 두고 에이전트의 궤적을 추적했습니다. 결론 두 개가 뼈아픕니다. 정교한 스캐폴딩을 얹어도 맥락 검색 성능은 조금밖에 안 올랐고, LLM과 에이전트 모두 일관되게 정밀도(precision)보다 재현율(recall)을 택했습니다. 쉽게 말해 에이전트는 “일단 많이 가져오고 보자”는 성향이 있습니다. 이게 바로 컨텍스트가 부풀고 토큰이 새는 근원입니다.

6. 실전 — 하이브리드 검색 도구 세트 만들기

직접 에이전트를 만든다면 핵심은 “좋은 검색기를 하나 고르기”가 아니라 세 도구를 잘 설명해서 쥐어 주기입니다. 모델은 도구 설명(description)을 보고 고릅니다. 설명이 흐리면 그냥 익숙한 것만 씁니다.

{{< highlight python >}} # 에이전트에 붙일 도구 정의. 설명에 "언제 쓰는지"를 못 박는 게 핵심입니다. TOOLS = [ { "name": "grep_code", "description": ( "정규식으로 저장소를 검색합니다. 찾는 심볼·문자열의 정확한 이름을 " "알 때 먼저 쓰세요. 인덱스를 거치지 않아 항상 현재 파일 상태를 봅니다." ), "input_schema": { "type": "object", "properties": { "pattern": {"type": "string", "description": "정규식"}, "glob": {"type": "string", "description": "예: **/*.py"}, }, "required": ["pattern"], }, }, { "name": "semantic_search_code", "description": ( "자연어 설명으로 관련 코드를 찾습니다. 찾는 대상의 '이름을 모를 때'만 " "쓰세요. 결과는 후보일 뿐이므로 반드시 grep_code나 read_file로 " "확인해야 합니다. 인덱스 기반이라 최근 커밋이 빠져 있을 수 있습니다." ), "input_schema": { "type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"], }, }, { "name": "find_references", "description": ( "심볼의 정의와 호출자를 코드 그래프에서 찾습니다. '이걸 고치면 무엇이 " "영향받나', '누가 이 함수를 부르나' 같은 관계 질문에 쓰세요." ), "input_schema": { "type": "object", "properties": { "symbol": {"type": "string"}, "direction": {"type": "string", "enum": ["callers", "callees"]}, }, "required": ["symbol"], }, }, ] {{< /highlight >}}

여기서 자주 놓치는 게 의미 검색 도구 설명에 “후보일 뿐이니 검증하라”를 넣는 것입니다. 이 한 줄이 있고 없고에 따라 에이전트가 낡은 인덱스 결과를 그대로 믿고 존재하지 않는 파일을 수정하려 드는 사고가 갈립니다.

인덱스가 낡았는지 스스로 알려 주기

의미 검색을 붙이기로 했다면, 인덱스가 어느 커밋 기준인지 결과에 같이 실어 보내세요. 모델은 이 정보를 받으면 의외로 잘 판단합니다.

{{< highlight python >}} import subprocess def index_staleness(): """인덱스가 만들어진 커밋과 현재 HEAD 사이에 몇 개 파일이 바뀌었는지.""" head = subprocess.run( ["git", "rev-parse", "HEAD"], capture_output=True, text=True ).stdout.strip() indexed = load_indexed_commit() # 인덱싱 시점에 저장해 둔 커밋 해시 if indexed == head: return {"stale": False, "changed_files": []} # 인덱싱 이후 바뀐 파일 목록 — 이 파일들은 인덱스를 믿으면 안 됩니다 diff = subprocess.run( ["git", "diff", "--name-only", f"{indexed}..{head}"], capture_output=True, text=True, ).stdout.split() return {"stale": True, "changed_files": diff} def semantic_search_code(query: str): hits = vector_index.search(query, top_k=8) status = index_staleness() if status["stale"]: # 바뀐 파일에서 나온 결과에는 경고를 붙여 모델이 재확인하게 유도합니다 changed = set(status["changed_files"]) for h in hits: if h["path"] in changed: h["warning"] = "이 파일은 인덱싱 이후 수정됨 — read_file로 확인 필요" return {"results": hits, "index_commit_behind": status["stale"]} {{< /highlight >}}

임베딩을 직접 만들어 본다면

코드 임베딩 API 자체는 문서 임베딩과 쓰는 법이 같습니다. 다만 input_type으로 질의와 문서를 구분해 주는 걸 잊지 마세요. 이걸 빼면 검색 품질이 눈에 띄게 떨어집니다.

{{< highlight python >}} import voyageai vo = voyageai.Client() # 인덱싱할 때: 코드 청크는 document 로 docs = vo.embed( ["def refund(order_id: str) -> Refund:\n ...", "..."], model="voyage-code-4", input_type="document", # 질의와 문서를 다르게 임베딩합니다 output_dimension=512, # Matryoshka — 저장 비용을 줄이고 싶으면 낮춰도 됩니다 ).embeddings # 검색할 때: 자연어 질의는 query 로 q = vo.embed( ["결제 취소했을 때 재고를 되돌리는 로직"], model="voyage-code-4", input_type="query", ).embeddings[0] {{< /highlight >}}
청킹은 줄 수가 아니라 구문 단위로. 코드를 “200줄씩” 자르면 함수 한가운데가 잘려 나갑니다. tree-sitter로 파싱해 함수·클래스 경계로 자르고, 각 청크 앞에 파일 경로와 소속 클래스명을 한 줄 붙여 주세요. 이 한 줄이 “이 함수가 어디 속한 무엇인지”를 임베딩에 넣어 줍니다.

7. 흔한 실수 · 팁

실수 1 — 인덱스를 만들어 놓고 갱신 파이프라인을 안 만든다. 데모에서는 완벽하게 동작합니다. 2주 뒤 팀원들이 “에이전트가 자꾸 없는 함수를 부른다”고 합니다. 인덱스를 붙이는 결정은 인덱스를 계속 살아 있게 유지하는 운영 작업을 떠안는 결정과 같습니다. 그럴 자신이 없으면 어휘 검색으로 시작하세요.
실수 2 — 검색 결과를 통째로 컨텍스트에 붓는다. ContextBench가 보여 준 대로 에이전트는 정밀도보다 재현율을 택하는 성향이 있습니다. 여기에 검색기까지 넉넉하게 뱉으면 컨텍스트가 순식간에 찹니다. 도구가 반환하는 결과는 파일 경로 + 매칭 줄 번호 + 앞뒤 2~3줄로 제한하고, 전문은 모델이 read_file로 요청할 때만 주세요.
실수 3 — grep 한 번으로 끝났다고 생각한다. agentic search의 힘은 반복에서 나옵니다. 한 번 검색하고 끝내면 grep의 약점만 그대로 떠안습니다. 에이전트가 검색 → 읽기 → 재검색을 여러 번 돌 수 있도록 턴 제한과 도구 호출 예산을 넉넉히 잡아 주세요.
실수 4 — 대형 저장소에서 정규식을 안전장치 없이 던진다. rg '.*' 같은 패턴 하나면 수만 줄이 컨텍스트로 밀려듭니다. 검색 도구 쪽에 최대 결과 수와 파일당 최대 매칭 수를 하드 리밋으로 걸고, 넘치면 “결과가 너무 많습니다. 패턴을 좁히세요”라고 되돌려 주는 게 좋습니다. 모델은 이 피드백을 받으면 알아서 좁힙니다.
실수 5 — 코드를 외부로 보내는 걸 나중에 생각한다. 임베딩 인덱스는 코드의 사본입니다. 어디에 저장되고 누가 읽을 수 있는지가 곧 보안 심사 항목이 됩니다. Anthropic이 자사 코드베이스를 외부 인덱스에 올리기엔 너무 민감하다고 판단했던 것도 같은 이유입니다. 사내 규정을 먼저 확인하고 아키텍처를 고르세요. 순서를 바꾸면 다 만들고 나서 갈아엎게 됩니다.
팁 — 우리 저장소로 직접 재 보세요. 실제로 있었던 이슈 20~30개를 모아 “이 이슈를 고치려면 어느 파일을 봐야 하나”의 정답을 손으로 달아 두면 훌륭한 평가 세트가 됩니다. 그다음 방식별로 정답 파일이 상위 k개 안에 들어오는 비율과 거기 도달할 때까지 쓴 토큰을 같이 재세요. 이 두 숫자를 놓고 보면 남의 벤치마크가 필요 없어집니다.
팁 — 어휘 검색부터, 그다음에 저울질. 인덱스 없는 구성으로 먼저 굴려 보고, 위 평가 세트에서 실패하는 질의가 어떤 종류인지 보세요. “이름을 모르는 질문”이 계속 실패하면 그때 의미 검색을 얹고, “영향 범위 질문”이 실패하면 그래프를 얹으면 됩니다. 아프기 전에 붙인 인덱스는 대부분 짐이 됩니다.

8. 마무리 (TL;DR)

  • 코딩 에이전트 작업의 절반은 검색입니다. 검색 방식이 정확도와 토큰 비용을 동시에 결정하므로, 나중에 튜닝할 항목이 아니라 처음에 정할 아키텍처입니다.
  • 세 갈래를 질문 유형으로 나눠 기억하세요. 어휘·구조 검색(ripgrep·ast-grep·LSP)은 “이름을 알 때”, 의미 검색(임베딩)은 “개념만 알 때”, 코드 그래프는 “관계를 물을 때”입니다.
  • Claude Code는 인덱스를 걷어냈습니다. agentic search가 대체로 더 낫고 단순하며 보안·프라이버시·최신성·신뢰성 문제가 없다는 판단이었습니다. 정확도만의 승부가 아니라 운영 부담까지 포함한 결정입니다.
  • 반대편에는 데이터가 있습니다. Cursor는 전용 임베딩 모델로 응답 정확도를 평균 12.5% 올렸다고 밝혔고, 2026-08-13 공개된 voyage-code-4는 실제 이슈 해결 PR의 검색 패턴으로 학습한 에이전트 전용 코드 임베딩 모델입니다.
  • 연구 결과는 “공짜 점심 없음”을 가리킵니다. Codebase-Memory는 코드 그래프가 품질 92%→83%를 내주는 대신 토큰 1/10, 도구 호출 1/2.1을 쓴다고 보고했습니다. CORE-Bench는 일반 임베딩 모델이 에이전트형 코드 검색에서 크게 떨어진다는 걸, ContextBench는 에이전트가 정밀도보다 재현율을 택한다는 걸 보여 줍니다.
  • 실무 답은 하이브리드입니다. 셋을 도구로 쥐어 주고, 설명에 “언제 쓰는지”와 “결과는 후보일 뿐”을 못 박고, 마지막에 반드시 파일을 읽어 검증하게 하세요.
  • 인덱스는 사본이고 사본은 낡습니다. 붙이기로 했다면 인덱스 기준 커밋을 결과에 같이 실어 보내고, 갱신 파이프라인을 함께 만드세요. 그럴 여력이 없으면 어휘 검색으로 시작하는 게 정답에 가깝습니다.
