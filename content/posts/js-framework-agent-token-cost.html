1. 도입 — 같은 앱을 60번 만들었더니

프레임워크 논쟁은 웹 개발의 오랜 스포츠입니다. 번들 크기, 렌더링 성능, DX(개발자 경험)… 그런데 이번 주에는 완전히 새로운 잣대 하나가 링에 올라왔습니다. "코딩 에이전트가 그 프레임워크로 앱을 만들 때 토큰이 얼마나 드는가"입니다.

웹 성능 분야에서 오래 활동한 엔지니어 Nolan Lawson이 10월 28일 공개한 The AI cost of JavaScript frameworks는 실험 하나로 이 질문에 숫자를 붙였습니다. Claude Code(Opus 5.5)에게 같은 스펙, 같은 테스트, 같은 한 줄짜리 프롬프트를 주고, 프레임워크 이름만 바꿔 가며 포켓몬 도감(Pokédex) 앱을 만들게 한 겁니다. 스택은 Next.js부터 vanilla JS까지 12종, 스택마다 5번씩, 총 60번. 결과는 선명했습니다. 가장 싼 Nuxt는 중앙값 385만 토큰, 가장 비싼 Angular는 976만 토큰 — 약 2.5배 차이입니다.

이 글은 Hacker News 1면에 올라 약 470포인트, 댓글 380개가 넘는 논쟁을 불렀습니다. 그리고 더 흥미로운 일이 이어졌습니다. 저자가 하네스 전체와 원시 결과를 공개해 둔 덕분에, 공개 닷새 만에 다른 개발자가 포크로 재실험을 돌려 원래 결론을 뒤흔드는 교란 변수를 찾아낸 겁니다.

그래서 오늘은 순위표만 훑고 끝내지 않습니다. 에이전트 토큰 고지서가 쌓이는 구조부터, 이 벤치마크의 밀폐(hermetic) 설계, 그리고 "에이전트 벤치마크 숫자를 어떻게 의심해야 하는가"까지 — 주니어 엔지니어가 앞으로 수없이 마주칠 종류의 숫자를 읽는 법을 연습해 봅니다.

2. 배경 — 에이전트 토큰 고지서는 어떻게 쌓이나

먼저 "앱 하나 만드는데 토큰 976만 개"라는 숫자가 어디서 오는지부터 이해해야 합니다. 976만 토큰이면 책 수십 권 분량인데, 에이전트가 정말 그만큼 '읽고 쓰는' 걸까요?

절반만 맞습니다. 코딩 에이전트는 루프로 동작합니다. 모델이 도구 호출(파일 읽기, 명령 실행…)을 결정하면 하네스가 실행하고, 그 결과를 대화에 붙여 모델을 다시 호출합니다. 이게 한 '턴'이고, npm test가 통과할 때까지 수십~수백 턴을 돕니다. 중요한 건 LLM API가 무상태(stateless)라는 점입니다. 매 턴마다 지금까지의 대화 전체 — 시스템 프롬프트, 스펙, 읽은 파일, 도구 출력 전부 — 를 다시 보내야 합니다.

그래서 총 토큰은 대략 이렇게 쌓입니다:

총 토큰 ≈ Σ (턴마다 다시 보내는 컨텍스트) + 새 입력 + 출력

턴 수가 늘수록, 그리고 턴마다 끌고 다니는 컨텍스트가 클수록 비용이 곱으로 늘어나는 구조입니다. 실제로 이번 벤치마크에서 전체 토큰의 95% 안팎이 캐시 읽기(cache read)였습니다. 매 턴 재전송되는 똑같은 앞부분을 프롬프트 캐싱이 받아 주는 덕에 단가는 기본 입력의 10% 수준으로 떨어지지만(이 블로그의 프롬프트 캐싱 편 참고), 토큰 수 자체는 고스란히 쌓입니다.

이 구조를 알면 "프레임워크가 토큰 비용에 영향을 준다"는 말이 자연스러워집니다. 프레임워크가 다르면 에이전트가 읽어야 하는 문서·설정·코드의 양이 다르고, 막히고 되돌아가는 횟수(턴 수)가 다르기 때문입니다. 비유하자면, 외국에서 운전하기와 같습니다. 운전 실력(모델)이 같아도 표지판이 익숙한 나라(훈련 데이터에 많은 프레임워크)에서는 내비게이션을 힐끔 보고 끝나지만, 낯선 나라에서는 지도를 펴 놓고 한참 읽어야 하죠. 그 '지도 읽는 시간'이 전부 토큰입니다.

3. 해부 ① — 밀폐(hermetic) 벤치마크 설계

이 벤치마크가 HN에서 진지하게 받아들여진 이유는 결과보다 설계의 꼼꼼함에 있습니다. 변인 통제를 어떻게 했는지 뜯어보면, 에이전트 평가(밀폐 평가 편에서 다룬 개념)의 좋은 실습 교재가 됩니다.

조건은 모두에게 동일합니다. 에이전트는 같은 SPEC.md(로컬 PokeAPI 기반 포켓몬 도감), 같은 Playwright 인수 테스트, 같은 디자인 토큰을 받고, 프롬프트는 프레임워크 이름만 다른 딱 한 줄입니다:

{{< highlight text >}} Implement the app described in SPEC.md using {framework}. Use the latest stable version. Work autonomously until `npm test` passes. {{< /highlight >}}

그리고 격리가 철저합니다. 각 실행의 흐름은 이렇습니다:

주니어 입장에서 눈여겨볼 설계 포인트 세 가지만 짚습니다.

첫째, 채점과 생성의 분리. 에이전트가 만든 결과물 중 app/ 디렉터리만 깨끗한 컨테이너로 복사해 원본 테스트를 다시 돌립니다. 에이전트가 테스트를 고치거나 데이터를 구워 넣어도(에이전트는 실제로 이런 유혹에 약합니다 — 리워드 해킹 편 참고) 점수에 반영되지 않습니다. 심지어 빌드 후 API 데이터를 바꿔치기한 상태로 테스트를 한 번 더 돌려서, 빌드 타임에 데이터를 박제한 앱을 잡아냅니다.

둘째, 정답과 하네스 숨기기. 에이전트에게 건네는 저장소는 커밋 하나짜리로 새로 내보낸(export) 사본입니다. git 히스토리, 저자가 만든 참조 구현(gold), 측정 코드가 에이전트 눈에 띄지 않습니다. 컨테이너 안에서 pokeapi.co는 localhost로 묶여 있어 몰래 실서버를 쓸 수도 없습니다.

셋째, 프레임워크별 공식 AI 도구도 조건의 일부. 각 에이전트에는 그 프레임워크 공식 문서가 권하는 MCP 서버나 스킬이 설치됩니다(Angular CLI MCP, Nuxt MCP, Svelte 플러그인 등). 도구가 없는 프레임워크는 그냥 없이 갑니다. 불공평해 보이지만 저자는 의도적이라고 말합니다 — 그 프레임워크를 고르면 따라오는 생태계 전체가 측정 대상이라는 거죠.

결과 표의 핵심 열만 추리면 이렇습니다(스택별 5회 중앙값, 토큰 많은 순 역정렬):

표에서 읽어낼 포인트를 하나씩 봅니다.

60회 전부 테스트를 통과했습니다. 12개 스택 × 5회 모두 npm test 통과, Lighthouse 접근성 점수도 전부 100입니다. 즉 이 벤치마크의 차이는 "에이전트가 할 수 있느냐"가 아니라 "얼마나 들었느냐"에 있습니다. 능력(capability)이 상향 평준화되면 다음 경쟁 축은 효율이라는, 에이전트 엔지니어링 전반의 흐름과 같습니다.

vanilla는 싸지 않았습니다. "프레임워크 없이 가면 에이전트가 문서 읽을 일도 없으니 제일 싸겠지"라는 직관은 틀렸습니다. vanilla(5.00M)는 Nuxt·Astro·Hono+htmx보다 비쌌습니다. 라우팅, 데이터 로딩 같은 기반 설비를 에이전트가 손수 다시 짓느라 턴을 쓰기 때문입니다. 프레임워크가 제공하는 건 코드만이 아니라 모델 가중치 속에 이미 들어 있는 관례이기도 합니다.

비싼 스택들의 사연은 제각각입니다. 저자의 트랜스크립트 분석에 따르면 대략 세 유형입니다:

  • 낯섦 — Gracile+Lit(9.04M)은 훈련 데이터에 거의 없는 신생 프레임워크라, 에이전트가 node_modules 안의 소스 코드를 직접 읽어 가며 사용법을 역공학했습니다. 읽은 게 전부 컨텍스트에 쌓여 매 턴 재전송됩니다.
  • 세대 격차 — SvelteKit(8.53M)에서 에이전트는 Svelte 5 마이그레이션 문서를 반복해서 읽었습니다. 저자는 모델이 알고 있는 Svelte(4 시절 문법)와 최신 안정판의 간극 때문일 거라고 추정합니다. 모델은 아는데 버전이 달라진 경우가 완전히 모르는 것보다 비쌀 수 있다는 흥미로운 사례입니다.
  • 세리머니 — Angular(9.76M)는 같은 앱에 코드가 2,009줄로 가장 많았고(최소인 Hono+htmx의 1.47배), 턴도 117번으로 가장 많았습니다. 쓸 코드가 많으면 출력 토큰과 턴 수가 같이 늘어납니다.

여기서 직접 계산해 볼 만한 파생 지표가 하나 있습니다. 코드 한 줄당 토큰입니다. Nuxt는 3.85M ÷ 1,415줄 ≈ 2,700토큰/줄인데, SvelteKit은 8.53M ÷ 1,611줄 ≈ 5,300토큰/줄로 거의 2배입니다. 코드량 차이(최대 1.47배)보다 줄당 토큰 차이(최대 1.95배)가 큽니다. 즉 비용을 가르는 건 "코드를 얼마나 쓰느냐"보다 "한 줄 쓰기까지 얼마나 헤매느냐" — 익숙함이 더 큰 지렛대라는 뜻입니다.

토큰 비용과 런타임 성능은 별개의 축입니다. 에이전트에게 싼 스택이 사용자에게도 좋은 건 아닙니다. Next.js는 토큰으로는 중위권(4.99M)인데 전송 JS는 142KiB로 가장 많았고, Gracile은 토큰으로는 최하위권인데 JS는 8KiB로 최상위권입니다. Astro는 둘 다 좋았습니다(4.13M, JS 0KiB). 선택은 결국 두 축을 같이 놓고 해야 합니다.

비용 열 읽을 때 주의: 저자는 Claude Max 플랜에서 실행했고, 달러 숫자는 Claude Code가 보고한 API 환산 가격입니다. 실제 청구서가 아니라 사용량 비교용 명목값입니다. 또 캐시 읽기 단가(기본 입력의 ~10%)가 적용된 금액이므로, 캐싱 없는 환경이라면 차이가 훨씬 커집니다.

5. 해부 ③ — 공개 5일 만에 나온 반론들

여기까지가 원문 내용입니다. 그런데 이 벤치마크의 가장 교육적인 부분은 공개 이후에 벌어진 일입니다. 저자가 하네스와 원시 결과(트랜스크립트, 측정 로그 전부)를 공개한 덕분에, 커뮤니티가 숫자를 직접 검증하기 시작했습니다.

11월 2일, 한 개발자가 포크로 재실험을 돌리고 이슈 #1을 올렸습니다. 두 가지 발견이 핵심입니다.

발견 ① — '실패'한 Angular 2회는 사실 테스트를 통과했습니다. 원 결과에서 Angular 5회 중 2회는 측정이 안 됐는데, 원시 데이터를 열어 보면 두 실행 모두 final_test_exit=0(54/54 통과)입니다. 실패는 측정 단계에서 났습니다. Angular SSR 서버가 허용 목록에 없는 Host 헤더를 400으로 거절하는데, 테스트는 localhost로 돌지만 측정 프록시는 app.localhost:8443으로 접근했기 때문입니다. 에이전트 입장에서는 보이지 않는 실패였죠. (이 글을 쓰며 공개된 원시 데이터에서 두 실행의 run-info.txt를 직접 확인했는데, 실제로 둘 다 테스트 통과가 기록되어 있습니다.)

발견 ② — 렌더링 모드가 교란 변수(confounder)였습니다. 스펙은 렌더링 전략을 에이전트 자유에 맡겼는데, 결과적으로 측정된 54개 앱 중 52개가 서버 렌더링(SSR)을 골랐고, 클라이언트 렌더링(CSR) SPA를 만든 건 vanilla 5회 전부와 Angular 1회뿐이었습니다. 즉 성능 비교표의 상당 부분은 "프레임워크 간 비교"가 아니라 "SSR 대 CSR 비교"였던 셈입니다.

포크는 렌더링 모드를 프롬프트에 명시하고(ssr/csr), 공식 도구를 켜고 끄는 조건을 추가해 Angular·Next.js·SvelteKit·vanilla로 파일럿을 돌렸습니다. 결과가 흥미롭습니다:

  • 모드를 고정하자 Angular는 더 이상 일관되게 최고가가 아니었고, Angular CSR은 오히려 가장 싼 셀이었습니다.
  • 같은 조건의 반복 실행 간 빌드 토큰이 ±34%씩 출렁였습니다. 중앙값 5개로 세운 순위가 흔들리기에 충분한 분산입니다.
  • 유지보수(변경 요청 4건)는 빌드의 1/5~1/8 비용이었고 프레임워크 간 차이도 작았습니다. 실무에서 대부분의 시간은 유지보수인데, 이 벤치마크는 그린필드 빌드만 측정합니다.
  • 에이전트는 설치된 공식 MCP·스킬을 거의 쓰지 않았습니다(Next.js는 한 번도). "공식 AI 도구를 깔아 주면 에이전트가 잘 쓰겠지"라는 가정도 데이터 앞에서는 흔들립니다.

별도의 통계 분석들도 비슷한 방향을 가리켰습니다. 한 분석은 12개 스택의 쌍 66개 중 60개에서 비용 범위가 겹친다고 지적했습니다 — 반면 전송 JS 크기는 거의 겹치지 않는, 훨씬 단단한 신호였습니다. 또 다른 재분석은 위에서 본 "코드량보다 익숙함이 큰 지렛대"라는 해석을 같은 표에서 끌어냈습니다.

그래서 이 벤치마크는 틀렸다는 걸까요? 반대입니다. 원 저자는 README에서 "반복 1회는 일화다", "이 결과는 그날의 생태계 전체(모델·프레임워크·문서)의 스냅숏이다"라고 한계를 먼저 못 박았고, 재현 가능한 하네스와 원시 데이터를 전부 공개했습니다. 그랬기 때문에 닷새 만에 교란 변수가 발견되고 지식이 전진한 겁니다. 폐쇄형 벤치마크였다면 "Angular는 비싸다"가 그대로 밈이 됐겠죠. 에이전트 벤치마크를 만들 때 배워야 할 건 순위표가 아니라 이 공개·반증 사이클입니다.

6. 실전 — 내 스택의 에이전트 비용 직접 재기

남의 포켓몬 도감보다 중요한 건 내 저장소입니다. 다행히 측정 원리는 간단해서, Claude Code의 stream-json 출력만 있으면 벤치마크의 토큰 회계를 그대로 따라 할 수 있습니다.

먼저 비교하고 싶은 작업을 헤드리스로 실행하면서 트랜스크립트를 남깁니다:

{{< highlight bash >}} # 같은 과제를 조건만 바꿔 실행하고, 세션 전체를 JSONL로 저장 claude -p "SPEC.md의 기능을 구현하고 npm test가 통과할 때까지 진행해" \ --output-format stream-json --verbose > transcript.jsonl {{< /highlight >}}

트랜스크립트 마지막의 result 이벤트에 세션 전체 회계가 들어 있습니다. 벤치마크의 집계 스크립트(bench/tokens.mjs)와 같은 일을 하는 파이썬 버전입니다:

{{< highlight python >}} import json, sys result = None turns = 0 with open(sys.argv[1]) as f: for line in f: ev = json.loads(line) if ev.get("type") == "result": result = ev # 마지막 result 이벤트가 최종 집계 u = result["usage"] cache_read = u.get("cache_read_input_tokens", 0) cache_write = u.get("cache_creation_input_tokens", 0) fresh_in = u.get("input_tokens", 0) out = u.get("output_tokens", 0) total = cache_read + cache_write + fresh_in + out print(f"턴 수 : {result['num_turns']}") print(f"캐시 읽기 : {cache_read:>12,} ({cache_read/total:.0%})") print(f"비캐시 입력 : {fresh_in + cache_write:>12,}") print(f"출력 : {out:>12,}") print(f"총 토큰 : {total:>12,}") print(f"보고된 비용 : ${result.get('total_cost_usd', 0):.2f}") {{< /highlight >}}

그리고 비교가 의미를 가지려면, 이 벤치마크가 보여 준 원칙을 그대로 가져옵니다:

  • 과제·완료 조건을 고정합니다. 같은 스펙, 같은 테스트, "테스트 통과까지"라는 같은 종료 조건. 조건이 다르면 토큰 비교는 무의미합니다.
  • 3회 이상 반복하고 중앙값을 씁니다. 같은 조건도 ±34%씩 출렁인다는 걸 봤습니다. 1회 실행은 데이터가 아니라 일화입니다.
  • 깨끗한 환경에서 시작합니다. 이전 실행의 산출물이나 대화가 남아 있으면 비교가 오염됩니다. 컨테이너까지는 아니어도 최소한 fresh clone + 새 세션으로.
  • 결과물 검증은 생성과 분리합니다. 에이전트가 "완료"라고 말한 것과 테스트가 통과하는 것, 그리고 (Angular 사례처럼) 테스트가 통과하는 것과 실제 배포 환경에서 동작하는 것은 각각 다른 명제입니다.

이렇게 재 보면 "우리 레거시 모듈은 에이전트한테 유난히 비싸다" 같은 사실이 숫자로 잡힙니다. 그다음 줄일 방법은 이 블로그에서 다뤘던 레퍼토리 그대로입니다 — AGENTS.md로 관례를 문서화해서 헤매는 턴을 줄이고, 도구 출력 다이어트로 턴당 컨텍스트를 줄이는 식으로요.

7. 흔한 실수 · 팁

  • 벤치마크 1회 실행으로 결론 내리기. 이번 데이터가 보여 준 반복 간 분산은 ±34%입니다. 순위가 한 번 뒤집히는 건 노이즈로도 충분히 일어납니다. 중앙값, 그리고 가능하면 범위(최소~최대)까지 같이 보세요.
  • 달러 숫자를 청구서로 읽기. 구독 플랜에서 보고되는 비용은 API 환산 명목가입니다. 또 캐싱 적용 여부에 따라 같은 토큰도 금액이 10배 가까이 달라집니다. 비교엔 토큰 수가, 그중에서도 "캐시 읽기 / 비캐시 입력 / 출력" 분해가 더 안정적인 단위입니다.
  • "프레임워크 없음 = 에이전트 비용 0"이라는 가정. vanilla가 중위권이었다는 게 이번 벤치마크의 조용한 교훈입니다. 모델이 이미 아는 관례 위에 올라타는 게, 모든 걸 손수 짓게 하는 것보다 쌉니다.
  • 공식 MCP·스킬을 깔아 주면 쓸 거라는 가정. 포크 실험에서 에이전트는 설치된 공식 도구를 거의 부르지 않았습니다. 도구를 제공했다면, 트랜스크립트에서 실제 호출 여부를 확인하세요. 안 쓰는 도구 정의는 그 자체로 토큰 비용이기도 합니다.
  • 테스트 통과를 "동작함"과 동일시하기. Angular의 Host 헤더 사례처럼, 에이전트의 성공 조건(localhost 테스트)과 실제 환경(프록시 뒤) 사이의 틈은 에이전트 눈에 보이지 않습니다. 완료 조건을 설계할 때 "에이전트가 볼 수 없는 실패"가 어디 숨을 수 있는지 한 번 더 생각해 보세요.
  • 그린필드 빌드 비용으로 스택을 고르기. 유지보수는 빌드의 1/5~1/8 비용이고 프레임워크 간 차이도 작았습니다. 실무 비용의 대부분은 유지보수 쪽에서 발생하니, 빌드 벤치마크 하나로 스택을 바꾸는 건 성급합니다.

8. 마무리 (TL;DR)

  • Nolan Lawson의 벤치마크: Claude Code(Opus 5.5)가 같은 포켓몬 도감 앱을 12개 JS 스택으로 각 5회, 총 60회 구현. 전부 테스트 통과, 그러나 토큰은 Nuxt 3.85M ~ Angular 9.76M으로 2.5배 차이.
  • 에이전트 비용의 구조: 매 턴 대화 전체가 재전송되므로 총 토큰 ≈ 턴 수 × 평균 컨텍스트. 이번 데이터에서 95%가 캐시 읽기.
  • 비싼 이유는 제각각: 낯선 프레임워크의 소스 역공학(Gracile), 구버전 지식과 신버전의 간극(SvelteKit), 코드 세리머니와 턴 수(Angular). vanilla도 싸지 않다 — 모델이 아는 관례가 자산이다.
  • 공개 5일 만의 반전: 렌더링 모드(52/54가 SSR)가 교란 변수였고, '실패'한 Angular 2회는 측정 버그였으며, 반복 간 분산은 ±34%, 비용 범위 66쌍 중 60쌍이 겹침. 모드를 고정하자 Angular는 최고가가 아니었다.
  • 진짜 교훈은 순위가 아니라 방법론: 밀폐 설계(생성·채점·측정 분리, 정답 숨기기), 반복과 중앙값, 그리고 하네스·원시 데이터 공개가 만든 반증 사이클.
  • 내 저장소에서도 stream-json 트랜스크립트로 같은 회계를 돌릴 수 있다 — 과제 고정, 3회 이상 반복, 깨끗한 환경, 검증 분리.
