# 📚 주목 논문

## WideSWE: 저장소 하나만 잘 고치는 에이전트의 한계 (arXiv:2609.33382)

- **저자**: Baoyi Wang, Xingliang Wang, Chen Zhi, Jianwei Yin 외 (Zhejiang Univ. ACES-ISE 랩) · cs.SE · 9/27 제출
- **핵심 기여**: 코딩 에이전트 평가는 여전히 단일 코드베이스 안에서 끝나지만, 실제 생태계에서는 기능 하나가 **여러 저장소의 조율된 변경**을 요구합니다. 103개 소프트웨어 생태계를 마이닝해 실전 태스크 120개(버그픽스 60 + 기능 60)를 확정, 히든 테스트로 채점.
- **방법**: 에이전트에게 공유 요청 하나와 대상 저장소들이 담긴 워크스페이스를 주고, 모든 대상 저장소가 통과해야 성공으로 인정. 다양한 구현을 허용하도록 히든 테스트를 수작업 검수.
- **결과**: 7개 에이전트 구성에서 완전 성공률 **10.83%~42.50%**. 최고는 Codex CLI + GPT-5.6-sol 조합. 실패는 "필요한 변경을 못 찾음 → 찾고도 미완성 → 고치고도 요구사항 미충족" 순으로 수렴.
- 🛠 **시사점**: 저장소를 하나씩 순차 실행하면 누락된 작업은 회복되지만, 한 번 시도해 실패한 구현은 잘 못 고칩니다. 반대로 공동 실행은 이웃 저장소 정보를 구현·검증에 활용 — 멀티레포 에이전트 설계 시 "컨텍스트 공유 vs 순차 분리"를 태스크 유형별로 갈라야 할 근거.
- **한계**: 생태계 41개로 좁혀진 최종 분포가 전체 오픈소스를 대표하는지는 검증 필요.
- [arXiv](https://arxiv.org/abs/2609.33382) · [코드/하네스](https://github.com/ZJU-ACES-ISE/WideSWE) · [데이터셋](https://huggingface.co/datasets/wangbaoyi/WideSWE)

## TokenCast: 에이전트 실행 중 토큰 소모를 예측한다 (arXiv:2609.35760)

- **저자**: Chaoqian Ouyang, Ling Yue, Libin Zheng 외 10명 (arXiv에 소속 미표기) · 9/28 제출
- **핵심 기여**: 같은 태스크도 실행마다 토큰 소모가 10배 이상 출렁이는데, 원인은 툴 피드백에 따라 갈리는 다음 행동과 **매 호출의 입력을 불리는 컨텍스트 누적**. 실행 전 예측이 아니라 "실행 중 갱신되는 예측"을 제안.
- **방법**: 실행 세그먼트마다 (자체 소모, 유발한 컨텍스트 증가량)을 담는 합성 가능한 비용 표현을 학습. 인접 세그먼트를 합성하면 "앞 컨텍스트를 뒤 호출들이 재독하는 추가 비용"까지 반영된 누적 추정치가 나오고, 새 관측으로 갱신 — 추가 LLM 호출 없이 런당 평균 32.8ms.
- **결과**: 4개 태스크 스위트 × 6개 모델(96개 조합)에서 최강 비교군 대비 평균 절대 오차 **-14.5%**. 예산 제어 리플레이에서는 고정 예산 정책 대비 동일 완료율에 **토큰 -21.3%**.
- 🛠 **시사점**: 토큰 예산을 "태스크당 상한 하나"로 걸고 있다면 낭비가 큽니다. 아래 실전 팁 참고.
- **한계**: 코드 저장소는 아직 README뿐, "공개 예정" 상태(클론으로 확인).
- [arXiv](https://arxiv.org/abs/2609.35760) · [저장소](https://github.com/DEFENSE-SEU/TokenCast)

# 🧑‍💻 Codex & Claude Code 실전 팁

**🟩 Codex · Workflow** — [기본 모델 교체 커밋](https://github.com/openai/codex/commit/b1e72963c3b71a9265a551e54beff078384efed9)

- 💡 Codex의 번들 카탈로그 기본 모델이 어제부로 `gpt-6.1-sol`입니다. 모델을 핀하지 않았다면 다음 업데이트부터 팀 전체의 모델이 조용히 바뀝니다.
- 📝 재현성이 필요한 파이프라인은 명시적으로 고정하세요:

```toml
# ~/.codex/config.toml
model = "gpt-6-sol"   # 검증 전까지 구버전 핀
```

- 🎯 새 모델은 reasoning level 체계가 함께 실렸으니, 기존 effort/level 스윕 결과를 재측정한 뒤에 기본값을 따라가는 순서를 추천. ⚠️ Bedrock 사용자도 같은 날 `openai.gpt-6.1-sol` + multi-agent V2가 활성화돼 영향권입니다. ⭐ 추천도: 상

**🟦 Claude Code · MCP** — [v2.1.285 릴리즈](https://github.com/anthropics/claude-code/releases/tag/v2.1.285)

- 💡 플러그인에 번들된 `.mcpb` MCP 서버는 지금까지 설치 후 `/plugin` → Configure를 열어야 설정할 수 있었는데, 2.1.285부터 **설치 시점에 설정 주입**이 됩니다.
- 📝 CI·팀 온보딩 스크립트에서 한 줄로:

```bash
claude plugin install my-plugin --config 'myserver.api_base=https://internal.example'
claude plugin configure my-plugin        # 옵션과 미설정 항목 확인
```

- 🎯 신규 팀원 셋업 스크립트, headless 환경에서 플러그인+MCP를 상호작용 없이 세우고 싶을 때. ⚠️ 같은 릴리즈에 관리 설정 `allowedProviders`(허용 API 프로바이더 제한)도 추가 — 사내 게이트웨이 강제 시 유용하지만 기존 세션 구성과 충돌 여부 확인. ⭐ 추천도: 상

**🟪 공통 · Context** — [TokenCast (arXiv:2609.35760)](https://arxiv.org/abs/2609.35760)

- 💡 에이전트 비용 관리의 최소 단위는 "태스크당 상한"이 아니라 **세그먼트 로그**입니다. 툴콜 단위로 (자체 소모, 컨텍스트 증가량) 두 필드만 쌓아도 실행 중 누적 예측이 가능해집니다.
- 📝 시작은 가볍게: 오케스트레이터 로그 스키마에 `tokens_self`, `context_delta` 필드를 추가하고, 누적 예측이 예산의 80%를 넘으면 중단·재계획하는 훅 하나. 🎯 같은 태스크의 소모가 런마다 크게 출렁이는 장기 실행 에이전트. ⚠️ 논문 코드는 아직 미공개라 지표 설계만 차용할 것. ⭐ 추천도: 중
