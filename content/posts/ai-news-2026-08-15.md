# 🔥 오늘의 핵심

모델 쪽 뉴스는 **"베이스는 그대로, 포스트트레이닝만"** 이다. GLM-5.3이 GLM-5.2와 동일한 베이스로 Terminal-Bench 3.0을 4.6 → **28.3**까지 끌어올렸다. 능력은 이제 사전학습이 아니라 **훈련 환경 설계**에서 나온다는 신호다.

그리고 오늘 arXiv 두 편은 우연히 같은 얘기를 한다 — 에이전트의 실전 품질은 평균 성능이 아니라 **경계에서의 결정**에서 갈린다. 도구가 실패했을 때(재시도/전환/중단), 그리고 되돌릴 수 없는 액션 직전(실행/보류). 오늘 바로 할 일은 하나다: **도구 실패를 주입한 회귀 테스트 1개**를 파이프라인에 추가하는 것.

# 📚 주목 논문

## 1. Retry, Switch, or Abstain? — 도구가 실패하는 세상에서의 복구 정책

- **저자**: Chaoran Chen, Vy Nguyen, Ziji Zhang 외 10인
- **arXiv**: [2608.11977](https://arxiv.org/abs/2608.11977) · cs.AI (2026-08-12)
- **핵심 기여**: 도구가 항상 성공하는 벤치마크를 **확률적 실패 환경으로 변환**하는 프레임워크 `BENCH2ROBUST`. 재시도해야 풀리는 episode, 대체 경로로 전환해야 풀리는 episode, **아예 답이 없어 중단해야 하는** episode를 명시적으로 구성한다.
- **방법 (3줄)**: 기존 멀티턴 벤치(Retail 등)에 일시적·지속적·**무성(silent)** 실패를 주입. 여기에 두 가지 개입을 비교 — 런타임 복구 컨텍스트를 주는 `Bayesian Tool Memory(BTM)`, 그리고 커리큘럼 기반 RL.
- **핵심 결과 (검증)**:
  - 4개 패밀리 7개 모델에서 도구 실패 시 **거의 보편적인 견고성 갭**이 관측됨
  - held-out Retail 태스크에서 **BTM만으로 재학습 없이 최대 +16.8%p**
  - BTM + RL 조합은 실패 주입 환경에서 **40.8~45.5%** 도달, 무실패 환경 성능은 유지
- 🛠 **에이전트 빌더 시사점**: 지금 코드에 `retry(3)`밖에 없다면 절반만 만든 것이다. **"대체 경로 전환"과 "경로 소진 시 중단"** 을 1급 액션으로 만들고, 도구별 성공 이력을 프롬프트에 주입해 다음 결정을 바꿔라. 재학습 없이 컨텍스트만으로 두 자릿수 개선이 가능하다는 게 이 논문의 실용적 포인트.
- ⚠️ **한계**: Retail·멀티턴 툴 벤치 중심이라 도메인 이식성은 직접 확인 필요. BTM의 사전확률 설계도 환경마다 튜닝이 든다.

## 2. SteerBench-Work — 되돌릴 수 없는 액션 직전의 판단을 측정한다

- **저자**: Oguz Serdar, Cuneyt Mertayak
- **arXiv**: [2608.12654](https://arxiv.org/abs/2608.12654) · cs.AI (2026-08-12)
- **핵심 기여**: 메일 발송·PR 머지·송금처럼 **커밋 직전의 게이트 결정**(진행 vs 보류)만 떼어내 측정하는 벤치마크. 실제 공개 사건에 기반한 106개 시나리오와, **증거를 뒤집은 미러 케이스**를 쌍으로 제공한다.
- **방법 (2줄)**: 모델에 제안된 액션과 확보된 증거를 주고 게이트 결정을 받는다. 라벨을 proceed/hold 거의 반반으로 맞춰 **두 방향 오류에 동일한 기회**를 준 것이 설계의 핵심.
- **핵심 결과 (검증)**: 30개 모델 조건에서 실패가 **한 방향으로 쏠린다** — 정당하고 증거도 확보된 작업을 **잘못 보류하는 비율 28.1%**, 위험한 작업을 잘못 허용하는 비율은 **1.0%**. 유명 사건 자체에서는 98.5%로 잘 막지만, 증거를 반대로 뒤집은 미러 케이스에서는 **63.8%** 로 급락. 성능이 높은 모델일수록 오히려 커밋 경계에서 **과잉 거부**하는 경향.
- 🛠 **에이전트 빌더 시사점**: 승인 게이트를 평가할 때 정확도 하나로 뭉뚱그리면 실제 문제를 못 본다. **오탐(false hold)과 미탐(false allow)을 분리해 기록**하라. 사내 에이전트가 "안전하다"는 평판을 얻고도 아무도 안 쓰게 되는 흔한 실패는 대개 28% 쪽에서 나온다. 그리고 "위험 트리거가 이미 해소된 케이스"를 eval에 반드시 넣을 것.
- ⚠️ **한계**: v2026-05 릴리즈 106 시나리오로 규모가 크지 않고, 사건 기반이라 도메인 편향이 있다. 리더보드는 논문에 명시된 steerbench.com.

![실패 경계와 커밋 경계를 나눈 에이전트 워크플로 다이어그램](/images/ai-news-2026-08-15/boundary-flow.svg)
*위: 도구 실패 시 retry/switch/abstain 분기와 BTM. 아래: 커밋 직전 게이트와 28.1% 대 1.0%의 오류 비대칭. 출처: 두 논문 기반 재구성.*

# 🧑‍💻 Codex & Claude Code 실전 팁

### 🟩 Codex — `--full-auto` 제거 (카테고리: Workflow / CI)

- **출처**: [Codex 변경 로그](https://developers.openai.com/codex/changelog/), [PR #36054](https://github.com/openai/codex/pull/36054)
- 💡 **핵심**: `codex exec --full-auto`가 **제거**됐다(v0.128부터 deprecated, v0.147.0 기준 삭제). 이제 샌드박스 모드를 명시적으로 골라야 한다.
- 📝 **해야 할 일** — CI 스크립트를 grep해서 치환:

```bash
# 영향받는 곳 찾기
rg -n -- '--full-auto' .github/ scripts/ Makefile

# 치환: 암묵적 매핑 → 명시적 지정
# before: codex exec --full-auto "run the migration"
# after:
codex exec --sandbox workspace-write "run the migration"
```

- 🎯 **언제**: 오늘 당장. CI에서 Codex를 비대화식으로 돌리고 있다면 조용히 깨지는 게 아니라 플래그 오류로 잡힌다.
- ⚠️ **주의**: `workspace-write`는 워크스페이스 쓰기를 허용한다. 무심코 넓게 열지 말고 읽기만 필요한 잡에는 더 좁은 모드를 쓸 것 — 이번 변경의 취지 자체가 "블랭킷 자동화 플래그"를 없애고 권한을 명시하게 만드는 것이다.
- ⭐ **추천도**: ★★★★★ (선택이 아니라 필수 마이그레이션)

### 🟦 Claude Code — 서브에이전트 fork 기본값 ON과 세션 간 멘션 (카테고리: Subagent / Context)

- **출처**: [v2.1.232 릴리즈 노트](https://www.claudeupdates.dev/version/2.1.232), [DevelopersIO 정리](https://dev.classmethod.jp/en/articles/20260814-cc-updates-v2-1-232/)
- 💡 **핵심**: `subagent_type: "fork"` 서브에이전트가 **전체 대화와 프롬프트 캐시를 상속**하고, 이 forking이 이제 기본값이다. 별도로 `@`를 입력하면 다른 Claude 세션을 이름으로 멘션해 `SendMessage`로 직접 전달할 수 있다.
- 📝 **활용법**: 긴 세션에서 "여기까지 맥락 그대로 두고 위험한 리팩터만 분기해서 시도"가 재설명 없이 된다. 그리고 세션 간 메시지는 `/config`의 **"Messages from your other sessions"** 에서 `accept` / `hold` / `refuse` 세 값으로 제어한다.

```text
/config → Messages from your other sessions
  accept : 다른 세션 메시지를 자동 수신
  hold   : 검토 대기열에 보류   ← 공용/CI 머신 기본값 권장
  refuse : 수신 거부
```

- 🎯 **언제**: 긴 컨텍스트를 쌓아둔 세션에서 실험적 변경을 시도할 때, 그리고 장시간 작업 세션과 리뷰 세션을 분리해 돌릴 때.
- ⚠️ **주의**: fork는 캐시를 상속하는 만큼 **오염된 컨텍스트도 함께 상속**한다. 잘못된 전제가 이미 대화에 박혀 있으면 fork가 그걸 그대로 물려받는다. 깨끗한 시작이 필요하면 fork가 아닌 새 에이전트를 명시적으로 띄울 것. 세션 간 인바운드는 공용 머신에서 `hold`로 두는 편이 안전하다.
- ⭐ **추천도**: ★★★★☆

### 🟪 공통 — "실패 주입 회귀 테스트 1개" 규칙 (카테고리: Eval)

- **출처**: [arXiv:2608.06790](https://arxiv.org/abs/2608.06790), [arXiv:2608.11977](https://arxiv.org/abs/2608.11977)
- 💡 **핵심**: 대부분의 에이전트 eval은 도구가 항상 성공하는 세상에서 돈다. 실전 실패의 상당수는 그 바깥에서 나온다.
- 📝 **최소 구현** — eval 스위트에 시나리오 3개만 추가하면 된다:

```text
1) transient  : 첫 호출만 5xx → 재시도로 복구되는가?
2) persistent : 해당 도구 계속 실패 → 대체 경로로 전환하는가?
3) exhausted  : 모든 경로 실패 → 조용히 지어내지 않고 중단·보고하는가?
```

  각 시나리오의 결과를 `retry / switch / abstain` 중 무엇을 선택했는지로 기록하면, 릴리즈마다 복구 정책의 분포 변화를 추적할 수 있다.

- 🎯 **언제**: 되돌릴 수 없는 액션(쓰기·결제·외부 전송)을 하나라도 가진 에이전트라면 전부.
- ⚠️ **주의**: 3번이 가장 중요한데 가장 자주 빠진다. "모르면 멈춘다"를 명시적으로 보상하지 않으면 모델은 그럴듯한 답을 지어내는 쪽을 고른다.
- ⭐ **추천도**: ★★★★★
