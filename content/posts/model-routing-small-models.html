도입 — 한 주 만에 벌어진 가격표의 양극화

이번 주 LLM 가격표에 재미있는 일이 벌어졌습니다. 한쪽 끝에서는 Mistral Large 4 같은 대형 모델 발표가 Hacker News를 도배했고(약 2,000포인트), 반대쪽 끝에서는 Anthropic이 10월 7일 Claude Haiku 5.5를 내놨습니다. 입력 100만 토큰당 $0.10. 같은 집안 상위 모델인 Opus 5.5($4.00)의 1/40, Sonnet 5.5($2.00)의 1/20 가격입니다. HN에서도 약 690포인트, 댓글 340개가 넘게 달리며 "작은 모델을 어디까지 믿고 쓸 수 있나"가 한 주 내내 실무자들의 화제였습니다.

흥미로운 건 가격이 아니라 성능의 바닥이 올라왔다는 점입니다. Anthropic 공식 발표 기준으로 Haiku 5.5는 터미널 작업 벤치마크인 Terminal-Bench 4.0에서 39.2%를 기록했는데, 전작 Haiku 4.5는 0.0%였습니다. 컴퓨터 사용 벤치마크 OSWorld 2.1(offline subset)에서는 15.7% → 72.4%로 뛰었고요. 1년 전의 "작은 모델"은 분류나 간단한 요약 정도가 한계였다면, 지금의 작은 모델은 웬만한 에이전트 작업의 하위 단계를 통째로 맡길 수 있는 수준이 됐다는 뜻입니다.

그래서 오늘의 주제는 Haiku 5.5 자체가 아니라, 이 가격 양극화 시대에 필요한 설계 기술입니다. 모델 라우팅(model routing) — 들어오는 요청마다 난이도에 맞는 모델로 보내서, 품질은 지키고 비용과 지연 시간은 깎는 엔지니어링이죠. "제일 좋은 모델 하나로 전부 처리"가 왜 금방 한계에 부딪히는지, 그리고 현장에서 검증된 네 가지 패턴을 코드와 함께 하나씩 살펴보겠습니다.

배경 — 토큰 과금과 에이전트의 토큰 식성

따라오는 데 필요한 최소 지식부터 정리합니다. LLM API는 토큰(token) 단위로 과금합니다. 모델이 읽는 입력 토큰과 모델이 생성하는 출력 토큰의 단가가 다르고, 보통 출력이 5배쯤 비쌉니다. 그리고 거의 모든 프로바이더가 모델을 2~3개 체급(tier)으로 나눠 팝니다. Anthropic이라면 Haiku(소형·고속) → Sonnet(중형) → Opus(대형) 순이죠.

모델입력 $/1M 토큰출력 $/1M 토큰Opus 5.5 대비 입력 단가
claude-haiku-5-5$0.10$0.501/40
claude-sonnet-5-5$2.00$10.001/2
claude-opus-5-5$4.00$20.00—

단서 하나: Haiku 5.5의 위 단가는 프롬프트 10만 토큰 이하 기준입니다. 프롬프트가 10만 토큰을 넘는 요청은 입력 $0.50 / 출력 $2.50으로 5배가 적용됩니다. 뒤의 "흔한 실수"에서 다시 다룹니다.

왜 이 단가 차이가 갑자기 중요해졌을까요? 에이전트 때문입니다. 챗봇은 한 번 묻고 한 번 답하면 끝이지만, 에이전트(agent)는 도구를 부르고 결과를 읽고 다시 생각하는 루프를 돕니다. Anthropic이 자사 멀티에이전트 시스템을 해부한 엔지니어링 블로그에 따르면, 에이전트는 일반 채팅 대비 약 4배, 멀티에이전트 시스템은 약 15배의 토큰을 씁니다. 토큰 소비가 15배면, 모델 선택 한 번의 단가 차이가 그대로 15배로 증폭된다는 얘기입니다. 챗봇 시절에는 모델 선택이 취향이었다면, 에이전트 시대에는 아키텍처 결정입니다.

계산 한 번 해 봅시다 — 왜 라우팅인가

감이 아니라 숫자로 봅시다. 고객 문의를 카테고리로 분류하는 작업이 있다고 하죠. 요청당 입력 2,000토큰(문의 + 지시문), 출력 100토큰, 월 100만 건입니다.

{{< highlight text >}} Opus 5.5로 전부 처리: 입력 2,000 tok × 1,000,000건 = 20억 tok × $4.00/1M = $8,000 출력 100 tok × 1,000,000건 = 1억 tok × $20.00/1M = $2,000 → 월 $10,000 Haiku 5.5로 전부 처리: 입력 20억 tok × $0.10/1M = $200 출력 1억 tok × $0.50/1M = $50 → 월 $250 {{< /highlight >}}

같은 작업이 월 1,000만 원 대 30만 원 수준으로 갈라집니다. 분류처럼 정형화된 작업에서 두 모델의 정확도 차이는 보통 몇 퍼센트포인트 이내라서, 이 차이를 40배 비용으로 사는 건 수지가 안 맞습니다. 반대로 아키텍처 설계 리뷰처럼 추론이 깊은 작업을 Haiku에 맡기면 틀린 결과를 싸게 사는 꼴이 되고요. 결국 질문은 "어느 모델이 좋은가"가 아니라 "이 요청은 어느 모델감인가"가 됩니다. 이 판단을 코드로 옮긴 것이 라우팅입니다.

라우팅이 새 아이디어는 아닙니다. 2023년 Stanford의 FrugalGPT(Chen, Zaharia, Zou)가 "싼 모델부터 시도하고 필요할 때만 승격하는 캐스케이드로, 최고 모델과 같은 성능을 최대 98% 싸게 얻을 수 있다"는 걸 보였고, 2024년 UC Berkeley의 RouteLLM(ICLR 2025)이 선호도 데이터로 라우터를 학습시켜 품질 저하 없이 비용을 2배 이상 줄였습니다. 달라진 건 환경입니다. 작은 모델의 성능 바닥이 올라오고 단가 격차는 더 벌어지면서, 논문 속 기법이 "이번 분기 인프라 비용" 문제가 된 거죠.

패턴 ① 정적 태스크 라우팅 — 가장 쉽고, 대개 충분한

가장 단순한 라우팅은 작업 유형별로 모델을 고정하는 겁니다. 요청의 난이도를 실시간으로 판단하는 게 아니라, 시스템을 설계할 때 "이 경로의 작업은 이 모델"이라고 미리 정해 두는 방식이죠. 파이프라인이 여러 단계로 나뉘어 있고 단계마다 성격이 다르다면 — 대부분의 실서비스가 그렇습니다 — 이것만으로 비용의 절반 이상이 깎입니다.

{{< highlight python >}} import anthropic client = anthropic.Anthropic() # 작업 유형 → 모델. 코드 리뷰에서 변경 이력이 보이도록 테이블로 관리합니다. MODEL_TABLE = { "classify": "claude-haiku-5-5", # 분류: 짧고 반복적 → 소형 "summarize": "claude-haiku-5-5", # 요약·압축: 소형으로 충분 "codegen": "claude-sonnet-5-5", # 코드 생성: 중형 "review": "claude-opus-5-5", # 설계 리뷰: 깊은 추론 → 대형 } def run(task_type: str, prompt: str) -> str: response = client.messages.create( model=MODEL_TABLE[task_type], max_tokens=1024, messages=[{"role": "user", "content": prompt}], ) return "".join(b.text for b in response.content if b.type == "text") {{< /highlight >}}

어떤 작업을 소형 모델로 내릴지 감이 안 올 때는 Anthropic이 발표문에서 직접 꼽은 Haiku 5.5의 용도가 좋은 출발점입니다: 요약, 컨텍스트 압축(compaction), 분류, 데이터베이스 질의 같은 대량 반복 작업, 그리고 실시간 고객 지원이나 브라우저 조작처럼 지연 시간에 민감한 작업. 실제로 초기 도입사인 Asana는 에이전트 턴당 추론이 최대 2.5배 빨라졌다고 보고했습니다. 소형 모델의 매력이 비용만이 아니라 속도이기도 하다는 점은 기억해 둘 만합니다.

모델을 바꾸기 전에 돌려볼 다이얼이 하나 더 있습니다. 최신 Claude 모델에는 effort라는 추론 강도 설정이 있습니다(output_config: {"effort": "low"}처럼 지정). 같은 모델을 낮은 effort로 돌리면 토큰 소비가 줄어드는데, 최신 세대 모델의 낮은 effort가 이전 세대의 높은 effort 성능과 맞먹는 경우가 많습니다. 모델이 하나면 프롬프트도 캐시도 하나로 관리되니, 멀티 모델 라우팅을 짜기 전에 "큰 모델 + 낮은 effort"라는 더 단순한 대안부터 측정해 보세요. 이번 Haiku 5.5는 Haiku 계열 처음으로 이 effort 다이얼이 달린 모델이기도 합니다.

패턴 ② 캐스케이드와 패턴 ③ 학습 라우터

정적 라우팅의 한계는 같은 유형 안의 난이도 편차입니다. "고객 문의 답변"이라는 한 경로에도 영수증 재발송 같은 쉬운 건과 환불 분쟁 같은 어려운 건이 섞여 들어오죠. 이때 쓰는 두 패턴이 캐스케이드와 학습 라우터인데, 갈림길은 난이도 판단을 언제 하느냐입니다.

패턴 ② 캐스케이드(cascade)는 사후 판단입니다. 일단 싼 모델이 답하게 하고, 그 답이 충분한지 검사한 뒤 부족할 때만 비싼 모델로 승격(escalate)합니다. FrugalGPT가 정립한 구조로, 쉬운 요청이 다수라면 대부분의 트래픽이 소형 모델 선에서 끝납니다. 대신 요청이 어려울수록 "싼 모델 호출 + 판정 + 비싼 모델 호출"로 호출이 늘어나 지연 시간이 길어지는 게 비용입니다.

패턴 ③ 학습 라우터(learned router)는 사전 판단입니다. 요청을 모델에 보내기 전에, 가볍고 작은 판별기가 난이도를 예측해서 처음부터 알맞은 모델로 보냅니다. RouteLLM이 대표적인데, Chatbot Arena의 사람 선호 데이터로 라우터를 학습시켜 "강한 모델 성능의 95%를 유지하면서 호출의 대부분을 약한 모델로" 보내는 식의 운영점을 고를 수 있게 했습니다. 벤치마크에 따라 30~70%의 비용 절감을 같은 품질에서 달성했고, 라우터를 다른 모델 쌍에 갈아 끼워도 작동하는 전이성도 보였습니다. 호출이 한 번이라 지연 시간은 유리하지만, 라우터를 만들고 평가할 데이터가 필요하다는 진입 장벽이 있습니다.

캐스케이드에서 품질을 좌우하는 건 사실 모델이 아니라 판정기(judge)입니다. 판정이 너무 후하면 품질 사고가 나고, 너무 짜면 전부 승격돼 비용 절감이 사라집니다. 실무에서 자주 쓰는 판정 방법은 세 가지입니다. 형식 검증(JSON 스키마, 테스트 통과처럼 기계적으로 확인 가능한 것 — 가장 싸고 확실), 모델 자기 평가(답과 함께 확신도를 출력하게 하기 — 싸지만 과신 경향 주의), 별도 판정 모델(작은 모델에게 채점시키기 — FrugalGPT의 방식). 기계적 검증이 가능한 작업이라면 무조건 그걸 먼저 쓰세요.

패턴 ④ 오케스트레이터-워커 — 서브에이전트 오프로딩

마지막 패턴은 요청 단위가 아니라 역할 단위의 라우팅입니다. 에이전트 시스템에서 토큰을 가장 많이 먹는 건 보통 판단이 아니라 물량입니다 — 파일 수십 개 읽기, 검색 결과 훑기, 로그 뒤지기. 이런 "많이 읽고 조금 판단하는" 하위 작업을 소형 모델 워커(worker)에게 떼어 주고, 비싼 모델은 계획·분해·종합이라는 판단 역할에만 쓰는 구조가 오케스트레이터-워커입니다.

Anthropic의 멀티에이전트 리서치 시스템이 이 구조의 공개된 사례입니다. 대형 모델(Opus 4)이 리드 에이전트로 조사를 지휘하고, 중형 모델(Sonnet 4) 서브에이전트들이 병렬로 자료를 뒤졌는데, 단일 대형 모델 에이전트보다 내부 리서치 평가에서 90.2% 더 좋은 성과를 냈습니다. 단, 같은 글에서 Anthropic은 멀티에이전트가 채팅 대비 약 15배의 토큰을 쓴다고 경고합니다. 토큰 소비 자체가 커지는 구조라서, 워커를 얼마나 싼 모델로 내릴 수 있느냐가 이 패턴의 채산성을 결정합니다. 서브에이전트 하나하나는 "주어진 소스를 읽고 요약해 와라" 수준의 좁은 작업을 받기 때문에, 이번 세대 소형 모델이 가장 먼저 투입될 자리이기도 합니다. Anthropic이 Haiku 5.5 용도로 "코딩 작업에서 Opus 5.5·Sonnet 5.5와 나란히 쓰는 서브에이전트"를 명시한 것도 같은 맥락입니다.

이 패턴을 비용 절감 수단으로 먼저 집지는 마세요. 오케스트레이터-워커의 본래 동기는 품질(병렬 탐색, 깨끗한 컨텍스트 분리)이고, 총 토큰은 오히려 늘어납니다. "단일 에이전트로는 컨텍스트가 넘치거나 품질이 안 나오는 작업"이라는 전제가 성립할 때, 그 안에서 워커 모델을 싸게 고르는 것이 올바른 순서입니다.

실전 — 비용을 찍어 보는 미니 라우터 만들기

정적 라우팅 + 캐스케이드를 합친 최소 구현을 만들어 봅시다. 포인트는 두 가지입니다. 모든 호출의 비용을 로그로 남겨서 라우팅의 효과를 숫자로 보는 것, 그리고 판정을 기계 검증 → 모델 판정 순서로 거는 것.

{{< highlight python >}} import anthropic client = anthropic.Anthropic() PRICE = { # $/1M 토큰 (입력, 출력) — 2026-10 공식 단가, Haiku는 100K 이하 프롬프트 기준 "claude-haiku-5-5": (0.10, 0.50), "claude-sonnet-5-5": (2.00, 10.00), } def ask(model: str, prompt: str, max_tokens: int = 1024) -> str: r = client.messages.create( model=model, max_tokens=max_tokens, messages=[{"role": "user", "content": prompt}], ) pin, pout = PRICE[model] cost = (r.usage.input_tokens * pin + r.usage.output_tokens * pout) / 1e6 print(f"[{model}] in={r.usage.input_tokens} out={r.usage.output_tokens} ${cost:.6f}") return "".join(b.text for b in r.content if b.type == "text") {{< /highlight >}} {{< highlight python >}} import json def answer_inquiry(inquiry: str) -> dict: """고객 문의를 소형 모델로 먼저 처리하고, 판정에 걸리면 승격하는 캐스케이드.""" task = ( "고객 문의에 대한 답변 초안을 JSON으로 작성하세요. " '형식: {"category": "...", "reply": "...", "needs_human": true/false}\n' f"문의: {inquiry}" ) draft = ask("claude-haiku-5-5", task) # 1차 판정: 기계 검증 — 형식이 깨졌으면 모델 판정까지 갈 것도 없이 승격 try: parsed = json.loads(draft) assert {"category", "reply", "needs_human"} <= parsed.keys() except (json.JSONDecodeError, AssertionError): return json.loads(ask("claude-sonnet-5-5", task)) # 2차 판정: 소형 모델에게 채점시키기 — OK / ESCALATE 한 단어만 받습니다 verdict = ask( "claude-haiku-5-5", "아래 답변이 문의를 정확히 해결하면 OK, 사실관계가 불확실하거나 " "분쟁 소지가 있으면 ESCALATE — 한 단어로만 답하세요.\n" f"문의: {inquiry}\n답변: {parsed['reply']}", max_tokens=16, ) if "ESCALATE" in verdict.upper(): return json.loads(ask("claude-sonnet-5-5", task)) # 승격: 중형 모델이 재작성 return parsed {{< /highlight >}}

이 코드를 실제 트래픽 샘플 100건에 돌려 보면 print 로그만으로도 "몇 %가 승격됐고, 평균 비용이 얼마인지"가 나옵니다. 승격률이 10%라면 요청당 평균 비용은 소형 모델 단독의 1.3~1.5배 선에서 끝나면서 품질은 중형 모델에 수렴합니다. 반대로 승격률이 50%를 넘으면 이 작업은 캐스케이드감이 아니라 처음부터 중형 모델감이라는 신호입니다. 승격률이야말로 캐스케이드의 핵심 운영 지표입니다.

흔한 실수 · 팁

  • 요청당 비용이 아니라 "완료된 작업당 비용"으로 측정하세요 — 소형 모델이 요청당 40배 싸도, 재시도와 승격이 잦아 작업 하나를 끝내는 데 호출이 3배 들면 실제 절감은 확 줄어듭니다. 라우팅 전후 비교는 반드시 작업 단위 완료 비용과 품질 지표를 같이 봐야 합니다.
  • 평가셋 없이 라우팅 조정 금지 — "Haiku로 내렸는데 티가 안 나는 것 같다"는 느낌은 측정이 아닙니다. 작업별로 수십 건이라도 좋으니 채점 가능한 평가셋을 먼저 만들고, 모델을 내릴 때마다 돌려 보세요. 평가셋이 없으면 라우팅은 비용 절감이 아니라 품질 러시안룰렛이 됩니다.
  • 프롬프트 캐시는 모델 단위라는 것 — prompt caching의 캐시는 모델별로 분리됩니다. 요청을 여러 모델로 흩뿌리면 각 모델이 캐시를 따로 쌓아야 해서, 캐시 적중률이 떨어지는 만큼 라우팅 절감분을 되돌려주게 됩니다. 시스템 프롬프트가 길고 캐시 의존이 큰 경로라면 "모델 하나 + effort 조절"이 더 쌀 수 있습니다.
  • Haiku 5.5의 장문 단가 점프 — 프롬프트가 10만 토큰을 넘는 순간 입력 $0.50 / 출력 $2.50으로 5배가 됩니다. "싸니까 컨텍스트를 아낌없이"는 이 모델에서 자충수입니다. 소형 모델에는 좁은 작업과 좁은 컨텍스트를 주는 게 설계 의도에 맞습니다.
  • 판정기 비용과 지연을 잊지 말 것 — 캐스케이드의 판정 호출도 돈과 시간입니다. 판정기는 가장 싼 모델로, 출력은 한 단어로 제한하고, JSON 파싱·테스트 실행처럼 모델 없이 되는 검증이 있으면 그걸 1차로 거세요.
  • 모델을 바꾸면 프롬프트도 다시 조율해야 합니다 — 같은 프롬프트가 모델마다 다르게 작동합니다. 라우팅으로 모델을 내릴 때는 해당 경로의 프롬프트를 소형 모델에 맞게 손보는 작업까지가 한 세트입니다. 이 블로그의 프롬프트 마이그레이션 엔지니어링 편에서 자세히 다뤘습니다.
  • 라우팅 테이블을 코드 리뷰 대상으로 — "이 경로는 왜 Sonnet인가"가 커밋 메시지와 리뷰에 남아 있어야, 모델 세대가 바뀔 때(그리고 요즘은 분기마다 바뀝니다) 어떤 경로를 재평가할지 알 수 있습니다. 새 소형 모델이 나올 때마다 평가셋을 돌려 "한 단계 내릴 수 있는 경로"를 찾는 것이 이 시대의 정기 점검입니다.

마무리 (TL;DR)

  • 이번 주 공개된 Claude Haiku 5.5는 입력 $0.10/1M 토큰으로 Opus 5.5의 1/40 가격인데, Terminal-Bench 0.0→39.2%, OSWorld 15.7→72.4%로 전작 대비 성능 바닥이 크게 올라왔습니다. 가격 양극화 + 소형 모델의 상향 = 모델 라우팅의 수익성이 커진 한 주였습니다.
  • 패턴은 네 가지 — ① 정적 태스크 라우팅(설계 때 작업 유형별 모델 고정, 가장 쉽고 대개 충분), ② 캐스케이드(싼 모델 먼저 + 판정 + 승격, FrugalGPT 최대 98% 절감), ③ 학습 라우터(사전 난이도 예측, RouteLLM 30~70% 절감), ④ 오케스트레이터-워커(판단은 대형, 물량은 소형 워커).
  • 순서가 중요합니다: 평가셋 → 같은 모델 + 낮은 effort → 정적 라우팅 → 캐스케이드/라우터. 멀티 모델은 캐시 분리라는 숨은 비용이 있어서, 더 단순한 대안을 측정으로 제낀 뒤에 도입해야 합니다.
  • 운영 지표는 승격률과 완료 작업당 비용. 승격률 50% 넘는 경로는 캐스케이드감이 아니고, 요청당 비용만 보는 비교는 착시입니다.
  • 함정: Haiku 5.5는 프롬프트 100K 토큰 초과 시 단가 5배, 캐시는 모델 단위, 모델 교체는 프롬프트 재조율과 한 세트.
