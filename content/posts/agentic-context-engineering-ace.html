1. 왜 지금 ACE가 화제인가

2026년 실무 담론의 중심에는 컨텍스트 엔지니어링(context engineering)이 있습니다. 모델에게 "무엇을, 어떤 순서로, 얼마나 넣어 줄까"를 설계하는 일이죠. 프롬프트를 손보는 것을 넘어, 검색 결과·툴 출력·과거 대화·메모리까지 컨텍스트라는 한정된 창에 어떻게 배치하느냐가 에이전트 품질을 좌우한다는 공감대가 굳어졌습니다.

그 흐름에서 이번 주에도 반복해서 회자된 아이디어가 ACE(Agentic Context Engineering, 에이전트형 컨텍스트 엔지니어링)입니다. Stanford·UC Berkeley·SambaNova가 함께 낸 논문(arXiv:2510.04618, ICLR 2026)으로, 오픈소스 구현(ace-agent/ace)까지 공개되며 "State of Context Engineering 2026" 같은 회고 글들이 앞다퉈 다뤘습니다. 한 문장으로 요약하면 이렇습니다 — 컨텍스트를 '고정된 지시문'이 아니라 '스스로 자라는 플레이북(evolving playbook)'으로 다루자.

핵심 매력은 반직관적인 결론에 있습니다. 보통 우리는 컨텍스트가 길어지면 "요약해서 깔끔하게 정리"하려고 합니다. 그런데 ACE 팀은 그 요약이 오히려 지식을 무너뜨린다는 걸 보여 줬습니다. 그리고 모델을 재훈련하지 않고 컨텍스트만 진화시켜서, 에이전트 벤치마크에서 강력한 기준선 대비 +10.6%, 금융 추론에서 +8.6%를 얻었습니다. 그것도 정답 라벨 없이, 에이전트가 스스로 만든 실행 피드백만으로요.

이 글에서는 ACE가 어떤 문제를 푸는지, 왜 "요약"이 함정인지, 그리고 Generator·Reflector·Curator 세 역할이 어떻게 돌아가는지를 코드까지 함께 풀어 봅니다. 프레임워크를 그대로 쓰지 않더라도, 여기서 배우는 델타 업데이트 사고방식은 여러분의 에이전트 메모리 설계에 바로 써먹을 수 있습니다.

2. 배경: 모델을 바꾸는 두 가지 길

에이전트를 "더 잘하게" 만드는 방법은 크게 두 갈래입니다. 이 구분을 잡고 가면 ACE의 위치가 선명해집니다.

  • 가중치를 바꾸는 길 (파인튜닝·RL) — 모델 내부 파라미터를 다시 학습시킵니다. 강력하지만 GPU·데이터·시간이 많이 들고, 한 번 구우면 되돌리기 어렵습니다. 무엇을 왜 배웠는지 들여다보기도 힘들죠.
  • 컨텍스트를 바꾸는 길 (context adaptation) — 모델은 그대로 두고, 입력으로 넣어 주는 컨텍스트만 다듬습니다. 시스템 프롬프트, 규칙 모음, 참고 예시, 에이전트 메모리 같은 것들이죠. 사람이 읽을 수 있고, 즉시 고칠 수 있고, 비용도 훨씬 쌉니다.

ACE는 두 번째 길을 극단까지 밀어붙입니다. LLM은 맥락 안에서 배우는(in-context learning) 능력이 뛰어납니다. 프롬프트에 좋은 예시와 규칙을 넣어 주면, 가중치를 안 바꿔도 그 자리에서 더 잘합니다. 그렇다면 "무엇을 넣어 줄지"를 에이전트 스스로 계속 개선하게 만들면 어떨까요? 이게 self-improving context, 곧 스스로 개선하는 컨텍스트의 발상입니다.

비유하자면 이렇습니다. 신입에게 매번 똑같이 구두로 설명하는 대신, 팀이 공유하는 업무 노트(플레이북)를 하나 만들어 둡니다. 누군가 새 함정을 발견하면 노트에 한 줄 추가하고, 잘 먹힌 요령엔 별표를 칩니다. 시간이 지날수록 노트는 두꺼워지고, 그 노트만 읽으면 누구든 지난 실수를 반복하지 않죠. ACE는 이 "업무 노트"를 에이전트가 자기 손으로 쓰고 관리하게 만든 것입니다.

한 줄 정리: ACE는 "모델을 다시 훈련"하는 대신 "컨텍스트를 계속 진화"시킵니다. 값싸고, 사람이 읽을 수 있고, 언제든 되돌릴 수 있습니다.

3. 함정: 요약이 지식을 갉아먹는다

"컨텍스트를 계속 키운다"는 말에 곧바로 반문이 나옵니다. "그럼 컨텍스트가 무한정 길어지지 않나요? 당연히 주기적으로 요약해서 압축해야죠." 맞는 걱정입니다. 그런데 바로 그 요약이 ACE가 지목한 두 가지 함정의 원인입니다.

함정 ① brevity bias (간결함 편향)

사람이든 LLM이든 컨텍스트를 다듬으라고 하면 짧고 일반적인 문장으로 정리하려는 경향이 있습니다. "예외 상황에선 재시도 간격을 2초→4초→8초로 늘리고, 단 429 응답의 Retry-After 헤더가 있으면 그 값을 우선한다" 같은 구체적 노하우가, 요약을 거치면 "적절히 재시도하라" 정도로 뭉개집니다. 짧아서 깔끔해 보이지만, 정작 일을 되게 만들던 디테일이 사라집니다. 이걸 brevity bias(간결함 편향)라고 부릅니다.

함정 ② context collapse (컨텍스트 붕괴)

더 무서운 건 두 번째입니다. 컨텍스트 전체를 매번 통째로 다시 쓰는(monolithic rewrite) 방식이 문제입니다. 애써 수천 토큰까지 쌓아 올린 플레이북을, 모델에게 "정리해서 다시 써 줘"라고 시키는 순간 — 한 번의 재작성으로 몇 줄로 쪼그라드는 사고가 납니다. ACE 팀은 이걸 context collapse(컨텍스트 붕괴)라고 이름 붙였습니다.

왜 이런 일이 생길까요? 전언 게임(telephone game)을 떠올리면 됩니다. 한 사람이 옆 사람에게 말을 전하고, 그게 또 다음 사람에게 전해지면서 조금씩 뭉개지죠. 컨텍스트를 반복해서 다시 쓰면 매번 아주 조금씩 정보가 새고, 그 손실이 누적됩니다. 게다가 재작성은 확률적이라, 어느 순간 모델이 "요약본"이라며 핵심을 통째로 날려 버릴 수 있습니다.

ACE의 해법은 단순하면서 강력합니다. 컨텍스트를 다시 쓰지 말고, 조금씩 덧붙여라. 기존 지식은 그대로 두고, 새로 배운 것만 델타(delta) 항목으로 추가합니다. 통째로 재작성하는 스텝이 없으니, 전언 게임 식 손실도 붕괴도 원천적으로 안 생깁니다.

4. ACE의 핵심: 세 역할 + 델타 업데이트

ACE는 컨텍스트를 개선하는 일을 세 개의 역할로 나눕니다. 한 모델이 세 역할을 번갈아 맡아도 되고, 서로 다른 모델을 써도 됩니다. 중요한 건 "일을 하는 두뇌"와 "복기하는 두뇌"와 "노트를 정리하는 손"을 분리했다는 점입니다.

  • Generator(생성자) — 현재 플레이북을 참고해 실제 과제를 풉니다. 그 과정에서 어떤 추론을 했고 어떤 툴을 호출했는지, 즉 실행 궤적(trajectory)이 그대로 남습니다. 이게 다음 단계의 재료입니다.
  • Reflector(성찰자) — 그 궤적을 되짚어 구체적 교훈을 뽑습니다. "이 과제가 왜 성공/실패했나? 어떤 규칙이 도움이 됐고, 무엇을 몰라서 틀렸나?" 정답 라벨이 있으면 쓰고, 없으면 실행 피드백(에러 메시지, 테스트 통과 여부 등)만으로도 배웁니다.
  • Curator(큐레이터) — Reflector가 뽑은 교훈을 작은 델타 항목으로 바꿔 플레이북에 병합합니다. "이 규칙 추가", "저 규칙의 성공 카운터 +1", "이건 이제 안 통하니 폐기 표시"처럼요. 병합은 결정론적(deterministic)으로 이뤄져, 여러 델타를 동시에 안전하게 적용할 수 있습니다.

델타 항목은 어떻게 생겼나

플레이북은 자유 형식 글이 아니라, 구조화된 항목(bullet)의 목록입니다. 각 항목엔 고유 ID와 메타데이터가 붙습니다. 그래서 "덮어쓰기" 없이도 개별 항목을 정확히 가리켜 추가·수정·폐기할 수 있죠. 대략 이런 모습입니다.

{{< highlight json >}} { "id": "b-0007", "content": "429(Too Many Requests) 응답에 Retry-After 헤더가 있으면, 지수 백오프 대신 그 값(초)을 그대로 기다린다.", "tags": ["http", "rate-limit", "retry"], "helpful": 12, // 이 규칙을 따랐을 때 성공한 횟수 "harmful": 0, // 이 규칙 때문에 틀린 횟수 "status": "active" // active | deprecated } {{< /highlight >}}

Curator는 이 목록에 대해 작은 연산만 합니다 — 새 항목 append, helpful/harmful 카운터 증가, status를 deprecated로. 어느 것도 다른 항목을 다시 쓰지 않습니다. 이렇게 카운터가 쌓이면, 나중에 "잘 안 먹히는 규칙"을 데이터로 골라낼 수 있습니다.

grow-and-refine: 무한정 커지지 않게

"계속 추가만 하면 결국 터지지 않나?"라는 걱정은 grow-and-refine(키우고 다듬기) 원칙으로 답합니다. 새 항목을 더하며 키우되(grow), 주기적으로 의미가 겹치는 항목을 중복 제거(dedup)하고 폐기 표시된 것을 정리해 다듬습니다(refine). 여기서도 핵심은 "통째로 다시 쓰지 않는다"입니다. 중복 제거는 임베딩 유사도 같은 결정론적 방법으로 처리하지, 모델에게 전체를 재작성시키지 않습니다.

포인트: ACE가 기존 "메모리에 요약을 쌓는" 방식과 갈리는 지점이 바로 여기입니다. 요약은 손실 압축이라 반복하면 무너지고, 델타 병합은 무손실 축적이라 안전하게 자랍니다.

5. 실전: 미니 ACE 루프를 코드로

프레임워크를 통째로 들이지 않아도, ACE의 뼈대는 몇십 줄로 흉내 낼 수 있습니다. 아래는 세 역할과 델타 병합을 최소한으로 담은 개념 코드입니다. 실제 LLM 호출부(llm_json)는 여러분이 쓰는 API로 바꾸면 됩니다.

{{< highlight python >}} import json, hashlib # 플레이북: 구조화된 항목의 리스트. 통째로 덮어쓰지 않는 게 규칙. playbook = [] def render(pb): """플레이북을 프롬프트에 넣을 텍스트로. active 항목만, helpful 높은 순.""" items = [b for b in pb if b["status"] == "active"] items.sort(key=lambda b: b["helpful"] - b["harmful"], reverse=True) return "\n".join(f'- ({b["id"]}) {b["content"]}' for b in items) or "(아직 비어 있음)" # ── ① Generator: 현재 플레이북을 보고 과제를 푼다 ── def generator(task): prompt = ( f"다음 플레이북을 참고해 과제를 풀어라.\n[플레이북]\n{render(playbook)}\n\n" f"[과제]\n{task}\n\n푼 과정(추론·행동)과 최종 답을 함께 내라." ) return llm_json(prompt, schema={"trajectory": "str", "answer": "str"}) # ── ② Reflector: 궤적 + 실행 피드백에서 '교훈'을 뽑는다(정답 라벨은 선택) ── def reflector(task, gen, feedback): prompt = ( f"[과제]\n{task}\n[에이전트가 한 일]\n{gen['trajectory']}\n" f"[실행 결과/피드백]\n{feedback}\n\n" "무엇이 성공/실패를 갈랐는지 '재사용 가능한 규칙'으로 1~3개만 뽑아라. " "추상적 훈수 말고, 다음에 그대로 따를 수 있는 구체적 규칙으로." ) return llm_json(prompt, schema={"lessons": ["str"]}) # ── ③ Curator: 교훈을 '델타'로 바꿔 결정론적으로 병합한다 ── def curator(lessons): for text in lessons: bid = "b-" + hashlib.md5(text.encode()).hexdigest()[:6] hit = next((b for b in playbook if b["id"] == bid), None) if hit: # 이미 있는 규칙이면 → 카운터만 +1 (덮어쓰기 X) hit["helpful"] += 1 else: # 없으면 → 새 항목 append (기존은 그대로) playbook.append({"id": bid, "content": text, "helpful": 1, "harmful": 0, "status": "active"}) # ── 루프: 과제를 풀고 → 복기하고 → 델타를 더한다 ── def ace_step(task, run_and_check): gen = generator(task) feedback = run_and_check(gen["answer"]) # 예: 테스트 실행, 에러 캡처 (라벨 불필요) lessons = reflector(task, gen, feedback)["lessons"] curator(lessons) # 플레이북이 조금 자란다 return gen["answer"] {{< /highlight >}}

눈여겨볼 대목은 curator()입니다. 어디에도 "플레이북 전체를 다시 써 줘" 같은 호출이 없습니다. 오직 append와 카운터 증가뿐이죠. 이 결정론적 병합이 context collapse를 구조적으로 막습니다. 또 reflector()는 정답 라벨 없이 feedback(테스트 통과 여부, 에러 메시지)만으로도 교훈을 뽑을 수 있어, 라벨이 없는 실무 환경에서도 돌아갑니다.

주기적인 refine은 이렇게 덧붙일 수 있습니다. 완전히 별개의 정리 단계라, 과제 처리와 섞이지 않습니다.

{{< highlight python >}} def refine(pb, embed, sim_threshold=0.92): """의미가 겹치는 항목을 결정론적으로 중복 제거(모델 재작성 없음).""" kept = [] for b in sorted(pb, key=lambda x: x["helpful"], reverse=True): v = embed(b["content"]) if all(cosine(v, embed(k["content"])) < sim_threshold for k in kept): kept.append(b) # 충분히 새로운 항목만 남긴다 else: kept[-1]["helpful"] += b["helpful"] # 겹치면 점수만 흡수 return kept {{< /highlight >}}
주의: Reflector 프롬프트에서 "구체적 규칙"을 강하게 요구하지 않으면, 모델이 "코드를 꼼꼼히 확인하라" 같은 하나 마나 한 훈수를 뱉습니다. 그러면 brevity bias를 코드로 재현하는 꼴이 됩니다. "다음에 그대로 따를 수 있는가?"를 기준으로 삼으세요.

6. 숫자로 보는 효과

ACE 논문이 보고한 결과 중 검증된 수치만 추립니다. 벤치마크는 에이전트 과제(AppWorld 계열)와 도메인 과제(금융 추론) 두 축입니다.

항목수치의미
에이전트 벤치마크 정확도+10.6%강한 기준선 대비 향상(가중치 훈련 없이)
금융 추론 정확도+8.6%도메인 과제에서도 동일한 이득
평균 적응 지연(adaptation latency)86.9% ↓컨텍스트를 갱신하는 데 드는 시간이 크게 감소
vs GEPA(오프라인)지연 82.3% ↓, 롤아웃 75.1% ↓더 적은 시도로 더 빨리 적응
vs Dynamic Cheatsheet(온라인)지연 91.5% ↓, 토큰 비용 83.6% ↓온라인 메모리 방식보다 훨씬 저렴

숫자 자체보다 맥락이 인상적입니다. AppWorld 리더보드에서 ACE는 더 작은 오픈소스 모델을 쓰고도 상위권 프로덕션급 에이전트와 평균 점수를 맞췄고, 더 어려운 test-challenge 구간에서는 오히려 앞섰습니다. "덜 정리하고(요약 안 하고) 델타만 더하는" 값싼 방법이, 무겁게 튜닝한 시스템에 견줬다는 얘기입니다.

여기서 두 비교 대상도 짚어 둘 만합니다. GEPA는 프롬프트를 자동 최적화하는 옵티마이저이고, Dynamic Cheatsheet는 온라인으로 메모리를 쌓는 방식입니다. ACE가 둘보다 지연·비용에서 크게 앞선 핵심 이유는 반복적 재작성을 피하고 델타를 병렬·결정론적으로 병합하기 때문입니다. "어떻게 갱신하느냐"가 "무엇을 갱신하느냐"만큼 중요하다는 걸 보여 줍니다.

주의: 위 수치는 논문의 특정 세팅·벤치마크 결과입니다. 여러분 과제에 그대로 재현된다는 보장은 없으니, 늘 그렇듯 자기 데이터로 A/B를 돌려 확인하세요.

7. 흔한 실수 · 팁

흔한 실수왜 문제인가대신 이렇게
컨텍스트가 길어지면 "요약해서 다시 써"로 정리 brevity bias·context collapse로 디테일이 통째로 증발 재작성 대신 델타 append. 정리는 dedup으로만
Reflector가 추상적 훈수를 뱉게 방치 "꼼꼼히 하라" 같은 규칙은 도움이 안 되고 자리만 차지 "다음에 그대로 따를 수 있는 구체적 규칙"만 요구
정답 라벨이 있어야만 학습된다고 가정 실무엔 라벨이 없는 경우가 대부분 테스트 결과·에러 등 실행 피드백으로 복기
플레이북을 자유 형식 글로 관리 개별 항목을 가리켜 폐기·수정하기 어려움 ID·카운터가 붙은 구조화된 항목 목록으로
helpful/harmful 카운터를 안 씀 안 먹히는 규칙이 계속 쌓여 노이즈가 됨 harmful이 잦은 항목은 deprecated로 내림
refine(정리)을 매 스텝 모델로 돌림 비용·지연이 커지고 collapse 위험이 되살아남 refine은 가끔·결정론적으로(임베딩 dedup)

한 가지 더. ACE가 만병통치는 아닙니다. 플레이북이 커질수록 매 호출에 들어가는 입력 토큰이 늘어, 컨텍스트 로트(context rot)나 비용 문제를 다시 불러올 수 있습니다. 그래서 helpful 순 정렬로 상위 항목만 주입하거나, 과제 종류별로 플레이북을 나눠 관련된 항목만 넣는 식의 조합이 현실적입니다. "무손실로 쌓되, 넣을 땐 골라서"가 실전 감각입니다.

8. 마무리 (TL;DR)

  • ACE(Agentic Context Engineering) = 모델 가중치를 안 건드리고, 컨텍스트를 '스스로 자라는 플레이북'으로 계속 개선하는 방법. (arXiv:2510.04618, ICLR 2026)
  • 함정은 요약이다. 통째로 다시 쓰면 brevity bias(디테일 뭉개짐)와 context collapse(한순간에 붕괴)가 난다.
  • 해법은 델타 업데이트. 기존 항목은 그대로 두고 새 항목만 append, 카운터만 증가. 결정론적 병합이라 붕괴가 구조적으로 없다.
  • 세 역할로 나눈다 — Generator(푼다) · Reflector(복기해 교훈을 뽑는다) · Curator(델타로 병합). grow-and-refine으로 키우고 dedup으로 다듬는다.
  • 정답 라벨 없이 실행 피드백만으로 학습 가능. 에이전트 +10.6%, 금융 +8.6%, 적응 지연 평균 86.9%↓ — 더 작은 모델로 프로덕션급 에이전트와 대등.
  • 프레임워크를 안 써도 좋다. "요약 말고 델타"라는 사고방식만 가져가도 에이전트 메모리 설계가 달라진다.
