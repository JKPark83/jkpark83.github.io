1. 도입 — "모델을 바꿔치기해도 아무도 모른다"

LLM API를 쓰는 개발자라면 한 번쯤 품어 본 의심이 있습니다. "요즘 응답이 좀 멍청해진 것 같은데… 혹시 뒤에서 모델을 바꾼 거 아냐?" 새 모델이 나올 때마다 커뮤니티에 "nerf됐다"는 글이 올라오고, 제공사는 "모델은 그대로"라고 답하는 풍경이 반복됩니다. 문제는 이 논쟁을 끝낼 방법이 지금껏 없었다는 겁니다. 출력 품질은 프롬프트·온도·운에 따라 출렁이니, 출력만 보고 어떤 모델이 돌았는지 판별하는 건 사실상 불가능합니다.

의심할 이유는 충분합니다. 여러 제공사를 중개하는 라우팅 서비스가 요청을 더 싼 모델로 슬쩍 돌릴 수도 있고, 피크 시간에만 양자화(quantization)된 버전을 내보낼 수도 있고, 추론 서버에 접근한 공격자가 토큰 스트림을 조작할 수도 있습니다. 전부 사용자 쪽에서는 검출할 수 없는 시나리오입니다.

11월 2일, Anthropic의 Frontier Red Team이 EPFL·MIT·StarkWare 연구자들과 함께 이 문제에 암호학으로 답하는 오픈소스 프로토타입 FlashProve를 공개했습니다. 핵심 주장은 한 문장입니다. "이 응답은, 미리 commit해 둔 바로 그 가중치에서 나왔다"는 걸 가중치를 공개하지 않고 수학적으로 증명할 수 있다. 그것도 장난감 모델이 아니라 400B 파라미터 MoE 모델(Llama 4 Maverick)에서, 증명 생성 110 토큰/초라는 "쓸 만한" 속도로요. 공개 직후 TechCrunch를 비롯한 외신이 다뤘고, Hacker News에서는 "진짜 프로덕션에서 돌아가겠냐"는 회의론과 "서빙 신뢰 문제의 첫 실용적 해법"이라는 반론이 부딪히며 이번 주 AI 엔지니어링 쪽의 뜨거운 주제가 됐습니다.

이 글은 FlashProve를 입구 삼아 provable inference(증명 가능한 추론)라는 분야 자체를 해부합니다. 영지식 증명을 몰라도 따라올 수 있게 바닥부터 쌓고, "왜 70배나 느린데도 의미가 있는지", 그리고 juniors가 여기서 가져갈 서빙 신뢰 모델의 사고방식까지 정리합니다.

2. 배경 — zkSNARK와 commitment, 3분 요약

암호학 용어 두 개만 잡으면 나머지는 술술 읽힙니다.

commitment(커밋먼트)는 "내용은 숨기되, 나중에 바꿀 수 없게 봉인하는" 장치입니다. 비유하면 이렇습니다. 제가 예측 하나를 종이에 적어 금고에 넣고 잠근 뒤, 금고 열쇠 구멍 모양만 사진으로 공개합니다. 여러분은 안에 뭐가 적혔는지 모르지만, 제가 나중에 내용물을 몰래 바꿀 수 없다는 건 압니다. FlashProve에서 제공사는 모델 가중치 전체를 이렇게 봉인하고, 짧은 '지문'(fingerprint)만 공개합니다. 가중치는 영업 비밀로 남지만, 이 지문이 가리키는 가중치는 단 하나로 고정됩니다.

zkSNARK(zero-knowledge succinct argument of knowledge, 영지식 간결 논증)는 "어떤 계산을 올바르게 수행했다"는 사실을, 계산 내용물을 보여 주지 않고 증명하는 기술입니다. 세 가지 성질이 핵심입니다.

  • 완전성(completeness) — 정직하게 만든 증명은 항상 통과합니다.
  • 건전성(soundness) — 거짓 명제의 증명을 위조하는 건 계산적으로 불가능합니다. FlashProve 저장소가 제시하는 수치로는, 해시 질의를 q번 하는 공격자가 속일 확률이 약 q/2124 + 2-101 — 사실상 0입니다.
  • 영지식(zero-knowledge) — 검증자는 증명에서 가중치도, 중간 계산값도, 어떤 expert가 선택됐는지도 알아낼 수 없습니다.

여기에 간결성(succinctness)이 붙습니다. 증명 파일은 작고, 검증은 원래 계산보다 훨씬 쌉니다. 400B 모델의 추론을 검증하는 데 GPU가 아니라 평범한 CPU에서 수 초~수십 초면 됩니다. "검증이 생성보다 압도적으로 싸다"는 이 비대칭이 provable inference 전체를 떠받치는 기둥입니다. 제공사 한 곳이 비싸게 증명을 만들면, 세상 누구나 싸게 검증할 수 있으니까요.

용어 정리: 이런 기술을 LLM에 적용하는 분야를 통틀어 zkML(zero-knowledge machine learning) 또는 verifiable inference라고 부릅니다. FlashProve는 그중 "프론티어급 모델에서 처음으로 실용적인 속도를 보여 준" 사례로 주목받고 있습니다.

3. 프로토콜 — 봉인하고, 증명하고, 아무나 검증한다

FlashProve의 흐름은 오프라인 1단계 + 온라인 2단계로 나뉩니다.

순서를 뜯어 보면 설계 의도가 보입니다.

① commitment는 모델당 한 번. 약 232GB짜리 양자화 가중치를 봉인하는 데 39분이 걸리지만, 한 번 만든 commitment는 약 1,600만 요청까지 재사용합니다. 검증자가 미리 받아 둘 것은 6.5MB짜리 commitment 파일뿐입니다.

② 증명은 '사후(post-hoc)'에 배치로. FlashProve는 서빙 경로에 끼어들지 않습니다. 이미 끝난 요청들(프롬프트 + 출력 토큰)을 24개씩 모아, 프리필(prefill)과 비슷한 병렬 패스로 한꺼번에 다시 읽으며 증명을 만듭니다. 응답 지연에 영향을 주지 않는 대신, 증명은 나중에 도착합니다. "지금 이 응답"이 아니라 "어제의 트래픽"을 감사하는 모델에 가깝습니다.

③ 검증은 철저히 가볍게. 검증자가 가진 것은 commitment, 프롬프트, 응답, 증명 파일 네 가지뿐입니다. 가중치도, GPU도 필요 없습니다. 증명이 통과하면 "이 출력 토큰들은 commit된 모델을 평가했을 때 나오는 토큰이 맞다"는 명제가 수학적으로 보증됩니다.

의사 코드로 쓰면 이 정도 그림입니다.

{{< highlight python >}} # 개념 흐름 — 실제 API가 아니라 프로토콜의 뼈대입니다 # ① 오프라인: 제공사가 모델당 1회 수행 commitment = commit(quantize_int4(weights)) # 가중치는 비공개, 지문만 공개 publish(commitment) # 약 6.5MB # ② 온라인: 서빙이 끝난 요청을 모아 사후 증명 batch = collect_finished_requests(n=24) # (프롬프트, 출력 토큰) 쌍 proofs = prove(weights, batch) # H100 1장, 110 tok/s send_to_verifier(proofs) # 요청당 약 19MB # ③ 검증: 누구나, CPU로 ok = verify(commitment, prompt, reply, proof) # 17~21초 # ok == True 이면: "commit된 그 모델이 이 토큰들을 생성했다"가 보증됨 {{< /highlight >}}

4. 엔지니어링 — 부동소수점은 적, MoE는 아군

"신경망 계산을 zkSNARK로 증명한다"는 아이디어 자체는 몇 년 된 이야기입니다. 문제는 속도였습니다. 프론티어급 모델에 닿으려면 두 개의 벽을 넘어야 하고, FlashProve의 재미는 이 벽을 넘는 방식에 있습니다.

벽 1: GPU 부동소수점은 증명하기 끔찍하다

zkSNARK는 계산을 유한체(finite field) 위의 산술, 쉽게 말해 깔끔한 정수 연산으로 바꿔서 증명합니다. 그런데 GPU 추론은 부동소수점(floating point) 세상입니다. 반올림 규칙이 복잡하고, 더하는 순서에 따라 결과가 미세하게 달라지는 비결정성(nondeterminism)까지 있습니다. "어젯밤 GPU가 뱉은 바로 그 부동소수점 계산"을 증명 대상으로 삼으면 비용이 폭발합니다.

FlashProve의 선택은 과감합니다. 증명 대상을 아예 정수 모델로 바꿔 버립니다. 공개된 4-bit 양자화 가중치로 정수 산술 프리필을 정의하고, 그 정수 모델에 대해 "각 검증 토큰이 모델의 greedy 선택(가장 확률 높은 토큰)과 일치한다"를 증명합니다. 정수 모델은 결정적이므로 증명하기 좋고, 저자들의 측정으로는 부동소수점 추론과의 불일치율도 작습니다. 대신 트레이드오프가 생깁니다 — 증명이 보증하는 건 어디까지나 정수 버전 모델의 greedy 출력이고, temperature 샘플링이나 부동소수점 경로가 다른 토큰을 골랐다면 그 지점부터는 증명과 어긋날 수 있습니다. 7장에서 다시 봅니다.

벽 2: 400B 파라미터를 다 증명할 수는 없다

여기서 MoE(Mixture-of-Experts) 구조가 뜻밖의 아군이 됩니다. Llama 4 Maverick은 전체 400B 파라미터지만, 토큰 하나를 처리할 때 실제로 활성화되는 건 약 17B뿐입니다. FlashProve의 prover 비용은 전체 파라미터가 아니라 활성 파라미터에 비례하도록 설계됐습니다. 23배 차이입니다. 밀집(dense) 400B 모델이었다면 지금의 속도는 나오지 않았을 겁니다. 영리한 점은, 증명 비용은 활성 expert만큼만 내면서도 어떤 expert가 선택됐는지는 영지식으로 숨긴다는 것입니다. expert 선택 패턴도 모델의 영업 비밀일 수 있으니까요.

하드웨어 요구 사항도 눈여겨볼 만합니다. 증명에는 H100 8장이 아니라 80GB GPU 한 장 + 호스트 메모리 약 290GB면 됩니다. 가중치를 레이어 단위 조각으로 쪼개 호스트 메모리에서 GPU로 흘려보내는(streaming) 구조라, VRAM에 모델이 통째로 들어갈 필요가 없습니다. 증명은 지연에 민감하지 않은 배치 작업이니 가능한 설계입니다 — 같은 모델을 '서빙'할 때와 '증명'할 때의 하드웨어 전략이 갈리는 지점이 재미있습니다.

5. 숫자로 보기 — 110 토큰/초와 72배의 의미

Anthropic이 보고한 수치를 한 표로 모으면 이렇습니다. 모두 Llama 4 Maverick(400B MoE, 활성 17B), 공개된 4-bit 가중치, prover는 H100 1장 + CPU 24코어 기준입니다.

항목수치비고
commitment 생성약 39분모델당 1회, 약 1,600만 요청까지 재사용
commitment 다운로드약 6.5MB검증자가 미리 받아 둘 파일
증명 생성 처리량약 110 토큰/초24개 요청 배치, 배치당 약 223초
증명 크기약 18.78MB1,024 토큰 요청 1건 기준
검증 시간17초(24스레드) / 21초(1스레드)CPU만 사용, 오프라인 검사 포함
서빙 대비 오버헤드약 72배 (측정 66~77배)vLLM(FP8, H100 8장) 대비 GPU 시간 기준, 최고 부하에선 약 94배

"72배"라는 숫자만 보면 비현실적으로 느껴질 수 있습니다. 하지만 이 분야의 직전 기록들과 나란히 놓으면 이야기가 달라집니다.

직전 공개 연구인 VerInf는 같은 Llama 4 Maverick에서 1,000토큰을 증명하는 데 14.3시간, 증명 크기는 93.6GB였습니다. FlashProve는 같은 분량을 초 단위로 증명하고 증명 크기도 19MB 수준입니다. "원리적으로 가능하다"에서 "감사(audit) 용도로는 쓸 만하다"로 체급이 바뀐 셈이고, 이게 이번 공개가 화제가 된 실질적 이유입니다.

그래서 비용은? 오버헤드 72배를 뒤집으면, 전체 트래픽의 일부만 표본 추출해 증명하는 그림이 나옵니다. 예컨대 트래픽의 1%만 무작위로 골라 증명해도 "상시 바꿔치기"는 통계적으로 금방 들통납니다. 전수 증명이 아니라 감사 표본이라고 생각하면 72배는 갑자기 현실적인 숫자가 됩니다.

6. 실전 — 저장소를 열어 직접 검증해 보기

FlashProve는 github.com/anthropics/FlashProve에 Apache 2.0으로 전부 공개돼 있습니다. prover(C++/CUDA, H100 필요), CPU 검증기, Lean 4 형식 증명, 프로토콜 명세, 그리고 샘플 증명 파일까지 들어 있어서, GPU 없이도 검증 쪽은 직접 만져 볼 수 있습니다.

{{< highlight bash >}} git clone https://github.com/anthropics/FlashProve cd FlashProve # 구조 훑어보기 # prover/ — GPU prover (H100 + CUDA, 증명 '생성'은 여기) # verifier/ — C++ 고속 검증기 cp_verify (CPU만으로 동작) # lean/ — 프로토콜 건전성의 Lean 4 형식 증명 (THEOREM.md부터) # docs/ — 프로토콜 명세와 증명 파일 포맷 # examples/ — 수락되는 증명 / 거부되는 증명 샘플 # integrations/ — check_proof.py 등 검증 연동 스크립트 {{< /highlight >}}

junior에게 권하는 코스는 세 단계입니다. 먼저 examples/의 샘플로 "통과하는 증명"과 "거부되는 증명"을 검증기에 넣어 보고, 다음으로 docs/의 포맷 문서로 증명 파일 안에 뭐가 들었는지 확인하고, 마지막으로 lean/THEOREM.md에서 "이 코드가 증명한다고 주장하는 명제가 정확히 뭔지"를 읽는 것입니다. 특히 세 번째가 중요합니다 — 이 프로젝트의 독특한 점이 완전성·건전성·영지식이라는 최상위 보안 명제를 Lean으로 형식화했다는 것이기 때문입니다(랜덤 오라클 모델 기준). 검증기도 두 벌입니다. 빠른 C++ 검증기와, 느리지만 Lean 명세에서 직접 나온 실행 가능한 검증기가 있고, 모든 테스트에서 두 결과가 일치합니다.

Lean이 낯설다면 — 이 블로그의 LLM과 형식 검증 글에서 "코드가 아니라 명제를 믿는다"는 개념을 먼저 잡고 오면 THEOREM.md가 한결 수월합니다. 다만 거기서는 LLM이 증명을 '쓰는' 쪽이었다면, 여기서는 암호 프로토콜의 안전성을 사람이 Lean으로 못 박아 둔 경우라 방향이 반대입니다.

현실적인 기대치도 적어 둡니다. 실제 Maverick 크기의 증명 생성을 재현하려면 H100과 300GB 넘는 RAM이 필요하고, README 기준 단일 토큰 증명에도 시간 단위가 걸립니다. 저장소 설명에는 "research prototype, not maintained"가 명시돼 있습니다. 학습용 교보재이자 재현 가능한 벤치마크이지, 가져다 붙이는 라이브러리가 아닙니다.

7. 한계와 흔한 오해

발표가 화제가 된 만큼 과대 해석도 많이 돌았습니다. 증명이 보증하는 범위를 정확히 긋는 게 이 주제의 절반입니다.

  • "내 채팅이 증명되는 건 아니다." 컨텍스트 한계가 1,024 토큰입니다. 시스템 프롬프트만으로 수천 토큰을 쓰는 실제 챗·에이전트 트래픽에는 아직 턱없이 짧습니다. 저자들도 컨텍스트 확장을 1순위 future work로 꼽습니다.
  • greedy 디코딩만 증명합니다. 증명 명제는 "각 토큰이 정수 모델의 greedy 선택과 일치한다"입니다. temperature 샘플링으로 뽑은 응답은 어느 지점부터 greedy 경로와 갈라질 수 있고, 그 토큰은 증명 대상이 아닙니다.
  • 증명되는 건 '정수 모델'입니다. 실제 서빙되는 부동소수점 모델과 commit된 4-bit 정수 모델은 수학적으로 다른 함수입니다. 둘의 출력이 거의 일치한다는 건 경험적 측정이지 증명이 아니고, 저자들 스스로 적대적으로 설계된 프롬프트에서는 이 근사가 보장되지 않는다고 적었습니다.
  • 아키텍처는 숨기지 않습니다. 가중치·중간값·expert 선택은 영지식으로 보호되지만, MoE 구조라는 사실 자체는 공개 전제입니다. 아키텍처까지 숨기는 commitment는 future work입니다.
  • 타이밍 같은 사이드 채널 공격은 범위 밖이고, "제공사가 내 데이터로 몰래 학습하지 않는다" 같은 것도 이 증명이 보증하는 명제가 아닙니다.
  • Anthropic이 API에 붙인다는 발표가 아닙니다. TechCrunch 보도에 따르면 당장 배포 계획은 없습니다. 연구 분야 자체를 가속하려는 오픈소스 공개로 읽는 게 정확합니다.

그럼에도 junior 엔지니어가 이 주제를 알아 둘 이유는 분명합니다. 첫째, 서빙 신뢰 모델이라는 사고방식입니다. "API 응답을 믿는다"는 말에는 사실 모델 동일성·버전 고정·비조작이라는 여러 가정이 뭉쳐 있고, 이번 공개는 그 가정들을 처음으로 분해해 하나씩 검증 가능하게 만들었습니다. KV 캐시 유출 사고에서 봤듯, 서빙 계층의 신뢰는 공짜가 아닙니다. 둘째, 제3자 라우터 생태계가 커질수록 "중개자가 약속한 모델을 정말 호출했는가"는 돈이 걸린 질문이 됩니다. 셋째, 규제와 평가입니다. 벤치마크 제출 모델과 서빙 모델이 같다는 것, 감사 시점의 모델이 승인받은 그 모델이라는 것을 증명할 수단은 지금까지 "회사의 말"뿐이었습니다. 평가 무결성에 민감한 조직이라면 이 흐름이 어디로 가는지 지켜볼 가치가 있습니다.

8. 마무리 (TL;DR)

  • 11월 2일 Anthropic Frontier Red Team이 EPFL·MIT·StarkWare와 함께 FlashProve를 공개했습니다 — "이 응답은 commit된 그 가중치에서 나왔다"를 가중치 공개 없이 증명하는 provable inference의 오픈소스 프로토타입입니다(Apache 2.0).
  • 프로토콜은 3단계: 모델당 1회 commitment(39분, 6.5MB) → 서빙이 끝난 요청을 배치로 모아 zkSNARK 증명 생성(H100 1장, 110 tok/s, 요청당 약 19MB) → 누구나 CPU로 검증(17~21초).
  • 핵심 엔지니어링 두 가지: 부동소수점 대신 4-bit 정수 모델 + greedy 디코딩을 증명 대상으로 고정했고, MoE 덕에 증명 비용이 400B 전체가 아니라 활성 17B에만 비례합니다(expert 선택은 영지식으로 은닉).
  • 서빙(vLLM FP8, H100 8장) 대비 오버헤드는 GPU 시간 기준 약 72배(최고 부하 94배). 전수 증명이 아니라 트래픽 표본 감사로 보면 현실적인 숫자이고, 직전 연구(같은 모델에서 1,000토큰에 14.3시간)와 비교하면 체급이 다릅니다.
  • 한계도 뚜렷합니다: 컨텍스트 1,024 토큰, greedy만, 정수 모델 근사(적대적 프롬프트 미보장), 아키텍처 비은닉, 연구 프로토타입("not maintained"). Anthropic API에 붙는다는 발표가 아닙니다.
  • 완전성·건전성·영지식 명제를 Lean 4로 형식화한 점이 독특합니다. GPU 없이도 저장소의 샘플 증명과 lean/THEOREM.md로 "무엇이 증명되고 무엇이 아닌지"를 직접 확인해 볼 수 있습니다.
