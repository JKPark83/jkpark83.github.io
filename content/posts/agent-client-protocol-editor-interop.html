1. 도입 — 안드로이드 스튜디오에 Claude가 들어온 날

2026년 10월 28일, 구글은 Android Dev Summit에서 Android Studio의 새 안정판(Rabbit 2)을 발표하면서 흥미로운 결정을 함께 내놨습니다. 자사 IDE 안에서 Anthropic의 Claude Agent, OpenAI의 Codex를 1급 시민으로 쓸 수 있게 개방한 겁니다. 기본 제공되는 세 에이전트(Claude Agent, Codex, 구글의 Antigravity) 외에도, 설정 화면에서 40여 개의 외부 코딩 에이전트를 골라 연결할 수 있습니다. 연결된 에이전트는 Android Studio의 빌드 시스템, 에뮬레이터, Logcat까지 활용합니다.

구글이 경쟁사의 에이전트에게 자기 IDE의 문을 열었다는 점 자체도 화제였지만, 엔지니어링 관점에서 진짜 주인공은 따로 있습니다. 이 개방을 기술적으로 가능하게 만든 공개 표준, ACP(Agent Client Protocol)입니다. 구글이 에이전트 하나하나와 전용 연동을 만든 게 아닙니다. ACP라는 프로토콜 하나를 구현했더니, ACP를 말할 줄 아는 에이전트 전부가 따라 들어온 겁니다.

1년 전만 해도 상황은 정반대였습니다. Claude Code는 터미널이나 전용 확장에서, Codex는 자체 앱에서, 각 에디터는 각자 만든 에이전트 패널에서 — 에이전트와 에디터의 조합마다 전용 통합을 새로 만들어야 했습니다. 오늘은 이 문제를 어떻게 프로토콜 하나로 풀었는지, 에디터와 에이전트 사이에 실제로 무슨 JSON이 오가는지를 바닥부터 해부합니다. 마지막에는 파이썬으로 미니 ACP 클라이언트를 직접 만들어 봅니다.

2. 배경 — N×M 통합 지옥, 그리고 LSP가 남긴 교훈

문제의 구조는 단순합니다. 에디터가 N개, 코딩 에이전트가 M개 있으면, 모든 조합을 지원하는 데 N×M개의 통합이 필요합니다. VS Code·JetBrains·Zed·Neovim·Android Studio에 Claude Code·Codex·Copilot·Qwen Code를 다 연결하려면 20개의 전용 플러그인을 각각 만들고 유지보수해야 합니다. 에이전트 개발사는 에디터마다 UI를 다시 짜고, 에디터 개발사는 에이전트마다 연동을 다시 짭니다.

개발 도구 업계는 이 문제를 이미 한 번 풀어 본 적이 있습니다. LSP(Language Server Protocol)입니다. LSP 이전에는 에디터마다 언어별 자동완성·정의 이동 기능을 따로 구현했지만, LSP가 "에디터 ↔ 언어 서버" 사이의 공용 규약이 된 뒤로는 언어 서버 하나만 만들면 모든 에디터에서 돌아갑니다. N×M이 N+M으로 줄어든 거죠.

ACP는 같은 아이디어를 코딩 에이전트에 적용한 겁니다. 에디터 개발사 Zed가 2025년 8월 27일 공개했고, 구글 Gemini CLI 팀과 협력해 첫 레퍼런스 통합을 만들었습니다. Apache 2.0 라이선스의 오픈 소스이고, 지금은 Zed 단독 프로젝트가 아니라 독립 GitHub 조직(agentclientprotocol)에서 관리됩니다. 공개 14개월 만에 Zed·Neovim·Emacs·JetBrains IDE를 거쳐 Android Studio까지 품은 셈입니다.

다만 LSP와 똑같지는 않습니다. LSP는 "커서 위치의 심볼 정의가 어디냐" 같은 짧은 요청-응답 중심이지만, 에이전트와의 대화는 한 턴이 몇 분씩 이어지고 그 사이에 계획 수립·파일 수정·명령 실행·사용자 승인이 뒤섞입니다. 그래서 ACP는 긴 턴 동안의 스트리밍 업데이트와, 에이전트가 거꾸로 에디터를 호출하는 역방향 요청(권한 요청, 파일 읽기/쓰기)을 프로토콜의 중심에 뒀습니다. 이 구조가 아래에서 볼 핵심입니다.

3. 해부 ① — ACP의 뼈대: 프로세스, 전송, 핸드셰이크

에이전트는 에디터의 자식 프로세스입니다

ACP의 배치는 간단합니다. 에디터(스펙 용어로는 Client)가 에이전트 실행 파일을 서브프로세스로 띄우고, 그 프로세스의 stdin/stdout으로 JSON-RPC 2.0 메시지를 주고받습니다. 메시지 프레이밍은 개행 구분 JSON(newline-delimited JSON)입니다. 스펙은 "메시지는 개행(\n)으로 구분되며, 메시지 안에 개행이 포함되면 안 된다"고 못 박습니다. LSP가 Content-Length 헤더로 메시지를 구분하는 것과 달리, MCP의 stdio 전송과 같은 방식을 택한 겁니다. 한 줄 = 한 메시지라서 디버깅할 때 tee로 흘려보기도 쉽습니다.

중요한 건 통신이 양방향이라는 점입니다. 어느 쪽도 일방적인 서버가 아닙니다.

방향메서드역할
에디터 → 에이전트initialize, authenticate버전·capability 협상, 인증
session/new, session/load대화 세션 생성·복원
session/prompt, session/cancel, session/set_mode사용자 메시지 전달, 턴 취소, 모드 전환
에이전트 → 에디터session/update (알림)진행 상황 스트리밍 — 텍스트 조각, 계획, tool call
session/request_permission"이 tool call 실행해도 될까요?" 승인 요청
fs/read_text_file, fs/write_text_file, terminal/*에디터를 통한 파일 접근·터미널 실행 (선택 capability)

에이전트가 파일을 직접 읽지 않고 굳이 fs/read_text_file로 에디터에 부탁하는 이유가 뭘까요? 에디터 버퍼에만 있는, 아직 저장 안 된 수정 내용까지 읽을 수 있기 때문입니다. 반대로 에이전트가 fs/write_text_file로 쓰면 에디터는 그 변경을 버퍼에 반영하면서 undo 히스토리·diff 뷰에 자연스럽게 통합할 수 있습니다. "파일 시스템 접근을 UI 계층에 위임한다"는 설계죠.

핸드셰이크: capability 협상

연결 후 첫 메시지는 항상 에디터가 보내는 initialize입니다. 서로 "나는 뭘 할 수 있다"를 교환합니다.

{{< highlight json >}} // 에디터 → 에이전트 { "jsonrpc": "2.0", "id": 0, "method": "initialize", "params": { "protocolVersion": 1, "clientCapabilities": { "fs": { "readTextFile": true, "writeTextFile": true }, // 파일 접근 대행 가능 "terminal": true // 터미널 실행 대행 가능 } } } // 에이전트 → 에디터 (응답) { "jsonrpc": "2.0", "id": 0, "result": { "protocolVersion": 1, "agentCapabilities": { "loadSession": true, // 과거 세션 복원 지원 "promptCapabilities": { "image": true, "embeddedContext": true } }, "authMethods": [] } } {{< /highlight >}}

세션은 session/new로 만듭니다. 파라미터는 두 가지가 핵심입니다. cwd는 세션의 작업 디렉터리인데 반드시 절대 경로여야 하고, mcpServers는 에디터가 쓰던 MCP 서버 목록을 에이전트에게 넘겨주는 통로입니다(5장에서 다시 봅니다). 응답으로 sessionId를 받으면 준비 끝입니다.

4. 해부 ② — prompt turn: 한 번의 대화가 흘러가는 길

사용자가 메시지를 입력하고 에이전트가 응답을 마칠 때까지의 한 사이클을 스펙은 prompt turn이라고 부릅니다. ACP에서 가장 정교하게 설계된 부분입니다.

에디터는 session/prompt로 턴을 시작합니다. 본문은 콘텐츠 블록 배열이라서, 텍스트와 함께 사용자가 @멘션한 파일 내용을 리소스 블록으로 임베드해 보낼 수 있습니다. 여기서부터 턴이 끝날 때까지, 에이전트는 진행 상황을 session/update 알림으로 계속 흘려보냅니다. 대표적인 update 종류는 이렇습니다.

  • plan — 에이전트의 실행 계획. 항목마다 내용·우선순위·상태가 있어 에디터가 체크리스트 UI를 그릴 수 있습니다.
  • agent_message_chunk — 스트리밍되는 응답 텍스트 조각. (생각 과정은 별도의 thought chunk로 옵니다.)
  • tool_call / tool_call_update — 도구 호출의 시작과 상태 변화.

tool call은 작은 상태 머신입니다. pending으로 태어나 in_progress를 거쳐 completed 또는 failed로 끝나고, 각 단계가 tool_call_update로 중계됩니다. kind 필드(read, edit, execute, search 등 10종)는 에디터가 아이콘을 고르는 힌트고, 파일 diff(oldText/newText)나 터미널 출력을 결과 콘텐츠로 실어 보낼 수 있어 에디터가 네이티브 diff 뷰로 보여줄 수 있습니다.

{{< highlight json >}} // 에이전트 → 에디터: tool call 시작을 알리는 session/update 알림 { "jsonrpc": "2.0", "method": "session/update", "params": { "sessionId": "sess_abc123def456", "update": { "sessionUpdate": "tool_call", "toolCallId": "call_001", "title": "main.py 수정", "kind": "edit", "status": "pending" } } } {{< /highlight >}}

권한 요청 — 승인 UI의 표준화

위험한 작업 전에 에이전트는 session/request_permission을 역방향으로 호출합니다. 요청에는 선택지 목록이 들어 있고, 각 선택지의 kind는 allow_once / allow_always / reject_once / reject_always 네 가지 중 하나입니다. 에디터는 이걸로 승인 다이얼로그를 그리고, 사용자가 고른 optionId를 응답으로 돌려줍니다. "항상 허용"을 기억하는 주체는 에이전트 쪽이고, 그 범위와 유효 기간도 에이전트가 정합니다. 에디터는 사용자 설정에 따라 자동 승인·자동 거절을 해도 됩니다 — YOLO 모드와 보수 모드가 프로토콜 위에서 자연스럽게 공존하는 구조입니다.

턴의 끝은 에이전트가 맨 처음 받은 session/prompt 요청에 응답을 돌려주는 순간입니다. 응답에는 stopReason이 담깁니다: 정상 종료 end_turn, 토큰 한도 max_tokens, 턴당 모델 호출 수 초과 max_turn_requests, 거부 refusal, 취소 cancelled. 취소 흐름도 꼼꼼하게 정의되어 있습니다. 에디터가 session/cancel 알림을 보내면, 에이전트는 진행 중인 작업을 멈추고 남은 update를 모두 흘려보낸 뒤 stopReason: "cancelled"로 응답해야 합니다. 중단으로 생긴 예외를 에러로 올리지 말고 cancelled로 변환하라는 것까지 스펙에 적혀 있습니다.

5. 지도 그리기 — MCP · ACP · A2A는 각자 어디를 맡나

프로토콜 이름이 셋이나 나오니 헷갈리기 쉽습니다. 역할로 구분하면 깔끔합니다.

프로토콜연결 구간해결하는 문제
MCP (Model Context Protocol)에이전트 ↔ 도구·데이터 소스"에이전트에게 어떤 도구와 컨텍스트를 줄 것인가"
ACP (Agent Client Protocol)에디터(UI) ↔ 에이전트"에이전트를 사람 앞에 어떻게 보여주고 조종할 것인가"
A2A (Agent2Agent)에이전트 ↔ 에이전트"서로 다른 에이전트끼리 어떻게 협업할 것인가"

셋은 경쟁 관계가 아니라 스택의 서로 다른 층입니다. 실제로 ACP는 MCP와 합을 맞추도록 설계됐습니다. 에디터는 session/new의 mcpServers 파라미터로 자기가 알고 있는 MCP 서버 목록(stdio 명령 또는 HTTP 엔드포인트)을 넘기고, 에이전트가 그 서버들에 대신 연결합니다. 사용자가 에디터에 MCP 서버를 한 번 등록해 두면, 어떤 ACP 에이전트로 갈아타도 같은 도구를 그대로 쓰는 거죠. stdio 전송 지원은 모든 에이전트의 의무이고, HTTP는 mcpCapabilities.http를 선언한 에이전트만 받습니다. 콘텐츠 블록 표현도 MCP의 형식을 따르므로, MCP를 구현해 본 팀이라면 ACP의 절반은 익숙할 겁니다.

A2A와 MCP를 깊게 파고 싶다면 이 블로그의 A2A 프로토콜 해부와 MCP 코드 실행 글을 함께 읽어 보세요.

6. 실전 — 파이썬 60줄로 미니 ACP 클라이언트 만들기

프로토콜은 직접 말을 걸어 봐야 체득됩니다. 공식 SDK(TypeScript @agentclientprotocol/sdk, Rust agent-client-protocol, Python·Kotlin·Java SDK)도 있지만, 여기서는 일부러 SDK 없이 날 것의 JSON-RPC로 에이전트를 구동해 보겠습니다. 와이어에 뭐가 흐르는지 눈으로 보는 게 목적이니까요.

{{< highlight python >}} import json, subprocess, itertools, os # ACP를 지원하는 에이전트 실행 명령이면 뭐든 됩니다. # 예: Claude Code 어댑터 → ["npx", "@zed-industries/claude-code-acp"] AGENT_CMD = ["npx", "@zed-industries/claude-code-acp"] proc = subprocess.Popen( AGENT_CMD, stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True, bufsize=1, # 줄 단위 버퍼링 — ndjson이므로 중요 ) _id = itertools.count() def send(method, params, *, notify=False): msg = {"jsonrpc": "2.0", "method": method, "params": params} if not notify: msg["id"] = next(_id) # 개행 구분 JSON: 메시지 안에 개행이 있으면 안 되므로 한 줄로 직렬화 proc.stdin.write(json.dumps(msg) + "\n") return msg.get("id") def recv(): return json.loads(proc.stdout.readline()) def wait_result(rid): """rid의 응답을 기다리며, 그 사이의 알림·역방향 요청을 처리합니다.""" while True: m = recv() if m.get("id") == rid and "result" in m: return m["result"] if m.get("method") == "session/update": u = m["params"]["update"] kind = u["sessionUpdate"] if kind == "agent_message_chunk": print(u["content"].get("text", ""), end="", flush=True) else: print(f"\n[update] {kind}") elif m.get("method") == "session/request_permission": # 데모용: allow 계열 첫 옵션을 자동 선택 (실전에서는 사용자에게 물어야 함) opt = next(o for o in m["params"]["options"] if o["kind"].startswith("allow")) proc.stdin.write(json.dumps({ "jsonrpc": "2.0", "id": m["id"], "result": {"outcome": {"outcome": "selected", "optionId": opt["optionId"]}}, }) + "\n") print(f"\n[권한 자동 승인] {opt['name']}") # 1) 핸드셰이크 — 우리는 fs/terminal 대행을 지원하지 않는 최소 클라이언트 rid = send("initialize", {"protocolVersion": 1, "clientCapabilities": {}}) caps = wait_result(rid) print("에이전트 capability:", caps["agentCapabilities"]) # 2) 세션 생성 — cwd는 반드시 절대 경로 rid = send("session/new", {"cwd": os.getcwd(), "mcpServers": []}) session_id = wait_result(rid)["sessionId"] # 3) prompt turn 시작 rid = send("session/prompt", { "sessionId": session_id, "prompt": [{"type": "text", "text": "이 프로젝트 구조를 요약해줘"}], }) print("\n--- 턴 종료:", wait_result(rid)["stopReason"]) {{< /highlight >}}

이 짧은 스크립트가 에디터가 하는 일의 뼈대 전부입니다. 돌려 보면 세 가지가 손에 잡힙니다. 첫째, wait_result 루프가 곧 에디터의 이벤트 루프입니다 — 응답을 기다리는 동안에도 update 알림과 역방향 권한 요청이 섞여 들어오므로, 메시지를 종류별로 분기하는 구조가 필수입니다. 둘째, 권한 요청에 응답하지 않으면 에이전트는 그 tool call 앞에서 영원히 기다립니다. 셋째, 실제 에디터가 추가로 하는 일은 이 이벤트들을 diff 뷰·체크리스트·승인 다이얼로그 같은 UI로 그려 주는 것뿐입니다. 프로토콜을 이해하면 Obsidian 플러그인이든 사내 코드 리뷰 도구든, ACP 에이전트를 품는 자체 프런트엔드를 만들 수 있다는 뜻입니다.

7. 생태계 — 레지스트리, 어댑터, 그리고 v2 초안

레지스트리. 에이전트가 많아지면 "내 에디터에서 뭘 어떻게 연결하지"가 다음 문제가 됩니다. 그래서 JetBrains와 Zed는 2026년 1월 ACP Agent Registry를 공개했습니다. 설치 명령·인증 방식이 검증된 에이전트들의 큐레이션 목록으로, JetBrains IDE와 Zed에 내장되어 있습니다. Android Studio의 40여 개 에이전트 목록(Settings > Tools > AI > Agents)도 같은 레지스트리 생태계 위에 서 있습니다. Codex, Copilot, Devin, Junie, OpenCode, Qwen Code 같은 이름들이 올라와 있죠.

어댑터 패턴. 기존 에이전트가 ACP를 네이티브로 지원하지 않아도, 에이전트의 자체 SDK를 ACP로 번역하는 얇은 프로세스를 끼우면 됩니다. 대표적인 예가 Zed가 만든 @zed-industries/claude-code-acp입니다. Claude Code의 SDK(현 Claude Agent SDK)를 감싸 ACP 메시지로 바꿔 주는 어댑터로, 2025년 10월 Zed의 Claude Code 통합이 바로 이 구조였고, 지금 다른 에디터들도 재사용하고 있습니다. 직접 만든 사내 에이전트를 회사 전체 에디터에 배포하고 싶을 때도 이 패턴을 그대로 쓰면 됩니다.

v2 초안. 프로토콜은 지금 버전 1이 안정판이고, v2 초안이 공개 작업 중입니다. 세션 관리가 session/resume·session/list·session/close로 재정리되고, 인증이 auth/login 흐름으로 다듬어지고, 포그라운드 작업이 끝났음을 알리는 state_update 알림이 들어오는 등 "에이전트 여러 개를 오래 띄워 두고 관리하는" 시나리오 쪽으로 진화하고 있습니다. 참고로 생태계의 변화 속도를 보여주는 장면 하나: ACP의 첫 통합 주자였던 Gemini CLI는 2026년 중반 구글이 Antigravity CLI로 세대교체를 진행하면서, Zed 커뮤니티에서 통합을 갈아 끼우는 논의가 진행 중입니다. 프로토콜이 표준이면 이런 교체도 "에이전트 바이너리만 바꾸면 되는 일"이 됩니다.

8. 흔한 실수 · 팁

  • JSON을 pretty-print로 보내지 마세요. ACP의 stdio 전송은 개행 구분입니다. 들여쓰기가 들어간 여러 줄 JSON을 쓰는 순간 상대방 파서가 깨집니다. 직렬화는 항상 한 줄로, 마지막에 \n 하나만.
  • 에이전트를 만들 때 stdout에 로그를 찍지 마세요. stdout은 프로토콜 전용 채널입니다. print 디버깅 한 줄이 통신 전체를 오염시킵니다. 로그는 stderr나 파일로 보내세요. (MCP stdio 서버를 만들 때와 같은 함정입니다.)
  • cwd는 절대 경로. 스펙이 MUST로 요구합니다. 상대 경로를 넣으면 어떤 에이전트는 받아 주고 어떤 에이전트는 거부하는, 가장 재현하기 어려운 종류의 버그가 됩니다.
  • capability를 선언하지 않았으면 호출도 오지 않습니다. clientCapabilities.fs를 빼놓고 "에이전트가 파일을 안 고친다"고 고민하지 마세요. 에이전트는 협상된 capability 밖의 메서드를 호출하면 안 되므로, 선언하지 않은 기능은 조용히 비활성화됩니다.
  • 취소 처리는 양쪽 모두의 의무입니다. 에디터는 취소 시 대기 중인 권한 요청에 cancelled outcome으로 응답해야 하고, 에이전트는 중단 예외를 에러가 아닌 stopReason: "cancelled"로 변환해야 합니다. 이걸 빼먹으면 취소 버튼을 누를 때마다 UI에 에러 토스트가 뜨는 어설픈 통합이 됩니다.
  • 동명이인 패키지를 조심하세요. 공식 Claude Code 어댑터는 npm의 @zed-industries/claude-code-acp(스코프 포함)입니다. 스코프 없는 비공식 동명 패키지들이 존재합니다. 지난주 공급망 보안 글에서 다뤘듯, AI 도구 체인은 지금 공격자들의 1순위 표적입니다.
  • mcpServers의 env·headers는 자격 증명입니다. 세션 생성 파라미터를 통째로 로그에 남기면 API 키가 함께 남습니다. 스펙도 셸을 거치지 않고 실행하라고 경고합니다.

9. 마무리 (TL;DR)

  • 10월 28일 Android Dev Summit에서 Android Studio Rabbit 2가 안정판이 되면서, Claude Agent·Codex·Antigravity를 포함한 40여 개 외부 코딩 에이전트를 IDE에 연결하는 BYOA가 열렸습니다. 그 기반이 공개 표준 ACP(Agent Client Protocol)입니다.
  • ACP는 Zed가 2025년 8월 시작한 에디터 ↔ 에이전트 프로토콜로, LSP가 언어 서버에서 풀었던 N×M 통합 문제를 코딩 에이전트에서 다시 풉니다. 에이전트는 에디터의 서브프로세스로 돌고, 개행 구분 JSON-RPC 2.0을 stdio로 주고받습니다.
  • 핵심 흐름은 initialize(capability 협상) → session/new(cwd + MCP 서버 전달) → session/prompt로 시작하는 prompt turn입니다. 턴 동안 에이전트는 session/update로 계획·텍스트·tool call을 스트리밍하고, session/request_permission으로 승인을 역방향 요청하며, stopReason으로 턴을 닫습니다.
  • MCP는 에이전트↔도구, ACP는 UI↔에이전트, A2A는 에이전트↔에이전트 — 경쟁이 아니라 스택의 다른 층이고, ACP는 MCP 서버 목록을 세션에 넘겨주는 식으로 MCP와 맞물립니다.
  • 프로토콜만 이해하면 60줄짜리 스크립트로도 어떤 ACP 에이전트든 구동할 수 있습니다. 거꾸로 사내 에이전트에 ACP(또는 어댑터)를 입히면 모든 주요 에디터가 공짜 프런트엔드가 됩니다.
