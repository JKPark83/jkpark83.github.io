1. 도입 — "거대 모델 한 대"가 당연하지 않은 분야

요즘 AI 엔지니어링의 기본 반사는 "문제가 어려우면 더 큰 모델을 쓴다"입니다. 그런데 이 반사가 정면으로 깨지는 분야가 하나 있습니다. 바로 진화적 탐색(evolutionary search)입니다. 알고리즘을 자동으로 발견하거나 수치 해법을 최적화하는 이 일은, 모델 한 번의 영리함보다 "같은 예산으로 얼마나 많은 후보를 시험해 보느냐"가 성패를 가릅니다.

11월 둘째 주 arXiv에 올라온 SwarmEvolve: Latent Agent Swarms for Evolutionary Discovery and Optimization(arXiv:2611.08483, Qile Jiang·George Em Karniadakis)가 화제가 된 건 이 통념을 데이터로 뒤집었기 때문입니다. 핵심 결과 한 줄이 강렬합니다. Qwen3 8B짜리 작은 모델을 떼로 돌린 SwarmEvolve가, 같은 문제에서 다른 프레임워크가 Qwen3 32B로 돌린 결과보다 평균 점수가 높았습니다. 게다가 다른 최신 시스템이 60분 걸려 도달하는 점수에, SwarmEvolve는 중앙값 기준 3~8분이면 닿았습니다. Hugging Face Daily Papers와 alphaXiv 트렌딩에 함께 오르며 "작은 모델 + 영리한 엔지니어링이 프런티어 모델을 이긴다"는, 실무자들이 좋아하는 바로 그 서사를 만들었습니다.

이 글의 목표는 보도가 아니라 설계를 읽는 것입니다. SwarmEvolve가 쓴 트릭 — 텍스트 대신 latent 공간에서 생각하기, 대화 대신 KV 캐시를 직접 주고받기, 그리고 다양성을 숫자로 관리하기 — 는 진화 탐색만의 묘수가 아닙니다. "같은 비용으로 더 많은 시도를 돌려야 하는" 모든 에이전트 시스템에 그대로 옮겨 붙는 사고방식입니다. junior 엔지니어에게 이 세 가지는 꽤 오래 써먹을 도구가 됩니다.

2. 배경 — 진화적 코딩 에이전트가 뭐고, 왜 비싼가

먼저 진화적 코딩 에이전트(evolutionary coding agent)가 뭔지 짚고 갑니다. 2025년 5월 Google DeepMind가 공개한 AlphaEvolve가 이 분야를 대중화했습니다. 발상은 생물의 진화를 코드에 적용한 것입니다.

  1. 풀고 싶은 문제와 채점 함수(evaluator)를 준다. 채점 함수는 코드를 받아 점수(실행 시간, 정확도, 오차 등)를 숫자로 돌려줍니다. 이게 "적합도(fitness)"입니다.
  2. LLM이 기존 프로그램을 변형(mutation)한다. "이 코드를 이렇게 바꿔 봐"라고 LLM에게 시켜 새 후보를 만듭니다.
  3. 후보를 채점한다. 실제로 돌려서 점수를 매깁니다.
  4. 잘한 후보를 살려 다음 세대의 부모로 쓴다. 점수 높은 것들을 보관소(program database)에 넣고, 그 이력을 다시 프롬프트에 넣어 더 나은 변형을 유도합니다.

이 루프를 수천 번 돌리면 사람이 생각 못 한 해법이 나옵니다. AlphaEvolve는 이 방식으로 4×4 복소수 행렬 곱셈을 48번의 스칼라 곱으로 해내는 절차를 찾아 — Strassen 알고리즘 이후 56년 만의 개선 — 을 보고했고, Google 내부 스케줄링 휴리스틱을 개선해 전 세계 컴퓨팅 자원의 0.7%를 회수했다고 밝혔습니다. 이 아이디어를 오픈소스로 재현한 OpenEvolve·ShinkaEvolve·CodeEvolve 같은 프레임워크도 줄줄이 나왔습니다.

그런데 여기에 구조적인 비용 문제가 있습니다. 진화 탐색의 힘은 "많이 시도하기"에서 나오는데, AlphaEvolve 계열은 후보 하나를 만들 때마다 프런티어 LLM(Gemini급)을 한 번씩 호출합니다. 후보를 10배 더 보려면 LLM 호출도 10배입니다. 돈과 시간이 선형으로 폭발합니다. 더 뼈아픈 건, 많은 후보가 금방 비슷해진다는 점입니다. 거대 모델 열 번 호출해서 거의 똑같은 변형 열 개를 얻으면, 아홉 번은 버린 돈입니다.

핵심 전제 하나 — 진화 탐색에서는 "생성(LLM이 후보 만들기)"보다 "채점(후보 돌려 보기)"이 느릴 때가 많고, 그래서 생성 비용을 극단적으로 낮추면 같은 예산으로 탐색 폭을 훨씬 넓힐 수 있습니다. SwarmEvolve의 모든 설계는 이 한 문장에서 출발합니다. 생성을 싸게 만드는 데 집중한 것이죠.

그래서 질문이 이렇게 바뀝니다. "더 똑똑한 모델 하나로 후보를 신중하게 만들까?"가 아니라, "멍청해도 좋으니 후보를 아주 싸게, 아주 많이, 그리고 서로 다르게 만들 수는 없을까?" SwarmEvolve의 답이 바로 이겁니다.

3. SwarmEvolve의 세 가지 뒤집기

SwarmEvolve는 "거대 모델 한 대"를 "작은 모델의 떼(swarm)"로 바꿉니다. 기본 설정은 한 떼에 latent 에이전트 45마리이고, 이런 떼를 여러 개(논문은 라운드마다 10개 떼) 병렬로 돌립니다. 이게 가능하려면 에이전트 한 마리당 비용이 극단적으로 싸야 합니다. 그 비용을 깎는 트릭이 세 가지입니다.

트릭 ① — latent 공간에서 생각한다. 보통 LLM 에이전트는 생각을 토큰으로 "써 내려가며" 추론합니다. 토큰을 한 개씩 디코딩하는 이 과정이 느리고 비쌉니다. SwarmEvolve의 latent 에이전트는 이걸 건너뜁니다 — 중간 추론을 텍스트로 뱉지 않고 모델 내부의 hidden state(은닉 상태, 모델이 각 층에서 들고 있는 벡터) 수준에서 처리합니다. 디코딩을 안 하니 한 마리당 비용이 급감하고, 그래서 45마리를 한 배치(batch)로 묶어 GPU에 한꺼번에 태울 수 있습니다. 이 "토큰 없이 생각하기"는 Coconut 계열의 latent reasoning 연구 흐름에 닿아 있는데, SwarmEvolve는 그걸 한 마리의 추론이 아니라 떼의 병렬 탐색에 쓴 게 핵심입니다.

트릭 ② — KV 캐시를 직접 주고받는다. 에이전트끼리 협력하려면 보통 자연어로 "내 생각은 이래"라고 메시지를 주고받습니다. 그런데 latent 에이전트는 애초에 텍스트를 안 만들죠. 대신 자기 KV 캐시(어텐션이 참고하는, 지금까지 읽은 내용의 내부 표현)를 그대로 넘깁니다. 떼의 아이디어를 섞는 역할은 summarizer 에이전트가 맡는데, 이 녀석이 떼 전원의 KV 캐시를 합쳐서 받습니다. 진화 알고리즘에서 두 부모의 특성을 섞는 "교배(crossover)"가, 여기서는 텍스트 요약 없이 latent 공간에서 자연스럽게 일어나는 겁니다. 구현도 영리합니다. 같은 프로그램을 읽는 latent 에이전트들은 그 프로그램의 KV 캐시를 1벌만 두고 공유합니다 — vLLM의 paged FlashAttention 커널이 이걸 가능하게 해서, 45마리가 제각각 같은 내용을 중복 저장하는 메모리·연산 낭비를 없앱니다.

트릭 ③ — 다양성을 숫자로 관리한다. 후보를 싸게 많이 만들어도, 다 비슷하면 소용없습니다. SwarmEvolve는 novelty filter(참신성 필터)로 이걸 막습니다. 에이전트들의 hidden state 벡터 사이 거리를 직접 재서, 서로 가까운(즉 비슷한 생각을 하는) 후보는 쳐내고 멀리 떨어진(참신한) 것만 다음 단계로 보냅니다. "다양성"이라는 추상적인 목표를 벡터 거리라는 측정 가능한 신호로 바꾼 것이죠. 진화 탐색이 한 봉우리에 갇히지(수렴해 버리지) 않게 하는, 값싸고 기계적인 장치입니다.

4. 한 라운드가 돌아가는 모습

세 트릭이 한 라운드 안에서 어떻게 맞물리는지 흐름으로 보겠습니다.

중요한 건 이 흐름의 뼈대 자체는 AlphaEvolve와 똑같다는 점입니다. 부모를 뽑고, 변형하고, 채점하고, 좋은 걸 살려 다시 넣는 — 고전적인 진화 알고리즘입니다. SwarmEvolve가 바꾼 건 "변형" 단계의 단가와 병렬도뿐입니다. 거대 모델 한 번 호출 대신, 거의 공짜에 가까운 latent 에이전트 45마리를 돌리는 것으로요. 그 결과 같은 시간·같은 GPU에서 훨씬 많은 세대를 굴릴 수 있고, 진화 탐색에서 "많이 굴리기"는 거의 언제나 승리 공식입니다.

5. 숫자로 보기 — 작은 떼가 큰 모델을 이긴다

논문이 보고한 핵심 수치를 정리하면 이렇습니다(모두 저자 보고치이며 아직 독립 재현 전입니다).

가장 많이 인용된 결과는 "8B 떼 > 남의 32B"입니다. 같은 Qwen3 계열에서 4배 작은 모델을 떼로 묶었더니, 네 배 큰 모델을 한 대씩 쓴 경쟁 프레임워크를 이겼습니다. 이게 왜 중요한지 junior 관점에서 다시 짚으면 — 진화 탐색의 성능은 "모델 한 대의 IQ"가 아니라 "탐색의 폭×다양성"에서 나온다는 걸 숫자로 보여 주기 때문입니다. 생성을 싸게 만들어 폭을 늘리고(latent·배치), 중복을 걷어내 다양성을 지키면(novelty filter), 작은 모델로도 큰 모델을 넘어설 수 있습니다.

숫자를 읽을 때 주의 — 이건 전부 저자 보고치입니다. 공개 저장소는 글을 쓰는 시점에 스타 2개·라이선스 없음·README에 "code coming soon"만 적혀 있어, 제3자 재현이 아직 안 됐습니다. "8B가 32B를 이겼다"는 특정 벤치마크 묶음(수학·과학 계산 21문제) 안에서의 평균이고, 모든 도메인으로 일반화되는 주장은 아닙니다. 인상적이되, "검증 대기 중"으로 분류해 두는 게 맞습니다.

6. 실전 — 진화 루프를 코드로 감 잡기

SwarmEvolve 자체는 코드가 아직 안 풀렸으니, 여기서는 진화 탐색의 뼈대를 손에 익히는 걸 목표로 합니다. 아래는 "거대 모델 한 대" 버전의 최소 진화 루프입니다. SwarmEvolve가 어느 줄을 바꾸는지 주석으로 표시했습니다.

{{< highlight python >}} import random # evaluator: 후보 코드를 받아 점수(높을수록 좋음)를 돌려주는 채점 함수. # 진화 탐색에서 "느리고 비싼" 쪽은 보통 이 채점입니다. def evaluate(program: str) -> float: ... # 실제로 실행해 정확도/속도/오차 등을 점수로 환산 # 프로그램 보관소: (점수, 코드) 쌍이 세대를 거쳐 쌓이는 곳. database = [(evaluate(seed), seed) for seed in initial_programs] for round_i in range(NUM_ROUNDS): # ① 부모 선택 — 점수가 높을수록 뽑힐 확률을 높인다 parents = weighted_sample(database, k=PARENTS_PER_ROUND) children = [] for parent_score, parent_code in parents: # ② 변형(mutation) — 여기가 비용의 핵심. # 기존 방식: 프런티어 LLM을 1번 호출해 후보 1개 생성(비쌈). # SwarmEvolve: 이 한 줄이 "latent 에이전트 45마리 배치"로 바뀐다. # 텍스트를 안 뽑고 KV 캐시로 교배해 후보 여러 개를 싸게 생성. child_code = mutate_with_llm(parent_code, history=parent_score) children.append(child_code) # ③ 참신성 필터 — SwarmEvolve는 hidden state 벡터 거리로 중복 후보를 쳐낸다. # (아래는 개념만 보여 주는 단순 버전) children = drop_near_duplicates(children) # ④ 채점 후 보관소에 환원 — 점수 높은 후보만 다음 세대의 부모가 된다 for code in children: score = evaluate(code) database.append((score, code)) # 보관소가 너무 커지지 않게 상위만 유지(다양성 보존 로직을 함께 두기도 함) database = keep_top_and_diverse(database, size=POOL_SIZE) best = max(database, key=lambda sc: sc[0]) # 지금까지 가장 좋은 해 {{< /highlight >}}

이 스켈레톤에서 SwarmEvolve가 건드리는 건 사실상 ② 변형과 ③ 필터 두 줄입니다. 나머지 진화 뼈대(부모 선택·채점·환원·풀 관리)는 그대로 둡니다. 그래서 이 글의 교훈이 재사용 가능한 겁니다. 여러분이 이미 돌리는 에이전트 루프가 있다면, "생성 단계를 더 싸게, 더 병렬로, 중복 없이" 만들 여지가 있는지 같은 눈으로 보면 됩니다.

직접 손에 익히고 싶다면, 코드가 공개된 OpenEvolve 같은 오픈소스 진화 프레임워크로 작은 문제(예: 간단한 정렬·수치 최적화) 하나를 돌려 보는 걸 권합니다. 세대가 지날수록 점수가 오르는 걸 눈으로 보고 나면, SwarmEvolve가 "왜 하필 생성 비용을 깎았는가"가 몸으로 이해됩니다.

7. 흔한 오해 · 남은 한계

  • "작은 모델이 큰 모델보다 똑똑하다"는 뜻이 아닙니다. 같은 모델 한 대끼리 붙이면 32B가 8B보다 낫습니다. SwarmEvolve의 결과는 "탐색 시스템 전체"를 비교한 것입니다 — 8B를 떼로 영리하게 굴린 시스템이, 32B를 단순하게 굴린 시스템을 이긴 것이죠. 모델이 아니라 설계가 이겼습니다.
  • 아무 문제에나 통하지 않습니다. 진화 탐색의 대전제는 "값싸고 자동화된 채점 함수가 있다"입니다. 점수를 기계적으로 매길 수 있는 수학·알고리즘·수치 최적화에 강하고, "좋음"의 기준이 주관적이거나 채점이 느린·비싼 문제에는 잘 안 맞습니다. 적용 전에 "내 문제에 빠른 evaluator가 있나?"부터 물어야 합니다.
  • latent 협력은 공짜 점심이 아닙니다. KV 캐시를 주고받는 다중 에이전트 방식은 "중간 생각이 텍스트로 안 남는다"는 특성 때문에 관측·디버깅이 어렵습니다. 실제로 "relay된 KV 캐시의 무결성"을 다룬 별도 연구들이 나올 만큼, latent 통신은 신뢰·검증 측면에서 아직 연구 중인 영역입니다.
  • 지금은 한 가지 모델 계열만 씁니다. 저자들도 한계로 적었듯, 현재 떼의 에이전트는 모두 같은 모델 패밀리(Qwen3)에서 돕니다. 서로 다른 모델을 섞어 더 다양한 "유전자 풀"을 만드는 건 앞으로의 과제입니다.
  • 재현은 아직입니다. 앞서 적었듯 코드가 완전히 풀리지 않았습니다. 지금 이 글을 읽는 목적은 "당장 갖다 쓰기"가 아니라 설계 패턴을 배우기입니다.

그럼에도 이 주제를 지금 알아 둘 이유는 분명합니다. "에이전트를 크게 하나 vs 작게 여럿"이라는 선택은 진화 탐색을 넘어 점점 더 많은 곳에서 등장합니다. 멀티 에이전트 오케스트레이션에서 리드 모델과 값싼 워커를 나누던 발상, latent로 생각하는 에이전트에서 본 "토큰 없이 추론하기", KV 캐시 직접 통신에서 본 "텍스트 대신 내부 표현으로 대화하기" — SwarmEvolve는 이 조각들을 진화 탐색이라는 구체적인 과제 위에서 하나로 합쳐 "작게·많이·다르게"가 통한다는 걸 보여 준 사례입니다. 다음에 "더 큰 모델을 붙일까?"라는 질문이 떠오르면, "같은 돈으로 더 많이·다양하게 돌릴 방법은 없나?"를 먼저 떠올려 보세요.

8. 마무리 (TL;DR)

  • 11월 둘째 주 arXiv에 올라온 SwarmEvolve(arXiv:2611.08483)는 진화적 코딩 에이전트의 비용 구조를 뒤집습니다 — 거대 모델 한 대 대신 작은 latent 에이전트 45마리의 떼를 돌립니다.
  • 세 가지 트릭: ① latent 공간에서 생각(토큰 디코딩 생략 → 생성이 쌈), ② KV 캐시를 직접 주고받기(summarizer가 떼의 캐시를 합쳐 latent에서 교배), ③ novelty filter(hidden state 거리로 중복 제거 → 다양성 유지).
  • 핵심 결과: Qwen3 8B 떼의 평균 점수가 경쟁 프레임워크의 Qwen3 32B-FP8보다 높고, 남들이 60분 걸리는 점수에 median 3~8분에 도달. 일부 문제에선 AlphaEvolve가 프런티어 LLM으로 찾은 해도 개선(모두 저자 보고치).
  • 교훈: 진화 탐색의 성능은 "모델 한 대의 IQ"가 아니라 탐색의 폭 × 다양성에서 나온다. 생성을 싸게 만들면 폭이, 중복을 걷어내면 다양성이 는다.
  • 전제와 한계: 빠른 자동 채점 함수가 있는 문제(수학·알고리즘·수치 최적화)에 강하고, latent 협력은 관측·디버깅이 어렵습니다. 아직 한 모델 계열만 쓰고, 코드 미공개로 독립 재현 전입니다.
  • 재사용 포인트: "에이전트를 크게 하나 vs 작게 여럿"의 선택은 어디서든 옵니다. 내 루프의 생성 단계를 더 싸게·병렬로·중복 없이 만들 여지가 있는지 같은 눈으로 보세요.
