도입 — 에이전트는 잘 만드는데, 왜 전달이 안 될까

팀 동료가 쓸 만한 에이전트를 하나 만들었다고 해 봅시다. GitHub 이슈를 정리해 주는 에이전트인데, 옆자리 동료에게 건네주려는 순간 익숙한 체크리스트가 시작됩니다. "저장소 clone 받고, Python 3.11 이상 맞추고, venv 만들고, 의존성 설치하고, .env 만들고…" 에이전트의 본질은 시스템 프롬프트 몇 줄과 도구 목록인데, 전달되는 건 프레임워크와 의존성 더미입니다. 받아 가는 쪽 입장에서는 앱 하나 쓰려고 빌드 환경을 통째로 복제하는 셈이죠.

어디서 많이 본 문제 아닌가요? 10여 년 전 "제 컴퓨터에서는 되는데요"를 끝낸 해법이 컨테이너였습니다. 그리고 이번 주, Docker가 같은 해법을 에이전트에 적용한 docker-agent로 Hacker News 프런트페이지에 이틀 연속 올랐습니다(10월 7일 등판 후 집계 기준 약 300포인트, 댓글 130개 이상). Docker Engineering이 만든 오픈소스(Apache 2.0) 에이전트 빌더 겸 런타임으로, docker CLI 플러그인이라 docker agent run으로 실행합니다. Docker Desktop 4.63 이상에는 아예 기본 탑재돼 있어서, Docker를 쓰는 개발자라면 설치 과정조차 없습니다.

핵심 아이디어는 한 문장입니다. 에이전트를 코드가 아니라 아티팩트(artifact)로 취급한다. YAML 한 장으로 정의하고, 컨테이너 이미지처럼 OCI 레지스트리에 push하고, 다른 머신에서 pull해서 그대로 돌립니다. 이 글에서는 이 관점 전환이 에이전트 엔지니어링에서 무엇을 바꾸는지 — 선언적 정의, 멀티에이전트 배선 두 가지 패턴, 그리고 배포 — 를 하나씩 뜯어봅니다.

배경 — 에이전트의 최소 해부도와 cagent 계보

따라오는 데 필요한 최소 지식부터 정리합니다. 에이전트(agent)는 결국 루프입니다. 모델이 응답을 생성하다가 도구 호출(tool call)을 내놓으면, 런타임이 그 도구를 실행해 결과를 돌려주고, 모델이 결과를 반영해 다음 응답을 만듭니다. 이 반복이 끝날 때까지 도는 루프가 에이전트의 전부입니다.

그래서 에이전트 하나를 규정하는 요소는 생각보다 적습니다. 어떤 모델을 쓰는지, 어떤 지시(instruction)를 받았는지, 어떤 도구를 쥐고 있는지. 이 세 가지면 끝입니다. 도구 쪽은 MCP(Model Context Protocol)라는 표준이 자리 잡으면서 "도구 서버를 연결한다"는 한 줄로 수렴했고요. 그런데도 많은 프레임워크가 이 세 가지를 Python 코드 안에 흩어 놓습니다. 설정에 가까운 정보가 코드에 묶여 있으니, 공유하려면 코드 실행 환경이 통째로 따라가야 하는 겁니다.

Docker는 이 지점을 2025년 9월 cagent라는 실험 프로젝트로 건드렸습니다. "에이전트 = 모델 + instruction + 도구라면, 그건 코드가 아니라 선언적 설정이어야 한다"는 주장이었죠. 그 cagent가 다듬어져 지금의 docker-agent가 됐습니다. 현재 버전 기준으로 OpenAI, Anthropic, Gemini, AWS Bedrock, Mistral, xAI 등 주요 프로바이더를 지원하고, Docker Model Runner를 통하면 로컬 모델도 돌릴 수 있습니다. 릴리스 주기도 빨라서 글 쓰는 시점의 최신 버전은 v1.150.0(2026-10-09)입니다.

선언적 정의 — YAML 한 장이 에이전트가 되기까지

가장 작은 에이전트는 이렇게 생겼습니다. 파일 하나, 네 줄이 전부입니다.

{{< highlight yaml >}} # agent.yaml — 최소 구성 agents: root: # 진입점 에이전트는 root라는 이름을 씁니다 model: openai/gpt-5 description: A helpful assistant instruction: You are a helpful assistant. {{< /highlight >}} {{< highlight bash >}} docker agent run agent.yaml {{< /highlight >}}

여기에 도구를 붙이고 싶으면 toolsets를 추가합니다. 내장 도구는 type 한 줄로 켜고(filesystem, shell, think, todo, memory 등), 외부 도구는 MCP 서버를 연결합니다. MCP는 세 가지 방식 — Docker 컨테이너로 돌리는 docker: 참조(MCP Gateway 경유), 로컬 프로세스(stdio), 원격 서버(Streamable HTTP/SSE) — 를 모두 지원합니다.

{{< highlight yaml >}} agents: root: model: anthropic/claude-sonnet-4-5 description: 웹 검색이 되는 리서치 조수 instruction: | 질문을 받으면 웹을 검색해 근거를 모은 뒤 답하세요. toolsets: - type: think # 내장 도구: 생각 정리용 - type: mcp ref: docker:duckduckgo # MCP 서버를 컨테이너로 실행 {{< /highlight >}}

설정 파일의 전체 뼈대는 10개 안팎의 섹션으로 구성됩니다. models에 이름 붙은 모델 정의(온도, 최대 토큰 등 파라미터 포함), agents에 에이전트들, mcps에 재사용할 MCP 서버 정의, permissions에 도구 허용·차단 규칙, rag에 검색 소스를 적는 식입니다. 모델은 openai/gpt-5처럼 인라인으로 쓸 수도 있고, models 섹션에 정의해 두고 이름으로 참조할 수도 있습니다.

이 구조의 효과는 Dockerfile을 떠올리면 이해가 빠릅니다. Dockerfile이 "이 이미지가 무엇으로 구성되는지"만 선언하고 빌드·실행은 Docker 엔진에 맡기듯, agent.yaml은 "이 에이전트가 무엇인지"만 선언하고 루프·도구 실행·승인 처리 같은 공통 로직은 런타임에 맡깁니다. 버전 관리는 git diff로 되고, 코드 리뷰도 설정 리뷰가 됩니다. 참고로 부작용이 있는 도구(shell 명령, 파일 쓰기)는 기본값으로 실행 전에 사용자 승인을 요구합니다. --yolo 플래그로 전부 자동 승인할 수 있지만, 이름이 경고하는 그대로의 플래그입니다.

로컬 모델도 같은 문법: provider: dmr로 Docker Model Runner를 지정하면 ai/qwen3 같은 로컬 모델을 API 비용 없이 쓸 수 있습니다. "간단한 역할은 로컬 모델, 핵심 추론은 클라우드 모델"처럼 역할별로 섞는 구성이 YAML 수준에서 됩니다.

멀티에이전트 — delegation과 handoff, 두 가지 배선

docker-agent가 단순 래퍼(wrapper)와 갈라지는 지점이 멀티에이전트 지원입니다. 복잡한 작업은 만능 에이전트 하나보다 역할이 좁은 에이전트 여럿이 낫다는 건 이제 업계의 상식에 가까운데, 문제는 "여럿을 어떻게 배선하느냐"입니다. docker-agent는 두 가지 패턴을 제공하고, 이 구분이 다른 프레임워크를 쓸 때도 그대로 통하는 일반 개념이라 자세히 볼 가치가 있습니다.

패턴 1: delegation(위임) — 부모 에이전트가 sub_agents에 등록된 자식에게 작업을 떼어 줍니다. 부모는 transfer_task라는 내장 도구로 "이 작업을 이런 결과물로 해 와라"를 전달하고, 자식은 별도의 서브세션에서 깨끗한 작업 설명만 받아 자기 루프를 돈 뒤 결과만 돌려줍니다. 부모는 그동안 기다렸다가 결과를 받아 종합하죠. 계층형(부모→자식→부모) 구조라서 "코디네이터가 전문가에게 일을 시키고 결과를 모은다"는 그림에 맞습니다.

패턴 2: handoffs(인계) — 에이전트가 handoff 도구로 대화 자체를 통째로 다음 에이전트에게 넘깁니다. 서브세션이 생기지 않고, 넘겨받은 에이전트가 전체 대화 히스토리를 그대로 보면서 활성 에이전트가 됩니다. A→B→C→A처럼 순환하는 그래프도 만들 수 있어서, 파이프라인 처리나 상담원 라우팅(접수→전문가→접수) 같은 흐름에 맞습니다.

두 패턴의 결정적 차이는 컨텍스트가 어떻게 흐르느냐입니다. delegation은 자식에게 깨끗한 작업 설명만 주니까 자식의 컨텍스트가 가볍고, 부모가 결과를 통제합니다. handoff는 다음 에이전트가 대화 전체를 보니까 맥락 손실이 없는 대신, 넘길수록 컨텍스트가 무거워집니다. "전문가에게 시킬 일"이면 delegation, "같은 대화를 이어받아 처리할 일"이면 handoff — 이 감각만 있어도 멀티에이전트 설계 논의를 따라갈 수 있습니다.

실무에서 바로 쓸 만한 디테일도 몇 가지 있습니다.

  • force_handoff — handoff는 모델이 도구를 호출해야 일어나는데, 모델이 깜빡하면 파이프라인이 끊깁니다. force_handoff: summarizer를 선언하면 모델의 선택과 무관하게 런타임이 응답 완료 시점에 강제로 다음 에이전트로 라우팅합니다. 순환(A→B→A)은 설정 로드 시점에 거부됩니다.
  • background_agents — transfer_task는 순차 실행이라 부모가 기다립니다. 독립적인 작업 여러 개를 동시에 돌리려면 background_agents 도구로 작업을 비동기 디스패치하고, 작업 ID로 조회·대기·취소합니다.
  • harness 서브에이전트 — 자식 자리에 모델 대신 외부 코딩 CLI(Claude Code, Codex 등)를 꽂을 수 있습니다. model: 대신 harness: {type: claude-code}를 쓰면, 오케스트레이션은 docker-agent가 하고 코딩 루프는 해당 CLI가 돕니다.

배포 — 에이전트를 OCI 아티팩트로 push·pull하기

여기가 docker-agent의 가장 Docker다운 부분입니다. 만든 에이전트를 OCI(Open Container Initiative) 아티팩트로 패키징해서, 컨테이너 이미지가 다니는 길(Docker Hub, GitHub Container Registry 등 아무 OCI 호환 레지스트리)로 유통합니다.

{{< highlight bash >}} # 에이전트를 레지스트리에 올리기 docker agent share push ./agent.yaml docker.io/myorg/review-agent:v1 # 다른 머신에서 — pull 없이 바로 실행도 됩니다 docker agent run myorg/review-agent:v1 {{< /highlight >}}

받는 쪽에 필요한 건 docker-agent(Docker Desktop이면 이미 설치됨)와 API 키뿐입니다. 저장소 clone도, 의존성 설치도 없습니다. 도입부의 "에이전트 전달 체크리스트"가 명령 한 줄로 줄어드는 거죠.

더 재미있는 건 레지스트리의 에이전트를 남의 팀 구성원으로 바로 참조할 수 있다는 점입니다. sub_agents 목록에 로컬 에이전트 이름 대신 레지스트리 참조를 적으면, 실행 시 자동으로 받아와 자식 에이전트로 씁니다.

{{< highlight yaml >}} agents: root: model: openai/gpt-5 description: 로컬·외부 에이전트를 섞어 쓰는 코디네이터 instruction: 작업에 맞는 서브에이전트에게 위임하세요. sub_agents: - local_helper # 같은 파일에 정의된 로컬 에이전트 - myorg/agent:tag # 레지스트리에서 자동 pull, 이름은 "agent" - reviewer:docker.io/myorg/review-agent@sha256:44117e… # digest 고정 {{< /highlight >}}

라이브러리를 패키지 매니저로 가져오듯 에이전트를 조립하는 그림입니다. 다만 세 번째 줄의 @sha256:…에 주목하세요. 태그 참조(myorg/agent:tag)는 매 실행마다 레지스트리에 digest를 조회합니다. 호출되지 않는 서브에이전트라도 시작 시점에 참조당 네트워크 왕복이 한 번씩 붙고, 레지스트리가 느리면 시작이 함께 느려집니다. digest로 고정(pinning)하면 로컬 캐시에서 바로 읽어 시작이 빠르고, 어느 머신에서든 완전히 같은 팀이 재현됩니다 — 컨테이너에서 latest 태그 대신 digest를 고정하라는 조언과 정확히 같은 이유입니다.

공급망 걱정도 챙겨 뒀습니다. share push --key로 서명하면 서명·메타데이터가 DSSE 봉투에 담긴 in-toto Statement로 매니페스트 주석에 기록되고, share pull --key가 "이 YAML이 그 키 주인이 그 주소로 올린 그대로인지"를 검증한 뒤에만 받아들입니다. cosign 등 기존 공급망 도구가 쓰는 포맷 그대로라 docker-agent 없이도 읽을 수 있습니다. 단, 서명이 덮는 범위는 에이전트 YAML과 발행 주소까지입니다 — 매니페스트의 나머지 주석(작성자, 라이선스 표기 등)은 인증 대상이 아니니 거기에 정책을 걸면 안 됩니다.

실전 — 코드 리뷰 미니팀을 직접 만들어 보기

배운 걸 전부 모아 "리뷰어 + 테스터를 거느린 개발팀"을 만들어 봅시다. 역할마다 모델과 도구를 다르게 주는 게 포인트입니다.

{{< highlight yaml >}} # dev-team.yaml models: smart: provider: anthropic model: claude-sonnet-4-5 max_tokens: 64000 cheap: provider: openai model: gpt-5-mini temperature: 0.2 # 분석 역할이라 낮게 agents: root: model: smart description: 개발을 지휘하는 테크 리드 instruction: | 요청을 분석해 알맞은 전문가에게 위임하세요. 결과를 검토한 뒤 사용자에게 종합해 답하세요. sub_agents: [developer, reviewer] toolsets: - type: think # 위임 판단을 정리할 생각 도구 developer: model: smart description: 코드를 작성하는 개발자 instruction: 클린 코드를 작성하고 모범 사례를 따르세요. toolsets: - type: filesystem - type: shell - type: todo shared: true # 팀 전체가 같은 todo를 공유 reviewer: model: cheap # 리뷰는 저렴한 모델로 충분 description: 코드 품질·보안 리뷰어 instruction: 품질, 보안, 유지보수성 관점에서 실행 가능한 피드백을 주세요. toolsets: - type: filesystem # 읽기만 — shell은 주지 않습니다 - type: todo shared: true {{< /highlight >}} {{< highlight bash >}} # 실행 — 부작용 있는 도구는 승인 프롬프트가 뜹니다 docker agent run dev-team.yaml # 다중 에이전트 설정에서 특정 에이전트만 골라 실행 docker agent run dev-team.yaml -a reviewer # 완성됐으면 팀에 공유 docker agent share push ./dev-team.yaml docker.io/myorg/dev-team:v1 {{< /highlight >}}

동료는 docker agent run myorg/dev-team:v1 한 줄로 같은 팀을 띄웁니다. 코디네이터의 위임 판단은 각 에이전트의 description을 보고 이뤄지므로, description을 "무슨 일을 맡길 수 있는지"가 드러나게 쓰는 것이 멀티에이전트 품질에 직접적인 영향을 줍니다.

흔한 실수 · 팁

  • 외부 서브에이전트를 태그로 참조한 채 방치 — 매 실행마다 참조당 레지스트리 왕복이 생기고, 태그가 가리키는 내용이 바뀌면 팀 동작도 조용히 바뀝니다. 런타임도 태그 참조에 시작 경고를 띄웁니다. @sha256:…으로 고정하세요. digest는 Docker Hub 태그 옆이나 docker buildx imagetools inspect로 확인합니다.
  • 습관성 --yolo — 승인 프롬프트가 귀찮다고 전부 자동 승인하면, shell 도구를 쥔 에이전트의 모든 명령이 무확인으로 나갑니다. 특히 transfer_task는 원래부터 자동 승인(위임이 막히지 않도록)이라, 부모에게만 승인을 걸어도 자식이 위험한 도구를 쥐고 있으면 소용없습니다. 애초에 자식에게 필요한 최소 도구만 주는 게 정답입니다. 위 예제에서 reviewer에게 shell을 주지 않은 이유입니다.
  • 모든 에이전트에 think·memory 도구 끼워 넣기 — think 도구는 네이티브 추론이 없는 모델의 코디네이터용 보조입니다. 추론 내장 모델에는 군더더기 컨텍스트만 늘립니다. 도구 하나하나가 시스템 프롬프트에 설명으로 추가된다는 걸 기억하세요.
  • handoff 파이프라인이 가끔 끊기는 문제 — 모델이 handoff 호출을 "깜빡"하는 건 드물지 않습니다. 순서가 고정된 파이프라인이라면 모델의 선의에 기대지 말고 force_handoff로 런타임에 강제하세요.
  • 서명 검증 없이 외부 에이전트 실행 — 레지스트리의 에이전트 YAML에는 instruction과 도구 구성이 그대로 들어 있습니다. 출처가 불분명한 에이전트를 받아 실행하는 건 모르는 스크립트를 curl | sh 하는 것과 같은 급의 행동입니다. 팀 내 유통에는 서명을 걸고, 처음 보는 에이전트는 YAML을 열어 도구 목록부터 확인하세요.
  • 설정 크기 한도 — HTTP(S)나 OCI로 불러오는 설정은 압축 해제 기준 32MiB로 제한됩니다. instruction에 문서를 통째로 붙여 넣는 식의 설계라면(그 자체로 재고할 신호이기도 합니다) RAG 섹션으로 옮기는 편이 낫습니다.
프레임워크 선택 관점의 한마디: docker-agent의 선언적 접근은 "에이전트 = 모델 + instruction + 도구 + 팀 배선"으로 환원되는 에이전트에 강합니다. 반대로 루프 자체를 커스텀해야 하는 경우 — 특수한 종료 조건, 자체 검증 단계, 비표준 상태 관리 — 라면 코드 기반 프레임워크(또는 직접 구현)가 여전히 맞는 도구입니다. YAML은 "무엇을"의 언어이지 "어떻게"의 언어가 아니니까요.

마무리 (TL;DR)

  • Docker Engineering의 오픈소스 에이전트 런타임 docker-agent가 이번 주 HN 프런트페이지에 이틀 연속 올랐습니다. docker CLI 플러그인이고, Docker Desktop 4.63+에 기본 탑재돼 있습니다.
  • 핵심은 관점 전환: 에이전트 = 코드가 아니라 아티팩트. 모델·instruction·도구·팀 구조를 YAML 한 장에 선언하고, 루프·도구 실행·승인은 런타임이 전담합니다.
  • 멀티에이전트 배선은 두 패턴 — delegation(sub_agents + transfer_task, 서브세션에 깨끗한 작업만 위임)과 handoffs(대화 전체를 넘기며 활성 에이전트 교대). 순서 고정이 필요하면 force_handoff, 병렬은 background_agents.
  • OCI 레지스트리로 push·pull합니다. 레지스트리 에이전트를 sub_agents로 바로 조립할 수 있고, 태그 대신 digest 고정이 시작 속도와 재현성을 모두 가져갑니다. 서명(DSSE/in-toto)으로 변조·출처 검증도 됩니다.
  • 안전 수칙: 자식 에이전트에 최소 도구만, --yolo는 신중히, 출처 불명 에이전트는 YAML부터 열어 볼 것.
