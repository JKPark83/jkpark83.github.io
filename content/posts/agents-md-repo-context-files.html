새 코딩 에이전트를 열 때마다 같은 말을 반복하고 있지 않나요? “테스트는 pnpm test로 돌려”, “src/legacy는 건드리지 마”, “커밋 메시지는 이런 형식으로”… 대화창을 닫으면 이 지식은 매번 증발합니다.

1. 왜 지금 AGENTS.md가 화제인가

코딩 에이전트(coding agent)는 저장소를 처음 보는 능력 좋은 신입과 비슷합니다. 코드는 잘 읽지만, 이 프로젝트만의 “집안 규칙”은 모릅니다. 테스트를 npm test로 돌리는지 pytest로 돌리는지, 포매터가 있는지, 절대 만지면 안 되는 생성 파일이 어디인지 — 이런 건 코드에 안 적혀 있죠. 그래서 에이전트는 추측하고, 종종 틀립니다.

AGENTS.md는 이 문제를 겨냥한 파일입니다. 저장소 루트에 두는 Markdown 한 장에 프로젝트의 규칙을 적어 두면, Codex·Cursor·GitHub Copilot·Aider·Gemini CLI 같은 대부분의 코딩 에이전트가 작업을 시작할 때 이 파일을 자동으로 읽어 컨텍스트에 넣습니다. 원래 OpenAI가 2025년 8월에 공개한 단순한 규약인데, 지금은 6만 개가 넘는 오픈소스 저장소가 쓰고 있습니다.

그런데 왜 이번 주 다시 talking point가 됐을까요? 두 갈래입니다. 하나는 거버넌스 — AGENTS.md는 2025년 말 Linux Foundation 산하 Agentic AI Foundation(AAIF)로 넘어가 MCP·goose와 나란히 표준으로 관리되는데, 2026년 7월 AAIF가 첫 앰배서더 코호트(41개국 138명)와 ‘Agentic AI Momentum Report’를 발표하며 다시 주목받았습니다. 다른 하나가 더 흥미롭습니다 — GitHub가 2,500여 개 저장소를 분석한 글과 ETH Zürich의 ‘AGENTS.md가 정말 도움이 되나’ 연구가 나란히 퍼지면서, “다들 쓰라고 하는데, 진짜 도움이 되긴 하나?”라는 논쟁에 불이 붙었죠. 결론부터 말하면 답은 “쓰기 나름”입니다. 이 글에서 그 “나름”을 구체적으로 풀어 봅니다.

한 줄 요약. AGENTS.md는 코딩 에이전트에게 저장소의 집안 규칙(빌드·테스트 명령, 코드 스타일, 하지 말 것)을 알려 주는 표준 지시 파일입니다. 잘 쓰면 에이전트가 헤매지 않고, 잘못 쓰면 비용만 늘고 오히려 방해가 됩니다.

2. 배경 — 파편화된 지시 파일의 시대

AGENTS.md가 왜 필요했는지는 그 이전을 보면 바로 이해됩니다. 코딩 에이전트마다 “나한테 규칙을 주려면 이 파일에 써”라고 요구하는 파일 이름이 제각각이었습니다.

  • Claude Code → CLAUDE.md
  • Cursor → .cursorrules
  • GitHub Copilot → .github/copilot-instructions.md
  • Windsurf → .windsurfrules …

같은 팀이 Cursor와 Copilot을 섞어 쓰면, 똑같은 규칙을 파일 서너 개에 복붙해 두고 하나 고칠 때마다 나머지도 손봐야 했습니다. 전형적인 파편화(fragmentation) 문제죠. AGENTS.md의 발상은 단순합니다 — 파일 하나, 모든 에이전트. 도구 이름이 아니라 역할로 파일을 정의하니, 새 에이전트가 나와도 같은 파일을 읽으면 됩니다.

핵심은 특별할 게 없다는 점입니다. AGENTS.md는 그냥 Markdown이고, 필수 항목도, 정해진 스키마도 없습니다. 사람이 읽는 README가 “사람을 위한 안내서”라면, AGENTS.md는 “에이전트를 위한 안내서”입니다. README에는 홍보 문구와 배지가 들어가지만, AGENTS.md에는 에이전트가 실제로 작업할 때 필요한 실행 가능한 정보만 담습니다.

README와 뭐가 다른가요? 역할이 다릅니다. README는 “이 프로젝트가 뭐고 왜 좋은지”를 사람에게 팔고, AGENTS.md는 “빌드는 이렇게, 테스트는 이렇게, 이건 건드리지 마”를 에이전트에게 지시합니다. 둘을 합치지 마세요. 에이전트에게 배지와 스크린샷은 토큰 낭비일 뿐입니다.

3. 어떻게 발견되고, 누가 이기는가

여기서부터가 실무 지식입니다. 큰 저장소, 특히 모노레포(monorepo)에서는 규칙이 폴더마다 다릅니다. 프런트엔드는 Prettier를 쓰고 백엔드는 gofmt를 쓰는데, 루트에 규칙 하나만 두면 서로 안 맞죠. 그래서 AGENTS.md는 여러 개를 중첩(nested)해서 둘 수 있습니다.

규칙은 딱 하나만 기억하면 됩니다 — 작업 중인 파일에서 가장 가까운(위쪽으로 가장 먼저 만나는) AGENTS.md가 이깁니다. 루트의 파일은 저장소 전체에 적용되고, 하위 폴더의 파일이 그 아래 영역에서 루트를 덮어씁니다. 실제로 OpenAI 자기 저장소에도 AGENTS.md가 88개나 들어 있습니다.

정리하면 우선순위는 이렇습니다.

  1. 사용자의 직접 지시(프롬프트) — 가장 셉니다. “이번만 lint 건너뛰어”가 파일을 이깁니다.
  2. 가장 가까운 AGENTS.md — 수정 중인 파일에서 위로 올라가며 처음 만나는 파일.
  3. 상위 폴더 / 루트의 AGENTS.md — 더 가까운 파일이 말하지 않은 부분을 채웁니다.
주의: 도구마다 중첩 지원이 아직 완전하지 않습니다. 예를 들어 하위 폴더의 AGENTS.md를 자동으로 찾아 읽는 기능은 도구·버전에 따라 켜야 하거나 아직 개발 중일 수 있습니다. 모노레포라면 “내 에이전트가 하위 폴더 파일을 정말 읽는가”를 한 번 확인하고 쓰세요. 안 읽는다면 루트 파일에 폴더별 섹션으로 나눠 적는 게 안전합니다.

4. 좋은 AGENTS.md의 해부 — 무엇을 넣나

정해진 스키마는 없지만, 수천 개 저장소가 공통으로 쓰는 사실상의 표준 섹션이 있습니다. 핵심 원칙은 하나 — “코드를 봐도 알 수 없는 것”만 적는다. 언어의 기본값이나 코드에 이미 드러난 것은 토큰 낭비입니다.

말보다 예시가 빠릅니다. 아래는 작지만 쓸모 있는 AGENTS.md의 모습입니다.

{{< highlight markdown >}} # AGENTS.md ## 프로젝트 TypeScript(5.x) + React 18 웹 앱. 패키지 매니저는 pnpm. ## 빌드 · 테스트 - 설치: `pnpm install` - 개발 서버: `pnpm dev` - 전체 테스트: `pnpm test` - 단일 파일 테스트: `pnpm test src/cart/cart.test.ts` - 커밋 전 반드시: `pnpm lint && pnpm typecheck` # 둘 다 통과해야 함 ## 코드 스타일 - 포매팅은 Prettier가 담당 — 수동으로 정렬하지 말 것. - 컴포넌트는 함수형만. 클래스 컴포넌트 새로 만들지 말 것. - import는 절대경로(`@/...`) 사용. ## 하지 말 것 - `src/generated/`는 코드젠 결과물 — 절대 직접 수정하지 말 것. - `.env`, 비밀키를 코드나 커밋에 넣지 말 것. ## 커밋 - Conventional Commits 형식: `feat:`, `fix:`, `chore:` … - PR은 `main`으로, 테스트가 초록불일 때만. {{< /highlight >}}

보다시피 40줄도 안 됩니다. 그런데 이 짧은 파일이 에이전트의 흔한 실수 — 손으로 코드 정렬하기, 생성 파일 덮어쓰기, 테스트 명령 잘못 추측하기 — 를 대부분 막아 줍니다. “진짜 명령어 한 줄이 설명 세 문단을 이긴다”는 게 GitHub이 2,500개 저장소에서 뽑은 교훈입니다.

5. 반전 — 연구가 밝힌 '독이 되는' 경우

여기서 이번 주 논쟁의 핵심입니다. AGENTS.md는 “있으면 무조건 좋다”가 아닙니다. 오히려 잘못 쓰면 성능을 떨어뜨립니다.

ETH Zürich 연구팀은 ‘Evaluating AGENTS.md’(arXiv:2602.11988)에서 이걸 정면으로 측정했습니다. 실제로 개발자가 손으로 쓴 컨텍스트 파일이 들어 있는 저장소 12곳에서 약 5,700개 PR을 추려 138개 작업 벤치마크(AGENTBENCH)를 만들고, 파일이 있을 때 / 없을 때 에이전트의 작업 성공률을 비교했죠. 결과는 뜻밖이었습니다.

  • 컨텍스트 파일을 넣어도 작업 성공률은 통계적으로 나아지지 않았다.
  • 대신 추론 비용(inference cost)은 평균 20% 넘게 늘었다. 매 호출마다 그 토큰을 다시 내니까요.
  • 이 경향은 여러 LLM·여러 에이전트에서 공통으로 나타났고, 사람이 쓴 파일과 LLM이 자동 생성한 파일 양쪽 모두에서 관찰됐다.
  • 특히 LLM이 자동 생성한 파일은 살짝 마이너스였고, 사람이 쓴 파일은 살짝 플러스에 그쳤다.

GitHub의 2,500개 저장소 분석도 같은 방향을 가리킵니다 — 파일이 150줄을 넘어가면 효용은 정체되고, 추론 비용만 20~23% 더 붙습니다. 성능은 그대로인데 청구서만 커지는 거죠.

왜 이런 일이 벌어질까요? 두 가지 이유입니다. 첫째, 컨텍스트가 길어지면 정작 중요한 지시가 묻힙니다(context rot). 둘째, 파일에 “이것도 확인해, 저것도 지켜”라는 불필요한 요구가 쌓이면 작업 자체가 더 어려워집니다. ETH 연구팀의 조언이 명쾌합니다 — “사람이 쓴 컨텍스트 파일은 최소한의 요구만 적어야 한다.”

“AGENTS.md 만들어 줘”의 함정. 에이전트에게 시켜서 자동 생성한 AGENTS.md가 특히 위험합니다. 코드를 훑어 그럴듯한 문단을 잔뜩 뽑아내지만, 대부분 코드만 봐도 아는 내용이라 토큰만 먹고 성공률엔 마이너스입니다. 자동 생성은 초안으로만 쓰고, 반드시 사람이 잘라내 “진짜 필요한 것”만 남기세요.

그럼 쓰지 말라는 건가요? 아닙니다. 연구가 반대하는 건 길고 부정확한 파일이지 AGENTS.md 자체가 아닙니다. 실제로 빌드·테스트 명령처럼 “코드로는 알 수 없는데 틀리면 작업이 통째로 막히는” 정보는, 짧게라도 있으면 에이전트가 헛수고와 재시도를 크게 줄입니다. 요점은 양이 아니라 밀도입니다.

6. 실전 — 5분 만에 쓸모 있는 파일 만들기

연구 결과를 실천으로 옮기면 레시피는 단순합니다. 비어 있는 파일에서 시작해, 에이전트가 실제로 틀린 것만 채워 넣으세요.

  1. 루트에 AGENTS.md를 만든다. 처음엔 “빌드·테스트 명령”과 “하지 말 것” 두 섹션이면 충분합니다.
  2. 명령어는 추측 없이 복사한다. package.json/Makefile에서 실제 스크립트를 그대로 옮깁니다.
  3. 에이전트를 한 번 굴려 본다. 그리고 틀린 것만 규칙으로 추가합니다. “손으로 정렬했네 → ‘Prettier가 담당’ 추가”, “생성 파일 고쳤네 → ‘generated/ 금지’ 추가”. 관찰 → 교정의 반복입니다.
  4. 커밋해서 팀과 공유한다. AGENTS.md는 저장소에 들어가므로, 팀 전체와 CI의 에이전트가 같은 규칙을 씁니다.

모노레포라면 루트에는 공통 규칙만 두고, 폴더마다 진짜 다른 부분만 하위 AGENTS.md로 뺍니다. 디렉터리는 이런 모습이 됩니다.

{{< highlight text >}} myrepo/ ├── AGENTS.md # 공통: 커밋 규칙, 절대 금지 파일 ├── apps/ │ └── web/ │ └── AGENTS.md # 프런트: pnpm, Prettier, 함수형 컴포넌트 └── services/ └── api/ └── AGENTS.md # 백엔드: go test ./..., gofmt, 마이그레이션 규칙 {{< /highlight >}}

기존에 CLAUDE.md나 .cursorrules가 이미 있다면? 내용을 AGENTS.md로 옮기고, 도구가 옛 파일도 계속 찾는다면 얇은 포인터 하나만 남기는 방법이 흔합니다(예: CLAUDE.md에 “See AGENTS.md” 한 줄, 또는 심볼릭 링크). 이렇게 하면 규칙의 단일 출처(single source of truth)는 AGENTS.md 하나가 됩니다.

7. 흔한 실수 · 팁

실수왜 문제인가대신 이렇게
README를 그대로 복붙 배지·홍보·설치 안내는 에이전트에 무의미. 토큰만 먹음 실행 가능한 지시만. 소개는 한 줄
“AGENTS.md 만들어 줘”로 자동 생성 후 방치 코드로 아는 내용이 대부분 → 성공률 마이너스, 비용↑ 초안만 받고 사람이 잘라 최소화
모든 걸 다 적기 (수백 줄) 중요한 지시가 묻히고(context rot) 비용 20%+↑ 150줄 이내, “코드로 모를 것”만
명령을 애매하게 (“테스트 돌려”) 에이전트가 명령을 추측하다 실패·재시도 정확한 명령어와 플래그를 그대로
말로 코드 스타일 설명 장황하고 해석 여지가 큼 규칙은 포매터에 위임, 예시 코드 한 줄
비밀키·내부 URL을 파일에 적기 저장소에 커밋되어 유출 위험 “건드리지 말 것”만 적고 값은 절대 금지
중첩 지원을 가정 도구가 하위 폴더 파일을 안 읽을 수 있음 지원 여부 확인, 아니면 루트에 섹션으로
팁 — AGENTS.md도 코드처럼 관리하세요. 규칙이 틀리거나 낡으면 에이전트를 잘못된 방향으로 이끕니다. 프로젝트 관례가 바뀌면(포매터 교체, 테스트 명령 변경) AGENTS.md도 같은 PR에서 함께 고치는 습관을 들이면, 파일이 항상 진실을 유지합니다.

8. 마무리 (TL;DR)

  • AGENTS.md는 코딩 에이전트를 위한 저장소 설명서입니다. 루트에 두는 Markdown 한 장을 Codex·Cursor·Copilot·Aider 등 대부분의 에이전트가 자동으로 읽습니다.
  • 도구마다 다르던 CLAUDE.md·.cursorrules·copilot-instructions.md를 하나로 통합합니다. 지금은 6만+ 저장소가 쓰고, Linux Foundation의 AAIF가 표준으로 관리합니다.
  • 발견 규칙은 하나 — 가장 가까운 AGENTS.md가 이깁니다. 모노레포는 폴더별로 중첩하고, 사용자의 직접 지시는 어떤 파일보다 우선합니다.
  • 넣을 것은 “코드로는 알 수 없는 것”뿐 — 정확한 빌드·테스트 명령, 다른 점만 적은 코드 스타일, 하지 말 것, 커밋 규칙. 진짜 명령어 한 줄이 설명 세 문단을 이깁니다.
  • 반전: 길고 자동 생성한 파일은 오히려 독입니다. ETH·GitHub 연구에서 성공률은 안 오르고 추론 비용만 20%+ 늘었으며, 자동 생성 파일은 성능에 마이너스였습니다. 양이 아니라 밀도 — 150줄 이내로, 관찰→교정하며 최소한만 채우세요.
