1. 도입 — "에이전트를 더 붙이면 되지 않을까?"에 도착한 청구서

에이전트가 작업을 자꾸 틀리면, 요즘 가장 흔한 처방은 이렇습니다. "플래너 에이전트를 앞에 두고, 작업별 워커 에이전트로 쪼개고, 마지막에 리뷰어 에이전트를 붙이자." 다이어그램은 근사해지고, 데모도 그럴듯하게 돌아갑니다. 문제는 이 처방이 실제로 성공률을 올리는지 아무도 통제된 조건에서 재 보지 않은 채, 업계 기본값처럼 퍼졌다는 점입니다.

이번 주 그 공백을 정면으로 겨눈 연구가 나왔습니다. 11월 첫째 주 arXiv에 올라온 Amazon·워싱턴대 공동 연구 "Agent Architecture Cost-Success Trade-offs"(arXiv:2611.12953)입니다. 모델·태스크·도구를 전부 고정하고 아키텍처만 바꿔 가며 13개 기업형 업무 절차를 돌렸더니, 멀티 에이전트든 스킬 구성이든 구조를 추가한 쪽은 토큰을 1.4~4.7배 쓰면서 성공률 이득은 대부분 통계적으로 유의미하지 않았습니다. 결론 한 줄이 꽤 도발적입니다 — "싱글 에이전트가 효율적인 기본값(efficient default)이다."

공교롭게 같은 주, 반대 방향의 사례도 화제였습니다. 11월 9일 AWS Strands 공식 블로그에 Amazon 내부 팀이 티켓 분류 스텝에서 Claude Sonnet 4.6을 떼어내고 2B급 decision model(Strands Decider)로 바꿔 분류 비용을 약 98% 줄였다는 글이 올라왔고, Hacker News에서 700점 넘게 오르며 하루 종일 토론이 이어졌습니다. 방향은 반대처럼 보이지만(하나는 "구조를 늘리지 마라", 하나는 "모델을 줄여라") 교훈은 하나로 모입니다. 기본값으로 크고 복잡하게 가지 말고, 스텝마다 '오른쪽 크기(right size)'를 측정해서 찾아라. 이번 글에서 두 사건을 묶어 뜯어봅니다.

2. 배경 — 1년 반짜리 논쟁과 꼭 필요한 용어들

이 논문은 진공에서 나오지 않았습니다. "멀티 에이전트를 지어야 하나"는 2025년 중반부터 업계가 가장 크게 갈라진 질문 중 하나였습니다.

2025년 6월, Devin을 만든 Cognition의 Walden Yan이 "Don't Build Multi-Agents"라는 에세이로 포문을 열었습니다. 요지는 두 원칙입니다. ① 컨텍스트는 최대한 공유하라(개별 메시지가 아니라 에이전트의 전체 작업 흔적을). ② 모든 행동에는 암묵적 결정이 실려 있다 — 에이전트를 쪼개면 결정이 흩어지고, 서로 모순된 암묵적 결정 위에서 시스템이 부서진다는 겁니다. 거의 같은 시기 Anthropic은 정반대 데이터를 공개했습니다. 자사 리서치 기능의 멀티 에이전트 시스템이 싱글 에이전트 대비 내부 리서치 평가에서 90.2% 더 좋았다고요. 단, 같은 글에 비용 경고도 함께 있었습니다 — 멀티 에이전트는 일반 채팅의 약 15배 토큰을 쓰고, 성능 분산의 약 80%는 아키텍처가 아니라 토큰 사용량이 설명한다는 겁니다. 올해 4월 Cognition은 후속 글 "Multi-Agents: What's Actually Working"에서 입장을 다듬었습니다. 읽기(조사·리뷰)는 병렬로 돌려도 되지만, 쓰기는 단일 스레드를 유지하는 패턴만 살아남았다고요.

즉 1년 반 동안 양쪽 다 일화와 자사 사례는 많았는데, 같은 모델·같은 태스크·같은 도구에서 아키텍처만 바꿔 본 통제 실험이 없었습니다. 이번 논문이 채운 빈칸이 정확히 그것입니다.

용어 세 개만 정리하고 갑니다.

  • SOP(Standard Operating Procedure, 표준 운영 절차): "환불 요청이 오면 ① 주문 조회 ② 정책 확인 ③ 승인 또는 에스컬레이션"처럼, 기업 업무를 단계·조건으로 적어 둔 절차서입니다. 이 논문의 태스크는 전부 이런 절차 실행형입니다.
  • 스킬(skill): 절차의 한 덩어리를 "이 작업은 이렇게 하고, 이 도구만 쓴다"로 묶어 에이전트에게 주는 구조화된 지시문입니다. 에이전트 수는 하나로 유지하면서 구조만 더하는 방식입니다.
  • 오케스트레이터-워커(orchestrator-worker): 분해 담당 에이전트가 작업을 쪼개 워커 에이전트들에게 나눠 주고, 결과를 합치는 멀티 에이전트의 대표 패턴입니다.

3. 실험 해부 — 모델·태스크·도구를 고정하고 아키텍처만 바꾸면

실험 설계가 이 논문의 핵심 기여입니다. 비교 대상인 네 아키텍처(세부 변형 포함 총 8개 구성)에 같은 모델, 같은 13개 SOP 태스크, 같은 도구 목록을 주고 아키텍처 변수만 바꿨습니다. 태스크는 SOP-Bench에서 가져왔는데, 자연어 절차서와 도구 스키마에 결정적(deterministic) mock 도구 응답과 정답(ground truth)이 딸려 있어 채점이 재현 가능합니다.

왜 이 통제가 중요할까요? 지금까지의 멀티 에이전트 성공담 대부분은 아키텍처를 바꾸면서 모델 조합도, 프롬프트도, 도구 노출 방식도 함께 바꿨습니다. 그 상태에서 성능이 오르면 무엇의 공인지 알 수 없습니다. 반대로 이 실험에서는 성공률 차이가 나면 그건 아키텍처의 효과이고, 차이가 안 나면 아키텍처는 (적어도 이 과제군에서는) 비용만 더하는 장식이라는 해석이 가능해집니다.

4. 숫자 읽기 — 토큰 1.4~4.7배, 성공률은 '대부분' 제자리

결과를 한 장으로 요약하면 이렇습니다.

하나씩 뜯어 보겠습니다.

첫째, 기준선이 생각보다 셉니다. SOP 전문과 도구 전부를 받은 평범한 function-calling 싱글 에이전트가 성공률 67.4%를 기록했습니다. 구조를 추가한 구성들이 넘어야 할 선이 여기입니다.

둘째, 스킬은 품질이 전부입니다. 잘 작성된 스킬(각 스킬이 선언한 도구만 노출)은 성공률을 73.1%로 올렸지만, 품질이 떨어지는 스킬은 기준선 아래로 떨어뜨렸습니다. 같은 아키텍처인데 결과가 품질에 따라 반대로 갈린 겁니다. 논문이 스킬 품질 평가 루브릭을 함께 제안한 이유가 여기 있습니다. 아키텍처 선택보다 구현 품질이 더 큰 변수라는 게 이 실험의 숨은 주인공입니다.

셋째, 멀티 에이전트는 '그럴듯하게' 만들면 집니다. 흔히 하는 방식대로 구현한 분해-워커-합성 구성은 기준선보다 낮았고, 최악 구성은 58.2%까지 떨어졌습니다. 과제 특성에 맞춰 공들여 재설계한 멀티 구성 하나만 75.6%로 기준선을 유의미하게 넘었습니다. 즉 멀티 에이전트가 이기는 건 가능하지만, 기본 패턴을 가져다 붙이는 수준으로는 안 되고, 그 노력에는 토큰 1.4~4.7배·지연 2.6~5.8배라는 고정 비용이 따라붙습니다.

왜 멀티 에이전트가 절차 실행에서 약할까? SOP는 단계 사이에 상태가 이어지는 과제입니다. 3단계의 판단이 1단계에서 본 고객 정보에 달려 있는 식입니다. 워커마다 SOP 조각과 도구 부분집합만 주는 컨텍스트 격리는 토큰을 아끼려는 설계지만, 절차 실행에서는 바로 그 격리가 "앞 단계의 암묵적 결정"을 끊어 먹습니다. Cognition이 말한 "행동에는 암묵적 결정이 실려 있다"가 통제 실험에서 숫자로 확인된 셈입니다. 이 블로그의 핸드오프 제약 약화 글에서 다룬 현상과 같은 뿌리입니다.

읽을 때 주의할 점도 있습니다. 이 실험은 특정 모델 하나, 기업형 SOP 13개라는 조건 안의 결과입니다. 논문 스스로도 복잡하고 분기가 많은 SOP에서는 구조 추가가 도움이 되는 방향성(directional)이 보인다고 적고 있습니다 — 다만 통계적으로 유의미한 수준은 아니었다는 단서와 함께요.

5. 반대쪽 증거와 화해 — 과제 유형이라는 숨은 축

"그럼 Anthropic의 90.2%는 뭐였나?"라는 질문이 자연히 나옵니다. 거짓말이 아니라, 과제 유형이 달랐습니다.

Anthropic의 리서치 시스템이 푸는 과제는 넓은 웹을 동시에 탐색하는 읽기 병렬형입니다. 서브에이전트들이 서로 다른 검색 경로를 독립적으로 파고들어도 충돌할 '쓰기'가 없고, 수확한 정보를 합치면 그대로 이득입니다. 이런 과제에서는 컨텍스트 격리가 단점이 아니라 장점입니다 — 각자 자기 창을 꽉 채워 쓸 수 있으니까요. 반면 SOP 실행은 단계가 순서대로 이어지고 상태를 공유해야 하는 순차 절차형입니다. 병렬화할 것이 애초에 적고, 쪼개면 결정만 흩어집니다.

Cognition의 4월 후속 글이 내린 결론도 같은 선 위에 있습니다. 살아남은 멀티 에이전트 패턴은 "읽기는 병렬, 쓰기는 단일 스레드"였고, Devin의 코드 작성과 리뷰를 일부러 컨텍스트를 공유하지 않는 별도 에이전트로 둔 것도 리뷰가 '새로운 눈'이 필요한 읽기 작업이기 때문입니다. 세 증거를 겹치면 이런 결정 기준이 나옵니다.

중요한 건 이 축이 "멀티 에이전트냐 아니냐"라는 이분법이 아니라는 점입니다. 실제 시스템은 스텝의 연속이고, 스텝마다 과제 모양이 다릅니다. 그래서 다음 질문은 자연히 "스텝 하나하나를 어떤 크기로 짓나"가 됩니다.

6. 실전 — 스텝 단위 right-sizing, Strands Decider 사례

같은 주 화제였던 Strands 블로그 사례가 정확히 이 질문의 실전판입니다. Amazon 내부 팀의 에이전트 파이프라인에는 "들어온 티켓을 20개 카테고리 중 하나로 분류"하는 스텝이 있었고, 여기에 Claude Sonnet 4.6을 쓰고 있었습니다. 분류는 위 결정 트리의 맨 왼쪽, 보기가 정해진 닫힌 결정입니다. 문장을 생성할 필요가 전혀 없는 스텝에 프런티어 모델을 쓰고 있었던 거죠.

팀은 이 스텝만 Strands Decider로 바꿨습니다. Decider는 AWS Strands Labs가 공개한 decision model(결정 전용 모델) 계열로, 텍스트 생성 헤드를 떼고 스코어링 헤드를 얹어 "보기 중 선택(choice)", "예/아니오(noul)", "루브릭 점수(score)" 세 종류의 결정만 보정된 확률과 함께 돌려줍니다. 2026년 10월 Apache-2.0으로 공개됐고(기준 모델은 Qwen3.5-2B 기반, 이후 Gemma 4 기반 E2B/E4B/12B/26B-A4B 빌드 추가), 이 팀은 Gemma 4 E4B 빌드를 SageMaker ml.g5.xlarge에 올렸습니다. 블로그가 공개한 수치는 이렇습니다 — 티켓 100만 건당 비용 약 $22,200 → 약 $500(정가 기준, 약 98% 절감), 호출당 지연 4,215ms → 897ms, 티켓당 토큰 6,724 → 2,010. 벤더가 공개한 자사 사례 수치라는 점, 정확도 비교의 상세 수치는 공개되지 않았다는 점은 감안하고 읽어야 합니다.

사용감은 이렇게 단순합니다.

{{< highlight bash >}} pip install strands-decider # 상태(state)를 주고, 닫힌 질문을 던진다 strands-decider ask StrandsAgents/strands-decider-2B-qwen3.5-v1-2610 \ --state "Help! My payouts have been failing for 3 days!" \ --choice "Which team should handle this?=billing,sales,retail" \ --noul "Does this convey urgency?" # → 선택지별 확률 분포 + 보정된 confidence가 돌아온다 {{< /highlight >}}

이 교체에서 비용 절감보다 배울 게 많은 건 롤아웃 방식입니다. 팀은 한 번에 바꾸지 않고 3단계 스위치를 뒀습니다. ① Sonnet 단독(기존) → ② 두 모델 병행: 응답은 Sonnet 것을 쓰되 Decider의 답을 나란히 기록해 비교(shadow mode) → ③ 일치율이 확인된 뒤 Decider 단독. 모델 교체를 되돌릴 수 있는 설정값으로 만든 겁니다. 개념 코드로 옮기면 이렇습니다.

{{< highlight python >}} # 스텝 교체를 '한 방 수술'이 아니라 '되돌릴 수 있는 스위치'로 만드는 패턴 MODE = "shadow" # "legacy" → "shadow" → "decider" def classify_ticket(ticket: str) -> str: if MODE == "legacy": return sonnet_classify(ticket) # 기존 경로 그대로 if MODE == "shadow": label = sonnet_classify(ticket) # 응답은 여전히 기존 모델 d = decider_classify(ticket) # 새 모델은 기록만 log_comparison(ticket, legacy=label, # 일치율·confidence를 쌓는다 candidate=d.label, conf=d.confidence) return label d = decider_classify(ticket) # MODE == "decider" if d.confidence < 0.9: return sonnet_classify(ticket) # 낮은 확신은 큰 모델로 폴백 return d.label {{< /highlight >}}

마지막 네 줄이 decision model 특유의 설계 포인트입니다. Decider README는 처음 보는 짧은 분류 과제에서 confidence 0.9 이상인 답이 약 95% 정답이라는 보정(calibration) 결과를 공개하고, 그 아래 확신은 사람이나 큰 모델로 넘기라고 권합니다. 일반 LLM API는 이런 보정된 확신값을 주지 않으니, "언제 큰 모델로 폴백할지"를 체계적으로 정할 수 있다는 것 자체가 기능입니다. 이 블로그에서 다룬 System One 모델, OpenAI Decisions API와 같은 흐름이고, 더 넓게는 모델 라우팅·캐스케이드의 한 사례입니다.

정리하면, 이번 주 두 사건이 실무자에게 시키는 일은 하나입니다. 파이프라인을 스텝으로 쪼개 보고, 스텝마다 "지금 이 크기가 맞나?"를 측정으로 답하기. 구조(에이전트 수)는 과제 모양이 요구할 때만 늘리고, 모델 크기는 스텝이 닫힌 결정이라면 과감히 줄이는 겁니다. 양쪽 다 감이 아니라 영수증(토큰·지연·성공률 로그)으로 결정합니다.

7. 흔한 실수 · 팁

실수왜 문제인가 / 어떻게 고치나
성능이 안 나오면 일단 에이전트를 추가 통제 실험에서 '그럴듯한' 멀티 구성은 기준선보다 낮았습니다. 구조를 늘리기 전에 프롬프트·스킬·도구 설명 품질부터 점검하세요. 아키텍처보다 구현 품질이 더 큰 변수입니다.
아키텍처 비교를 성공률로만 판단 토큰 1.4~4.7배·지연 2.6~5.8배는 매 요청 반복 청구되는 고정 비용입니다. 성공률 +2%p가 토큰 3배 값을 하는지는 과제 가치에 따라 다릅니다. 비교표에 반드시 비용 열을 넣으세요.
멀티 에이전트 성공담을 내 과제에 그대로 이식 읽기 병렬형(리서치)에서의 승리가 순차 절차형(SOP)으로 옮겨지지 않습니다. 내 과제가 어느 모양인지부터 분류하세요. 쓰기가 끼어 있다면 쓰기는 단일 스레드로 남기세요.
문장 생성이 필요 없는 스텝에 프런티어 LLM 사용 분류·라우팅·게이트는 닫힌 결정입니다. decision model이나 소형 모델 + confidence 기반 폴백으로 바꾸면 비용과 지연이 크게 떨어집니다. 단, 보기가 닫혀 있지 않은 다단계 추론에는 decision model이 약합니다.
모델·아키텍처 교체를 한 번에 배포 shadow mode 없이 바꾸면 품질 저하를 사용자보다 늦게 알게 됩니다. 기존 응답을 유지한 채 새 경로의 답을 나란히 기록하는 병행 구간을 반드시 두세요.
벤더 공개 수치를 내 워크로드 전망치로 사용 98% 절감은 '20개 카테고리 분류'라는 특정 스텝, 벤더 자사 사례의 수치입니다. 내 스텝의 절감 폭은 내 shadow 로그가 말해 줍니다.

8. 마무리 (TL;DR)

  • Amazon·워싱턴대의 arXiv:2611.12953는 모델·태스크·도구를 고정하고 아키텍처만 바꾼 보기 드문 통제 실험입니다. 13개 기업형 SOP에서 싱글 에이전트 기준선은 67.4%, 구조를 추가한 구성들은 토큰 1.4~4.7배·지연 2.6~5.8배를 쓰면서 성공률 이득은 대부분 통계적으로 유의미하지 않았습니다.
  • 예외가 둘 있었습니다 — 고품질 스킬(73.1%)과 과제 맞춤으로 재설계한 멀티 구성(75.6%). 반대로 저품질 스킬과 '그럴듯한' 멀티 구성은 기준선보다 나빴습니다. 아키텍처 선택보다 구현 품질이 더 큰 변수입니다.
  • Anthropic의 멀티 에이전트 +90.2% 사례와 모순되지 않습니다. 그쪽은 읽기 병렬형 과제였고, 이번 실험은 순차 절차형입니다. "읽기는 병렬 가능, 쓰기는 단일 스레드, 절차 실행은 컨텍스트를 쪼개지 말 것"이 세 증거의 교집합입니다.
  • 같은 주 Strands 블로그의 Decider 사례는 반대 방향의 같은 교훈입니다 — 닫힌 결정 스텝(20개 카테고리 분류)에서 Sonnet 4.6을 2B급 decision model로 바꿔 비용 약 98%·지연 약 79% 절감. 핵심은 보정된 confidence 기반 폴백과 shadow mode 3단계 롤아웃입니다.
  • 실무 지침 한 줄: 기본값은 싱글 에이전트. 구조는 과제 모양이 요구할 때만, 모델 크기는 스텝이 필요로 하는 만큼만. 결정은 감이 아니라 토큰·지연·성공률 영수증으로.
