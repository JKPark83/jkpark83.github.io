1. 도입 — 스킬은 좋은데, 누가 다 쓰나요?

에이전트에게 도메인 전문성을 얹는 방법으로 SKILL.md 기반 Agent Skills는 이제 사실상 표준이 됐습니다. 그런데 이 방식에는 조용히 깔린 전제가 하나 있습니다. 스킬은 사람이 손으로 쓴다는 것. vLLM 배포 노하우를 스킬로 만들려면, vLLM을 잘 아는 사람이 앉아서 문서를 읽고, 함정을 정리하고, 검증 절차를 적어야 합니다. 스킬이 10개면 어떻게든 됩니다. 그런데 ML 생태계의 주요 저장소 1,000개를 커버하려면요?

이번 주(9월 첫째 주) 이 전제를 정면으로 뒤집는 논문이 화제가 됐습니다. 9월 2일 공개된 Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills(arXiv:2609.02749)입니다. 베이징인공지능연구원(BAAI)을 중심으로 한 연구진은 DisCo라는 에이전트에게 GitHub 저장소를 읽혀서 스킬을 자동으로 만들게 했고, 그 결과물인 AREX-Skill 라이브러리는 저장소 1,000개에서 증류한 검증된 스킬 5,000여 개를 담고 있습니다. 효과도 큽니다. 같은 Codex 에이전트, 같은 harness, 같은 실행 예산에서 스킬만 얹었더니 MLE-bench 메달 획득률이 31.11%에서 72.89%로, 상대 기준 +134.3% 뛰었습니다.

논문은 Hugging Face 데일리 페이퍼에 오르고 Turing Post 등 X 계정들이 정리 스레드를 올리면서 빠르게 퍼졌습니다. 마침 같은 주에 Arize의 "MCP vs CLI/Skills" 평가 글이 돌면서 "에이전트 능력의 단위는 무엇인가"라는 논쟁이 다시 붙었는데, Repo-To-Skill은 여기에 "스킬이 맞다, 심지어 손으로 안 써도 된다"는 강한 한 표를 던진 셈입니다.

비유하자면 이렇습니다. 지금까지의 스킬 작성이 장인이 한 권씩 쓰는 사내 위키였다면, Repo-To-Skill은 위키를 쓰는 사서를 고용한 것입니다. 사서가 도서관(GitHub) 전체를 돌며 책마다 "이 도구는 언제 쓰고, 뭘 실행하고, 어떻게 검증하고, 실패하면 어떻게 복구하는지"를 규격화된 카드로 만들어 꽂아 둡니다. 에이전트는 일하다가 필요한 카드만 뽑아 읽습니다.

2. 배경 — SKILL.md 30초 복습, 그리고 '운영 지식'

따라오는 데 필요한 배경은 두 가지뿐입니다.

첫째, Agent Skills 포맷. 스킬은 SKILL.md 파일 하나가 담긴 폴더입니다. 프런트매터에 이름과 "언제 이 스킬을 쓰는지" 설명이 있고, 본문에 절차가 있고, 옆에 references/(참고 문서)와 scripts/(실행 가능한 헬퍼)를 둘 수 있습니다. 핵심 원리는 점진적 공개(progressive disclosure)입니다. 평소에는 이름·설명만 컨텍스트에 올려 두고, 요청과 맞을 때만 본문을, 더 필요할 때만 참고 문서를 펼칩니다. 자세한 동작은 이전 글에서 다뤘으니 여기서는 이 정도만 기억하면 됩니다. AREX-Skill도 독자 포맷이 아니라 이 공개 표준(agentskills/agentskills)을 패키징 규약으로 그대로 씁니다. 그래서 만들어진 스킬을 Codex나 Claude Code 같은 기존 코딩 에이전트에 바로 설치할 수 있습니다.

둘째, 이 논문의 문제 설정인 운영 지식(operational knowledge). 방법을 "아는 것"과 실제로 "돌아가게 만드는 것" 사이의 노하우를 말합니다. 어떤 라이브러리 버전 조합이 실제로 설치되는지, 어떤 API를 어떤 순서로 불러야 하는지, 학습 파이프라인 설정에서 다들 걸려 넘어지는 함정이 뭔지 같은 것들이죠. 이 지식은 세상에 이미 있습니다. 논문에, 저장소에, 이슈 스레드에요. 문제는 전부 사람이 읽으라고 쓴 형태라는 겁니다. 에이전트가 작업 중에 통째로 로드하기엔 너무 크고, 검색해서 짜깁기하자니 매번 같은 삽질을 반복합니다.

즉 Repo-To-Skill의 관점에서 스킬은 저장소의 요약이 아닙니다. README를 줄여 놓은 게 아니라, "이 도구를 실전에서 굴리는 법"을 실행 가능한 형태로 옮긴 인터페이스입니다. 이 구분이 이 논문 전체를 관통합니다.

3. 스킬 하나 해부 — vLLM 스킬은 실제로 이렇게 생겼다

추상적으로 듣는 것보다 실물을 보는 게 빠릅니다. AREX-Skill 저장소에 실제로 들어 있는 vLLM 스킬의 루트 SKILL.md는 이렇게 시작합니다(발췌).

{{< highlight yaml >}} --- name: vllm description: "Route vLLM tasks across offline inference, OpenAI-compatible serving, structured/tool/reasoning, multimodal/LoRA/pooling, and deployment/performance workflows." disable-model-invocation: true # 모델에게 항상 보이는 목록에서는 뺀다 (아래 설명) metadata: disco-role: operating license: Apache 2.0 --- {{< /highlight >}}

본문에서 눈에 띄는 특징은 네 가지입니다.

루트 스킬은 라우터입니다. vLLM처럼 기능이 많은 저장소는 스킬 하나로 안 끝납니다. 루트 SKILL.md는 "사용자가 Python 인프로세스 추론을 원하면 sub-skills/offline-inference/로, vllm serve와 OpenAI 호환 서버 얘기면 sub-skills/openai-serving/로, 메모리·병렬화·양자화·벤치마크면 sub-skills/deployment-performance/로 가라"는 라우팅 표를 담고, 실제 명령과 코드는 하위 스킬에 있습니다. 저장소 하나가 스킬 그래프(skill graph)가 되는 구조입니다.

안전 기본값이 명시돼 있습니다. "사용자가 승인하기 전에는 서버를 띄우거나, 모델을 다운로드하거나, trust_remote_code를 켜지 말라"처럼, GPU 실행·다운로드·멀티 노드 같은 비싼 행동을 환경 게이트 뒤로 밀어 둡니다. 스킬이 절차만이 아니라 행동 규범도 실어 나른다는 뜻입니다.

실행 가능한 진단 스크립트가 붙어 있습니다. scripts/vllm_skill_doctor.py는 모델을 내려받거나 서버를 띄우지 않고도 import·CLI·백엔드 상태를 점검합니다. "말로 된 지시"와 "돌려 볼 수 있는 코드"가 한 패키지에 있는 거죠.

검증 범위를 스스로 밝힙니다. 맨 아래 Verification Scope 절은 "이 스킬은 소스·문서·예제·테스트와 CPU 환경 점검으로 생성했고, 실제 GPU 서빙은 사용자 환경에서 검증해야 한다"고 적습니다. 어디까지 확인된 지식인지 출처와 한계를 남기는 것 — 이게 뒤에서 볼 증류 파이프라인의 '검증' 단계와 이어집니다.

그럼 스킬이 5,000개면 컨텍스트가 터지지 않을까요? 여기서 프런트매터의 disable-model-invocation: true가 등장합니다. 저장소 스킬 루트는 모델에게 항상 보이는 스킬 목록에서 빠지고, 대신 모델에게 보이는 것은 repo-skills-router라는 라우터 스킬 하나입니다. 에이전트는 라우터를 읽고 분류 체계에서 영역(area) 한두 개를 고르고 → 해당 영역 페이지만 읽고 패키지 패밀리를 비교하고 → 선택된 저장소의 SKILL.md를 열고 → 필요한 하위 스킬과 스크립트만 읽습니다. 툴을 지연 로딩하는 것과 같은 원리를 지식에 적용한, 점진적 공개의 대규모 버전입니다.

4. DisCo의 4단계 증류 파이프라인

그럼 이런 스킬을 에이전트가 어떻게 만들까요? 스킬을 만들고(Creator) 쓰는(Researcher) 에이전트가 DisCo이고, Creator의 증류 워크플로는 4단계입니다.

출발점은 앵커(anchor)입니다. 앵커가 저장소나 논문 같은 소스면 미리 해 두는 태스크 불특정(task-agnostic) 증류이고 — AREX-Skill 라이브러리가 이렇게 만들어졌습니다 — 앵커가 지금 풀어야 할 문제면 그 자리에서 필요한 스킬을 뽑는 태스크 지향(task-oriented) 증류입니다.

단계별로 풀면 이렇습니다.

① 범위 설정(scope) — 앵커에서 "이 저장소가 제공하는 능력"의 목록을 뽑습니다. vLLM이라면 오프라인 추론, OpenAI 호환 서빙, 구조화 출력, 배포·성능 튜닝 같은 단위들이죠. 이 단위가 그대로 하위 스킬 후보가 됩니다.

② 근거 확보(ground) — 각 능력을 허용 가능한 근거에 붙들어 맵니다. 소스 코드, 공식 문서, 예제, 테스트, 패키지 메타데이터처럼 확인 가능한 것들이요. 모델의 사전 지식으로 "아마 이렇겠지"라고 채우는 걸 막는 단계입니다. LLM이 그럴싸하게 지어내는 능력이 뛰어나다는 걸 생각하면, 스킬 증류에서 가장 중요한 방어선입니다.

③ 그래프 구성(construct) — 근거가 붙은 능력들을 라우팅 가능한 스킬 그래프로 조립합니다. 루트는 라우터, 하위는 워크플로별 스킬, 옆에 references와 scripts.

④ 검증·정제(verify & refine) — 후보 스킬을 실제로 점검하고, 고칠 수 있으면 고치고, 남은 공백은 공백대로 기록합니다. 검증을 통과하지 못한 스킬은 라이브러리에 들어가지 못합니다. 이때 근거 출처·검증 체크·미해결 공백이 구성 기록(construction record)으로 남아서, 나중에 업스트림이 바뀌었을 때 스킬을 갱신(refresh)하는 기준이 됩니다.

주목할 점: 이 파이프라인에서 모델 가중치는 전혀 건드리지 않습니다. 파인 튜닝도, 학습도 없습니다. 늘어나는 건 에이전트가 로드할 수 있는 파일뿐입니다. 그래서 스킬은 git으로 버전 관리하고, diff로 리뷰하고, 다른 에이전트로 들고 갈 수 있습니다. 에이전트 메모리를 어떤 기질에 저장할 것인가라는 논의에서 "사람이 읽을 수 있는 파일" 쪽 극단을 대규모로 밀어붙인 사례로 볼 수도 있습니다.

5. 숫자 읽는 법 — +134.3%는 무슨 뜻인가

공식 결과표부터 보겠습니다. 에이전트 설정·harness·실행 예산을 고정하고, AREX 스킬 유무만 바꾼 비교입니다.

이 표를 junior의 눈으로 의심하며 읽는 연습을 해 봅시다.

+134.3%는 절대치가 아니라 상대 이득입니다. 31.11% → 72.89%니까 절대로는 +41.78%p입니다. 상대 퍼센트는 기저가 낮을수록 커 보인다는 걸 항상 기억하세요. 그래도 Kaggle 대회 75개 중 메달권 결과를 내는 비율이 3분의 1에서 4분의 3으로 올랐다는 건, 방향과 크기 모두 인상적인 결과입니다.

이득이 벤치마크마다 다른 것 자체가 정보입니다. MLE-bench(+134.3%)는 라이브러리·환경 설정·디버깅 같은 운영 지식이 승부를 가르는 과제라 스킬 효과가 극대화됩니다. 반면 FrontierCS(+9.2%)는 알고리즘적 사고가 중심이라 "절차 카드"가 해 줄 수 있는 게 상대적으로 적습니다. 스킬은 만능이 아니라 운영 지식이 병목인 곳에서 힘을 씁니다. 저자들 표현으로는 "스킬이 비싼 무작정 시행착오를 줄이고, 예산을 실험과 검증에 쓰게 해 준다"입니다.

자기 보고 수치라는 한계도 있습니다. 이 표는 저자 측 평가이고, 글을 쓰는 시점 기준 세부 방법을 담은 완전한 기술 보고서는 아직 공개 전입니다(저장소에 "forthcoming"으로 명시). 제3자 재현이 나오기 전까지는 "저자 보고 기준 이 정도"로 잡아 두는 게 안전합니다. 반가운 점은 라이브러리와 CLI가 Apache 2.0으로 전부 공개돼 있어서, 누구든 같은 비교를 돌려 볼 수 있다는 것입니다.

6. 계보 — '경험을 스킬로'는 하나의 연구 축이 됐다

Repo-To-Skill이 갑자기 튀어나온 건 아닙니다. 올여름부터 "에이전트의 경험과 인류의 문서를 스킬로 압축한다"는 논문이 줄줄이 나오면서 스킬 증류(skill distillation)가 하나의 축으로 자리 잡았습니다. 지도를 그려 보면:

무엇에서 증류하는가로 나눌 수 있습니다. Microsoft Research의 Skill-DisCo(arXiv:2606.26669, 6월)는 에이전트 자신의 성공 트레이스에서 증류합니다. 반복되는 행동 패턴을 파라미터화된 절차(제어 흐름 서브그래프)로 컴파일해서, ALFWorld·WebArena에서 성공률을 올리고 턴 수를 줄였습니다. "같은 유형 문제를 매번 처음부터 푸는 낭비를 없애자"는 문제의식이죠. Resource2Skill(arXiv:2606.29538)은 사람이 만든 튜토리얼·문서 같은 멀티모달 자료에서, 그리고 Repo-To-Skill은 GitHub 저장소에서 증류합니다. 소재는 달라도 산출물은 같습니다 — 에이전트가 로드할 수 있는, 검증된 절차 단위.

이 흐름은 이 블로그에서 다뤘던 두 줄기가 만나는 지점이기도 합니다. 하나는 스킬의 수명 주기 관리 — 스킬을 언제 만들고 언제 폐기하는가. 다른 하나는 컨텍스트 엔지니어링 — 무엇을 컨텍스트에 올리고 무엇을 미룰 것인가. 스킬 증류는 전자의 "만들기"를 자동화하고, 후자의 라우팅·점진적 공개를 규모 있게 실증했습니다. 그리고 이번 주 MCP 대 스킬 논쟁의 관점에서 보면, 스킬 진영의 가장 약한 고리였던 "그 많은 스킬을 누가 유지보수하나"에 대한 답변 시도이기도 합니다.

7. 실전 — 설치해 보고, 내 저장소도 증류해 보기

직접 만져 보는 게 제일 빠릅니다. 두 가지 실습을 제안합니다.

실습 A — AREX-Skill 라이브러리 써 보기. DisCo CLI는 npm 패키지(@arex-skill/disco)로 배포됩니다. Node.js 22.19 이상이 필요합니다.

{{< highlight bash >}} # DisCo 설치 (postinstall 스크립트 실행을 막는 --ignore-scripts 권장) npm install -g --ignore-scripts @arex-skill/disco # 라이브러리 설치 후 Researcher 모드 시작 disco repo-skills install disco # 첫 실행 시 /login 또는 OPENAI_API_KEY / ANTHROPIC_API_KEY 등으로 프로바이더 설정 {{< /highlight >}}

프롬프트에서 구체적인 과제를 줘 보세요. 예를 들어 "설치된 스킬을 써서 이 머신에서 vLLM과 SGLang을 같은 모델·워크로드·하드웨어 조건으로 벤치마크하고, 재현에 필요한 명령과 측정값을 보존해 줘" 같은 것. 라우터가 관련 저장소 스킬을 고르고, 필요한 지시만 점진적으로 로드하는 걸 지켜볼 수 있습니다. 이미 쓰는 코딩 에이전트가 있다면 스킬만 내보낼 수도 있습니다.

{{< highlight bash >}} # vLLM·SGLang 스킬을 Claude Code의 사용자 스킬 디렉터리로 내보내기 disco --creator -p "/skill:import-repo-skills-to-agent import vllm and sglang to ~/.claude" # 내보낸 뒤 대상 에이전트를 재시작해야 새 스킬을 읽습니다 {{< /highlight >}}

실습 B — 파이프라인을 내 저장소에 흉내 내 보기. DisCo 없이도 4단계 증류의 핵심은 아무 코딩 에이전트로 재현할 수 있습니다. 회사 코드베이스의 "부족 지식"을 스킬로 만드는 데 그대로 써먹을 수 있는 패턴입니다. 포인트는 프롬프트에 근거 강제와 검증 단계를 명시하는 것입니다.

{{< highlight text >}} 이 저장소를 읽고 Agent Skills 포맷의 스킬 그래프를 만들어 줘. 1. (범위) 이 저장소가 제공하는 능력을 3~7개 단위로 나열해. 2. (근거) 각 능력마다 근거가 되는 파일 경로·문서·테스트를 명시해. README와 코드에서 확인되지 않는 내용은 절대 쓰지 마. 3. (구성) 루트 SKILL.md는 라우팅 표만 담고, 능력별 sub-skill에 절차·명령·흔한 실패와 복구법을 적어. 진단용 스크립트가 가능하면 scripts/에 만들어. 4. (검증) 각 sub-skill의 명령을 실제로 실행해 보고, 실패하면 스킬을 고쳐. 실행으로 확인 못 한 항목은 "미검증"으로 표시해. {{< /highlight >}}

4번을 빼먹으면 어떻게 되는지 꼭 한번 비교해 보세요. 검증 없는 증류는 "그럴싸하지만 낡았거나 틀린 절차"를 양산합니다. 스킬 품질의 승부처는 생성이 아니라 검증이라는 걸 몸으로 느낄 수 있습니다.

8. 흔한 실수 · 팁

스킬을 README 요약으로 만들지 마세요. 요약은 "무엇인가"를 답하지만 스킬은 "언제 쓰고, 뭘 실행하고, 어떻게 검증하고, 어떻게 복구하는가"를 답해야 합니다. 넷 중 검증·복구가 빠져 있다면 그건 스킬이 아니라 소개글입니다.

검증 안 된 스킬은 오염된 컨텍스트입니다. 에이전트는 스킬을 신뢰하고 따르기 때문에, 틀린 스킬은 프롬프트 인젝션만큼이나 조용히 결과를 망칩니다. AREX처럼 "검증 통과 못 하면 발행 금지 + 확인 못 한 범위는 명시" 원칙을 지키세요.

스킬은 썩습니다. 업스트림 저장소가 버전업하면 스킬 속 명령과 API가 낡습니다. AREX-Skill이 스킬마다 소스 커밋과 갱신 요건을 기록해 두는 이유입니다. 직접 만들 때도 프로비넌스(어느 커밋 기준인지)를 남기고, 주기적 refresh를 계획에 넣으세요.

스킬 수가 늘면 라우팅이 병목이 됩니다. 스킬 다섯 개면 설명만 보고 골라도 되지만, 수천 개면 영역→패밀리→저장소 같은 계층 라우터가 필요합니다. 라우터가 잘못 고르면 그 아래가 아무리 좋아도 소용없으니, 스킬 본문보다 description과 라우팅 표에 더 공을 들이세요.

남이 만든 스킬은 남이 만든 코드입니다. 스킬에는 에이전트가 따를 지시와 실행할 스크립트가 들어 있습니다. 외부 스킬 라이브러리를 설치하는 건 의존성을 설치하는 것과 같은 보안 결정입니다. 읽고, 샌드박스에서 돌려 보고, 신뢰 범위를 정하세요.

벤치마크 이득을 내 워크로드에 그대로 대입하지 마세요. +134.3%는 "운영 지식이 병목인 ML 엔지니어링 과제"에서의 수치입니다. 운영 지식 의존도가 낮은 작업이라면 FrontierCS처럼 한 자릿수 이득에 가까울 수 있습니다.

9. 마무리 (TL;DR)

  • 이번 주 화제작 Repo-To-Skill(arXiv:2609.02749, BAAI 중심)은 스킬을 사람이 쓰는 대신, DisCo 에이전트가 GitHub 저장소에서 자동으로 증류하는 방법을 제시했습니다. 결과물인 AREX-Skill 라이브러리는 저장소 1,000개 → 검증된 스킬 5,000+개(Apache 2.0 공개)입니다.
  • 스킬은 저장소 요약이 아니라 운영 지식의 인터페이스입니다: 언제 쓰는가 · 무엇을 실행하는가 · 어떻게 검증하는가 · 실패하면 어떻게 복구하는가.
  • 증류는 범위 설정 → 근거 확보 → 그래프 구성 → 검증·정제의 4단계이고, 검증을 통과한 스킬만 발행됩니다. 모델 가중치는 건드리지 않으므로 스킬은 git으로 버전 관리·리뷰·이식이 됩니다.
  • 스킬 5,000개는 라우터 + 점진적 공개(영역→패밀리→저장소 그래프→하위 스킬)로 감당합니다. 초기 컨텍스트에는 라우터 하나만 올라갑니다.
  • 효과는 저자 보고 기준 MLE-bench 메달률 31.11%→72.89%(+134.3%). 단, 운영 지식이 병목인 과제에서 크고, 알고리즘 중심 과제(FrontierCS +9.2%)에선 작습니다. 완전한 기술 보고서는 아직 공개 전이니 제3자 재현을 기다릴 필요가 있습니다.
  • 실무 교훈: 스킬 품질의 승부처는 생성이 아니라 검증과 갱신입니다. 근거를 강제하고, 실행으로 확인하고, 프로비넌스를 남기고, 낡으면 refresh하세요.
