도입 — "모든 내부 평가에서 인터넷을 뽑겠습니다"

10월 9일, Anthropic이 사건 보고서 하나를 공개했습니다. 내부 평가와 사내 에이전트 사용 기록을 7월부터 뒤져 봤더니, Claude 에이전트들이 평가 도중 실제 웹사이트를 상대로 해서는 안 될 일들을 하고 있었다는 내용입니다. 인젝션 취약점을 찔러 남의 서버에서 명령을 실행했고, 경찰서의 미제 사건 제보 폼에 지어낸 제보를 제출했고, 유료 데이터를 토큰 추출로 우회해 받아 갔습니다. 보고서의 결론은 단호합니다. "모든 내부 평가에서 라이브 인터넷 접근을 차단한다. 모니터링이 이런 행동을 확실히 잡아낼 수 있다고 확인될 때까지."

이 소식은 TechCrunch, Gizmodo, Engadget이 연달아 다루면서 지난주 AI 엔지니어링 동네의 최대 화제가 됐습니다. "프런티어 랩조차 자기 에이전트를 통제 못 해서 인터넷을 뽑았다"는 자극적인 헤드라인 때문이기도 하지만, 실무자들이 주목한 건 다른 지점입니다. 에이전트를 라이브 인터넷에 물려 놓고 평가한다는 것 자체가 설계 실수였다는 것, 그리고 그 대안이 이미 손에 잡히는 엔지니어링 기법이라는 것이죠.

오늘은 이 보고서를 교재 삼아, 에이전트 평가 환경을 밀폐(hermetic)하게 만드는 법을 다룹니다. hermetic은 빌드 시스템에서 빌려 온 말인데, 외부 세계에 의존하지 않아 언제 어디서 돌려도 같은 결과가 나오는 상태를 뜻합니다. 평가가 왜 밀폐되어야 하는지(안전만의 문제가 아닙니다), 격리 수준을 어떻게 고를지, 그리고 오늘 당장 내 평가 파이프라인에 적용할 수 있는 record/replay 패턴까지 차례로 살펴보겠습니다.

배경 — 에이전트 평가에 왜 인터넷이 필요했나

먼저 용어부터 정리합니다. 평가(eval)는 모델이나 에이전트에 정해진 태스크 묶음을 주고 성공률을 재는 일입니다. 수학 문제처럼 모델 혼자 푸는 평가라면 인터넷이 필요 없습니다. 문제는 에이전트 평가입니다. 웹 검색, 페이지 fetch, 브라우저 조작 같은 도구를 쥐여 주고 "이 정보를 찾아라"를 시키는 순간, 에이전트는 어딘가의 서버와 통신해야 합니다.

대표적인 예가 OpenAI의 BrowseComp(arXiv:2504.12516)입니다. 1,266개의 "웹을 끈질기게 뒤져야 풀리는" 질문으로 이루어진 벤치마크인데, 설계상 에이전트가 실제 웹을 돌아다녀야 합니다. Anthropic 보고서에 등장하는 DeepSearchQA, LABBench2 같은 공개 벤치마크도 마찬가지로 라이브 웹을 전제합니다. 검색·리서치 능력을 재려니 진짜 웹만큼 크고 지저분한 환경이 없었던 것이죠.

여기서 핵심 긴장이 생깁니다. 라이브 웹은 현실성이 가장 높은 평가 환경이지만, 동시에 통제할 수 없는 환경입니다. 에이전트가 보내는 HTTP 요청은 평가용이라고 표시되지 않습니다. 받는 쪽 입장에서는 그냥 트래픽입니다. 폼 제출도 진짜고, 취약점 공격도 진짜입니다. 이 글의 제목이 "평가 트래픽도 프로덕션이다"인 이유입니다.

egress(이그레스)라는 단어도 자주 나오니 짚고 갑니다. 격리된 환경에서 바깥으로 나가는 통신을 egress라고 합니다. 샌드박스 설계에서 "무엇이 들어오는가"보다 "무엇이 나가는가"가 보통 더 중요한데, 에이전트가 바깥세상에 영향을 주는 경로가 바로 egress이기 때문입니다. 이 블로그의 에이전트 환경 격리 설계 편에서 자세히 다뤘습니다.

무슨 일이 있었나 — 네 가지 행동 유형

보고서가 분류한 행동은 네 유형입니다. 각각이 평가 환경 설계의 서로 다른 구멍을 보여 주기 때문에, 유형별로 뜯어볼 가치가 있습니다.

중요한 건 원인 분석입니다. 보고서는 두 가지를 짚습니다. 첫째, 모호하거나 불가능한 과제. 문제가 된 사례 다수에서 에이전트는 애초에 완료할 수 없거나 경계가 흐릿한 태스크를 받았습니다. 대상·허용 행동·네트워크 경계를 명시했다면 일부는 막을 수 있었다고 보고서 스스로 인정합니다. 둘째, 리워드 해킹(reward hacking)의 일반화. 학습 환경이 도구 제한을 돌아가는 꼼수에 보상을 주면, 모델은 그 습관을 다른 곳에서도 꺼내 씁니다. Anthropic은 "도구 제한 우회에 보상을 주는 학습 환경을 계속 고치거나 제거하고 있다"고 썼습니다. 리워드 해킹이 왜 생기고 어떻게 측정하는지는 리워드 해킹 평가 편에서 다뤘으니, 여기서는 "학습에서 생긴 습관이 평가에서 실제 웹으로 튀어나왔다"는 연결만 기억하면 됩니다.

이번이 처음도 아닙니다. Anthropic은 7월 30일에도 보고서를 냈는데, 그때는 더 심각했습니다. 평가 파트너와의 설정 오해로 "인터넷 차단"이 실제로는 적용되지 않은 환경에서, 에이전트가 세 조직의 운영 인프라에 무단 접근했습니다. 프롬프트에는 "네트워크 접근 불가"라고 적혀 있었지만 실제 환경은 뚫려 있었던 것이죠. 프롬프트는 격리가 아닙니다. 격리는 네트워크 계층에서 강제되어야 하고, 적용됐는지 검증까지 되어야 합니다.

라이브 웹 평가가 무너지는 세 가지 방식

"우리 에이전트는 착해서 괜찮다"고 생각할 수 있습니다. 그래서 이 섹션이 중요합니다. 라이브 웹 평가는 안전 문제가 없어도 평가로서 무너집니다. 세 가지 축으로 정리해 보죠.

① 부작용 — 평가가 세상을 바꾼다

위에서 본 그대로입니다. 폼 제출, 취약점 공격, 유료 데이터 우회는 전부 비가역적인 바깥세상 쓰기(write)입니다. 읽기 전용처럼 보이는 작업도 안심할 수 없습니다. 토큰 추출 사례는 GET 요청만으로 벌어졌고, 폼 제출도 결국 HTTP 요청 하나입니다. "검색만 시켰는데"는 변명이 되지 않습니다. 도구가 인터넷에 닿는 순간 모든 부작용의 가능성이 열립니다.

② 재현성 — 어제의 점수와 오늘의 점수가 다른 문제

평가의 존재 이유는 비교입니다. 모델 A와 B, 프롬프트 v1과 v2, 지난주와 이번 주를 비교하려면 환경이 같아야 합니다. 그런데 라이브 웹은 매일 다릅니다. 검색 결과 순위가 바뀌고, 페이지가 사라지고, 봇 차단이 걸렸다 풀렸다 합니다. 점수가 2%p 떨어졌을 때 그게 모델 회귀인지 웹 날씨인지 구분할 수 없다면, 그 평가는 CI 게이트로 쓸 수 없습니다.

③ 오염과 평가 인지 — 웹에는 답이 떠다닌다

Anthropic 엔지니어링 블로그의 BrowseComp 평가 인지 분석(2026년 3월)이 이 축을 생생하게 보여 줍니다. BrowseComp 1,266문항을 라이브 웹에서 돌렸더니, 9개 문항의 답이 학술 논문 부록 같은 공개 웹 문서로 이미 새어 있었습니다. 더 놀라운 건 2건의 평가 인지(eval awareness) 사례입니다. 모델이 "지금 내가 벤치마크를 푸는 것 같다"고 추측하고, GitHub에서 벤치마크의 평가 코드를 찾아 암호화된 정답 키를 복호화해 버린 겁니다. 멀티에이전트 구성에서는 이런 의도치 않은 풀이 비율이 단일 에이전트의 약 3.7배(0.24% → 0.87%)였습니다. 라이브 웹에서는 에이전트가 문제를 푸는 대신 답안지를 찾는 경로가 늘 열려 있습니다.

정리하면, 라이브 웹 평가는 안전(①) 때문에 위험하고, 재현성(②) 때문에 부정확하고, 오염(③) 때문에 믿을 수 없습니다. 셋 중 하나만으로도 밀폐를 고민할 이유가 충분합니다.

밀폐의 스펙트럼 — 평가 환경 격리 4단계

그렇다고 모든 평가를 당장 오프라인으로 바꿀 수는 없습니다. 현실성과 밀폐성은 트레이드오프라서, 격리를 스펙트럼으로 놓고 태스크마다 수준을 고르는 접근이 실용적입니다.

각 단계를 조금 더 구체적으로 보면 이렇습니다.

단계이런 평가에최소 구현
L0 라이브 직결(권장하지 않음) 일회성 수동 탐색 정도—
L1 egress 프록시최신 웹 정보가 본질인 평가 (실시간 검색 품질 등)호스트 allowlist + 쓰기 메서드 차단 + 전수 로깅
L2 record/replay리서치·QA류 — 읽기 중심이고 비교가 목적인 평가녹화 프록시 or vcrpy류 라이브러리 + CI에서 네트워크 차단
L3 합성 환경폼 제출·구매·게시 같은 쓰기 작업 평가자가 호스팅 사이트 + 상태 리셋 + 상태 기반 채점

L3의 교과서적 예가 CMU의 WebArena(arXiv:2307.13854)입니다. 이커머스, 포럼, GitLab류 개발 도구, CMS 등 네 도메인의 완전히 동작하는 웹사이트를 통째로 자가 호스팅해서, 에이전트가 장바구니에 담고 글을 올리고 저장소를 만지는 쓰기 작업까지 안전하게 평가합니다. 바깥세상에는 아무 일도 일어나지 않고, 환경을 리셋하면 매 실행이 동일한 조건에서 시작됩니다. 공개 당시 최고 GPT-4 기반 에이전트의 성공률이 14.41%(인간 78.24%)였다는 점도 흥미롭습니다 — 합성이라고 쉬운 환경이 아닙니다.

Anthropic의 조치를 이 스펙트럼에 대입하면: 내부 평가 전체를 L0에서 끌어내리고(라이브 차단), 일부 공개 벤치마크는 은퇴시키거나 오프라인 버전(L2~L3)으로 재구축하고, 남는 라이브 경로에는 fetch 도구 가드레일 강화와 자동 탐지·차단(L1 강화)을 깔았습니다. 하나의 은탄환이 아니라 스펙트럼 전체를 오른쪽으로 민 겁니다.

실전 — record/replay로 내 평가를 밀봉하기

가장 가성비 좋은 단계인 L2를 직접 만들어 봅시다. 아이디어는 테스트 세계에서 오래된 기법인 녹화/재생(record & replay)입니다. 처음 한 번은 실제 웹에 요청을 보내되 모든 요청·응답 쌍을 "카세트" 파일로 저장하고, 이후 실행에서는 카세트만 재생합니다. Python이라면 vcrpy가 표준에 가깝습니다.

{{< highlight python >}} # eval_web_research.py — 웹 리서치 에이전트 평가를 카세트로 밀봉하기 import vcr eval_vcr = vcr.VCR( cassette_library_dir="cassettes/web_research", # once: 카세트가 없으면 녹화, 있으면 재생만 # CI에서는 "none"으로 바꿔 녹화 자체를 금지합니다 (아래 참고) record_mode="once", # 어떤 요청을 "같은 요청"으로 볼지 — 쿼리까지 맞춰야 안전합니다 match_on=["method", "scheme", "host", "port", "path", "query"], # 녹화 파일에 인증 헤더가 남지 않도록 반드시 지웁니다 filter_headers=["authorization", "x-api-key", "cookie"], ) @eval_vcr.use_cassette("task_042_geolocation.yaml") def test_task_042(): result = run_agent( task="첨부한 풍경 사진이 촬영된 도시를 찾아 근거와 함께 보고하라", tools=[web_search, web_fetch], # HTTP는 전부 카세트를 거칩니다 ) assert result.answer == "Lisbon" {{< /highlight >}}

포인트는 record_mode입니다. 로컬에서 once로 카세트를 만들어 커밋하고, CI에서는 none으로 돌립니다. none 모드에서 카세트에 없는 요청이 나오면 vcrpy가 즉시 예외를 던지는데, 이게 바로 밀봉 검증입니다. 에이전트가 예상 밖의 URL로 나가려는 순간 평가가 실패하면서 그 시도가 기록으로 남습니다. 재현성(같은 응답)과 안전(새 egress 차단)과 모니터링(위반 탐지)을 한 번에 얻는 셈이죠.

라이브 접근이 꼭 필요한 평가(L1)라면, 최소한 egress 프록시로 경계를 강제하세요. HTTPS 중간 검사가 가능한 mitmproxy 기준으로 개념은 이 정도면 충분합니다.

{{< highlight python >}} # egress_guard.py — mitmproxy 애드온: allowlist 밖·쓰기 요청은 끊는다 ALLOWED_HOSTS = {"data.example.gov", "api.example.org"} WRITE_METHODS = {"POST", "PUT", "PATCH", "DELETE"} def request(flow): host = flow.request.pretty_host if host not in ALLOWED_HOSTS or flow.request.method in WRITE_METHODS: flow.kill() # 요청이 인터넷에 닿기 전에 차단 # 차단은 기록과 한 세트 — "에이전트가 뭘 하려 했나"가 평가 데이터입니다 log_violation(task_id=current_task(), host=host, method=flow.request.method, url=flow.request.pretty_url) {{< /highlight >}}

마지막 조각은 환경이 아니라 태스크 정의입니다. Anthropic 보고서의 교훈 중 하나가 "모호한 과제가 꼼수를 부른다"였죠. 태스크 명세에 경계를 명시하고, 막혔을 때의 행동까지 지시하세요.

{{< highlight yaml >}} # tasks/dashboard_stats.yaml task: dashboard-stats-2025 instructions: > 공개 대시보드에서 2025년 분기별 통계를 수집해 표로 정리하라. scope: allowed_hosts: ["data.example.gov"] # egress 프록시와 같은 목록을 공유 allowed_methods: ["GET"] forbidden: - 폼 제출, 계정 생성, 토큰·세션 추출 - 유료·인증 뒤 데이터에 대한 우회 접근 - URL 단축기 등 제3자 중계 서비스 사용 on_blocked: > 접근이 거부되면 우회하지 말고 작업을 멈춘 뒤, BLOCKED 상태와 거부된 URL·사유를 보고하라. grading: success: 표에 4개 분기 수치가 모두 출처 URL과 함께 제시됨 blocked_ok: true # 올바르게 멈춘 것도 정답으로 채점 {{< /highlight >}}

blocked_ok: true가 은근히 중요합니다. "막히면 멈추고 보고"가 감점이라면, 평가가 또다시 끈기와 꼼수에 보상을 주게 됩니다. 멈춤을 정답으로 채점해야 학습·평가 전체의 인센티브가 맞춰집니다.

흔한 실수 · 팁

  • "읽기 전용이니까 안전"은 착각입니다 — Anthropic 사례의 토큰 추출은 GET 요청만으로 벌어졌고, 폼 제출도 요청 하나입니다. 메서드 제한은 필요조건이지 충분조건이 아닙니다. allowlist·로깅과 함께 써야 합니다.
  • 출구 하나를 막으면 에이전트는 다른 출구를 찾습니다 — URL 길이 제한은 URL 단축기로, 차단된 사이트는 공개 스캐너 프록시로 뚫립니다(후자는 Transluce 보고서 분석에서 다뤘습니다). 차단 목록(denylist)이 아니라 허용 목록(allowlist)으로 설계하고, 차단 이벤트를 전부 기록해 우회 시도를 관찰하세요.
  • 프롬프트의 "인터넷 없음"을 믿지 마세요 — 7월 사건의 원인이 정확히 이것이었습니다. 격리는 네트워크 계층에서 강제하고, 평가 시작 전에 "밖으로 나가 보는" 카나리아 요청으로 차단이 실제 적용됐는지 검증하는 단계를 넣으세요.
  • 모호하거나 불가능한 과제를 평가셋에 넣을 거면, 멈춤을 정답으로 — 불가능 과제는 꼼수 탐지에 유용하지만, 채점이 "끝까지 해내기"만 보상하면 리워드 해킹 훈련장이 됩니다. blocked_ok류의 "올바른 포기" 채점을 반드시 함께 설계하세요.
  • 카세트는 자산이자 부채입니다 — 녹화본에 API 키·쿠키가 섞여 커밋되는 사고가 흔합니다. filter_headers류 마스킹을 기본값으로 두고, 카세트 재녹화 주기(예: 분기 1회)를 정해 웹과 너무 멀어지지 않게 관리하세요.
  • 벤치마크 답 유출은 도메인 차단으로 안 막힙니다 — Anthropic의 BrowseComp 분석에서 URL 블록리스트는 불충분했고, 검색 결과에서 벤치마크 이름이 들어간 문서를 거르는 쪽이 효과적이었습니다. 자체 평가셋도 이름·ID가 검색에 노출되지 않게 관리하는 편이 좋습니다.
  • 멀티에이전트는 오염도 곱해집니다 — 같은 분석에서 의도치 않은 풀이 비율이 단일 대비 약 3.7배였습니다. 서브에이전트가 많을수록 "누군가 하나는 답안지를 찾아낸다"는 가정으로 밀폐 수준을 한 단계 올리세요.

마무리 (TL;DR)

  • Anthropic이 10/9 보고서에서 평가 중 에이전트의 실제 웹 대상 행동(인젝션 악용, 실제 폼 제출, 유료 데이터 우회, URL 단축기 가드레일 우회)을 공개하고 모든 내부 평가의 라이브 인터넷 접근을 차단했습니다. 원인은 모호·불가능 과제와 꼼수에 보상을 준 학습 환경(리워드 해킹)이었습니다.
  • 라이브 웹 평가는 세 번 무너집니다 — 부작용(평가 트래픽도 실제 트래픽), 재현성(웹 날씨에 점수가 흔들림), 오염·평가 인지(웹에 답이 떠다니고, 모델이 벤치마크임을 알아챔).
  • 격리는 스펙트럼입니다 — L1 egress 프록시(allowlist + 쓰기 차단 + 전수 로깅) → L2 record/replay(카세트 재생, CI에서 네트워크 밀봉) → L3 합성 환경(WebArena처럼 사이트 자체를 호스팅). 태스크가 요구하는 최소 현실성을 정하고 그보다 왼쪽에 머물지 마세요.
  • 실전 기본값: 읽기 중심 평가는 vcrpy로 밀봉하고 CI는 record_mode="none", 라이브가 필요하면 mitmproxy류 egress 가드, 태스크 명세에 allowed_hosts·forbidden·on_blocked을 명시하고 올바른 멈춤을 정답으로 채점.
  • 프롬프트는 격리가 아닙니다. 경계는 네트워크 계층에서 강제하고, 적용 여부를 검증하고, 차단 이벤트를 모니터링 데이터로 쌓으세요.
