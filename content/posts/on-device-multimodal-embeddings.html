도입 — 이번 주 임베딩이 다시 화제가 된 이유

10월 6일 Google DeepMind가 EmbeddingGemma 2를 공개했습니다. 텍스트·코드·이미지·영상·오디오 — 다섯 가지 입력을 전부 하나의 768차원 벡터 공간에 넣는 740M 파라미터 임베딩 모델입니다. 라이선스는 Apache 2.0, 가중치는 Hugging Face와 Kaggle에서 바로 받을 수 있고, 양자화하면 Pixel급 폰에서 0.5GB 남짓의 RAM으로 돌아갑니다.

이번 주 LLM 쪽에는 Gemini 4 Argon, Mistral Large 4, Claude Haiku 5.5 같은 굵직한 릴리스가 몰렸는데, 그 틈에서 임베딩 모델 하나가 HN 프런트페이지에 오른 건 이유가 있습니다. 댓글 분위기를 요약하면 두 가지였습니다. 하나는 "쓸 만한 중간 크기 임베딩 모델이 드디어 나왔다"는 실무자들의 반가움이고(Apache 2.0이라는 점을 콕 짚은 Simon Willison의 댓글이 최상단이었습니다), 다른 하나는 "이걸로 로컬 멀티모달 검색을 만들면 되겠다"는 기대였습니다. 실제로 같은 주에 macOS의 모든 사진·영상 프레임을 로컬에서 AI 검색하는 도구(SCM)가 나란히 트렌딩됐으니, 수요가 모여 있던 자리에 부품이 도착한 셈입니다.

이 글은 EmbeddingGemma 2를 소재로 온디바이스 멀티모달 임베딩 엔지니어링을 처음부터 정리하는 글입니다. 임베딩 모델이 뭘 하는 물건인지부터 시작해서, "모달리티별 인코더를 떼었다 붙였다 하는" 모듈러 아키텍처, 벡터를 잘라 쓰는 마트료시카 표현 학습(MRL, Matryoshka Representation Learning), 벤치마크 숫자를 어디까지 믿어야 하는지, 그리고 여러분 노트북에서 바로 돌려보는 코드까지 순서대로 갑니다.

배경 — 임베딩 모델은 뭘 하는 물건인가

임베딩(embedding)은 데이터를 의미를 보존하는 숫자 벡터로 바꾼 것입니다. 임베딩 모델에 "고양이가 소파에서 잔다"를 넣으면 768개의 실수가 나오고, "낮잠 자는 반려묘"를 넣으면 또 다른 768개가 나옵니다. 포인트는 의미가 비슷한 입력일수록 벡터가 가깝다는 것입니다. 두 벡터의 코사인 유사도를 계산하면 "이 두 문장이 얼마나 비슷한 얘기인가"를 숫자 하나로 얻습니다.

이 성질 하나로 검색이 만들어집니다. 문서(사진, 음성 메모, 코드 조각...)를 미리 전부 임베딩해 벡터 DB에 넣어 두고, 질문이 들어오면 질문도 임베딩한 뒤 가장 가까운 벡터를 찾으면 끝입니다. RAG의 retrieval이 바로 이것이고, 추천·중복 제거·분류·클러스터링도 같은 부품 위에 올라갑니다. 생성 모델이 "말하는 쪽"이라면 임베딩 모델은 "찾는 쪽"의 바탕입니다. 청킹 전략이나 2단계 검색 같은 윗단 설계는 예전 글(RAG 청킹, 리랭킹과 2단계 검색)에서 다뤘으니, 이 글은 그 아래층 — 임베딩 모델 자체에 집중합니다.

그럼 왜 "온디바이스"가 중요할까요? 지금까지 좋은 임베딩은 대부분 API 호출이었습니다(OpenAI text-embedding, Gemini Embedding, Cohere embed...). API 방식에는 엔지니어링 관점의 비용이 셋 붙습니다.

  • 데이터가 밖으로 나갑니다. 사용자의 사진·일기·사내 문서를 전부 서버로 보내야 인덱싱이 됩니다. 프라이버시가 중요한 제품에서는 이 지점에서 설계가 막힙니다.
  • 벡터가 벤더에 묶입니다. 임베딩은 모델이 다르면 서로 호환되지 않습니다. 벤더가 모델을 내리면(deprecate) 쌓아 둔 벡터 전체를 새 모델로 재임베딩해야 합니다. Willison이 HN에서 "독점·호스티드 전용 임베딩 모델은 나쁜 선택"이라고 쓴 이유가 이것입니다 — 가중치가 공개돼 있으면 최악의 경우 직접 서빙하면 되니까요.
  • 건당 비용과 왕복 지연이 쌓입니다. 검색은 타이핑할 때마다, 인덱싱은 파일마다 호출이 나갑니다. 로컬 모델이면 둘 다 0원이고 오프라인에서도 동작합니다.

문제는 지금까지 "로컬에서 돌아갈 만큼 작으면서 쓸 만한" 임베딩 모델이 드물었다는 점입니다. 작년 9월의 1세대 EmbeddingGemma(308M, 텍스트 전용)가 그 틈을 처음 제대로 메웠고, 이번 2세대는 같은 자리에 멀티모달을 얹었습니다. 이제 "지난달에 찍은 영수증 사진"이라는 텍스트 질문으로 사진을 찾는 검색이 폰 안에서 완결됩니다.

해부 — 모듈러 아키텍처와 공유 벡터 공간

EmbeddingGemma 2의 740M이라는 숫자는 한 덩어리가 아닙니다. 구조는 레고에 가깝습니다.

  • 텍스트 코어 270M — Gemma 4 기반 백본. 텍스트와 코드를 처리하는 본체로, 이것만 로드하면 270M짜리 텍스트 임베딩 모델입니다.
  • 비전 인코더 +170M — 이미지·영상 프레임을 받아 코어에 연결합니다. 텍스트+비전으로 440M.
  • 오디오 인코더 +300M — 음성·소리를 받아 코어에 연결합니다. 텍스트+오디오로 570M, 전부 합치면 740M.

핵심은 어떤 조합으로 로드하든 출력이 같은 768차원 공간에 떨어진다는 점입니다. 사진을 넣은 벡터와 문장을 넣은 벡터를 바로 코사인 유사도로 비교할 수 있습니다. 교차 모달(cross-modal) 검색 — 글로 사진 찾기, 글로 음성 메모 찾기 — 이 별도 변환 없이 되는 이유입니다.

이 설계가 엔지니어링 관점에서 반가운 이유는 메모리를 쓰는 만큼만 낸다는 점입니다. 텍스트 검색만 필요한 앱이 오디오 인코더 300M까지 로드할 이유가 없죠. 뒤의 실전 섹션에서 보겠지만, config_kwargs로 안 쓰는 인코더를 끄면 같은 모델 이름으로 270M만 올라갑니다.

컨텍스트 윈도우는 8,192토큰으로, 1세대(2K)의 4배입니다. Google 발표 기준으로 이미지 약 29장, 영상 프레임 58장, 오디오 약 5.5분 분량을 한 번에 넣을 수 있는 길이입니다. 지원 언어는 100개 이상이고(언어별 품질 편차는 있습니다 — 뒤에서 다시), 영상은 별도 인코더가 아니라 프레임을 비전 인코더로 처리하는 방식입니다.

이름 주의: 비슷한 시기에 나온 Gemini Embedding 2는 다른 물건입니다. 그쪽은 Gemini 기반의 호스티드 API 멀티모달 임베딩이고, EmbeddingGemma 2는 가중치를 받아 직접 돌리는 오픈 모델입니다. 품질 상한은 호스티드 쪽이 높지만, 이 글에서 다루는 온디바이스의 장점(프라이버시·비용·오프라인·벤더 독립)은 오픈 쪽에만 있습니다.

MRL — 벡터를 마트료시카처럼 잘라 쓰기

온디바이스 검색의 숨은 비용은 모델이 아니라 벡터 저장소입니다. 사진 10만 장을 768차원 float32로 임베딩하면 10만 × 768 × 4바이트 ≈ 300MB. 폰에서는 부담스러운 크기이고, 검색 시 거리 계산량도 차원에 비례해 늘어납니다.

마트료시카 표현 학습(MRL)은 이 문제를 학습 단계에서 풉니다. 훈련할 때 "768차원 전체로도, 앞 512개만으로도, 앞 256개만으로도, 앞 128개만으로도 좋은 임베딩이 되도록" 손실을 동시에 겁니다. 그 결과 벡터의 앞쪽 차원에 중요한 의미가 농축되고, 러시아 인형처럼 뒤를 잘라내도 작동하는 벡터가 나옵니다. 잘라낸 뒤 다시 정규화(normalize)만 해 주면 됩니다.

Google 가이드 기준으로 256차원에서 텍스트·코드 품질은 대부분, 이미지·영상·음성 검색 품질은 약 95%가 유지됩니다. 저장소는 3분의 1로 줄죠. 예전에 다룬 임베딩 양자화와는 직교하는 기법이라 겹쳐 쓸 수 있습니다 — 차원을 256으로 줄이고 int8로 양자화하면 float32 768차원 대비 저장소가 12분의 1이 됩니다. 온디바이스에서는 이 둘의 조합이 사실상 기본기입니다.

숫자 읽기 — 벤치마크와 메모리의 행간

모델 카드의 주요 숫자를 1세대와 비교하면 이렇습니다(768차원, full precision 기준).

이 표에서 읽을 행간이 세 가지 있습니다.

첫째, 텍스트 품질은 제자리걸음입니다. 61.15 → 61.36은 오차 수준입니다. Hugging Face 토론에서도 "V2 = V1 + 멀티모달"이라는 정리가 나왔죠. 이미 1세대로 텍스트 검색을 잘 쓰고 있다면, 멀티모달이나 8K 컨텍스트가 필요하지 않은 한 전량 재임베딩을 감수하며 갈아탈 이유는 약합니다.

둘째, 진짜 상승은 코드와 멀티모달입니다. 코드 검색은 68.76 → 78.68로 10점 가까이 뛰었습니다. 로컬 코드베이스 검색(코딩 에이전트의 코드 검색에서 다룬 그 문제)에 쓸 만한 오픈 모델이 생긴 셈입니다. 멀티모달 점수들은 비교 대상인 1세대가 없는 신설 항목이고, Google은 "10억 파라미터 미만 멀티모달 임베더 중 최고, 두 배 큰 전문 모델도 일부 능가"라고 주장합니다 — 다만 발표문과 모델 카드 어디에도 어떤 모델과 비교했는지가 없습니다. 벤더 주장은 자기 워크로드로 검증하기 전까지는 참고 숫자로 두세요. 실제로 HN에는 Google 문서의 분류 예제를 로컬에서 돌렸더니 결과가 좋지 않았다는 보고도 올라왔습니다.

셋째, 메모리 숫자에는 조건이 붙어 있습니다. 191MB/567MB는 "양자화된 가중치, Pixel 11 Pro" 기준입니다. float32로 풀 모델을 로드하면 가중치만 ~3GB입니다. 노트북에서 bfloat16으로 돌리면 그 절반 수준이고요. "0.5GB로 돌아간다"는 헤드라인은 양자화 빌드(GGUF, LiteRT) 기준이라는 걸 기억하세요. 배포 경로는 1세대처럼 넓습니다 — sentence-transformers, llama.cpp GGUF, Ollama, LiteRT가 출시일부터 지원됩니다.

실전 — sentence-transformers로 돌려보기

노트북에서 바로 해 볼 수 있는 코드입니다. 멀티모달 입력을 쓰려면 sentence-transformers 6.1.0 이상이 필요합니다.

{{< highlight bash >}} # 멀티모달 extras 포함 설치 (텍스트만 쓸 거면 extras 생략 가능) pip install "sentence-transformers[image,audio,video]>=6.1.0" {{< /highlight >}}

먼저 기본인 텍스트 검색입니다. 한 가지 주의 — 임베딩 모델은 질문과 문서에 서로 다른 프롬프트를 붙여 학습됩니다. EmbeddingGemma 2에서는 prompt_name으로 지정합니다.

{{< highlight python >}} from sentence_transformers import SentenceTransformer model = SentenceTransformer("google/embeddinggemma-2") query = "지난달 카페에서 쓴 돈 영수증" docs = [ "2026-09-14 스타벅스 역삼점 아메리카노 외 2건 13,500원", "9월 전기요금 고지서 — 납부 기한 10월 5일", "회의록: 4분기 검색 기능 개선 킥오프", ] # 질문은 SearchQuery, 문서는 Document 프롬프트 — 바꿔 끼우면 품질이 떨어집니다 q_emb = model.encode(query, prompt_name="SearchQuery") d_emb = model.encode(docs, prompt_name="Document") scores = model.similarity(q_emb, d_emb) # 코사인 유사도 print(scores) # 첫 번째 문서가 가장 높게 나와야 정상 {{< /highlight >}}

다음은 이 모델의 본론인 교차 모달 검색입니다. 이미지를 임베딩해 두면 텍스트 질문으로 바로 찾을 수 있습니다.

{{< highlight python >}} from PIL import Image # 인덱싱 타임: 사진을 임베딩해 로컬 벡터 DB에 저장 photos = [Image.open(p) for p in ["receipt_0914.jpg", "cat.jpg", "whiteboard.jpg"]] photo_embs = model.encode(photos) # 이미지는 비전 인코더를 거쳐 같은 공간으로 # 쿼리 타임: 텍스트 질문 → 같은 768차원 공간에서 최근접 탐색 q = model.encode("카페 영수증 사진", prompt_name="SearchQuery") print(model.similarity(q, photo_embs)) # 모달리티가 달라도 그냥 비교하면 됩니다 {{< /highlight >}}

마지막으로 메모리와 저장소를 조이는 운영 설정입니다.

{{< highlight python >}} # 1) 텍스트 검색만 필요하면 안 쓰는 인코더를 끄고 로드 — 740M 대신 270M만 올라감 model = SentenceTransformer( "google/embeddinggemma-2", config_kwargs={"vision_config": None, "audio_config": None}, ) # 2) MRL: 256차원으로 잘라 저장소 1/3 — 인덱스 전체가 같은 차원을 써야 합니다 model = SentenceTransformer("google/embeddinggemma-2", truncate_dim=256) # 3) GPU가 있으면 bfloat16으로 가중치 메모리 절반 model = SentenceTransformer( "google/embeddinggemma-2", model_kwargs={"torch_dtype": "bfloat16"}, ) {{< /highlight >}}

이 부품으로 만들 수 있는 로컬 검색 파이프라인의 전체 모양은 이렇습니다.

인덱스를 RAG로 확장하는 것도 어렵지 않습니다. 검색 결과를 로컬 LLM(로컬 에이전트 추론에서 다룬 Ollama·Magnitude 같은 스택)에 컨텍스트로 넣으면 완전 오프라인 RAG가 됩니다. 임베딩 모델은 "찾기"까지만 책임진다는 것, 답을 생성하는 건 별도 모델의 일이라는 역할 분담만 기억하세요.

흔한 실수 · 팁

  • 쿼리/문서 프롬프트를 빼먹지 마세요. 가장 흔한 품질 사고입니다. prompt_name="SearchQuery"와 "Document"는 장식이 아니라 모델이 그렇게 학습된 입력 형식입니다. 둘 다 생략하거나 바꿔 끼우면 검색 품질이 조용히 떨어집니다 — 에러가 안 나니 더 위험합니다.
  • 인덱스의 차원과 모델 설정을 하나로 고정하세요. MRL로 256차원 인덱스를 만들었다면 쿼리도 256차원으로 잘라야 합니다. 768차원 쿼리 벡터로 256차원 인덱스를 검색하면 차원 불일치로 터지거나(운이 좋은 경우), 코드가 앞 256개만 쓰면서 조용히 잘못된 결과를 줍니다. 모델 이름·차원·프롬프트를 인덱스 메타데이터로 함께 저장해 두는 게 기본기입니다.
  • 1세대 벡터와 섞지 마세요. EmbeddingGemma 1로 만든 벡터와 2로 만든 벡터는 호환되지 않습니다. 같은 768차원이어도 공간이 다릅니다. 갈아탈 거면 전량 재임베딩이고, 그래서 인덱스에 버전을 달아 두는 습관이 중요합니다. 이 비용 때문에 "텍스트 품질이 제자리면 굳이 안 갈아탄다"는 판단도 합리적입니다.
  • 128차원은 텍스트 전용이라고 생각하세요. 256까지는 멀티모달 품질이 약 95% 유지되지만 128에서는 급락합니다. 사진·오디오 검색이 섞인 인덱스라면 256을 하한으로 잡는 게 안전합니다.
  • 벤더 벤치마크는 자기 데이터로 재검증하세요. "두 배 큰 모델도 능가"는 비교 대상이 공개되지 않은 주장이고, 실제로 공식 예제가 로컬에서 재현되지 않았다는 보고도 있었습니다. 여러분의 문서·사진 몇백 개로 작은 검색 평가셋을 만들어 recall@k를 직접 재는 것이 반나절 투자로 가장 확실합니다.
  • 한국어 품질은 별도로 확인하세요. 100개 이상 언어를 지원하지만 Google 스스로 언어별 편차가 있다고 밝혔습니다. 한국어 중심 서비스라면 다국어 평균 점수(61.36)가 아니라 한국어 샘플로 직접 확인한 뒤 결정하세요.
  • 용도가 텍스트뿐이면 270M 구성으로 시작하세요. config_kwargs로 비전·오디오 인코더를 끄면 로드 시간과 메모리가 크게 줄어듭니다. 멀티모달이 필요해지는 시점에 설정만 바꾸면 되고, 텍스트 벡터 공간은 동일하므로 기존 인덱스를 버릴 필요가 없습니다.
  • 안전성 튜닝이 없는 모델임을 감안하세요. 임베딩 모델이라 생성형 리스크는 작지만, 검색 결과의 필터링·권한 처리는 애플리케이션 몫입니다.

마무리 (TL;DR)

  • 10월 6일 Google이 EmbeddingGemma 2를 Apache 2.0으로 공개 — 텍스트·코드·이미지·영상·오디오를 하나의 768차원 공간에 넣는 오픈 멀티모달 임베딩 모델입니다. 양자화 기준 폰에서 ~191MB(텍스트만)/~567MB(풀)로 돌아갑니다.
  • 구조는 모듈러입니다. 270M 텍스트 코어에 비전(+170M)·오디오(+300M) 인코더를 필요한 만큼만 붙이고, 어떤 조합이든 같은 공간으로 출력하므로 텍스트 질문으로 사진·음성을 찾는 교차 모달 검색이 그냥 됩니다.
  • MRL로 벡터를 768→512/256/128차원으로 잘라 저장소를 최대 6배 아낄 수 있습니다. 256이 스위트 스팟이고, 멀티모달 인덱스에서 128은 피하세요. 임베딩 양자화와 겹쳐 쓸 수 있습니다.
  • 숫자의 행간: 텍스트 품질은 1세대와 사실상 동일(61.15→61.36), 진짜 상승은 코드(68.76→78.68)와 멀티모달 신설입니다. "두 배 큰 모델 능가"는 비교 대상 미공개의 벤더 주장이니 자기 데이터로 recall@k를 재고 결정하세요.
  • 실전 수칙: 쿼리/문서 프롬프트 구분, 인덱스와 쿼리의 차원·모델 버전 고정, 1세대 벡터와 혼용 금지, 한국어 품질 별도 검증. 텍스트만 쓰면 config_kwargs로 270M 구성이 기본값입니다.
