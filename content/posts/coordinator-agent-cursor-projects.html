1. 도입 — 에이전트한테 같은 걸 몇 번이나 가르치고 계신가요

코딩 에이전트를 매일 쓰다 보면 이상한 반복이 생깁니다. 태스크마다 채팅을 새로 열고, 매번 같은 설명을 다시 합니다. "테스트는 pnpm test:unit으로 돌려", "이 레포는 서비스 레이어에서만 DB를 만져", "스타일은 이 컨벤션 따라". 어제 에이전트가 힘들게 알아낸 사실을 오늘의 에이전트는 모릅니다. 세션이 끝나면 컨텍스트가 통째로 버려지니까요. 에이전트는 매번 콜드 스타트(cold start)입니다.

9월 10일, Cursor가 이 문제를 정면으로 겨눈 기능을 내놨습니다. Projects입니다. 태스크마다 채팅을 여는 대신, 일이 끝날 때까지 — 며칠이든 몇 달이든 — 열려 있는 스레드 하나에서 코디네이터(coordinator) 에이전트와 대화합니다. 재미있는 건 이 코디네이터가 코드를 한 줄도 쓰지 않는다는 점입니다. 계획을 세우고, 실제 구현은 워커 에이전트들에게 나눠 주고, 끝난 일을 모아서 사람에게 가져오는 게 전부입니다. 그리고 에이전트들이 일하며 배운 것을 공유 컨텍스트 파일에 남겨, 다음 에이전트가 이어받게 합니다.

발표 직후 한 주 내내 이 설계가 화제였습니다. "코디네이터 하나가 수천 개의 서브에이전트를 지휘한다"는 헤드라인이 돌았고, "새 사용자는 PR을 30% 더 머지하고, Projects를 주로 쓰는 사용자는 6배 머지한다"는 Cursor의 자체 수치를 두고 갑론을박이 이어졌습니다. 지난주 OpenAI가 Agents API로 관리형 하네스를 상품화한 데 이어, 이번에는 그 위층 — 에이전트를 지휘하는 층 — 이 제품이 된 셈입니다.

이 글은 Cursor 홍보가 아닙니다. 코디네이터 패턴이 정확히 어떤 문제를 푸는지, 몇 달짜리 컨텍스트가 어떻게 유지되는지, 그리고 "6배"라는 숫자를 엔지니어답게 읽는 법까지 — 마지막에는 git worktree와 마크다운 파일 두 개로 미니 코디네이터를 직접 만들어 봅니다.

2. 배경 — 채팅 → 클라우드 에이전트 → 서브에이전트, 그리고 남은 문제

Projects가 왜 나왔는지 이해하려면 코딩 에이전트 UX가 밟아 온 단계를 보면 됩니다.

  • 1단계: 태스크당 채팅 하나. 에이전트 모드가 생긴 이래 기본 UX입니다. 문제는 위에서 말한 콜드 스타트. 세션이 곧 수명이라, 세션이 끝나면 배운 것도 사라집니다.
  • 2단계: 클라우드/백그라운드 에이전트. 실행을 클라우드로 옮겨 노트북을 덮어도 일이 계속되게 했습니다. 올해 6월 Pragmatic Engineer가 OpenAI·Anthropic·Cursor를 방문하고 쓴 글에서도 세 회사 모두 클라우드 에이전트에 올인하고 있다고 전했죠. 하지만 에이전트 하나하나는 여전히 서로를 모릅니다.
  • 3단계: 서브에이전트. Cursor는 2.4 버전에서 Subagents를 넣었습니다. 부모 에이전트의 태스크를 쪼개 각자 독립된 컨텍스트로 병렬 실행하는 구조입니다. 컨텍스트를 나누면 왜 좋은지는 컨텍스트가 적을수록 에이전트가 낫다 편에서 다뤘습니다. 그런데 부모 에이전트 자체가 여전히 채팅 세션에 묶여 있었습니다.

정리하면, 실행 위치(클라우드)와 병렬화(서브에이전트)는 풀렸는데 수명이 안 풀렸습니다. 마이그레이션처럼 "시작은 쉽고 끝내기는 어려운" 일 — 몇 주에 걸쳐 수백 개의 PR을 내야 하는 일 — 을 맡기려면, 세션보다 오래 사는 무언가가 필요합니다. Projects는 그 무언가를 프로젝트라는 단위로 만들고, 그 위에 상주하는 코디네이터를 앉힌 겁니다.

3. Cursor Projects 해부 — 코디네이터는 무엇을 하고, 무엇을 안 하나

공개된 내용을 기준으로 구조를 뜯어 보겠습니다. 큰 그림은 이렇습니다.

공식 발표 기준으로 확인되는 구성 요소는 다섯 가지입니다.

  • 코디네이터 에이전트 — 프로젝트당 하나. 코드베이스를 읽고 계획을 세우고, 워커 에이전트를 만들어 일을 나눠 줍니다. 필요한 만큼 병렬로 띄우고, 끝난 결과를 모아 사람에게 가져옵니다. 직접 코드를 쓰지 않으니 손이 비어 있고, 그래서 워커들이 일하는 동안에도 계속 계획하고 배분할 수 있습니다.
  • 전용 클라우드 머신 — 프로젝트는 자기 클라우드 컴퓨터에서 돕니다. 노트북을 덮어도 멈추지 않고, 노트북 사양과 무관하게 워커를 더 많이 병렬로 돌릴 수 있습니다.
  • 로컬 워커 — 내 머신에서만 확인할 수 있는 일(로컬 환경 의존 테스트 등)이 있으면 코디네이터가 로컬 에이전트를 띄워 처리합니다. 클라우드와 로컬이 섞인 하이브리드 실행이죠.
  • 공유 컨텍스트 파일 — 프로젝트마다 파일 묶음이 있고, 이 파일들이 프로젝트의 에이전트가 쓰는 모든 클라우드·로컬 머신에 동기화됩니다. 다음 절에서 자세히 봅니다.
  • 트리거 — 사람이 프롬프트를 치지 않아도 코디네이터가 움직입니다. Slack 채널을 감시하다 버그 리포트가 올라오면 워커에게 수정을 위임해 PR을 열고, 스케줄에 따라 반복 작업을 하고, 내 PR들을 팔로우하다 필요한 조치를 합니다.

대표 사용례로 Cursor가 미는 것이 마이그레이션입니다. 프레임워크 교체나 스타일링 시스템 전환처럼 패턴은 단순한데 범위가 넓은 일이요. 사람과 코디네이터가 먼저 안전한 접근 방식을 합의하고, 그다음 코디네이터가 그 방식을 코드베이스 전체에 점진적으로 적용합니다. Cursor는 사내에서 이런 식으로 수백 개의 PR에 걸친 전환 작업을 했다고 밝혔습니다. 초반에는 사람이 PR을 하나하나 꼼꼼히 보다가, 수정이 계속 믿을 만하면 점점 덜 보게 되는 — 발표문 스스로 "신뢰 곡선"이라 부르는 — 흐름을 전제로 한 설계입니다.

참고로 베타는 유료 플랜(월 $20부터) 전체에 순차 배포 중입니다. 코디네이터가 어떤 모델로 도는지는 공개 자료에서 확인되지 않았습니다.

4. 진짜 핵심 — 공유 컨텍스트 파일이라는 조직 기억

발표에서 가장 눈여겨볼 대목은 화려한 "수천 개 병렬 에이전트"가 아니라 수수한 파일 이야기입니다. 에이전트들은 일하면서 리서치 결과와 산출물, 그리고 코드베이스에 대해 배운 것과 사람이 선호하는 작업 방식을 프로젝트의 공유 파일에 남깁니다. 공식 예시가 딱 와닿습니다: 워커 하나가 어떤 서비스의 테스트 돌리는 법을 알아내면, 이후의 모든 에이전트가 그 방법을 물려받습니다.

이게 왜 중요할까요? 회사에 새로 온 사람을 떠올려 보세요. 온보딩 문서가 없는 팀은 신입이 올 때마다 선배가 같은 설명을 반복합니다. 온보딩 문서가 있는 팀은 신입이 문서를 읽고 시작하고, 새로 알게 된 함정을 문서에 추가합니다. 공유 컨텍스트 파일은 에이전트를 위한 온보딩 문서를 에이전트가 직접 쓰게 만든 것입니다. 채팅-퍼-태스크 시대의 지식은 세션과 함께 증발했지만, 프로젝트의 지식은 파일로 남아 복리로 쌓입니다.

눈치채셨겠지만 아이디어 자체가 새 발명품은 아닙니다. 저장소에 AGENTS.md를 두어 에이전트에게 레포 지식을 주입하는 관행은 AGENTS.md 편에서 다뤘고, 계획과 중간 산출물을 파일시스템에 내려놓는 딥 에이전트 패턴은 딥 에이전트 편에서 다뤘습니다. Projects가 한 일은 이 관행을 제품 기본값으로 만든 것입니다. 사람이 부지런히 AGENTS.md를 관리하지 않아도, 에이전트가 스스로 쓰고 스스로 읽는 순환이 프로젝트 단위로 돌아갑니다. "몇 달짜리 컨텍스트 유지"의 실체는 신비한 초장기 메모리가 아니라, 모델 밖 파일에 지식을 외재화하고 필요할 때 다시 읽는 것이라는 점 — 컨텍스트 엔지니어링의 오래된 정석이 그대로 적용된 셈입니다.

5. 실전 — git worktree로 미니 코디네이터 패턴 만들어 보기

Projects를 안 쓰더라도 코디네이터 패턴의 뼈대는 오늘 바로 흉내 낼 수 있습니다. 필요한 건 세 가지입니다: 워커별 독립 작업 공간(git worktree), 공유 학습 파일(LEARNINGS.md), 그리고 위임 루프를 도는 스크립트. 헤드리스 CLI 에이전트(여기서는 claude -p를 예로 들지만, 비슷한 헤드리스 모드가 있는 도구라면 무엇이든)면 충분합니다.

먼저 작업 공간을 준비합니다.

{{< highlight bash >}} # 워커마다 독립된 체크아웃을 준다 — 서로 파일을 밟지 않도록 git worktree add ../work-a feature/task-a git worktree add ../work-b feature/task-b # 프로젝트의 '기억'이 될 파일 (레포 루트에 커밋해 두면 팀 전체가 공유) cat > LEARNINGS.md <<'EOF' # 이 레포에서 일하는 에이전트를 위한 노트 - 테스트: `pnpm test:unit` (e2e는 CI에서만) - DB 접근은 services/ 레이어를 통해서만 EOF {{< /highlight >}}

다음은 코디네이터의 최소 루프입니다. 핵심은 두 줄입니다: 워커를 띄울 때 LEARNINGS.md를 읽게 하고, 끝날 때 새로 배운 것을 쓰게 하는 것.

{{< highlight bash >}} #!/usr/bin/env bash # mini-coordinator.sh — 태스크 목록을 워커들에게 나눠 주는 최소 코디네이터 set -euo pipefail TASKS=("로그인 폼 검증 버그 수정" "결제 모듈에 재시도 로직 추가") DIRS=("../work-a" "../work-b") for i in "${!TASKS[@]}"; do ( cd "${DIRS[$i]}" # 워커 프롬프트: 공유 노트를 먼저 읽고, 끝나면 노트를 갱신하게 한다 claude -p "먼저 LEARNINGS.md를 읽고 그 규칙을 따라라. 태스크: ${TASKS[$i]} 완료 조건: 테스트 통과 + 커밋. 작업 중 새로 알게 된 사실(빌드/테스트 방법, 함정)이 있으면 LEARNINGS.md 끝에 한 줄씩 추가하라." \ --allowedTools "Edit,Bash(git *),Bash(pnpm *)" ) & # & 로 병렬 실행 — 워커들은 서로 다른 worktree라 충돌하지 않는다 done wait # 코디네이터의 '검수' 단계: 결과를 모아 사람이 볼 요약을 만든다 for d in "${DIRS[@]}"; do echo "== $d =="; git -C "$d" log --oneline -3; git -C "$d" diff --stat HEAD~1 2>/dev/null | tail -1 done {{< /highlight >}}

장난감 수준이지만, Projects가 하는 일의 골격이 그대로 들어 있습니다. 계획(태스크 목록) → 격리 위임(worktree + 병렬 워커) → 지식 누적(LEARNINGS.md 읽기/쓰기) → 검수(요약을 사람에게). 여기서 실제 제품과의 격차가 무엇인지도 명확해집니다. Projects는 이 루프를 클라우드에 상주시키고(내가 자리를 떠도 돎), 트리거로 깨우고(Slack·스케줄·PR), 컨텍스트 파일을 모든 머신에 동기화합니다. 반대로 말하면, 그 세 가지가 필요 없는 규모의 일이라면 위 스크립트로도 코디네이터 패턴의 이득 대부분을 챙길 수 있습니다.

병렬 워커 몇 개가 좋은지 감이 없다면 작게 시작하세요. 검증 병목 편에서 다뤘듯, 생성 속도는 병렬로 늘어나지만 검증(리뷰) 속도는 사람 수에 묶여 있습니다. 워커 수는 "내가 하루에 성의 있게 리뷰할 수 있는 PR 수"에 맞추는 게 현실적인 상한입니다.

6. 숫자 읽기 · 흔한 실수 · 팁

이제 화제가 된 숫자를 봅시다. Cursor는 "Projects를 새로 쓰는 사용자는 PR을 30% 더 머지하고, 주로 Projects로 일하는 사용자는 6배 머지한다"고 발표했습니다. 이 숫자를 읽을 때 주의할 점이 세 가지 있습니다.

  • 베이스라인이 없습니다. AI Weekly가 지적했듯 비교 기준·코호트 크기·측정 기간이 공개되지 않았습니다. 벤더 자체 보고 수치는 언제나 "자체 보고"라는 딱지를 붙여 읽어야 합니다.
  • 셀렉션 바이어스가 있습니다. "주로 Projects로 일하는 사용자"는 애초에 에이전트 위임이 잘 먹히는 작업(마이그레이션 같은 반복 작업)을 하는 사람일 가능성이 높습니다. 6배가 도구의 효과인지 사용자·작업의 특성인지 이 데이터로는 구분할 수 없습니다.
  • 머지된 PR 수는 산출량 지표지 가치 지표가 아닙니다. PR이 6배가 되면 좋은 일이 6배가 아니라, 우선 리뷰할 것이 6배가 됩니다.

실제로 써 볼 때 junior가 밟기 쉬운 함정들입니다.

  • 스펜드 리밋 없이 트리거부터 켜기. 코디네이터의 클라우드 머신과 병렬 워커는 전부 과금 대상입니다. Slack 채널 감시 같은 트리거는 내가 안 볼 때도 토큰을 태웁니다. 지출 한도와 알림을 먼저 걸고, 트리거는 채널 하나·스케줄 하나처럼 좁게 시작하세요. 비용 구조 감각은 토큰 이코노믹스 편을 참고하세요.
  • 오염된 학습이 복제되는 것 방치하기. 공유 컨텍스트는 좋은 지식만 쌓지 않습니다. 워커 하나가 잘못 알아낸 사실("이 테스트는 원래 깨져 있으니 스킵")이 파일에 들어가면 이후 모든 워커가 물려받습니다. 콜드 스타트의 반대 급부는 오류의 복리입니다. 공유 파일도 코드처럼 주기적으로 리뷰하고, 이상 동작이 반복되면 컨텍스트 파일부터 의심하세요.
  • 신뢰 곡선을 건너뛰기. "수백 PR 마이그레이션" 사례의 전제는 초반 PR을 사람이 빡빡하게 검수해 접근 방식을 교정했다는 것입니다. 처음부터 자율 주행을 걸면, 잘못된 접근이 수백 PR로 복제된 뒤에 발견됩니다.
  • 격리 없이 병렬화하기. 직접 만들 때의 함정입니다. 워커들이 같은 체크아웃을 공유하면 서로의 변경을 밟습니다. worktree든 컨테이너든, 워커당 작업 공간 격리가 먼저입니다.
  • 코디네이터에게 구현까지 시키기. 계획자와 구현자를 한 컨텍스트에 섞으면 구현 디테일이 컨텍스트를 잠식해 계획 품질이 떨어집니다. 역할 분리는 컨텍스트 분리이기도 합니다.

7. 마무리 (TL;DR)

  • Cursor가 9월 10일 공개한 Projects는 태스크당 채팅 대신, 몇 달이고 열려 있는 프로젝트 스레드에서 코디네이터 에이전트와 일하는 구조입니다. 코디네이터는 코드를 쓰지 않고 계획·위임·검수만 합니다.
  • 프로젝트는 전용 클라우드 머신에서 상주 실행되고, Slack·스케줄·PR 팔로우 같은 트리거로 사람 없이도 움직입니다.
  • 진짜 핵심은 공유 컨텍스트 파일: 에이전트가 배운 것을 파일로 남겨 다음 에이전트가 물려받습니다. "몇 달짜리 컨텍스트"의 실체는 초장기 메모리가 아니라 지식의 파일 외재화입니다.
  • 코디네이터 패턴의 뼈대는 git worktree + 공유 LEARNINGS.md + 위임 루프로 오늘 바로 흉내 낼 수 있습니다. 제품이 더해 주는 것은 상주 실행·트리거·동기화입니다.
  • "PR 6배" 같은 수치는 베이스라인 미공개·셀렉션 바이어스를 감안해 읽고, 워커 수는 리뷰 용량에 맞추세요. 생성이 6배가 되면 병목은 검증으로 이동합니다.
  • 공유 컨텍스트는 지식만이 아니라 오류도 복리로 쌓습니다. 컨텍스트 파일도 코드처럼 리뷰하세요.
