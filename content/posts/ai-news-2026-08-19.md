# 🔥 오늘의 핵심

# 📚 주목 논문

## 1. StateM — 가중치 대신 런타임을 스케일링한다

- **저자**: Ziheng Qin, Yaxin Lu, Zhangyang Atlas Wang, Kai Wang (소속은 arXiv 메타데이터에 미표기)
- **arXiv**: [2608.15089](https://arxiv.org/abs/2608.15089) (cs.AI, 8/15 제출)
- **핵심 기여**: 장기 과제 에이전트의 실패 상당수는 "모델이 각 단계를 못 풀어서"가 아니라 **가변 상태를 놓치고, 이전 실행의 교훈을 재활성화하지 못하고, 아는 절차를 건너뛰고, 조기에 멈추기 때문**이라고 보고, 모델을 그대로 둔 채 실행 시스템만 키운다.
- **방법**: 지속되는 상태(durable state), 페이즈에 국한된 컨텍스트, **검사되는 상태 전이**, 복구 가능한 런북, 그리고 사람과 에이전트가 함께 열어볼 수 있는 **버전 관리되는 절차 규칙**으로 실행을 조직하는 에이전트 네이티브 런타임.
- **결과**: Terminal-Bench 2.1에서 GPT-5.5 xhigh를 **83.1 → 92.1**(GPT-5.6 Sol Ultra의 91.9보다 높음). 이 런북은 **수정 없이 GPT-5.6으로 이전**된다. GPT-5.6 Sol xhigh와 함께 쓰면 445회 시행에서 **raw accuracy 95.3%**, 89개 과제 전부를 최소 한 번은 성공. 고정 프로필로 GPT-5.6 Luna는 76.7 → 85.4. 같은 런타임·런북 구조로 **$38 미만**의 적응 비용을 들여 DeepSeek-V4 Flash를 82.7 → 88.1(공통 코어 88과제에서는 89.1)로 올렸다.
- **🛠 에이전트 빌더 시사점**: "성능이 부족하다 → 더 큰 모델"이라는 반사를 한 번 참아라. 같은 모델에서 **9포인트**를 실행 시스템만으로 회수했고, 비용은 38배 가까이 저렴했다. 특히 **사후분석 결과를 강제되는 사전조건으로 변환**하는 부분이 오늘 바로 흉내낼 수 있는 조각이다.
- **⚠️ 한계**: 저자들이 직접 밝히듯 구체적 규칙은 **실행 구조가 비슷한 과제끼리만** 일반화된다. BusinessBench에서 held-out 이득은 macro 0.55 / micro 1.34로 작았고, 메커니즘이 맞아떨어진 두 계열에서만 10.04포인트가 나왔다. 벤치 수치는 저자 자체 측정이다.
- 코드: 초록에 `github.com/henryqin1997/statem`으로 명시(오늘 세션에서는 GitHub 접근이 차단돼 star 수·활성도는 확인하지 못했다).

*세 모델 모두 가중치는 그대로다. 근거: arXiv 2608.15089 초록의 보고 수치. 자체 제작 차트.*

## 2. Agentic Transaction — 에이전트 실행에 ACID를 다시 정의하기

- **저자**: Zhaoyan Sun, Xiaoxiao Wang, Guoliang Li (소속은 arXiv 메타데이터에 미표기)
- **arXiv**: [2608.13900](https://arxiv.org/abs/2608.13900) (cs.DB 주 분류 / cs.AI, 8/14 제출)
- **핵심 기여**: 영속 환경을 다루는 에이전트가 겪는 문제가 트랜잭션 DB가 풀어온 문제와 같다고 보고, ACID를 **Semantic Atomicity / Consistency / Isolation / Durability** 네 가지 의미론적 보장으로 재해석한다.
- **방법**: 트랜잭션형 탐색–실행–검증 사이클, 트랜잭션형 스킬 허브, **confidence 발산 기반 검증**, 의미 의존성을 고려한 격리, 트랜잭션 인지 상태 관리로 데이터 에이전트를 구현했다.
- **결과**: 널리 쓰이는 벤치마크에서 **Claude Code를 포함한 기존 SOTA 대비 10.6% 개선**.
- **🛠 에이전트 빌더 시사점**: 에이전트가 파일·DB·워크스페이스를 건드리는 순간 "실패하면 반쯤 망가진 상태가 남는다"가 최대 리스크다. 검증 단계를 통과해야 커밋하고, 실패하면 되감는 구조는 프레임워크 없이도 오늘 손으로 넣을 수 있다.
- **⚠️ 한계**: 실증은 데이터 에이전트 한 종류에 대한 것이고, 10.6%의 벤치마크 구성과 비교 조건은 초록만으로는 판단하기 어렵다.

![Agentic Transaction 사이클 — 탐색·실행·검증과 커밋/롤백 분기, ACID 4보장](/images/ai-news-2026-08-19/acid-agent-flow.svg)
*박스 안 문구는 논문의 구조 설명을 개발자 언어로 옮긴 자체 도식이다. 근거: arXiv 2608.13900.*

# 🧑‍💻 Codex & Claude Code 실전 팁

> 오늘은 두 CLI의 공식 changelog에 접근하지 못했다. 그래서 **오늘 검증한 논문에서 곧장 실행 가능한 형태로** 뽑았다.

### 🟦 Claude Code — Context / Workflow

- **출처**: [arXiv 2608.15089 (StateM)](https://arxiv.org/abs/2608.15089)
- **💡 핵심 아이디어**: `CLAUDE.md`에 "이렇게 해줘"라고 부탁하지 말고, **깨지면 즉시 멈추는 사전조건**으로 적어라. StateM의 이득은 교훈을 서술문이 아니라 강제되는 규칙으로 바꾼 데서 나왔다.
- **📝 구체적 방법**: 사후분석에서 나온 규칙 하나를 검사 스크립트로 만들고, 그 스크립트를 훅으로 건다.

```bash
# scripts/preflight.sh — 실패하면 종료코드 1
set -e
test -f .env.example || { echo "PRECOND: .env.example 없음"; exit 1; }
git diff --cached --name-only | grep -q '\.env$' && { echo "PRECOND: .env 스테이징 금지"; exit 1; }
exit 0
```

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "./scripts/preflight.sh" }]
      }
    ]
  }
}
```

- **🎯 언제 쓰나**: 같은 실수를 두 번 이상 본 순간. 세 번째부터는 프롬프트가 아니라 검사로 옮긴다.
- **⚠️ 주의**: 훅은 매 호출마다 돈다. 검사는 밀리초 단위로 끝나야 하고, 실패 메시지에 **어떻게 고치는지**까지 적어야 에이전트가 자력 복구한다.
- **⭐ 추천도**: 높음. 규칙 하나만 옮겨도 효과가 바로 보인다.

### 🟩 Codex — Eval / Workflow

- **출처**: [arXiv 2608.16798 (ClawGym II)](https://arxiv.org/abs/2608.16798)
- **💡 핵심 아이디어**: **같은 모델도 하니스가 다르면 이득이 다르다.** 이 논문에서 Qwen3-30A3B는 OpenClaw를 통해 Pass@1 **+9.98**, Claude Code를 통해 **+14.81**을 얻었다. 즉 Claude Code에서 잘 듣던 규칙을 Codex로 그대로 옮기고 "됐겠지"라고 넘기면 안 된다.
- **📝 구체적 방법**: 규칙을 포팅한 뒤, 같은 과제 셋을 두 하니스에서 각각 돌려 비교한다.

```bash
# tasks.txt 한 줄 = 과제 하나
while read -r task; do
  codex exec --skip-git-repo-check "$task" > "out/codex-$(md5sum <<<"$task" | cut -c1-8).log" 2>&1
done < tasks.txt

grep -lc "FAIL" out/codex-*.log | wc -l   # 실패 건수만 세기
```

- **🎯 언제 쓰나**: `AGENTS.md`나 스킬을 다른 툴에서 가져왔을 때, 그리고 CLI를 업그레이드한 직후.
- **⚠️ 주의**: 과제가 10개 미만이면 노이즈가 신호를 덮는다. 최소 20개, 그리고 같은 과제를 2~3회 반복해 분산까지 봐야 한다.
- **⭐ 추천도**: 중간~높음. 세팅 비용은 있지만 한 번 만들면 계속 쓴다.

### 🟪 공통 — Debugging / Workflow

- **출처**: [arXiv 2608.13900 (Agentic Transaction)](https://arxiv.org/abs/2608.13900)
- **💡 핵심 아이디어**: 상태를 바꾸는 툴 호출은 **실행 전에 되돌리는 방법을 먼저 기록**하라. 실패했을 때 "반쯤 적용된 상태"가 가장 비싸다.
- **📝 구체적 방법**: 실행 직전에 보상(compensation) 항목을 로그에 남기고, 검증 실패 시 역순으로 실행한다.

```python
journal = []

def apply(do, undo, label):
    journal.append((undo, label))   # 먼저 되돌릴 방법을 적는다
    return do()

def rollback():
    for undo, label in reversed(journal):
        print(f"compensate: {label}")
        undo()
    journal.clear()
```

- **🎯 언제 쓰나**: 에이전트가 파일 쓰기, 마이그레이션, 외부 API 쓰기처럼 되돌리기 어려운 작업을 여러 단계로 할 때.
- **⚠️ 주의**: 모든 작업이 되돌려지지는 않는다(메일 발송, 결제). 그런 호출은 보상 목록이 아니라 **커밋 직전 단계**로 미루는 게 맞다.
- **⭐ 추천도**: 높음. 프레임워크 없이 20줄로 시작할 수 있다.
