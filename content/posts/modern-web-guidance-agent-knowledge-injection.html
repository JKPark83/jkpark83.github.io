1. 도입 — "모달 하나 만들어 줘"의 결과물이 2019년산인 이유

코딩 에이전트에게 "삭제 확인 모달 하나 만들어 줘"라고 시켜 보세요. 꽤 높은 확률로 <div class="modal-overlay">가 돌아옵니다. role="dialog"와 aria-modal="true"를 손으로 달고, focus trap을 수십 줄 직접 구현하고, body에 overflow: hidden을 걸어 스크롤을 잠급니다. 브라우저에 네이티브 <dialog> 요소가 있고, 이 모든 걸 공짜로 처리해 준다는 사실은 모델도 "알고" 있는데 말입니다.

이 문제를 겨눈 프로젝트가 이번 주 화제였습니다. 11월 10일 Modern Web Guidance가 프리뷰를 끝내고 1.0으로 정식 공개됐고, 같은 날 "Get your coding agent off ~2019 JavaScript, onto modern web primitives"라는 제목의 Show HN이 400점 넘게 오르며 프런트페이지에 걸렸습니다. 다음 날 Chrome 공식 블로그 발표가 이어졌습니다. 눈여겨볼 대목은 관리 주체입니다. Google Chrome 팀 혼자가 아니라 Chrome·Microsoft Edge·Mozilla Firefox·MDN 팀이 공동 관리하는, 브라우저 벤더들이 한편에 선 보기 드문 프로젝트입니다. 저장소 스타는 글 쓰는 시점에 7,200개를 넘었습니다.

이 글이 웹 프런트엔드 글은 아닙니다. Modern Web Guidance가 흥미로운 진짜 이유는, "모델의 지식이 낡았을 때 최신 지식을 어떻게 공급하는가"라는 AI 엔지니어링의 보편 문제를 아주 잘 설계된 방식으로 풀었기 때문입니다. 설치되는 스킬은 약 205토큰에 불과하고, 실제 지식은 오프라인 CLI로 필요한 순간에만 컨텍스트에 들어옵니다. 어떤 설계인지, 숫자는 어떻게 읽어야 하는지, 내 도메인에는 어떻게 응용하는지 차례로 보겠습니다.

2. 배경 — 컷오프, 분포, 그리고 "아는 것"과 "꺼내 쓰는 것"

에이전트가 낡은 코드를 쓰는 데는 겹쳐진 이유가 셋 있습니다.

첫째, 지식 컷오프(knowledge cutoff)입니다. 모델의 가중치는 학습이 끝난 시점에 고정됩니다. 그 뒤에 나온 API는 가중치 안에 아예 없습니다. 웹 플랫폼은 특히 변화가 빨라서, 작년에 학습된 모델은 올해 Baseline에 들어온 기능을 모릅니다.

둘째, 컷오프보다 더 지독한 데이터 분포 문제입니다. 모델이 학습한 공개 코드의 압도적 다수는 오래된 패턴입니다. jQuery 모달, float 레이아웃, moment.js 날짜 처리가 수백만 번 반복되고, <dialog>·container query·View Transitions의 좋은 사용 예는 상대적으로 극소수입니다. 통계적 다수결로 답을 뽑는 모델에게 "가장 그럴듯한 모달 코드"는 여전히 2019년식입니다. 컷오프 이전에 존재한 기능이라도 마찬가지입니다.

셋째, "아는 것"과 "꺼내 쓰는 것"은 다릅니다. "popover API 알아?"라고 물으면 모델은 정확히 설명합니다. 하지만 실제 구현 과제를 주면 익숙한 옛 패턴으로 돌아갑니다. Modern Web Guidance 저장소도 이 점을 명시합니다 — 모델이 API의 존재를 알아도, 프로덕션 수준의 실제 사용 패턴(폴백, 접근성, 엣지 케이스)은 학습 데이터에 충분히 없다는 겁니다.

용어 하나만 챙기고 갑시다. Baseline은 주요 브라우저가 모두 지원하는 웹 기능을 표시하는 업계 공통 지표입니다. "Baseline: widely available"이면 폴백 없이 써도 안전하다는 뜻입니다. Modern Web Guidance의 가이드는 이 지표를 기준으로 "그냥 써라 / 폴백과 함께 써라"를 구분합니다.

3. Modern Web Guidance 해부 — 203개 가이드, 250개 기능

구성은 단순합니다. 사용 사례(use case) 가이드 203개가 웹 플랫폼 기능 250개를 다룹니다. 기능 기준으로는 CSS·레이아웃 140개, JavaScript·API 74개, HTML·DOM 36개입니다. 가이드는 accessibility, forms, performance, security, ui-components, pwa, wasm, built-in-ai, webmcp 등 17개 주제 폴더로 묶여 있습니다. accordion, carousel, dark-mode-toggle, navigation-drawer처럼 "주니어가 오늘 당장 만들 법한 것"이 사용 사례 단위입니다.

설치는 한 줄입니다.

{{< highlight bash >}} # 대화형 설치 마법사 — 어떤 에이전트를 쓰는지 물어보고 맞는 위치에 스킬을 넣어 줌 npx modern-web-guidance@latest install {{< /highlight >}}

Claude Code(플러그인 마켓플레이스), OpenAI Codex, GitHub Copilot CLI, Google Antigravity, Grok Build, Kimi Code 등 주요 에이전트를 지원하고, Vercel Skills CLI(npx skills add)나 gh skill install로도 설치할 수 있습니다. 라이선스는 Apache-2.0입니다.

참고: 익명 텔레메트리(설치 수, 에이전트 이름, 조회한 가이드 ID, 검색어)가 기본 켜져 있습니다. 프롬프트 원문은 수집하지 않는다고 명시돼 있고, DISABLE_TELEMETRY=1로 끌 수 있습니다.

4. 핵심 설계 — 205토큰짜리 스킬과 just-in-time 지식 주입

여기부터가 AI 엔지니어링 관점의 본론입니다. 가이드 203개를 통째로 컨텍스트에 넣으면 어떻게 될까요? 수십만 토큰이 상시 점유되고, 비용이 치솟고, 정작 필요한 지시는 긴 컨텍스트 속에서 희석됩니다. Modern Web Guidance는 반대로 갑니다. 에이전트에 설치되는 SKILL.md는 약 205토큰입니다. 본체는 "웹 UI 작업을 시작하면 먼저 이 CLI로 검색해라"라는 트리거 선언뿐이고, 지식은 필요한 순간에만 들어옵니다.

런타임 흐름은 4단계입니다.

{{< highlight bash >}} # 1) search — 2~5단어로 플랫폼 기능 하나를 검색 (오프라인: 임베딩 + BM25) npx -y modern-web-guidance@latest search "modal confirmation dialog" # 2) retrieve — 매칭된 가이드를 ID로 로드 (여러 개면 쉼표로) npx -y modern-web-guidance@latest retrieve "dialog,forms" {{< /highlight >}}
  • search — 에이전트가 짧은 질의로 가이드를 찾습니다. 검색은 의존성 없는 경량 임베딩 모델 + BM25로 완전히 로컬에서 돕니다. 네트워크 호출도, API 키도 없습니다. 1.0에서 TensorFlow.js를 걷어내며 npm 패키지가 23.5MB에서 8.8MB로 줄었습니다.
  • retrieve — 가이드 본문(권장 패턴, gotcha, 폴백 코드)이 이 시점에야 컨텍스트에 들어옵니다.
  • verify — 작성한 코드를 가이드와 대조하고, 필요한 폴백을 적용합니다.
  • disclose — 답변 끝에 어떤 가이드를 참고해 어떤 함정을 피했는지 한 줄씩 공개합니다. 사람이 에이전트의 판단을 검수할 수 있게 하는 장치입니다.

이 구조, 어디서 본 것 같지 않나요? Agent Skills의 핵심 아이디어(짧은 선언 + 필요 시 본문 로드)와 tool search의 지연 로딩을 "도메인 지식"에 적용한 모양새입니다. 세부 설계도 꼼꼼합니다. 정식 지원 전인 단일 엔진 기능이나 Origin Trial 가이드는 검색에는 걸리지만, retrieve는 .mwgrc 파일로 명시적으로 opt-in해야 가능합니다. 에이전트가 "신기능이니까"라며 아직 불안정한 API를 멋대로 쓰는 사고를 설정 파일 단위에서 차단한 겁니다.

기존 코드베이스용으로는 legacy-scan 명령이 있습니다. 결정적(deterministic) 규칙으로 낡은 패턴을 정적 탐지해 교체 가이드와 매핑해 주는데, 각 탐지 결과에 keepWhen/dropWhen 기준표가 붙어 있어 에이전트가 오탐을 걸러내게 돼 있습니다. 전체 카탈로그의 약 20%만 커버한다고 스스로 한계도 밝힙니다.

5. 사례 — dialog 가이드가 고치는 코드

가이드 하나를 열어 보면 성격이 분명해집니다. ui-components/dialog.md는 먼저 피해야 할 legacy 패턴을 명시합니다. 네이티브 <dialog>에 role="dialog"를 중복으로 다는 것, 수동 focus trap, 커스텀 Esc 핸들러, body에 overflow: hidden으로 스크롤 잠그기, 닫을 때 포커스를 복원하는 코드 — 전부 "에이전트가 습관적으로 생성하지만 이제는 불필요한" 코드입니다. 권장 패턴은 이렇습니다.

{{< highlight html >}}

Delete this item?

 {{< /highlight >}}

focus trap, Esc 처리, top-layer 렌더링, 접근성 시맨틱이 전부 브라우저 몫이 됩니다. 가이드는 여기서 멈추지 않고 폴백까지 코드로 줍니다. 예컨대 Invoker Commands가 없는 브라우저 대응은 이렇게 기능 감지로 폴리필을 조건 로드합니다.

{{< highlight javascript >}} // 기능이 없을 때만 폴리필 로드 — 있는 브라우저에는 1바이트도 안 보냄 if (!('commandForElement' in HTMLButtonElement.prototype)) { await import('invokers-polyfill'); } {{< /highlight >}}

"권장 패턴 + 피해야 할 패턴 + 폴백 + gotcha"가 한 가이드에 압축돼 있고, 모델이 이미 잘 아는 내용은 평가를 돌려 가며 잘라냈다고 합니다. 사람이 읽는 문서가 아니라 모델에게 먹이는 문서를 토큰 예산 안에서 설계한 겁니다. 1.0에서는 가이드 약 70개를 접근성 전문가가 사람 손으로 재검수하기도 했습니다.

6. 숫자 읽기 — 50~60% → 86~98%, 그리고 주의 사항

효과는 자체 평가 수치로 공개돼 있습니다. 실제 앱에 기능을 구현시키고 Playwright 그레이더와 golden solution으로 채점하는 방식이고, v1.0.0 릴리스 노트 기준 결과는 이렇습니다.

에이전트 (모델)태스크 / 검증 항목가이드 없음가이드 적용상승 폭
Antigravity CLI (gemini-4-argon)215 / 1,67360%98%+38%p
Codex CLI (gpt-6.1-sol)220 / 1,79550%86%+36%p
Claude Code (claude-opus-5-5)221 / 1,80158%94%+35%p

숫자를 읽을 때 주의할 점이 둘 있습니다. 첫째, 출제자와 채점자가 같은 평가입니다. 가이드가 다루는 기능으로 평가 태스크를 만들었으니, 가이드를 주면 점수가 오르는 건 어느 정도 설계된 결과입니다. "웹 개발 실력이 40%p 오른다"가 아니라 "가이드가 다루는 영역에서는 최신 패턴 준수율이 크게 오른다"로 읽는 게 정확합니다. 그나마 평가 하네스와 대시보드를 나이틀리로 공개해 외부 검증 여지를 열어 둔 점은 평가할 만합니다. 둘째, Hacker News 스레드에서도 나온 반론인데, "모던 primitive가 항상 정답은 아니다"는 점입니다. 지원 브라우저 범위, 팀의 기존 스택, 디자인 시스템과의 충돌을 따지는 건 여전히 사람 몫입니다. 가이드가 Baseline 지위와 폴백을 함께 제공하는 이유이기도 합니다.

7. 실전 — 설치해 보기, 그리고 내 도메인에 응용하기

웹 작업이 있다면 직접 체험해 보는 게 가장 빠릅니다. 설치 없이도 검색과 스캔을 돌려 볼 수 있습니다.

{{< highlight bash >}} # 설치 없이 맛보기 npx modern-web-guidance@latest search "image carousel" # 가이드 검색 npx modern-web-guidance@latest retrieve carousel # 가이드 본문 출력 npx modern-web-guidance@latest legacy-scan ./src --json # 내 코드베이스의 legacy 패턴 스캔(읽기 전용) # 에이전트에 설치 (대화형) npx modern-web-guidance@latest install {{< /highlight >}}

에이전트 권한 설정에서는 npx * 전체가 아니라 npx -y modern-web-guidance@latest *처럼 패키지를 특정해서 허용하는 걸 SKILL.md 스스로 권장합니다. npx 와일드카드 허용은 임의 패키지 실행 권한과 같아서 위험하기 때문입니다 — 이틀 전 secrets hygiene 글에서 본 allow 규칙 설계 원칙 그대로입니다. 지원해야 할 브라우저 범위가 정해진 팀이라면, 그 정책을 AGENTS.md나 CLAUDE.md에 적어 두세요. 가이드의 폴백 판단이 팀 정책을 따라가게 됩니다.

더 중요한 응용은 이 패턴을 내 도메인에 복제하는 것입니다. 에이전트가 자꾸 낡은(혹은 사내 표준과 다른) 코드를 쓰는 영역이 있다면, Modern Web Guidance의 구조를 그대로 빌릴 수 있습니다.

  • 사용 사례 단위로 가이드를 쪼갭니다. "우리 디자인 시스템으로 폼 만들기", "사내 인증 SDK로 로그인 붙이기"처럼, 에이전트가 받을 법한 작업 단위로 씁니다. 사람용 레퍼런스 문서를 통째로 넣는 것보다 훨씬 잘 듣습니다.
  • 각 가이드에 "피해야 할 패턴"을 명시합니다. 모델은 다수결로 legacy를 뽑으므로, "이렇게 하라"만큼 "이건 하지 마라(왜냐하면)"가 효과적입니다.
  • 본문은 상시 로드하지 말고, 짧은 스킬 + 검색/조회 도구로 JIT 주입합니다. 가이드가 10개 이내면 목차만 스킬에 넣고 파일 경로를 읽게 하는 것으로도 충분합니다.
  • 효과는 평가로 확인합니다. 가이드 적용 전후를 같은 태스크로 돌려 보는 before/after 평가가 없으면, 가이드가 토큰 낭비인지 성능 향상인지 알 수 없습니다. 모델이 이미 아는 내용을 가이드에서 잘라내는 것도 평가가 있어야 가능합니다.

8. 흔한 실수 · 팁

실수왜 문제인가 / 어떻게 고치나
최신 지식 문서를 통째로 시스템 프롬프트에 상주 토큰 비용이 작업마다 반복 청구되고, 긴 컨텍스트 속에서 정작 중요한 지시가 희석됩니다. 트리거(수백 토큰)와 본문(필요 시 로드)을 분리하세요.
"모델이 이미 아는 내용"까지 가이드에 포함 효과 없는 토큰이 매번 소비됩니다. Modern Web Guidance는 평가를 돌려 모델이 이미 잘하는 내용을 가이드에서 잘라냈습니다. 내 가이드도 같은 다이어트가 필요합니다.
벤더 자체 평가 수치를 일반 성능 향상으로 해석 출제와 채점을 같은 쪽이 설계한 평가는 "그 범위 안에서의" 효과만 보여 줍니다. 내 워크로드에서의 효과는 내 평가로 확인해야 합니다.
에이전트에게 npx * 와일드카드 허용 임의 npm 패키지 실행 권한과 같습니다. npx -y modern-web-guidance@latest *처럼 패키지를 특정해 허용하세요.
신기능 가이드를 받았다고 폴백 없이 배포 Baseline "widely available"이 아닌 기능은 가이드의 폴백 지침까지가 한 세트입니다. 지원 브라우저 정책을 AGENTS.md에 문서화해 두면 에이전트의 폴백 판단이 일관해집니다.

9. 마무리 (TL;DR)

  • 코딩 에이전트가 낡은 코드를 쓰는 이유는 셋입니다 — 지식 컷오프, 학습 데이터에서 legacy 패턴의 압도적 비중, 그리고 "아는 것"과 "꺼내 쓰는 것"의 간극. 셋 다 가중치 안에서는 못 고치므로, 답은 컨텍스트 주입입니다.
  • Modern Web Guidance 1.0(11/10 공개)은 Chrome·Edge·Firefox·MDN이 공동 관리하는 Apache-2.0 프로젝트로, 웹 기능 250개를 다루는 사용 사례 가이드 203개를 코딩 에이전트에게 공급합니다.
  • 설계의 핵심은 progressive disclosure: 설치되는 스킬은 약 205토큰, 지식 본문은 오프라인 CLI(임베딩+BM25)의 search → retrieve로 필요한 순간에만 주입됩니다. 불안정 기능은 .mwgrc opt-in 뒤에 잠겨 있습니다.
  • 자체 평가에서 세 에이전트의 pass rate가 50~60%에서 86~98%로 올랐습니다(+35~38%p). 단, 출제와 채점을 같은 쪽이 설계한 평가이므로 "가이드가 다루는 영역에서의 효과"로 읽어야 합니다.
  • 같은 패턴을 내 도메인에 복제할 수 있습니다 — 작업 단위 가이드, "피해야 할 패턴" 명시, JIT 주입, 그리고 before/after 평가. 문서는 이제 사람만 읽는 게 아니라 모델이 소비하는 입력입니다. 토큰 예산 안에서 설계하고, 효과는 평가로 증명하세요.
