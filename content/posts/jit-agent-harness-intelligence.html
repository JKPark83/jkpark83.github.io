1. 도입 — 8월 마지막 주, 하네스 담론의 세 번째 조각

8월 마지막 주 arXiv는 하네스(harness) 이야기로 뜨거웠습니다. 이 블로그에서도 두 편을 연달아 다뤘습니다. Prime Agent는 "모델 훈련 없이 하네스만 갈아 끼워 점수를 3배로 올렸다"고 주장했고, Agent Lightning v1.0은 "RL을 하려면 배포 하네스째로 학습하라"고 못 박았습니다. 방향은 달라도 전제는 같습니다. 에이전트 성능에서 하네스의 기여는 모델의 기여를 넘어설 수 있다.

그리고 같은 주, 이 담론의 세 번째 조각이 Hugging Face 데일리 페이퍼 트렌딩에 올랐습니다. 8월 26일 공개된 JIT-Agent: Scaling Harness Intelligence via Just-in-Time Harness Evolution(Guibin Zhang 외, arXiv:2608.25593)입니다. 이 논문이 겨누는 과녁은 앞의 두 편과 또 다릅니다. 하네스가 그렇게 중요하다면서, 왜 아직도 사람이 손으로 짜는가?

생각해 보면 이상한 일입니다. 하네스 설계는 지금도 수작업이고, 과제 특화이고, 그래서 확장이 안 됩니다. Claude Code의 하네스는 수많은 엔지니어가 다듬은 결과물이지만, 그 설계 하나로 리서치 과제도, 사무 자동화도, 여행 계획도 다 감당해야 합니다. JIT-Agent의 답은 이렇습니다. 하네스를 기계가 생성할 수 있는 산출물로 정형화하고, 하네스를 만들고·고치고·진화시키는 능력 자체를 별도 모델에 학습시키자. 논문은 이 능력을 하네스 인텔리전스(harness intelligence)라 부릅니다. 과제가 들어오면 27B짜리 '하네스 담당 모델'이 그 과제에 맞는 하네스를 즉석에서 합성해, 어떤 기성(off-the-shelf) LLM에든 입혀 줍니다.

이 글에서 얻어 갈 것. ① 하네스 수작업이 왜 병목인지와 AOT→JIT라는 관점 전환, ② 하네스를 메모리·플래닝·액션·능력 오케스트레이션 4모듈로 쪼개는 프로토콜, ③ 하네스 합성 모델을 만드는 3단계 학습 레시피(cold start → repair → Evo-GDPO), ④ "DeepSeek-V4-Flash가 GPT-5.6을 넘었다"는 숫자의 읽는 법, ⑤ 프레임워크 없이 오늘 훔칠 수 있는 설계 아이디어.

2. 배경 — AOT 하네스의 한계와 '하네스 인텔리전스'

복습부터 짧게. 하네스는 모델을 감싸고 실행을 굴리는 껍데기 전부입니다. 시스템 프롬프트, 도구 목록과 실행기, 메모리 전략, 컨텍스트 압축, 재시도, 서브에이전트 구성 — Claude Code 같은 에이전트에서 모델을 뺀 나머지입니다. 하네스가 왜 성능을 좌우하는지는 하네스 엔지니어링 글에서 다뤘으니 여기서는 넘어갑니다.

지금의 하네스 개발 방식을 컴파일러에 비유하면 AOT(ahead-of-time) 컴파일입니다. 개발자가 설계 시점에 하네스를 한 벌 만들어 두고, 런타임에는 어떤 과제가 오든 그 하네스를 그대로 씁니다. AOT의 장점 그대로 안정적이고 예측 가능하지만, 약점도 그대로입니다. 런타임에 알게 되는 정보를 활용하지 못합니다. 웹 리서치 과제는 넓게 탐색하는 플래닝과 검색 도구 중심의 구성이 유리하고, 스프레드시트 정리는 촘촘한 작업 메모리와 파일 도구가 유리합니다. 옷 한 벌로 모든 계절을 나면 어딘가는 항상 헐렁하거나 낍니다.

그래서 최근 반년 사이 "하네스도 자동으로 만들자"는 연구가 줄줄이 나왔습니다. 실패 로그를 보고 하네스를 고치는 관측 기반 하네스 진화, 하네스와 정책을 함께 진화시키는 HarnessForge, 실행 중에 하네스를 고치는 테스트 타임 하네스 진화(TTHE) 같은 것들입니다. 다만 이 계열은 대부분 탐색(search)입니다. 후보 하네스를 여러 개 만들어 굴려 보고 좋은 걸 고르는 방식이라, 후보 하나를 평가할 때마다 에이전트 롤아웃을 통째로 돌려야 해서 비쌉니다.

JIT-Agent는 여기서 한 발 더 나갑니다. 탐색 휴리스틱이 아니라, 하네스를 잘 짓는 능력을 모델 가중치에 새겨 넣습니다. 논문의 표현을 빌리면 하네스 인텔리전스란 "에이전트의 운영 골격(scaffold)을 구성하고(construct), 수리하고(repair), 진화시키는(evolve) 학습된 능력"입니다. 이 능력을 가진 모델이 있으면, 과제마다 좋은 하네스를 새로 탐색할 필요 없이 한 번의 생성으로 뽑아낼 수 있습니다. AOT에서 JIT(just-in-time)로의 전환입니다.

3. 하네스를 부품으로 쪼개다 — 4모듈 프로토콜과 HarnessFactory

"모델이 하네스를 생성한다"고 하면 자유분방한 에이전트 프로그램을 통째로 코딩하는 그림이 떠오르지만, 그렇게 하면 생성물마다 구조가 달라 검증도 재사용도 불가능합니다. JIT-Agent의 첫 번째 설계 결정은 그래서 생성 공간을 좁히는 것입니다. 모든 하네스는 고정된 4모듈 프로토콜을 따라야 합니다.

모듈담당예시 선택지
메모리(memory)상태와 히스토리를 어떻게 들고 갈 것인가전체 히스토리 유지 / 요약 압축 / 작업 노트 분리
플래닝(planning)어떤 전략으로 일을 쪼개고 진행할 것인가plan-and-execute / ReAct식 즉흥 / 재계획 주기
액션(action)모델의 출력과 실제 실행을 잇는 규약tool call 스키마 / 코드 실행 / 검증·재시도 규칙
능력 오케스트레이션(capability orchestration)도구·스킬·서브에이전트를 언제 무엇으로 조합할 것인가검색 중심 / 파일 도구 중심 / 서브에이전트 분업

네 모듈은 HarnessFactory라는 공용 코드베이스의 공유 인터페이스를 구현합니다. HarnessFactory는 대표적인 스캐폴드 패턴들을 이 공통 인터페이스 아래 모아 둔 부품 창고입니다. 덕분에 "하네스를 생성한다"는 말의 실체는 자유 형식 프로그램이 아니라, 정해진 인터페이스에 맞춘 구조화된 코드를 방출(emit)하는 것이 됩니다. 레고에 비유하면, 아무 플라스틱이나 사출하는 게 아니라 규격 블록을 골라 조립하는 겁니다. 블록 규격이 있으니 조립 결과를 실행할 수 있고, 검증할 수 있고, 나중에 다른 과제에서 부품 단위로 재사용할 수 있습니다.

주목할 점 하나. 하네스 담당 모델과 실행 담당 모델이 분리되어 있습니다. JIT-Agent는 하네스만 짓고, 그 안에서 실제로 일하는 백본 LLM은 따로입니다. 이 분리 덕에 "하네스 잘 짓는 능력"이 특정 모델에 묶이지 않고, 저렴한 백본에 좋은 하네스를 입히는 조합이 가능해집니다. 6장의 숫자가 바로 이 조합의 결과입니다.

4. 추론 시점에 벌어지는 일 — 생성·선택·실행·아카이브

과제 하나가 들어왔을 때의 흐름을 순서대로 따라가 봅니다. 공개된 코드베이스 기준입니다.

  1. 입력 조립. 과제 명세, 실행 프로토콜(규약과 제약), 사용 가능한 도구·스킬 레지스트리, 그리고 아카이브에서 검색해 온 과거 하네스 몇 개가 JIT-Agent의 프롬프트로 들어갑니다. 과거 하네스는 "비슷한 과제에서 뭐가 통했는지"의 참고 답안 역할입니다.
  2. 하네스 생성. JIT-Agent가 4모듈을 선택·조립한 실행 코드를 방출합니다. 후보를 여러 개 만들 수 있습니다(--rollouts).
  3. 선택. 후보가 여럿이면 셀렉터가 하나를 고릅니다. 저지 모델(judge)이 설계를 심사하는 방식과, 생성 logprob 기반으로 고르는 방식 두 가지를 지원합니다(--selector judge|logprob).
  4. 실행. 선택된 하네스가 백본 LLM을 감싸고 과제를 수행합니다. 실행 궤적과 지표가 기록됩니다.
  5. 아카이브 갱신. 이 하네스의 성적이 아카이브에 쌓이고, 다음 과제의 생성 단계에서 검색 대상이 됩니다.

여기서 이 시스템의 은근히 중요한 성질이 나옵니다. 배포 후에 생성기 가중치는 그대로인데도 시스템은 계속 좋아집니다. 좋아지는 실체가 가중치가 아니라 아카이브이기 때문입니다. 실행할수록 "이런 과제엔 이런 하네스"라는 사례가 쌓이고, 생성은 그 사례를 검색해 딛고 올라섭니다. Prime Agent가 실행 중에 자기 하네스를 직접 수정하는 것과 비교하면 결이 다릅니다. 그쪽은 에이전트 본인이 셀프 개조하는 구도라 오염과 폭주의 위험을 함께 안고 가는 반면, JIT-Agent는 하네스 생성을 별도 모델·별도 단계로 떼어 놓아 과제 실행과 하네스 개선의 관심사를 분리했습니다.

5. 하네스 짓는 법을 가르치다 — 3단계 학습 레시피

JIT-Agent-27B는 Qwen3.6-27B를 베이스로, 세 단계에 걸쳐 하네스 인텔리전스를 학습합니다. 각 단계가 3장의 세 능력 — 구성·수리·진화 — 에 하나씩 대응합니다.

Stage I — 과제 조건부 커스터마이즈(cold start). 교사 모델이 만든 프로토콜 준수 예제들로 지도학습합니다. "이런 과제 명세가 오면 이런 4모듈 조합을 짜라"의 기본기를 익히는 단계입니다. 이 단계가 없으면 뒤의 RL이 탐색할 출발점 자체가 없습니다.

Stage II — 피드백 기반 수리(repair). 생성이 실패한 사례를 버리지 않고 학습 재료로 씁니다. 컴파일 에러, 인터페이스 불일치, 런타임 실패를 입력으로 주고 고쳐진 하네스를 목표로 하는 수리 궤적(repair trajectory)을 학습합니다. 생성된 하네스는 결국 실행돼야 하는 코드이므로, "그럴듯한 설계"보다 "돌아가는 설계"를 보장하는 이 단계가 실전 신뢰성을 좌우합니다.

Stage III — 진화적 정책 최적화(Evo-GDPO). 마지막으로 Evolutionary Group-Decoupled Policy Optimization이라는 RL 단계를 얹습니다. 목표가 재미있습니다. 그냥 "좋은 하네스를 내라"가 아니라, 현재 아카이브의 프런티어(지금까지의 최고 기록)를 넘어서는 하네스를 제안하도록 최적화합니다. 이때 보상·지연시간·비용을 따로 정규화해서, 점수만 높고 느리고 비싼 하네스로 쏠리지 않게 잡습니다. 4장에서 본 테스트 타임 개선 루프가 잘 도는 이유가 여기 있습니다. "아카이브를 딛고 더 나은 것을 내는 행동" 자체가 훈련된 능력이지, 바깥에 붙인 탐색 휴리스틱이 아니기 때문입니다.

단계가르치는 것학습 재료대응 능력
Stage I과제에 맞는 4모듈 조합 짜기교사 생성 프로토콜 준수 예제구성(construct)
Stage II깨진 하네스를 돌아가게 고치기컴파일 에러·인터페이스 불일치·런타임 실패 → 수리 궤적수리(repair)
Stage III아카이브 프런티어를 넘는 제안Evo-GDPO — 보상·지연·비용 분리 정규화진화(evolve)
왜 "수리"가 별도 단계일까? LLM으로 코드 생성을 해 본 분은 압니다. 첫 생성이 완벽한 경우보다 "거의 맞는데 조금 깨진" 경우가 압도적으로 많습니다. 사람 개발자도 첫 커밋보다 리뷰 반영을 더 많이 하죠. 실패를 supervision으로 바꾸는 Stage II는 이 현실을 학습 설계에 그대로 반영한 것입니다. 이번 여름 나온 Harness-R1도 실패 궤적에서 하네스 수정을 배우는 같은 계열의 접근입니다.

6. 숫자 읽는 법 — "Flash급이 GPT-5.6을 넘었다"는 말의 조건

논문의 대표 숫자는 이렇습니다. 저렴한 백본인 DeepSeek-V4-Flash에 JIT-Agent 하네스를 입혔더니, 딥 리서치 벤치마크 DeepSearchQA에서 GPT-5.6을 +9.1포인트, 사무 업무 벤치마크 OdysseyBench에서 +4.3포인트 앞섰다는 것. 이미 강한 GLM-5.2 백본에서도 xBench-DS 등에서 최대 +20.2포인트를 더 얻었고, DeepSeek V4·Mimo-V2.5·Qwen3.6 계열의 크고 작은 모델 전반에서 일관된 개선을 보였으며, 생성된 하네스가 OpenCode나 Claude Code 같은 성숙한 에이전트 런타임과 성능으로 경쟁할 만하다고 보고합니다. 평가는 딥 리서치·사무 업무·플래닝·워크스페이스의 네 범주(코드 기준 deepsearchqa, xbench, officebench, odyssey, travel 등)에서 이뤄졌습니다.

고무적인 숫자지만, 그대로 삼키기 전에 걸러야 할 조건이 있습니다.

  • 벤더 자체 보고입니다. 저자들이 고른 벤치마크에서 저자들이 잰 숫자입니다. 제3자 재현은 아직 없습니다. 코드와 체크포인트(Hugging Face의 jit-27b)가 공개돼 있으니 재현 가능성은 열려 있습니다.
  • 비교 대상의 하네스가 무엇이었는지가 관건입니다. "JIT 하네스 + Flash > 기본 하네스 + GPT-5.6"이라면, 이건 모델 비교가 아니라 하네스 포함 시스템 비교입니다. GPT-5.6에도 최적 하네스를 입히면 격차가 어떻게 될지는 별개 질문입니다.
  • 하네스 생성 비용이 추가로 듭니다. 27B 모델 호출 + 후보 여러 개 + judge 심사가 과제마다 얹힙니다. 지연시간과 비용에 민감한 서비스라면 "하네스는 좋아졌는데 첫 응답이 느려진" 상황이 될 수 있습니다. Stage III가 지연·비용을 분리 정규화하는 이유이기도 합니다.
  • 벤치마크 하네스 과적합 가능성. 아카이브가 특정 벤치마크 분포에서 자랐다면, 그 프런티어를 넘는 능력이 완전히 새로운 도메인으로 얼마나 전이될지는 지켜봐야 합니다.

그래도 이 논문이 남기는 방향성은 분명합니다. 어제 글의 표현을 빌리면 지난주 담론은 "하네스째 학습하라"였는데, JIT-Agent는 거기서 한 칸 더 나아가 "하네스 자체가 학습의 산출물이 될 수 있다"를 보였습니다. 모델 스케일링과 별개의 축 — 스캐폴드 축 — 에서 성능을 끌어올릴 수 있다는 증거가 하나 더 쌓인 셈입니다.

7. 실전 — 직접 돌려 보기, 그리고 오늘 훔칠 수 있는 아이디어

저장소가 공개되어 있어 직접 굴려 볼 수 있습니다. 준비물은 OpenAI 호환 엔드포인트 하나(백본 실행용)와, 선택적으로 메타 모델·저지 모델·검색 API 키(Serper, Jina)입니다.

{{< highlight bash >}} git clone https://github.com/bingreeky/JIT.git && cd JIT conda env create -f environment.yml && conda activate jit cp .env.example .env # 실행 모델·judge·메타 모델 엔드포인트와 키 기입 # 1) 메타 모델 없이, 고정 하네스 하나로 스모크 테스트 python -m scripts.run_seed_harness --bench xbench \ --harness plan_and_execute --max-samples 5 {{< /highlight >}}

흥미로운 부분은 run_jit입니다. 하네스를 생성하는 메타 모델 자리에 공개 체크포인트 JIT-Agent/jit-27b를 서빙해 꽂을 수도 있고, 호스팅 API(GPT 계열 등)를 대신 넣어 "학습 안 된 범용 모델이 하네스를 얼마나 잘 짓는지"와 비교해 볼 수도 있습니다.

{{< highlight bash >}} # 2) jit-27b 체크포인트를 로컬 서빙해 하네스 생성까지 풀 코스 MODEL=JIT-Agent/jit-27b SERVED_NAME=jit TP=4 \ bash scripts/serve_meta_model.sh python -m scripts.run_jit --bench xbench \ --meta-model jit --selector logprob \ --tokenizer JIT-Agent/jit-27b --rollouts 3 {{< /highlight >}}

27B 메타 모델을 서빙할 GPU가 없어도 괜찮습니다. 이 논문에서 오늘 당장 훔칠 수 있는 것은 모델이 아니라 설계 습관 두 가지입니다.

첫째, 하네스를 코드에 흩뿌리지 말고 명세로 모으세요. 4모듈 프로토콜의 교훈은 "하네스 구성이 데이터가 되는 순간, 하네스를 프로그램적으로 다룰 수 있다"입니다. 시스템 프롬프트·도구 목록·메모리 전략·재시도 규칙이 코드 곳곳에 하드코딩되어 있으면 아무것도 못 합니다. 한곳에 모으면 과제 유형별 프리셋 전환부터 A/B 테스트까지 열립니다.

{{< highlight python >}} from dataclasses import dataclass, field @dataclass class HarnessSpec: """하네스 구성을 코드가 아니라 데이터로 — JIT-Agent 4모듈의 미니 버전""" memory: str # "full_history" | "summarize" | "scratchpad" planning: str # "react" | "plan_and_execute" action: dict # 검증·재시도 규칙 tools: list[str] # 이 과제에 노출할 도구만 PRESETS = { # 과제 유형별 프리셋 = 나만의 '하네스 아카이브' 0단계 "research": HarnessSpec("summarize", "plan_and_execute", {"max_retries": 2}, ["web_search", "fetch"]), "office": HarnessSpec("scratchpad", "react", {"max_retries": 1, "verify": True}, ["read_file", "write_file", "spreadsheet"]), } def pick_harness(task: str) -> HarnessSpec: # 시작은 규칙 기반이면 충분 — 나중에 이 함수만 LLM 호출로 바꾸면 # "과제를 보고 하네스를 고르는" JIT의 최소 형태가 됩니다 return PRESETS["research" if "조사" in task or "리서치" in task else "office"] {{< /highlight >}}

둘째, 실행이 끝날 때마다 "구성 + 성적"을 기록하세요. JIT-Agent 아카이브의 최소 형태는 로그 한 줄입니다. 어떤 하네스 구성으로 어떤 과제를 돌렸고 성공했는지, 토큰을 얼마나 썼는지. 이게 쌓이면 프리셋을 데이터로 개선할 수 있고, 나중에 "비슷한 과제의 과거 구성을 검색해 프롬프트에 넣는" 단계로 자연스럽게 확장됩니다. 진화는 그다음 문제입니다.

8. 흔한 실수 · 팁

  • 자유 형식 하네스 생성부터 시작하는 것. "LLM에게 에이전트 코드를 통째로 짜게 하자"는 매력적이지만, 생성물마다 구조가 달라 디버깅도 비교도 안 됩니다. JIT-Agent가 굳이 4모듈 프로토콜로 생성 공간을 좁힌 이유를 기억하세요. 좁은 설계 공간 + 공유 인터페이스가 먼저이고, 생성은 그다음입니다.
  • 생성된 하네스를 맨몸으로 실행하는 것. 모델이 방출한 하네스는 결국 실행되는 코드입니다. 신뢰 경계가 하나 늘어난 것이므로, 코드 실행 샌드박스 글에서 다룬 격리 원칙이 그대로 적용됩니다. 특히 아카이브에서 검색해 온 과거 하네스를 프롬프트에 넣는 구조는, 아카이브가 오염되면 오염된 설계가 재생산되는 경로가 됩니다.
  • 아카이브를 무한정 키우는 것. 프런티어 갱신 없이 사례만 쌓이면 검색 품질이 떨어지고 비슷한 하네스가 중복 저장됩니다. 메모리 통합 글의 교훈과 같습니다 — 아카이브도 넣는 것보다 남기고·합치고·버리는 규칙이 본체입니다.
  • 하네스 생성 비용을 지표에서 빼먹는 것. 후보 3개 생성 + judge 심사면 과제 시작 전에 이미 LLM 호출이 여러 번입니다. 하네스 품질 지표만 보지 말고 과제당 총비용과 첫 응답 지연을 함께 재세요. 짧고 단순한 과제는 고정 하네스가 정답인 경우가 많습니다 — JIT는 과제가 다양하고 무거울 때 이득이 큽니다.
  • "하네스 vs 모델" 비교를 뒤섞는 것. 사내 평가에서 하네스를 바꾸며 모델도 함께 바꾸면 무엇이 효과였는지 알 수 없게 됩니다. JIT-Agent 논문 실험처럼 백본 고정 후 하네스만 교체, 하네스 고정 후 백본만 교체를 분리해 재는 습관을 들이세요.

9. 마무리 (TL;DR)

  • 하네스는 에이전트 성능의 절반을 좌우하지만, 여전히 사람이 손으로, 설계 시점에(AOT) 만듭니다. 과제가 달라도 옷은 한 벌이라 어딘가는 항상 헐렁합니다.
  • 8월 26일 공개돼 Hugging Face 트렌딩에 오른 JIT-Agent(arXiv:2608.25593)는 하네스를 메모리·플래닝·액션·능력 오케스트레이션 4모듈의 기계 생성 가능한 산출물로 정형화하고, 과제마다 맞춤 하네스를 즉석 합성하는 하네스 인텔리전스 모델(27B, Qwen3.6 기반)을 학습시켰습니다.
  • 학습은 3단계: 교사 예제로 기본기(cold start) → 실패를 수리 궤적으로(repair) → 아카이브 프런티어를 넘도록 RL(Evo-GDPO, 보상·지연·비용 분리 정규화).
  • 추론 시점엔 생성→선택→실행→아카이브의 루프가 돌고, 가중치는 프리즈인데 아카이브가 자라며 시스템이 계속 좋아집니다.
  • 보고된 결과: DeepSeek-V4-Flash + JIT 하네스가 DeepSearchQA에서 GPT-5.6을 +9.1p, OdysseyBench에서 +4.3p 추월, GLM-5.2에서도 최대 +20.2p. 단, 벤더 자체 보고이고 하네스 포함 시스템 비교이며, 하네스 생성 비용이 추가된다는 조건을 달고 읽어야 합니다.
  • 오늘 훔칠 것: ① 하네스 구성을 코드가 아니라 명세(데이터)로 모으기, ② 실행마다 구성+성적을 기록해 나만의 하네스 아카이브 만들기. 생성된 하네스는 실행 코드이므로 샌드박스는 필수.
