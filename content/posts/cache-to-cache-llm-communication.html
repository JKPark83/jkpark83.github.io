1. 도입 — 에이전트는 왜 아직도 "말"로 통신하나

멀티 에이전트 시스템을 하나라도 만들어 봤다면, 에이전트 사이의 통신이 전부 텍스트라는 사실을 당연하게 받아들였을 겁니다. 플래너가 계획을 텍스트로 쓰면 워커가 읽고, 코드 전문 에이전트가 분석 결과를 텍스트로 요약하면 리뷰 에이전트가 다시 읽습니다. 사람끼리 일하는 방식을 그대로 옮긴 거죠.

그런데 생각해 보면 이상합니다. 모델 내부에는 문제를 "이해한 상태"가 수천 차원의 벡터로 풍부하게 들어 있는데, 다음 모델에게 넘길 때는 그걸 굳이 몇십~몇백 개의 토큰으로 눌러 담습니다. 받는 쪽은 그 토큰을 다시 읽어 자기 내부 표현으로 복원해야 하고요. 두 뇌가 협업하는데, 매번 좁은 빨대로 뜻을 주고받는 셈입니다.

이 빨대를 치워 버리자는 논문이 이번 주 다시 화제에 올랐습니다. 칭화대 NICS-EFC 연구실의 Cache-to-Cache(C2C, arXiv:2510.03215)입니다. 2025년 10월 공개 당시 Hugging Face 데일리 페이퍼 1위에 올랐던 이 논문은 올해 1월 ICLR 2026에 채택됐고, 지난 9월 19~20일 Hacker News에 "Cache-to-Cache: Direct Semantic Communication Between LLMs"로 다시 올라 이틀 연속 AI 다이제스트 상위권을 지켰습니다. 댓글창에서는 "아예 KV 캐시가 호환되는 모델 패밀리를 만들자"는 아이디어까지 나왔죠. 마침 공식 저장소에는 이번 9월 "에이전트가 관리하는 KV 캐시 서빙 시스템을 준비 중"이라는 로드맵이 올라왔습니다. 멀티 에이전트를 많이 돌릴수록 통신 비용이 아픈 시대라, 다시 주목받을 만한 타이밍입니다.

이 글은 논문 리뷰이면서 동시에 "에이전트 간 통신 채널"을 다시 생각해 보는 글입니다. C2C를 당장 프로덕션에 넣지 않더라도, 텍스트가 유일한 통신 수단이 아니다라는 관점 하나는 그대로 가져갈 수 있습니다.

2. 배경 — KV 캐시 3분 요약

C2C를 이해하려면 KV 캐시(KV-cache)만 알면 됩니다. 이미 안다면 이 절은 건너뛰어도 좋습니다.

트랜스포머는 토큰을 생성할 때마다 앞의 모든 토큰을 다시 참조합니다(어텐션). 이때 앞 토큰들의 Key·Value 벡터를 매번 다시 계산하면 낭비이므로, 한 번 계산한 값을 레이어별로 저장해 두고 재사용합니다. 이 저장소가 KV 캐시입니다.

여기서 중요한 관점 전환 하나. KV 캐시는 단순한 "계산 재활용 버퍼"가 아니라, 모델이 입력을 읽고 이해한 결과가 레이어별로 쌓여 있는 내부 표현이기도 합니다. 같은 문장이라도 모델이 다르면 캐시 내용이 다르고, 같은 모델이라도 문맥이 풍부하면 캐시가 더 "잘 이해한 상태"가 됩니다. C2C는 바로 이 성질을 통신에 씁니다. 앞 모델(논문 용어로 Sharer)의 캐시를 뒷 모델(Receiver)의 캐시 공간으로 옮겨 심겠다는 겁니다.

3. 텍스트 핸드오프의 두 가지 비용

텍스트 통신의 비용은 두 종류입니다.

① 의미 손실. 내부 표현을 토큰 열로 바꾸는 순간, 토큰으로 표현되지 않는 정보는 버려집니다. 미묘한 확신도, 여러 해석 사이의 긴장, 구조에 대한 감각 같은 것들이죠. 게다가 자연어는 태생적으로 모호해서, 받는 쪽이 다르게 해석할 여지도 생깁니다. 요약을 거칠수록 손실은 누적됩니다.

② 지연. 텍스트를 만들려면 토큰을 하나씩 자기회귀(autoregressive)로 생성해야 합니다. 논문 실험에서 텍스트 통신은 Sharer가 평균 80토큰 정도의 전달용 메시지를 생성했는데, 여기에 약 1,312ms가 걸렸습니다. 뒤에서 보겠지만 C2C의 캐시 융합은 같은 역할을 약 90ms에 해냅니다. 통신 한 번에 열 배 이상 차이가 나는 셈입니다.

4. 오라클 실험 — 캐시는 더 담을 수 있고, 옮길 수 있다

"캐시를 직접 넘긴다"는 아이디어가 성립하려면 두 가지 질문에 먼저 답해야 합니다. 논문은 본 방법에 앞서 이 둘을 오라클(oracle) 실험 — 정답을 아는 이상적 조건에서 상한선을 확인하는 실험 — 으로 검증합니다.

질문 1: 캐시를 "더 잘 이해한 상태"로 바꾸면 답이 좋아지나? 토큰 수(캐시 길이)를 그대로 둔 채 캐시의 내용만 더 풍부한 문맥으로 채워 넣자, 같은 질문에 대한 정확도가 58.42%에서 62.34%로 올랐습니다. 즉 성능을 올리는 건 토큰 개수가 아니라 캐시에 담긴 의미의 질입니다. 흥미롭게도 모든 레이어를 바꾸는 것보다 일부 레이어만 골라 바꾸는 쪽이 더 좋았는데, 이 관찰이 뒤에 나올 게이트 설계로 이어집니다.

질문 2: 서로 다른 모델의 캐시 공간은 이어질 수 있나? Qwen3-4B의 캐시를 3층 MLP로 Qwen3-0.6B의 캐시 공간에 투영해 보니, 변환된 캐시가 대상 모델 캐시 분포(manifold) 안쪽에 안착하는 것을 t-SNE 시각화로 확인했습니다. 모델이 달라도 캐시 사이에 학습 가능한 다리를 놓을 수 있다는 뜻입니다.

5. C2C Fuser 해부 — 투영, 가중, 게이트

본 방법인 C2C Fuser는 위 두 결론을 하나의 모듈로 합친 것입니다. Sharer와 Receiver가 같은 입력을 각자 프리필(prefill)해 캐시를 만들고 나면, Fuser가 레이어별로 다음 세 단계를 거칩니다.

① 투영(projection). Sharer의 K·V 벡터를 Receiver의 캐시 공간으로 변환합니다. 두 캐시를 이어 붙인 뒤 MLP에 통과시키는 구조로, 차원이 다른 모델 쌍도 이 단계에서 맞춰집니다.

② 동적 가중(dynamic weighting). 입력에 따라 어텐션 헤드별로 Sharer 정보를 얼마나 반영할지 조절합니다. 모든 입력에 같은 비율로 섞는 게 아니라, "이 질문엔 Sharer의 이해가 더 필요하다"를 학습으로 판단하는 셈입니다.

③ 학습 가능한 게이트(learnable gate). 레이어마다 융합할지 말지를 결정하는 스위치입니다. 오라클에서 봤듯 모든 레이어를 바꾸면 오히려 나빠지므로, 학습 중 온도를 서서히 낮추는(temperature annealing) 방식으로 유용한 레이어만 남깁니다. 최종 출력은 Receiver의 원래 캐시에 잔차(residual)로 더해집니다.

중요한 설계 제약 하나: 두 LLM은 전혀 건드리지 않습니다. 학습되는 것은 Fuser(프로젝터)뿐이고, Sharer·Receiver의 가중치는 얼려 둔 채로 둡니다. 그래서 이미 배포된 모델 조합 위에 붙이기가 상대적으로 쉽습니다.

6. 숫자로 보는 효과 — 정확도 +8.5~10.5%p, 지연 절반

공식 저장소가 요약하는 결과는 세 줄입니다. Qwen2.5·Qwen3·Llama 3.2·Gemma 3 조합으로 MMLU-Redux, C-Eval, OpenBookQA, ARC-Challenge를 평가했을 때:

비교 대상결과해석
Receiver 단독평균 정확도 +8.5~10.5%p작은 모델이 Sharer의 이해를 빌려 더 똑똑해짐
텍스트 통신(T2T)평균 +3.0~5.0%p같은 협업이라도 채널이 캐시면 더 정확
지연(레이턴시)평균 약 2배 빠름통신용 토큰 생성이 사라진 효과. 통신 구간만 보면 1,312ms → 약 90ms

포인트는 "텍스트 통신보다 낫다"에 있습니다. 텍스트 통신도 Receiver 단독보다는 좋아지는데, C2C는 같은 정보를 더 적은 손실·더 적은 시간에 전달해서 그 위에 3~5%p를 더 얹습니다. 참고로 이후 갱신된 논문 버전(v2)에서는 개선 폭을 6.4~14.2%p(단독 대비), 3.1~5.4%p(텍스트 대비), 약 2.5배(지연)로 보고합니다. 실험 구성이 늘어난 결과이니, 인용할 때는 어느 버전 숫자인지 밝혀 주는 게 안전합니다.

7. 실전 — 공개 코드로 돌려보기

코드는 thu-nics/C2C에 Apache-2.0으로 공개돼 있고(글 쓰는 시점 star 약 677개), 학습을 건너뛸 수 있게 미리 학습된 Fuser 체크포인트를 Hugging Face nics-efc/C2C_Fuser로 배포합니다. 공식 README의 최소 예제는 이렇게 시작합니다.

{{< highlight python >}} import torch from huggingface_hub import snapshot_download from script.playground.inference_example import load_rosetta_model, run_inference_example # 미리 학습된 Fuser 내려받기 # (Sharer=Qwen2.5-0.5B, Receiver=Qwen3-0.6B 조합) checkpoint_dir = snapshot_download( repo_id="nics-efc/C2C_Fuser", allow_patterns=["qwen3_0.6b+qwen2.5_0.5b_Fuser/*"], ) {{< /highlight >}}

이후 load_rosetta_model()로 Sharer·Receiver·Fuser를 하나로 감싼 RosettaModel을 만들고, run_inference_example()로 융합 추론을 실행합니다. 다른 모델 쌍을 쓰고 싶으면 저장소의 recipe/train_recipe/에 있는 학습 설정(JSON)을 참고해 Fuser를 직접 학습하면 되는데, 이때도 두 모델 가중치는 얼린 채 프로젝터만 학습합니다. 개념만 의사코드로 요약하면 추론 경로는 다음과 같습니다.

{{< highlight python >}} # 개념 의사코드 — 실제 API가 아니라 동작 원리를 요약한 것 def c2c_generate(query, sharer, receiver, fuser): kv_s = sharer.prefill(query) # Sharer가 질문을 읽고 캐시 생성 kv_r = receiver.prefill(query) # Receiver도 같은 질문을 프리필 fused = [] for layer, (s, r) in enumerate(zip(kv_s, kv_r)): if fuser.gate[layer]: # ③ 이 레이어를 융합할까? proj = fuser.project(s, r, layer) # ① Sharer 캐시를 Receiver 공간으로 r = r + fuser.weight(proj, layer) # ② 헤드별 가중 후 잔차 합산 fused.append(r) return receiver.decode(fused) # 융합 캐시로 답변 생성 (토큰 통신 없음) {{< /highlight >}}

어디에 써볼 수 있을까요? 논문 구도가 "작은 Receiver + 잘 이해하는 Sharer"이므로, 도메인 특화 소형 모델이 이해를 공급하고 범용 모델이 답을 쓰는 조합, 또는 프라이버시 때문에 원문은 못 넘기고 "이해한 상태"만 넘기고 싶은 파이프라인 같은 곳이 후보입니다. 공식 저장소도 2025년 12월 multi-sharer(여러 모델의 캐시를 한 Receiver에 융합)를 추가하며 멀티 에이전트 쪽으로 확장 중입니다.

8. 계보와 논쟁 — DroidSpeak부터 "KV-aligned 모델 패밀리"까지

C2C가 최초의 시도는 아닙니다. 2024년의 DroidSpeak(arXiv:2411.02820)는 같은 아키텍처의 모델끼리 프리필된 KV 캐시를 재사용하는 시스템으로, 일부 레이어만 다시 계산하는 방식으로 프리필을 약 3.1배 빠르게 만들었습니다. 다만 "같은 계열 모델"이라는 제약이 있었죠. C2C는 학습된 프로젝터로 계열이 다른 모델 사이에 다리를 놓았다는 점이 다릅니다. 비슷한 시기의 KVComm(arXiv:2510.03346)처럼 선택적 KV 공유로 통신 효율을 노리는 연구도 이어지고 있어, "캐시 = 통신 매체"는 이제 하나의 연구 갈래로 자리 잡는 분위기입니다.

이번 주 Hacker News 스레드에서 가장 흥미로운 논점은 한발 더 나간 상상이었습니다. 매 모델 쌍마다 프로젝터를 학습할 게 아니라, 애초에 KV 캐시 표현을 정렬(align)해 둔 모델 패밀리를 만들면 프로젝터 없이도 캐시를 서로 읽을 수 있지 않냐는 겁니다. 실현된다면 "임베딩 호환"처럼 "캐시 호환"이 모델 선택 기준이 되는 미래도 상상해 볼 수 있습니다. 물론 지금은 아이디어 단계입니다.

주의할 점도 분명합니다. VentureBeat가 짚었듯 C2C는 추론 스택을 직접 제어할 수 있는 팀의 이야기입니다. KV 캐시에 접근할 수 없는 API 전용 모델(GPT, Claude 같은 상용 API)끼리는 애초에 적용할 수 없습니다. 또 캐시가 통신 채널이 되는 순간, 프롬프트 인젝션에 해당하는 "캐시 인젝션"류 공격면이 새로 생긴다는 점도 기억해 둘 만합니다. 텍스트는 사람이 읽고 감사할 수 있지만, 융합된 캐시는 들여다보기 어렵습니다. 관측 가능성(observability) 관점에서는 오히려 후퇴일 수 있다는 뜻입니다.

9. 흔한 실수 · 팁

① "아무 모델 쌍이나 바로 붙는다"는 오해. Fuser는 모델 쌍마다 학습해야 합니다. 공개된 체크포인트는 Qwen3-0.6B/1.7B/8B를 Receiver로 하는 몇 가지 조합뿐이고, 새 조합은 직접 학습이 필요합니다. 학습 비용 자체는 프로젝터만 학습하므로 파인튜닝보다 가볍지만, 공짜는 아닙니다.

② 논문 버전에 따라 다른 숫자 인용. v1(공식 README)은 +8.5~10.5%p·2.0배, v2는 +6.4~14.2%p·2.5배를 보고합니다. 블로그나 발표에서 두 버전 숫자를 섞어 쓰면 재현 논쟁의 단골 소재가 됩니다.

③ 통신 지연과 전체 지연 혼동. "2배 빠르다"는 통신 구간이 사라진 효과가 평균에 반영된 수치입니다. Receiver의 프리필·디코딩은 그대로 있으므로, 파이프라인 전체가 2배 빨라지는 게 아닙니다. 병목이 통신이 아닌 시스템이라면 체감 효과는 작습니다.

④ 텍스트 로그를 잃는 비용 무시. 텍스트 통신은 느리지만 디버깅 로그가 공짜로 남습니다. 캐시 통신으로 바꾸면 "에이전트가 서로 뭘 주고받았는지"를 사람이 읽을 수 없게 됩니다. 평가·감사 경로를 따로 설계하지 않으면 장애 분석이 어려워집니다.

⑤ 벤치마크 범위 과신. 검증된 것은 지식·추론형 QA 벤치마크(MMLU-Redux, C-Eval, OpenBookQA, ARC-C)와 소형 모델 조합입니다. 긴 멀티턴 에이전트 루프나 대형 모델 조합에서의 효과는 아직 열린 문제입니다.

10. 마무리 (TL;DR)

  • 멀티 에이전트의 기본 통신 채널인 텍스트는 의미 손실 + 토큰 생성 지연이라는 이중 비용을 낸다.
  • C2C(arXiv:2510.03215, ICLR 2026)는 Sharer의 KV 캐시를 신경망(Fuser)으로 Receiver 캐시 공간에 투영·융합해, 텍스트 없이 "이해한 상태"를 직접 전달한다.
  • Fuser = 투영 MLP + 헤드별 동적 가중 + 레이어별 학습 게이트, 잔차 합산. 두 모델은 얼려 두고 Fuser만 학습한다.
  • 결과: Receiver 단독 대비 +8.5~10.5%p, 텍스트 통신 대비 +3.0~5.0%p, 지연 약 절반(통신 구간 1,312ms→약 90ms).
  • 코드·사전 학습 Fuser 공개(thu-nics/C2C, Apache-2.0). 단, 모델 쌍마다 Fuser 학습이 필요하고 API 전용 모델에는 적용 불가.
  • 이번 주 HN 재부상의 논점: "KV-aligned 모델 패밀리" — 캐시 호환이 모델 설계 요구사항이 되는 미래. 반대급부로 관측 가능성·보안(캐시 인젝션) 숙제도 함께 온다.
