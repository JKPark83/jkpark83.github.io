# 🔥 오늘의 핵심

새 프런티어 모델은 조용하다(7월 Opus 5·GPT-5.6 물결 이후). 오늘 신호는 **툴 정의(tool specification)** 한 축으로 모인다. 어제 07-31 arXiv에 올라온 논문 **SafeKeep**은, LLM이 에이전트로 배포되면 갑자기 덜 안전해지는 원인을 **스키마 형식의 tool spec**으로 지목한다 — 그 형식이 모델 내부의 **refusal(거부) 신호를 약화**시킨다는 것. 오늘 할 일: **안전 판단을 툴 실행에서 분리**하고(SafeKeep 패턴), 낯선 MCP 서버를 붙이기 전 **툴 설명을 스캔**(mcp-scan)하라.

# 🤖 모델 & 릴리즈 레이더

- **큰 신규 프런티어 모델 소식은 오늘 조용.** 7월의 물결(Claude Opus 5 · 7/24, GPT-5.6 Terra · 7/9, Gemini 3.6 Flash · 7/21, Qwen3.7 Flash · 7/27)은 이미 지난주 커버했다. 오늘의 무게중심은 새 릴리즈가 아니라 **에이전트 안전·신뢰성 인프라**로 옮겨가 있다.
- **통제점은 이제 "툴 권한"이다.** Codex는 **샌드박스 정책**(`read-only` / `workspace-write` / `danger-full-access`)과 **승인 정책**으로 툴이 만질 수 있는 파일·네트워크 범위를 나눈다. 프로덕션 에이전트일수록 기본을 좁게 잡는 게 오늘 논문의 결론과 정확히 맞물린다. → 에이전트 빌더에게: 모델 성능이 아니라 **툴에게 무엇을 허용할지**가 안전의 1차 변수다. 출처: [developers.openai.com/codex/config-basic](https://developers.openai.com/codex/config-basic)
- **Claude Code도 같은 방향.** 최근 auto mode는 미해결 변수의 `rm -rf`나 파괴적 git 명령 전에 **되묻고**, 권한 규칙은 `Tool(param:value)` 단위로 **막을 걸 막는다**(아래 팁 참고). 출처: [code.claude.com/docs/en/whats-new](https://code.claude.com/docs/en/whats-new/2026-w28)

# 📚 주목 논문

## 1) SafeKeep — "tool spec 형식이 안전을 떨어뜨린다"

- **저자**: Minghui Pan, Jiayuxuan Yang, Yuanyuan Yuan, Yu Jiang, Zhenpeng Chen (5인)
- **arXiv**: [2607.29254](https://arxiv.org/abs/2607.29254) · category `cs.AI` · 2026-07-31
- **핵심 기여**: LLM이 에이전트로 배포되면 눈에 띄게 덜 안전해지는데, 원인이 불명확했다. 이 논문은 **스키마 형식의 tool spec** 자체를 주범으로 지목하고, **white-box 표현 분석**으로 그 형식이 모델의 **내부 refusal 신호를 약화**시켜 위험한 툴 실행에 기여함을 보인다.
- **방법(2–3줄)**: **SafeKeep**은 추론 시점 세이프가드로, **안전 판단과 툴 실행을 분리**한다. 요청의 위험도는 **평문으로 flatten한 tool spec**으로 평가하고, 실제 실행에는 **원래 스키마 형식 spec을 그대로** 쓴다.
- **핵심 결과(검증)**: 2개 벤치·4개 LLM(white/black-box)에서 유해 요청 **거부율 23.8% → 70.6%**, observation-level 프롬프트 주입의 **공격 성공률 25.6% → 2.5%**. 기존 세이프가드보다 우수하면서 **작업 처리 능력은 유지**. 코드·데이터 공개: `github.com/snowcatsmoking/SafeKeep`.
- 🛠 **agent-builder 시사점**: 안전 필터에 JSON 스키마 tool spec을 그대로 넣지 말 것. **사람이 읽는 평문 설명으로 "이 요청을 이 툴로 실행해도 되나?"를 먼저 판정**한 뒤, 실행 단계에서만 스키마를 쓰는 **2단 게이트**를 넣어라.
- ⚠️ **한계**: 추론 시점 오버헤드(판정용 평문 spec 별도 유지)와 벤치 2종 범위 — 실제 프로덕션 툴셋 일반화는 추가 검증 필요.

![SafeKeep 흐름도. 위쪽은 기존 방식: 스키마 형식 tool spec이 내부 refusal 신호를 약화시켜 위험 요청도 툴 실행. 아래쪽은 SafeKeep: 요청을 두 갈래로 분리해 안전 판단은 flatten한 평문 spec으로, 툴 실행은 원래 스키마 spec으로 수행. 하단 막대는 거부율 23.8%에서 70.6%, 주입 공격 성공률 25.6%에서 2.5%.](/images/ai-news-2026-08-04/safekeep-flow.svg)
*스키마 형식이 refusal을 흐리게 한다 — 판단은 평문으로, 실행은 스키마로 분리. 수치는 arXiv 2607.29254 초록 기준. (자체 제작 SVG)*

## 2) AMTFV — "툴 플로우로 답을 검증하라"

- **저자**: Rui Zou, Yutao Zhu, Mengqi Wei, Ji-Rong Wen (4인)
- **arXiv**: [2607.29549](https://arxiv.org/abs/2607.29549) · category `cs.AI` · 2026-07-31
- **핵심 기여**: LLM의 수학 답안을 신뢰성 있게 **검증**하는 건 여전히 어렵다. 자연어 reflection은 정확한 계산을 못 받치고, 검증 프로그램 직접 생성은 **모델링과 저수준 구현을 너무 일찍 결합**한다. AMTFV는 그 사이를 끊는다.
- **방법(2–3줄)**: **Mathematical Tool Flow(MTF)**를 **interrupt–execute–resume 인터페이스**로 도입해 **검증 모델링과 실행을 분리**한다. 검증 에이전트가 워크플로우를 짜고 계산 의도를 MTF 요청으로 보내면, 툴박스 에이전트가 실행 가능한 호출로 파싱해 백엔드에서 **정확 계산**을 수행하고, 그 결과로 답안·워크플로우를 교정한다.
- **핵심 결과(검증)**: 5개 수학 추론 데이터셋 · DeepSeek/GPT/Gemini 7개 구성에서 전반적으로 대표 베이스라인 상회. 단일 구성 기준 **평균 정확도 최대 +8.3%p**, 중·고난도 검증 샘플에서 이득이 더 큼.
- 🛠 **agent-builder 시사점**: LLM이 "스스로 검산"하게 두지 말고, **검증 단계에 결정론적 툴 호출**을 끼워라. 툴 플로우를 실행 세부와 분리하면 검증 로직을 재사용·감사하기 쉽다.
- ⚠️ **한계**: 수학 도메인·정확 계산 툴박스 전제 — 계산으로 환원 안 되는 도메인엔 그대로 적용 어려움.

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — Security / 최소권한 샌드박스

- **출처**: [developers.openai.com/codex/config-basic](https://developers.openai.com/codex/config-basic)
- 💡 **core idea**: 에이전트의 기본 권한을 **좁게** 시작하라. 툴이 만질 수 있는 파일·네트워크를 좁히면, 프롬프트 주입이 성공해도 **피해 반경**이 작다.
- 📝 **how-to**: 미검증 MCP 서버·낯선 리포를 다룰 땐 read-only로 시작하고, 필요할 때만 승인/승격.

```bash
# 파일 읽기만 허용, 네트워크·쓰기 차단 (조사·리뷰용 기본값)
codex --sandbox read-only

# 워크스페이스 안에서만 쓰기 허용, 위험 명령은 승인 요청
codex --sandbox workspace-write --ask-for-approval on-request
```

- 🎯 **when**: 신뢰도 낮은 코드베이스 탐색, 새 MCP 서버 첫 연결, 자동화 파이프라인.
- ⚠️ **caveat**: `danger-full-access`는 **일회용 컨테이너**에서만. 정확한 config 키는 링크된 문서에서 확인.
- ⭐ **추천**: 팀 표준으로 "프로덕션 에이전트 = read-only 기본"을 못박아 두면 사고를 대부분 예방한다.

## 🟦 Claude Code — Permissions / deny·allow 규칙

- **출처**: [code.claude.com/docs/en/settings](https://code.claude.com/docs/en/settings)
- 💡 **core idea**: 툴 권한을 **파라미터 단위**로 명시하라. `Tool(pattern)` 매칭으로 위험 명령·비밀 파일을 아예 막고, 필요한 것만 allow.
- 📝 **how-to**: `.claude/settings.json`의 `permissions`에 deny를 우선 배치(denylist가 allowlist보다 우선).

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}
```

- 🎯 **when**: 비밀키·토큰이 있는 리포, 외부 네트워크 호출을 막고 싶은 자동화 세션.
- ⚠️ **caveat**: allow에 넓은 와일드카드(`Bash(*)`)를 두면 deny로 다 막기 어렵다 — **좁게 시작**하라.
- ⭐ **추천**: `.env`·`secrets/**` deny는 모든 리포 공통 베이스라인으로.

## 🟪 공통 — Eval / 안전 판단 ↔ 툴 실행 분리

- **출처**: [arxiv.org/abs/2607.29254](https://arxiv.org/abs/2607.29254)
- 💡 **core idea**: SafeKeep의 교훈을 프레임워크 무관하게 적용 — **위험도 판정용 컨텍스트**와 **실행용 컨텍스트**를 분리하라.
- 📝 **how-to**:
  1. 툴 카탈로그를 **평문 설명**으로도 유지(스키마와 별개).
  2. 실행 직전, 평문 spec + 사용자 요청으로 "허용/거부"를 먼저 판정.
  3. 새 MCP 서버는 붙이기 전 `mcp-scan`으로 툴 설명을 스캔.
- 🎯 **when**: 외부 툴·MCP를 다루는 모든 에이전트, 특히 실제 부수효과(파일/네트워크/결제)가 있는 액션.
- ⚠️ **caveat**: 판정용 평문 spec을 따로 관리하는 유지비가 든다 — 고위험 툴부터 우선 적용.
- ⭐ **추천**: 거부율·주입 ASR을 **리그레션 지표**로 잡아 A/B로 추적.
