# 📚 주목 논문

## Raven: 하네스를 만드는 하네스 (arXiv:2609.33439)

- **저자**: EverMind AI (기술 보고서) · cs.AI · 9/27 제출 · Hugging Face 데일리 1위(9/30, 업보트 450)
- **핵심 기여**: 하네스가 복잡해질수록 수작업 설계가 안 되고, 도메인에 밀착할수록 범용성이 죽는다 — 그래서 "더 강한 하네스"가 아니라 **하네스를 자동으로 만들고 경험으로 진화시키는 시스템**을 제안. 실행 가능한 "모델–하네스 쌍"을 합성 가능한 지능 단위로 취급합니다.
- **방법**: Host Agent가 목표를 분해해 도메인별 특화 하네스(Research/Code/Design/Oncall 등)에 위임하고, EverOS 메모리로 세션 간 컨텍스트·에이전트 경험을 보존하며 하네스 자체를 개선.
- 🛠 **시사점**: OpenAI가 Codex를 "하네스 엔지니어링"이라 부르기 시작한 흐름과 정확히 같은 방향. 하네스를 손으로 깎고 있다면, "하네스 생성·평가 루프를 자동화할 수 있는가"가 다음 질문입니다.
- **한계**: 단일 조직 보고서라 벤치마크가 자체 보고 중심 — 외부 재현 대기.
- [arXiv](https://arxiv.org/abs/2609.33439) · [코드 (Apache-2.0, v0.2.3)](https://github.com/EverMind-AI/Raven) — 9/30에도 커밋, 클론으로 검증

## 에이전트는 에이전트용 라이브러리를 설계할 수 있나 (arXiv:2609.36730)

- **저자**: Gabriel Orlanski, Alex L. Zhang, Frederic Sala, Aws Albarghouthi 외 7명 · cs.AI · 9/29 제출
- **핵심 기여**: 에이전트들은 서로의 코드를 **재사용하지 않고 재구현**하며 코드베이스를 불린다는 문제의식에서, 2단계 벤치마크 **LibraryDesignBench** 제안 — 에이전트가 스펙만 보고 라이브러리를 설계하면, 다른 모델 패밀리의 사용자 에이전트 3종이 그 라이브러리로 프로그램을 짜서 정확성·단순성을 채점.
- **결과**: 4개 언어, 15개 설계 태스크, 검증된 문제 242개. 15개 중 11개 태스크에서 에이전트 설계가 인간 프로덕션 라이브러리의 추상화를 재현. 그런데 사용자 에이전트들은 인간산·에이전트산 가리지 않고 **라이브러리를 채택하고도 덜 활용**하며 기능을 재구현.
- 🛠 **시사점**: 문제는 설계 능력이 아니라 **재사용 습관**입니다. 아래 공통 팁 참고.
- **한계**: 저자 소속은 arXiv 미표기, 채점이 사용자 에이전트 3종 구성에 민감할 수 있음.

**1. 🟩 Codex · Debugging/Eval — skill 사용을 OpenTelemetry로 관측**

- 출처: [커밋 0a76a25 (9/30)](https://github.com/openai/codex/commit/0a76a2520f45af68b7a5386688a9714af0a3ccd2)
- 💡 Codex가 `codex.skill_invocation` 로그 이벤트를 방출하기 시작했습니다. 명시적으로 주입한 skill뿐 아니라 **암묵적으로 감지된 사용**(skill 도구를 통한 읽기 포함)까지 기록.
- 📝 이벤트에는 skill 이름, `invocation_type`(explicit/implicit), 대화·턴 ID, 모델 메타데이터가 담기고, skill 내용·프롬프트·툴 인자는 제외됩니다. 기존 OTel 익스포터 설정을 그대로 타므로 별도 옵트인이 없습니다:

```toml
# config.toml — 이미 OTel을 쓰고 있다면 추가 설정 없이 방출됨
[otel]
exporter = "none"   # 이렇게 꺼두면 skill 이벤트도 안 나감
```

- 🎯 팀 공용 skill을 여러 개 배포했다면: 어떤 skill이 실제로 호출되는지 대시보드를 만들어 안 쓰이는 것을 정리하고, skill 사용과 태스크 성공률·비용의 상관을 볼 때.
- ⚠️ 암묵적 사용 감지는 best-effort고 턴 내 중복 제거됩니다 — "성공적으로 쓰였다"가 아니라 "사용이 감지됐다"는 신호입니다.
- ⭐ 추천도: 상 — 상세는 저장소의 `codex-rs/otel/README.md`.

**2. 🟦 Claude Code · Workflow — 2.1.286, 헤드리스의 모델 장애 내성**

- 출처: [v2.1.286 릴리즈](https://github.com/anthropics/claude-code/releases/tag/v2.1.286)
- 💡 API가 기본 모델(또는 별칭이 가리키는 모델)을 거부하면 **같은 티어의 이전 모델로 1회 자동 재시도**하고, `--fallback-model`은 fast 실행이 불가하면 standard 속도로 내려서 계속 돕니다.
- 📝 야간 배치·CI라면 폴백을 명시해 두는 편이 안전합니다:

```bash
claude -p "리포트 생성 작업" --fallback-model claude-sonnet-5-5
```

- 🎯 모델 디프리케이션·일시 거부·과부하로 자동화 파이프라인 전체가 죽는 일을 막을 때. 사흘 연속 신모델이 쏟아지는 지금 같은 주간에 특히.
- ⚠️ 폴백으로 돈 턴의 산출물은 품질 기준이 다를 수 있으니, 로그에서 폴백 발생 여부를 확인하는 습관을.
- ⭐ 추천도: 상 — 이번 릴리즈에는 stacked 권한 프롬프트의 "2 of 5" 표시 등 UX 개선도 포함.

**3. 🟪 공통 · Context — "reuse-first" 규칙을 명시하라**

- 출처: [LibraryDesignBench (arXiv:2609.36730)](https://arxiv.org/abs/2609.36730)
- 💡 에이전트는 라이브러리를 잘 설계하고도, 쓸 때는 **채택만 하고 재구현**하는 경향이 측정됐습니다. 재사용은 기본값이 아니라 지시해야 나오는 행동입니다.
- 📝 시스템 프롬프트나 AGENTS.md에 두 가지를 추가: ① "새 구현 전에 기존 유틸/라이브러리 검색 → 있으면 그것을 사용, 없을 때만 구현" ② 프로젝트 핵심 유틸의 **인벤토리 목록**(이름 + 한 줄 용도). 리뷰 단계에서 "기존 API 중복 구현" 항목을 체크리스트에 넣으면 회귀를 잡을 수 있습니다.
- 🎯 여러 에이전트가 같은 코드베이스에 장기간 커밋하는 프로젝트일수록 효과가 큽니다.
- ⚠️ 인벤토리가 낡으면 오히려 해가 되니, 생성 스크립트로 주기 갱신을.
- ⭐ 추천도: 상
