1. 도입 — "요약은 하네스의 규칙, 조회는 모델의 프로그램"

긴 세션을 굴리는 에이전트라면 예외 없이 마주치는 순간이 있습니다. 컨텍스트 윈도우가 차오르고, 하네스가 지난 대화를 요약본으로 눌러 담고, 몇 턴 뒤 모델이 이렇게 말하는 순간요. "말씀하신 파일 경로를 다시 알려 주시겠어요?" 분명히 세션 초반에 나온 정보인데, 요약을 거치며 사라진 겁니다.

이번 주 X(트위터)의 AI 엔지니어링 타임라인에서는 이 오래된 고통에 새 이름표를 붙인 논문 하나가 돌았습니다. Rohan Paul의 스레드가 던진 질문이 요지를 잘 요약합니다. "컨텍스트 관리가 하네스가 적용하는 규칙이 아니라, 모델이 작성하는 프로그램이라면 어떨까?" 대상은 Alibaba가 8월 21일 공개한 Context as an Environment: Programmatic Context Management for Long-Horizon Agents(Yin Lin, Elaine Ang, Erkang Zhu, Bolin Ding, Jingren Zhou — arXiv:2608.21690), 시스템 이름은 Scroll입니다.

Scroll의 제안을 한 문장으로 줄이면 이렇습니다. 히스토리는 무손실로 남기고, 프롬프트에 넣을 것은 모델이 코드를 써서 그때그때 꺼내 오게 하라. 요약처럼 "쓰기 시점에 중요한 걸 미리 맞히는" 게임을 그만두고, "질문이 온 다음에 필요한 걸 조회하는" 게임으로 갈아타자는 겁니다. 데이터베이스 엔지니어라면 익숙한 관점이죠 — 원본 테이블을 지우고 요약 테이블만 남기는 시스템은 없으니까요.

이 글에서 얻어 갈 것. ① 컴팩션·외부 메모리·긴 윈도우라는 기존 3대 해법이 공유하는 구조적 약점, ② Scroll의 네 가지 설계 부품(이벤트 로그·퍼시스턴트 커널·print 투영·eviction landmark), ③ LongMemEval 94.8% 같은 숫자를 읽을 때 확인할 조건, ④ 프레임워크 없이 50줄로 만들어 보는 장난감 버전과 지금 하네스에 이식할 아이디어 세 가지.

2. 배경 — 컨텍스트가 넘칠 때 우리가 쓰던 세 가지 방법과 공통 약점

먼저 문제를 정확히 놓고 갑시다. 에이전트가 몇 시간, 며칠짜리 과제를 굴리면 대화·도구 출력·중간 산출물이 쌓여 세션 히스토리가 컨텍스트 윈도우를 훌쩍 넘어갑니다. 지금까지 업계의 대응은 크게 세 갈래였습니다.

  • 더 큰 윈도우 — 모델의 컨텍스트 한도를 키웁니다. 하지만 창이 커져도 채우면 그만이고, 길게 채울수록 성능이 미끄러지는 컨텍스트 부패(context rot)가 따라옵니다. Lost in the Middle 이후 반복 확인된 현상입니다.
  • 컴팩션(compaction) — 윈도우가 차면 지난 히스토리를 LLM으로 요약해 갈아 끼웁니다. Claude Code의 auto-compact가 대표적이고, Anthropic과 OpenAI 모두 공식 기능으로 제공합니다. 자세한 내용은 컴팩션 글에서 다뤘습니다.
  • 외부 메모리 — 중요해 보이는 내용을 벡터 DB나 메모리 저장소에 적어 두고 검색으로 되찾습니다. 메모리 통합 글에서 다룬 계열입니다.

Scroll 논문이 겨누는 지점은, 뒤의 두 방법이 공유하는 공통 전제입니다. 요약이든 메모리 쓰기든, "이건 나중에 필요할 테니 남기자"는 판단을 쓰기 시점(write-time)에 내립니다. 그런데 나중에 어떤 질문이 올지는 그 시점엔 모릅니다. 요약기가 "테스트 12개 통과"라고 눌러 담는 순간, "그중 스킵된 테스트 이름이 뭐였지?"라는 미래의 질문은 답을 잃습니다. 요약은 비가역 손실 압축이고, 손실된 비트는 프롬프트를 아무리 잘 써도 복원되지 않습니다.

비유하자면 이렇습니다. 회의가 끝날 때마다 녹음 원본을 지우고 회의록만 남기는 회사와, 원본은 아카이브에 두고 필요할 때 해당 구간을 다시 듣는 회사. 전자는 회의록 작성자의 안목에 미래가 걸려 있고, 후자는 "잘 찾는 능력"만 있으면 됩니다. 기존 컨텍스트 관리 대부분이 전자였습니다.

낯익은 방향이라면 맞습니다. 컨텍스트를 프롬프트 밖 변수로 두고 코드로 다루는 흐름은 이 블로그에서도 여러 번 스쳤습니다. RLM은 긴 컨텍스트를 REPL 변수로 놓고 모델이 코드로 뒤지게 했고, MCP 코드 실행은 도구 출력을 프롬프트에 통과시키지 않고 코드 안에서 처리했습니다. Scroll은 이 아이디어를 "세션 히스토리 관리" 전체로 확장해 하나의 시스템으로 조립한 논문입니다. Context-Folding, AgentProg 같은 선행 연구와 같은 계보로 읽으면 됩니다.

3. Scroll의 세 부품 — 이벤트 로그 · 살아 있는 커널 · print 투영

Scroll은 세션을 문자열 버퍼가 아니라 실행 가능한 환경(Session Environment)으로 취급합니다. 그 환경은 세 부품으로 이루어집니다.

① append-only 이벤트 로그(Event Log). 세션에서 일어난 모든 일 — 사용자 메시지, 모델 출력, 도구 결과 — 을 수정·삭제 없이 차곡차곡 기록합니다. 각 이벤트에는 안정적인 주소가 붙어서, 나중에 "그 지점"을 정확히 다시 열 수 있습니다. 이 로그가 무손실 원본(ground truth)입니다. 요약본이 히스토리를 대체하는 컴팩션과 달리, 원본은 항상 살아 있습니다.

② 세션 내내 살아 있는 Python 커널. 샌드박스 안에서 커널 하나가 모델 호출 사이에도 죽지 않고 유지됩니다. 핵심은 커널이 들고 있는 타입 있는 네임스페이스입니다. 도구 출력, 로그에서 되찾은 히스토리, 중간 계산 결과가 매 호출마다 프롬프트에 직렬화되는 대신 df, test_results 같은 변수로 묶여 남습니다. Jupyter 노트북을 떠올리면 정확합니다 — 셀을 100번 실행해도 변수는 커널에 계속 있죠.

③ working view와 print 투영. 모델이 실제로 읽는 프롬프트(working view)에는 커널 상태 전체가 아니라, 모델이 쓴 코드가 exec로 실행되면서 명시적으로 print한 결과만 들어갑니다. 논문은 이를 투영(projection)이라 부릅니다. 100MB짜리 데이터가 변수에 있어도, 모델이 print(df.describe())를 골랐다면 컨텍스트에 들어가는 건 요약 통계 몇 줄뿐입니다.

이 구조에서 눈여겨볼 점 하나. "무엇을 컨텍스트에 남길까"라는 문제가 프롬프트 튜닝 문제에서 코딩 문제로 바뀝니다. 요약 프롬프트의 품질에 기대는 대신, 모델의 코드 작성 능력에 기대는 겁니다. 논문 표현을 빌리면 컨텍스트 관리가 "LLM의 향상되는 코딩 능력을 상속하는" 과제가 됩니다. 코딩 벤치마크가 오르는 속도를 생각하면 꽤 영리한 베팅입니다.

4. 한 턴이 흘러가는 방식 — 그리고 eviction landmark

부품을 알았으니 한 턴을 따라가 봅시다. 사용자가 "아까 스킵된 테스트, 원인 정리해 줘"라고 물었다고 합시다.

  1. 질문이 이벤트 로그에 새 이벤트로 기록됩니다.
  2. 모델은 working view(최근 대화 + 이전 투영들)를 보고, 답에 필요한 정보가 손에 없다는 걸 압니다. 그래서 조회 코드를 씁니다 — 로그에서 테스트 실행 이벤트를 찾아 파싱하는 코드요.
  3. 커널이 코드를 exec로 실행합니다. 중간 결과는 변수로 네임스페이스에 남고, 모델이 print한 결과만 밖으로 나옵니다.
  4. 그 출력이 다음 호출의 working view에 붙습니다. 모델은 이제 근거를 손에 쥐고 답을 씁니다.

개념을 잡기 위한 예시 코드는 이런 모양입니다(논문의 실제 프롬프트가 아니라 이해를 돕는 가상 예시입니다).

{{< highlight python >}} # 모델이 작성해 커널로 보내는 조회 코드 (개념 예시) hits = log.search(kind="tool_result", query="pytest") # 이벤트 로그 검색 runs = [parse_pytest(e.payload) for e in hits] # 변수로만 유지 — 컨텍스트에 안 들어감 skipped = [t for r in runs for t in r.tests if t.status == "skipped"] # print한 이 몇 줄만 다음 호출의 working view에 들어간다 for t in skipped: print(f"{t.name}: {t.reason} (event {t.addr})") {{< /highlight >}}

여기서 "몇 시간짜리 세션이면 working view도 결국 차지 않나?"라는 질문이 나와야 합니다. Scroll의 답이 eviction landmark입니다. working view가 예산에 다가가면 오래된 구간(stale span)을 밀어내는데, 그냥 지우지 않습니다. eviction index에 "여기에 무엇이 있었는지"를 짧게 적은 랜드마크를 남기고, 그 랜드마크를 이벤트 로그의 정확한 주소에 연결해 둡니다. 나중에 그 내용이 필요해지면 모델은 로그 전체를 뒤지는 게 아니라 랜드마크를 보고 해당 주소로 직행합니다. 책을 통째로 다시 읽는 대신, 접어 둔 페이지를 펴는 겁니다.

컴팩션과의 차이가 여기서 선명해집니다. 컴팩션의 요약도 일종의 랜드마크지만, 원본이 없는 랜드마크입니다. Scroll의 랜드마크는 뒤에 무손실 로그가 버티고 있어서, 밀어내기(eviction)가 "잊기"가 아니라 "책갈피 꽂고 덮어 두기"가 됩니다.

5. 숫자 읽는 법 — 94.8%와 +37.4pt의 조건

논문이 내세우는 성적은 세 벤치마크에서 나옵니다. 각각 무엇을 재는지부터 알아야 숫자가 읽힙니다.

벤치마크무엇을 재나Scroll (Qwen3.8-Max 백본)
LongMemEval_S긴 다중 세션 대화에서의 장기 기억 — 정보 추출, 세션 간 추론, 시간 추론, 지식 갱신, 답변 보류(abstention) 5개 능력 (ICLR 2025)94.8%
BEAM_10M1M·10M 토큰 스케일의 초장기 메모리 — 선호 따르기, 모순 해소, 사건 순서 등 10개 카테고리73.1% (기존 발표된 최고 메모리 시스템 +5.1pt)
LOCA_256K환경 설명이 8K→256K 토큰으로 커질 때 에이전트가 버티는지 — 극단적 컨텍스트 증가 하의 과제 수행86.7% (기존 발표된 최고 장기 에이전트 +37.4pt)

인상적인 건 세 번째 줄입니다. LOCA-bench는 환경 묘사 자체가 256K 토큰까지 부풀 때 에이전트가 얼마나 무너지는지를 재는데, 여기서 +37.4pt라는 간격은 "요약을 잘한다"로는 설명이 안 됩니다. 원본을 잃지 않는 구조 자체가 극단적 스케일에서 이긴다는 신호로 읽는 편이 맞습니다. LongMemEval 원 논문이 상용 어시스턴트들의 정확도가 지속 대화에서 30%까지 떨어진다고 보고했던 걸 떠올리면, 94.8%는 체감이 되는 숫자입니다.

다만 조건을 같이 읽어야 합니다. ① 보고된 수치는 Qwen3.8-Max 단일 백본 기준입니다. 조회 코드를 얼마나 잘 쓰느냐에 성능이 걸려 있으니, 코딩이 약한 모델에서는 간격이 줄어들 수 있습니다. ② 세 벤치마크 모두 장기 기억·장기 과제 중심입니다. 짧은 세션에서는 커널·로그를 유지하는 오버헤드가 이득을 잠식할 수 있습니다. ③ 글 쓰는 시점 기준 공식 코드 저장소는 확인하지 못했습니다. 숫자의 독립 재현은 아직 없다고 보는 게 안전합니다.

6. 실전 — 장난감 버전 만들어 보기, 오늘 훔칠 아이디어

Scroll 자체는 아직 못 돌려 보지만, 핵심 메커니즘 — 죽지 않는 네임스페이스 + exec + print 투영 + 무손실 로그 — 은 표준 라이브러리만으로 흉내 낼 수 있습니다. 구조를 몸으로 이해하는 데는 이만한 게 없습니다.

{{< highlight python >}} import io, json, time, contextlib class ToySessionEnv: """Scroll의 뼈대만 흉내 낸 장난감: 이벤트 로그 + 퍼시스턴트 네임스페이스 + print 투영""" def __init__(self, log_path="events.jsonl"): self.log_path = log_path self.ns = {"log": self} # 커널 네임스페이스 — 호출 사이에도 유지 self.addr = 0 def append(self, kind, payload): # 모든 사건을 무손실로 기록 self.addr += 1 ev = {"addr": self.addr, "ts": time.time(), "kind": kind, "payload": payload} with open(self.log_path, "a") as f: f.write(json.dumps(ev, ensure_ascii=False) + "\n") return self.addr def search(self, kind=None, query=""): # 조회 코드가 쓰는 로그 검색 with open(self.log_path) as f: evs = [json.loads(l) for l in f] return [e for e in evs if (kind is None or e["kind"] == kind) and query in json.dumps(e["payload"], ensure_ascii=False)] def exec_code(self, code: str) -> str: """모델이 쓴 코드를 실행. 변수는 ns에 남고, print된 것만 반환된다.""" self.append("code", code) buf = io.StringIO() with contextlib.redirect_stdout(buf): exec(code, self.ns) # ⚠️ 실전에서는 반드시 샌드박스 안에서 projection = buf.getvalue() self.append("projection", projection) return projection # ← 이 문자열만 다음 프롬프트에 붙인다 env = ToySessionEnv() env.append("tool_result", {"tool": "pytest", "raw": "412 passed, 3 skipped ..."}) # LLM 호출부에서: working_view += env.exec_code(모델이_생성한_코드) print(env.exec_code( "hits = log.search(kind='tool_result', query='skipped')\n" "results = [h['payload']['raw'] for h in hits] # 변수로만 유지\n" "print(results[0][:60]) # 이 한 줄만 컨텍스트로\n" )) {{< /highlight >}}

50줄이 안 되지만 Scroll의 세 부품이 다 들어 있습니다. 에이전트 루프에 붙일 때는 시스템 프롬프트에 "정보가 필요하면 log.search()를 쓰는 코드를 작성하고, 컨텍스트에 남길 것만 print하라"는 규약을 넣으면 됩니다. 그리고 실제 하네스에 오늘 이식할 만한 아이디어는 세 가지입니다.

  • 큰 도구 출력은 변수로 받기. 10만 줄짜리 로그를 프롬프트에 통과시키지 말고, 코드 실행 환경의 변수에 묶은 뒤 조회 결과만 넘기세요. Anthropic의 code execution with MCP와 programmatic tool calling이 정확히 이 패턴입니다.
  • 버리기 전에 주소를 남기기. 컴팩션을 하더라도, 요약에 "원본: 세션 로그 파일 어느 구간"이라는 포인터를 함께 넣으세요. 요약이 랜드마크가 되고, 파일 시스템이 이벤트 로그가 됩니다. Claude Code가 긴 출력을 파일로 떨구고 경로만 컨텍스트에 남기는 것도 같은 원리입니다.
  • 요약 프롬프트 대신 조회 함수 다듬기. "요약을 더 잘 시키는 프롬프트"에 쓰는 시간을, 에이전트가 히스토리를 검색·파싱하기 좋은 헬퍼(search, slice, tail)를 깎는 데 옮겨 보세요. 후자는 모델이 좋아질수록 공짜로 좋아집니다.

7. 흔한 실수 · 팁

  • exec를 맨몸으로 돌리지 않기. 모델이 쓴 코드를 실행한다는 건 프롬프트 인젝션이 곧 코드 실행이 된다는 뜻입니다. 위 장난감 코드의 exec는 학습용이고, 실전은 반드시 격리된 샌드박스 안이어야 합니다. 코드 실행 샌드박스 글과 격리 설계 글에서 다룬 원칙이 그대로 적용됩니다.
  • print 폭주 조심. 모델이 print(df)로 데이터프레임 전체를 쏟으면 투영이 곧 컨텍스트 폭발입니다. 투영에도 토큰 상한을 걸고, 넘치면 잘라서 "…(총 N행, 전체는 변수 df)"처럼 축약해 돌려주세요.
  • 커널과 로그의 불일치. 커널이 죽으면 변수는 날아갑니다. 복구 가능하게 만들려면 상태의 원천은 항상 이벤트 로그이고, 커널 상태는 로그를 재생(replay)해 재구성할 수 있어야 합니다. "로그가 진실, 커널은 캐시"라는 원칙을 지키면 재현성 문제도 같이 풀립니다.
  • 짧은 세션에 오버엔지니어링하지 않기. 대화 수십 턴짜리 챗봇에 커널·로그·eviction 인덱스를 다 얹는 건 낭비입니다. 그림 3의 결정 기준을 먼저 통과하는지 보세요.
  • 조회 실패도 관측하기. 이 구조의 새로운 실패 모드는 "정보가 없어서"가 아니라 "정보는 로그에 있는데 조회 코드가 못 찾아서"입니다. 조회 코드가 빈 결과를 돌려준 비율을 따로 로깅해 두면, 헬퍼 함수를 어디부터 고칠지 보입니다.

8. 마무리 (TL;DR)

  • 요약·컴팩션·외부 메모리는 모두 "무엇이 중요한가"를 쓰기 시점에 정합니다. 미래의 질문을 모른 채 내리는 비가역 결정이라, 버린 디테일은 돌아오지 않습니다.
  • Alibaba의 Scroll(arXiv:2608.21690)은 세션을 실행 환경으로 취급합니다 — append-only 이벤트 로그(무손실 원본) + 세션 내내 살아 있는 Python 커널(변수 네임스페이스) + print 투영(모델이 쓴 조회 코드의 출력만 컨텍스트에).
  • working view가 차면 지우는 대신 eviction landmark를 남깁니다. 로그 주소로 연결된 책갈피라, 밀어내기가 "잊기"가 아니라 "덮어 두기"가 됩니다.
  • 성적은 LongMemEval_S 94.8%, BEAM_10M 73.1%(+5.1pt), LOCA_256K 86.7%(+37.4pt). 단, Qwen3.8-Max 단일 백본·장기 과제 중심 벤치마크·코드 미공개라는 조건과 함께 읽어야 합니다.
  • 오늘 훔칠 것: 큰 도구 출력은 변수로 받고, 버리기 전에 원본 주소를 남기고, 요약 프롬프트 대신 조회 헬퍼를 다듬으세요. 그리고 모델이 쓴 코드의 exec는 반드시 샌드박스 안에서.
