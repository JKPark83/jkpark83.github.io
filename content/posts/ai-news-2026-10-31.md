# 📚 주목 논문

## 1. Matched Capabilities, Different Behaviors (MICA)

- **저자**: Zhenning Shi, Liang Pang, Yongqi Li
- **arXiv**: [2610.34298](https://arxiv.org/abs/2610.34298) (cs.AI, 10/25 공개)
- **핵심 기여**: MCP와 CLI가 같은 연산을 노출해도 모델이 보는 표현이 다르면 행동이 달라지는지를 통제 실험으로 검증.
- **방법**: 하나의 시맨틱 액션 계약에서 MCP 버전과 CLI 버전을 자동 렌더링하고, 디코딩된 액션을 동일한 런타임으로 실행(MICA 프레임워크). 6개 모델 × 3개 인터랙티브 환경.
- **결과**: 능력을 맞췄는데도 과제 성능과 인터랙션 비용이 크게 갈렸다. 차이는 표면적 유효성(포맷 오류)을 넘어 액션 선택, 실패 경로, 복구 행동까지 이어진다.
- 🛠 **에이전트 빌더 시사점**: 같은 백엔드라도 MCP 툴로 줄지, 셸 명령으로 줄지는 성능 변수다. 모델·과제별로 A/B 측정할 것.
- **한계**: 환경 3개 규모의 실험이고, 초록 기준 구체 수치는 본문을 봐야 한다.

![MICA 실험 설계](/images/ai-news-2026-10-31/mica-mcp-cli.svg)

*하나의 액션 계약을 MCP/CLI 두 방식으로 렌더링해 동일 런타임에서 비교하는 MICA 구조.*

## 2. Your Benchmark Is an Empirical Measure Over Difficulty

- **저자**: Yifan Sun, Naicheng Yu, Jiawen Gong, Jingyan Shen, Huan Zhang
- **arXiv**: [2610.29927](https://arxiv.org/abs/2610.29927) (cs.LG, 10/21 공개)
- **핵심 기여**: 벤치마크를 "문항 모음"이 아니라 난이도 축 위의 경험적 분포로 본다. 실패 모드 두 가지를 공식화 — 의도한 난이도 분포와 다른 **measure mismatch**, 특정 난이도 구간이 비어 있어 국소적 진전을 못 잡는 **coverage gap**.
- **방법**: 두 실패 모드를 잡는 진단 지표 2종을 제안하고 이론적 보증 제공. 7개 도메인 25개 벤치마크의 문항 난이도를 추정해 분석.
- **결과**: 다수 벤치마크가 특정 난이도 구간에 암묵적으로 과대 가중되어 있어, 리더보드 결론을 그대로 믿기 어렵다.
- 🛠 **에이전트 빌더 시사점**: 내부 eval 셋도 난이도 분포를 그려볼 것. "점수 정체"가 실제 정체인지, 측정 공백인지 구분된다.
- **한계**: 문항 난이도 추정 자체에 의존하므로 추정 품질이 전제 조건.

# 🧑‍💻 Codex & Claude Code 실전 팁

### 🟩 Codex — deferred tool world state 기본 활성화

- **카테고리**: MCP / Context · **출처**: [commit 0e31c29](https://github.com/openai/codex/commit/0e31c29e2512dfe3d2a3fcec83160626772deca5) (10/30)
- 💡 **핵심**: 지연 로딩되는 MCP 툴 네임스페이스가 이제 기본으로 developer 컨텍스트의 tools 영역에 노출된다. 지금까지는 tool_search 설명 안에만 있었다.
- 📝 **방법**: 업그레이드만 하면 기본 동작이 바뀐다. 이전 방식(검색 설명에 디스커버리 메타데이터 유지)이 필요하면 feature flag를 명시적으로 끈다:

```toml
# ~/.codex/config.toml
[features]
deferred_tool_world_state = false
```

- 🎯 **언제**: MCP 서버를 여러 개 물려 쓰는 셋업. 모델이 "어떤 네임스페이스가 존재하는지"를 검색 없이 먼저 알게 되므로 툴 선택 경로가 달라질 수 있다.
- ⚠️ **주의**: 시스템 컨텍스트 구성이 바뀌므로 프롬프트 캐시 히트와 툴 선택 행동이 미묘하게 달라질 수 있다. 업그레이드 전후 비용·행동을 비교해볼 것.
- ⭐ **추천도**: MCP 헤비 유저라면 전후 비교 필수.

### 🟦 Claude Code — 작업 디렉터리 밖 쓰기 차단

- **카테고리**: Workflow / 권한 · **출처**: [CHANGELOG 2.1.314](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- 💡 **핵심**: 새 설정 `permissions.blockWritesOutsideWorkingDirectories`를 켜면 Write·Edit·NotebookEdit가 어떤 권한 모드에서도 작업 디렉터리 밖 경로를 거부한다.
- 📝 **방법**:

```json
// .claude/settings.json
{
  "permissions": {
    "blockWritesOutsideWorkingDirectories": true
  }
}
```

- 🎯 **언제**: 자동 승인 모드(auto/yolo)로 장시간 돌리는 세션, CI·스케줄 작업처럼 사람이 안 보는 실행. "홈 디렉터리의 엉뚱한 파일을 고쳐놨다" 류 사고를 구조적으로 막는다.
- ⚠️ **주의**: 스크래치 디렉터리 등 의도적으로 밖에 쓰는 워크플로가 있다면 먼저 작업 디렉터리에 포함시킬 것.
- ⭐ **추천도**: 무인 실행 세션에는 사실상 기본값으로 추천.

### 🟪 공통 — 툴 인터페이스도 eval 축이다

- **카테고리**: Eval / Workflow · **출처**: [arXiv 2610.34298](https://arxiv.org/abs/2610.34298)
- 💡 **핵심**: MICA 결과대로면 "MCP냐 CLI냐"는 취향이 아니라 측정 대상이다.
- 📝 **방법**: 자주 쓰는 작업 5~10개를 골라 같은 기능을 (1) MCP 툴, (2) 셸 명령 두 방식으로 노출하고 성공률·토큰 비용·실패 후 복구 횟수를 기록한다.
- 🎯 **언제**: 새 모델로 갈아탈 때, 또는 MCP 서버를 새로 붙일지 기존 CLI를 쓸지 고민될 때.
- ⚠️ **주의**: 모델별로 결과가 다르므로 한 모델의 결론을 다른 모델에 이식하지 말 것.
- ⭐ **추천도**: 반나절 투자로 인터페이스 결정 근거가 생긴다.
