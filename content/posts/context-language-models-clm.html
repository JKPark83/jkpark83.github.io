도입 — 요약이 지워 버린 그 한 줄

코딩 에이전트를 오래 돌려 본 분이라면 한 번쯤 겪었을 겁니다. 컨텍스트 창이 차서 하네스가 자동 compaction을 돌렸는데, 하필 그 요약이 "포트는 8081을 써야 한다"는 한 줄을 지워 버립니다. 모델은 다음 턴부터 태연하게 8080으로 돌아가고, 같은 디버깅을 처음부터 다시 합니다. 요약은 하네스가 했는데, 뭘 지우면 안 되는지는 모델만 알고 있었던 거죠.

이번 주 X와 Hacker News를 달군 논문은 바로 이 분업을 겨냥합니다. 9월 29일 University of Washington과 Meta Superintelligence Labs 연구진(Rulin Shao, Luke Zettlemoyer, Pang Wei Koh 등)이 공개한 Context Language Models(CLM)입니다. 1저자 Rulin Shao는 발표 스레드에서 이렇게 요약했습니다 — "컨텍스트 관리의 bitter lesson: 사람이 설계한 SOTA보다, 모델에게 컨텍스트 통제권을 통째로 주는 쪽이 이긴다." 공개 사흘 만에 공식 저장소가 스타 400개를 넘겼고, Hacker News 토론에 오르고, 다른 에이전트 프레임워크 저장소에는 벌써 "CLM 방식 넣어 달라"는 feature request가 달렸습니다.

핵심 아이디어는 허무할 만큼 단순합니다. 컨텍스트를 파일로 미러링해 모델에게 주고, 그 파일을 마음대로 고치게 둔다. 지우기, 고치기, 요약하기, 다시 꺼내 오기 — 전부 모델 마음입니다. 이 글에서는 이게 정확히 어떻게 동작하는지, 왜 기존 방식을 이기는지, 서빙 비용은 어떻게 되는지, 그리고 아직 남은 위험은 뭔지 순서대로 뜯어봅니다.

배경 — 컨텍스트 관리, 제어의 사다리

먼저 전제부터. LLM의 컨텍스트는 기본적으로 append-only입니다. 대화가 진행되면 턴이 뒤에 계속 붙기만 하고, 한 번 들어간 토큰은 수정되지 않습니다. 창이 유한하니 언젠가 넘치고, 넘치기 전에도 길어질수록 정확도가 떨어집니다(context rot). 그래서 장시간 도는 에이전트에는 반드시 컨텍스트 관리(context management)가 필요합니다.

지금까지의 해법들은 "누가 결정하느냐"를 기준으로 사다리처럼 배열할 수 있습니다.

1단이 지금 가장 흔한 방식입니다. 하네스가 규칙(창 사용률, 턴 수)에 따라 오래된 턴을 요약으로 교체합니다. 구현이 단순하고 예측 가능하지만, 도입부의 "포트 8081" 사고처럼 무엇이 중요한지 모르는 쪽이 지우개를 쥐고 있다는 구조적 문제가 있습니다. 이 블로그에서 다뤘던 compaction이 여기에 속합니다. 2단은 모델에게 메모리 도구를 줘서 "언제"는 모델이 정하게 하되, 가능한 연산은 저장·검색 등으로 고정된 방식입니다. CLM은 3단, 즉 연산 자체를 제한하지 않는 끝판입니다.

bitter lesson이 왜 여기서 나오나요? Rich Sutton의 원래 bitter lesson은 "사람이 지식을 하드코딩한 방법은 결국 계산과 학습에 밀린다"는 교훈입니다. CLM 저자들의 주장도 같은 구조입니다 — 컨텍스트 관리 '정책'을 사람이 규칙으로 설계하지 말고, 모델이 스스로 배우고 결정하게 두라는 것. 그래서 발표 스레드 제목이 "The Bitter Lesson for context management"였습니다.

메커니즘 — 컨텍스트를 파일로 미러링한다

CLM의 구현은 논문 제목의 거창함에 비해 놀랄 만큼 소박합니다. 새 아키텍처도, 특수 토큰도 없습니다. 기존 모델에 그대로 얹을 수 있는 약 40줄짜리 시스템 프롬프트와 파일 동기화 루프가 전부입니다.

  1. 미러링 — 매 턴, 라이브 컨텍스트(서버에 쌓인 대화 전체)를 작업 공간의 파일 하나로 그대로 내려씁니다. 파일 경로는 시스템 프롬프트에 적어 줍니다.
  2. 편집 — 모델은 평소처럼 토큰을 뒤에 이어 쓸 수도 있고, Bash나 Python으로 그 파일을 아무 데나 고칠 수도 있습니다. 중간 턴을 지우거나, 한 줄을 바꾸거나, 전체를 요약본으로 갈아 끼우거나 — 제한이 없습니다.
  3. 동기화 — 파일이 바뀌면 다음 모델 호출 때 그 내용이 곧 라이브 컨텍스트가 됩니다. 즉 모델이 방금 고친 파일이, 다음 턴에 자기가 읽을 프롬프트입니다.

이 설계의 영리한 점은 기존 도구 사용 능력을 재활용한다는 데 있습니다. 요즘 모델은 파일을 읽고, sed로 치환하고, Python으로 텍스트를 가공하는 일을 코딩 에이전트 훈련 덕분에 이미 잘합니다. 컨텍스트를 파일로 바꿔 주는 순간, 그 능력이 전부 "자기 컨텍스트 관리 능력"이 됩니다. 별도 하네스 로직을 새로 만들 필요가 없는 거죠. 저자 Pang Wei Koh는 이 점을 "no more harness engineering"이라고 표현했습니다.

왜 기존 방식으로는 안 되는지 보여 주려고, 논문은 네 가지 진단 과제를 먼저 제시합니다. 요점만 추리면 이렇습니다.

전부 "별것 아닌" 과제인데도, 고정된 연산만 가진 기존 방식은 어느 하나에서든 구멍이 납니다. 무제한 편집이 가능한 CLM만 네 과제를 모두 통과합니다.

결과 — 사람이 설계한 전략을 정확도·연산량 모두에서 이겼다

CLM은 세 가지 방법으로 만들 수 있습니다. ① 기존 모델에 40줄 프롬프트만 얹는 zero-shot, ② 컨텍스트 관리 요령을 자연어 지침으로 진화시키는 skill-optimization(스킬 최적화 루프로 지침을 다듬으면 held-out 과제 정확도가 최대 35.9포인트 상승), ③ 온라인 강화학습(stepwise GRPO)으로 아예 가중치에 정책을 굽는 방법입니다.

주목할 건 zero-shot만으로 이미 사람이 설계한 SOTA를 이긴다는 점입니다. 논문 초록 기준으로:

  • BrowseComp-Plus(웹 리서치) — 최강 베이스라인이었던 Codex식 요약 대비 정확도 상대 +11.4%, FLOPs는 21.5% 절감.
  • 12시간 EdgeBench(저장소 최적화, 검증기 피드백 포함 장기 과제) — 점수 +5%에 FLOPs 59% 절감. 논문 보고 기준 CLM은 179 PFLOPs로 44.6점, 요약 베이스라인은 437 PFLOPs를 쓰고도 42.3점이었습니다.
  • 24시간 멀티 저장소 agent swarm(에이전트 6개) — 같은 컴퓨트로 개선 폭이 65% 더 컸습니다.
  • RL까지 얹으면 — Qwen3.5-9B의 BrowseComp-Plus 성능이 28.8%에서 42.5%로(+47.6%), FLOPs는 오히려 12% 줄었습니다. 작은 모델도 정책을 가중치로 배울 수 있다는 증거입니다.

FLOPs가 줄어드는 이유는 직관적입니다. append-only에서는 쌓인 토큰 전부가 매 턴 prefill 비용으로 되돌아옵니다. CLM이 컨텍스트를 6~8K 토큰으로 유지하면, 그 작은 창이 수백 턴 내내 반복 과금되는 단가가 됩니다. 정확도 향상과 비용 절감이 한 동작에서 같이 나오는 구조입니다.

창발 전략 — 아무도 가르쳐 주지 않은 수법들

이 논문에서 제일 재미있는 부분은 숫자가 아니라 모델이 스스로 발명한 관리 전략들입니다. 프롬프트에는 "파일을 편집할 수 있다"고만 적혀 있을 뿐, 어떻게 쓰라는 지시는 없습니다. 그런데 관찰된 행동은 이렇습니다.

  • 상태 블록(scoreboard) — 서브에이전트들을 굴려 수학 문제를 풀던 모델이, 컨텍스트 맨 위에 "현재 최고 점수·에이전트 수·핵심 파일"을 담은 상태 블록을 만들어 두고 163번 제자리 갱신했습니다. 그동안 전체 컨텍스트는 6~8K 토큰으로 일정하게 유지됐습니다.
  • 자작 헬퍼 함수 — 오래된 턴들을 접는 compact_turns() 함수를 스스로 작성해 두고 과제 내내 37번 호출했습니다. 컨텍스트 관리를 재사용 가능한 코드로 추상화한 겁니다.
  • 내부 메모용 role 발명 — 대화 형식에 없던 새 chat role을 만들어 자기만 보는 노트를 구분해 두는 행동도 관찰됐습니다.

멀티 에이전트로의 확장도 우아합니다. 컨텍스트가 파일이라면, 에이전트 N개 = 컨텍스트 파일 N개입니다. 서브에이전트를 띄우고 싶으면 컨텍스트 파일을 하나 새로 만들면 되고, 끝내고 싶으면 그 파일을 지우면 됩니다. 오케스트레이터가 워커의 컨텍스트 파일을 직접 읽거나 고칠 수도 있습니다. 별도의 멀티 에이전트 프레임워크 없이, 파일 시스템이 곧 오케스트레이션 레이어가 되는 셈입니다.

이 블로그에서 다뤘던 Scroll의 프로그래머틱 컨텍스트 관리나 RLM(재귀 언어 모델)과 비교해 보면 위치가 선명해집니다. Scroll은 append-only 로그 위에 코드로 뷰를 만드는 쪽이고, RLM은 큰 컨텍스트를 변수로 두고 재귀 호출로 파고드는 쪽입니다. CLM은 더 급진적으로, 라이브 컨텍스트 자체를 가변(mutable) 상태로 만들어 버립니다.

서빙 문제 — 편집은 캐시를 깬다, Suffix Cache Reuse

여기까지 읽고 "그럼 당장 프로덕션에 넣자"가 안 되는 이유가 하나 있습니다. 프리픽스 캐시(prefix cache)입니다. vLLM·SGLang 같은 서빙 엔진은 이전 요청과 앞부분이 같으면 KV 캐시를 재사용해 prefill을 건너뜁니다(프롬프트 캐싱에서 다뤘던 그 원리입니다). 그런데 CLM이 컨텍스트 중간을 고치면, 고친 지점 이후의 캐시가 전부 무효가 됩니다. 어텐션의 위치 인코딩이 토큰 위치에 묶여 있어서, 뒷부분이 한 칸이라도 밀리면 기존 KV를 그대로 못 쓰기 때문입니다. 최악의 경우 턴마다 전체 재prefill — 모처럼 아낀 토큰을 캐시 미스로 도로 뱉는 꼴이 됩니다.

그래서 논문은 서빙 쪽 장치를 하나 같이 내놨습니다. Suffix Cache Reuse(SCR)입니다. 아이디어는 "일치하는 프리픽스까지만 재사용"이라는 기존 규칙을 깨고, 편집에서 살아남은 뒷부분(suffix)의 캐시도 재사용하는 것입니다. 살아남은 구간의 KV를 새 위치로 옮기고, RoPE(회전 위치 인코딩) 키를 새 위치 기준으로 다시 회전시켜 맞춥니다. 수학적으로 완전히 동일한 값은 아니지만, 논문 실험에서는 과제 성능을 유지하면서 표준 SGLang 대비 서버 측 연산을 35% 줄였습니다. 공식 저장소에 suffix_cache_reuse 모듈로 공개돼 있습니다.

정리하면 CLM의 비용 방정식은 "편집으로 아끼는 prefill − 편집이 깨는 캐시 + SCR의 회수분"입니다. API 과금(토큰 단가) 기준으로는 컨텍스트가 작아지는 것만으로 이득이 크지만, 자체 서빙이라면 SCR 같은 캐시 전략까지 묶어서 봐야 진짜 절감이 나옵니다.

실전 — 미니 CLM 루프 직접 만들어 보기

공식 구현을 쓰는 게 정석이지만, 원리를 몸으로 익히기엔 직접 40줄짜리 루프를 짜 보는 게 최고입니다. 핵심은 "매 호출 전에 파일에서 메시지를 다시 읽는다" 한 줄입니다.

{{< highlight python >}} import json, subprocess CTX_PATH = "context.json" # 라이브 컨텍스트의 미러 파일 SYSTEM = f"""너의 대화 컨텍스트 전체는 {CTX_PATH} 파일에 JSON으로 미러링되어 있다. run_bash 도구로 이 파일을 자유롭게 편집해도 된다 — 오래된 턴 삭제, 제자리 수정, 요약으로 교체 모두 가능하다. 편집 결과는 다음 턴부터 네가 읽을 컨텍스트가 된다. 중요한 제약·결정·상태는 반드시 파일에 남겨라.""" def save(messages): with open(CTX_PATH, "w") as f: json.dump(messages, f, ensure_ascii=False, indent=1) def load(): with open(CTX_PATH) as f: return json.load(f) messages = [{"role": "system", "content": SYSTEM}] save(messages) while not task_done(): messages = load() # ← 핵심: 모델이 고친 파일을 다시 읽는다 reply = llm(messages, tools=[run_bash]) # 평소 쓰는 LLM API 호출 if reply.tool_calls: for call in reply.tool_calls: out = subprocess.run(call.args["cmd"], shell=True, capture_output=True, text=True) messages.append(tool_result(call, out.stdout[-2000:])) else: messages.append({"role": "assistant", "content": reply.content}) save(messages) # 턴 결과를 다시 미러링 {{< /highlight >}}

모델이 run_bash로 context.json을 고치면, 다음 루프의 load()가 그 편집을 라이브 컨텍스트로 승격시킵니다. 이게 전부입니다. 논문 수준의 결과를 재현하려면 예산 리마인더(창 사용률 알림)와 편집 실패 시 롤백 정도를 더 얹으면 됩니다.

공식 구현으로 바로 돌려 보고 싶다면 facebookresearch/context-language-models를 받아서:

{{< highlight bash >}} pip install -e . # Harbor 태스크를 CLM 하네스(clm-minimal)로 실행 clm-harbor run -p -a clm-minimal -m openai/ \ --agent-kwarg api_base=http://localhost:8000/v1 {{< /highlight >}}

저장소에는 zero-shot 하네스(clm/clm_harness) 외에 in-context 학습(clm_icl), GRPO 학습 코드(clm_rl), SCR 서빙 패치(suffix_cache_reuse)가 함께 들어 있습니다. 라이선스는 CC BY-NC 4.0, 즉 비상업 조건이니 회사 프로덕션에 코드를 그대로 가져다 쓰기 전에 꼭 확인하세요(아이디어 자체를 직접 구현하는 것과는 별개 문제입니다).

흔한 실수 · 팁

  • 편집 비용을 공짜로 계산하지 마세요. 중간 편집 한 번은 그 지점 이후의 프리픽스 캐시를 날립니다. API 모델 위에서 흉내 낼 때는 편집을 턴마다 하지 말고, 창 사용률 임계(예: 70%)에서 몰아서 하는 쪽이 캐시 적중률을 덜 해칩니다.
  • self-injection을 경계하세요. CLM의 구조적 위험은 "모델이 다음 턴에 읽을 텍스트를 모델이 쓴다"는 점입니다. 모델이 쓴 요약에 지시문이 섞여 들어가 다음 턴에 시스템 지시처럼 작동한 사고는 이미 하네스 compaction에서도 보고된 바 있습니다. 컨텍스트 파일에서 지시형 문장을 걸러 내는 sanitize 단계, 그리고 시스템 프롬프트 영역은 편집 불가로 묶는 보호가 필요합니다. 논문도 이 방어는 숙제로 남겨 뒀습니다.
  • 벤치마크 숫자는 조건을 같이 읽으세요. CLM 쪽에만 예산 리마인더·롤백이 주어진 비대칭 비교라는 지적이 있고, 장기 과제 결과는 시드 수가 적습니다(EdgeBench best-of-3 등). "zero-shot으로도 이긴다"는 방향성은 탄탄하지만, 여러분 워크로드에서의 폭은 직접 재야 합니다.
  • 작은 모델에 바로 기대하지 마세요. 편집 전략의 질은 모델 능력을 따라갑니다. 9B급은 zero-shot만으로는 약하고, GRPO 학습을 얹어야 본 실력이 나왔습니다. 호스팅 프런티어 모델일수록 zero-shot CLM의 이득이 큽니다.
  • 지우기 전에 치워 두는 습관을 들이세요. 무제한 편집이라도 "삭제"보다는 "별도 파일로 옮기고 컨텍스트에서 제거"가 안전합니다. 나중에 필요하면 다시 꺼내 올 수 있고, 창발 전략 중에서도 성적이 좋았던 패턴입니다.

마무리 (TL;DR)

  • UW·Meta의 Context Language Models(arXiv:2609.37725, 9/29 공개)는 컨텍스트를 파일로 미러링해 모델이 Bash/Python으로 무제한 편집하게 하는 방식입니다 — 편집된 파일이 다음 턴의 라이브 컨텍스트가 됩니다.
  • 약 40줄 시스템 프롬프트의 zero-shot만으로 Codex식 요약 등 사람이 설계한 SOTA를 이겼습니다: BrowseComp-Plus 정확도 +11.4%·FLOPs −21.5%, 12시간 EdgeBench 점수 +5%·FLOPs −59%, 24시간 6-에이전트 swarm 개선 폭 +65%.
  • 모델은 상태 블록 163회 제자리 갱신, 자작 compact_turns() 헬퍼 같은 창발 전략을 만들어 냈고, 멀티 에이전트는 "컨텍스트 파일 N개"로 자연히 확장됩니다.
  • 중간 편집은 프리픽스 캐시를 깹니다. 논문은 살아남은 suffix의 KV를 재배치·RoPE 재회전으로 살리는 Suffix Cache Reuse로 SGLang 대비 서버 연산 35%를 회수했습니다.
  • 남은 숙제: 모델이 자기 컨텍스트에 지시를 심는 self-injection 방어, 비대칭 비교·적은 시드라는 평가 한계, 작은 모델의 약한 zero-shot 성능, 그리고 CC BY-NC 라이선스.
  • 방향은 분명합니다 — 컨텍스트 관리의 결정권이 하네스에서 모델로 넘어가는 중입니다. 하네스 엔지니어의 일은 "정책 설계"에서 "편집 가능한 환경과 안전장치 설계"로 옮겨 갑니다.
