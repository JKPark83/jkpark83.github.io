프롬프트 인젝션(prompt injection)은 대화가 끝나면 같이 끝납니다. 그런데 그 대화 중에 에이전트가 뭔가를 기억해 버렸다면? 거짓 한 줄이 메모리에 남아, 며칠 뒤 아무 상관 없어 보이는 질문에서 조용히 되살아납니다.

— 메모리를 붙이는 순간, 공격은 "지금 터지는 것"에서 "기다렸다 터지는 것"으로 바뀝니다.

요즘 에이전트에 장기 메모리(long-term memory)를 붙이는 건 거의 기본이 됐습니다. 사용자 선호를 기억하고, 지난 작업을 이어받고, 대화가 끊겨도 맥락을 유지하려면 메모리가 필요하죠. Mem0·Zep·Letta 같은 라이브러리, LangGraph·CrewAI 같은 프레임워크가 이걸 몇 줄로 만들어 줍니다. 에이전트 메모리 설계는 이미 한 번 다뤘습니다.

그런데 메모리에는 잘 안 보이는 뒷면이 있습니다. 에이전트가 "무엇을 기억할지"를 스스로 정하는데, 그 재료가 웹페이지·도구 응답·다른 사용자의 메시지처럼 믿을 수 없는 입력이라는 점입니다. 공격자가 거짓 사실이나 숨은 지시를 슬쩍 흘려 넣어 에이전트가 그걸 기억하게 만들면, 그 오염된 기억은 세션이 끝나도 저장소에 남습니다. 이게 메모리 포이즈닝(memory poisoning), 우리말로는 메모리·컨텍스트 오염입니다.

이 이야기가 2026년 7월 들어 다시 화제가 된 데는 이유가 있습니다. 하나, 메모리가 "옵션"에서 "기본 아키텍처"로 넘어오면서 공격 표면이 넓어졌습니다. 둘, OWASP가 Top 10 for Agentic Applications 2026에서 이걸 ASI06 — Memory & Context Poisoning으로 정식 등재했습니다. 셋, 지난 몇 주 사이 "심어 두고 나중에 터뜨리는" 공격을 다룬 연구가 여러 각도에서 쏟아졌습니다(TheNextWeb의 정리). junior 개발자가 지금 에이전트를 만든다면 반드시 알아야 할 주제가 된 셈이죠.

이 글은 메모리 포이즈닝을 처음부터 짚습니다. 왜 위험한지, 프롬프트 인젝션과 어떻게 다른지, 공격이 어떤 3단계로 작동하는지, 그리고 실제 코드로 다층 방어를 어떻게 짜는지 — 쉽고 자세하게 살펴봅니다.

1. 배경 — 에이전트에게 "기억한다"는 것

먼저 용어를 맞춥니다. 에이전트의 "메모리"는 컨텍스트 창(context window)과 다릅니다. 컨텍스트 창은 이번 호출에 모델이 실제로 읽는 토큰들이고, 대화가 끝나면 날아갑니다. 반면 메모리는 그 밖에 따로 저장해 두는 것 — 다음 대화, 다음 세션에서도 꺼내 쓰려고 DB에 적어 두는 정보입니다.

메모리의 동작은 보통 세 박자로 굴러갑니다. 쓰기(write) — 대화나 도구 결과에서 기억할 만한 걸 골라 저장소에 넣습니다. 관리(manage) — 요약하고, 오래된 걸 지우고, 중복을 정리합니다. 읽기(read) — 새 질문이 오면 관련 있는 기억을 검색해 컨텍스트 창에 끼워 넣습니다. 저장소는 대개 벡터 DB라, 읽기는 "질문과 의미가 가까운 기억 top-k 검색"입니다.

여기서 꼭 짚을 게 하나 있습니다. RAG 지식베이스도 사실상 메모리입니다. 에이전트가 답할 때 참고하려고 미리 넣어 둔 문서 인덱스든, 대화하며 쌓는 장기 기억이든, "저장해 뒀다가 검색해서 컨텍스트에 넣는다"는 구조가 같거든요. 그래서 메모리 포이즈닝은 장기 기억만이 아니라 RAG 인덱스까지 함께 노립니다.

한 줄 정리. 메모리 = "세션을 넘어 살아남는, 검색으로 다시 불러오는 저장소". 장기 기억이든 RAG 인덱스든 이 구조는 같고, 바로 그 지속성이 편리함이자 약점입니다.

2. 프롬프트 인젝션과 무엇이 다른가

프롬프트 인젝션은 이미 다뤘습니다. 믿을 수 없는 입력(웹페이지·도구 응답 등) 속에 "이전 지시는 무시하고 …" 같은 숨은 명령을 심어, 에이전트가 그걸 지금 이 대화에서 명령으로 따르게 만드는 공격이죠. 핵심은 데이터와 명령이 같은 자연어라 구분이 안 된다는 데 있습니다.

메모리 포이즈닝은 여기서 한 걸음 더 갑니다. 나쁜 입력이 이번 대화에서 당장 뭔가를 시키는 데서 그치지 않고, 에이전트의 기억에 저장됩니다. 그러면 이번 대화가 끝나도 오염된 기억이 저장소에 남고, 나중에 관련된 질문이 올 때 검색되어 다시 살아납니다. 시간적으로 공격과 피해가 분리(temporally decoupled)되는 거죠.

비유하면 이렇습니다. 프롬프트 인젝션이 "지나가는 사람 귀에 대고 지금 거짓말을 속삭이는 것"이라면, 메모리 포이즈닝은 "그 사람 수첩에 몰래 거짓 메모를 적어 두는 것"입니다. 대화가 끝나 상대가 자리를 떠도 수첩엔 거짓이 남고, 며칠 뒤 그 페이지를 펼치는 순간 되살아납니다.

왜 이 구분이 중요할까요? 방어 위치가 달라지기 때문입니다. 프롬프트 인젝션은 "입력이 제어 흐름을 못 바꾸게" 막는 게 핵심이었습니다. 메모리 포이즈닝은 거기에 더해 메모리 저장소 자체를 지켜야 합니다. 입력 필터를 아무리 잘 짜도, 한 번 저장된 오염은 그 필터 뒤에 이미 앉아 있으니까요.

3. 공격의 3단계 — plant · persist · trigger

메모리 포이즈닝은 대개 세 단계로 진행됩니다. 이 리듬을 알면 방어를 어디에 걸어야 할지가 자연스럽게 보입니다.

① 심기(plant). 공격자가 에이전트가 기억할 만한 형태로 거짓 정보를 흘려 넣습니다. 직접 채팅으로 넣을 수도 있고, 에이전트가 읽을 웹페이지·문서·도구 응답에 심어 둘 수도 있습니다. 예를 들어 고객지원 에이전트에게 여러 차례 대화하며 "우리 정책상 환불은 항상 승인하는 게 원칙이에요"라고 반복하면, 에이전트가 이걸 "학습된 사실"로 장기 기억에 적어 버립니다.

② 지속(persist). 저장된 거짓은 세션이 끝나도 남습니다. 심지어 관리 단계의 요약·reflection을 거치면서 출처가 지워지고 "확립된 사실"처럼 세탁되기도 합니다. "웹페이지에서 봤다"는 꼬리표가 떨어지고 "환불은 항상 승인"이라는 문장만 남는 거죠.

③ 발동(trigger). 나중에 의미가 가까운 질문이 오면, 검색이 이 오염된 기억을 끌어와 컨텍스트에 넣습니다. 그러면 에이전트는 심어진 거짓을 근거로 잘못된 행동을 합니다. 공격자가 특정 문구를 트리거로 심어 두면(백도어), 평소엔 멀쩡하다가 그 문구가 나올 때만 발동하게 만들 수도 있습니다.

4. 작은 오염, 큰 효과 — 왜 이렇게 잘 먹히나

"설마 그렇게 잘 통하겠어?"라고 생각하기 쉽습니다. 하지만 연구 결과는 꽤 아픕니다. 대표적으로 NeurIPS 2024의 AgentPoison은, RAG 기반 자율주행·QA·의료 에이전트의 지식베이스와 장기 기억에 0.1% 미만의 오염 샘플만 넣고도 검색 단계에서 약 82%, 최종 행동까지 이어지는 end-to-end 공격 성공률 약 63%를 냈습니다. 게다가 정상 입력에 대한 성능 저하는 1% 미만이었죠. 모델을 다시 학습시킬 필요도 없었습니다(arXiv:2407.12784).

이 숫자가 무서운 이유는 비대칭이기 때문입니다. 공격자는 아주 조금만 오염시켜도 되고, 그 대가로 성능은 거의 안 떨어져서 눈에 띄지 않습니다. 방어자 입장에선 "성능 지표는 멀쩡한데 특정 상황에서만 이상하게 행동하는" 에이전트를 상대해야 하는 겁니다.

지속성은 복리로 쌓입니다. 프롬프트 인젝션 한 번은 한 번의 피해로 끝나지만, 오염된 기억 하나는 발견해 지우기 전까지 모든 미래 세션에 영향을 줍니다. 여러 에이전트가 메모리를 공유한다면(멀티 에이전트), 한 곳의 오염이 팀 전체로 번지기도 합니다(OWASP ASI07·ASI08과 맞물리는 지점).

5. 방어 설계 — 메모리 저장소를 지키는 다섯 겹

정답은 "한 방"이 아니라 다층 방어(defense in depth)입니다. 공격이 여러 단계라, 방어도 여러 겹으로 걸어 각 단계마다 마찰을 줍니다. 실무에서 자주 쓰는 다섯 겹을 순서대로 봅니다.

① 쓰기 시 검증(validate on write). 가장 중요한 겹입니다. "무엇을 기억할지"를 그냥 통과시키지 말고 게이트를 겁니다. 믿을 수 없는 출처(웹·도구 응답)에서 나온 내용은 "사실"로 저장하지 않거나, 저장하더라도 낮은 신뢰로 표시합니다. 정책·권한·안전에 관한 문장은 애초에 대화에서 배우지 못하게 막습니다("환불 규정을 바꾸라"는 건 대화가 아니라 코드/설정에서 옵니다).

② 출처 이력(provenance) 부착. 모든 기억 항목에 어디서 왔는지를 태그로 답니다 — 출처, 저장 시각, 신뢰 수준, 검증 상태. 나중에 "이 결정이 어떤 기억 때문이었나"를 역추적할 수 있고, 오염이 발견되면 같은 출처의 기억을 한꺼번에 격리할 수 있습니다. provenance가 없으면 요약을 거치며 "웹에서 봤다"가 지워지고 "사실"로 둔갑합니다.

③ 신뢰 점수 + 시간 감쇠(trust scoring & decay). 각 기억(또는 각 출처)에 신뢰 점수를 매기고, 행동 신호에 따라 올리고 내립니다. 오래된 기억이나 검증 안 된 기억은 신뢰를 시간에 따라 감쇠시켜, 낡은 한 줄이 영원히 진실 행세를 못 하게 합니다.

④ 신뢰 기반 검색(trust-aware retrieval). 읽기 단계에도 게이트를 겁니다. 의미가 가깝다고 무조건 컨텍스트에 넣지 말고, 신뢰 임계값을 넘는 기억만 넣습니다. 검색이 오염을 끌어오더라도 여기서 한 번 더 걸러집니다.

⑤ 격리 + 감사(segmentation & audit). 메모리를 사용자·작업·도메인별로 네임스페이스로 분리해, 한 사용자의 오염이 다른 사용자에게 새지 않게 합니다. 그리고 모든 쓰기/검색을 로그로 남겨, 사후에 "언제 무엇이 심어졌나"를 감사할 수 있게 합니다. 최근 연구는 여기서 더 나아가 쓰기 시 HMAC로 출처를 서명하고, 검색 결과를 무작위로 일부 빼 가며 다수결로 판정하는 식의 인증된 방어까지 제안합니다(7월 연구 물결 정리).

고르는 법. 다 붙이면 좋지만, 딱 하나만 먼저 한다면 ① 쓰기 시 검증입니다. 저장소에 오염이 들어가기 전에 막는 게 가장 싸고 확실하거든요. 그다음 ②provenance와 ④신뢰 기반 검색을 얹으면, "들어와도 추적되고, 추적돼도 안 쓰인다"는 두 겹이 더 생깁니다.

6. 실전 예제 — 100줄짜리 memory firewall

말로만 하면 감이 안 오니, 위 다섯 겹 중 핵심을 담은 작은 memory firewall를 만들어 봅니다. 프레임워크와 무관하게 개념이 보이도록 순수 파이썬으로 씁니다. 먼저 쓰기 단계 — 무엇을 기억할지 게이트하고 provenance를 붙입니다.

{{< highlight python >}} import time, re # 정책/권한을 바꾸려는 문장은 대화에서 "사실"로 배우지 않는다. # (진짜 정책은 코드·설정에서 오지, 사용자 채팅에서 오지 않는다) POLICY_PATTERNS = [ r"항상|무조건|always|never", # "환불은 항상 승인" 류 r"규정|정책|policy|권한|permission", r"이전 지시|무시|ignore|override", # 인젝션 냄새 ] def classify_source(source: str) -> float: """출처별 기본 신뢰도. 사용자 직접 입력·도구 응답은 낮게 잡는다.""" return { "system": 1.0, # 코드/설정에서 온 값 (가장 믿음) "user_verified": 0.8, # 본인 확인된 선호 등 "user_chat": 0.4, # 그냥 대화 중 언급 "tool_output": 0.3, # 도구/MCP 응답 "web": 0.2, # 웹페이지 (가장 안 믿음) }.get(source, 0.2) def memory_write_gate(text: str, source: str) -> dict | None: """쓰기 시 검증 + provenance 부착. 통과 못 하면 None(저장 안 함).""" trust = classify_source(source) # ① 정책·권한을 바꾸려는 문장은 믿을 수 없는 출처에서 오면 거부 if trust < 0.8 and any(re.search(p, text) for p in POLICY_PATTERNS): return None # 저장 자체를 막는다 (가장 싼 방어) # ② 통과하면 출처 이력(provenance)을 함께 저장 return { "text": text, "source": source, # 어디서 왔나 "trust": trust, # 신뢰 점수 "ts": time.time(), # 언제 저장했나 "verified": source in ("system", "user_verified"), } {{< /highlight >}}

핵심은 memory_write_gate가 None을 돌려줄 수 있다는 점입니다. "환불은 항상 승인" 같은 정책 문장이 web이나 user_chat에서 오면 아예 저장하지 않습니다. 통과한 기억에도 source·trust·ts를 붙여 두어, 나중에 추적·감쇠·격리가 가능해집니다.

다음은 읽기 단계 — 검색해 온 기억을 신뢰 임계값과 시간 감쇠로 한 번 더 거릅니다.

{{< highlight python >}} HALF_LIFE = 30 * 24 * 3600 # 30일이면 신뢰가 절반으로 (검증 안 된 기억) def effective_trust(mem: dict, now: float) -> float: """검증 안 된 오래된 기억은 신뢰를 시간에 따라 낮춘다.""" if mem["verified"]: return mem["trust"] # 검증된 건 감쇠 없음 age = now - mem["ts"] decay = 0.5 ** (age / HALF_LIFE) # 지수 감쇠 return mem["trust"] * decay def trust_aware_retrieve(candidates: list[dict], threshold: float = 0.35) -> list[dict]: """의미가 가까워도, 신뢰 임계값을 넘는 기억만 컨텍스트에 넣는다.""" now = time.time() kept = [m for m in candidates if effective_trust(m, now) >= threshold] # 감사 로그: 걸러 낸 기억을 남긴다 (사후 분석용) for m in candidates: if m not in kept: log_filtered(m) # "무엇이 왜 걸러졌나" return kept {{< /highlight >}}

이제 흐름이 완성됩니다. 쓰기 때 memory_write_gate로 들어오는 것을 막고, 읽기 때 trust_aware_retrieve로 나가는 것을 막습니다. 설령 낮은 신뢰로 저장된 오염이 있어도, 검색 단계에서 임계값에 걸려 컨텍스트에 안 들어가거나, 시간이 지나며 감쇠해 밀려납니다. 한 겹이 뚫려도 다음 겹이 받쳐 주는 구조죠.

실무 팁. Mem0·Zep·LangGraph 같은 걸 쓴다면, 위 게이트를 메모리 add 콜백과 검색 후처리에 끼우면 됩니다. 핵심은 프레임워크가 아니라 "쓰기와 읽기 양쪽에 게이트를 둔다"는 패턴입니다. threshold·HALF_LIFE 같은 손잡이는 반드시 평가셋으로 오탐/미탐을 재 가며 맞추세요.

7. 흔한 실수 · 팁

  • RAG 인덱스는 안전하다는 착각 — 장기 기억만 지키고 RAG 지식베이스는 무방비인 경우가 많습니다. 인덱싱도 "쓰기"입니다. 크롤링·업로드로 들어오는 문서에도 write gate를 거세요.
  • 요약·reflection이 오염을 세탁한다 — 관리 단계에서 여러 기억을 요약하면 출처 태그가 사라지고 "확립된 사실"만 남습니다. 요약 결과에도 provenance를 상속시키고, 근거가 낮은 신뢰뿐이면 요약도 낮은 신뢰로 두세요.
  • 프롬프트 인젝션 방어만으로 됐다고 생각 — 입력 필터는 "심기"를 줄일 뿐, 이미 저장된 오염엔 무력합니다. 저장소 쪽 방어(provenance·신뢰 검색·감사)가 따로 필요합니다.
  • "최신 = 진실" 가정 — 신뢰 점수 없이 최근 기억을 우선하면, 공격자는 그냥 방금 심으면 됩니다. 최신성과 신뢰는 별개 축으로 다루세요.
  • 사용자 간 메모리 공유 — 격리 없이 한 저장소를 여러 사용자가 쓰면, 한 명이 심은 오염이 모두에게 번집니다. 사용자·테넌트별 네임스페이스로 분리하세요.
  • 감사 로그 없음 — 오염이 터졌을 때 "언제 무엇이 심어졌나"를 못 찾으면 지울 수도 없습니다. 쓰기/검색을 provenance와 함께 기록해, 사후 감사와 일괄 격리가 가능하게 하세요.
  • 고위험 행동을 기억만 믿고 실행 — 환불·송금·삭제처럼 되돌리기 힘든 행동은, 근거가 검증 안 된 기억뿐이라면 사람 확인(human-in-the-loop)을 한 번 거치게 하세요.
방어도 만능은 아닙니다. 신뢰 임계값을 너무 높이면 정상적인 학습(사용자 선호 기억 등)까지 막혀 에이전트가 "금붕어"가 됩니다. 반대로 너무 낮추면 오염이 샙니다. 그래서 이건 측정으로 튜닝하는 문제입니다 — 정상 기억 유지율과 오염 차단율을 함께 보는 작은 평가·관측 세트를 두고 손잡이를 맞추세요.

8. 마무리 (TL;DR)

  • 에이전트에 장기 메모리·RAG 인덱스를 붙이면, "저장했다가 검색해 다시 쓰는" 그 지속성이 곧 새 공격 표면이 된다.
  • 메모리 포이즈닝은 프롬프트 인젝션과 달리 세션을 넘어 지속한다. 심은 거짓이 며칠 뒤 관련 질문에서 발동한다(시간차 분리). 그래서 입력 필터만으론 못 막는다.
  • 공격은 plant(심기) → persist(지속) → trigger(발동) 3단계. 요약·reflection이 출처를 세탁해 오염을 "사실"로 둔갑시키기도 한다.
  • 비대칭이 무섭다 — AgentPoison은 0.1% 미만 오염으로 최종 공격 성공률 ~63%, 정상 성능 저하는 1% 미만. 지표는 멀쩡해 보이는데 특정 상황만 뚫린다.
  • 방어는 다층으로 — ① 쓰기 시 검증 ② 출처 이력(provenance) ③ 신뢰 점수+시간 감쇠 ④ 신뢰 기반 검색 ⑤ 격리+감사. 하나만 먼저면 ①.
  • 핵심 패턴은 "쓰기와 읽기 양쪽에 게이트". 들어오는 것도 막고, 나가는 것도 거른다. 임계값은 평가셋으로 튜닝한다.
  • OWASP는 이걸 ASI06 — Memory & Context Poisoning으로 등재했다. 에이전트 보안 체크리스트에 반드시 넣자.
