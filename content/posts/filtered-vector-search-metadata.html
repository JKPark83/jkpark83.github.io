RAG는 잘 돌아가고 있었습니다. 그런데 “2024년 이후 문서만 찾아 줘”라는 요구가 들어와 WHERE created_at > '2024-01-01' 한 줄을 얹었더니 — 10개를 달라고 했는데 3개만 돌아옵니다. 그마저도 관련 없는 것들이죠.

— 버그가 아닙니다. 벡터 검색의 심장인 HNSW가 ‘그래프’라는 사실이 드러난 것뿐입니다.

1. 필터 한 줄에 결과가 비는 이유

실무 RAG에는 순수한 의미 검색만 있는 경우가 거의 없습니다. 거의 항상 메타데이터 필터(metadata filter)가 붙습니다 — “이 사용자의 문서만”, “2024년 이후만”, “공개 등급만”, “한국어만”처럼요. 벡터로 ‘의미가 비슷한 것’을 찾되, 그중 조건에 맞는 것만 골라야 하죠.

SQL 감각으로 보면 그냥 WHERE 한 줄입니다. 그런데 벡터 검색에서는 이게 생각보다 훨씬 까다롭습니다. 증상은 대개 셋 중 하나입니다.

  • 과소반환 — 10개를 요청했는데 3개만 돌아온다.
  • 정확도 저하 — 필터는 맞지만 정말 가까운 문서를 놓치고 애매한 게 올라온다.
  • 지연 폭발 — 필터를 걸었더니 오히려 검색이 몇 배 느려진다.

왜 이럴까요? 답은 검색 엔진이 벡터를 저장하는 방식에 있습니다. 수백만 개 벡터에서 ‘가장 가까운 것’을 매번 전부 비교해 찾으면(브루트포스) 너무 느리므로, 실무는 대부분 근사 최근접 이웃(ANN, approximate nearest neighbor) 인덱스를 씁니다. 그리고 가장 널리 쓰이는 ANN 인덱스가 바로 HNSW입니다. HNSW는 “그래프”라, 필터로 노드를 지우면 길이 끊깁니다. 이게 문제의 핵심입니다.

왜 요즘 화제인가. 2026년 들어 “filtered vector search”는 벡터 DB 진영의 단골 주제가 됐습니다. Weaviate가 필터드 검색을 가속하는 ACORN 전략을 정식 릴리스에 넣었고, Qdrant는 filterable HNSW를 다룬 상세 가이드를 냈으며, pgvector는 0.8.0에서 ‘과소반환’을 잡는 iterative index scan을 추가했습니다. 필터드 ANN을 제대로 평가하려는 벤치마크 논문도 잇달아 나왔죠. RAG가 멀티테넌시·권한·기간 필터를 달고 프로덕션으로 넘어가면서, “필터와 벡터 검색을 어떻게 함께 태우나”가 실무 talking point가 된 겁니다.

2. 배경 — HNSW는 ‘그래프’다 (한 문단 정리)

HNSW(Hierarchical Navigable Small World, 계층적 탐색 가능 소세계)는 이름은 거창하지만 발상은 단순합니다. 벡터 하나하나를 노드로 두고, 서로 가까운 벡터끼리 엣지(간선)로 이어 그래프를 만듭니다. 검색은 아무 노드에서 출발해 “질의와 더 가까워지는 이웃”으로 계속 걸어가는 그래프 탐색입니다. 지도에서 목적지에 가까워지는 길로만 이동하는 것과 같죠.

기억할 파라미터는 둘입니다. m은 노드마다 몇 개의 엣지를 둘지(보통 16). ef_search는 탐색 중 후보를 몇 개나 유지할지(보통 40 안팎)입니다. 여기서 이미 함정이 보입니다. 그래프 탐색이 제대로 되려면 노드들이 엣지로 촘촘히 연결돼 있어야 하는데, 필터는 바로 그 노드들을 없애 버립니다.

비유 하나. HNSW 그래프를 “징검다리”라고 생각해 보세요. 돌에서 돌로 건너 목적지에 갑니다. 필터를 건다는 건 조건에 안 맞는 돌들을 물에 잠기게 하는 것과 같습니다. 잠긴 돌이 몇 개면 돌아가면 되지만, 대부분이 잠기면 다음 돌까지 닿지 못하고 강 한복판에 갇힙니다. 필터드 벡터 검색의 어려움이 정확히 이겁니다.

3. 두 가지 순진한 방법과 각각의 실패

“벡터 검색 + 필터”를 처음 붙일 때 떠오르는 방법은 딱 둘입니다. 검색부터 하고 거르기(post-filter)와 거르고 나서 검색하기(pre-filter). 그런데 둘 다 순진하게 하면 앞의 증상들이 그대로 터집니다.

3-1. Post-filter (검색 후 필터) — 과소반환

먼저 HNSW로 상위 k개를 뽑고, 그다음 WHERE로 조건에 맞는 것만 남기는 방식입니다. 문제는 필터를 인덱스가 모른 채 검색이 끝난다는 겁니다. 예를 들어 ef_search=40으로 40개 후보를 봤는데, 그중 필터 통과율이 10%라면 평균 4개만 남습니다. 사용자는 10개를 원했는데 말이죠. 이게 pgvector 0.8.0 이전에 흔히 겪던 “결과가 LIMIT보다 적게 나오는” 대표적 상황입니다.

3-2. Pre-filter (필터 후 검색) — 브루트포스로 붕괴

반대로 WHERE로 먼저 후보 집합을 정하고, 그 안에서만 벡터 검색을 하는 방식입니다. 정확도는 보장되지만, 그 부분집합만을 위한 그래프 인덱스가 없다는 게 함정입니다. 결국 조건에 맞는 벡터를 하나하나 다 비교하는 브루트포스로 주저앉기 쉽습니다. 부분집합이 작으면 오히려 이게 빠르지만, 수십만 개면 검색이 몇 배로 느려집니다.

그래프 단절. 더 깊은 원인은 연결성입니다. m=16인 그래프에서 필터가 노드의 96%를 지우면, 살아남은 노드는 평균 엣지가 1개도 안 남습니다. 탐색은 몇 발짝 못 가 고립된 노드에 갇히고, 진짜 가까운 문서 근처엔 닿지도 못합니다. “정확도 저하”의 정체가 이겁니다.

4. 해법 — 필터를 ‘의식하는’ 검색

해법의 방향은 하나로 모입니다. 인덱스가 필터를 ‘알면서’ 탐색하게 만들자. 검색과 필터를 따로 떼지 말고, 그래프를 걷는 도중에 필터를 함께 반영하는 거죠. 요즘 벡터 DB들이 쓰는 방법은 크게 셋입니다.

  • 계속 더 뽑기(iterative) — 필터 통과분이 목표 개수를 채울 때까지 인덱스에서 후보를 더 끌어온다. 과소반환을 직접 해결.
  • 그래프 걷다가 건너뛰기(in-graph / two-hop) — 필터에 걸린 노드는 결과에서 빼되, 연결이 끊기지 않도록 그 노드를 건너뛰어(두 칸 점프) 옆으로 이어 간다.
  • 작으면 그냥 전부 비교(flat) — 필터 통과 후보가 아주 적으면, 그래프를 걷는 것보다 그 몇 개를 정확히 다 비교하는 게 더 빠르고 정확하다.

여기서 판단의 기준이 되는 개념이 선택도(selectivity)입니다 — 필터가 전체에서 얼마나 많이 ‘통과’시키는지를 뜻합니다. 통과분이 아주 적으면(선택도 낮음) flat이 유리하고, 많이 통과하면(선택도 높음) 그래프 탐색 + 인라인 필터가 유리합니다. 좋은 엔진은 이 선택도를 보고 전략을 자동으로 고릅니다.

5. 엔진별 접근 (pgvector·Qdrant·Weaviate)

같은 문제를 세 엔진이 조금씩 다르게 풉니다. 쓰는 스택에 맞춰 골라 보세요.

엔진핵심 기법한 줄 요약
pgvector (Postgres)iterative index scan (0.8.0+)목표 개수를 채울 때까지 인덱스에서 후보를 계속 더 끌어와 과소반환을 없앤다.
Qdrantfilterable HNSW + payload indexpayload 값별로 연결된 서브그래프를 미리 만들어 두고, 선택도에 따라 플래너가 전략을 고른다.
WeaviateACORN + 적응 전략엣지를 안 쳐내고 남겨 two-hop으로 건너뛰며, 후보 크기에 따라 flat/ACORN/sweeping 자동 선택.

pgvector는 가장 익숙한 선택입니다. 0.8.0의 iterative scan은 “한 번 뽑고 끝” 대신, 필터를 통과한 결과가 부족하면 인덱스에서 후보를 더 당겨옵니다. 모드는 셋 — off(옛 동작), strict_order(거리 순서 정확히 보존, 선택도 낮으면 느림), relaxed_order(개수는 맞추되 결과 안에서 순서는 근사). 실무 권장은 대개 relaxed_order입니다.

Qdrant는 좀 더 근본적으로 접근합니다. 자주 필터링하는 필드에 payload 인덱스를 만들면, Qdrant가 그 값별로 “연결이 보장된 서브그래프”를 그래프에 겹쳐 놓습니다. 그래서 brand = Apple 같은 필터를 걸어도 Apple 노드끼리 이미 이어져 있어 탐색이 안 끊깁니다. 질의 시엔 플래너가 필터 선택도(cardinality)를 보고 — 통과분이 적으면 payload 인덱스로 뽑고, 많으면 그래프를 걸으며 안 맞는 노드를 건너뛰는 in-place 필터를 씁니다.

Weaviate의 ACORN은 “두 칸 건너뛰기” 그 자체입니다. 보통 HNSW는 엣지를 가지치기(prune)하는데, ACORN은 엣지를 남겨 두고 필터에 걸린 노드를 two-hop으로 우회합니다. 게다가 후보 크기에 따라 세 전략을 자동으로 바꿉니다 — 아주 작으면 flat(그냥 전부 비교), 중간이면 ACORN, 크면 걸으며 검사하는 sweeping. 설정 없이 질의마다 알아서 고릅니다.

6. 실전 — 재현하고 고쳐 보기

말보다 코드가 빠릅니다. pgvector로 “과소반환”을 직접 재현하고 고쳐 봅시다. 먼저 문제 상황입니다.

{{< highlight sql >}} -- docs(embedding vector(768), created_at date, ...) 에 HNSW 인덱스가 있다고 하자 CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops); -- "2024년 이후 문서 중 질의와 가까운 10개"를 원한다 SELECT id, created_at FROM docs WHERE created_at > '2024-01-01' -- 메타데이터 필터 ORDER BY embedding <=> :query_embedding -- 벡터 거리순 LIMIT 10; -- 문제: 0.8.0 이전엔 인덱스가 top-k를 먼저 뽑고 필터를 나중에 적용 → -- 필터 통과분이 적으면 10개를 못 채우고 3~4개만 나온다. {{< /highlight >}}

pgvector 0.8.0 이상이라면 iterative scan 한 줄이면 해결됩니다. 세션에서 모드만 켜 주면, 부족할 때 인덱스가 후보를 더 당겨 목표 개수를 채웁니다.

{{< highlight sql >}} -- 개수를 맞추되 결과 안 순서는 근사 (대부분의 프로덕션 권장값) SET hnsw.iterative_scan = relaxed_order; -- 필요하면 얼마나 더 뽑을지 상한도 조절 (기본값을 늘리면 재현율↑, 속도↓) SET hnsw.max_scan_tuples = 20000; -- 같은 쿼리를 다시 실행 → 이제 10개가 채워진다 SELECT id FROM docs WHERE created_at > '2024-01-01' ORDER BY embedding <=> :query_embedding LIMIT 10; {{< /highlight >}}

Qdrant라면 “필터 필드에 payload 인덱스를 먼저 만든다”가 핵심입니다. 그래야 filterable HNSW의 필터 인지 엣지가 생깁니다.

{{< highlight python >}} from qdrant_client import QdrantClient, models client = QdrantClient(url="http://localhost:6333") # 1) 자주 거는 필터 필드에 payload 인덱스를 먼저 생성 (순서 중요!) client.create_payload_index( collection_name="docs", field_name="created_at", field_schema=models.PayloadSchemaType.DATETIME, ) # 2) 검색 시 filter를 그대로 넘기면, 플래너가 선택도를 보고 전략을 고른다 hits = client.query_points( collection_name="docs", query=query_vector, query_filter=models.Filter(must=[ models.FieldCondition( key="created_at", range=models.DatetimeRange(gt="2024-01-01T00:00:00Z"), ) ]), limit=10, ).points {{< /highlight >}}

세 경우 모두 공통점이 있습니다. “벡터 검색 따로, 필터 따로”를 애플리케이션에서 손으로 붙이지 말고, 엔진에게 필터를 그대로 넘겨 인덱스가 필터를 의식하게 만드는 것입니다. 직접 top-k를 뽑아 파이썬에서 if로 거르는 순간, 3장의 함정으로 되돌아갑니다.

7. 흔한 실수 · 팁

실수 1 — 애플리케이션에서 손으로 post-filter. “top 50 뽑아서 파이썬에서 걸러야지”가 가장 흔한 함정입니다. 선택도가 낮으면 50개로도 모자라고, 높이면 느려집니다. 필터는 엔진에 넘기세요. 그게 이 모든 최적화가 동작하는 전제입니다.

실수 2 — 선택도를 모르고 튜닝. 필터가 전체의 0.1%만 통과시키는지, 90%를 통과시키는지에 따라 최적 전략이 정반대입니다. 낮은 선택도(예: 특정 사용자 문서)면 브루트포스/flat이 오히려 정답일 수 있습니다. 필터 통과율부터 재 보세요.

실수 3 (Qdrant) — payload 인덱스를 나중에. filterable HNSW의 필터 인지 엣지는 payload 인덱스가 있는 상태에서 만들어질 때 생깁니다. 데이터를 다 넣고 나서 인덱스를 붙이면 이점을 못 누립니다. 필터 필드 인덱스를 먼저 잡으세요.

실수 4 — 필터·질의 상관관계 간과. 필터가 “질의와 가까운 영역”을 통째로 도려내는 경우(예: 질의는 최신 이슈인데 필터는 ‘2020년 이전’)엔, 어떤 기법도 관련 문서를 못 만들어 냅니다. 통과분은 많아도 정작 가까운 게 다 걸러진 상황이죠. 이건 검색이 아니라 데이터·질의 설계 문제입니다.

팁 — 재현율은 반드시 측정. iterative scan이나 in-place 필터는 모두 ‘근사’라, 설정에 따라 진짜 최근접을 놓칠 수 있습니다. 브루트포스 결과를 정답으로 두고 recall@10을 주기적으로 재서, 속도를 위해 정확도를 얼마나 내주고 있는지 눈으로 확인하세요.

팁 — 필터가 늘 강하면 파티셔닝도 고려. 테넌트별처럼 항상 강한 필터가 걸린다면, 아예 컬렉션/테이블을 테넌트 단위로 나눠 각자 작은 인덱스를 두는 편이 단순하고 빠를 때가 많습니다. 필터를 ‘검색 안’이 아니라 ‘검색 밖’에서 푸는 방법입니다.

8. 마무리 (TL;DR)

  • 증상: 벡터 검색에 메타데이터 필터를 붙이면 결과가 모자라거나, 부정확하거나, 느려집니다.
  • 원인: HNSW는 그래프라, 필터로 노드를 지우면 길이 끊깁니다. post-filter는 과소반환, 순진한 pre-filter는 브루트포스로 붕괴합니다.
  • 해법: 인덱스가 필터를 의식하게 만드세요 — 부족하면 더 뽑기(iterative), 걸린 노드는 건너뛰기(two-hop), 작으면 전부 비교(flat).
  • 엔진별: pgvector = iterative scan(relaxed_order), Qdrant = payload 인덱스 + filterable HNSW, Weaviate = ACORN 자동 전략.
  • 철칙: 필터를 애플리케이션에서 손으로 걸지 말고 엔진에 넘기고, 선택도를 측정하고, recall을 눈으로 확인하세요.

벡터 검색은 “가까운 것 찾기”라 단순해 보이지만, 거기에 현실의 WHERE 한 줄이 더해지는 순간 완전히 다른 문제가 됩니다. 다행히 2026년의 벡터 DB들은 이 문제를 정면으로 풀고 있으니, 우리가 할 일은 하나입니다 — 필터를 엔진에게 맡기고, 결과 개수와 recall을 의심하는 습관. 다음에 RAG에 필터를 얹을 때, 결과가 LIMIT을 채우는지부터 확인해 보세요.
