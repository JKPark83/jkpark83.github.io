1. 도입 — 요약(compaction)의 숨은 청구서

에이전트를 오래 돌려본 사람이라면 누구나 같은 벽에 부딪힙니다. 턴이 쌓일수록 컨텍스트가 비대해지고, tool 호출 결과 — 검색 결과 수십 KB, 파일 내용, 로그 덤프 — 가 대부분의 자리를 차지합니다. 그래서 거의 모든 에이전트 하네스가 같은 처방을 씁니다. 컨텍스트가 임계치를 넘으면 지난 대화를 요약(summarization/compaction)해서 짧은 텍스트로 바꿔치기하는 겁니다. Claude Code의 compaction이 대표적이고, Anthropic의 컨텍스트 엔지니어링 가이드도 compaction을 장기 세션의 기본 도구로 소개합니다.

그런데 이 처방에는 영수증에 잘 안 찍히는 비용이 있습니다. 요약은 히스토리를 다시 쓰는 행위입니다. 메시지 배열이 바뀌는 순간, 서빙 엔진이 애써 만들어 둔 KV 캐시는 prefix가 깨져서 대부분 무효가 됩니다. 다음 요청에서 모델은 요약문을 포함한 컨텍스트 전체를 처음부터 다시 프리필(re-prefill)해야 합니다. 요약을 "토큰을 아끼는 기술"로만 알고 있었다면, 실제로는 요약할 때마다 전체 컨텍스트만큼의 프리필 비용을 한 번씩 더 내고 있던 셈입니다.

10월 20일 arXiv에 올라온 논문 Cache Engineering for Agents(Tianyu Fu 외)는 바로 이 지점을 찌릅니다. 공개 직후 Hugging Face 트렌딩 페이퍼에 올랐고, 같은 주에 KV 캐시 × 에이전트를 다룬 논문이 여럿 쏟아지면서 "컨텍스트 엔지니어링 다음은 캐시 엔지니어링"이라는 말이 나오기 시작했습니다. 주장은 간단합니다. 텍스트(컨텍스트)를 고쳐 쓰지 말고, 서버에 있는 KV 캐시를 에이전트가 직접 관리하게 하자는 겁니다. 코드도 AKV라는 이름으로 Apache 2.0 라이선스로 공개됐습니다.

2. 배경 — KV 캐시와 prefix caching 3분 복습

트랜스포머가 다음 토큰을 만들 때는 앞선 모든 토큰의 key/value 벡터가 필요합니다. 이를 매번 다시 계산하지 않도록 GPU 메모리에 저장해 두는 것이 KV 캐시입니다. 토큰 하나당 모든 레이어의 K, V 벡터가 저장되므로, 컨텍스트가 길어질수록 캐시는 수 GB 단위로 커집니다. 자세한 구조는 예전 글 LLM 서빙 엔진 내부에서 다뤘습니다.

여기에 vLLM, SGLang 같은 서빙 엔진은 prefix caching을 얹습니다. 두 요청의 앞부분이 토큰 단위로 완전히 같으면, 그 구간의 KV를 다시 계산하지 않고 재사용하는 기법입니다. 에이전트는 매 턴 "지금까지의 전체 대화 + 새 메시지"를 보내므로 prefix caching과 찰떡궁합입니다. API 쪽에도 같은 개념이 있습니다. Anthropic의 prompt caching은 캐시 읽기를 기본 입력 단가의 10%로 과금합니다. 캐시에 맞으면 10분의 1 가격, 깨지면 정가라는 뜻입니다.

그래서 에이전트 하네스의 제1원칙이 "컨텍스트는 append-only로 유지하라"가 됐습니다. 뒤에 붙이기만 하면 prefix가 보존되고 캐시가 계속 맞습니다. 문제는 이 원칙과 "컨텍스트를 줄여야 한다"는 요구가 정면으로 충돌한다는 겁니다. 요약이든 오래된 메시지 삭제든, 컨텍스트 중간을 건드리는 순간 append-only가 깨지고 캐시도 함께 깨집니다. 지금까지는 둘 중 하나를 포기해야 했습니다.

용어 정리: 이 글에서 컨텍스트 엔지니어링은 "모델에게 보낼 텍스트(메시지 배열)를 설계·편집하는 일", 캐시 엔지니어링(cache engineering)은 "서버에 이미 계산돼 있는 KV 캐시 자체를 유지·제외·압축하는 일"을 가리킵니다. 전자는 클라이언트의 일이었고, 후자는 지금까지 서빙 엔진만의 일이었습니다. 이 논문은 후자의 제어권을 에이전트에게 넘깁니다.

3. 발상의 전환 — 텍스트가 아니라 캐시를 관리하라: drop과 reposition

논문의 핵심 관찰은 이렇습니다. 요약이 캐시를 깨는 이유는 토큰 시퀀스를 바꾸기 때문입니다. 그렇다면 토큰 시퀀스는 그대로 두고, 필요 없어진 부분의 KV만 앞으로의 attention 계산에서 제외하면 어떨까요? 텍스트 차원에서는 아무것도 지우지 않았으니 히스토리는 멀쩡하고, 살아남은 KV는 재계산 없이 그대로 재사용됩니다. re-prefill이 아예 발생하지 않습니다.

이를 위해 논문은 두 가지 연산을 정의합니다.

  • drop — 지정한 메시지의 KV 엔트리를 이후 attention에서 제외합니다. 메시지 히스토리 자체는 수정하지 않습니다. 오래된 tool 결과처럼 "한 번 보고 버려도 되는" 덩어리가 주 대상입니다.
  • reposition — drop만 하면 살아남은 토큰들의 위치(position)에 빈틈이 생깁니다. reposition은 남은 KV의 위치 인코딩을 다시 매겨 빈틈을 압축합니다. 모델 입장에서는 컨텍스트가 실제로 짧아진 효과가 납니다.

비유하자면 이렇습니다. 요약이 "책의 앞 챕터들을 찢어내고 한 장짜리 줄거리로 다시 제본하는 것"이라면, drop은 "책은 그대로 두고 다 읽은 챕터에 '다시 안 봐도 됨' 포스트잇을 붙이는 것"입니다. 제본을 다시 하면(요약) 책 전체를 다시 들춰봐야 하지만(re-prefill), 포스트잇 방식은 책장도 그대로, 읽던 자리도 그대로입니다. 게다가 포스트잇은 떼면 그만이라, 정책에 따라서는 나중에 되살릴 여지도 있습니다 — 요약으로 날린 디테일은 영영 복구할 수 없는 것과 대조적입니다.

흥미로운 점은 품질입니다. 직관적으로는 "요약이라도 남기는 쪽"이 정보를 덜 잃을 것 같지만, 논문의 실험에서는 tool 결과를 통째로 drop하는 쪽이 요약 기반 베이스라인보다 벤치마크 평균 점수가 1.7점 더 높았습니다. 요약 과정 자체가 디테일을 뭉개고, 모델이 자기가 쓴 요약문을 과신하는 부작용이 있는 반면, drop은 "최근 것은 원문 그대로, 오래된 것은 깔끔하게 제외"라는 더 예측 가능한 컨텍스트를 만들기 때문으로 해석할 수 있습니다. 컨텍스트가 길수록 품질이 떨어지는 현상(context rot)을 생각하면, 안 쓰는 KV를 attention에서 빼는 것 자체가 품질에도 득이 됩니다.

4. AKV 엔진 — stateless API 뒤의 stateful 캐시

"KV를 골라서 빼자"는 아이디어는 간단해 보이지만, 서빙 시스템 입장에서는 골치 아픈 문제를 하나 만듭니다. 기존 prefix caching은 "토큰 시퀀스가 같으면 캐시 상태도 같다"는 가정 위에 서 있습니다. 그런데 drop이 들어오는 순간 이 가정이 깨집니다. 똑같은 메시지 배열이라도, 2번 메시지를 drop한 세션과 안 한 세션의 캐시 상태는 서로 다릅니다. 즉 같은 토큰 ≠ 같은 캐시가 되어, 단순 prefix 매칭으로는 캐시를 올바르게 재사용할 수 없습니다.

논문이 SGLang 위에 구현한 AKV(thu-nics/AKV)는 이 문제를 "겉은 stateless, 속은 stateful"로 풉니다. 클라이언트는 평소처럼 OpenAI 호환 Chat Completions API로 전체 메시지를 보내되, 요청 페이로드에 캐시 지시 필드 두 개만 얹습니다.

{{< highlight json >}} { "model": "gpt-oss-120b", "messages": [ /* 전체 히스토리를 평소처럼 그대로 */ ], "drop_message": {"4": [2]}, // 메시지 4 처리 후, 메시지 2의 KV를 drop "reposition": [4] // 메시지 4 이후 남은 KV의 위치를 압축 } {{< /highlight >}}

drop_message는 "어느 시점에(키), 어떤 메시지들을(값) 뺄 것인가"의 매핑입니다. 인덱스는 0부터 시작하고, 예를 들어 {"3": [1, 2]}는 메시지 3까지 처리한 뒤 메시지 1, 2의 KV를 제외하라는 뜻입니다. 두 연산이 같은 시점에 걸리면 drop을 먼저, reposition을 나중에 적용합니다. 서버는 내부적으로 세션별 캐시 연산 이력을 추적하면서 재사용·축출(eviction)·복원을 관리합니다. 응답의 usage.prompt_tokens_details에는 cached_tokens, drop_skipped_tokens, repos_tokens 세 필드가 추가돼, 캐시가 실제로 얼마나 재사용되고 얼마나 건너뛰었는지 요청 단위로 확인할 수 있습니다.

왜 API가 stateless를 유지하는 게 중요할까요? 세션 상태를 클라이언트가 들고 있게 하면(예: 캐시 핸들을 주고받는 방식) 하네스와 로드밸런서, 재시도 로직 전부를 뜯어고쳐야 합니다. AKV는 "전체 메시지 + 캐시 지시"라는 기존 요청 형태를 유지해서, 하네스 쪽 변경을 요청 필드 두 개 추가로 최소화했습니다. 기존 에이전트 코드와의 호환성이 이 설계의 핵심 셀링 포인트입니다.

성능 면에서는, 요약처럼 전체 re-prefill을 일으키는 연산이 사라지니 서버의 프리필 부하가 급감합니다. 논문 보고치는 출력 처리량 최대 1.18배, P95 요청 지연 1.51배 단축입니다. 비용 절감이 서비스 수준 지표(SLO) 개선으로도 이어진다는 뜻입니다.

5. CachePolicy — 언제, 무엇을, 어떻게 뺄 것인가

그럼 "무엇을 언제 drop할지"는 누가 정할까요? AKV의 에이전트 레이어(akv.agent)는 이 결정을 CachePolicy라는 세 부품의 조합으로 추상화합니다.

부품역할내장 구현
trigger언제 정리를 발동할지 (bool 반환)턴 수 기반 · 토큰 수 기반 · 모델 판단 기반
selector무엇을 drop할지 (메시지 ID 집합 반환)턴 기반 · 토큰 기반 · 모델 판단 기반
reposition위치 압축을 할지 말지 (bool 반환)턴 기반 · 토큰 기반 · 모델 판단 기반

논문이 메인으로 내세우는 정책은 tool-response rolling drop입니다. 아이디어는 소박합니다. "tool 결과는 받은 직후 몇 턴만 원문이 필요하고, 그 뒤로는 거의 안 쓴다. 그러니 최근 K개의 tool 결과만 남기고 더 오래된 것부터 순서대로(rolling) drop하라." 에이전트 컨텍스트의 대부분을 tool 결과가 차지한다는 점을 생각하면, 이 단순한 규칙만으로 컨텍스트 팽창이 사실상 평평하게 눌립니다. 임계치에 도달할 때마다 한 번에 크게 요약하는 기존 방식과 달리, 매 턴 조금씩 정리하므로 비용 스파이크도 없습니다.

한 발 더 나아간 것이 CacheTool입니다. 정책을 하네스에 하드코딩하는 대신, drop_context 같은 도구를 모델에게 쥐여 주고 모델이 스스로 "이 메시지들은 이제 필요 없음"을 판단해 tool call로 drop을 지시하게 합니다. 하네스는 그 호출을 다음 요청의 drop_message 필드로 변환하기만 하면 됩니다. 컨텍스트 관리의 주체가 하네스 개발자에서 모델 자신으로 옮겨가는 그림입니다.

P95 요청 지연 (AKV 엔진)1.51배 단축〃
정책 자가 개선 후 비용추가 −7.1%사람이 설계한 정책 대비

실험에는 GPT-OSS-120B, MiniMax-M2.7 등이 쓰였고, BCP 벤치마크(100개 태스크 서브셋, 태스크당 4회 시행)에서 GPT-OSS-120B가 61.0%로 비교 기법 중 가장 높은 pass rate를 기록했으며, SWE-bench Verified에서도 태스크 성능과 서빙 처리량을 함께 측정했습니다.

개인적으로 가장 눈이 가는 건 마지막 줄입니다. 저자들은 캐시 정책 코드 자체를 에이전트에게 주고 "벤치마크 성능과 비용을 보고 정책을 고쳐 봐라"는 재귀적 자가 개선(recursive self-improvement) 실험을 했습니다. 그 결과물이 전문가가 손으로 설계한 정책보다 held-out 태스크에서 비용을 7.1% 더 줄였습니다. trigger/selector/reposition이라는 좁고 명확한 인터페이스 덕분에, "에이전트가 자기 인프라 코드를 최적화한다"는 다소 아찔한 아이디어가 안전하고 측정 가능한 놀이터 안에서 작동한 사례입니다.

7. 실전 — 직접 돌려보기 & 지금 내 에이전트에 가져갈 것

AKV는 pip 패키지가 아니라 연구용 코드지만, GPU가 있다면 README의 Quick Start 그대로 돌려볼 수 있습니다.

{{< highlight bash >}} # 설치 (Python 3.12 + uv) git clone https://github.com/thu-nics/AKV && cd AKV uv venv --python 3.12 source .venv/bin/activate uv pip install -e . # AKV 서버 띄우기 (GPT-OSS-120B 예시, GPU 2장 텐서 병렬) python -m akv.system.launch_server \ --model-path /path/to/gpt-oss-120b \ --reasoning-parser gpt-oss \ --tool-call-parser gpt-oss \ --tp-size 2 \ --port 8000 # 캐시 정책이 적용된 에이전트 데모 python examples/demo.py \ --base-url http://localhost:8000/v1 \ --model gpt-oss-120b \ --output local/demo-tool-01 {{< /highlight >}}

지원 모델은 현재 Qwen 계열(Qwen2/2.5/3, MoE 변형 포함), GPT-OSS, MiniMax-M2 계열이고, drop/reposition은 SGLang의 --page-size 1(기본값)에서만 동작합니다. 직접 서빙하지 않고 상용 API만 쓰는 입장이라도, 이 논문의 사고방식은 바로 적용할 수 있습니다.

  • 컨텍스트 편집의 진짜 비용을 계산하세요. 요약으로 아끼는 토큰 수만 보지 말고, "요약 직후 1회의 전체 re-prefill(정가) + 요약 모델 호출 비용"을 빼 보세요. 캐시 읽기가 정가의 10%인 요금 체계에서는, 캐시를 깨는 요약이 오히려 손해인 구간이 생각보다 넓습니다. 세션이 얼마나 길어야 요약이 이득인지 손익분기점을 한 번 구해 보면 감이 옵니다.
  • 요약 대신 '통째 제거'를 먼저 검토하세요. 논문의 rolling drop이 시사하듯, tool 결과는 요약할 가치조차 없는 경우가 많습니다. 상용 API에서도 "오래된 tool 결과를 플레이스홀더로 치환"하는 전략은 요약보다 싸고 예측 가능합니다. 단, 이 역시 히스토리를 수정하므로 캐시는 깨집니다 — 그래서 매 턴이 아니라 가끔, 한꺼번에 하는 게 유리합니다. OpenAI와 Anthropic 모두 비슷한 방향의 컨텍스트 편집 기능을 제공하기 시작했으니 사용하는 API의 문서를 확인해 보세요.
  • 캐시 지표를 대시보드에 올리세요. AKV가 cached_tokens/drop_skipped_tokens를 노출하듯, 상용 API 응답의 캐시 히트 필드(Anthropic의 cache_read_input_tokens 등)를 로깅하면 "우리 하네스가 캐시를 얼마나 깨먹고 있는지"가 한눈에 보입니다. 에이전트 토큰 경제학에서 다뤘듯, 긴 세션 에이전트의 비용은 출력이 아니라 입력(프리필) 쪽에서 터집니다.

8. 흔한 실수 · 팁

  • "drop했으니 모델이 그 내용을 기억할 것"이라고 착각하기. drop된 KV는 이후 attention에서 완전히 제외됩니다. 모델 입장에서는 그 메시지가 처음부터 없던 것과 같습니다. 최종 답변에 꼭 필요한 정보(태스크 목표, 핵심 발견)는 drop 대상에서 제외하거나, drop 전에 짧은 메모로 다시 써 두는 설계가 필요합니다.
  • reposition 없이 drop만 쌓기. drop만 하면 위치 인덱스에 빈틈이 남아 유효 컨텍스트 길이는 줄지 않습니다. 길이 한계에 부딪혀서 정리하는 거라면 reposition까지 해야 실제로 자리가 생깁니다.
  • 클라이언트 측 trimming과 혼동하기. 하네스에서 오래된 메시지를 배열에서 지우는 것(trimming)은 prefix를 깨서 전체 re-prefill을 유발합니다. drop은 반대로 배열을 그대로 두고 서버 쪽 KV만 건드립니다. 겉보기 효과는 비슷해도 비용 구조가 정반대입니다.
  • 벤더 API에 그대로 이식하려 하기. drop_message/reposition은 AKV 서버의 확장 필드입니다. OpenAI/Anthropic API에는 (아직) 이런 KV 수준 제어가 없습니다. 상용 API에서는 "캐시 브레이크포인트를 안정된 prefix 뒤에 두기, 편집은 드물게 한꺼번에" 같은 간접 전략이 현실적인 대안입니다.
  • 모델 기반 trigger/selector를 공짜로 여기기. "모델이 판단해서 drop"은 그 판단 자체가 추가 호출/토큰입니다. 대부분의 워크로드에서는 턴·토큰 기반의 멍청한 규칙이 가성비가 좋고, 논문의 메인 결과도 단순한 rolling 규칙에서 나왔습니다.

9. 마무리 (TL;DR)

  • 10/20 공개된 Cache Engineering for Agents(arXiv:2610.28577)가 Hugging Face 트렌딩에 올랐습니다. 요지: 긴 에이전트 세션의 지배적 비용은 KV 캐시이며, 요약/트리밍 같은 컨텍스트 편집은 캐시를 깨고 전체 re-prefill을 청구합니다.
  • 해법은 텍스트가 아니라 KV 캐시를 직접 관리하는 것: drop(선택한 메시지의 KV를 이후 attention에서 제외)과 reposition(남은 KV의 위치 압축). 히스토리는 append-only 그대로, re-prefill은 0.
  • 오래된 tool 결과를 순서대로 빼는 rolling drop 정책만으로 요약 대비 비용 −27.7%, 점수 +1.7(저자 보고치). 요약보다 싸면서 품질도 좋았다는 게 포인트.
  • drop이 생기면 "같은 토큰 = 같은 캐시" 가정이 깨지므로, SGLang 기반 AKV 엔진이 stateless API(drop_message/reposition 필드) 뒤에서 세션별 캐시 상태를 추적합니다. 처리량 1.18배, P95 지연 1.51배 단축.
  • 정책은 trigger(언제)/selector(무엇을)/reposition(압축할지)으로 분해되고, CacheTool로 모델이 직접 drop을 지시할 수도, 에이전트가 정책 코드를 스스로 개선(추가 −7.1%)할 수도 있습니다.
  • 상용 API 사용자도 교훈은 동일합니다: 컨텍스트 편집의 비용에 re-prefill을 포함해 계산하고, 요약보다 통째 제거를 먼저 검토하고, 캐시 히트 지표를 상시 관측하세요.
