# 🔥 오늘의 핵심

모델 릴리즈는 이틀째 조용하지만, 논문 두 편이 같은 경고를 들고 왔다 — **초록불(통과)은 정답이 아니다.** 꼼꼼히 검증하고 출시한 Terminal-Bench 2.0조차 과제의 약 30%에서 결함이 발견됐고, API 마이그레이션 후 LLM이 고친 코드는 테스트를 다 통과해도 41%가 오답이었다. 좋은 소식은 처방이 싸다는 것: **릴리즈 노트에서 뽑은 엣지 입력 1개**가 오답 릴리즈율을 6.5%로 떨어뜨린다. 오늘 당장 CI 게이트에 넣어볼 수 있는 수준의 교훈이다.

# 📚 주목 논문

## 1. Benchmarks as Software — Terminal-Bench에도 '유지보수 부채'가 쌓인다

- **저자**: E. Kelly Buchanan, Crystal Zhou, Scott W. Linderman, Christopher Ré (Stanford의 Linderman·Ré 그룹)
- **arXiv**: [2611.08417](https://arxiv.org/abs/2611.08417) (cs.AI)
- **핵심 기여**: 벤치마크는 출시 때 한 번 검증하고 끝나는 자산이 아니라 **썩는 소프트웨어**라는 관점. 모델이 좋아지면 검증기가 거부하는 '정답 아닌 정답'이 나오고, 평가 인프라가 바뀌면 과제에 박힌 가정이 깨진다. 이 누적을 **벤치마크 유지보수 부채**라 이름 붙였다.
- **방법**: 커뮤니티 리포트 + 과제 아티팩트 + 에이전트 트레이스 + 자동 오라클 검사 + 사람이 승인하는 수리로 이어지는 **상시 검증 워크플로**를 Terminal-Bench 2.0에 적용했다.
- **결과**: 출시 전에 레드팀까지 거친 벤치마크인데도 약 30% 과제에서 문제를 발견, 수리판을 Terminal-Bench 2.1로 공개. 수리만으로 정확도가 10pp 이상 오르고 리더보드 순위가 최대 3계단 움직였다(전체 상관은 ρ=0.958로 유지). 고정 wall-clock의 영향도 커서, 시간 제한을 늘리자 GPT 5.4의 하네스 간 20pp 격차가 사라졌다.
- 🛠 **시사점**: 내부 에이전트 평가 세트도 똑같이 썩는다. "작년에 만든 평가 100개"가 지금 모델의 유효한 풀이를 거부하고 있지 않은지, 에이전트 트레이스를 샘플링해 검증기 쪽 오류를 주기적으로 감사할 것. 그리고 시간 제한이 결과를 바꾼다 — 벤치 점수를 비교할 땐 wall-clock 조건부터 맞춰라.
- **한계**: 사람이 수리를 승인하는 구조라 완전 자동은 아니고, 수리 기준 자체에 판단이 들어간다.

![Terminal-Bench 2.1 감사 결과와 Accepted but Wrong의 오답 릴리즈율 비교 차트](/images/ai-news-2026-11-09/green-light.svg)

*왼쪽: 검증된 벤치마크도 30%가 결함. 오른쪽: 테스트 통과 ≠ 정답 — 엣지 입력 1개의 힘.*

## 2. Accepted but Wrong — 통과한 수리의 41%가 오답이었다

- **저자**: Xiaobo Chen, Genliang Zhu, Ziyuan Wang, Chu Wang (소속 미표기)
- **arXiv**: [2611.08269](https://arxiv.org/abs/2611.08269) (cs.SE)
- **핵심 기여**: 런타임/API 마이그레이션 후 LLM이 고친 코드는 **깨끗하게 돌고 테스트도 통과하는데 결과가 틀린** 채로 출시될 수 있다. 이 '조용한 실패'의 비율을 사전등록 연구로 측정했다.
- **방법**: CPython·Node.js·SQLite의 문서화된 변경 60건, 73개 과제. 후보 수리를 실제 런타임에서 비공개 계약(contract)에 대해 실행해 채점했다.
- **결과**: 일반 입력 + 전체 단언 게이트는 오답 수리의 41.0%를 통과시켰다. 릴리즈 노트를 보고 쓴 **엣지 입력 1개**를 추가하면 6.5%로, 프로그램을 본 적 없는 블라인드 모델이 쓴 입력 3개로는 7.0%로 떨어진다. 단, 일부러 만든 교묘한 오답(기존 출력과 일반 입력에서 일치)은 15~17%가 여전히 통과 — 만능은 아니다. 모델의 셀프 테스트는 이보다 덜 효과적이었다.
- 🛠 **시사점**: Node 메이저 업그레이드나 라이브러리 마이그레이션을 에이전트에게 맡기고 있다면, "기존 테스트 통과"를 완료 조건으로 삼지 말 것. 아래 공통 팁에서 구체적인 워크플로로 푼다.
- **한계**: 범위가 세 런타임의 문서화된 변경에 한정되고, 아티팩트는 저자 요청 공개다.

NVIDIA GPU(Linux/Windows) 또는 Apple Silicon이 필요하고, 정식 오픈소스 라이선스가 아닌 점은 확인하고 쓸 것.
- **[grim-prompter](https://github.com/jmanico/grim-prompter)** — MIT, 약 400★. OWASP 쪽에서 오래 활동한 Jim Manico의 **코딩 에이전트용 위협 모델링 스킬**. 36개 아키텍처 워크플로와 29개 분석 기법 프롬프트를 제공하고, Claude Code는 `/threat-model`, Codex는 `$threat-model`로 실행한다. 런북이 read-only 검사와 파일:라인 단위 증거 인용을 강제하는 게 핵심 — 결과의 모든 주장이 코드로 추적된다. **용도**: 릴리즈 전 `threat-model change main...feature`로 브랜치가 기존 위협 모델을 어떻게 바꾸는지 점검.

Scott Hanselman의 신작. **매번 새로 태어나는 1회용 Windows 11 머신**을 CLI(`sbx`)와 선택형 MCP 어댑터로 에이전트에게 쥐여준다(Windows Sandbox 자동화, GUI 시나리오 왕복 약 40~50초). **용도**: "내 PC에선 되는데" 사냥 — 깨끗한 네트워크 차단 PC에서 설치·실행해 빠진 의존성(VC++ 재배포판 같은)을 30초 만에 잡는다. 어제 다룬 devvm의 Windows 데스크톱 앱 버전인 셈.

# 🧑‍💻 Codex & Claude Code 실전 팁

### 🟦 Claude Code — 태스크형 MCP 호출은 이제 자동으로 백그라운드

- **카테고리**: MCP · **출처**: [CHANGELOG v2.1.319](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- 💡 **핵심**: MCP 서버가 툴 호출을 '태스크'로 실행하면, Claude Code가 그 호출을 즉시 백그라운드로 보내고 끝났을 때 결과를 모델에게 알려준다. 느린 MCP 작업이 턴을 잡아먹지 않는다.
- 📝 **방법**: 기본 동작이라 설정이 필요 없다. 예전처럼 툴 호출 안에서 기다리게 하려면:

```bash
export CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND=1
```

- 🎯 **언제**: 빌드·배포·대량 조회처럼 수십 초 이상 걸리는 작업을 MCP 서버로 감싸 쓸 때. 서버 쪽을 태스크 방식으로 바꿔두면 에이전트가 기다리는 동안 다른 일을 진행한다.
- ⚠️ **주의**: 후속 턴이 그 결과에 바로 의존하는 파이프라인이라면 비활성화 변수를 켜는 쪽이 디버깅하기 쉽다.
- ⭐ **추천도**: 장시간 MCP 작업이 있는 팀이라면 서버 쪽 태스크 지원을 검토할 가치가 충분하다.

### 🟩 Codex — MCP 네트워크 정책이 보수적으로 바뀌었다

- **카테고리**: MCP / Debugging · **출처**: [commit b7d2321](https://github.com/openai/codex/commit/b7d2321ef7b2405b72a4186447c810756866896b)
- 💡 **핵심**: MCP 네트워크 정책을 컨트롤러·환경 정책, 권한 프로필, 승인 설정, 저장된 규칙에서 **유도**하도록 정리하면서 두 가지가 바뀌었다. 메타데이터로 판단할 수 없는 트래픽(검토 필요, 훅, DNS 검사 대상)은 기본 거부하고, 저장된 **거부 규칙은 grant가 깨지거나 규칙 저장이 실패해도 유지**된다(거부를 먼저 적용하고 저장은 나중에).
- 📝 **방법**: 할 일은 없고, 진단 포인트가 바뀐다 — 어제까지 되던 MCP 서버의 외부 호출이 갑자기 거부된다면 버그가 아니라 보수적 기본값일 수 있다. 네트워크 접근이 필요한 서버는 허용 규칙을 명시적으로 승인해 둘 것.
- 🎯 **언제**: 외부 API를 부르는 MCP 서버를 Codex 샌드박스 안에서 쓸 때.
- ⚠️ **주의**: 오래된 저장 규칙이 꼬여 있다면 정책 파일을 정리하고 다시 승인하는 쪽이 빠르다.
- ⭐ **추천도**: 직접 할 건 없지만, MCP 네트워크 이슈를 디버깅할 때 이 변경을 모르면 한참 헤맨다.

### 🟪 공통 — 마이그레이션 수리 게이트에 '릴리즈 노트發 엣지 입력 1개'를 넣어라

- **카테고리**: Eval / Workflow · **출처**: [arXiv 2611.08269](https://arxiv.org/abs/2611.08269)
- 💡 **핵심**: 기존 테스트 전체 통과는 마이그레이션 수리의 오답 41%를 걸러내지 못한다. 변경을 설명하는 릴리즈 노트에서 **경계 조건을 겨냥한 입력 1개**를 뽑아 추가하는 것만으로 6.5%까지 떨어진다.
- 📝 **방법**: 에이전트에게 마이그레이션을 맡길 때 완료 조건을 이렇게 걸어라.

```text
1. 수리 전에: 이 변경의 공식 릴리즈 노트/CHANGELOG를 읽고,
   바뀐 동작의 경계를 때리는 입력 1~3개를 먼저 테스트로 작성하라.
   (예: 타임존 경계, 빈 컬렉션, 오버플로 직전 값, 새 기본 인코딩)
2. 그 테스트가 '기존 코드에서는 실패'하는 것을 확인하라.
3. 그 다음에 수리하고, 기존 스위트 + 새 엣지 테스트를 모두 통과시켜라.
```

- 🎯 **언제**: Node/Python 메이저 업그레이드, DB 엔진 교체, SDK 마이그레이션을 에이전트에게 맡기는 모든 경우.
- ⚠️ **주의**: 수리하는 에이전트 자신이 쓴 셀프 테스트는 효과가 덜했다. 엣지 입력은 수리 전에, 가능하면 다른 세션/모델에서 뽑는 게 논문 설정에 가깝다.
- ⭐ **추천도**: 오늘 팁 중 최우선. 비용은 테스트 1개, 효과는 측정돼 있다.
