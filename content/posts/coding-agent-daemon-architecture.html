도입 — 한 주에 몰린 세 사건, 질문은 하나

이번 주(10/12~18) 코딩 에이전트 씬에서는 서로 달라 보이는 사건 세 개가 연달아 터졌습니다. 시간순으로 놓고 보면 사실 하나의 이야기입니다.

  • 10/12~14 — OpenCode 2.0 공개. 오픈소스 코딩 에이전트 OpenCode가 2.0을 공식 발표하고 Product Hunt에도 올랐습니다. 핵심 변화는 기능이 아니라 구조입니다. 터미널마다 따로 뜨던 프로세스를 버리고, 터미널·데스크톱 앱·웹 UI가 전부 하나의 백그라운드 서비스에 접속하는 구조로 다시 썼습니다.
  • 10/15 — Codex CLI 데몬 논란. OpenAI의 Codex CLI가 상주하며 스스로 업데이트하는 백그라운드 데몬을 기본으로 설치한다는 사실이 알려지며 Hacker News 프런트페이지에 올랐습니다. 공식 문서에는 데몬 설명이 없고, 끄는 방법도 비공식 플래그뿐이라는 점에 "malware 같다"는 격한 반응까지 나왔습니다.
  • 10/17 — OpenCode Console 침해 공개. OpenCode가 X 공지로 Console 사용자 1.4%에 영향을 준 보안 침해를 알렸습니다. 공격자는 사용자가 연결해 둔 OpenAI·Anthropic·Google API 키를 탈취해 대규모 distillation 공격에 썼고, 피해자들은 자신이 쓰지 않은 요금 청구를 목격했습니다.

세 사건을 관통하는 질문은 이겁니다. "코딩 에이전트 런타임은 어디서, 어떤 모습으로 살아야 하는가?" 1년 전 코딩 에이전트는 터미널에서 명령 한 번에 뜨고 창을 닫으면 사라지는 CLI 프로그램이었습니다. 지금은 두 주요 에이전트가 모두, 운영체제에 상주하면서 여러 클라이언트를 받아 주는 로컬 서버(데몬)로 이사하는 중입니다. 왜 이런 전환이 일어나는지, 코드 레벨에서 어떻게 구현됐는지, 그리고 이번 주 논란이 보여 준 비용은 무엇인지 차근차근 보겠습니다.

배경 — 일회성 프로세스와 상주 데몬, 그리고 선배들

용어부터 정리하겠습니다. 데몬(daemon)은 터미널에 붙어 있지 않고 백그라운드에서 계속 도는 프로세스입니다. 보통 ① 사용자가 명시적으로 띄우지 않아도 필요할 때 자동으로 시작되고, ② 터미널이나 앱을 닫아도 살아남으며, ③ 소켓 같은 통신 채널로 요청을 받아 처리합니다.

일회성 CLI와 데몬의 차이는 "일을 누가 들고 있느냐"입니다. 일회성 CLI에서는 프로세스가 곧 작업입니다. 프로세스가 죽으면 진행 중이던 모든 상태 — 대화 히스토리, 켜 둔 권한, 파일 감시 — 가 함께 사라집니다. 데몬 모델에서는 작업이 서버에 살고, CLI는 서버에 붙었다 떨어지는 얇은 클라이언트가 됩니다.

이 전환 자체는 전혀 새롭지 않습니다. 개발 도구의 역사에서 반복돼 온 패턴입니다.

  • Docker: docker run이라는 CLI는 사실 상주 데몬 dockerd에 API 요청을 보내는 클라이언트입니다. 컨테이너는 CLI가 아니라 데몬이 들고 있어서, 터미널을 닫아도 계속 돕니다.
  • LSP(Language Server Protocol): 자동완성·정의 이동 같은 언어 지능을 에디터마다 다시 구현하는 대신, 언어 서버 하나를 띄우고 모든 에디터가 JSON-RPC로 접속하게 만들었습니다. "클라이언트가 여럿이면 엔진을 서버로 뽑아내라"의 교과서적 사례입니다.
  • ssh-agent: 개인 키를 메모리에 들고 상주하면서, 여러 ssh 세션이 소켓으로 서명을 요청하게 합니다. 크레덴셜을 한 프로세스에 모아 두는 데몬의 원형입니다.

코딩 에이전트의 데몬 전환은 이 세 선배의 동기를 전부 물려받았습니다. 그리고 뒤에서 보겠지만, 위험도 전부 물려받았습니다.

에이전트는 왜 데몬을 원하나

그냥 CLI로 두면 안 됐을까요? 에이전트 워크로드의 네 가지 변화가 상주 서버를 강하게 요구합니다.

첫째, 클라이언트가 여럿이 됐습니다. 같은 에이전트를 터미널에서도, 데스크톱 앱에서도, 웹에서도, IDE 확장에서도 씁니다. 엔진을 프런트엔드마다 내장하면 상태가 갈라집니다. 터미널에서 시작한 세션을 데스크톱에서 이어 보려면, 세션은 어느 한 프런트엔드가 아니라 공유 서버에 살아야 합니다. LSP가 풀었던 문제 그대로입니다.

둘째, 세션이 프로세스보다 오래 삽니다. 에이전트 작업은 이제 수십 분짜리가 흔합니다. 터미널 창을 실수로 닫았다고 30분짜리 리팩터링이 날아가면 곤란합니다. 세션을 데몬이 들고 있으면 클라이언트는 언제든 다시 붙으면 됩니다. 실제로 Codex CLI 소스에는 codex agents라는 명령이 "공유 로컬 app-server 데몬 위의 모든 에이전트 세션을 둘러본다"고 설명돼 있습니다.

셋째, 백그라운드 작업이 늘었습니다. 서브에이전트를 병렬로 돌리고, 긴 테스트를 돌려 두고 다른 일을 하는 식의 워크플로는 "요청을 받아 두고 나중에 결과를 돌려주는" 서버 구조와 자연스럽게 맞습니다.

넷째, 프로그래밍 가능한 표면이 필요해졌습니다. 에이전트를 스크립트나 다른 도구에서 조작하려면 안정된 API가 필요합니다. OpenCode는 아예 서버의 OpenAPI 스펙에서 SDK를 생성해 배포합니다. "에이전트 = 로컬 API 서버"가 되면 에이전트 위에 도구를 쌓는 일이 보통의 웹 개발과 같아집니다.

구현 해부 ① — OpenCode 2.0: localhost HTTP 서버

이제 두 구현이 실제로 어떻게 생겼는지 보겠습니다. 둘 다 오픈소스라 코드로 직접 확인할 수 있습니다.

OpenCode는 원래부터 서버 지향이었습니다. v1에서도 opencode를 실행하면 내부적으로 HTTP 서버가 뜨고 TUI는 그 서버의 클라이언트로 동작했습니다. 공식 문서가 설명하듯 opencode serve로 headless 서버만 따로 띄울 수도 있고, 서버는 OpenAPI 3.1 스펙을 /doc 경로에 게시하며, 이 스펙에서 SDK가 생성됩니다. 다만 v1에서는 터미널마다 서버가 하나씩 떴습니다.

2.0의 전환은 "서버를 하나로 합치기"입니다. 여러 분석 글이 전하듯 터미널·데스크톱·웹이 같은 백그라운드 서비스 하나에 접속합니다. 저장소 코드를 열어 보면 설계가 꽤 구체적으로 드러납니다. CLI의 service-config.ts는 서비스 등록 파일(service.json)에 호스트명·포트·비밀번호·CORS 허용 목록을 저장하고, 기본 포트는 재치 있게도 0xC0DE, 즉 49374번입니다. Windows에서는 Hyper-V가 그 대역을 예약하는 문제를 피해 0xB0DE(45278)로 옮깁니다. 소스 주석에 "低 12비트를 유지한다: 0xC0DE가 0xB0DE가 된다"는 설명까지 달려 있습니다.

보안 표면도 명시적입니다. 서버는 기본적으로 127.0.0.1에만 바인딩되고, OPENCODE_SERVER_PASSWORD를 설정하면 HTTP basic auth가 걸립니다. 외부에서 접속하는 원격 접근은 기본 꺼짐이고, 켜면 예측 불가능한 비밀 서브도메인이 생성되며(끄고 다시 켜면 주소가 바뀝니다), 사용자가 "인터넷에 노출하는 데 동의했다"는 플래그(remoteAccepted)를 명시적으로 기록합니다. 상주 서버가 생기는 순간 이런 것들이 전부 설계 항목이 된다는 점을 눈여겨봐 두세요.

구현 해부 ② — Codex: 유닉스 소켓 위의 app-server

Codex CLI는 Rust로 짜인 app-server라는 데몬을 씁니다. 전송 계층이 OpenCode와 다릅니다. TCP 포트 대신 유닉스 도메인 소켓(Unix domain socket) — 네트워크가 아니라 파일시스템 경로로 접근하는 프로세스 간 통신 채널 — 을 씁니다. 소스 기준으로 제어 소켓은 $CODEX_HOME/app-server-control/app-server-control.sock에 생기고, 그 위로 WebSocket을 올려 JSON-RPC 메시지를 주고받습니다. 프로토콜은 thread/list, turn/completed처럼 스레드(세션)와 턴을 일급 개념으로 다룹니다.

유닉스 소켓 선택에는 보안상 장점이 있습니다. TCP localhost 포트는 그 머신의 모든 로컬 프로세스(브라우저에서 돌아가는 악성 스크립트 포함)가 접근을 시도할 수 있지만, 유닉스 소켓은 파일 권한으로 접근을 제한할 수 있습니다. 대신 원격·브라우저 클라이언트를 받기 어렵습니다. OpenCode가 HTTP를 고른 것과 정확히 반대 방향의 트레이드오프입니다.

표의 마지막 줄이 이번 주 논란의 진원지입니다. Codex 소스의 기능 플래그 정의를 보면 daemon_auto_start는 안정(Stable) 단계에 default_enabled: true로 선언돼 있습니다. 즉 사용자가 아무것도 설정하지 않아도, codex를 실행하는 순간 데몬이 깔리고 상주를 시작합니다.

데몬의 세금 — 자동 업데이트, 버전 skew, 키 금고

10/15 Hacker News 논란의 제목은 "Codex CLI installs a persistent, self-updating background daemon by default"였습니다. 쟁점을 하나씩 분해해 보면, 전부 데몬이라는 아키텍처가 구조적으로 만들어 내는 비용입니다.

① 동의 없는 상주. 데몬은 사용자가 띄운 적 없는 프로세스가 계속 돌고 있다는 뜻입니다. 그 자체는 dockerd도 마찬가지지만, Docker는 설치 과정에서 데몬의 존재가 명시적입니다. Codex의 데몬은 GitHub 이슈 #48195가 지적하듯 기본 켜짐인데, 제가 저장소 docs/ 디렉터리를 직접 확인해 봐도 데몬을 설명하는 공식 문서가 없습니다. 끄는 방법(config.toml의 [features] daemon_auto_start = false)은 커뮤니티 정리 글을 통해 퍼졌습니다.

② 자가 업데이트가 작업을 중단시킨다. Codex 데몬의 업데이트 루프는 소스 기준으로 시작 5분 뒤 첫 확인, 이후 기본 60분 간격으로 새 버전을 확인하고(auto_update_enabled 역시 기본 켜짐), 설치 후 데몬을 재시작합니다. CLI의 codex daemon update 도움말조차 "진행 중인 작업을 중단시킬 수 있음(may interrupt running work)"이라고 적어 뒀습니다. 실제로 이슈 #51763에는 자동 업데이트가 활성 세션을 끊어 버리고, 업데이트된 데몬이 아직 안 업데이트된 클라이언트와 호환되지 않는 상태를 만들었다는 보고가 올라와 있습니다.

③ 버전 skew. 엔진과 UI가 한 바이너리일 때는 존재하지 않던 문제입니다. 클라이언트와 서버가 따로 업데이트되는 순간, "서버는 v2인데 클라이언트는 v1" 조합이 생깁니다. 두 프로젝트 모두 이를 코드로 방어합니다. Codex의 데몬 시동 정책은 자동 시동 시 호환되는 공유 서버를 요구하고 실패하면 내장(embedded) 모드로 떨어지며, OpenCode는 서비스 등록 파일에 버전·채널을 기록하고 채널마다 포트를 분리해 dev 빌드와 안정 빌드가 서로의 데몬에 붙는 사고를 막습니다. 데몬을 직접 만든다면 반드시 베껴야 할 설계입니다.

④ 환경의 고착. 데몬은 처음 띄운 프로세스의 환경변수를 들고 계속 삽니다. HN 스레드에서는 첫 세션의 프록시 설정이 데몬에 박제돼 이후 세션에 계속 적용되는 문제가 지적됐습니다. 터미널에서 export HTTPS_PROXY=...를 바꿔도 이미 떠 있는 데몬에는 전달되지 않습니다. 일회성 CLI 감각으로는 도저히 디버깅이 안 되는 종류의 문제입니다.

⑤ 그리고 키 금고. 데몬·플랫폼 전환의 마지막 비용은 10/17 OpenCode Console 침해가 보여 줬습니다. 에이전트 런타임은 성격상 가장 민감한 크레덴셜 — 모델 프로바이더 API 키 — 을 보관합니다. 로컬 데몬이면 내 디스크에, Console 같은 클라우드 서비스에 연결하면 그쪽 서버에 저장되죠. OpenCode의 공지에 따르면 공격자는 폐기 중이던 레거시 시스템을 통해 Console 사용자 1.4%의 연결된 프로바이더 키에 접근했고, 이 키들로 distillation 공격 — 훔친 키로 프런티어 모델에 대량 질의를 던져 그 출력을 자기 모델 학습 데이터로 수집하는 공격 — 을 돌렸습니다. 피해 사용자들은 승인한 적 없는 사용량 청구를 보고 이상을 알아챘습니다. 훔친 API 키가 그 자체로 "프런티어 모델 출력을 뽑는 자원"으로 거래되는 시대라는 뜻이기도 합니다.

교훈을 정확히 읽기: 이 침해는 로컬 데몬이 아니라 OpenCode의 클라우드 서비스(Console)에서 일어났습니다. 로컬 데몬 전환 자체의 취약점이 아닙니다. 그러나 방향은 같습니다 — 에이전트 인프라는 어디에 있든 크레덴셜이 집중되는 지점이 되고, 그래서 가장 매력적인 표적이 됩니다. 키를 맡기는 곳이 하나 늘 때마다 공격 표면도 하나 늡니다.

실전 — 내 머신의 에이전트 데몬 점검하기

읽기만 하면 남의 일 같으니, 지금 내 머신에서 직접 확인해 봅시다. 코딩 에이전트를 하나라도 쓰고 있다면 몇 분이면 됩니다.

1단계 — 무엇이 떠 있는지 본다. 데몬은 프로세스 목록과 리스닝 소켓에 흔적을 남깁니다.

{{< highlight bash >}} # 에이전트 관련 상주 프로세스 찾기 ps aux | grep -iE "codex|opencode" | grep -v grep # OpenCode 2.x 백그라운드 서비스의 기본 포트(0xC0DE=49374) 확인 # (Windows는 45278, macOS는 lsof -i :49374) ss -ltnp | grep 49374 # Codex 데몬: TCP 포트 대신 유닉스 소켓을 쓰므로 소켓 파일을 확인 ls -l ~/.codex/app-server-control/ {{< /highlight >}}

2단계 — 공식 명령으로 상태를 묻는다. Codex는 데몬 관리 서브커맨드를 제공합니다. 설치된 CLI와 떠 있는 데몬의 버전을 나란히 보여 주는 version이 특히 유용합니다 — 앞서 본 버전 skew를 직접 눈으로 확인하는 명령입니다.

{{< highlight bash >}} codex daemon version # CLI 버전과 실행 중인 app-server 버전을 JSON으로 출력 codex daemon stop # 데몬 중지 codex daemon start # 다시 시작 # 데몬 없이 일회성 프로세스로 실행 (문제 격리용) codex --no-daemon {{< /highlight >}}

3단계 — 정책을 명시한다. 자동 시작·자동 업데이트를 원하지 않으면 설정 파일에 적어 둡니다. "기본값에 동의하는지"를 한 번은 의식적으로 결정하는 것이 핵심입니다.

{{< highlight toml >}} # ~/.codex/config.toml — 데몬 자동 시작 끄기 [features] daemon_auto_start = false {{< /highlight >}}

4단계 — 서버를 역이용한다. 데몬 아키텍처는 위험만 주는 게 아니라 프로그래밍 표면도 줍니다. OpenCode 서버는 로컬에서 바로 호출할 수 있는 HTTP API입니다.

{{< highlight bash >}} # headless 서버를 명시적으로 띄우고 (기본 127.0.0.1:4096) opencode serve # 헬스 체크 — 서버 버전 확인 curl http://localhost:4096/global/health # 서버가 게시하는 OpenAPI 3.1 스펙 — 전체 API 지도 curl http://localhost:4096/doc # SSE 이벤트 스트림 구독 — 에이전트의 모든 활동이 실시간으로 흐른다 curl -N http://localhost:4096/global/event {{< /highlight >}}

마지막 명령을 띄워 두고 다른 터미널에서 에이전트에게 일을 시켜 보세요. 세션 생성, 도구 호출, 메시지 스트림이 이벤트로 흘러갑니다. 에이전트 모니터링 대시보드나 커스텀 클라이언트가 "이 스트림을 구독하는 프로그램"일 뿐이라는 감각이 생기면, 이번 전환이 열어 주는 가능성이 보이기 시작합니다.

흔한 실수 · 팁

  • "프로세스를 껐는데 설정이 안 먹어요." 데몬 모델에서 가장 흔한 함정입니다. 환경변수·프록시·설정 변경은 이미 떠 있는 데몬에 전달되지 않습니다. 설정을 바꿨으면 codex daemon restart처럼 데몬을 재시작하세요. "터미널을 새로 열면 리셋된다"는 직관은 더 이상 통하지 않습니다.
  • 기업 프록시 환경에서는 NO_PROXY부터. 클라이언트가 로컬 서버와 HTTP로 통신하는 구조에서는, 프록시 설정이 localhost 트래픽까지 가로채면 루프가 생깁니다. OpenCode 문서도 NO_PROXY=localhost,127.0.0.1을 필수로 안내합니다.
  • 버전 skew를 의심 목록에 넣기. 에이전트가 어제까지 되던 기능에서 이상하게 실패하면, 클라이언트·데몬 버전부터 비교하세요(codex daemon version). 자동 업데이트는 내가 모르는 사이에 반쪽만 일어날 수 있습니다.
  • localhost 서버도 인증이 필요합니다. "내 컴퓨터 안인데 뭘"이라고 생각하기 쉽지만, 로컬의 다른 프로세스나 브라우저의 악성 스크립트도 localhost 포트에 요청을 보낼 수 있습니다. OpenCode라면 OPENCODE_SERVER_PASSWORD를 설정하고, 원격 접근은 꼭 필요할 때만 켜세요.
  • 에이전트에 연결한 API 키는 '위임한 키'로 관리하기. 지출 한도와 사용량 알림을 걸어 두면, OpenCode Console 피해자들이 그랬듯 이상 사용을 청구서가 아니라 알림으로 먼저 알 수 있습니다. 플랫폼 침해 공지가 뜨면 해당 키는 즉시 회전(revoke 후 재발급)이 기본입니다.
  • 데몬을 직접 만든다면 두 저장소를 교과서로. 채널별 포트 분리와 등록 파일(OpenCode), 호환성 검사 후 내장 모드 폴백과 --no-daemon 탈출구(Codex)는 전부 오픈소스로 공개돼 있습니다. 특히 탈출구 없는 데몬은 만들지 마세요 — 이번 주 반발의 상당 부분은 기능이 아니라 "끌 수 없음"을 향했습니다.

마무리 (TL;DR)

  • 이번 주(10/12~18) 세 사건 — OpenCode 2.0의 공유 서비스 재설계 발표, Codex CLI의 상주 데몬 논란(10/15 HN), OpenCode Console 키 유출(10/17) — 은 하나의 질문으로 수렴합니다: 에이전트 런타임은 어디서 살아야 하는가.
  • 전환의 동기는 네 가지입니다. 멀티 클라이언트(터미널·데스크톱·웹·IDE), 프로세스보다 오래 사는 세션, 백그라운드 작업, 프로그래밍 가능한 API 표면. LSP·dockerd·ssh-agent가 걸었던 길 그대로입니다.
  • 구현은 갈립니다. OpenCode는 localhost HTTP + OpenAPI 3.1 + SSE(기본 포트 0xC0DE=49374, basic auth, 옵트인 원격 터널), Codex는 유닉스 소켓 + WebSocket JSON-RPC($CODEX_HOME/app-server-control/, 파일 권한 기반)입니다. 접근성과 격리의 트레이드오프입니다.
  • 데몬의 세금: 동의 없는 상주(Codex daemon_auto_start 기본 켜짐 + 공식 문서 부재), 자가 업데이트로 인한 세션 중단(시작 +5분, 이후 60분 간격 확인 — 소스 기본값), 클라이언트·서버 버전 skew, 첫 세션 환경변수의 고착, 그리고 크레덴셜 집중.
  • OpenCode Console 침해는 저장된 프로바이더 키(OpenAI·Anthropic·Google)가 탈취돼 distillation 공격에 쓰인 사건으로, Console 사용자 1.4%가 영향을 받았습니다. 에이전트 인프라는 어디에 있든 키 금고이고, 키 금고는 표적이 됩니다.
  • 오늘 할 일: 내 머신의 에이전트 데몬을 확인하고(ss -ltnp, codex daemon version), 자동 시작·업데이트에 대한 내 정책을 설정 파일에 명시하고, 에이전트에 연결한 키에는 지출 한도·알림을 걸어 두기.
  • 데몬을 설계한다면: 버전·채널 격리, 호환성 검사와 폴백, 명시적 동의 기록, 그리고 무엇보다 끌 수 있는 스위치. 이번 주 논란은 아키텍처가 아니라 '기본값과 투명성'을 향한 것이었습니다.
