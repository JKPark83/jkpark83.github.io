1. 도입 — 이번 주, 하네스가 '실측의 영역'이 되다

코딩 에이전트를 써 본 사람이라면 한 번쯤 이런 논쟁을 봤을 겁니다. "Claude Code가 낫다", "아니다, 미니멀한 하네스가 낫다", "플래닝 도구는 필수다", "아니다, 컨텍스트만 낭비한다". 문제는 지금까지 이 논쟁에 숫자가 없었다는 것입니다. 하네스(harness) — 모델을 감싸고 도구·컨텍스트·루프를 관리하는 실행 계층 — 는 늘 통째로 비교됐고, 그 안의 어떤 부품이 성능을 만드는지는 아무도 몰랐습니다.

이번 주에 그 공백이 한꺼번에 메워졌습니다. 9월 16일 UC Berkeley와 Arena 연구진이 HarnessTax를 공개했습니다. 같은 모델 7종을 Claude Code·Codex CLI·Pi 세 하네스에 태워 동일 과제를 풀게 했더니, 성공률 차이는 벤치마크별로 ±2~5포인트 수준인데 비용은 최대 5배까지 벌어졌습니다. 바로 다음 날인 9월 17일에는 arXiv에 An Empirical Study of Harness Design for Coding Agents(arXiv:2609.20804)가 올라왔고, 이틀 뒤 Hacker News 프론트페이지(약 200점)에 오르며 하네스 논쟁에 다시 불을 붙였습니다. 이 논문은 하네스를 통째로 비교하는 대신 부품 단위로 잘라 176개 조합을 실측한, 최초의 컴포넌트 수준 절제 연구입니다.

결론부터 말하면 이렇습니다. 하네스의 부품들은 "항상 좋은 것"이 하나도 없습니다. 컨텍스트 관리도, 플래닝도, 잘 짜인 도구 세트도 — 전부 조건부로만 도움이 됩니다. 어떤 조건에서 무엇이 통하는지, 이제 숫자로 말할 수 있게 됐습니다.

2. 배경 — 하네스, 그리고 절제 실험이라는 도구

하네스가 낯설다면 이렇게 생각하면 됩니다. 모델이 엔진이라면 하네스는 차체입니다. 시스템 프롬프트, 도구 정의, 도구 실행, 대화 이력 관리, 루프 종료 조건 — 모델 바깥의 모든 것이 하네스입니다. Claude Code, Codex CLI, OpenHands 같은 제품이 전부 "모델 + 하네스" 패키지입니다. 하네스라는 개념 자체가 처음이라면 이전 글 하네스 엔지니어링을 먼저 읽고 오면 좋습니다.

절제 실험(ablation study)은 원래 신경과학 용어입니다. 뇌의 특정 부위를 제거하고 행동이 어떻게 달라지는지 보는 방법인데, ML에서는 시스템에서 부품 하나만 빼거나 바꿔서 그 부품의 기여도를 재는 실험을 뜻합니다. 핵심은 "하나만" 바꾸는 것입니다. 하네스 A와 하네스 B를 통째로 비교하면 수십 개 차이가 뒤섞여 무엇이 효과를 냈는지 알 수 없습니다. 실제로 지난 5월 나온 포지션 페이퍼 Stop Comparing LLM Agents Without Disclosing the Harness는 "하네스를 공개하지 않은 에이전트 비교는 무의미하다"고 지적했습니다. 이번 논문은 그 지적에 대한 실행 답안인 셈입니다.

3. 실험 설계 — 루프는 고정하고 다이얼 세 개만 돌린다

연구진(UMass Amherst·Emory·UNC Charlotte, Zoom 인턴십 기간 수행)은 가벼운 자체 하네스를 만들고 실행 루프는 고정했습니다. 생각하고, 도구를 부르고, 결과를 관찰하는 기본 루프는 모든 실험에서 같습니다. 그리고 세 개의 다이얼만 돌렸습니다.

평가는 실무에서 가장 널리 쓰이는 두 벤치마크로 했습니다. 실제 GitHub 이슈를 고치는 SWE-Bench Verified(500개 과제)와 터미널 작업 중심의 Terminal-Bench 2.1입니다. 모델은 능력 스펙트럼을 커버하도록 Nemotron-3 30B/120B/550B와 Mistral-Medium-3.5-128B 네 가지를 썼습니다. 작은 모델부터 프론티어급까지 걸쳐 있다는 점이 중요한데, 뒤에서 보겠지만 거의 모든 결론이 모델 능력에 따라 뒤집히기 때문입니다.

4. 다이얼 ① 컨텍스트 관리 — 창이 좁을수록 생명줄

긴 작업을 하다 보면 대화 이력이 컨텍스트 윈도우를 넘칩니다. 이때 하네스가 취할 수 있는 전략을 논문은 세 가지 기본 메커니즘으로 정리합니다.

  • M1 — elision(생략): 오래된 도구 관찰 결과의 본문을 짧은 스텁(stub)으로 교체합니다. 규칙 기반이라 공짜에 가깝습니다.
  • M2 — recall(회수): 생략한 원본을 외부 저장소에 보관하고, recall_event 도구로 다시 불러올 수 있게 합니다. elision을 "되돌릴 수 있게" 만드는 장치입니다.
  • M3 — summarization(요약): 오래된 메시지를 같은 모델의 별도 호출로 접어 러닝 서머리로 만듭니다. 품질은 좋지만 호출 비용이 듭니다.

이 셋을 조합해 다섯 단계 전략(T0~T4)을 만들었습니다. T0은 아무것도 안 함(넘치면 그냥 실패), T1은 elision만, T2는 elision + recall, T3은 요약만, T4는 셋 다 — 단 단계적으로: 소프트 임계값에서 먼저 싼 elision을 걸고, 하드 임계값에 닿아야 비싼 요약을 돌립니다.

숫자를 보면 그림이 명확합니다. 32k 예산에서는 관리 없는 하네스(T0)가 관리 있는 하네스보다 35.7포인트 뒤지고, 실패한 과제의 78.7%가 그냥 컨텍스트 오버플로로 죽었습니다. 그런데 예산을 128k로 넓히면 격차는 2.7포인트까지 줄어듭니다. 즉 컨텍스트 관리의 가치는 대부분 "오버플로 사고 방지"에서 나오지, 요약이 모델을 더 똑똑하게 만들어서가 아닙니다.

두 가지 실무 결론이 여기서 나옵니다. 첫째, 순서가 돈을 결정합니다. 싼 elision을 먼저 걸고 정말 필요할 때만 요약을 돌리는 T4가 8개 패널(모델 4 × 벤치마크 2) 중 7개에서 같은 정확도로 최저 비용을 기록했습니다. 처음부터 요약부터 돌리면 품질은 같은데 LLM 호출 요금만 더 냅니다. 둘째, recall은 빼도 됩니다. "지운 걸 다시 불러올 수 있다"는 안전장치는 그럴듯해 보이지만, 실측하니 세팅의 56.3%에서 모델이 recall_event를 단 한 번도 부르지 않았고(중앙값 호출 횟수 0), 정확도는 elision 단독 대비 오히려 −0.36포인트였습니다. 모델은 지나간 관찰 결과를 다시 찾지 않습니다. 기계만 늘었습니다.

컨텍스트를 접는 기법 자체가 궁금하다면 이전 글 컨텍스트 컴팩션과 짝지어 읽으면 좋습니다. 이번 논문은 그 기법들에 "언제, 어떤 순서로"라는 실측 답을 붙여 준 셈입니다.

5. 다이얼 ② 플래닝 — 약한 모델의 버팀목, 강한 모델의 절약 장치

플래닝 컴포넌트는 update_plan 도구로 구현했습니다. 모델이 계획을 세우고 갱신하면 그 계획이 컨텍스트에 지속적으로 고정되는 스캐폴드입니다. Claude Code의 TODO 리스트나 Codex의 플랜 모드와 같은 계열입니다.

결과는 "플래닝은 필수인가"라는 질문 자체가 잘못됐음을 보여 줍니다. 약한 모델에게 플래닝은 정확도 버팀목입니다. 계획을 붙잡아 주면 성공률이 오르는 대신 토큰을 더 씁니다. 반면 강한 모델에게는 정확도가 거의 안 변하고, 대신 비용이 내려갑니다. 계획이 고정돼 있으면 강한 모델은 "내가 어디까지 했더라"를 확인하는 중복 검증 스텝을 덜 밟기 때문입니다. 같은 부품이 모델에 따라 완전히 다른 일을 하는 겁니다 — 하나는 정확도 장치, 하나는 비용 장치.

6. 다이얼 ③ 액션 공간 — 도구를 줘야 할 모델, 뺏어야 할 모델

액션 공간 실험은 두 팔로 나뉩니다. 한쪽은 사전 정의 도구 8종(read_file, write_file, edit_file, list_files, glob_files, grep_text, web_fetch, bash), 다른 쪽은 bash 하나만. 주의할 점: 양쪽 다 bash는 있습니다. "bash-only"는 셸을 주는 대신 파일·검색 보조 도구를 뺀 구성이지, 도구를 아예 안 주는 게 아닙니다.

가장 작은 30B에게 도구 8종은 큰 도움입니다(SWE +15.0, Terminal +10.1포인트). 셸 명령을 서툴게 조합하다 실수하는 대신, 잘 정의된 edit_file을 부르면 되니까요. 그런데 120B에서 격차가 +1.6/+4.5로 줄더니, 550B에서는 역전됩니다. bash만 준 쪽이 +3.6/+5.6포인트 더 정확하고, 비용은 SWE에서 −53%, Terminal에서 −30%였습니다. 셸에 능숙한 모델에게 8개 도구 정의는 매 요청 실려 가는 컨텍스트 짐일 뿐이고, grep_text 한 번 부를 일을 파이프라인 한 줄로 끝내는 쪽이 오히려 빠릅니다. Mistral-Medium-3.5는 과제 성격에 따라 갈렸습니다 — GitHub 이슈 수정(SWE)에서는 도구가 +23.2로 크게 이겼지만, 터미널 중심 과제에서는 bash-only가 +6.7로 이겼습니다. 즉 모델의 셸 숙련도와 과제의 셸 친화도가 함께 답을 결정합니다.

도구 정의가 컨텍스트를 얼마나 잡아먹는지는 이전 글 도구 과부하와 지연 로딩에서 다뤘습니다. 이번 결과는 그 문제의식에 "능력이 충분하면 도구를 빼는 것도 답"이라는 데이터를 보탭니다.

7. 하네스 세금 — HarnessTax가 잰 '기본 요금'

절제 연구가 "부품별 효과"를 쟀다면, 같은 주에 나온 HarnessTax는 "완제품 하네스의 요금표"를 쟀습니다. 모델 7종 × 하네스 3종(Claude Code, Codex CLI, Pi) = 21개 조합에, SWE-bench Lite와 Terminal-Bench 2.0에서 각 30개 과제를 3회씩 시도하게 하고, 9월 1일자 고정 가격표로 비용을 계산했습니다.

결과의 핵심은 한 문장입니다. 하네스는 성공률을 크게 못 바꾸지만, 청구서는 크게 바꿉니다. 성공률에 대한 하네스 효과는 SWE-bench Lite에서 ±2포인트, Terminal-Bench 2.0에서 ±5포인트 수준이었는데, 같은 모델의 비용은 하네스에 따라 최대 5배까지 벌어졌고, 하네스를 잘 고르는 것만으로 정확도 손실 없이 비용을 71% 줄인 사례가 보고됐습니다.

왜 이렇게 벌어질까요? 요청당 기본 컨텍스트를 보면 답이 나옵니다. Claude Code는 시스템 프롬프트와 도구 스키마를 합쳐 요청당 약 27,000 입력 토큰을 깔고 시작하고, Codex CLI는 약 15,000, 미니멀 하네스 Pi는 약 2,600 토큰입니다. 분석 글들이 지적한 디테일이 아픕니다 — 벤치마크 실행에서 정의만 되고 한 번도 호출되지 않은 도구 24개의 스키마가 매 요청 함께 실려 갔습니다. 게다가 에이전트 루프는 이력을 계속 다시 보내니, 장황한 도구 호출 포맷은 대화가 길어질수록 복리로 불어납니다. 캐싱이 실비를 상당히 줄여 주긴 하지만, 기본 컨텍스트가 10배면 절대량의 차이는 남습니다.

두 연구를 겹쳐 읽으면 메시지가 선명해집니다. 절제 연구가 "부품은 조건부로만 가치가 있다"를 보였고, HarnessTax는 "조건에 안 맞는 부품의 값은 성능이 아니라 요금으로 돌아온다"를 보인 겁니다.

8. 실전 — 내 하네스에 바로 적용하는 체크리스트

두 연구의 결론을 실무 규칙으로 옮기면 이렇게 됩니다.

상황권장 설계근거
컨텍스트 예산이 빠듯함 (≤64k)컨텍스트 관리 필수, elision 먼저 → 요약은 하드 임계값에서만32k에서 격차 35.7pt, T4가 7/8 패널 최저 비용
예산이 넉넉함 (≥128k)관리 로직 단순하게 — 격차 2.7pt뿐효용 대부분이 오버플로 방지
recall(지운 내용 복구) 도구넣지 마라56.3% 세팅에서 호출 0회, 정확도 −0.36pt
작은/약한 모델플래닝 켜기(정확도↑), 파일·검색 도구 제공30B에서 도구 +15.0pt
크고 셸에 능한 모델플래닝은 비용 절감용, 도구는 bash 위주로 최소화550B에서 bash-only +3.6~5.6pt, 비용 −30~53%
어떤 하네스를 쓰든요청당 기본 컨텍스트(시스템 프롬프트+도구 스키마)를 측정하라27k vs 2.6k — 성공률은 비슷, 비용은 최대 5배

T4의 단계형 컨텍스트 관리는 직접 구현해도 몇십 줄입니다. 뼈대만 옮기면 이렇습니다.

{{< highlight python >}} SOFT_LIMIT = 0.70 # 윈도우의 70% — 싼 elision 시작 HARD_LIMIT = 0.90 # 90% — 이때만 비싼 LLM 요약 def manage_context(messages, window_budget): used = count_tokens(messages) # 1단계: 규칙 기반 elision — 오래된 도구 관찰부터 스텁으로 교체 if used > window_budget * SOFT_LIMIT: for m in oldest_tool_observations(messages): m.content = f"[생략됨: {m.tool_name} 결과 {m.orig_tokens} 토큰]" used = count_tokens(messages) if used <= window_budget * SOFT_LIMIT: break # 2단계: 그래도 하드 임계값을 넘으면 그때만 요약 호출 if used > window_budget * HARD_LIMIT: old, recent = split_keep_recent(messages, keep_ratio=0.3) summary = llm_summarize(old) # 별도 호출 — 여기가 유일한 추가 비용 messages = [summary] + recent return messages # recall 저장소는 없다 — 실측상 모델이 쓰지 않는다 {{< /highlight >}}

포인트는 두 임계값의 순서입니다. 요약을 먼저 돌리는 하네스는 같은 정확도에 요금만 더 냅니다. 그리고 마지막 주석이 이번 논문의 기여입니다 — "혹시 몰라서" 넣고 싶은 복구 장치를 데이터가 잘라 줍니다.

하네스 세금 쪽은 측정부터 시작하세요. 쓰고 있는 하네스의 요청 로그에서 첫 요청의 입력 토큰 수를 확인하면 됩니다. 그 숫자가 곧 대화가 길어질수록 복리로 불어나는 원금입니다.

9. 흔한 실수 · 팁

실수 1 — "좋은 하네스 부품"을 무조건 다 넣는다. 이번 주 두 연구의 공통 결론은 "부품의 가치는 조건부"라는 것입니다. 플래닝·recall·풍부한 도구 세트를 다 넣은 하네스는 최강 구성이 아니라, 강한 모델 기준으로는 가장 비싼 구성일 가능성이 큽니다.

실수 2 — 벤치마크 표에서 하네스를 무시한다. "모델 A가 모델 B보다 좋다"는 표를 볼 때, 두 모델이 같은 하네스로 측정됐는지 먼저 확인하세요. 하네스가 다르면 모델 비교가 아니라 시스템 비교입니다. 하네스 공개 없는 에이전트 비교를 중단하라는 포지션 페이퍼가 나온 이유입니다.

실수 3 — "bash-only가 이겼다더라"를 도구 무용론으로 읽는다. 실험의 양쪽 팔 모두 bash는 있었습니다. 뺀 것은 파일·검색 보조 도구입니다. 그리고 그 결과조차 550B급에서의 이야기입니다. 30B급 모델을 bash에 던져 놓으면 15포인트를 잃습니다.

실수 4 — 컨텍스트 관리를 "지능 향상 장치"로 기대한다. 실측상 효용의 대부분은 오버플로 사고 방지입니다. 128k 예산에서 격차가 2.7포인트뿐이라는 건, 넉넉한 창에서는 요약 파이프라인을 정교하게 다듬는 것보다 다른 곳에 시간을 쓰는 게 낫다는 뜻입니다.

팁 — 절제 정신을 내 하네스에도. 이 논문의 진짜 교훈은 특정 숫자보다 방법입니다. 하네스에 기능을 넣거나 뺄 때, 켠 버전과 끈 버전을 같은 과제 세트에 돌려 보세요. 과제 20~30개면 방향은 보입니다. "그럴듯해서 넣은" 부품이 recall처럼 호출 0회로 판명나는 일이 생각보다 흔합니다.

10. 마무리 (TL;DR)

  • 이번 주 하네스 실측 연구 두 편이 연달아 나왔습니다 — 9/16 HarnessTax(UC Berkeley·Arena, 하네스 3종 × 모델 7종)와 9/17 하네스 부품 절제 논문(arXiv:2609.20804, 176개 조합, HN 프론트페이지 약 200점).
  • 하네스 부품에 "항상 좋은 것"은 없습니다. 컨텍스트 관리·플래닝·도구 세트 전부 윈도우 예산, 모델 능력, 과제 성격에 따라 효과가 뒤집힙니다.
  • 컨텍스트 관리의 가치는 대부분 오버플로 방지입니다: 32k에서 격차 35.7pt(무관리 실패의 78.7%가 오버플로) → 128k에서 2.7pt. 싼 elision 먼저, 요약은 하드 임계값에서만 거는 단계형(T4)이 7/8 패널에서 같은 정확도로 최저 비용.
  • recall 도구는 빼세요. 세팅의 56.3%에서 호출 0회, 정확도 기여 −0.36pt.
  • 플래닝은 약한 모델에겐 정확도 버팀목, 강한 모델에겐 비용 절감 장치입니다. 액션 공간은 크로스오버합니다 — 30B엔 도구 8종이 +15pt, 550B엔 bash-only가 오히려 +3.6~5.6pt에 비용 −30~53%.
  • 하네스는 성공률(±2~5pt)보다 청구서(최대 5배)를 바꿉니다. 요청당 기본 컨텍스트가 Claude Code ≈27k, Codex CLI ≈15k, Pi ≈2.6k 토큰 — 내 하네스의 첫 요청 입력 토큰부터 재 보세요.
