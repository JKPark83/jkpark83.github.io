1. 도입 — 분명히 "배포 금지"라고 적었는데

멀티에이전트 파이프라인을 만들어 본 분이라면 한 번쯤 겪는 시나리오입니다. 플래너 에이전트가 계획을 세우면서 분명히 적었습니다. "스테이징 smoke 테스트가 통과하기 전에는 프로덕션 배포를 절대 하지 말 것." 계획이 길어지니 오케스트레이터가 요약을 만들어 실행 에이전트에게 넘깁니다. 요약에도 "스테이징 검증 관련 주의 필요"라는 문장이 들어 있긴 합니다. 그런데 실행 에이전트는 태연하게 배포 명령을 실행합니다. 로그를 다시 읽어 봐도 이상합니다. 정보가 사라진 것도 아닌데, 왜 지켜지지 않았을까요?

이번 주 AI 엔지니어링 커뮤니티가 정확히 이 질문에 대한 답을 얻었습니다. 8월 25일 공개된 논문 When "Must" Becomes "Maybe": Constraint Weakening in LLM Agent Workflows(arXiv:2608.24569)는 이 현상에 제약 약화(constraint weakening)라는 이름을 붙이고, 1,296개의 통제된 에피소드로 원인을 분리해 냈습니다. 결론이 꽤 충격적입니다. 흔히 쓰는 자유 서술 요약으로 핸드오프하면 안전 차단 조건이 100% 무력화되고, 금지된 행동의 54.2%가 실제로 실행됐습니다. 멀티에이전트의 실패를 분류한 MAST 연구에서 에이전트 간 정보 전달 문제가 전체 실패의 36.9%를 차지한다는 결과와 겹쳐 읽히면서, "핸드오프는 자유 서술이 아니라 스키마여야 한다"는 논의가 이번 주 내내 이어졌습니다.

결론부터 말하면 이렇습니다. 정보가 전달되는 것과 구속력이 전달되는 것은 완전히 별개의 문제입니다. 요약 속에 "언급"된 제약은 다음 에이전트에게 그저 배경 지식일 뿐, 행동을 막는 힘이 없습니다. 이 글에서는 제약이 어디서 어떻게 새는지, 그리고 스키마와 검증 게이트로 어떻게 막는지를 숫자와 코드로 뜯어봅니다.

이 글에서 얻어 갈 것. ① 핸드오프 아티팩트(요약·계획·티켓·메모리)가 왜 제약을 녹여 버리는지, ② "운영 상태(operational state)"와 "참고 정보"의 구분법, ③ 2608.24569 실험의 설계와 수치 해석, ④ Cognition·Anthropic이 먼저 도착해 있던 설계 원칙, ⑤ pydantic 스키마 + 실행 전 검증 게이트로 만드는 방어 코드.

2. 배경 — 핸드오프란 무엇이고, 왜 통째로 넘기지 못하나

핸드오프(handoff)는 한 에이전트가 하던 일을 다른 에이전트에게 넘기는 지점입니다. 플래너가 세운 계획을 실행 에이전트가 받거나, 리서치 서브에이전트의 조사 결과를 리드 에이전트가 취합하거나, 오늘 세션의 작업 내역을 내일 세션이 메모리로 이어받는 순간이 전부 핸드오프입니다.

이때 이전 에이전트의 컨텍스트를 통째로 넘기면 되지 않을까 싶지만, 실무에서는 그러기 어렵습니다. 첫째, 컨텍스트가 길어질수록 토큰 비용이 커지고, 둘째, 길이 자체가 성능을 갉아먹습니다. 이 블로그에서 다룬 컨텍스트 부패(context rot) 현상처럼, 관련 없는 내용이 쌓이면 모델은 정작 중요한 것을 놓칩니다. 그래서 대부분의 프레임워크는 핸드오프 지점에서 컨텍스트를 중간 아티팩트로 변환합니다. 요약, 계획 문서, 작업 티켓, 압축된 메모리가 대표적입니다. 예를 들어 OpenAI Agents SDK의 handoff는 기본값으로는 전체 대화 이력을 넘기지만, input_filter로 이력을 잘라내고 가공하는 것을 표준 패턴으로 안내합니다.

문제는 이 변환이 손실 압축이라는 점입니다. 어릴 때 하던 '옮겨 말하기 게임(전화 게임)'을 떠올려 보세요. 첫 사람이 "내일 오전 9시까지 반드시 우산을 가져와"라고 속삭였는데, 네 사람을 거치면 "우산 얘기가 있었던 것 같아"가 됩니다. 정보의 흔적은 남지만, 지시로서의 힘은 사라집니다. 에이전트 파이프라인의 요약도 똑같은 일을 합니다.

이게 드문 엣지 케이스가 아니라는 근거도 있습니다. 버클리 연구진이 150개 이상의 실행 트레이스를 분석해 만든 실패 분류학 MAST(Why Do Multi-Agent LLM Systems Fail?)는 멀티에이전트 실패를 14가지 모드, 3개 범주로 나눴는데, 그중 에이전트 간 부정합(inter-agent misalignment) — 소통 단절, 핸드오프 중 컨텍스트 손실, 형식 불일치 — 이 전체 실패의 36.9%를 차지했습니다. 멀티에이전트가 이상해질 때 세 번에 한 번은 에이전트 사이의 '전달'이 범인이라는 뜻입니다.

3. 제약 약화 — '언급됐다'와 '구속력이 유지됐다'는 다르다

2608.24569 논문의 핵심 통찰은 컨텍스트 안의 정보가 두 종류로 나뉜다는 것입니다.

  • 참고 정보(reference information) — 알고 있으면 도움이 되는 배경. 압축하거나 뭉개도 큰일이 나지 않습니다. "이 프로젝트는 Python 3.12를 쓴다" 같은 것.
  • 운영 상태(operational state) — 실행을 구속하는 살아 있는 상태. "조건 X가 해소되기 전에는 행동 Y 금지" 같은 차단 조건, 권한 범위, 실패 시 폴백, 지금까지의 실행 결과. 한 글자라도 뭉개지면 행동이 달라집니다.

자유 서술 요약은 이 둘을 구분하지 않습니다. LLM에게 "이 계획을 간결하게 요약해 줘"라고 하면, 모델은 문장을 자연스럽게 만드는 과정에서 운영 상태를 참고 정보의 문체로 다시 씁니다. "스테이징 테스트 통과 전 배포 금지(활성 차단)"가 "배포 전 스테이징 검증이 권장됨"이 되는 식입니다. 정보는 남았지만 양태(modality)가 바뀌었습니다. '반드시(must)'가 '아마도/하면 좋음(maybe/should)'으로 미끄러진 겁니다. 논문 제목이 정확히 이 현상을 가리킵니다.

왜 이런 일이 생길까요? 요약을 만드는 LLM의 목적 함수는 "자연스럽고 간결한 글"이지 "구속력 보존"이 아니기 때문입니다. 자연어에서 명령문과 서술문의 경계는 흐릿하고, 압축 과정에서 가장 먼저 뭉개지는 것이 바로 이 경계입니다. 게다가 받는 쪽 에이전트도 요약 속 문장을 지시가 아니라 맥락으로 읽습니다. 전달자와 수신자 양쪽에서 이중으로 약해지는 셈입니다.

4. 숫자 읽기 — 100% 무력화, 54.2% 금지 행동, 그리고 4개 필드

논문의 실험 설계는 깔끔합니다. 워크플로 안에 안전 차단 조건(safety blocker)을 심습니다. 차단 조건은 네 가지 상태 필드를 갖습니다: 전제조건(무엇이 해소돼야 풀리나), 권한(누가 풀 수 있나), 폴백(못 풀면 어떻게 하나), 실행 결과(지금 상태가 뭔가). 그리고 핸드오프 변환 방식만 바꿔 가며 — 다른 변수는 고정한 채 — 다운스트림 실행 에이전트가 차단 조건을 지키는지를 1,296개의 합성 에피소드에서 측정했습니다.

초록이 보고한 결과를 요약하면 이렇습니다.

이 세 구성이 각각 말해 주는 바를 풀어 보겠습니다.

첫째, 자유 서술 요약은 생각보다 훨씬 심하게 샙니다. 100%라는 수치는 "가끔 놓친다"가 아니라 "구조적으로 항상 놓친다"는 뜻입니다. 프롬프트에 "중요한 제약은 꼭 유지해"라고 덧붙이는 수준으로는 바뀌지 않는, 표현 형식 자체의 문제라는 겁니다.

둘째, 검증 게이트는 최후의 방어선이지 해결책이 아닙니다. 실행 직전에 "이 행동이 차단 조건에 걸리는지" 별도로 검사하는 게이트를 붙이면 금지 행동은 사라집니다. 하지만 아티팩트의 95.3%에서는 차단 조건이 여전히 무력화된 채입니다. 무슨 뜻이냐면, 게이트가 없는 다른 경로 — 예를 들어 아티팩트를 이어받은 세 번째 에이전트, 또는 사람이 그 요약을 읽고 내리는 판단 — 는 여전히 무방비라는 겁니다. 안전망 하나로 구조 문제를 덮은 상태입니다.

셋째, 고치는 비용은 의외로 쌉니다. 거창한 학습이나 새 모델이 필요한 게 아니라, 핸드오프 아티팩트에 전제조건·권한·폴백·실행 결과 네 필드를 구조화된 형태로 복원하는 것만으로 보존율 100%, 금지 행동 0%가 됐습니다. 문제는 능력이 아니라 형식이었던 겁니다.

주의. 이 수치는 통제된 합성 에피소드 기준이고, 아직 피어 리뷰 전의 프리프린트입니다. 실제 프로덕션의 지저분한 조건(업스트림 탐지 오류, 모호한 제약 표현)에서는 절대값이 달라질 수 있습니다. 다만 "형식이 구속력을 좌우한다"는 방향성은 아래에서 볼 다른 연구·실무 보고와 일관됩니다.

5. 더 큰 그림 — constraint drift, 그리고 선배들의 원칙

이 논문이 외딴 발견은 아닙니다. 올해 5월 공개된 Safe Multi-Agent Behavior Must Be Maintained, Not Merely Asserted(arXiv:2605.10481)는 더 넓은 개념으로 제약 표류(constraint drift)를 정의했습니다. 제약이 메모리, 위임, 통신, 도구 사용, 감사, 최적화라는 여섯 경로를 지나며 손실·왜곡·약화·완화되는 현상입니다. 시스템이 최종 답변만 보면 멀쩡한데, 중간에 내부 메시지로 비공개 정보를 흘리거나, 원래 범위를 넘는 권한을 위임하거나, 어떤 행동이 왜 허용됐는지 재구성할 증거를 잃어버릴 수 있다고 지적합니다. 처방도 같은 방향입니다. 안전에 관련된 제약은 프롬프트 속 문장이 아니라 명시적 실행 상태(explicit execution state)로 유지해야 한다는 것.

실무 쪽 선배들은 경험적으로 같은 결론에 먼저 도착해 있었습니다. Devin을 만든 Cognition의 Don't Build Multi-Agents(2025)는 "행동은 암묵적 결정을 운반한다(actions carry implicit decisions)"며, 컨텍스트를 쪼개 나눠 가진 에이전트들은 서로 충돌하는 전제 위에서 행동하게 된다고 경고했습니다. 핸드오프에서 제약이 새는 것은 이 경고의 구체적 사례입니다. Anthropic의 멀티에이전트 리서치 시스템 구축기도 같은 교훈을 담고 있습니다. 서브에이전트에게 일을 맡길 때는 목표, 출력 형식, 사용할 도구와 소스 안내, 작업 경계를 명시해야 하며, 이게 없으면 에이전트들이 일을 중복하고, 빈틈을 남기고, 필요한 정보를 찾지 못했다고 보고합니다. 위임(핸드오프의 한 방향)에서도 자유 서술 대신 구조화된 명세가 답이었던 겁니다.

세 갈래 — 통제 실험, 이론적 분류, 실무 보고 — 가 한 지점을 가리킵니다. 제약은 '주장'하는 것이 아니라 '상태로 유지'하는 것이고, 핸드오프는 그 상태가 가장 쉽게 증발하는 지점입니다.

6. 실전 — 스키마 핸드오프 + 검증 게이트 만들기

이제 직접 만들어 봅시다. 방어는 두 겹입니다. ① 핸드오프 아티팩트를 스키마로 강제해서 운영 상태가 자유 서술 속으로 녹아들지 못하게 하고, ② 실행 직전 검증 게이트를 별도 코드로 둬서 모델의 선의에 기대지 않는 겁니다.

먼저 흔한 안티패턴부터 보겠습니다.

{{< highlight python >}} # ❌ 안티패턴: 자유 서술 요약으로 핸드오프 plan = planner_agent.run(task) summary = llm.complete( f"다음 계획을 간결하게 요약해 줘:\n{plan}" ) result = executor_agent.run(context=summary) # → "배포 금지"가 "검증 권장"으로 문체가 바뀌어도 아무도 모른다 {{< /highlight >}}

이제 스키마를 도입합니다. 핵심은 참고 정보와 운영 상태를 별도 필드로 분리하고, 운영 상태에는 논문이 말한 4필드(전제조건·권한·폴백·실행 결과)를 필수로 요구하는 겁니다.

{{< highlight python >}} from typing import Literal from pydantic import BaseModel, Field class Blocker(BaseModel): """실행을 구속하는 차단 조건 — 압축·의역 금지, 무손실 전달 대상""" id: str forbidden_action: str # 무엇이 금지되나: "prod 배포" precondition: str # 해제 전제조건: "staging smoke 테스트 전체 통과" authority: str # 누가 해제할 수 있나: "release-manager 승인" fallback: str # 해제 불가 시: "배포 중단 후 사람에게 보고" status: Literal["active", "cleared"] # 실행 결과/현재 상태 class HandoffArtifact(BaseModel): goal: str context_summary: str = Field( description="참고 정보. 자유롭게 압축해도 되는 배경." ) blockers: list[Blocker] = Field( description="운영 상태. 원문 그대로 복사해 전달할 것." ) permissions: list[str] # 이 에이전트에게 허용된 행동 범위 done_criteria: str # 완료 판정 기준 # 요약 LLM에게는 context_summary만 만들게 하고, # blockers는 코드가 이전 아티팩트에서 그대로 복사한다 artifact = HandoffArtifact( goal=plan.goal, context_summary=llm.complete(f"배경만 3문장으로: {plan.body}"), blockers=plan.blockers, # ← LLM을 거치지 않는다! permissions=plan.permissions, done_criteria=plan.done_criteria, ) {{< /highlight >}}

여기서 제일 중요한 줄은 blockers=plan.blockers입니다. 차단 조건은 LLM의 재서술을 거치지 않고 구조화된 데이터로 복사됩니다. 요약 모델이 아무리 문장을 다듬어도 운영 상태는 건드릴 수 없습니다. 논문 실험에서 "4필드 복원 = 보존 100%"가 나온 이유가 바로 이겁니다. 보존을 모델의 능력 문제에서 파이프라인의 형식 문제로 옮긴 겁니다.

두 번째 겹, 검증 게이트입니다. 실행 에이전트가 도구를 호출하기 직전에 코드가 차단 조건을 검사합니다.

{{< highlight python >}} class BlockedActionError(Exception): pass def verify_gate(artifact: HandoffArtifact, tool_name: str, args: dict): """도구 실행 직전 호출 — 모델의 판단이 아니라 코드가 막는다""" for b in artifact.blockers: if b.status != "active": continue # 금지 행동 매칭은 도메인에 맞게: 여기선 도구 이름 기준 예시 if matches(b.forbidden_action, tool_name, args): raise BlockedActionError( f"[{b.id}] '{tool_name}' 차단됨. " f"해제 조건: {b.precondition} / 권한: {b.authority} / " f"폴백: {b.fallback}" ) # 에이전트 루프에 끼워 넣기 for tool_call in agent_response.tool_calls: verify_gate(artifact, tool_call.name, tool_call.args) # 통과해야만 execute(tool_call) # 실행된다 {{< /highlight >}}

이 게이트는 프롬프트가 아니라 코드라는 점이 핵심입니다. 이 블로그의 가드레일 컨트롤 플레인 편에서 다뤘던 원칙 — "정책은 모델 바깥에서 집행한다" — 의 핸드오프 버전입니다. 프레임워크를 쓴다면 같은 자리를 찾으면 됩니다. OpenAI Agents SDK라면 handoff의 input_filter에서 blockers를 보존·주입하고 guardrail 훅에서 게이트를 걸고, LangGraph라면 노드 사이 state 스키마에 blockers 필드를 두고 실행 노드 앞에 검증 노드를 끼우는 식입니다.

덤으로 얻는 것. blockers가 구조화돼 있으면 관측성도 공짜로 따라옵니다. "현재 활성 차단 조건 개수", "차단 조건이 해제된 이력(누가, 언제, 어떤 전제조건으로)"을 대시보드에 그대로 띄울 수 있고, 사고가 났을 때 어느 핸드오프에서 상태가 사라졌는지 diff로 추적할 수 있습니다. 자유 서술 요약에서는 불가능한 일입니다.

7. 흔한 실수 · 팁

  • "요약 프롬프트에 '제약을 유지해'라고 쓰면 되지 않나?" — 완화는 되지만 해결이 안 됩니다. 문제의 본질은 자유 서술이라는 형식이 양태(must/should/maybe)를 보존하지 못한다는 것이므로, 형식을 바꿔야 합니다. 프롬프트 지시는 스키마의 보조 수단으로만 쓰세요.
  • blockers 필드를 만들어 놓고 LLM에게 채우게 한다. — 스키마의 절반만 쓰는 겁니다. 요약 모델이 blockers를 다시 쓰게 하면 그 과정에서 또 약화됩니다. 차단 조건은 코드가 이전 단계에서 복사하고, LLM은 새 차단 조건을 추가만 할 수 있게 하는 편이 안전합니다.
  • 검증 게이트만 믿는다. — 논문 수치가 보여 주듯 게이트는 금지 행동을 0%로 만들지만 아티팩트의 95.3%는 여전히 무력화된 채입니다. 게이트가 커버하지 않는 소비자(다른 에이전트, 사람, 배치 잡)가 그 아티팩트를 읽는 순간 구멍이 다시 열립니다. 스키마 보존이 본체, 게이트는 보험입니다.
  • 모든 것을 blocker로 만든다. — 전부 운영 상태로 승격하면 컨텍스트가 다시 비대해지고, 진짜 차단 조건의 신호가 희석됩니다. "위반하면 되돌리기 어려운 행동이 실행되는가?"를 기준으로 소수만 엄격하게 관리하세요. 나머지는 참고 정보로 압축하는 게 맞습니다.
  • 해제 권한을 실행 에이전트 자신에게 준다. — authority가 "본인 판단"이면 차단 조건이 아니라 권고입니다. 해제는 다른 주체(사람, 별도 검증 에이전트, 테스트 통과 이벤트)만 할 수 있어야 하고, 해제 이력을 남겨야 합니다. 승인 피로 편에서 다룬 것처럼, 사람 승인을 요구할 지점은 좁고 명확하게 잡으세요.
  • 멀티에이전트 자체를 반성 없이 늘린다. — 핸드오프는 존재 자체가 위험 지점입니다. Cognition의 조언대로, 컨텍스트를 공유하는 단일 에이전트로 충분한 작업이라면 핸드오프를 만들지 않는 것이 최고의 방어입니다. 쪼개야 한다면 이 글의 패턴을 쓰고, 쪼개지 않아도 된다면 쪼개지 마세요.

8. 마무리 (TL;DR)

  • 멀티에이전트 핸드오프에서 정보 전달과 구속력 전달은 별개입니다. 요약에 "언급"된 제약은 다음 에이전트에게 배경 지식일 뿐, 행동을 막지 못합니다.
  • When "Must" Becomes "Maybe"(2026-08-25)는 이를 통제 실험으로 규명했습니다. 자유 서술 압축 핸드오프에서 안전 차단 조건 100% 무력화, 금지 행동 54.2% 실행. 상태 4필드(전제조건·권한·폴백·실행 결과)를 복원하면 보존 100%, 금지 행동 0%.
  • 다운스트림 검증 게이트만으로는 부족합니다. 사고(금지 행동)는 막아도 아티팩트의 95.3%는 무력화된 채 남아, 게이트 밖 소비자에게 그대로 새어 나갑니다.
  • 이 발견은 MAST의 "실패의 36.9%는 에이전트 간 부정합", constraint drift 연구의 "제약은 명시적 실행 상태로", Cognition·Anthropic의 실무 원칙과 한 방향입니다.
  • 실전 처방 두 겹: ① 핸드오프 아티팩트를 스키마로 강제하되 차단 조건은 LLM을 우회해 코드로 복사하고, ② 실행 직전 코드 게이트로 한 번 더 지키세요. 그리고 가능하다면 핸드오프 수 자체를 줄이는 것이 최고의 방어입니다.
