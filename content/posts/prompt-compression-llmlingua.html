1. 왜 프롬프트가 무거워지는가

LLM에 뭔가를 시킬 때, 우리가 보내는 건 대부분 “질문”이 아닙니다. 질문은 한 줄이고, 나머지는 그 질문에 답하도록 모델을 준비시키는 컨텍스트(context)입니다. 시스템 프롬프트, RAG로 찾아 온 문서 청크 여러 개, few-shot 예시 몇 개, 지금까지의 대화 기록… 이런 것들이 쌓여 프롬프트의 90%를 차지하곤 합니다.

문제는 이 토큰을 매 호출마다 낸다는 데 있습니다. 입력 토큰에도 돈이 붙고, 입력이 길수록 모델이 첫 글자를 뱉기까지의 시간(프리필, prefill)도 늘어납니다. RAG에서 정확도를 올리겠다고 청크를 3개에서 10개로 늘리면, 청구서와 지연 시간은 정직하게 3배 넘게 커집니다. 게다가 그 청크에는 정작 답에 필요 없는 문장이 잔뜩 섞여 있죠.

그래서 실무자들 사이에서 꾸준히 다시 화제가 되는 게 프롬프트 압축(prompt compression)입니다. 2026년 들어 “LLM API 비용 줄이기”, “inference 최적화” 계열 글이 여러 엔지니어링 블로그에서 다시 상위에 올랐고, 공통으로 빠지지 않고 등장하는 항목이 바로 프롬프트 압축입니다. 핵심 아이디어는 단순합니다 — 같은 뜻이라면, 굳이 긴 토큰으로 보낼 필요가 없다.

한 줄 요약. 프롬프트 압축은 프롬프트의 의미는 최대한 지키면서 토큰 수만 줄이는 기법입니다. 사람이 읽을 땐 어색해도, 모델이 답을 뽑는 데 필요한 정보만 남기면 됩니다. 대표 도구인 Microsoft의 LLMLingua는 최대 20배까지 줄이면서도 성능 손실을 작게 유지한다고 보고합니다.

2. 배경 — 압축은 캐싱·요약과 뭐가 다른가

“토큰 줄이기”라는 말은 여러 기법에 걸쳐 쓰여서 헷갈리기 쉽습니다. 시작하기 전에 이웃 개념들과 선을 그어 둡시다. 넷 다 목적은 “컨텍스트 비용 줄이기”지만, 손대는 대상과 방식이 다릅니다.

기법무엇을 하나정보 손실언제
프롬프트 캐싱
(prompt caching)		똑같은 프리픽스의 계산 결과를 재사용없음(손실 X)같은 앞부분을 반복해 보낼 때
시맨틱 캐싱
(semantic caching)		비슷한 질문의 답을 재사용없음(응답 재사용)비슷한 질문이 자주 올 때
compaction
(요약 압축)		대화가 길어지면 앞부분을 요약으로 갈아끼움있음(요약 손실)컨텍스트 창이 찰 때
프롬프트 압축
(prompt compression)		보내기 직전 프롬프트에서 덜 중요한 토큰을 솎아냄있음(솎아내기 손실)매 호출의 컨텍스트가 클 때

차이를 한 문장으로 정리하면 이렇습니다. 캐싱은 “아낀다(재사용)”, 압축은 “줄인다(버린다)”입니다. 캐싱은 원본을 그대로 두고 계산·응답만 재활용하니 손실이 없습니다. 반면 압축은 프롬프트 자체를 더 짧게 다시 써서 보내므로, 어쩔 수 없이 뭔가를 버립니다. compaction과도 헷갈리기 쉬운데, compaction은 주로 에이전트의 대화 기록을 요약해 갈아끼우는 장기 전략이고, 프롬프트 압축은 이번 호출에 들어갈 컨텍스트를 보내기 직전에 토큰 단위로 솎는 즉석 처리입니다.

중요한 건 이들이 경쟁이 아니라 조합이라는 점입니다. RAG 청크를 압축해 짧게 만든 뒤, 그 짧아진 프리픽스를 캐싱해 재사용할 수도 있습니다. 이 글은 그중 “압축” 한 조각을 깊게 팝니다.

3. LLMLingua — 정보량 낮은 토큰을 솎아내기

가장 널리 쓰이는 도구는 Microsoft Research의 LLMLingua입니다(GitHub 별 약 6.5천). 발상은 정보 이론에서 옵니다. 문장 속 모든 토큰이 똑같이 중요하지는 않죠. “그, 를, 은, 에서” 같은 토큰은 앞뒤만 봐도 쉽게 예측되지만, 고유명사나 숫자, 핵심 동사는 예측하기 어렵습니다. 예측하기 어려운 토큰일수록 정보량이 크다는 뜻입니다.

이 “예측 어려움”을 수치로 잰 게 perplexity(당혹도)입니다. LLMLingua는 GPT 같은 큰 모델이 아니라 작은 언어 모델(예: LLaMA-7B, 더 작게도 가능)을 하나 두고, 프롬프트의 각 토큰에 대해 “이 토큰이 얼마나 뜻밖인가”를 계산합니다. 그리고 perplexity가 낮은(=뻔한) 토큰부터 지웁니다. 목표 압축률에 도달할 때까지요. 뻔한 토큰은 지워도 큰 모델이 문맥으로 복원할 수 있으니, 정보 손실이 작다는 논리입니다.

여기에 두 갈래의 확장이 있습니다. LongLLMLingua는 긴 컨텍스트(특히 RAG)를 겨냥합니다. 문서가 길어지면 모델이 중간을 잘 못 보는 “lost in the middle” 문제가 생기는데, LongLLMLingua는 질문과 관련도가 높은 문서·문장에 예산을 더 주고 순서까지 재배치합니다. 논문은 이 방식으로 RAG 성능을 최대 21.4%까지 끌어올리면서 토큰은 원본의 약 25%만 썼다고 보고합니다. 덜 넣었는데 더 잘 맞히는 구간이 존재한다는 뜻입니다. 관련 없는 토큰이 오히려 방해였던 셈이죠.

왜 “덜 넣었는데 더 잘” 될까? 긴 컨텍스트에는 답과 무관한 문장이 많고, 그 노이즈가 모델의 주의를 흩뜨립니다. 관련 낮은 토큰을 걷어 내면 신호 대 잡음비가 올라가, 특정 구간에서는 압축이 정확도까지 올립니다. 물론 너무 세게 압축하면 정답 근거까지 날아가니, 압축률은 늘 실측으로 정해야 합니다.

4. LLMLingua-2 — perplexity를 버리고 분류기로

원조 LLMLingua에는 약점이 있었습니다. perplexity는 “다음 토큰 예측”이라는 단방향 신호라, 정작 어떤 토큰을 지워야 뜻이 안 상하는지와 완벽히 맞아떨어지지 않습니다. 또 매번 작은 LM으로 perplexity를 계산하는 비용도 은근히 큽니다.

LLMLingua-2는 접근을 바꿨습니다. 압축을 토큰 분류(token classification) 문제로 다시 정의합니다 — 각 토큰에 “유지(keep)” 또는 “삭제(drop)” 라벨을 붙이는 이진 분류죠. 이걸 위해 GPT-4에게 회의록 데이터(MeetingBank)를 “핵심은 남기고 군더더기는 빼고 압축하라”고 시켜 원본–압축본 쌍을 대량으로 만들고(데이터 증류, data distillation), 그 라벨로 BERT급의 작은 인코더(XLM-RoBERTa)를 학습시킵니다.

결과는 실무에 유리한 방향입니다. 분류기는 양방향 문맥을 한 번에 보므로 어떤 토큰이 중요한지 더 정확히 짚고, 작은 인코더라 원조보다 3~6배 빠릅니다. 학습 도메인 밖 데이터에서도 잘 버텨(“task-agnostic”), 어떤 프롬프트가 올지 모르는 프로덕션에 더 실용적입니다. 정리하면 이렇습니다.

어느 걸 고를까? 특별한 이유가 없다면 프로덕션에서는 LLMLingua-2가 기본값으로 무난합니다. 빠르고, 처음 보는 프롬프트에도 잘 버티니까요. 아주 긴 RAG 컨텍스트를 다루고 관련도 기반 재배치까지 원하면 LongLLMLingua를 따로 검토하세요.

5. hard vs soft — 텍스트를 지울까, 임베딩으로 뭉갤까

지금까지 본 LLMLingua 계열은 전부 hard prompt 압축입니다. 결과물이 여전히 사람이 읽을 수 있는 “텍스트”라서요(어색하긴 해도요). 장점은 명확합니다 — 어떤 모델에도 그대로 넣을 수 있고, 무엇이 남았는지 눈으로 확인할 수 있습니다.

다른 갈래는 soft prompt 압축입니다. 텍스트를 지우는 대신, 긴 컨텍스트를 몇 개의 임베딩(벡터)으로 뭉쳐 넣습니다. 대표적으로 Gist 토큰은 프롬프트를 소수의 특수 토큰 활성값으로 압축해 캐싱하는데, 최대 26배까지 줄었다고 보고합니다. xRAG는 검색된 문서를 임베딩 모델로 뽑은 단 하나의 토큰으로 밀어 넣어 극단적으로 압축합니다.

대신 soft 방식은 대가가 있습니다. 벡터라 사람이 못 읽고(디버깅이 어렵고), 그 벡터를 이해하도록 모델 쪽을 손봐야 해서 아무 API 모델에나 못 붙입니다. 또 xRAG 같은 극단 압축은 “대략 무슨 주제”는 잘 담지만 숫자·날짜·이름 같은 세부는 흘리기 쉽습니다. 정밀한 사실이 걸린 작업엔 위험하죠.

6. 실전 — 코드로 RAG 컨텍스트 압축하기

말보다 코드가 빠릅니다. llmlingua 패키지 하나면 됩니다. 여기서는 프로덕션에 무난한 LLMLingua-2로 RAG 문서 청크를 압축해 보겠습니다.

{{< highlight bash >}} pip install llmlingua {{< /highlight >}} {{< highlight python >}} from llmlingua import PromptCompressor # LLMLingua-2 압축기 로드 (BERT급 인코더라 가볍고 빠르다) compressor = PromptCompressor( model_name="microsoft/llmlingua-2-xlm-roberta-large-meetingbank", use_llmlingua2=True, ) # RAG로 찾아 온 긴 문서 청크(예: 수백~수천 토큰) context = retrieved_docs_joined # 검색 결과를 이어 붙인 긴 문자열 result = compressor.compress_prompt( context, rate=0.5, # 목표: 토큰을 절반으로 (0.33이면 1/3만 남김) force_tokens=["\n", ".", "?", ":"], # 이 토큰들은 지우지 않고 보호(구조 유지) ) print(result["compressed_prompt"]) # 압축된 텍스트 print(result["origin_tokens"], "→", result["compressed_tokens"]) print("절감률:", result["rate"]) # 실제 압축 비율 {{< /highlight >}}

compress_prompt이 돌려주는 건 딕셔너리입니다. compressed_prompt에 압축된 텍스트가 들어 있고, origin_tokens·compressed_tokens로 몇 토큰이 몇 토큰으로 줄었는지 바로 확인할 수 있습니다. 이제 이 compressed_prompt를 원래 청크 자리에 넣어 LLM을 호출하면 됩니다.

핵심은 명령과 질문은 압축기에 넣지 않는다는 점입니다. LLMLingua에는 이를 위한 인자가 따로 있습니다.

{{< highlight python >}} # 명령(instruction)과 질문(question)은 그대로 두고, 가운데 컨텍스트만 압축 result = compressor.compress_prompt( context, # 압축 대상: RAG 문서만 instruction="다음 자료만 근거로 한국어로 답하라.", # 그대로 유지 question="2019년 한국 GDP 성장률은?", # 그대로 유지 rate=0.5, force_tokens=["\n", ".", "?", ":"], ) # 최종 프롬프트 = 유지된 명령 + 압축된 컨텍스트 + 유지된 질문 final_prompt = result["compressed_prompt"] answer = call_llm(final_prompt) # 실제 답변용 큰 모델 호출 {{< /highlight >}}
왜 명령·질문은 빼나요? 지시문과 질문은 답의 방향을 정하는 “설계도”라, 여기서 토큰 하나만 어긋나도 결과가 통째로 흔들립니다. 게다가 이 부분은 대개 짧아서 압축해 봐야 몇 토큰 못 아낍니다. 부풀기 쉬운 컨텍스트만 줄이고, 짧고 결정적인 부분은 원본 그대로가 원칙입니다.

돌려 보면 감이 옵니다. 압축률(rate)을 0.3~0.5로 두면 대개 눈에 띄는 품질 저하 없이 토큰을 크게 아낄 수 있고, 그보다 세게 줄이면(0.2 이하) 답이 흔들리기 시작합니다. 이 경계는 데이터마다 다르므로 반드시 내 평가셋으로 재 보세요. “압축률을 조금씩 올리며 정답률이 꺾이는 지점 직전”이 실전 스위트스폿입니다.

7. 에이전트에서는 왜 깨지는가

여기서부터가 이 글에서 가장 중요한 부분입니다. 프롬프트 압축은 RAG 문서·few-shot·긴 대화 기록처럼 “자연어 덩어리”에는 잘 듣지만, 에이전트의 프롬프트에는 그대로 쓰면 오히려 망가지기 쉽습니다.

이유는 문법입니다. 에이전트 프롬프트에는 tool 호출 형식, JSON 스키마, 함수 이름과 인자, 코드, 특수 토큰, 정확한 파일 경로 같은 구조(structure)가 잔뜩 들어 있습니다. 자연어에서는 조사 하나쯤 빠져도 큰 모델이 문맥으로 메웁니다. 하지만 {"name": "search", "args": {"q": ...}}에서 따옴표나 중괄호, 필드 이름의 한 토큰이 “정보량이 낮다”는 이유로 솎여 나가면, 그건 복원 대상이 아니라 깨진 문법이 됩니다. 최근 연구들은 이처럼 토큰 단위 추출 압축이 에이전트의 “행동 문법(action grammar)”을 파괴해, 툴 호출이 실패하거나 형식이 어긋난다고 지적합니다.

그래서 에이전트에서는 접근을 바꿔야 합니다. 토큰을 마구 솎는 대신, 구조는 통째로 지키고 “줄일 수 있는 덩어리”만 골라서 다룹니다. 실무에서 잘 통하는 패턴은 이렇습니다.

  • 구조는 압축 금지 목록에 넣는다. 시스템 프롬프트, tool 정의, JSON 스키마, 코드 블록은 압축기에 아예 넣지 않습니다.
  • 큰 tool 결과는 압축 말고 “치운다”. 검색·크롤링 결과처럼 큰 tool 출력은 토큰을 솎기보다, 코드로 필요한 필드만 뽑아 요약본만 컨텍스트에 남기는 편이 안전합니다(프로그래매틱 tool 호출).
  • 대화 기록은 압축보다 compaction/요약이 자연스럽다. 오래된 turn은 토큰 솎아내기보다 요약으로 갈아끼우는 편이 구조를 덜 해칩니다.
기억하세요. 프롬프트 압축의 “좋은 재료”는 자연어 덩어리(RAG 문서, few-shot 본문, 긴 배경 설명)입니다. tool 호출·JSON·코드처럼 문법이 있는 부분은 압축의 대상이 아니라 보호의 대상입니다.

8. 흔한 실수 · 팁

  • 명령·질문·스키마를 압축 대상에 넣지 마세요. 답의 방향을 정하는 부분이라 손실에 극도로 취약합니다. instruction·question 인자로 분리하거나, 애초에 압축기에 넣지 않습니다.
  • 압축은 공짜가 아닙니다. 압축기(작은 LM/인코더)를 돌리는 데도 시간과 연산이 듭니다. 아끼는 토큰보다 압축 지연이 크면 손해입니다. 짧은 프롬프트에는 쓸 이유가 없고, 길고 반복적으로 재사용되는 컨텍스트일수록 이득이 큽니다.
  • 압축률은 실측으로 정하세요. 0.5에서 시작해 0.3, 0.2로 조여 가며 내 평가셋의 정답률이 꺾이는 지점을 찾습니다. “대충 세게”가 아니라 “정확도가 버티는 최대치”가 목표입니다.
  • 숫자·이름·날짜가 걸린 작업은 특히 조심. soft 압축(xRAG 등)은 이런 세부를 잘 흘립니다. 정밀 사실이 중요하면 hard 압축을 쓰고, force_tokens로 핵심 토큰을 보호하세요.
  • 압축과 캐싱을 섞을 땐 순서를 고정. 압축은 매번 결과가 조금씩 달라질 수 있어, 캐싱하려는 프리픽스가 압축 대상이면 캐시 적중률이 떨어질 수 있습니다. “변하지 않는 부분은 캐싱, 매번 새로 오는 문서만 압축”처럼 역할을 나누세요.
  • 먼저 “안 넣기”를 시도하세요. 가장 싼 압축은 애초에 관련 없는 청크를 검색 단계에서 걸러내는 것(리랭킹·필터)입니다. 압축은 “꼭 필요한데 그래도 긴” 컨텍스트에 얹는 다음 단계로 두는 게 맞습니다.

9. 마무리 (TL;DR)

  • 문제: RAG 청크·few-shot·대화 기록이 프롬프트를 부풀리고, 그 토큰 값을 매 호출마다 낸다. 입력 비용과 프리필 지연이 함께 커진다.
  • 프롬프트 압축: 뜻은 지키되 토큰만 줄이는 기법. 캐싱이 “재사용(무손실)”이라면 압축은 “줄이기(손실 있음)”. 서로 경쟁이 아니라 조합.
  • LLMLingua: 작은 LM으로 토큰 정보량(perplexity)을 재서 뻔한 토큰부터 삭제, 최대 20배 압축. LongLLMLingua는 RAG용으로 관련도 재배치, 토큰 25%로 성능 +21.4%까지 보고.
  • LLMLingua-2: 압축을 keep/drop 분류로 재정의, GPT-4 증류 데이터로 BERT급 인코더 학습. 원조보다 3~6배 빠르고 도메인 밖에서도 안정 → 프로덕션 기본값.
  • hard vs soft: hard(LLMLingua)는 읽히는 텍스트라 어디에나 붙고 확인이 쉽다. soft(Gist·xRAG)는 압축률이 높지만 불투명하고 모델 개조가 필요하며 세부 손실 위험.
  • 가장 중요한 함정: 명령·JSON·코드·tool 호출 같은 구조는 압축하면 문법이 깨진다. 에이전트 프롬프트에 토큰 압축을 그대로 쓰지 말 것. 압축은 자연어 덩어리에만.
  • 실무 순서: ① 검색 단계에서 관련 없는 것부터 안 넣기 → ② 그래도 긴 자연어 컨텍스트만 압축 → ③ 압축률은 평가셋으로 실측. 명령·질문·스키마는 항상 원본 그대로.
