MCP로 에이전트에 도구를 붙이는 건 이제 다들 합니다. 그런데 옆 팀이 만든 에이전트, 혹은 다른 회사가 API로 파는 에이전트와 협업하려면 어떻게 해야 할까요? 지금까지의 답은 대개 "그 에이전트를 도구처럼 감싸서 부른다"였습니다.

— A2A는 "에이전트를 도구로 위장시키지 말고, 에이전트답게 서로 대화하게 하자"는 방향의 프로토콜입니다.

지난 한 주 동안 AI 엔지니어링 쪽에서 "MCP냐 A2A냐"를 정리하는 글이 부쩍 많이 돌았습니다. 마침 MCP(Model Context Protocol)의 다음 스펙(2026-07-28)이 확정 단계에 들어가면서, "MCP는 도구, A2A는 에이전트"라는 2계층 그림이 엔터프라이즈 에이전트 배치의 사실상 기본형으로 굳어지고 있기 때문입니다. MCP는 여기서 여러 번 다뤘으니, 오늘은 그 옆자리를 맡는 A2A(Agent2Agent) 프로토콜을 처음부터 차근차근 풀어 보겠습니다.

먼저 문제부터 봅시다. 요즘 에이전트는 한 팀이 하나의 프레임워크로 다 만들지 않습니다. 검색 에이전트는 LangGraph로, 예약 에이전트는 CrewAI로, 사내 결재 에이전트는 또 다른 사내 툴킷으로 만들어지곤 하죠. 심지어 어떤 에이전트는 아예 다른 회사가 운영합니다. 이들을 하나의 흐름으로 협업시키려면 공통의 대화 규약이 필요합니다. HTTP가 없었다면 서로 다른 웹 서버·브라우저가 대화할 수 없었던 것과 똑같습니다.

A2A는 바로 그 공통 규약입니다. 서로 다른 프레임워크·벤더가 만든 에이전트가 서로를 발견하고, 안전하게 대화하고, 작업을 위임하게 해 주는 개방형 표준이죠. Google이 2025년 4월에 공개했고, 같은 해 6월 Linux Foundation에 기증해 특정 회사에 묶이지 않는 커뮤니티 표준이 됐습니다. 공개 저장소(a2aproject/A2A)는 GitHub 스타 2.5만 개를 넘겼고, AWS·Microsoft·Salesforce·SAP 등 150곳이 넘는 조직이 지지 명단에 이름을 올렸습니다.

1. 왜 필요한가 — "에이전트는 도구가 아니다"

"그냥 그 에이전트를 도구로 등록해서 부르면 되잖아?" 처음엔 다들 이렇게 생각합니다. 실제로 오래 통했던 방식이기도 합니다. 상대 에이전트를 하나의 함수처럼 감싸서, 내 에이전트의 도구 목록에 얹는 거죠. 문제는 이렇게 하면 에이전트의 진짜 능력이 대부분 잘려 나간다는 데 있습니다.

도구(tool)와 에이전트(agent)는 성격이 다릅니다. 도구는 대개 무상태(stateless)이고, 정해진 입력을 받아 정해진 결과를 내는 함수입니다. 계산기나 DB 조회처럼요. 반면 에이전트는 자율적이고, 여러 턴에 걸쳐 되묻고(clarify)·협상하고·오래 걸리는 일을 진행합니다. "여행을 예약해 줘"라는 요청에 예약 에이전트는 "출발일이 언제인가요?"라고 되물어야 하고, 좌석이 없으면 대안을 제시해야 하며, 결제까지 몇 분이 걸릴 수도 있습니다.

이런 상호작용을 단순한 함수 호출 한 방으로 우겨넣으면, 되묻기도 협상도 진행 상황 알림도 사라집니다. A2A 공식 문서가 "에이전트는 도구가 아니다"라고 못 박는 이유가 이것입니다. A2A는 에이전트를 도구로 위장시키는 대신, 에이전트 대 에이전트로, 여러 턴에 걸쳐, 자기 방식대로 대화하게 합니다.

2. 배경 — MCP는 수직, A2A는 수평

A2A를 이해하는 가장 빠른 길은 MCP와 나란히 놓는 것입니다. 둘은 자주 "경쟁 프로토콜"처럼 묶여 소개되지만, 사실은 서로 다른 층을 맡습니다. 실제로 Google은 처음부터 Anthropic과 상호 운용을 염두에 두고 A2A를 설계했다고 밝혔습니다.

  • MCP = 수직 축. 한 에이전트를 그 아래의 도구·데이터에 연결합니다. 계산기, DB 조회, 파일 읽기 같은 기능이죠. 도구는 보통 무상태이고 역할이 정해져 있습니다. "모델이 손발(도구)을 얻는" 연결입니다.
  • A2A = 수평 축. 한 에이전트를 그 옆의 다른 에이전트에 연결합니다. 위임·조율·협상처럼, 상대를 도구가 아니라 대등한 협업자로 대하는 연결입니다. "에이전트가 동료(다른 에이전트)를 얻는" 연결이죠.

그래서 실전 배치는 대개 이 둘을 겹쳐 씁니다. 사용자의 복잡한 요청을 받은 오케스트레이터 에이전트가, A2A로 여러 전문 에이전트에게 일을 나눠 주고(수평), 각 전문 에이전트는 다시 MCP로 자기 도구를 부려 실제 일을 처리합니다(수직). 이 "MCP + A2A" 2계층 구조가 요즘 엔터프라이즈 에이전트의 기본 배치로 자리 잡는 중입니다. 표지 그림이 정확히 이 모습입니다.

한 줄 비유: MCP는 한 사람이 쓰는 연장통이고, A2A는 여러 전문가가 함께 일하기 위한 공용어입니다. 목수 한 명에게 좋은 연장(MCP)을 쥐여 줘도, 목수·전기공·배관공이 한 현장에서 협업하려면 서로 통하는 말(A2A)이 따로 필요합니다.

3. A2A의 핵심 4개념: Agent Card · Task · Message · Artifact

A2A는 웹에서 이미 검증된 것들 위에 세워졌습니다. 통신은 HTTP(S) 위에서 일어나고, 메시지 형식은 JSON-RPC 2.0을 씁니다(원격 함수를 JSON으로 호출하는 표준). 새로 외운다기보다, 익숙한 조각을 재조립한다고 보면 됩니다. 등장인물과 핵심 개념부터 정리합시다.

등장인물은 셋입니다. User(사람 또는 자동화 서비스)가 목표를 던지면, A2A Client(요청하는 에이전트, Client Agent)가 사용자를 대신해 통신을 시작하고, A2A Server(원격 에이전트, Remote Agent)가 HTTP 엔드포인트로 요청을 받아 처리합니다. 여기서 중요한 원칙 하나 — 원격 에이전트는 클라이언트 입장에서 불투명(opaque)한 블랙박스입니다. 내부 로직·메모리·도구를 밖에 드러내지 않고, 오직 선언한 능력과 주고받는 메시지로만 협업합니다. 서로의 영업 비밀을 지키면서도 협업할 수 있게 하는 설계죠.

그 위에서 오가는 데이터는 네 가지 개념으로 정리됩니다.

개념무엇인가핵심 역할
Agent Card 에이전트의 신원·능력·엔드포인트·스킬·인증 요구사항을 담은 JSON 명함. 클라이언트가 이 에이전트가 뭘 하고, 어떻게 안전하게 부르는지를 파악하는 발견(discovery)의 출발점.
Task 고유 ID와 생명주기를 가진 상태 있는 작업 단위. 오래 걸리는 일을 추적하고, 여러 턴에 걸친 협업을 가능하게 함.
Message / Part 한 번의 대화 턴. role("user" 또는 "agent")과 여러 Part로 구성. Part는 텍스트·파일·구조화 데이터 중 하나를 담음. 지시·질문·답변·상태 같은, 꼭 산출물은 아닌 대화 내용을 전달.
Artifact 에이전트가 작업 중 만들어 낸 실제 산출물(문서·이미지·구조화 데이터). 고유 artifactId를 가짐. 작업의 최종 결과물을 구조적으로 전달. 스트리밍으로 조금씩 보낼 수도 있음.

하나 더 알아 둘 개념이 contextId입니다. 서버가 발급하는 식별자로, 여러 Task를 하나의 논리적 세션으로 묶습니다. "이 여행 계획"이라는 큰 맥락 아래 항공권 Task·호텔 Task·환율 Task가 함께 묶이는 식이죠. 클라이언트가 다음 메시지에 같은 contextId를 실으면 "아까 그 맥락을 이어 간다"는 뜻이 됩니다.

4. 동작 흐름 — 발견부터 Task 생명주기까지

이제 요청 하나가 처음부터 끝까지 어떻게 흐르는지 봅시다. 크게 발견 → 인증 → 메시지 전송 → Task 진행의 네 단계입니다.

① 발견(discovery). 클라이언트는 상대 에이전트의 도메인에서 표준 경로로 Agent Card를 가져옵니다. 경로는 https://{도메인}/.well-known/agent-card.json으로 정해져 있습니다(웹의 /.well-known/ 관례, RFC 8615). 즉 "이 에이전트 명함 좀 줘"를 평범한 HTTP GET 한 번으로 끝냅니다.

② 인증(authentication). Agent Card 안의 securitySchemes를 보고 필요한 인증 방식(예: OAuth 2.0 / OpenID Connect)을 확인한 뒤, 토큰을 받아 둡니다. 이때 자격 증명은 A2A 메시지 본문이 아니라 HTTP 헤더로 실어 보냅니다. 웹 API가 늘 하던 방식 그대로라, 기존 보안 인프라를 재사용하기 좋습니다.

③ 메시지 전송. 클라이언트는 SendMessage로 사용자의 요청을 담아 보냅니다. 서버는 두 가지로 답할 수 있습니다. 바로 끝나는 간단한 일이면 Message로 즉답하고, 시간이 걸리거나 추적이 필요한 일이면 Task를 새로 만들어 돌려줍니다.

④ Task 진행. Task로 넘어가면, 진행 상황을 받는 방법이 세 가지입니다. (1) 주기적으로 GetTask로 폴링(polling), (2) SSE(Server-Sent Events)로 실시간 스트리밍, (3) 아주 오래 걸리거나 연결이 끊긴 상황이면 서버가 푸시 알림(webhook)으로 알려 주기. 오래 걸리는 작업(LRO)과 비동기를 처음부터 염두에 둔 설계입니다.

이제 Task 생명주기를 조금 더 파 봅시다. Task는 8개의 상태를 오갑니다. 크게 진행 중, 중단(입력·인증 대기), 종료 세 부류로 묶어서 이해하면 쉽습니다.

왜 Task가 한 번 끝나면 못 되살아날까? 종료된 Task를 불변으로 두면, 입력→출력의 대응이 깔끔하게 남습니다. 추적(tracing)과 오케스트레이션이 쉬워지고, 산출물이 어느 작업에서 나왔는지도 또렷해지죠. 후속 작업은 "되살리기"가 아니라 같은 contextId 안의 새 Task로 모델링합니다.

5. 실전 — Agent Card와 SendMessage를 코드로

개념만 보면 뜬구름이니 실제 JSON을 봅시다. 먼저 원격 에이전트가 /.well-known/agent-card.json으로 내놓는 Agent Card입니다(핵심만 남긴 축약본).

{{< highlight json >}} { "name": "환율 에이전트", "description": "실시간 환율 조회와 통화 변환을 제공합니다.", "supportedInterfaces": [ { "url": "https://fx-agent.example.com/a2a/v1", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" } ], "capabilities": { // 이 에이전트가 지원하는 A2A 기능 "streaming": true, // SSE 스트리밍 가능 "pushNotifications": true // webhook 푸시 알림 가능 }, "securitySchemes": { // 어떻게 인증해야 하는지 "google": { "openIdConnectSecurityScheme": { "openIdConnectUrl": "https://accounts.google.com/.well-known/openid-configuration" } } }, "defaultInputModes": ["application/json", "text/plain"], "defaultOutputModes": ["application/json"], "skills": [ // 사람·기계가 읽는 능력 카탈로그 { "id": "convert", "name": "통화 변환", "description": "한 통화 금액을 다른 통화로 변환합니다.", "tags": ["fx", "currency", "money"], "examples": ["100 USD를 KRW로 바꿔 줘"] } ] } {{< /highlight >}}

클라이언트는 이 카드를 읽고 "streaming을 지원하는구나", "OIDC로 인증해야겠구나", "convert라는 스킬이 있구나"를 파악합니다. 스킬의 examples는 오케스트레이터가 "이 요청은 이 에이전트에게 보내면 되겠다"를 판단하는 힌트가 됩니다.

다음은 실제 요청입니다. JSON-RPC 2.0 형식으로 SendMessage를 부릅니다. 사용자의 한 턴을 message로 담고, 그 안의 parts에 실제 내용을 넣습니다.

{{< highlight json >}} // → 클라이언트가 보내는 요청 (HTTP 헤더에 인증 토큰이 함께 실림) { "jsonrpc": "2.0", "id": 1, "method": "SendMessage", "params": { "message": { "role": "user", "messageId": "m-001", "parts": [ { "text": "100 USD를 KRW로 바꿔 줘" } ] } } } {{< /highlight >}}

서버가 즉시 답할 수 있으면 Message를, 시간이 걸리면 Task를 돌려줍니다. 아래는 Task로 응답한 경우입니다. id(taskId)와 contextId, 그리고 현재 status.state가 담깁니다.

{{< highlight json >}} // ← 서버 응답: 상태 있는 Task로 시작 { "jsonrpc": "2.0", "id": 1, "result": { "id": "task-7f3a", // taskId "contextId": "ctx-91", // 이 대화 맥락 (후속 Task를 여기에 묶음) "status": { "state": "TASK_STATE_WORKING" } } } {{< /highlight >}}

이제 클라이언트 쪽을 의사코드로 그려 봅시다. 발견 → 전송 → (완료까지) 상태 확인의 흐름이 그대로 드러납니다. 라이브러리 API 이름은 SDK마다 조금씩 다르지만, 뼈대는 어디서나 같습니다.

{{< highlight python >}} import httpx BASE = "https://fx-agent.example.com" # ① 발견: well-known 경로에서 Agent Card 가져오기 card = httpx.get(f"{BASE}/.well-known/agent-card.json").json() endpoint = card["supportedInterfaces"][0]["url"] token = get_oidc_token(card["securitySchemes"]) # ② 인증(축약) def rpc(method, params): # JSON-RPC 2.0 호출. 인증 토큰은 '본문'이 아니라 '헤더'로 r = httpx.post(endpoint, headers={"Authorization": f"Bearer {token}"}, json={"jsonrpc": "2.0", "id": 1, "method": method, "params": params}) return r.json()["result"] # ③ 전송: 사용자 한 턴을 message로 task = rpc("SendMessage", {"message": { "role": "user", "messageId": "m-001", "parts": [{"text": "100 USD를 KRW로 바꿔 줘"}]}}) # ④ 진행: 종료 상태가 될 때까지 폴링 (스트리밍/푸시로 대체 가능) TERMINAL = {"TASK_STATE_COMPLETED", "TASK_STATE_FAILED", "TASK_STATE_CANCELED", "TASK_STATE_REJECTED"} while task["status"]["state"] not in TERMINAL: task = rpc("GetTask", {"id": task["id"]}) # taskId로 조회 # 필요하면 input-required 상태일 때 추가 입력을 보내면 됨 print(task.get("artifacts")) # 완료 시 산출물(Artifact) 확인 {{< /highlight >}}
전송(transport) 선택지: 위 예시는 가장 단순한 JSON-RPC 바인딩입니다. A2A는 같은 동작을 세 가지 바인딩으로 제공합니다 — JSON-RPC 2.0, gRPC, 그리고 HTTP+JSON/REST. REST로 하면 SendMessage가 POST /message:send, GetTask가 GET /tasks/{id}처럼 익숙한 엔드포인트로 매핑됩니다. 팀 상황에 맞는 걸 고르면 됩니다.

6. MCP와 A2A를 함께 쓰기 (2계층 스택)

이제 처음의 표지 그림으로 돌아가 전체를 조립해 봅시다. "국제 여행을 계획해 줘"라는 요청이 들어오면 흐름은 이렇습니다.

  1. 오케스트레이터 에이전트가 요청을 쪼갭니다: 항공권·호텔·환율.
  2. 각 하위 작업을 A2A(수평)로 해당 전문 에이전트에게 위임합니다. 항공권 에이전트에 SendMessage, 호텔 에이전트에 SendMessage 하는 식이죠. 오래 걸리면 각각 Task로 추적합니다.
  3. 각 전문 에이전트는 내부에서 MCP(수직)로 자기 도구를 부립니다. 항공권 에이전트는 항공 예약 API를, 호텔 에이전트는 재고·결제 도구를 MCP로 호출하죠. 이 내부 사정은 오케스트레이터에게 보이지 않습니다(opaque).
  4. 결과가 Artifact로 돌아오면, 오케스트레이터가 하나의 여행 계획으로 합쳐 사용자에게 답합니다.

핵심은 역할 분담입니다. A2A는 "누구에게 무엇을 위임하고, 진행 상태를 어떻게 추적할지"(에이전트 간 조율)를 맡고, MCP는 "각 에이전트가 실제 도구를 어떻게 부릴지"(도구 접근)를 맡습니다. 그래서 둘 중 하나를 고르는 문제가 아니라, 층을 나눠 함께 쓰는 문제입니다.

언제 무엇을? 상대가 정해진 함수 하나로 충분한가요? 그럼 MCP 도구가 맞습니다. 굳이 A2A로 감쌀 필요 없습니다. 반대로 상대가 스스로 판단하고 되묻고 오래 일하는 자율 주체인가요? 그럼 A2A로 에이전트답게 부르세요. "단순 기능은 MCP, 자율 협업은 A2A"가 실전 기준선입니다.

7. 흔한 실수 · 팁

  • Agent Card를 무조건 신뢰하기. 카드는 그냥 URL에서 받아 온 JSON입니다. 스푸핑되거나 악의적 엔드포인트를 가리킬 수 있으니, 출처를 검증하세요. 스펙에는 카드에 signatures(JWS 서명)를 붙일 수 있고, 민감 정보는 인증된 확장 카드(GetExtendedAgentCard)로 따로 받도록 되어 있습니다. 발견 엔드포인트에도 접근 제어를 거는 게 좋습니다.
  • 남의 에이전트를 도구로 감싸기. 1장의 함정을 실전에서 또 반복하기 쉽습니다. 자율적으로 되묻고 협상해야 하는 상대를 함수 한 방으로 축소하면, 다회차 상호작용이 통째로 막힙니다. 상대가 에이전트라면 A2A로 노출하세요.
  • 오래 걸리는 작업을 동기 호출로만 처리. 몇 분 걸리는 Task를 SendMessage 하나로 붙잡고 응답을 기다리면 타임아웃에 걸립니다. Task로 받고 스트리밍(SSE)이나 푸시 알림으로 진행 상황을 받으세요. A2A가 비동기를 기본으로 두는 이유가 이것입니다.
  • contextId를 안 넘겨서 맥락이 끊김. 후속 요청에 이전 contextId를 실어야 "아까 그 여행 계획"으로 이어집니다. 안 넘기면 서버 입장에선 매번 처음 보는 요청이 됩니다.
  • opaque 원칙을 어기고 내부 상태 공유를 기대. 상대 에이전트의 메모리·프롬프트·도구는 밖에서 안 보이는 게 정상입니다. "그쪽 내부 변수를 직접 읽어서…" 같은 설계는 A2A와 맞지 않습니다. 협업은 선언된 능력과 주고받는 메시지로만 하세요.
  • 인증 정보를 A2A 메시지 본문에 담기. 자격 증명은 프로토콜 메시지가 아니라 HTTP 헤더로 보냅니다. 표준 웹 인증(OAuth/OIDC)과 결이 맞고, 로깅·전파에서 토큰이 새는 사고도 줄어듭니다.
  • MCP로 될 일을 A2A로 과설계. 계산기 하나 붙이려고 그걸 A2A 에이전트로 감싸는 건 과합니다. 단순·무상태 기능은 MCP 도구가 더 가볍고 명확합니다.

8. 마무리 (TL;DR)

  • 무엇: A2A(Agent2Agent)는 서로 다른 프레임워크·벤더가 만든 에이전트가 서로를 발견하고, 안전하게 대화하고, 작업을 위임하게 해 주는 개방형 표준이다. Google이 2025년 4월 공개, 6월 Linux Foundation에 기증.
  • 왜: 남의 에이전트를 "도구로 감싸면" 되묻기·협상·장기 작업 같은 에이전트 고유 능력이 잘려 나간다. A2A는 에이전트를 에이전트답게 부른다.
  • MCP와의 관계: 경쟁이 아니라 층이 다르다. MCP = 수직(에이전트↔도구/데이터), A2A = 수평(에이전트↔에이전트). "MCP + A2A" 2계층이 표준 배치로 굳는 중.
  • 핵심 개념: Agent Card(/.well-known/agent-card.json의 명함), Task(상태 있는 작업, 8상태 생명주기), Message/Part(대화 턴), Artifact(산출물), contextId(맥락 묶기).
  • 어떻게: HTTP(S) 위 JSON-RPC 2.0(또는 gRPC·REST). 발견 → 인증(헤더 토큰) → SendMessage → Task를 폴링·SSE·푸시로 추적. 원격 에이전트는 opaque 블랙박스.
  • 기준선: 단순·무상태 기능은 MCP, 자율적으로 협업하는 상대는 A2A. 그리고 Agent Card는 항상 검증하고, 오래 걸리는 일은 비동기로.
