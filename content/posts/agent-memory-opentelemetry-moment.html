1. 도입 — 기억은 쌓이는데, 이사를 못 간다

이번 주 Hacker News는 사실상 '에이전트 메모리 주간'이었습니다. 11월 6일 Anthropic의 The components of agent memory가 프런트페이지에 올랐고, latent 메모리 논문 Memorilla가 뒤를 이었고, "여러 클라이언트와 프로젝트에 걸친 에이전트 컨텍스트를 어떻게 관리하느냐"는 Ask HN 스레드까지 섰습니다. 메모리를 어떻게 쌓을지는 어제 글에서 자세히 다뤘습니다.

그런데 11월 7일, 이 흐름에 조금 다른 각도의 글이 하나 끼어들었습니다. 오픈소스 메모리 도구 LoreKit을 만드는 Mads Thines의 Agent memory needs its OpenTelemetry moment입니다. 질문은 간단합니다. 그렇게 공들여 쌓은 기억, 도구를 바꾸면 가져갈 수 있습니까?

지금 답은 '아니오'입니다. Claude Code가 몇 달간 프로젝트에서 배운 교훈은 MEMORY.md와 /memories 폴더에 있고, Copilot이 저장소에서 추출한 사실은 GitHub 서버에 있고, Cursor 규칙은 .mdc 파일에 있고, Mem0에 쌓인 사실은 또 다른 스키마로 있습니다. 전부 '기억'인데 서로 한 줄도 못 읽습니다. 글의 한 문장이 문제를 정확히 요약합니다 — "The problem isn't a missing tool. It's a missing agreement." 부족한 건 도구가 아니라 합의라는 겁니다.

이 글은 Hacker News에서 100개가 넘는 댓글이 달리며 꽤 날카로운 논쟁을 만들었습니다. "메모리 도구 만드는 사람이 표준 만들자는 건 당연한 포지션 아니냐"부터 "트레이스는 append-only지만 기억은 고쳐진다, 비유가 깨진다"까지. 오늘은 이 논쟁을 재료로, 표준이라는 것이 엔지니어링에서 어떻게 만들어지고 어디서 부러지는지를 에이전트 메모리라는 구체적인 사례로 뜯어봅니다. 표준이 없는 오늘 당장 기억을 '이사 가능한 모양'으로 쌓는 요령도 챙깁니다.

2. 배경 — 2019년, observability가 똑같은 문제를 풀었다

제목의 'OpenTelemetry 순간'부터 풀고 가겠습니다. junior 입장에서는 OpenTelemetry(OTel)를 "트레이싱 라이브러리" 정도로 알고 있기 쉬운데, 이 글에서 중요한 건 라이브러리가 아니라 합의의 역사입니다.

2019년 이전의 observability 세계는 지금의 에이전트 메모리와 똑같이 생겼습니다. 모니터링 벤더마다 자기 수집 에이전트와 자기 데이터 포맷이 있었습니다. Datadog 계측을 깔면 데이터가 Datadog 모양으로 쌓이고, 다른 벤더로 가려면 계측을 전부 다시 깔아야 했습니다. 이걸 고치려고 OpenTracing과 OpenCensus라는 두 오픈소스 프로젝트가 나왔는데 — 얄궂게도 표준을 만들려는 프로젝트 둘이 서로 경쟁하는 상황이 됐습니다.

2019년에 두 프로젝트가 OpenTelemetry로 합병하면서 상황이 끝났습니다. 벤더들이 합의한 건 크게 네 층입니다.

  • 데이터 모델 — 트레이스·스팬·메트릭이 어떤 필드를 갖는가
  • 시맨틱 컨벤션(semantic conventions) — 속성 이름의 공용 사전. HTTP 상태 코드는 누가 기록하든 http.response.status_code
  • 프로토콜(OTLP) — 데이터를 주고받는 와이어 포맷
  • 구현(SDK) — 언어별 레퍼런스 구현

핵심은 벤더들이 경쟁을 멈춘 게 아니라는 점입니다. 데이터의 '모양'만 합의하고, 그 데이터로 뭘 해 주는지(대시보드, 알림, 분석)로는 계속 경쟁합니다. 수집은 공용, 활용은 경쟁 — 이 분리가 OTel이 성공한 이유고, 메모리에도 같은 분리가 가능하다는 게 글의 뼈대입니다. 트레이스·스팬 개념 자체가 낯설다면 에이전트 관측성 글을 먼저 읽고 오면 좋습니다.

3. 지금의 메모리 지형 — 도구마다 '기억의 단위'가 다르다

"포맷이 다 다르다"는 말은 쉽게 하지만, 실제로 얼마나 다를까요? 글이 고마운 지점은 주요 도구들의 메모리를 기억의 단위 · 주소(어디에 속하는가) · 잊는 방식 세 축으로 나란히 비교한 것입니다. 추려 보면 이렇습니다.

지시 파일AGENTS.md, CLAUDE.md, Cursor .mdcMarkdown 파일 통째, 경로로 주소 지정안 잊음 — 사람이 고칠 때까지

표를 세로로 읽어 보면 문제의 깊이가 보입니다. 어떤 도구에서 기억은 '파일'이고, 어떤 도구에서는 '글자 수 제한이 있는 블록'이고, 어떤 도구에서는 '그래프의 엣지'입니다. 단위부터 합의가 안 돼 있으니 변환기(converter)를 짜는 수준으로는 해결이 안 됩니다. 파일 하나를 그래프 엣지 몇 개로 쪼갤지는 변환 규칙이 아니라 해석의 문제이기 때문입니다.

흥미로운 건 글이 각 도구를 깎아내리지 않고 "훔쳐 올 것"을 하나씩 집어낸다는 점입니다. Copilot에서는 사실마다 코드 인용을 붙여 검증 가능하게 만든 것과 '기본적으로 잊는' 정책을, LangGraph에서는 put(namespace, key, value)라는 최소 인터페이스를, Graphiti에서는 "사실이 참이었던 기간"과 "그걸 기록한 시점"을 분리한 두 개의 시간 축을, AGENTS.md에서는 뻔한 경로에 있는 평범한 파일이라는 접근성을. 표준이란 결국 이런 장점들의 교집합을 고르는 작업입니다.

4. 공유 스펙의 모양 — 다섯 가지 질문과 레코드 하나

그럼 합의한다면 무엇을 합의해야 할까요? 글은 공유 스펙이 답해야 할 질문을 다섯 개로 압축합니다.

  1. 이 기억은 어디서 참인가? — 전역? 프로젝트? 특정 저장소? 특정 브랜치?
  2. 이 기억의 정체성은 무엇인가? — 같은 내용을 두 번 쓰면 갱신인가, 중복인가?
  3. 무슨 내용인가? — 본문의 포맷과 종류(교훈, 사실, 결정, 선호…)
  4. 언제부터 참이 아닌가? — 만료, 무효화, 잊는 규칙
  5. 어느 버전이 현재인가? — 고쳐진 기억과 옛 기억의 구분

그리고 "필드 이름은 예시일 뿐"이라는 단서와 함께 레코드 하나를 스케치합니다. 모양은 익숙합니다 — YAML frontmatter가 봉투, Markdown 본문이 기억입니다.

{{< highlight yaml >}} # 예시 레코드 — frontmatter는 '봉투', 본문이 '기억' id: 8f0c2a6e-4b1d-4c7a-9e2f-3a5b6c7d8e9f address: { level: repo, value: github.com/acme/checkout } # 어디서 참인가 key: tests-need-local-postgres # 정체성 (같은 키 = 같은 기억) kind: lesson # 무슨 종류인가 version: 3 # 같은 주장에 대한 3번째 교정본 supersedes: 41b9e0c2-7d3a-4f15-8c6e-0a9b8c7d6e5f # 이 레코드가 대체한 옛 레코드 written_by: { type: agent, name: claude-code } # 사람? 에이전트? 추출 서비스? content_type: text/markdown lifecycle: { expires_at: null, extended_by: write } # 언제까지 참인가 {{< /highlight >}}

다섯 질문 중에 저자가 "진짜 갈림길"로 꼽는 건 의외로 written_by입니다. 기억을 쓴 주체가 사람인가, 모델인가, 대화에서 사실을 뽑아내는 추출 서비스인가에 따라 그 기억을 얼마나 신뢰할지가 달라지는데, 지금 도구 대부분은 이 구분을 기록하지 않습니다. 사람이 직접 적은 "테스트는 로컬 Postgres가 필요하다"와, 모델이 대화에서 추측해 적은 같은 문장은 신뢰 등급이 달라야 한다는 겁니다.

레코드 위로는 OTel의 네 층이 거의 그대로 대응됩니다.

세부 선택 두 가지가 재미있습니다. 첫째, 프로토콜을 새로 만들지 않고 MCP 위의 오퍼레이션 집합(write·read·list·search·archive)으로 정의하자고 합니다. 전송은 이미 있는 표준을 타고, 레코드의 모양만 새로 합의하자는 거죠. 둘째, 레퍼런스 구현 대신 적합성 테스트를 두자고 합니다. "이 구현은 모르는 속성을 버리지 않는다", "superseded된 레코드는 superseded로 읽힌다" 같은 행동을 테스트로 못 박으면, 구현은 몇 개가 나와도 상관없습니다.

왜 '모르는 속성 보존'이 테스트 항목일까? 표준의 수명을 결정하는 조항이기 때문입니다. 미래의 도구가 ci.flaky_rate 같은 새 속성을 붙였을 때, 옛 구현이 그걸 이해 못 하더라도 버리지 않고 그대로 통과시켜야 생태계가 호환성을 유지한 채 진화합니다. HTML이 모르는 태그를 만나도 죽지 않는 것, HTTP 헤더가 모르는 필드를 무시하고 전달하는 것과 같은 원리입니다.

5. 이미 나온 제안들 — export는 풀었고, live addressing은 못 풀었다

"그런 표준, 누가 벌써 만들고 있지 않나?" 맞습니다. 글이 검토하는 기존 제안이 셋 있습니다.

  • Portable Memory (MacPaw Research, 2026-07 프리프린트) — 자기완결적인 .mem 번들. 바이트 단위로 재현 가능한 직렬화, 삭제를 증명하는 tombstone, 선택적 Ed25519 서명까지 담은 가장 공들인 제안입니다. 저자들 스스로 아직 널리 채택되진 않았다고 말합니다.
  • Open Memory Protocol (2026-04 드래프트) — 대화와 거기서 파생된 기억을 manifest가 든 ZIP으로 묶어 플랫폼 사이에 옮기는 포맷입니다.
  • COGX (Cognee) — Mem0, Letta, Zep에서 가져오기(import)를 지원하는 교환 포맷입니다.

셋 다 의미 있는 시도지만, 글의 진단은 이렇습니다 — 전부 export, 즉 '한 사람의 기억을 벤더 A에서 벤더 B로 이사시키는 문제'를 풉니다. 그런데 2026년의 실제 워크로드는 이사가 아니라 동거에 가깝습니다. 같은 저장소 위에서 CI 작업, 에디터 에이전트, 리뷰 봇이 동시에 같은 기억을 읽고 써야 합니다. 글은 이걸 live addressing이라고 부릅니다 — "이 기억은 github.com/acme/checkout의 main 브랜치에서 참"이라고 주소를 매겨, 여러 에이전트가 실시간으로 같은 주소를 바라보게 하는 것.

이 구분은 junior가 표준 논쟁을 읽을 때 쓸 수 있는 좋은 렌즈입니다. 어떤 표준 제안을 보면 "이건 데이터를 옮기는 표준인가, 데이터를 공유하는 표준인가"부터 물어보세요. 파일 포맷(이사)과 프로토콜+주소 체계(동거)는 난이도가 다른 문제입니다. 동거에는 동시성, 권한, 신선도, 그리고 다음 절에서 볼 '버전' 문제가 전부 따라옵니다.

6. 반론 다섯 개 — 그리고 스펙이 이틀 만에 고쳐진 이야기

글이 좋은 또 하나의 이유는 반론을 피하지 않고 다섯 개를 정면으로 받는다는 겁니다. 짧게 정리하면:

  • "메모리 도구 만드는 사람이 표준 타령하는 건 자기 장사 아닌가." — LoreKit은 비교 표의 한 행일 뿐 템플릿이 아니고, 다른 표준이 서면 따라가겠다는 답. (건강한 의심은 유지합시다 — 표준 제안자의 포지션은 항상 할인해서 읽어야 합니다.)
  • "MCP가 이미 표준인데?" — MCP가 표준화하는 건 호출이지 호출로 오가는 레코드가 아닙니다. 프로토콜만 있고 데이터 모델이 없으면, 모두가 같은 전화선으로 서로 다른 언어를 말하는 상황이 됩니다.
  • "공유 메모리는 prompt injection 통로다." — 인정. 그래서 레코드에 작성 주체를 기록하고, 서명을 허용하고, 의존하는 코드를 가리키게 하자는 것. 다만 어떤 포맷도 포이즈닝을 불가능하게 만들지는 못한다고 선을 긋습니다. 이 주제는 메모리 포이즈닝 방어 글에서 자세히 다뤘습니다.
  • "표준 하나 더 만들면 n+1개가 될 뿐." — 그 유명한 xkcd 927. 답은 "OTel은 표준을 추가해서가 아니라 기존 프로젝트들이 합병해서 성공했다"입니다.
  • "트레이스는 append-only지만, 기억은 고쳐진다." — 가장 아픈 반론이고, 저자도 여기가 OTel 비유의 가장 약한 고리라고 인정합니다.

이 마지막 반론의 전개가 이번 주 에피소드에서 제일 배울 게 많은 대목입니다. 트레이스는 한 번 기록하면 끝이지만, 기억은 수명 내내 교정됩니다. 1월에 적은 runbook이 3월에 고쳐졌다면, 버전 규칙이 없는 포맷에서는 두 사본이 똑같이 '참'처럼 보입니다. 독자들이 이 구멍을 찔렀고, 저자는 이틀 뒤인 11월 9일 스펙 스케치를 공개적으로 고쳤습니다. 다섯 번째 질문("어느 버전이 현재인가")과 두 필드가 그렇게 추가된 겁니다.

  • version — 같은 주장에 대한 교정이면 번호를 올린다 (v2, v3, …)
  • supersedes — 다른 주장이 옛 주장을 대체하면, 새 레코드(v1)를 만들고 옛 레코드를 가리킨다

그리고 적합성 테스트에 "superseded된 레코드는 superseded로 읽힌다"가 추가됐습니다. "고치면 버전, 뒤집으면 새 레코드 + supersedes" — 데이터베이스의 UPDATE와 '새 행 + 포인터'의 구분과 같은 사고방식입니다. 반론이 스펙을 수정시키고 그 과정이 전부 공개 저장소에 남는 것, 이게 표준이 만들어지는 실제 모습입니다.

7. 실전 — 표준이 없는 오늘, 기억을 '이사 가능한 모양'으로 쌓기

표준은 아직 없습니다. 그럼 오늘 뭘 할 수 있을까요? 결론부터 말하면 — 어느 도구에 기억을 맡기든, 도구가 사라져도 남는 사본 하나는 '뻔한 경로의 평범한 파일'로 유지하라입니다. AGENTS.md 계열이 기능은 제일 빈약한데도 사실상 표준처럼 번진 이유가 정확히 이것입니다. 어떤 도구든 파일은 읽을 수 있으니까요.

여기에 이 글의 다섯 질문을 미니 컨벤션으로 얹으면, 나중에 어떤 표준이 이기든 기계적으로 변환할 수 있는 상태가 됩니다. 예를 들어 프로젝트에 .memory/ 폴더를 하나 두고, 레코드 하나를 파일 하나로 이렇게 적는 겁니다.

{{< highlight markdown >}} --- key: tests-need-local-postgres kind: lesson address: repo # 이 저장소 안에서만 참 version: 2 written_by: agent:claude-code # 사람이 쓴 게 아님 → 신뢰 등급 구분 verified_at: 2026-11-10 # 마지막으로 사실 확인한 날 --- 통합 테스트는 로컬 Postgres 16이 떠 있어야 통과한다. 테스트 셋업이 자동으로 띄워 주지 않는다. `make db-up` 먼저 실행할 것. {{< /highlight >}}

읽는 쪽은 20줄짜리 스크립트면 충분합니다. 핵심은 같은 key가 여러 개면 최고 버전만 살리는 것 — 6절의 version 규칙을 코드 네 줄로 구현한 셈입니다.

{{< highlight python >}} from pathlib import Path import yaml def load_memory(root: str = ".memory"): records = {} for f in Path(root).glob("*.md"): front, _, body = f.read_text().removeprefix("---").partition("---") meta = yaml.safe_load(front) meta["body"] = body.strip() k = meta["key"] # 같은 key가 여러 파일이면 version이 높은 쪽이 '현재' if k not in records or meta["version"] > records[k]["version"]: records[k] = meta return records # 에이전트 컨텍스트에 주입할 때는 신뢰 등급을 함께 노출 for r in load_memory().values(): trust = "사람 작성" if r["written_by"].startswith("person") else "에이전트 작성(검증 필요)" print(f"[{r['kind']}/{trust}] {r['body']}") {{< /highlight >}}

이 구조의 장점은 셋입니다. 첫째, Claude Code든 Cursor든 파일을 읽을 수 있는 도구라면 전부 소비 가능합니다 — 각 도구의 지시 파일에서 ".memory/를 읽고 따르라" 한 줄이면 연결됩니다. 둘째, git에 들어가니 기억의 변경 이력이 코드 리뷰를 탑니다 — 에이전트가 이상한 '교훈'을 적으면 diff에서 보입니다. 셋째, 나중에 Portable Memory든 다른 표준이든 승자가 정해지면, frontmatter에 다섯 질문의 답이 이미 있으니 변환 스크립트가 하루 일감입니다.

주의 — 공유 기억은 공유 공격면입니다. 여러 에이전트가 읽는 저장소에 한 에이전트가 쓴 기억이 들어가는 순간, 그 파일은 prompt injection의 전달 통로가 될 수 있습니다. written_by를 남기는 건 장식이 아니라 방어선입니다 — 에이전트가 쓴 레코드는 자동 주입하지 말고 검증 후 승격하거나, dreaming 같은 오프라인 패스에서 원본 기록과 대조한 뒤에만 신뢰 등급을 올리세요.

8. 흔한 실수 · 팁

  • 벤더 전용 메모리에만 기억을 쌓기. 호스팅형 메모리는 편하지만, 그 기억은 계정과 함께 삽니다. 중요한 교훈은 저장소 안의 파일로도 남기세요. 기억의 '원장'은 내가 소유한 곳에 두고, 도구들은 그걸 읽게 하는 구도가 안전합니다.
  • 변환기로 해결하려 하기. 도구 A → B 변환 스크립트는 단위가 같을 때만 성립합니다. 파일 ↔ 그래프 엣지 ↔ 글자 제한 블록 사이의 변환은 정보를 깎아 먹습니다. 공용 사본을 두는 쪽이 n²개의 변환기보다 쌉니다.
  • 교정 이력 없이 덮어쓰기. 기억 파일을 그냥 덮어쓰면 "예전엔 왜 그렇게 알고 있었지?"를 추적할 수 없습니다. 최소한 version 필드 하나, 뒤집는 내용이면 새 레코드 + supersedes. git이 이력을 받쳐 주는 것도 .memory/를 저장소에 두는 이유입니다.
  • 작성 주체를 안 남기기. 사람이 적은 규칙과 모델이 추측한 규칙이 같은 폴더에 같은 모양으로 섞이면, 포이즈닝 분석도 신뢰 등급 구분도 불가능해집니다. written_by는 필수 필드로 취급하세요.
  • 만료를 설계하지 않기. "안 쓰면 28일 뒤 삭제"라는 Copilot의 선택은 과격해 보이지만, 지난 분기의 낡은 교훈이 영원히 주입되는 것보다는 낫습니다. 최소한 verified_at을 적고, 오래된 레코드는 주기적으로 재검증하거나 강등하세요.
  • 표준 뉴스에 바로 올라타기. 드래프트 단계의 표준(.mem, Open Memory Protocol 등)을 프로덕션 포맷으로 채택하는 건 이릅니다. 지금 단계에서 가져갈 것은 포맷 자체가 아니라 다섯 질문이라는 체크리스트입니다.

9. 마무리 (TL;DR)

  • 이번 주 에이전트 메모리 담론의 두 번째 축 — 11월 7일 LoreKit의 Mads Thines가 쓴 Agent memory needs its OpenTelemetry moment. 도구마다 기억의 단위·주소·잊는 방식이 전부 달라 서로 못 읽는 지금 상황은 2019년 이전의 observability와 같고, 필요한 건 도구가 아니라 합의라는 주장입니다.
  • OTel이 합의한 네 층(데이터 모델 · 시맨틱 컨벤션 · 프로토콜 · 구현)이 메모리에도 거의 그대로 대응됩니다 — 레코드 · 컨벤션 레지스트리 · MCP 위의 read/write 계약 · 레퍼런스 구현 대신 적합성 테스트. 저장·랭킹·UI는 일부러 스펙 밖(경쟁 영역)에 둡니다.
  • 공유 스펙이 답할 다섯 질문: 어디서 참인가 · 정체성은 · 내용은 · 언제까지 참인가 · 어느 버전이 현재인가. 진짜 갈림길은 written_by — 사람/에이전트/추출 서비스의 구분이 신뢰 등급을 가릅니다.
  • 기존 제안(MacPaw Portable Memory의 .mem, Open Memory Protocol, Cognee COGX)은 export(이사)는 풀지만, CI·에디터·리뷰 봇이 같은 기억을 동시에 읽고 쓰는 live addressing(동거)은 아직 아무도 못 풀었습니다.
  • "트레이스는 append-only지만 기억은 고쳐진다"는 반론에 스펙은 이틀 만에 공개적으로 고쳐졌습니다 — 같은 주장의 교정은 version 증가, 다른 주장의 대체는 새 레코드 + supersedes.
  • 표준이 없는 오늘의 실전: 기억의 원장을 뻔한 경로의 평범한 파일(.memory/*.md + frontmatter)로 소유하고, 다섯 질문을 미니 컨벤션으로 얹고, 에이전트가 쓴 레코드는 검증 후에만 승격. 어떤 표준이 이기든 변환은 하루 일감이 됩니다.
