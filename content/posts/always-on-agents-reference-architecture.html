1. 도입 — 설계도가 나왔다

11월 13일, Anthropic이 "Building always-on agents"라는 가이드를 공개했습니다(William Hu, 읽는 데 14분짜리 장문입니다). 반응은 빨랐습니다. 다음 날부터 "Always On, Mostly Asleep" 같은 실무자 후기, FourWeekMBA·SmartScope의 정리 글이 줄줄이 나왔고, Anthropic이 내부에서 준비 중이라고 보도된 상시 가동 에이전트 제품(코드명 Conway) 소식과 맞물려 "Anthropic이 Claude를 always-on 에이전트로 바꾸고 있다"는 분석까지 이어졌습니다. 지난주 goal engineering 글에서 본 Harrison Chase의 문제의식 — "에이전트가 상시 가동으로 넘어가면 새 설계 문제가 생긴다" — 에 대해, 이번에는 모델 회사가 직접 아키텍처 답안지를 낸 셈입니다.

이 블로그는 10월 초에 상시 가동/앰비언트 에이전트 글로 이 전환 자체를 다뤘습니다. 그때의 질문이 "왜 다들 always-on으로 가는가, 트리거에는 어떤 종류가 있는가"였다면, 오늘의 질문은 한 단계 아래로 내려갑니다. "그래서 뭘로 짓는가?" Anthropic 가이드의 답은 다섯 부품입니다. 이벤트 인박스(event inbox), 타이머(timers), 메모리(memory), 권한(permissions), 아웃박스(outbox). 그리고 이 글의 관전 포인트를 미리 말하면 — 이 다섯 개를 뜯어 보면 전부 어디서 본 것들입니다. 작업 큐, cron 스케줄러, 트랜잭셔널 아웃박스. LLM만 새것이고, 주변은 수십 년 검증된 분산 시스템 패턴입니다. 주니어 입장에서는 오히려 좋은 소식입니다. 배워야 할 게 "신비한 에이전트 마법"이 아니라, 원래 백엔드 공부하면 나오는 그 패턴들이라는 뜻이니까요.

2. 배경 — 런, 세션, 사이클: 잠이 기본값인 에이전트

용어부터 잡고 갑시다. 가이드는 세 단어를 구분해서 씁니다.

  • 런(run) — 한 번의 작업 구간. 이벤트를 받고, 일을 끝내고, 결과를 저장하면 런 하나가 끝납니다.
  • 세션(session) — 메시지와 도구 호출이 쌓이는 대화 기록(transcript). 런은 세션 안에서 일합니다. 하나의 세션이 여러 런에 걸쳐 이어질 수 있습니다.
  • 사이클(cycle) — 잠 → 깨어남 → 런 → 다시 잠. 상시 가동 에이전트의 일생은 이 사이클의 무한 반복입니다.

여기서 많은 사람이 처음 갖는 오해가 깨집니다. "항상 켜져 있는(always-on) 에이전트"라고 하면 24시간 돌아가는 프로세스에서 LLM이 쉼 없이 토큰을 뿜는 그림을 떠올리기 쉽지만, 실제로는 정반대입니다. 잘 설계된 상시 가동 에이전트는 대부분의 시간을 잠들어 있고, 잠든 동안 토큰을 한 개도 쓰지 않습니다. "항상 켜져 있다"는 건 모델이 아니라 깨우는 장치가 켜져 있다는 뜻입니다. 비유하자면 당직 의사입니다. 병원에 상주하지만, 호출벨이 울릴 때만 일어나서 일하고, 끝나면 다시 눈을 붙입니다. 월급(토큰 비용)은 깨어 있는 시간만큼만 나갑니다.

왜 하필 지금 이 가이드가 나왔을까요. 가이드 자신이 두 가지 이유를 듭니다. 첫째, 최신 모델은 "사용자 의도가 뭔지, 언제 사람에게 확인해야 하는지"에 대한 판단이 좋아져서 감독 없이 돌릴 만해졌습니다. 둘째, 비용이 내려갔습니다. 가이드가 인용하는 수치로, 한 장기(long-horizon) 코딩 벤치마크에서 Opus 5.5는 Opus 5 대비 해결한 과제당 비용이 78% 낮았고, 일반적인 워크로드에서도 40% 낮았습니다. 과제당 비용이 1/5이 되면, "하루 종일 대기시키다가 필요할 때만 깨우는" 운영 방식이 갑자기 수지에 맞기 시작합니다.

족보 한 줄 — 이 아이디어 자체는 Anthropic의 발명이 아닙니다. LangChain의 Harrison Chase가 2025년 1월 "Introducing ambient agents"에서 "이벤트 스트림을 듣고 움직이는 에이전트 + 사람이 확인하는 Agent Inbox"를 제안했고, 올해 들어 OpenAI·Meta의 제품 발표가 이어졌습니다(10월 글 참고). 이번 가이드의 가치는 아이디어가 아니라 부품 단위의 설계 결정과 그 이유를 처음으로 공식 문서화했다는 데 있습니다.

3. 이벤트 인박스 — 왜 webhook이 에이전트를 직접 부르면 안 되나

첫 부품이자 가장 중요한 부품입니다. 순진한 구현을 먼저 봅시다. GitHub webhook이 오면 HTTP 핸들러에서 바로 에이전트를 실행하는 겁니다. 작동은 합니다 — 이벤트가 하나씩 올 때까지만. 문제는 두 가지 형태로 터집니다. 이벤트 두 개가 동시에 도착하면 런 두 개가 경쟁하면서 같은 일을 두 번 하거나 서로의 결과를 덮어쓰고, 처리 중에 프로세스가 죽으면 그 이벤트는 증발합니다. webhook 제공자는 "응답 200 받았으니 전달 완료"라고 기록했는데 실제로는 아무 일도 안 일어난 거죠.

그래서 가이드는 이벤트 소스와 에이전트 사이에 인박스를 끼워 넣으라고 합니다. 구성은 세 조각입니다.

  • 이벤트 목록 — 보통 데이터베이스 테이블. 각 이벤트의 상태(대기/처리 중/완료)를 추적하고, 소스가 준 식별자로 중복 이벤트를 걸러냅니다(같은 webhook이 재전송돼도 한 번만 처리 — 멱등성).
  • 핸들러 — 이벤트를 받아 목록에 적는 HTTP 엔드포인트. 하는 일은 그게 전부여야 합니다. webhook 제공자는 응답이 느리면 실패로 간주하고 재시도하므로, 가벼운 검증만 하고 즉시 ACK합니다. 프롬프트 인젝션 검사 같은 깊은 검증은 런 안에서 합니다.
  • 워커 — 목록에서 대기 이벤트를 꺼내 런을 시작하는 백그라운드 서비스.

백엔드를 해 본 분이라면 눈치챘을 겁니다. 이건 그냥 작업 큐(work queue)입니다. 그런데 큐 위에 에이전트 특유의 규칙 몇 개가 얹힙니다. 전부 가이드의 권고 사항인데, 하나같이 "왜?"가 재미있습니다.

  • 사용자당 인박스 1개로 시작하라. 더 쪼개는 건 병렬성이 정말 필요해질 때. 섣불리 쪼개면 "내가 아까 뭐라고 했는지"가 인박스 사이에 흩어집니다.
  • 인박스당 활성 워커는 1개만. 워커가 둘이면 같은 사용자에 대해 런 두 개가 동시에 돌며 메모리를 서로 덮어씁니다. 일반 작업 큐는 워커를 늘려 처리량을 올리지만, 에이전트는 한 사용자의 문맥이 일관되게 이어지는 것이 처리량보다 중요합니다.
  • 인박스가 유일한 진실의 원천(source of truth)이다. 워커가 죽어도 이벤트는 테이블에 남아 있으니, 새 워커가 깨어나면서 대기 이벤트를 다시 집어 들면 됩니다. 재시도가 공짜로 따라옵니다.
  • 몰려온 이벤트는 배칭하라. 사용자가 메시지를 연달아 세 개 보냈다면, 런 세 번에 답장 세 개가 아니라 한 런에 묶어서 한 번만 답하는 쪽이 자연스럽습니다.
  • 런 도중에 새 이벤트가 오면 선택지는 셋입니다: 다음 런으로 미루기, 지금 런에 끼워 넣기, 런을 중단하고 새로 시작하기. 뭐가 정답인지는 제품마다 다르지만, 셋 중 하나를 의식적으로 골라야 한다는 게 포인트입니다.

이어서 "이벤트가 기존 작업의 연속인가"에 따라 세션 연결이 갈립니다. 사용자의 답장처럼 이전 일의 연속이면 기존 세션을 이어서(resume) 쓰고, 새 일이면 새 세션을 엽니다. 세션을 어떻게 이어 쓰는지의 API 레벨 이야기는 message threads 글에서 다뤘습니다.

4. 타이머 — 스스로 깨어나는 법

webhook은 바깥세상이 깨워 주는 장치입니다. 그런데 상시 가동 에이전트의 매력 절반은 스스로 깨어나는 것에서 나옵니다. "3일 뒤에 답장 왔는지 확인해야지", "매일 아침 9시에 브리핑을 보내야지" 같은 것들요. 가이드는 타이머를 두 종류로 나눕니다.

팔로업(follow-up)스케줄(schedule)
무엇에이전트가 스스로 건 1회성 마감 — "수요일에 리마인드"정해진 주기의 반복 작업 — "평일 아침 뉴스레터"
누가 만드나주로 에이전트 자신 (런 도중 도구 호출로)주로 사람 (설정으로)
발화 후완료 처리하고 끝다음 회차로 due_at 갱신 — 반복 규칙을 추적해야 함

구현에서 중요한 결정이 두 개 있습니다. 첫째, 타이머는 인박스와 다른 테이블에 둡니다. 인박스는 "지금 처리할 일"만 담는 곳이고, "미래의 약속"이 섞이면 워커가 매번 아직 안 된 일을 걸러내야 합니다. 둘째, 다소 김 빠지는 사실이지만 — 타이머는 스스로 런을 시작하지 못합니다. 시계가 알아서 에이전트를 깨우는 마법은 없습니다. 별도의 스케줄러가 일정 간격으로 돌면서 ① 기한이 지난 타이머를 찾고, ② 팔로업은 완료 처리·스케줄은 다음 회차로 갱신하고, ③ 인박스에 이벤트를 넣어 워커를 깨웁니다. 그러니까 타이머도 결국 인박스로 합류합니다 — 깨우는 경로를 하나로 통일하는 거죠. 유닉스의 cron 데몬이 crontab을 폴링해서 프로세스를 띄우는 것과 같은 구조입니다. 직접 만들기 싫으면 durable execution 엔진에 맡길 수도 있는데, 그 계열 이야기는 durable execution 글에서 다뤘습니다.

5. 메모리와 컨텍스트 오버헤드 — 매 런이 내는 입장료

런과 런 사이에 에이전트는 죽습니다(프로세스 관점에서). 그런데도 "어제 하던 그 일"을 이어서 하려면, 워커보다 오래 사는 저장소에 기억을 적어 둬야 합니다. 에이전트 메모리의 일반론은 Anthropic 메모리 글 해부에서 자세히 다뤘으니, 여기서는 이번 가이드가 always-on 맥락에서 추가한 것만 짚습니다. 가이드는 메모리를 네 종류로 나누고, 디렉터리 하나로 예시를 줍니다.

{{< highlight text >}} memory/ ├── instructions.md # 매 런 로드 — 사용자가 직접 준 지시 ├── index.md # 매 런 로드 — notes/·progress/의 목차만 ├── reported.md # 매 런 로드 — 이미 보고한 내용 (같은 소식 두 번 알리지 않기) ├── notes/ # 필요할 때만 — 사용자에 대해 배운 것 (역할·선호·교정) └── progress/ # 필요할 때만 — 진행 중 작업별 상태 (한 작업 = 한 파일) {{< /highlight >}}

두 가지 설계 원칙이 눈에 띕니다. 첫째, 다시 찾아볼 수 있는 건 저장하지 말 것. 이슈 트래커에 있는 내용을 메모리에 복사하면 그 순간부터 두 사본이 어긋나기 시작합니다. 포인터(링크·ID)만 저장하고 필요하면 다시 조회합니다. 둘째, index + 상세 파일 패턴. 런을 시작할 때 모든 노트를 다 읽는 게 아니라 목차(index.md)만 로드하고, 필요한 파일만 그때 가서 읽습니다. 왜 이렇게까지 아끼냐면 —

매 런에는 입장료가 있기 때문입니다. 시스템 프롬프트 + 도구 정의 + 매 런 로드되는 메모리. 이 오버헤드는 일을 시작하기도 전에, 모든 런마다 지불됩니다. 채팅 에이전트라면 하루 몇 번이지만, 상시 가동 에이전트는 하루에 수십~수백 번 깨어날 수 있습니다. 오버헤드가 2만 토큰이라면 하루 100런에 200만 토큰이 "입장료"로만 나갑니다. 그래서 가이드의 처방은 둘입니다. 오버헤드를 날씬하게 유지할 것, 그리고 변하지 않는 앞부분은 프롬프트 캐싱으로 할인받을 것. 세션이 길어지면 컴팩션(compaction)하거나 새 세션을 열게 되는데, 둘 다 디테일을 잃으므로 중요한 건 런 도중에 미리 메모리로 빼 두라는 당부도 붙습니다.

6. 권한과 아웃박스 — 아무도 안 볼 때의 안전장치, 그리고 침묵이라는 출력

가이드가 "위험이 가장 많이 모이는 곳"이라고 직접 못 박는 부품이 권한입니다. 당연합니다. 런은 사용자의 접근 권한을 들고, 아무도 지켜보지 않는 시간에 돌아갑니다. 채팅창이라면 이상한 행동을 사람이 바로 끊지만, 새벽 3시의 런은 끊어 줄 사람이 없습니다. 가이드의 안전장치는 세 겹입니다.

  • 크레덴셜은 에이전트 환경 밖에. 에이전트는 크레덴셜 없는 요청을 보내고, 환경 바깥의 프록시가 크레덴셜을 붙여 전달합니다. 모델이 토큰 문자열 자체를 아예 못 보게 만드는 구조로, 시크릿 위생 글에서 본 "유출은 막는 게 아니라 볼 수 없게 한다" 원칙과 같은 계열입니다.
  • 도구 호출마다 진행/차단/승인 대기 3분기. Claude Code의 auto mode처럼 분류기가 위험한 액션을 걸러내되, 가이드 스스로 "가장 중요한 결정에는 여전히 사람의 리뷰가 필요하다"고 한계를 긋습니다.
  • 지연된 도구 호출(deferred tool call). 이게 제일 흥미로운 메커니즘입니다. 승인이 필요한 도구 호출을 만나면 런을 도구 호출 중간 상태로 저장하고 끝냅니다. 승인 요청은 사용자에게 카드 형태로 전달되고(MCP Apps 같은 걸로 만든 인터랙티브 UI), 사용자의 응답이 인박스 이벤트로 돌아와 저장된 세션을 이어서 재개합니다. 포인트는 기다리는 동안 워커가 블록되지 않는다는 것 — 그 사이 다른 이벤트를 얼마든지 처리합니다.

마지막 부품, 아웃박스입니다. 상시 가동 에이전트는 과정을 스트리밍하지 않고 결과만 통보합니다. 그래서 런의 끝은 셋 중 하나입니다. ① 아웃박스에 메시지를 넣는다, ② 아무것도 보내지 않는다, ③ 지연된 도구 호출로 승인/입력을 요청한다. ②가 정식 선택지라는 게 중요합니다 — 채팅 에이전트는 매 턴 무조건 응답하지만, 상시 가동 에이전트에게 침묵은 버그가 아니라 가장 흔한 정상 출력입니다. "확인했고, 알릴 만한 게 없음"이요.

구현은 단순하게 시작해도 됩니다. 대부분의 에이전트는 메시지를 바로 보내는 send 도구 하나면 충분합니다. 메시지 발송 속도를 조절하거나 실패를 복구해야 할 때 정식 아웃박스 — 보낼 메시지 테이블 + 그걸 읽어 전달하는 디스패처 — 로 승격합니다. 이 역시 분산 시스템의 고전인 transactional outbox 패턴 그대로입니다. 그리고 보내는 양에 대한 가이드의 조언이 이번 문서에서 가장 인용 많이 된 문장입니다. 너무 자주 보내면 소음이고(사람이 알림을 끄는 순간 에이전트는 사망입니다), 너무 안 보내면 필요한 걸 놓칩니다. 이 균형은 감이 아니라 평가(evals)로 튜닝하되 — "조용하게 시작해서, 사용자의 주의(attention)를 서서히 벌어라(start quiet and earn more of the user's attention over time)."

7. 실전 — SQLite 하나로 만드는 최소 뼈대

다섯 부품이 머리에 들어왔는지 확인하는 가장 좋은 방법은 작게 만들어 보는 겁니다. 외부 큐도, durable execution 엔진도 없이 SQLite 파일 하나로 인박스·타이머·단일 워커 구조를 세워 보겠습니다. 프로덕션 코드가 아니라 구조를 손으로 만져 보기 위한 뼈대입니다.

{{< highlight python >}} # always_on.py — 인박스 + 타이머 + 워커 최소 뼈대 import sqlite3, time, json db = sqlite3.connect("agent.db") db.executescript(""" CREATE TABLE IF NOT EXISTS inbox( id INTEGER PRIMARY KEY, source_id TEXT UNIQUE, -- 같은 webhook 재전송은 한 번만(멱등성) type TEXT, payload TEXT, status TEXT DEFAULT 'pending' -- pending → done ); CREATE TABLE IF NOT EXISTS timers( id INTEGER PRIMARY KEY, due_at REAL, -- 발화 시각 (unix time) kind TEXT, -- 'followup' | 'schedule' period REAL, -- schedule일 때 반복 간격(초) payload TEXT ); """) def enqueue(source_id: str, type_: str, payload: dict): """핸들러가 하는 일의 전부: 적고, 즉시 ACK. 깊은 검증(인젝션 검사 등)은 런 안에서 합니다.""" db.execute("INSERT OR IGNORE INTO inbox(source_id, type, payload) VALUES(?,?,?)", (source_id, type_, json.dumps(payload))) db.commit() def scheduler_tick(): """타이머는 스스로 런을 못 깨웁니다 — 폴링해서 인박스로 옮겨야 합니다.""" now = time.time() due = db.execute("SELECT id, kind, period, payload FROM timers WHERE due_at <= ?", (now,)).fetchall() for tid, kind, period, payload in due: enqueue(f"timer:{tid}:{int(now)}", "timer", json.loads(payload)) if kind == "followup": db.execute("DELETE FROM timers WHERE id = ?", (tid,)) # 1회성: 끝 else: db.execute("UPDATE timers SET due_at = due_at + ? WHERE id = ?", (period, tid)) # 반복: 다음 회차로 db.commit() {{< /highlight >}}

워커 루프가 나머지 절반입니다. "인박스당 워커 1개" 규칙 덕분에 락도 분산 조율도 없이 단일 루프면 됩니다.

{{< highlight python >}} def worker_loop(): while True: scheduler_tick() batch = db.execute( "SELECT id, type, payload FROM inbox WHERE status='pending' ORDER BY id" ).fetchall() if batch: # 몰려온 이벤트는 한 런으로 배칭 — 답장도 한 번만 result = run_agent(events=batch) # 세션 열기/재개 → 모델 루프 → 메모리 갱신 db.executemany("UPDATE inbox SET status='done' WHERE id=?", [(e[0],) for e in batch]) db.commit() if result.message: # 런의 끝 ①: 보고할 게 있다 send_to_user(result.message) # 런의 끝 ②: result.message가 None이면 침묵 — 그것도 정상 출력 time.sleep(5) # 다음 깸까지 잠 — 토큰 소비 0 {{< /highlight >}}

run_agent() 안쪽은 평소의 에이전트 루프(모델 호출 → 도구 실행 반복)라서 생략했습니다. 이 뼈대에서 확인할 것은 세 가지입니다. 워커가 죽어도 pending 행이 남아 재시작 시 그대로 이어진다는 것(인박스 = 진실의 원천), 타이머 이벤트와 webhook 이벤트가 같은 길로 합류한다는 것, 그리고 result.message가 None인 평범한 날이 대부분이라는 것. 여기까지 손에 익으면 SQLite를 Postgres로, time.sleep 폴링을 큐의 블로킹 pop으로, 승인 분기를 지연된 도구 호출로 바꿔 가며 실물로 키워 가면 됩니다.

8. 흔한 실수 · 팁

  • webhook 핸들러에서 에이전트를 바로 실행 — 동시 이벤트에 런이 경쟁하고, 크래시에 이벤트가 증발합니다. 핸들러는 적고 ACK만, 실행은 워커가.
  • 핸들러에서 오래 걸리는 검증 — webhook 제공자가 타임아웃으로 실패 처리하고 재전송 폭탄을 보냅니다. 깊은 검사는 런 안으로.
  • 처리량 올리겠다고 한 인박스에 워커 여러 개 — 같은 사용자의 메모리를 서로 덮어씁니다. 병렬성이 필요하면 워커가 아니라 인박스를 쪼개세요.
  • 다른 시스템에 있는 데이터를 메모리로 복사 — 그 순간부터 썩기 시작하는 사본이 생깁니다. 포인터만 저장.
  • 입장료 무시 — 시스템 프롬프트·도구 정의·상시 로드 메모리는 모든 런마다 과금됩니다. 하루 100번 깨는 에이전트라면 오버헤드 1만 토큰 차이가 월 수천만 토큰 차이입니다.
  • 컴팩션을 믿고 세션에만 기록 — 컴팩션도 새 세션도 디테일을 잃습니다. 중요한 건 런 도중 메모리로 먼저 빼 두세요.
  • 승인 대기로 워커 블록 — 사람이 자리를 비운 6시간 동안 에이전트 전체가 멈춥니다. 지연된 도구 호출로 세션을 저장하고 워커를 풀어 주세요.
  • 시작부터 수다스러운 에이전트 — 사용자가 알림을 끄면 그걸로 끝입니다. 조용하게 시작해서 신뢰를 벌고, 메시지 볼륨은 evals로 튜닝하세요. 보고할 게 없으면 침묵이 정답입니다.

9. 마무리 (TL;DR)

  • 11월 13일 Anthropic이 "Building always-on agents"를 공개했습니다. webhook·스케줄·백그라운드 작업으로 스스로 깨어나는 에이전트의 공식 레퍼런스 아키텍처로, 실무자 후기와 정리 글이 이어지며 이번 주의 화두가 됐습니다.
  • 상시 가동의 역설: 잘 설계된 always-on 에이전트는 대부분 잠들어 있고, 잠든 동안 토큰을 쓰지 않습니다. 켜져 있는 건 모델이 아니라 깨우는 장치입니다.
  • 다섯 부품 — 인박스(durable 이벤트 테이블 + 빠른 핸들러 + 워커, 사용자당 1개·워커 1개·배칭), 타이머(팔로업/스케줄, 스케줄러가 폴링해 인박스로 합류), 메모리(포인터 원칙, index+상세 파일), 권한(크레덴셜 프록시, 지연된 도구 호출), 아웃박스(send 도구로 시작, 필요 시 테이블+디스패처로 승격).
  • 뜯어 보면 작업 큐 + cron + transactional outbox입니다. LLM만 새것이고 주변은 검증된 분산 시스템 패턴 — 백엔드 기본기가 그대로 에이전트 기본기가 됩니다.
  • 비용 감각: 매 런은 시스템 프롬프트·도구 정의·상시 메모리라는 입장료를 냅니다. 오버헤드를 날씬하게, 프롬프트 캐싱으로 할인을. 가이드 인용 수치로 Opus 5.5는 장기 과제 벤치마크에서 Opus 5 대비 과제당 비용 78% 절감 — 이 하락이 always-on을 수지맞게 만든 배경입니다.
  • 출력 철학: 침묵은 버그가 아니라 가장 흔한 정상 출력입니다. 조용하게 시작해서 사용자의 주의를 서서히 벌 것 — 메시지 볼륨은 감이 아니라 evals로.
