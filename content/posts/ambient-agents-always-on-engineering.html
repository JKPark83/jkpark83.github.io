1. 도입 — 업계가 일제히 '항상 켜진 에이전트'로

9월 29일 DevDay에서 OpenAI가 dots를 발표했습니다. 홍보 문구를 한 줄로 줄이면 이렇습니다. "채팅창을 닫아도 계속 일하는 에이전트." dot마다 자체 클라우드 컴퓨터와 브라우저를 받고, 4,000개 넘는 앱에 연결되고, 대화와 대화 사이에도 프로젝트를 지켜보다가 완성된 작업을 들고 돌아옵니다. Hacker News 스레드는 464점에 댓글 353개(9/30 집계)가 달리며 한 주 내내 화제였습니다.

dots 하나만이 아닙니다. 9월 한 달 동안 벌어진 일을 늘어놓으면 방향이 보입니다. 9월 8일 Meta가 이메일·캘린더·결제까지 연결해 여러 단계 목표를 알아서 처리하는 에이전트 Muse를 출시했고, 9월 10일 OpenAI는 durable session 위에서 장시간 도는 에이전트를 만드는 Agents API를 퍼블릭 베타로 열었습니다. 그리고 9월 29일 dots까지. 업계가 일제히 "사용자가 보고 있지 않은 시간"으로 에이전트를 밀어 넣고 있습니다.

이 글은 dots 사용 후기가 아닙니다. 제품 발표는 계기일 뿐이고, 진짜 질문은 이겁니다. 상시 가동 에이전트는 채팅 에이전트와 구조가 어떻게 다르고, 직접 만들려면 어떤 부품이 필요한가? 결론부터 말하면 부품은 세 가지입니다. 트리거, 상태를 잇는 런 라이프사이클, 그리고 사람을 부르는 타이밍 설계. 하나씩 뜯어봅니다.

참고로 이 개념 자체는 새것이 아닙니다. LangChain의 Harrison Chase가 2025년 1월 "ambient agents"라는 이름으로 정리했고, 오픈소스 이메일 비서로 시연까지 했습니다. 2026년 9월의 변화는 이 패턴이 프론티어 랩의 플래그십 제품이 됐다는 점입니다. 개념이 궁금하면 원문(Introducing ambient agents)을 함께 보세요.

2. 배경 — 채팅 에이전트와 뭐가 다른가

지금까지 만들던 에이전트는 대부분 채팅형입니다. 사람이 메시지를 보내야 시작하고, 사람이 화면을 보고 있는 동안 돌고, 답을 내놓으면 끝납니다. 상호작용의 시작점이 항상 사람입니다. 이 구조의 한계는 명확합니다. 사람이 시키지 않으면 아무 일도 안 하고, 사람 한 명이 동시에 볼 수 있는 채팅창 수만큼만 확장됩니다.

앰비언트 에이전트(ambient agent)는 시작점을 뒤집습니다. 사람 대신 이벤트가 에이전트를 깨웁니다. 새 이메일, CI 실패, 새벽 3시의 cron, 경쟁사 가격 변동 — 세상의 변화가 트리거이고, 사람은 중요한 순간에만 호출됩니다. 비유하면 채팅 에이전트는 "말을 걸어야 대답하는 비서"이고, 앰비언트 에이전트는 "우편함을 계속 지켜보다가 등기가 오면 전화해 주는 비서"입니다.

여기서 junior가 가장 많이 하는 오해가 하나 있습니다. "상시 가동이면 프로세스가 24시간 떠 있어야 하나?" 아닙니다. dots도, LangChain의 이메일 비서도, 실체는 트리거가 올 때마다 짧게 깨어나는 실행(run)의 연속입니다. LLM 호출은 어차피 stateless라서, "항상 켜져 있다"는 느낌은 실행과 실행 사이를 잇는 영속 상태(persistent state)가 만들어 냅니다. 그래서 엔지니어링 문제도 "데몬을 어떻게 띄우나"가 아니라 "깨어날 때마다 무엇을 이어받고, 무엇을 남기고 잠드나"가 됩니다.

3. 부품 ① 트리거 — 누가 에이전트를 깨우는가

트리거는 세 종류로 정리됩니다. 어떤 조합을 쓰느냐가 반응 속도와 비용을 동시에 결정합니다.

트리거동작 방식지연비용 특성예시
스케줄(schedule) cron처럼 정해진 시각에 실행 주기만큼 늦음 예측 가능, 빈 실행 낭비 있음 매일 아침 브리핑, 주간 리포트
이벤트(event) 웹훅·메시지 큐로 변화가 직접 쏨 수 초 변화 있을 때만 실행 — 가장 효율적 CI 실패 웹훅, 새 이메일, PR 코멘트
임계값 폴링(polling) 주기적으로 값을 읽어 조건 검사 주기만큼 늦음 웹훅이 없는 대상에 차선책 재고·가격·에러율 감시

원칙은 간단합니다. 웹훅이 있으면 웹훅, 없으면 폴링, 정기 요약은 스케줄. 그리고 폴링을 쓰더라도 LLM을 폴링 루프 안에 넣으면 안 됩니다. "값을 읽어 조건을 검사"하는 부분은 LLM 없이 일반 코드로 처리하고, 조건이 참일 때만 에이전트를 깨워야 합니다. dots 발표 당일 HN에서 가장 많이 나온 걱정이 "always-on이면 컴퓨트가 얼마나 낭비될까"였는데, 트리거 계층을 제대로 나누면 상시 가동 에이전트는 사실 거의 항상 잠들어 있습니다. 프레임워크 차원에서는 LangGraph가 cron 잡과 영속 상태를 내장해 이 패턴을 지원하고, OpenAI Agents API는 durable session으로 실행 사이의 상태 유지를 대신 해 줍니다(Agents API 해부 편 참고).

4. 부품 ② 런 라이프사이클 — 상태·멱등성·델타

트리거가 에이전트를 깨운 다음부터가 본론입니다. 한 번의 실행은 다섯 단계를 거칩니다.

세 가지 개념만 잡으면 됩니다.

멱등성(idempotency). 같은 트리거로 두 번 깨어나도 결과가 한 번 실행한 것과 같아야 한다는 성질입니다. cron은 중복 발화할 수 있고, 웹훅은 재전송되고, 실행 도중 죽어서 재시작될 수도 있습니다. 그래서 실행 첫 단계에서 "이 작업, 이미 했나?"를 확인하는 멱등성 키(날짜, 이벤트 ID 등)를 영속 상태에서 조회합니다. 실제로 이 블로그의 글도 매일 아침 에이전트가 발행하는데, 히스토리 파일에 오늘 날짜가 이미 있으면 아무것도 하지 않고 종료합니다. 그 한 줄이 없으면 스케줄러가 꼬인 날 같은 글이 두 번 올라갑니다.

워터마크(watermark)와 델타 감지. 매 실행이 세상 전체를 다시 읽으면 느리고 비쌉니다. "지난 실행이 어디까지 봤는지"를 표시한 지점이 워터마크이고, 이번 실행은 그 이후의 변화(델타)만 처리합니다. 이메일 비서라면 마지막으로 처리한 메시지 ID, 릴리스 감시라면 마지막으로 본 버전 태그가 워터마크입니다. 델타가 비어 있으면 LLM을 부르지도 않고 종료합니다 — 앞서 말한 "거의 항상 잠들어 있는" 구조가 여기서 나옵니다.

실행 간 상태 vs 실행 중 상태. 워터마크·누적 학습·감사 로그처럼 실행 사이를 잇는 상태는 파일이든 DB든 외부에 있어야 합니다. 반면 실행 도중의 대화 컨텍스트는 그 실행과 함께 버려지는 소모품입니다. 이 둘을 섞으면(컨텍스트를 통째로 저장해 다음 실행에 재주입) 컨텍스트가 무한히 자라며 썩습니다. 긴 작업 하나가 중간에 죽는 문제까지 다루려면 durable execution 편을, 잠든 시간을 역으로 활용하는 발상은 sleep-time compute 편을 이어서 보면 좋습니다.

5. 부품 ③ 사람을 부르는 타이밍 — notify·question·review

상시 가동 에이전트의 성패는 역설적으로 "사람을 언제 부르느냐"에서 갈립니다. 너무 자주 부르면 채팅 에이전트보다 나을 게 없고(그냥 알림 공장), 너무 안 부르면 새벽에 에이전트가 저지른 사고를 아침에 발견하게 됩니다.

LangChain은 앰비언트 에이전트의 사람 개입(human-in-the-loop) 패턴을 세 가지로 정리했습니다. 실무에서 그대로 쓸 수 있는 어휘입니다.

  • notify(알림) — "이런 일이 있었어요"라고 알려만 주고 행동은 하지 않습니다. 에이전트에게 권한이 없는 중요 이벤트에 씁니다. 예: 받은편지함에 서명 요청 문서가 도착했을 때.
  • question(질문) — 정보가 부족해 막혔을 때 추측하지 않고 사람에게 묻습니다. 예: "회신에 참석 여부를 적어야 하는데, 금요일 미팅 가시나요?"
  • review(검토/승인) — "이렇게 하려는데 승인해 주세요." 실행 능력은 있지만 위험하거나 대외적인 행동 앞에 세우는 게이트입니다. 예: 고객에게 나가는 이메일 발송 직전.

어느 패턴을 쓸지는 행동의 가역성과 파급 범위로 정하는 게 정석입니다. 내부에서 되돌릴 수 있는 일은 자율 실행하고 로그만 남기고, 외부로 나가거나 되돌리기 어려운 일은 review를 거칩니다. dots도 같은 구조를 제품화했습니다. 보도에 따르면 별도의 자동 검토(auto-review) 시스템이 파급이 큰 행동을 사용자 지시·Custom Rules·안전 요건과 대조해 자율 진행할지 승인을 받을지 결정하고, 비밀번호 변경 같은 민감한 작업은 아예 사람 전용으로 남겨 둡니다. 재미있는 건 하드웨어까지 내려간 흐름인데, 같은 주에 Nvidia가 "모든 AI 에이전트 옆에 감시용 워치독 칩을 두겠다"는 구상을 공개했을 정도입니다.

review 게이트를 만들면 곧바로 다음 문제가 옵니다. 승인 요청이 쌓이면 사람이 안 읽고 전부 승인 버튼을 누르기 시작합니다(승인 피로). 게이트의 임계값 설계는 승인 피로와 권한 설계 편에서 자세히 다뤘습니다.

6. 실전 — 릴리스 감시 앰비언트 에이전트 만들기

부품 세 개를 전부 조립해 봅니다. 시나리오: 우리 서비스가 의존하는 오픈소스 라이브러리의 새 릴리스를 감시하다가, 새 버전이 나오면 변경 사항을 읽고 우리 코드에 영향이 있는지 분석해 Slack으로 알려 주는 에이전트입니다. 트리거는 GitHub Actions의 스케줄을 씁니다.

{{< highlight yaml >}} # .github/workflows/release-watcher.yml name: release-watcher on: schedule: - cron: "0 */6 * * *" # 6시간마다 깨어남 (트리거 = 스케줄) workflow_dispatch: {} # 수동 실행도 가능하게 jobs: watch: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: python watcher.py env: ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }} SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }} {{< /highlight >}}

본체는 그림 2의 라이프사이클을 그대로 코드로 옮긴 형태입니다. 멱등성 검사와 델타 감지가 LLM 호출보다 앞에 있다는 점이 전부라고 해도 과언이 아닙니다.

{{< highlight python >}} # watcher.py — 런 라이프사이클 5단계를 그대로 코드로 import json, os, pathlib, urllib.request WATCHED = ["encode/httpx", "pydantic/pydantic"] STATE = pathlib.Path("state.json") # 실행 사이를 잇는 영속 상태 def load_state(): return json.loads(STATE.read_text()) if STATE.exists() else {} def latest_release(repo): url = f"https://api.github.com/repos/{repo}/releases/latest" with urllib.request.urlopen(url) as r: return json.loads(r.read()) def run(): state = load_state() # ① 상태 로드 for repo in WATCHED: rel = latest_release(repo) tag = rel["tag_name"] if state.get(repo) == tag: # ②+멱등성: 워터마크와 같으면 continue # LLM 없이 조용히 넘어감 impact = analyze(repo, rel) # ③ 새 릴리스만 LLM 분석 if impact["affected"]: notify_slack(repo, tag, impact) # ④ HITL: notify 패턴 state[repo] = tag # ⑤ 워터마크 전진 STATE.write_text(json.dumps(state)) # 다음 실행을 위해 저장 {{< /highlight >}}

분석 단계는 릴리스 노트와 우리 쪽 의존성 사용 방식을 함께 주고, 구조화된 판정을 받습니다. 여기서도 비용 습관 하나를 챙깁니다. 판정(싸고 자주)과 심층 분석(비싸고 가끔)을 나누고, 판정은 작은 모델로 돌리는 겁니다.

{{< highlight python >}} import anthropic def analyze(repo, rel): client = anthropic.Anthropic() # 1차 판정은 작은 모델 — 대부분의 릴리스는 "영향 없음"으로 끝남 resp = client.messages.create( model="claude-haiku-4-5-20251001", max_tokens=1024, messages=[{"role": "user", "content": f"""다음은 {repo}의 새 릴리스 노트입니다. 우리 프로젝트는 이 라이브러리를 requirements.txt로 고정해 씁니다. {rel["body"][:8000]} breaking change, deprecation, 보안 패치가 있는지 판정하고 JSON으로만 답하세요: {{"affected": bool, "severity": "low|med|high", "summary": "<한국어 두 문장 요약>"}}"""}], ) return json.loads(resp.content[0].text) {{< /highlight >}}

이 작은 에이전트에 이미 세 부품이 다 들어 있습니다. 트리거(6시간 cron), 영속 상태와 워터마크(state.json), HITL(notify). 여기서 확장하는 길도 자연스럽습니다. severity가 high면 업그레이드 PR 초안까지 만들되 머지는 review 게이트로 사람에게 넘기고(자율 실행 → review로 승격), 분석 결과를 누적해 "이 라이브러리는 마이너 버전에서도 자주 깨진다" 같은 판단 근거를 상태에 쌓으면 dots가 말하는 "피드백으로 학습하는" 구조의 축소판이 됩니다.

7. 흔한 실수 · 팁

  • 멱등성 없이 시작한다. 처음엔 티가 안 나다가 스케줄러 중복 발화, 웹훅 재전송, 재시작이 겹치는 날 사고가 납니다. 알림 두 번은 애교지만, "PR 두 개 생성"이나 "환불 두 번"은 사고입니다. 실행 첫 줄에 멱등성 키 검사부터 넣으세요.
  • 폴링 루프 안에 LLM을 넣는다. HN의 "컴퓨트 낭비" 걱정이 현실이 되는 지점입니다. 변화 감지는 일반 코드로, LLM은 델타가 있을 때만. 매 실행 앞부분이 같은 프롬프트라면 prompt caching도 겹쳐 쓰세요(캐시 인지 에이전트 편).
  • notify를 남발한다. "변화 없음, 이상 없음"까지 알리는 에이전트는 일주일 안에 음소거당하고, 음소거된 에이전트는 없는 에이전트입니다. 조용한 실행은 로그에만 남기고, 알림은 사람이 행동할 일이 있을 때만 보내는 게 원칙입니다.
  • 자격 증명을 통째로 넘긴다. dots 스레드에서 가장 뜨거웠던 우려가 이것입니다 — 상시 가동 에이전트는 사람이 안 보는 시간에도 자격 증명을 쥐고 있습니다. 읽기 전용 토큰부터 시작해 필요한 권한만 추가하고(최소 권한), 쓰기 권한이 필요한 행동은 review 게이트 뒤에 두세요.
  • 감사 로그를 안 남긴다. 채팅 에이전트는 사람이 실시간으로 지켜보는 게 곧 감사였지만, 앰비언트 에이전트는 아무도 안 볼 때 일합니다. "언제 깨어나 무엇을 읽고 무엇을 했는지"를 실행마다 남기지 않으면, 이상 동작을 발견해도 재구성할 방법이 없습니다.
  • 실행 중 컨텍스트를 영속 상태에 욱여넣는다. 대화 이력 전체를 저장해 다음 실행에 재주입하면 컨텍스트가 매 실행 커지며 품질이 떨어집니다. 남길 것은 워터마크·판정 결과·교훈 같은 증류된 상태뿐, 원본 컨텍스트는 실행과 함께 버리세요.
  • 팁: 처음 2주는 전부 notify 모드로 돌리세요. 자율 실행 예정인 행동도 "이렇게 했을 겁니다"만 보내게 해 두면, 에이전트의 판단 분포를 공짜로 관찰할 수 있습니다. 오탐률을 보고 나서 자율 실행으로 승격해도 늦지 않습니다.

8. 마무리 (TL;DR)

  • 9월 한 달 — Meta Muse(9/8), OpenAI Agents API 베타(9/10), OpenAI dots(9/29, HN 464점·353댓글) — 업계가 일제히 상시 가동 에이전트로 이동했습니다. 개념 자체는 LangChain이 2025년 1월 "ambient agents"로 정리한 것이고, 이제 프론티어 랩의 플래그십 제품이 됐습니다.
  • 상시 가동의 실체는 24시간 도는 데몬이 아니라 트리거가 올 때마다 깨어나 영속 상태를 이어받는 실행의 연속입니다. 부품은 셋: 트리거, 런 라이프사이클, 사람 개입 설계.
  • 트리거는 웹훅 > 폴링, 정기 요약은 스케줄. 변화 감지는 일반 코드가 맡고 LLM은 델타가 있을 때만 — 잘 만든 앰비언트 에이전트는 거의 항상 잠들어 있습니다.
  • 런 라이프사이클의 문지기는 멱등성 키(중복 실행 방지)와 워터마크(델타만 처리)입니다. 실행 사이에는 증류된 상태만 남기고, 실행 중 컨텍스트는 버립니다.
  • 사람 개입은 notify(알림만)·question(막히면 질문)·review(승인 후 실행) 세 패턴으로, 행동의 가역성과 파급 범위로 고릅니다. dots의 auto-review도 같은 구조의 제품화입니다. 그리고 아무도 안 보는 시간에 일하는 에이전트일수록, 최소 권한과 감사 로그가 생명줄입니다.
