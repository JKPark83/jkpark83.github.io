1. 도입 — 96%짜리 에이전트가 우리 레포에선 왜 헤맬까

코딩 에이전트를 회사 코드에 붙여 본 사람이라면 한 번쯤 느꼈을 겁니다. 리더보드에서는 사람보다 잘한다는 모델이, 우리 레포에서는 이상한 파일을 뒤지고 이미 있는 유틸을 다시 만들고 팀 컨벤션을 무시한 PR을 올립니다. 벤치마크 점수와 체감 사이의 이 간극은 다들 느끼면서도 숫자로 말하기 어려웠습니다. 공개 벤치마크는 계속 오르는데, 내 체감은 왜 안 오르는지 설명할 데이터가 없었으니까요.

이번 주에 그 숫자가 나왔습니다. Specific Labs가 공개한 Real-SWE는 한 번도 공개된 적 없는 실제 기업 코드베이스에서 뽑은 태스크로 프런티어 코딩 에이전트 8개를 시험했습니다. 결과는 평균 해결률 26.9%. 최고 성적을 낸 모델도 38.8%에 그쳤습니다. 같은 시기 공개 벤치마크인 SWE-bench Verified 상위권이 95~97%에 몰려 있는 것과 비교하면 충격적인 간극입니다. Hacker News 스레드는 하루 만에 포인트 270, 댓글 150개를 넘겼고, 댓글의 상당수가 "드디어 내가 보는 현실과 맞는 숫자가 나왔다"였습니다.

이 글은 단순히 "에이전트 별거 없네"로 끝나는 이야기가 아닙니다. 공개 벤치마크가 왜 못 믿을 물건이 됐는지, Real-SWE는 무엇을 다르게 했는지, 그리고 결론적으로 왜 모든 팀이 자기만의 프라이빗 벤치마크를 가져야 하는지 — 핀테크 기업 Ramp가 실제로 만든 사내 SWE-Bench 사례와 함께, 직접 만들 수 있는 수준까지 파고듭니다. 에이전트 평가의 기초는 에이전트 evals 편에서 다뤘으니, 오늘은 "무엇으로 시험 볼 것인가"라는 데이터 쪽 이야기입니다.

2. 배경 — 공개 벤치마크는 어떻게 무너졌나

먼저 용어부터. SWE-bench는 GitHub의 실제 오픈소스 이슈와 그 수정 PR로 만든 코딩 에이전트 벤치마크입니다. "이 이슈를 해결하라"는 지시를 주고, 에이전트가 만든 패치가 사람이 작성한 테스트를 통과하면 해결로 칩니다. 그중 사람이 문제 품질을 검수한 500문제 부분집합이 SWE-bench Verified인데, 지난 2년간 "기계가 코딩을 얼마나 하나"의 사실상 공식 점수판이었습니다.

그 점수판이 올해 세 방향에서 동시에 금이 갔습니다.

  • 포화(saturation) — 2026년 9월 기준 상위 모델들이 95~97%에 몰려 1%p 안에서 다툽니다. 이 구간에서는 점수 차이가 실력 차이인지 노이즈인지 구별할 수 없습니다.
  • 오염(contamination) — 벤치마크 문제가 모델의 학습 데이터에 섞여 들어간 상황을 말합니다. OpenAI가 직접 확인해 보니, 시험한 모든 프런티어 모델이 일부 문제에서 사람이 쓴 정답 패치를 토씨 하나 안 틀리고 재현했습니다. 500문제가 전부 공개 GitHub 저장소에서 왔으니 예정된 결말이었습니다. 문제를 푼 게 아니라 답을 외운 겁니다.
  • 결함 테스트 — OpenAI가 모델들이 유독 못 푸는 문제 138개(전체의 27.6%)를 사람 손으로 감사했더니, 그중 59.4% 이상이 테스트 자체에 결함이 있었습니다. 기능적으로 올바른 답을 내도 채점 테스트가 거부하는 문제들입니다. 즉 리더보드의 '남은 어려운 문제'는 상당수가 실력 문제가 아니라 채점 문제였습니다.

이 감사 결과를 담은 OpenAI의 글 "Why SWE-bench Verified no longer measures frontier coding capabilities"는 사실상의 은퇴 선언이었고, HN에서도 크게 다뤄졌습니다. 대안으로 지목된 것이 Scale AI의 SWE-bench Pro입니다. 문제 절반을 비공개 상용 코드베이스에서 뽑아 오염에 저항하도록 설계했는데, 여기서 이미 흥미로운 신호가 나왔습니다. 공개 세트와 비공개 세트의 점수 차이가 모델마다 다르게 벌어진 겁니다.

3. Real-SWE 해부 — 한 번도 공개된 적 없는 코드로 시험 보기

Real-SWE의 설계는 단순하지만 급진적입니다. 인터넷에 존재한 적이 없는 코드라면, 학습 데이터에 있을 수도 없다. 오염 문제를 필터링으로 완화하는 게 아니라 원천적으로 차단하는 접근입니다.

방법론을 뜯어 보면 이렇습니다.

  • 태스크 10개 — 실제 기업들에게 라이선스를 받은 비공개 프로덕션 코드베이스에서 뽑았습니다. 원래 담당 엔지니어들이 몇 주씩 붙어 해결한 실전 티켓들입니다.
  • 에이전트 8개, 네이티브 하네스 — 각 모델을 그 모델 제작사의 순정 하네스(harness) — 모델을 감싸고 파일 읽기·명령 실행·컨텍스트 관리를 대신해 주는 실행 계층 — 에서 돌렸습니다. 모델만이 아니라 "그 회사가 파는 에이전트 제품 전체"를 시험한 셈입니다.
  • 태스크당 8회 시도, 총 640회 롤아웃 — 점수는 pass@1(첫 시도 성공률)을 8회 독립 실행으로 평균 낸 값입니다. 에이전트는 실행마다 결과가 달라지므로 여러 번 돌려 분산을 줄였습니다.
  • Harbor 포맷, 채점 시점에 verifier 주입 — 태스크는 Laude Institute의 Terminal-Bench가 쓰는 표준 포맷인 Harbor(지시문 + 샌드박스 + verifier)로 만들어졌습니다. 채점용 verifier는 해당 코드베이스의 기존 테스트 스위트를 그대로 쓰거나 그에 기반해 작성했고, 에이전트 실행이 끝난 뒤에 주입됩니다. 에이전트가 채점 기준을 미리 보고 테스트에만 맞추는 것을 막기 위해서입니다.

결과가 이번 주 화제의 중심입니다.

순위도 흥미롭습니다. 1위는 Claude Fable 5.1(38.8%), 2위는 GPT-6 Astra, 3위는 Gemini 3.8 Flash로 1위와 7.6%p 차이였습니다. 오픈 웨이트 모델 중에서는 GLM 5.3이 4위로 가장 높았고, Grok·Muse Spark·Kimi·GPT-5.6 Sol이 뒤를 이었습니다. 비용 관점의 데이터도 있는데, 태스크 하나를 해결하는 데 든 평균 컴퓨트 비용이 Gemini는 약 $8, Fable은 약 $18이었습니다. 점수만이 아니라 "해결 1건당 비용"으로 보면 선택이 달라질 수 있다는 것 — 에이전트 토큰 경제학 편에서 다룬 관점이 벤치마크에도 들어오기 시작한 겁니다.

물론 한계도 뚜렷하고, HN 댓글의 절반은 그 얘기였습니다. 태스크가 10개뿐이라 통계적 신뢰구간이 넓고, 코드가 비공개라 제3자가 결과를 재현·검증할 수 없습니다. 한 댓글은 사람 베이스라인이 없다는 점을 정확히 짚었습니다 — "같은 티켓을 신입 엔지니어에게 주면 몇 %나 해결할까?"를 모르면 26.9%가 낮은 건지 높은 건지 판단할 수 없다는 겁니다. 원 담당자들이 몇 주씩 걸린 문제라는 걸 감안하면, 26.9%를 "겨우"가 아니라 "벌써"로 읽어야 한다는 반론도 있었습니다.

4. 간극의 정체 — 코드를 못 쓰는 게 아니라 시스템을 못 읽는다

Real-SWE 결과에서 점수보다 중요한 건 실패 분석입니다. 실패한 롤아웃을 뜯어 보니, 대부분의 실패는 코드를 잘못 써서가 아니라 남의 시스템을 잘못 읽어서였습니다. 문법도 맞고 그럴듯하게 도는 코드를 만들었지만, 그 코드베이스의 실제 구조·컨벤션·암묵적 요구사항과 어긋난 겁니다.

생각해 보면 당연합니다. 공개 벤치마크의 저장소들은 모델이 학습 중에 수없이 본 코드입니다. Django나 scikit-learn 이슈를 푸는 모델은 사실상 홈그라운드에서 오픈북 시험을 보는 셈입니다. 반면 처음 보는 사내 코드베이스에서는 신입 개발자와 똑같은 문제에 부딪힙니다.

  • 문서에 없는 의존성 — "이 서비스를 건드리면 저쪽 배치 잡이 깨진다"는 지식은 코드 어디에도 명시돼 있지 않습니다.
  • 티켓에 없는 요구사항 — 실제 티켓은 불완전합니다. 담당 엔지니어는 티켓에 안 적힌 요구사항을 회의와 슬랙에서 찾아냈지만, 에이전트에게는 티켓이 전부입니다.
  • 팀 컨벤션 — 에러 처리 방식, 레이어 구분, 금지된 패턴. 어기면 테스트는 통과해도 리뷰에서 반려됩니다.

이 관찰은 실무에 바로 시사점을 줍니다. 우리 레포에서 에이전트 성능을 올리는 지렛대는 더 좋은 모델을 기다리는 것보다 시스템을 읽을 수 있게 해 주는 것 — AGENTS.md·CLAUDE.md 같은 레포 컨텍스트 문서(해당 편 참고), 좋은 코드 검색 도구, 암묵지의 문서화 — 쪽에 있을 가능성이 높다는 겁니다. 그리고 "우리 레포에서 뭐가 부족한지"를 알려면, 결국 우리 레포로 시험을 봐야 합니다.

5. 실전 — Ramp처럼 우리 팀 프라이빗 eval 만들기

여기까지 오면 자연스러운 결론이 나옵니다. 벤치마크의 목적이 "어떤 모델·하네스가 우리 일을 잘하나"라면, 시험지도 우리 일에서 나와야 합니다. 이번 주 이 흐름을 상징한 또 하나의 사례가 핀테크 기업 Ramp의 Ramp SWE-Bench입니다. Ramp CEO Eric Glyman은 발표 트윗에서 이렇게 못박았습니다. "공개 벤치마크는 포화됐다. (...) 우리는 Ramp 내부에서 — 어떤 모델도 본 적 없는 코드로, 우리 엔지니어가 실제로 배포하는 기준으로 채점하는 — 벤치마크를 만들었다. AI로 돌아가는 회사라면 전부 자기 것이 필요하다."

Ramp의 설계에서 배울 점이 많습니다. 태스크는 사내 백그라운드 코딩 에이전트가 만들어 엔지니어 리뷰를 거쳐 실제 프로덕션에 배포된 변경에서 역으로 추출합니다. 태스크 선별은 자동화하되 최종 승인만 사람이 합니다. 하네스로는 SWE-bench 팀이 만든 mini-swe-agent(에이전트 본체가 파이썬 100줄 정도, bash만 쓰는 초경량 에이전트, 7.6k 스타)를 썼습니다. 특정 벤더의 하네스가 아니라 중립 하네스로 고정해야 모델끼리 공정하게 비교되기 때문입니다.

전체 파이프라인을 그림으로 보면 이렇습니다.

직접 시작한다면 첫 단계는 태스크 후보 찾기입니다. 최근 머지된 PR 중 "테스트가 함께 추가된, 적당한 크기의 변경"이 좋은 재료입니다. 간단한 휴리스틱으로 후보를 긁어 봅시다.

{{< highlight bash >}} # 최근 6개월 머지 커밋 중 태스크 후보 찾기: # 소스와 테스트를 함께 고친, 3~15개 파일 규모의 변경 git log --merges --since="6 months ago" --pretty="%H %s" | while read sha msg; do files=$(git diff-tree --no-commit-id --name-only -r "$sha") n=$(echo "$files" | wc -l) has_test=$(echo "$files" | grep -cE '(test|spec)' ) has_src=$(echo "$files" | grep -cvE '(test|spec)' ) # 테스트 포함 + 소스 포함 + 너무 크지 않은 변경만 통과 if [ "$has_test" -ge 1 ] && [ "$has_src" -ge 1 ] && [ "$n" -ge 3 ] && [ "$n" -le 15 ]; then echo "후보: $sha $msg" fi done {{< /highlight >}}

후보를 골랐으면 태스크로 포장합니다. 요즘의 사실상 표준은 Real-SWE도 쓴 Harbor 포맷입니다. Harbor는 Laude Institute가 Terminal-Bench를 만들며 정리한 오픈소스 프레임워크로, 태스크를 지시문(instruction) + 샌드박스(환경) + verifier(채점기) 세 조각의 표준 계약으로 묶고, 어떤 에이전트든 컨테이너에서 병렬 롤아웃을 돌려 줍니다. 태스크 하나의 뼈대는 단순화하면 이런 모양입니다.

{{< highlight text >}} tasks/fix-billing-rounding/ # 태스크 1개 = 디렉터리 1개 ├── task.yaml # 지시문: 에이전트에게 보여줄 티켓 본문 ├── environment/ │ └── Dockerfile # 문제 시점 커밋으로 고정된 코드 + 의존성 └── verifier/ └── test_outputs.py # 정답 판정 테스트 — 실행이 끝난 뒤 주입됨 {{< /highlight >}}

verifier는 해당 PR이 추가한 테스트를 출발점으로 삼되, 그대로 복사하지 말고 행동을 검증하도록 다듬는 게 좋습니다. 원래 구현의 함수 이름이나 파일 위치를 하드코딩하면, 다르게 접근했지만 올바른 해법이 억울하게 탈락합니다. SWE-bench Verified의 "결함 테스트 59.4%"가 바로 이렇게 만들어진 함정이었습니다.

{{< highlight python >}} # verifier/test_outputs.py — 나쁜 예 vs 좋은 예 # 나쁜 예: 원래 구현의 내부 구조를 하드코딩 (다른 접근을 전부 탈락시킴) def test_bad(): from billing.utils import round_krw # 에이전트가 다른 모듈에 구현하면 실패 assert round_krw(1004.5) == 1005 # 좋은 예: 시스템의 겉 동작(행동)만 검증 def test_good(client): r = client.post("/invoices", json={"amount": 1004.5}) assert r.json()["amount"] == 1005 # 어디에 어떻게 구현했든 통과 {{< /highlight >}}

처음부터 수백 개를 만들 필요는 없습니다. Ramp도 자동 추출 + 사람 승인으로 천천히 쌓았고, Real-SWE는 10개로 시작해 업계 대화를 바꿨습니다. 잘 검수된 태스크 10~20개면 "모델 A vs B", "하네스 바꾸기 전 vs 후" 같은 실무 의사결정에는 충분히 유용한 신호가 나옵니다. 대신 태스크당 반복 횟수를 늘려(Real-SWE는 8회) 분산을 줄이는 게 중요합니다. 에이전트를 CI에서 계속 평가하는 운영 이야기는 스테이트풀 에이전트 evals 편과 이어집니다.

6. 흔한 실수 · 팁

  • verifier를 채점 전에 컨테이너에 넣어 두기 — 에이전트가 테스트 파일을 읽고 테스트만 통과하는 코드를 짭니다. 리워드 해킹의 가장 흔한 형태입니다. verifier는 반드시 실행이 끝난 뒤 주입하세요.
  • 해피패스 태스크만 고르기 — "함수 하나 추가"짜리 깔끔한 PR만 태스크로 만들면 점수는 잘 나오지만 아무것도 알려 주지 않습니다. Real-SWE의 교훈은 실패가 시스템 읽기에서 나온다는 것 — 여러 모듈에 걸치고 암묵적 제약이 있는 태스크를 섞어야 합니다.
  • 베이스라인 없이 숫자 해석하기 — "우리 벤치에서 31%"는 그 자체로는 의미가 없습니다. 최소한 모델 2~3개를 같은 조건에서 돌려 상대 비교를 하고, 가능하면 신입 온보딩 과제로 같은 태스크를 줘서 사람 기준점도 잡아 보세요. Real-SWE가 받은 가장 뼈아픈 비판이 이 지점이었습니다.
  • 1회 실행으로 결론 내리기 — 에이전트는 같은 태스크도 돌릴 때마다 결과가 다릅니다. 태스크 10개 × 1회로 모델을 고르면 동전 던지기와 다르지 않습니다. 태스크 수가 적을수록 반복을 늘리세요.
  • 벤더 하네스와 모델 성능 혼동하기 — Real-SWE는 일부러 각사 순정 하네스로 "제품 전체"를 쟀고, Ramp는 일부러 중립 하네스로 "모델만" 쟀습니다. 둘 다 유효하지만 다른 질문입니다. 지금 내가 어느 질문에 답하려는 건지 먼저 정하세요.
  • 프라이빗 태스크의 유출 — 사내 코드가 담긴 태스크를 외부 API로 돌리는 순간 데이터 정책 문제가 됩니다. 벤더의 학습 제외(zero-retention) 조건을 확인하고, 민감한 코드는 익명화하거나 제외하세요. Real-SWE도 라이선스 계약으로 이 문제를 풀었습니다.

7. 마무리 (TL;DR)

  • SWE-bench Verified는 포화(상위권 95~97%) · 오염(정답 패치를 토씨까지 재현) · 결함 테스트(감사 대상의 59.4%)로 신뢰를 잃었고, OpenAI는 공식적으로 평가를 중단했습니다.
  • 이번 주 화제가 된 Real-SWE는 한 번도 공개된 적 없는 기업 코드 태스크 10개로 프런티어 에이전트 8개를 시험했고, 평균 해결률은 26.9%(최고 38.8%)였습니다.
  • 실패의 대부분은 코드 작성이 아니라 남의 시스템 읽기에서 나왔습니다. 우리 레포에서의 지렛대는 더 좋은 모델보다 레포 컨텍스트(문서·검색·컨벤션) 쪽에 있을 가능성이 큽니다.
  • 공개 점수가 비슷한 모델도 비공개 코드에서는 순위가 뒤집힙니다(SWE-bench Pro에서 최대 -13.9%p 하락). 모델 선택은 우리 코드로 검증해야 합니다.
  • 그래서 결론은 "모든 팀이 자기 벤치마크를 가져야 한다"입니다. 머지된 PR에서 태스크를 추출하고, 사람이 승인하고, Harbor 포맷(지시문 + 샌드박스 + verifier)으로 포장해 verifier는 채점 시점에 주입 — 잘 검수된 10~20개와 충분한 반복이면 실무 의사결정에 충분합니다.
