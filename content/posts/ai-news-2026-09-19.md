# 🔥 오늘의 핵심

오늘은 에이전트 **하네스 자체가 연구 대상**이 된 날이다. NVIDIA의 **SoL-Pi**는 하네스 개선을 자동 연구 루프에 맡겨 토큰 트래픽을 절반 가까이 줄였고, 별도의 실증 연구는 플래닝·툴·컨텍스트 관리를 부품 단위로 분해해 "뭐가 진짜 효과 있는지"를 176개 설정으로 쟀다. 오늘 해볼 일: 내 에이전트의 토큰 청구서에서 '반복 재전송되는 관찰 결과'가 몇 %인지 재보기 — SoL-Pi가 깎은 게 정확히 그 부분이다.

# 🤖 모델 & 릴리즈 레이더

프론티어 신모델 발표는 없었지만, 에이전트 운영 비용에 직결되는 문서 두 건이 나왔다.

- **DeepSeek-V4.1-Flash 테크 리포트 (9/17)** — 9월 초 배포된 모델의 상세가 공개됐다. 552B 백본 MoE, 1M 컨텍스트, 멀티모달. Causal Encoder-Decoder 구조로 **디코드 시 16B, 프리필 시 8B만 활성화**하고, cross-layer KV 재사용(CSA2)+FP4 KV 캐싱으로 **글로벌 KV 캐시를 토큰당 890바이트 — V4-Flash의 약 1/4**로 줄였다. SSD에 상주하는 persistent KV는 1/8. 롱-호라이즌 에이전트의 input-heavy 워크로드를 정면으로 겨냥한 설계다. [arXiv 2609.19969](https://arxiv.org/abs/2609.19969)
- **Claude Code 2.1.277 — AGENTS.md 공식 지원** — 프로젝트에 CLAUDE.md가 없으면 **AGENTS.md를 대신 읽는다**(`/config`의 Project instructions에서 변경, Bedrock/Vertex/Foundry는 아직). Codex·기타 툴과 지침 파일 하나로 통일할 길이 열렸다. 서브에이전트 결과에 출처 헤더를 붙여 본문 지시로 오인되지 않게 한 변경, 프롬프트 속 보이지 않는 유니코드 제거 등 인젝션 대비 수정도 함께 들어갔다(저장소 클론으로 확인, 최근 커밋 9/18). Codex CLI는 0.155.1 패치 태그가 올라온 정도로 조용한 하루. # 📚 주목 논문

## SoL-Pi: 하네스를 자동 연구 루프로 개선 (arXiv 2609.20519, cs.AI)

- **저자**: Haozhe Liu, Tian Ye, Mingchen Zhuge, Enze Xie, Song Han 외 — 총 14명, NVIDIA(NVlabs 저장소 기준, 9/17 공개, 오늘 HF Daily 상위권)
- **핵심 기여**: "에이전트 루프를 스케일하기 전에, 에이전트가 **하네스부터 스스로 효율화**할 수 있는가?"라는 질문. 다양한 환경에서 하네스 롤아웃을 자동 연구 루프로 돌려, 개발 환경 밖에서도 통하는 개선안만 남겼다.
- **방법**: 선택 과정에서 살아남은 4개 메커니즘이 SoL-Pi를 구성 — 편집+검증을 한 호출로 묶는 Action Fusion, 큰 관찰 결과를 핸들로 치환하는 ObservationPack, 인용 검증을 통과할 때만 로그를 축약하는 Evidence-Preserving Reducer, 완료된 플랜 단계를 압축하는 Online Context Compact.
- **검증된 결과(초록 기준)**: 51개 태스크 EdgeBench에서 GPT-5.6 Sol·Opus 5 모두 Pi와 성능 동급을 유지하면서 **기록 토큰 트래픽 44.7~49.0% 절감, API 비용 약 1/3 절감**. 시간당 추정 절감액은 네이티브 Codex·Claude Code 하네스 대비 $8.75~$13.50.
- 🛠 **에이전트 빌더 시사점**: 절감 포인트 4개가 전부 "성능을 깎지 않는 선"에서 골라졌다는 게 핵심 — 검증 생략·조기 종료 같은 꼼수 없이 하네스 배관만으로 이만큼 나온다는 데이터.
- **한계**: 구현이 Pi 하네스 전용이고 전 기능 opt-in — 다른 하네스로의 이식성은 아직 주장 단계다.
- [arXiv 링크](https://arxiv.org/abs/2609.20519)

![SoL-Pi 4개 메커니즘](/images/ai-news-2026-09-19/solpi-mechanisms.svg)

*자동 연구 루프에서 살아남은 4개 메커니즘과 EdgeBench 절감 폭.*

## 코딩 에이전트 하네스 설계 실증 연구 (arXiv 2609.20804, cs.AI)

- **저자**: Run-Ze Fan, Zihao Zhang, Fei Liu, Hamed Zamani, Xiaoyang Wang 외 — 총 9명(초록 메타데이터에 소속 미표기, 9/17 공개)
- **핵심 기여**: 하네스를 통짜로 비교하던 기존 연구와 달리, 실행 루프를 고정하고 **플래닝·액션 공간·컨텍스트 관리만 부품 교체**하며 효과를 분리 측정했다.
- **방법**: 모델 4종 × SWE-Bench Verified·Terminal-Bench 2.1에서 컨텍스트 관리 전략 5종, 윈도 예산 4종, 플래닝·액션 공간 절제 실험 — 총 176개 매칭 설정.
- **검증된 결과(초록 기준)**: ① 컨텍스트 관리의 이득 대부분은 오버플로 실패 방지에서 나오고 예산이 빡빡할수록 커진다 ② 규칙 기반 생략 → LLM 요약 순서의 스테이징이 최고 효율, '생략분 복구' 기능은 모델이 거의 안 쓴다 ③ 플래닝은 약한 모델엔 정확도 스캐폴드, 강한 모델엔 비용 절감 수단 ④ bash 능숙한 모델은 bash-only 인터페이스로 충분하며 비용이 크게 낮다.
- 🛠 **에이전트 빌더 시사점**: "툴을 더 만들까, 컨텍스트 압축을 넣을까" 같은 하네스 설계 질문에 처음으로 통제된 근거가 생겼다. 아래 공통 팁 참조.
- **한계**: 경량 하네스 하나에서의 결과 — 멀티에이전트나 장기 세션으로의 일반화는 미검증.
- [arXiv 링크](https://arxiv.org/abs/2609.20804)

# 🧑‍💻 Codex & Claude Code 실전 팁

## 🟩 Codex — 명령 정책을 규칙 파일로: execpolicy (Workflow)

- 소스: [codex-rs/execpolicy README](https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md)
- 💡 어떤 명령을 허용·확인·금지할지를 Starlark 규칙 파일로 선언하고, 규칙마다 유닛 테스트를 붙일 수 있다.
- 📝 규칙과 검증:

```starlark
prefix_rule(
    pattern = ["git", "reset", "--hard"],
    decision = "forbidden",   # allow | prompt | forbidden (기본 allow)
    justification = "destructive operation",
    match = [["git", "reset", "--hard"]],      # 이 규칙에 걸려야 하는 예시
    not_match = ["git reset --merge"],          # 걸리면 안 되는 예시 — 로드 시 검증
)
```

```bash
codex execpolicy check --rules policy.rules git status   # 결과를 JSON으로 출력
```

- 🎯 팀 공용 저장소에서 "에이전트가 절대 치면 안 되는 명령" 목록을 코드 리뷰 가능한 파일로 관리하고 싶을 때.
- ⚠️ 현재는 prefix-rule 서브셋만 지원 — 더 풍부한 언어는 예고 상태다.
- ⭐ `match`/`not_match`가 로드 타임에 검증된다는 점이 백미. 정책 파일에도 테스트를 달자.

## 🟦 Claude Code — /feature-dev: 7단계 기능 개발 워크플로 (Subagent)

- 소스: [feature-dev 플러그인 README](https://github.com/anthropics/claude-code/blob/main/plugins/feature-dev/README.md)
- 💡 공식 플러그인 `feature-dev`는 기능 개발을 요구사항 확인 → 코드베이스 탐색 → 질문 → 아키텍처 설계 → 구현 → 리뷰의 7단계로 강제한다.
- 📝 설치 후 한 줄:

```bash

```

탐색 단계에서 `code-explorer` 서브에이전트 2~3개가 병렬로 유사 기능·아키텍처·관련 구현을 각각 조사하고, 본체는 그 결과로 식별된 파일을 읽은 뒤에야 설계로 넘어간다.
- 🎯 "바로 코드부터 쓰는" 에이전트 습관 때문에 기존 패턴과 어긋난 구현이 나올 때.
- ⚠️ 단계마다 확인이 끼어들어 소소한 수정에는 과하다 — 신규 기능 단위에서 쓰자.
- ⭐ 병렬 탐색 서브에이전트 프롬프트 구성 자체가 자작 워크플로에 훔쳐올 만한 부분.

## 🟪 공통 — 컨텍스트 압축은 '규칙 먼저, LLM 나중' (Context)

- 소스: [arXiv 2609.20804](https://arxiv.org/abs/2609.20804)
- 💡 위 실증 연구의 결론을 그대로 기본값으로: 오래된 툴 결과를 규칙으로 먼저 쳐내고(elision), LLM 요약은 그 다음 단계에만 투입하는 스테이징이 효율 1위였다.
- 📝 적용 체크리스트:
  1. N턴 지난 대형 툴 결과는 규칙으로 자르거나 핸들로 치환 — LLM 호출 없이.
  2. LLM 요약은 규칙 통과 후 남은 것에만.
  3. '생략분 복구' 장치는 만들지 않는다 — 모델이 안 쓴다는 측정 결과가 있다.
  4. 모델이 bash에 능하다면 전용 툴 추가 전에 bash-only 비용을 먼저 재본다.
- 🎯 컨텍스트 관리 로직을 처음 넣거나, LLM 요약 비용이 배보다 큰 배꼽이 됐을 때.
- ⚠️ 단일 하네스 실험 결과다 — 자기 워크로드에서 A/B는 필수.
- ⭐ SoL-Pi의 ObservationPack·Online Context Compact와 정확히 같은 방향이라는 점이 오늘의 교차 검증.
