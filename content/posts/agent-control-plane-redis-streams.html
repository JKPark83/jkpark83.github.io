1. 도입 — 하나일 땐 안 보이던 문제

에이전트를 한두 개 돌릴 때는 인프라가 별로 문제되지 않습니다. 컨테이너 하나 띄우고, 끝나면 내리면 그만이니까요. 그런데 코딩 에이전트를 프로덕션에서 동시에 수만·수백만 개 돌리기 시작하면 이야기가 달라집니다. 에이전트 태스크는 대부분 짧게 살다 사라집니다. 파일 몇 개 읽고, 도구 한 번 호출하고, 몇 초 만에 끝나는 잡이 초당 수천 개씩 생겼다 없어지죠.

이렇게 짧게 살고 폭발적으로 생겼다 사라지는(high-churn) 워크로드는 기존 인프라의 약한 고리를 정확히 찌릅니다. 이번 주 화제의 중심이 바로 그 지점입니다. 9월 20일, Google이 오픈소스 에이전트 오케스트레이터 AX(Agent Executor)의 v0.3.0을 냈고 Hacker News 기술 섹션 1위에 올랐습니다. Go로 작성됐고 Apache-2.0 라이선스이며, 저장소는 릴리스 시점 기준 약 5.9천 개의 star가 붙어 있습니다.

이번 릴리스의 핵심 메시지는 딱 한 문장으로 요약됩니다. "에이전트 태스크 상태를 쿠버네티스(Kubernetes) 커스텀 리소스에 넣지 마라. etcd가 먼저 무너진다." AX는 런타임을 세 개의 서비스로 쪼개고, 태스크 상태를 etcd에서 Redis Streams로 통째로 옮겼습니다. 왜 그래야 했는지, 그리고 이 결정에서 우리가 배울 원칙이 무엇인지 하나씩 풀어보겠습니다.

이 글은 AX 사용법 튜토리얼이 아닙니다. "왜 이런 아키텍처가 필요한가"를 이해하는 게 목표입니다. AX를 안 쓰더라도, 에이전트를 스케일로 돌릴 계획이 있다면 여기서 나오는 상태 저장소 분리·리컨사일러·이벤트 스트림 패턴은 그대로 쓸모가 있습니다.

2. 배경 — 컨트롤 플레인·etcd·리컨사일 루프

AX는 쿠버네티스의 설계 철학을 거의 그대로 빌려 옵니다. 그래서 세 가지 개념만 먼저 잡고 가면 나머지가 쉽습니다.

선언적(declarative) 오케스트레이션. "이 명령을 순서대로 실행해라"(명령형)가 아니라 "최종 상태는 이래야 한다"(선언형)를 적어 주는 방식입니다. 예를 들어 "레포 A를 붙인 샌드박스에서 이 모델로 태스크를 하나 돌려라"라는 매니페스트(manifest)(원하는 상태를 적은 YAML 파일)를 던져 주면, 시스템이 알아서 그 상태를 만들어 냅니다.

컨트롤 플레인(control plane). 그 "알아서 만들어 내는" 두뇌입니다. 사용자가 원하는 상태(desired state)를 받아서 저장하고, 현재 상태(current state)와 비교해 차이를 메꾸는 쪽이죠. 실제로 태스크가 돌아가는 워커 노드(데이터 플레인)와 구분됩니다.

리컨사일 루프(reconcile loop). 컨트롤 플레인의 심장 박동입니다. "원하는 상태 = 3개 실행 중, 현재 = 2개 → 1개 더 띄운다" 같은 판단을 끊임없이 반복합니다. 이 루프를 도는 프로그램을 리컨사일러(reconciler) 또는 컨트롤러라고 부릅니다.

여기서 마지막 조각이 etcd입니다. 쿠버네티스는 이 모든 "원하는 상태"를 etcd라는 저장소에 보관합니다. etcd는 여러 대에 걸쳐 데이터를 강하게 일관되게(strongly consistent) 유지하는 key-value 저장소로, 내부적으로 Raft라는 합의(consensus) 알고리즘을 씁니다. 쉽게 말해 모든 쓰기가 과반수 노드의 동의를 받고 디스크에 기록돼야 완료되는, 정확성에 아주 신경 쓴 저장소입니다. 문제는 바로 이 성실함이 에이전트 스케일에서는 독이 된다는 점입니다.

3. 왜 etcd가 에이전트 스케일에서 무너지나

etcd가 나쁜 저장소라서가 아닙니다. etcd는 "많지 않은 수의 오래 사는 객체"에 최적화된 설계이기 때문입니다. 클러스터의 노드, 서비스, 배포 설정처럼 자주 안 바뀌고 개수도 수천~수만 개 수준인 데이터를 안전하게 지키는 게 etcd의 원래 임무죠. 에이전트 태스크는 정확히 그 반대입니다.

충돌 지점은 세 가지입니다.

① 모든 쓰기가 합의 + 디스크. Raft 특성상 태스크 하나를 만들고, 상태를 업데이트하고, 지우는 매 순간이 과반수 노드 동의와 디스크 fsync를 거칩니다. 짧게 사는 태스크가 초당 수천 개씩 생겼다 사라지면, 이 쓰기 폭풍이 그대로 합의 프로토콜에 부하로 쌓입니다. 컨트롤 플레인 전체가 느려지죠.

② 저장 용량 한도. etcd는 저장 공간에 명확한 상한이 있습니다. 기본 쿼터가 2GB, 실무 권장 상한이 8GB 안팎입니다. 태스크 객체 수백만 개를 쌓으면 이 공간이 금방 찹니다. 한도를 넘으면 etcd는 쓰기를 아예 막아 버리는(read-only 알람) 방어 모드로 들어가고, 그러면 클러스터 전체가 멈춥니다.

③ watch·히스토리·컴팩션 부담. 쿠버네티스 컨트롤러들은 etcd의 변경을 실시간으로 구독(watch)합니다. 객체가 폭발적으로 바뀌면 이 watch 이벤트와 리비전 히스토리가 같이 폭증하고, 오래된 리비전을 정리하는 컴팩션(compaction) 작업도 무거워집니다. 결국 저장소가 아니라 컨트롤 플레인 전체의 응답성이 무너집니다.

정리하면, 커스텀 리소스(CRD)로 "모든 태스크"를 표현하는 순간 etcd는 원래 감당하도록 설계되지 않은 종류의 부하를 뒤집어씁니다. AX 팀의 표현을 빌리면, etcd는 애초에 "수백만 개의 짧게 사는 에이전트 태스크가 만드는 churn"을 위해 만들어지지 않았습니다.

4. AX의 해법 — 런타임을 셋으로 쪼개고 상태를 옮긴다

AX v0.3.0의 두 가지 큰 변화는 이렇습니다.

변화 1: 런타임을 세 서비스로 분리. 예전엔 한 덩어리였던 런타임을 역할별로 쪼갰습니다.

  • ax-server — API 프론트엔드. 매니페스트를 받아 검증(validate)하고 저장합니다.
  • ax-controller (리컨사일러) — 원하는 상태와 현재 상태를 비교해 차이를 메꿉니다. 여러 인스턴스로 수평 확장됩니다.
  • 샌드박스 태스크 러너(task runner) — 실제로 (신뢰할 수 없는) 에이전트 코드를 격리된 샌드박스 안에서 실행합니다.

변화 2: 태스크 상태를 etcd → Redis로 이전. 여기가 핵심입니다. AX는 상태를 쿠버네티스 커스텀 리소스가 아니라 Redis에 저장합니다. 구체적으로 두 갈래를 씁니다.

  • Redis 해시(hash) — ax-server가 검증한 매니페스트(원하는 상태)를 스냅샷으로 저장합니다. "이 태스크는 이런 스펙"이라는 사실을 담는 자리입니다.
  • Redis Streams — "태스크가 생겼다 / 상태가 바뀌었다" 같은 이벤트를 로그처럼 순서대로 쌓습니다. ax-controller 풀이 이 스트림을 소비하며 일합니다.

흐름을 이어 보면 이렇습니다. ① 사용자가 매니페스트를 ax-server에 던진다 → ② ax-server가 검증 후 Redis 해시에 저장하고 이벤트를 스트림에 넣는다 → ③ ax-controller 풀이 스트림에서 이벤트를 집어 리컨사일한다 → ④ 태스크 러너가 샌드박스에서 실행한다. etcd는 이 뜨거운 경로(hot path)에서 완전히 빠집니다.

5. 왜 하필 Redis Streams인가 (consumer group)

단순히 "Redis가 빠르니까"가 답의 전부는 아닙니다. 리컨사일러를 여러 개로 늘려도 같은 이벤트를 중복 처리하지 않고 안전하게 나눠 갖는 장치가 필요한데, Redis Streams의 consumer group(컨슈머 그룹)이 정확히 그 역할을 합니다.

Redis Streams는 이름 그대로 이벤트가 시간 순서대로 append-only로 쌓이는 로그입니다(Kafka를 떠올리면 감이 옵니다). 여기에 consumer group을 붙이면 이런 성질을 얻습니다.

  • 부하 분산. 그룹에 속한 컨슈머(=컨트롤러 인스턴스)들이 이벤트를 나눠 받습니다. 컨트롤러를 3개→10개로 늘리면 처리량도 같이 늘어납니다.
  • at-least-once(최소 한 번) 전달. 컨슈머가 이벤트를 받으면 pending 목록에 잡혀 있다가, 처리를 끝내고 XACK로 확인 응답을 보내야 목록에서 빠집니다. 처리 중에 컨슈머가 죽으면 그 이벤트는 사라지지 않고 다른 컨슈머가 XCLAIM으로 넘겨받아 다시 처리합니다.

개념을 코드로 보면 이렇습니다. Redis 명령을 직접 쓴 예시입니다.

{{< highlight bash >}} # 1) ax-server: 태스크 생성 이벤트를 스트림에 추가(append) XADD ax:tasks '*' type created task_id t-8f2a spec_hash h:t-8f2a # 2) 컨트롤러 그룹을 한 번 만들어 둔다 (그룹명 reconcilers) XGROUP CREATE ax:tasks reconcilers '$' MKSTREAM # 3) 컨트롤러 인스턴스 c1이 아직 아무도 안 가져간 이벤트를 하나 받는다 XREADGROUP GROUP reconcilers c1 COUNT 1 BLOCK 5000 STREAMS ax:tasks '>' # 4) 리컨사일을 끝냈으면 확인 응답 → pending 목록에서 제거 XACK ax:tasks reconcilers 1699999999999-0 {{< /highlight >}}

핵심은 XACK가 있기 전까지 이벤트는 "처리 중"으로 남는다는 점입니다. 그래서 컨트롤러가 리컨사일 도중 죽어도 이벤트가 유실되지 않습니다. 이게 짧게 사는 태스크를 안정적으로 대량 처리하는 뼈대입니다.

at-least-once는 "최소 한 번은 전달되지만, 상황에 따라 두 번 이상 전달될 수도 있다"는 뜻입니다. 그래서 리컨사일 로직은 같은 이벤트를 두 번 처리해도 결과가 같은 멱등(idempotent) 형태여야 합니다. 이건 뒤의 "흔한 실수"에서 다시 짚겠습니다.

6. 네 개의 primitive — 선언적으로 에이전트 잡 정의하기

AX에서 에이전트 잡은 네 가지 기본 리소스(primitive)의 조합으로 표현됩니다. 매니페스트는 ax.io/v1alpha1 API 버전을 씁니다.

primitive역할
Task격리된 샌드박스에서 에이전트 코드를 실행한다. CPU·메모리 한도를 건다.
WorkspaceGit 레포·MCP 서버·skill 패키지를 미리 붙여 둔다(pre-wire). 에이전트가 첫 턴 전에 필요한 걸 갖춘 상태로 시작한다.
Gateway아웃바운드 트래픽을 허용 목록(allowlist)의 호스트·포트로만 제한한다. 신뢰할 수 없는 코드가 임의의 외부로 나가는 걸 막는다.
Model어떤 LLM을 쓸지, 자격증명(credential)은 무엇인지 지정한다. 키는 쿠버네티스 시크릿에서 가져온다.

매니페스트는 쿠버네티스 YAML과 거의 똑같이 생겼습니다. 개념을 잡기 위한 예시입니다(실제 필드명은 버전에 따라 다를 수 있으니 공식 문서를 확인하세요).

{{< highlight yaml >}} apiVersion: ax.io/v1alpha1 kind: Task metadata: name: fix-flaky-test # 태스크 이름 spec: workspace: repo-checkout # 아래 Workspace를 참조 model: claude-sonnet # 아래 Model을 참조 resources: cpu: "2" memory: 4Gi # 샌드박스 자원 한도 prompt: "CI에서 깜빡이는 테스트를 찾아 고쳐라" --- apiVersion: ax.io/v1alpha1 kind: Gateway metadata: name: repo-checkout-egress spec: allow: # 이 목록 밖으로는 못 나간다 - host: github.com - host: registry.npmjs.org {{< /highlight >}}

이렇게 "원하는 상태"만 적어 ax-server에 제출하면, 리컨사일러가 알아서 샌드박스를 띄우고, Gateway로 망을 막고, 지정한 모델로 태스크를 돌립니다. 명령형으로 컨테이너를 하나하나 관리할 필요가 없습니다.

7. 숫자로 보는 효과 — 250 세션을 8 파드에

AX는 실행 격리를 Agent Substrate라는 하부 계층에 맡깁니다. 여기서 나온 숫자가 왜 이 아키텍처가 의미 있는지 보여 줍니다. 보고된 바로는, Agent Substrate는 약 250개의 상태 유지(stateful) 에이전트 세션을 물리 쿠버네티스 파드 8개에 다중화(multiplex)합니다. 대략 30:1의 오버서브스크립션(oversubscription) 비율이죠.

비결은 하이버네이션(hibernation)입니다. 250개 세션이 전부 동시에 CPU를 쓰는 게 아닙니다. 어느 순간이든 실제로 실행 중인 건 일부이고, 나머지는 메모리·파일시스템 상태를 스냅샷으로 보존한 채 잠들어(hibernated) 있습니다. 필요할 때 다시 깨어나 이어서 실행하죠. 마치 노트북 절전 모드처럼요.

여기서 "상태를 어디에 두느냐"가 다시 중요해집니다. 세션이 잠들었다 깨어나도 진행 상황이 살아 있어야 하는데, 그 상태를 etcd에 두면 앞서 본 churn 문제로 돌아갑니다. 상태를 전용 저장소(Redis Streams 등)로 빼 두었기 때문에 이런 대규모 다중화가 가능해집니다. "컨트롤 플레인 상태 저장소 분리"와 "고밀도 다중화"는 한 몸입니다.

8. 실전 — AX를 안 써도 가져올 수 있는 원칙

대부분의 팀은 당장 AX를 도입하지 않을 겁니다. 그래도 이 아키텍처가 주는 교훈은 규모와 무관하게 적용됩니다. 에이전트를 조금이라도 대량으로 돌릴 계획이라면 다음을 기억하세요.

원칙 1 — 짧게 사는 상태를 "강한 일관성 저장소"에 넣지 마라. etcd(쿠버네티스 CRD), 또는 매 스텝마다 동기 커밋하는 RDB를 태스크 상태 저장소로 쓰면 churn에서 무너집니다. 짧고 빠르게 바뀌는 상태는 Redis 같은 인메모리 저장소로 빼세요.

원칙 2 — 이벤트는 스트림에, 스냅샷은 별도로. "무슨 일이 일어났다"는 이벤트 로그(Redis Streams·Kafka)와 "지금 상태는 이렇다"는 스냅샷(해시·테이블)을 분리하면, 리컨사일러를 자유롭게 늘렸다 줄일 수 있습니다.

원칙 3 — 워커에 일을 나눠 줄 땐 leasing을 써라. Redis Streams가 없더라도 관계형 DB로 같은 패턴을 흉내 낼 수 있습니다. 핵심은 한 태스크를 한 워커만 집게 만드는 것입니다.

{{< highlight sql >}} -- 여러 워커가 동시에 실행해도 태스크 하나는 한 워커만 집는다. -- FOR UPDATE SKIP LOCKED: 잠긴 행은 건너뛰고 다음 대기 태스크를 집는다. UPDATE tasks SET status = 'running', lease_until = now() + interval '30 seconds' WHERE id = ( SELECT id FROM tasks WHERE status = 'ready' ORDER BY created_at FOR UPDATE SKIP LOCKED -- 경쟁 워커끼리 안 부딪힌다 LIMIT 1 ) RETURNING id, spec; {{< /highlight >}}

여기에 하트비트로 lease_until을 갱신하고, 만료된 리스는 ready로 되돌리면(=워커가 죽으면 다른 워커가 다시 집으면) at-least-once 실행이 완성됩니다. AX의 consumer group이 하는 일을 작은 규모에서 SQL로 재현한 셈입니다.

원칙 4 — 격리와 아웃바운드 제한을 기본값으로. AX의 Gateway처럼, 신뢰할 수 없는 에이전트 코드는 샌드박스에 가두고 나가는 트래픽을 허용 목록으로 좁히세요. 스케일이 커질수록 "에이전트 하나가 뭘 할 수 있는가"의 기본값이 사고를 좌우합니다.

9. 흔한 실수 · 팁

실수 1 — "쿠버네티스가 있으니 CRD로 다 표현하자." 노드·서비스처럼 오래 사는 소수 객체는 CRD가 맞습니다. 하지만 초당 수천 개 생겼다 사라지는 태스크를 CRD로 만들면 etcd가 먼저 죽습니다. 객체의 수명과 개수로 저장소를 갈라 생각하세요.

실수 2 — at-least-once인데 핸들러가 멱등하지 않다. Redis Streams(또는 SQS 등)는 같은 이벤트를 두 번 줄 수 있습니다. "태스크 시작 → 결제 API 호출" 같은 부수효과(side effect)를 멱등 처리 없이 두면, 중복 전달 때 두 번 실행됩니다. 처리 전에 "이미 했는가"를 확인하거나, 유니크 키로 중복을 막으세요.

실수 3 — Redis를 "그냥 캐시"로만 보고 지속성을 안 챙긴다. 태스크 상태를 Redis에 두는 순간 Redis는 캐시가 아니라 사실상의 진실 원본입니다. AOF/스냅샷 같은 지속성 설정과 복제(replica)를 반드시 챙기세요. 안 그러면 Redis 재시작 한 번에 진행 중인 태스크가 통째로 날아갑니다.

실수 4 — 스트림을 안 잘라서 무한히 키운다. Redis Streams는 append-only라 방치하면 메모리를 계속 먹습니다. XADD ... MAXLEN ~ 100000처럼 최대 길이를 주거나 XTRIM으로 주기적으로 잘라 주세요.

팁 — 컨트롤 플레인과 데이터 플레인을 분리해 생각하는 습관. "상태를 관리하는 두뇌"와 "실제 코드를 돌리는 손발"을 나누면, 스케일 병목이 어디서 오는지 훨씬 빨리 짚을 수 있습니다. AX가 런타임을 셋으로 쪼갠 것도 결국 이 분리를 더 선명하게 만든 결정입니다.

10. 마무리 (TL;DR)

  • 에이전트를 대량으로 돌리면 병목은 모델이 아니라 컨트롤 플레인에서 먼저 온다. 짧게 살고 폭발적으로 바뀌는 태스크가 문제다.
  • 쿠버네티스의 etcd는 "적은 수의 오래 사는 객체"용 설계다. 매 쓰기가 합의+디스크를 거치고, 저장 한도(기본 2GB·권장 8GB 안팎)가 있으며, watch·컴팩션 부담이 커서 수백만 짧은 태스크의 churn을 못 버틴다.
  • Google AX v0.3.0(9/20, Apache-2.0, Go)은 런타임을 ax-server·ax-controller·태스크 러너 셋으로 쪼개고, 태스크 상태를 etcd에서 Redis 해시(스냅샷) + Redis Streams(이벤트)로 옮겼다.
  • Redis Streams의 consumer group이 리컨사일러 풀의 부하 분산과 at-least-once 전달(XACK·XCLAIM)을 맡아, 컨트롤러를 자유롭게 수평 확장한다.
  • 잡은 Task·Workspace·Gateway·Model 네 primitive의 선언적 매니페스트(ax.io/v1alpha1)로 표현한다.
  • Agent Substrate 기준 250 세션을 파드 8개에(약 30:1) 다중화한다. 하이버네이션 덕분인데, 이것도 상태를 컨트롤 플레인에서 분리했기에 가능하다.
  • AX를 안 써도 원칙은 그대로다. 짧은 상태는 강한 일관성 저장소에 넣지 말고, 이벤트/스냅샷을 분리하고, leasing(SKIP LOCKED)으로 태스크를 나누고, 격리·아웃바운드 제한을 기본값으로.
