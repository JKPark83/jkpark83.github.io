1. 도입 — 에이전트 시대, 토큰 속도가 곧 지능이다

코딩 에이전트를 돌려 본 적이 있다면 이런 경험이 있을 겁니다. 모델은 분명 똑똑한데, 턴 하나하나가 느려서 전체 작업이 한참 걸립니다. 에이전트 루프는 직렬입니다. 생각하고 → 도구를 부르고 → 결과를 읽고 → 다시 생각합니다. 턴이 30번이면 출력 속도의 차이가 30번 복리로 쌓입니다. 초당 50토큰과 초당 1,000토큰은 "조금 빠르다"가 아니라 3분짜리 작업과 1시간짜리 작업의 차이가 됩니다. reasoning 토큰까지 길게 뽑는 요즘 모델이라면 체감은 더 큽니다.

그래서 이번 주 Hacker News 프런트페이지에 오른 Cerebras의 엔지니어링 글이 눈에 띄었습니다. 10월 22일경 공개된 How we deploy trillion-parameter frontier models on Cerebras는 HN에서 약 350포인트를 받으며 한 주 내내 서빙 쪽 화제의 중심이었습니다. 요지는 도발적입니다. GPU도, HBM도 없이 온칩 메모리 44GB짜리 웨이퍼 스케일 칩을 수십 장 이어서, 2.8조(2.8T) 파라미터짜리 오픈 모델 Kimi K3를 초당 1,000~2,000토큰 이상으로 서빙하겠다는 설계를 숫자와 함께 공개한 겁니다. 마침 같은 주 HN 1위가 Moonshot의 Kimi K3.1 Pro 공개 스레드(1,000포인트 이상)였으니, "조 단위 오픈 모델을 누가 얼마나 빠르게 서빙하느냐"가 한 주의 테마였던 셈입니다.

이 글은 Cerebras 광고가 아닙니다. 이 블로그 포스트가 좋은 교재인 이유는, 따라가다 보면 LLM 추론의 제1원리 — 디코딩은 연산이 아니라 메모리 대역폭에 묶인다 — 가 저절로 이해되기 때문입니다. 이 원리를 알면 vLLM 튜닝 글도, GPU 스펙시트도, 추론 전문 업체들의 속도 경쟁 뉴스도 전부 다르게 읽힙니다. 하나씩 뜯어봅시다.

2. 배경 — 디코딩이 느린 진짜 이유: 연산이 아니라 메모리

먼저 3분 복습입니다. LLM 추론은 두 단계로 나뉩니다. 입력 프롬프트 전체를 한 번에 처리하는 프리필(prefill)과, 그 뒤에 토큰을 하나씩 만들어 내는 디코드(decode)입니다. 프리필은 수천 토큰을 병렬로 처리하니 GPU의 연산 능력을 꽉 채워 쓰는 compute-bound 작업입니다. 문제는 디코드입니다.

디코드에서 토큰 1개를 만들려면, 모델의 활성 가중치 전부를 메모리에서 한 번씩 읽어 와야 합니다. 행렬 곱 자체는 토큰 하나 분량이라 금방 끝나는데, 그 곱에 쓸 수십~수백 GB의 가중치를 메모리에서 연산기까지 실어 나르는 시간이 발목을 잡습니다. 연산기는 대부분의 시간을 데이터를 기다리며 놉니다. 이것이 memory-bound, 흔히 말하는 메모리 장벽(memory wall)입니다.

그래서 한 사용자가 체감하는 생성 속도의 상한은 대략 이렇게 어림할 수 있습니다.

{{< highlight text >}} 사용자당 최대 생성 속도(tok/s) ≈ 메모리 대역폭(GB/s) ÷ 토큰당 읽어야 하는 바이트(GB) 예) 활성 가중치 100GB(4-bit 양자화 후 ~50GB)를 HBM 대역폭 3.35TB/s로 읽으면 3,350 ÷ 50 ≈ 초당 67토큰이 이론 상한 (실제로는 이보다 낮음) {{< /highlight >}}

GPU 서빙이 이 한계를 우회하는 대표 기술이 배칭(batching)입니다. 가중치를 한 번 읽을 때 수십 개 요청의 토큰을 같이 계산하면, 읽기 비용이 분산돼 전체 처리량은 크게 오릅니다. 하지만 한 사용자가 느끼는 속도는 그대로입니다. 배칭은 식당이 테이블을 늘리는 것이지, 요리가 빨라지는 게 아니니까요. 추측 디코딩(speculative decoding) 같은 기법이 사용자당 속도를 몇 배 올려 주지만, 근본 상한은 여전히 "대역폭 ÷ 읽을 바이트"입니다.

이 식에서 남은 변수는 둘뿐입니다. 읽을 바이트를 줄이거나(양자화, MoE로 활성 파라미터 축소), 대역폭을 키우거나. Cerebras의 접근은 후자를 극단까지 밀어붙인 쪽입니다.

3. WSE-3 — HBM을 버리고 SRAM 44GB를 칩 위에 박다

Cerebras의 WSE-3(Wafer Scale Engine 3)는 이름 그대로 실리콘 웨이퍼 한 장을 통째로 칩 하나로 쓰는 프로세서입니다. 보통 웨이퍼 한 장에서 GPU 다이 수십 개를 잘라내는데, 이걸 자르지 않고 하나의 거대한 칩으로 만든 겁니다. 공개 스펙이 비현실적으로 들립니다. 면적 46,225mm²(H100의 약 57배), 트랜지스터 4조 개, 코어 90만 개. 그중 이 글의 주인공은 메모리입니다.

WSE-3에는 HBM이 없습니다. 대신 SRAM 44GB가 90만 개 코어 옆에 분산 배치돼 있고(코어당 48KB), 합산 대역폭이 21PB/s입니다. H100의 HBM3(3.35TB/s)와 비교하면 세 자리수 배 차이입니다. 연산기 바로 옆 메모리라 "실어 나르는 시간"이 사실상 사라집니다. 앞 절의 식에 넣어 보면, 같은 모델이라도 사용자당 생성 속도의 이론 상한이 완전히 다른 차원으로 올라갑니다.

물론 공짜가 아닙니다. SRAM은 HBM보다 훨씬 비싸고 집적도가 낮아서, 웨이퍼 한 장을 통째로 써도 44GB밖에 안 됩니다. H100 한 장(80GB)보다 적습니다. 그래서 바로 이런 질문이 나옵니다 — "44GB짜리 칩으로 2.8조 파라미터를 어떻게 서빙하지?" 이번 블로그 포스트가 답하는 질문이 정확히 이겁니다.

용어 정리: HBM(High Bandwidth Memory)은 GPU 패키지 옆에 쌓아 올리는 고대역폭 DRAM으로, 용량은 크지만(80~192GB) 칩 밖에 있어 대역폭에 물리적 한계가 있습니다. SRAM은 CPU 캐시에 쓰이는 초고속 메모리로, 연산기와 같은 실리콘 위에 있어 빠르지만 비싸고 용량을 키우기 어렵습니다. Cerebras 블로그는 최신 세대 웨이퍼를 WSE-3T로 표기하는데, 온칩 메모리 44GB라는 수치는 공개된 WSE-3 스펙과 같습니다.

4. 본론 — 44GB × 59장에 2.8조 파라미터를 올리는 산수

블로그의 작업 예제(worked example)는 Moonshot AI의 Kimi K3입니다. 7월에 공개된 2.8T 파라미터짜리 역대 최대 오픈 가중치 MoE 모델로, 구조가 이 계산에 핵심적입니다. 총 93개 레이어 중 69개는 KDA(Kimi Delta Attention)라는 선형 어텐션(linear attention) 레이어이고, 24개는 전체 어텐션(Gated MLA) 레이어입니다.

왜 이 구분이 중요할까요? KV 캐시 때문입니다. 전체 어텐션 레이어는 지나온 모든 토큰의 key/value를 쌓아 두므로, 컨텍스트가 길수록 캐시가 커집니다. 반면 선형 어텐션은 과거를 고정 크기 상태(state)로 압축해 들고 가므로, 컨텍스트가 100만 토큰이어도 캐시가 자라지 않습니다. 즉 메모리 관점에서 69개 레이어는 "가중치만 있으면 되는" 가벼운 레이어이고, 24개 레이어는 "가중치 + 큰 KV 캐시"가 필요한 무거운 레이어입니다.

블로그는 가중치 4-bit 양자화, KV 캐시 8-bit, 평균 요청 256K 토큰이라는 가정 아래 이렇게 배치합니다.

  • 선형 어텐션 레이어 69개 — KV 캐시가 필요 없으니 웨이퍼 한 장(44GB)에 두 레이어씩 넣습니다. → 35장
  • 전체 어텐션 레이어 24개 — KV 캐시 자리를 남겨야 하니 한 장에 한 레이어씩 넣습니다. → 24장
  • 합계 59장. 온칩 SRAM 총합은 59 × 44GB ≈ 2.6TB입니다.

산수가 맞는지 어림해 봅시다. 2.8T 파라미터를 4-bit(0.5바이트)로 저장하면 가중치만 약 1.4TB입니다. 93개 레이어로 나누면 레이어당 평균 15GB 수준(MoE라 레이어마다 편차는 있습니다). 선형 레이어 둘이면 약 30GB — 44GB 웨이퍼에 들어갑니다. 전체 어텐션 레이어는 가중치 ~15GB를 빼고 남는 ~29GB가 KV 캐시 몫입니다. 숫자가 아귀가 맞습니다.

여기서 주니어에게 중요한 관찰 하나. 모델 아키텍처가 서빙 하드웨어 소요량을 직접 결정합니다. Kimi K3가 93개 레이어 전부 전체 어텐션이었다면 93장이 필요했을 겁니다. 하이브리드 어텐션(선형 + 전체 혼합) 설계는 벤치마크 점수를 위한 선택이기도 하지만, 동시에 서빙 비용을 위한 선택이기도 합니다. "아키텍처 뉴스"를 읽을 때 KV 캐시 요구량을 같이 떠올리는 습관을 들이면, 뉴스가 훨씬 입체적으로 읽힙니다.

5. 파이프라인 — 웨이퍼 사이를 건너는 것은 활성값뿐

59장을 잇는 방식은 파이프라인 병렬화(pipeline parallelism)입니다. 각 웨이퍼가 자기 레이어를 계산하고, 그 출력인 활성값(activation)을 다음 웨이퍼로 넘깁니다. 공장 조립 라인과 같습니다. 핵심은 웨이퍼 사이를 건너는 데이터가 활성값뿐이라는 점입니다. 활성값은 토큰당 수십 KB 수준으로, 수백 GB짜리 가중치에 비하면 먼지만 합니다. 블로그 기준 이 전송은 RDMA over Ethernet으로 이뤄지고 홉당 약 2µs입니다. 59홉을 다 건너도 100µs대 — 토큰 생성 주기(1,000 tok/s면 토큰당 1ms)에 비해 작은 비용입니다.

GPU 클러스터에서 거대 모델을 서빙할 때 주로 쓰는 텐서 병렬화(tensor parallelism)와 대조해 볼 만합니다. 텐서 병렬화는 레이어 하나를 여러 GPU가 쪼개 계산하므로, 매 레이어마다 GPU들이 부분 결과를 교환(all-reduce)해야 합니다. 통신이 계산의 길목마다 끼어드는 구조라 인터커넥트(NVLink) 성능이 곧 속도입니다. 파이프라인 방식은 통신이 레이어 경계에서 한 방향으로만 일어나니 단순하지만, 대신 라인을 채울 동시 요청이 없으면 웨이퍼들이 놀게 됩니다. 그래서 이 설계의 동시 처리 가능 요청 수는 전체 어텐션 웨이퍼들에 남겨 둔 KV 캐시 공간이 상한을 정합니다. 요청이 많아 라인이 꽉 차면 효율적이고, 한가하면 세계에서 가장 비싼 유휴 장비가 됩니다.

비용 감각: 웨이퍼 59장이면 랙 수십 개 규모의 초고가 시스템입니다. 같은 돈이면 GPU를 훨씬 많이 살 수 있고, 배칭을 극대화한 GPU 서빙이 토큰당 비용(처리량)에서는 보통 유리합니다. 이 설계가 파는 것은 처리량이 아니라 사용자당 속도(인터랙티브 레이턴시)입니다. "싸게 많이"와 "빠르게 하나"는 다른 상품이라는 걸 기억하세요.

6. 숫자 읽기 — 981 tok/s의 의미와 전제

그래서 실제로 얼마나 빠를까요? 블로그의 1,000~2,000+ tok/s는 설계 목표치지만, 참고할 수 있는 실측이 있습니다. Cerebras는 올해 조 단위 파라미터 오픈 모델 Kimi K2.6을 프로덕션 서빙하면서, 독립 벤치마크 기관 Artificial Analysis의 측정으로 출력 981 tok/s를 기록했습니다. Cerebras 발표 기준으로 다음으로 빠른 GPU 클라우드의 6.7배, 중간값 프로바이더의 23배입니다. 역산하면 당시 가장 빠른 GPU 클라우드가 약 146 tok/s, 중간값이 약 43 tok/s였다는 뜻입니다. 체감 비교로는 입력 10,000토큰·출력 500토큰짜리 코딩 요청이 Cerebras에서 5.6초, Moonshot 공식 엔드포인트에서 163.7초 걸렸다는 자사 측정도 공개했습니다(이쪽은 독립 검증이 아닌 자사 수치입니다).

이 숫자들을 공정하게 읽는 법도 함께 챙깁시다.

  • 981은 K2.6, 1,000~2,000+는 K3 설계 목표. 둘은 다른 모델입니다. K3(2.8T)가 실서빙에서 어느 수치를 찍는지는 지켜봐야 합니다.
  • 사용자당 속도이지 처리량이 아닙니다. GPU 클라우드는 배칭으로 전체 처리량과 토큰 단가에서 앞설 수 있습니다. 비교 축이 다릅니다.
  • 4-bit 가중치·8-bit KV는 설계 가정입니다. 양자화는 품질에 영향을 줄 수 있고, 프로덕션 설정이 어떤지는 블로그가 못 박지 않습니다. 양자화 포맷별 트레이드오프는 예전 글을 참고하세요. (Kimi K3는 애초에 MXFP4 양자화 인지 학습으로 배포돼 이 가정이 자연스러운 편입니다.)
  • HN 스레드의 회의론도 유효합니다. 금싸라기 SRAM에 KV 캐시를 두는 게 맞느냐(더 싼 DRAM으로 뺄 수 없느냐), 수요가 라인을 못 채우면 경제성이 무너지지 않느냐 같은 지적이 나왔습니다. 벤더 블로그는 가장 유리한 조명 아래의 사진이라는 걸 잊지 마세요.

7. 실전 — 내 워크로드의 '진짜 속도'를 재는 법

웨이퍼를 살 일은 없어도, 오늘 바로 가져갈 수 있는 실전 기술이 있습니다. 프로바이더가 광고하는 속도 말고, 내 워크로드에서의 속도를 직접 재는 것입니다. 요즘은 같은 오픈 모델을 수십 개 업체가 서빙하므로(OpenRouter 등에서 선택 가능), 이 측정 하나로 에이전트 체감 속도가 몇 배 달라질 수 있습니다. 볼 지표는 세 개입니다.

  • TTFT(Time To First Token) — 첫 토큰까지의 시간. 프리필 성능 + 큐 대기를 반영합니다. 챗봇 체감에 중요합니다.
  • 출력 tok/s — 첫 토큰 이후의 생성 속도. 디코드 성능, 즉 이 글 내내 다룬 그 병목입니다. 긴 출력·에이전트 루프에 중요합니다.
  • E2E(요청 완료까지 총 시간) — 결국 사용자가 기다리는 시간. 에이전트라면 "턴당 E2E × 턴 수"가 작업 시간입니다.

OpenAI 호환 API라면 스트리밍으로 셋 다 한 번에 잴 수 있습니다.

{{< highlight python >}} import time, httpx def measure(base_url: str, api_key: str, model: str, prompt: str): t0 = time.perf_counter() ttft, n_tokens = None, 0 with httpx.stream( "POST", f"{base_url}/chat/completions", headers={"Authorization": f"Bearer {api_key}"}, json={"model": model, "stream": True, "max_tokens": 500, "messages": [{"role": "user", "content": prompt}]}, timeout=120, ) as r: for line in r.iter_lines(): if not line.startswith("data: ") or line == "data: [DONE]": continue if ttft is None: ttft = time.perf_counter() - t0 # 첫 청크 도착 = TTFT n_tokens += 1 # 근사치: 청크 ≈ 토큰 e2e = time.perf_counter() - t0 decode_tps = n_tokens / (e2e - ttft) # 첫 토큰 이후 생성 속도 return {"ttft_s": round(ttft, 2), "e2e_s": round(e2e, 2), "output_tok_s": round(decode_tps, 1)} # 같은 모델을 서빙하는 프로바이더 2~3곳에, 실제 워크로드와 비슷한 # 프롬프트(짧은 질문 말고 실제 길이의 컨텍스트!)로 각 5회 이상 돌려 비교 {{< /highlight >}}

측정할 때는 꼭 실제 워크로드와 비슷한 입력 길이로 재세요. 10토큰짜리 인사말로 재면 프리필 비용이 안 보이고, 에이전트처럼 수만 토큰 컨텍스트를 보내는 워크로드의 병목을 놓칩니다. 직접 만들기 귀찮다면 Artificial Analysis가 프로바이더별 TTFT·출력 속도를 상시 측정해 공개하니, 1차 스크리닝은 거기서 하고 최종 결정만 자체 측정으로 하는 것도 좋은 전략입니다.

8. 흔한 실수 · 팁

  • 처리량(throughput)과 사용자당 속도를 혼동하기. "이 시스템은 초당 10만 토큰"이라는 말은 배치 전체 얘기일 수 있습니다. 내 요청 하나가 빠르다는 뜻이 아닙니다. 벤치마크를 볼 때 항상 "per user인가, aggregate인가"부터 확인하세요.
  • 속도를 품질로 착각하기. 981 tok/s는 Kimi K2.6을 빠르게 서빙한다는 뜻이지 더 똑똑하게 만드는 게 아닙니다. 다만 같은 시간에 더 많은 reasoning 토큰·더 많은 에이전트 턴을 돌릴 수 있으니, 속도가 간접적으로 결과 품질을 끌어올리는 경로는 있습니다.
  • 벤더 수치와 독립 검증을 구분하지 않기. 이 글에서도 981 tok/s(독립 측정)와 5.6초 vs 163.7초(자사 측정)는 신뢰 등급이 다릅니다. 글을 쓰거나 의사결정을 할 때 이 구분을 유지하는 습관이 생각보다 큰 차이를 만듭니다.
  • 양자화 설정을 안 보고 속도만 비교하기. 같은 모델이라도 프로바이더마다 FP8/4-bit 등 서빙 양자화가 다를 수 있고, 속도 차이의 일부는 거기서 옵니다. 속도 비교에는 품질 스팟 체크(동일 프롬프트 몇 개로 출력 비교)를 곁들이세요.
  • 에이전트 지연을 모델 탓만 하기. 턴당 E2E에는 프리필(컨텍스트 재전송)도 큽니다. 출력 속도를 아무리 올려도 매 턴 50만 토큰을 재프리필하면 느립니다. 프롬프트 캐싱과 이번 글의 디코드 속도는 둘 다 챙겨야 하는 별개의 축입니다.

9. 마무리 (TL;DR)

  • 이번 주 HN을 달군 Cerebras 블로그: 온칩 SRAM 44GB짜리 웨이퍼 스케일 칩(WSE-3 세대) 59장을 파이프라인으로 이어 2.8T 파라미터 Kimi K3를 1,000~2,000+ tok/s로 서빙하는 설계를 공개했습니다.
  • 근본 원리: 디코드는 메모리 대역폭에 묶입니다. 토큰 1개 = 활성 가중치 전부 읽기. 사용자당 속도 상한 ≈ 대역폭 ÷ 토큰당 읽을 바이트. WSE-3의 온칩 21PB/s는 H100 HBM(3.35TB/s)의 세 자리수 배입니다.
  • 배치의 핵심 산수: KV 캐시가 안 자라는 선형 어텐션(KDA) 69개 레이어는 웨이퍼당 2개(35장), KV 캐시가 자라는 전체 어텐션 24개 레이어는 웨이퍼당 1개(24장). 웨이퍼 사이는 활성값만 RDMA(~2µs/hop)로 건넙니다. 모델 아키텍처가 곧 서빙 비용입니다.
  • 실측 근거: Kimi K2.6을 981 tok/s로 서빙(Artificial Analysis 독립 측정, 당시 최고속 GPU 클라우드 대비 6.7배). 단, 이 설계가 파는 건 토큰 단가가 아니라 사용자당 속도이고, 동시성 상한은 KV 캐시 공간이 정합니다.
  • 오늘 가져갈 것: 프로바이더를 고를 때 TTFT · 출력 tok/s · E2E를 내 워크로드 길이의 프롬프트로 직접 재세요. 에이전트 루프는 직렬이라 출력 속도가 턴 수만큼 복리로 쌓입니다.
