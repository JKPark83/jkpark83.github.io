도입 — 이번 주 트렌딩은 온통 '토큰 절약'이었다

이번 주 GitHub 트렌딩을 열어 본 분이라면 묘한 기시감을 느꼈을 겁니다. 하루 스타 증가 상위권에 Caveman(+507★/일), context-mode(+256★/일), 에이전트 하네스 최적화 시스템 ECC(+897★/일)가 나란히 올라왔는데, 전부 하는 일이 같습니다. 코딩 에이전트가 쓰는 토큰을 줄이는 것입니다. 트렌드를 집계하는 쪽에서는 "에이전트 최적화, 특히 토큰 효율 도구에 커뮤니티의 관심이 폭발했다"고 요약했을 정도입니다.

이유는 짐작대로입니다. Claude Code나 Cursor로 긴 세션을 돌려 본 사람은 누구나 두 가지 벽에 부딪힙니다. 컨텍스트 윈도우가 금방 차서 세션이 압축(compaction)되거나 끊기고, 월말 청구서 혹은 사용량 한도가 생각보다 빨리 소진됩니다. 그러니 "도구 출력을 98% 줄여 준다", "읽는 것 전부를 압축해 준다"는 도구에 스타가 쏟아지는 게 당연합니다. 이들을 전부 묶어 한 번에 설치하는 6계층 '토큰 최적화 스택' 저장소까지 등장했습니다.

그런데 같은 시기에 찬물을 끼얹는 실측 연구도 화제가 됐습니다. 제목부터 도발적입니다 — "Token Reduction Is Not Cost Reduction(토큰 절감은 비용 절감이 아니다)". Claude Code에서 도구 출력 압축을 켜고 실제 과금 기준으로 측정해 보니, 도구 출력 토큰을 38.4% 줄인 가장 공격적인 설정에서 청구 비용이 오히려 6.8% 늘었다는 겁니다. 범인은 프롬프트 캐시(prompt cache)였습니다.

그래서 오늘은 이 두 흐름을 한 번에 다룹니다. 토큰이 실제로 어디서 새는지, 이번 주의 다이어트 도구들은 에이전트 루프의 어느 지점에 끼어드는지, 그리고 왜 "토큰 수"가 아니라 "성공률로 보정한 청구 비용"을 봐야 하는지까지입니다. 도구 이름은 바뀌어도 이 구조는 오래 갈 테니, 지도를 머리에 넣어 두면 두고두고 써먹을 수 있습니다.

배경 — 토큰은 어디서 새는가: 에이전트 한 턴 해부

먼저 기본 구조부터 확인합시다. LLM API는 상태가 없습니다(stateless). 에이전트가 모델을 호출할 때마다 시스템 프롬프트, 도구 정의, 지금까지의 대화 히스토리, 도구 실행 결과를 전부 다시 보냅니다. 턴이 쌓일수록 매 호출의 입력이 커지는, 일종의 토큰 복리 구조입니다.

그 입력 안에서 덩치가 가장 큰 것은 무엇일까요? 시스템 프롬프트나 도구 정의도 수천~수만 토큰을 차지하지만, 한 번 보내면 크기가 변하지 않습니다. 진짜 주범은 턴마다 새로 쌓이는 도구 출력(tool output)입니다. context-mode가 공개한 실측 예가 감을 잡기 좋습니다. 브라우저 자동화 도구 Playwright의 페이지 스냅샷 하나가 56KB, GitHub 이슈 20개를 API로 받아오면 59KB입니다. 토큰으로 환산하면 한 번의 도구 호출이 만~수만 토큰을 컨텍스트에 밀어 넣는 셈입니다. 에이전트가 파일을 읽고, 테스트를 돌리고, 로그를 확인하는 평범한 디버깅 세션에서 이런 호출이 수십 번 일어납니다.

문제는 비용만이 아닙니다. 예전에 컨텍스트 로트(context rot) 글에서 다뤘듯, 컨텍스트가 길어질수록 모델이 중요한 정보를 놓치는 품질 저하도 함께 옵니다. Anthropic도 컨텍스트 엔지니어링 가이드에서 "컨텍스트는 한계 효용이 체감하는 유한 자원"이라고 못 박았습니다. 그러니 토큰 다이어트는 비용 절감이자 품질 관리이기도 합니다. 방향 자체는 옳습니다. 문제는 어디서, 어떻게 줄이느냐입니다.

지도 — 루프의 어느 지점에 끼어드는가

이번 주 트렌딩에 오른 도구들은 겉보기에 비슷해 보이지만, 에이전트 루프의 서로 다른 지점에 끼어듭니다. 지도를 그려 보면 구분이 선명해집니다.

도구 해부 — Headroom · context-mode · Caveman

Headroom — "읽는 모든 것"을 타입별로 압축하는 프록시

세 도구 중 가장 체계적인 접근입니다. Headroom은 에이전트와 모델 사이에 앉아, 모델로 들어가는 도구 출력·로그·RAG 청크·파일·히스토리를 압축합니다. 집필 시점 기준 GitHub 스타 7.4만 개로, 이 분야의 사실상 기준점이 된 프로젝트입니다. 핵심 설계가 셋 있습니다.

  • 타입별 압축기 라우팅. ContentRouter가 들어온 내용의 타입을 감지해 맞는 압축기로 보냅니다. JSON 배열은 SmartCrusher가 반복 구조를 접고, 소스 코드는 AST(구문 트리)를 이해하는 CodeCompressor가 시그니처 중심으로 줄이고, 일반 텍스트는 에이전트 트레이스로 학습한 소형 모델이 요약합니다. "코드·로그·JSON은 각각 다르게 줄여야 한다"는 발상이 중요합니다.
  • 가역 압축(CCR). 원본은 로컬에 캐시해 두고, 압축본에는 참조를 남깁니다. 모델이 "그 부분 자세히 보여줘"라고 하면 원문을 되살릴 수 있습니다. 비가역 요약이 디버깅 정보를 날려 버리는 문제에 대한 답입니다.
  • 캐시 정렬(CacheAligner). 뒤에서 자세히 다루겠지만, 압축이 프롬프트 캐시를 깨지 않도록 이미 전송된 프리픽스는 바이트 단위로 보존하고 새 내용만 압축합니다.

자체 벤치마크 수치도 비교적 솔직한 편입니다. 코드 검색 결과 100건은 21% 절감에 그치지만 로그가 많은 장애 디버깅 시나리오는 57%까지 줄었고, GSM8K·SQuAD 같은 정답형 벤치마크에서 압축 후에도 정확도가 유지됐다고 보고합니다. "모든 상황에서 95% 절감" 같은 말보다 이런 분포가 현실적입니다.

context-mode — 출력을 컨텍스트에 넣지 말고 '검색하게' 하라

context-mode는 더 급진적입니다. 압축조차 하지 않고, 도구 출력을 아예 컨텍스트 밖에 격리합니다. 도구 실행 결과는 샌드박스에 저장되고, SQLite FTS5 전문 검색(BM25 랭킹)으로 색인됩니다. 에이전트는 315KB짜리 원본 대신 "검색해서 찾은 관련 조각 5.4KB"만 받습니다. 자체 표현으로 98% 절감입니다. 세션 메모리도 SQLite에 남겨, 컨텍스트가 압축으로 날아간 뒤에도 파일 수정·git 작업·에러 이력을 복구할 수 있게 했습니다.

어디서 많이 본 패턴이지요? MCP 코드 실행이나 재귀 언어 모델(RLM) 글에서 다룬 "컨텍스트에 다 넣지 말고, 필요한 것만 꺼내 쓰는 환경을 제공하라"는 철학의 도구판입니다. 한 가지 주의할 점은 플랫폼 의존성입니다. 훅(hook)으로 강제할 수 있는 Claude Code 같은 환경에서는 98% 수준을 내지만, 훅이 없는 플랫폼에서는 지시문으로 모델에게 부탁하는 수준이라 효과가 60%대로 떨어진다고 스스로 밝히고 있습니다. 라이선스도 ELv2라 상업적 재배포에는 제약이 있습니다.

Caveman — 모델의 '말투'를 압축한다

앞의 둘이 입력을 공략한다면, Caveman은 반대쪽, 모델이 생성하는 출력을 공략합니다. 이름 그대로 "원시인 말투"입니다 — 능동태, 20단어 이내 문장, 군더더기 제거를 스킬로 강제해 모델의 장황한 설명을 깎습니다. 중요한 건 보존 계약(preservation contract)입니다. 파일 경로, 줄 번호, 테스트 이름, 에러 타입, 수치, 코드 블록은 원문 그대로 유지하고 산문만 줄입니다. 생성된 출력은 다음 턴의 입력으로 다시 들어가므로, 출력 압축은 곧 이후 모든 턴의 입력 절감이기도 합니다. 전체 세션 기준 입력 토큰 33.2% 절감, 품질 저하 없음(A/B 테스트 p=0.82)이 자체 보고 수치입니다.

재미있는 건 생태계의 수렴입니다. Headroom 저장소에는 "Caveman 모드를 통합하자"는 이슈가 올라와 있고, 두 도구에 RTK·context-mode까지 얹어 여섯 계층으로 묶은 스택 저장소가 트렌딩에 올랐습니다. 입력·출력·셸·검색을 각각 다른 도구가 맡는, 말 그대로 '다이어트 스택'입니다.

함정 — 프롬프트 캐시 경제학, 토큰 ≠ 비용

여기까지 보면 당장 다 설치하고 싶어집니다. 그 전에 이번 주의 반전, PointFive의 실측 연구를 봐야 합니다. 이 연구는 Claude Code에서 도구 출력 절감 도구를 켜고 끄며 실제 과금 데이터로 짝지은 코딩 태스크를 비교했습니다. 결과는 제목 그대로입니다. 도구 출력 토큰 38.4%를 깎은 가장 공격적인 설정에서 청구 비용이 6.8% 늘었습니다. 이유는 두 가지입니다.

첫째, 입력 비용의 대부분은 이미 캐시 트래픽입니다. 프롬프트 캐싱 글에서 다뤘듯, Claude API 기준 캐시에서 읽는 토큰은 기본 입력 단가의 0.1배, 캐시에 새로 쓰는 토큰은 1.25배입니다. 장수명 에이전트 세션의 입력 대부분은 이미 0.1배짜리 캐시 읽기입니다. 그런데 압축 도구가 이미 캐시된 과거 히스토리를 건드리면 어떻게 될까요? 프롬프트 캐시는 바이트 단위 정확한 프리픽스 일치를 요구합니다. 프리픽스가 1바이트라도 달라지는 순간 캐시 미스가 나고, 그 지점부터 전체를 1.25배 단가로 다시 써야 합니다. 0.1배짜리 토큰을 아끼려다 1.25배짜리 재작성을 유발하면, 토큰 수는 줄어도 금액은 늘어납니다.

둘째, 압축은 에이전트의 행동 궤적을 바꿉니다. 요약된 로그에서 단서를 놓친 에이전트는 다시 검색하고, 다시 테스트를 돌리고, 턴을 더 씁니다. 연구진은 압축이 추가 검색·진단·재시도 턴을 유발해 국소적인 토큰 절감을 상쇄하는 사례를 관측했습니다. 턴 하나가 늘면 그 턴의 입력 전체(캐시 읽기라도 수십만 토큰)가 추가되니, 몇 KB 아낀 게 금방 역전됩니다.

오해는 말아야 합니다. 이 연구의 결론은 "다이어트 도구를 쓰지 말라"가 아니라 "토큰 수는 비용의 대리 지표로 부적합하니, 성공률로 보정한 종단 간(end-to-end) 비용으로 평가하라"입니다. 실제로 좋은 도구들은 이미 이 함정을 알고 설계돼 있습니다. Headroom의 CacheAligner와 live-zone 압축이 정확히 "동결된 프리픽스는 건드리지 않는다"는 원칙이고, context-mode처럼 애초에 큰 출력을 컨텍스트에 넣지 않는 접근은 처음부터 캐시에 쓸 것 자체를 줄입니다. 함정에 빠지는 건 주로 "히스토리를 소급해서 다듬는" 종류의 순진한 개입입니다.

실전 — 측정부터 시작하는 다이어트

다이어트의 철칙은 체중계부터 사는 겁니다. 도구를 깔기 전에, 지금 세션에서 토큰이 어디로 가는지부터 재 봅시다. Claude Code라면 /cost와 /context로 현재 세션의 사용량·컨텍스트 구성을 바로 볼 수 있습니다. API를 직접 쓴다면 응답의 usage 필드에 비용 구조가 전부 들어 있습니다.

{{< highlight python >}} # 에이전트 루프에서 턴마다 usage를 기록해 봅시다 resp = client.messages.create(model=MODEL, messages=history, tools=tools, max_tokens=4096) u = resp.usage log({ "input": u.input_tokens, # 캐시 밖에서 새로 읽은 입력 (1.0x 단가) "cache_write": u.cache_creation_input_tokens, # 캐시에 새로 쓴 토큰 (1.25x 단가!) "cache_read": u.cache_read_input_tokens, # 캐시에서 읽은 토큰 (0.1x 단가) "output": u.output_tokens, }) # 턴마다 cache_read가 꾸준히 크고 cache_write가 작아야 정상입니다. # 압축 도구를 켠 뒤 cache_write가 치솟는다면 → 프리픽스를 깨고 있다는 신호 {{< /highlight >}}

이 네 숫자에 단가를 곱한 합계가 진짜 비용입니다. 토큰 총량이 아니라 단가 가중 합이라는 점이 핵심입니다. 측정이 준비됐으면, 개입은 효과가 확실하고 부작용이 적은 순서로 하나씩 올립니다.

  1. 공짜 다이어트 먼저. 도구가 필요 없는 것부터입니다. 검색 결과 개수 제한(head_limit), 파일 부분 읽기, 테스트 출력의 실패 부분만 반환하기 같은 도구 설계 개선은 캐시를 깰 일도, 정보를 잃을 일도 없습니다. 도구 설계 글에서 다룬 "도구가 말을 아끼게 하라"가 그대로 적용됩니다.
  2. 새 출력만 줄이는 도구를 올립니다. 도구 출력 샌드박스(context-mode)나 캐시 인지 압축(Headroom)처럼 아직 캐시에 쓰이지 않은 내용만 건드리는 계층입니다. 설치는 간단합니다: {{< highlight bash >}} # Headroom: 에이전트 명령을 감싸면 끝 (프록시 모드) uv tool install --python 3.13 "headroom-ai[all]" headroom wrap claude # 이후 claude 실행 시 자동으로 압축 계층 통과 # Caveman: Claude Code 스킬로 설치 npx skills add JuliusBrussee/caveman -g # 세션에서 /caveman 으로 활성화 {{< /highlight >}}
  3. 켜기 전/후를 같은 태스크로 비교합니다. 비교 지표는 토큰이 아니라 ① 태스크 성공 여부 ② 턴 수 ③ 단가 가중 비용 셋입니다. 성공률이 떨어지면 재시도 비용까지 포함해야 하니, 실패한 시도의 비용도 버리지 말고 합산하세요. PointFive 연구가 제안하는 "성공률 보정 종단 비용" 관점입니다.
어느 도구부터? 세션 로그를 봤을 때 도구 출력(특히 브라우저·API 응답·테스트 로그)이 비대하면 context-mode류 샌드박스가, 다양한 타입의 입력이 고루 크면 Headroom이, 모델의 설명이 장황해 출력 토큰이 아프면 Caveman이 먼저입니다. 병목을 보고 고르는 것이지, 여섯 계층을 한 번에 올리는 게 목표가 아닙니다.

흔한 실수 · 팁

  • 토큰 수를 KPI로 삼는 것. 이번 글의 핵심입니다. "입력 토큰 40% 절감!"은 캐시 단가를 무시하면 무의미하고, 성공률 하락을 무시하면 유해합니다. 지표는 항상 성공률로 보정한 청구 비용으로 잡으세요.
  • 캐시 지표를 안 보고 압축을 켜는 것. 압축 도구 도입 전후로 cache_read/cache_write 비율을 꼭 비교하세요. cache_write가 늘었다면 그 도구는 프리픽스를 소급 수정하고 있는 겁니다.
  • 비가역 요약으로 디버깅 정보를 날리는 것. 스택 트레이스의 "잡음"처럼 보이는 줄에 단서가 있는 경우가 많습니다. 원문 복구 수단(Headroom의 CCR, context-mode의 검색)이 있는 도구를 고르고, 에러 타입·경로·줄 번호를 보존하는지(Caveman의 보존 계약 같은) 확인하세요.
  • 짧은 세션에도 무조건 끼얹는 것. Caveman은 규칙 주입으로 매 세션 약 1,000토큰의 고정 오버헤드가 있다고 스스로 밝힙니다. 몇 턴짜리 가벼운 세션에서는 절감분보다 오버헤드가 클 수 있습니다. 긴 세션, 도구 호출이 많은 세션이 주 무대입니다.
  • 자체 벤치마크 수치를 내 워크로드 수치로 믿는 것. Headroom조차 시나리오에 따라 21%와 57%로 효과가 3배 가까이 벌어집니다. "98% 절감"은 Playwright 스냅샷 같은 극단적 입력의 수치입니다. 반드시 자기 워크로드로 재측정하세요.
  • 라이선스 확인 생략. Headroom·Caveman은 Apache/MIT지만 context-mode는 ELv2입니다. 사내 도구에 묶어 재배포할 계획이라면 먼저 확인해야 합니다.

마무리 (TL;DR)

  • 이번 주 GitHub 트렌딩은 토큰 절약 도구의 주간이었습니다. Headroom(입력 압축 프록시), context-mode(도구 출력 샌드박스), Caveman(출력 말투 압축)이 각각 루프의 다른 길목을 맡고, 이를 묶은 '토큰 다이어트 스택'까지 등장했습니다.
  • 에이전트 비용의 주범은 턴마다 쌓여 매 호출 다시 전송되는 도구 출력입니다. Playwright 스냅샷 하나가 56KB, 이슈 20개가 59KB입니다.
  • 그러나 토큰 절감 ≠ 비용 절감입니다. PointFive 실측에서 도구 출력 토큰 38.4% 절감이 청구 비용 6.8% 증가로 끝났습니다. 입력 지출의 대부분은 0.1배 단가의 캐시 읽기인데, 순진한 압축이 프리픽스를 깨면 1.25배 단가의 캐시 재작성과 추가 턴을 유발하기 때문입니다.
  • 따라서 원칙은 셋입니다. ① 측정 먼저(usage의 cache_read/cache_write까지), ② 캐시에 이미 쓰인 프리픽스는 건드리지 않는 도구만(캐시 인지 압축, 샌드박스), ③ 평가는 토큰 수가 아니라 성공률로 보정한 단가 가중 비용으로.
  • 도구 이름은 내년이면 바뀔 수 있지만, "어디서 새는가 → 어느 길목에 개입하는가 → 캐시와 궤적에 어떤 부작용을 주는가"라는 사고 틀은 오래갑니다.
