1. 도입 — 에이전트는 말을 너무 많이 한다

리즈닝 모델 기반 에이전트의 청구서를 열어 본 적이 있다면 알 겁니다. 비용의 상당 부분이 사용자에게 보이지도 않는 생각 토큰(thinking tokens)에서 나옵니다. 지금의 에이전트는 검색 한 번, 코드 실행 한 번을 하기 전에 "먼저 A를 확인하고, 그다음 B를 비교해서…" 같은 추론 과정을 전부 텍스트로 써 내려가야 합니다. 그 텍스트는 토큰 단위로 과금되고, 디코딩은 순차적이라 토큰 수만큼 시간이 걸립니다. 추론 예산 관리에서 다뤘듯, 그래서 모든 API가 "얼마나 오래 생각할지"를 돈 주고 조절하는 손잡이를 팔게 됐습니다.

그런데 한 발 물러서서 보면 이상한 구조입니다. 생각을 꼭 사람이 읽는 언어로 디코딩해 가며 해야 할까요? 모델 내부에는 이미 hidden state라는 풍부한 연속 벡터 표현이 있는데, 매 스텝 그걸 어휘 하나로 눌러 담았다가(토큰 샘플링) 다시 임베딩으로 풀어내는 과정은 정보를 깎아 먹는 병목이기도 합니다.

10월 13일 arXiv에 올라온 Hybrid Reasoning Agents(Stanford·UIUC·Together AI, Jiaru Zou 외)는 이 질문에 실용적인 답을 내놨습니다. 생각은 latent 벡터 루프로, tool 호출과 답변은 텍스트로. 하나의 생성 안에서 두 모드를 오가는 HybridAgent는 11개 벤치마크 평균 +10.4%, 토큰 35.5~54.7% 절감, 비용 2.7~3.7배 절감을 보고했습니다(저자 보고치). 공개 직후 Hacker News에서 500점·236댓글을 받으며 프런트페이지에 올랐고, X에서는 elvis의 "Banger paper" 스레드가 돌며 "latent reasoning이 드디어 에이전트에 왔다"는 이야기가 한 주 내내 이어졌습니다. 코드와 모델도 MIT 라이선스로 공개됐습니다.

2. 배경 — latent reasoning 3분 복습: Coconut이 연 길

이 논문을 이해하려면 먼저 latent reasoning(잠재 공간 추론)이 뭔지 알아야 합니다. 출발점은 Meta FAIR의 Coconut(Chain of Continuous Thought, 2024년 12월 공개, COLM 2025 채택)입니다. 아이디어는 한 문장입니다. 트랜스포머가 다음 토큰을 만들 때 쓰는 마지막 레이어의 hidden state를, 토큰으로 디코딩하지 않고 그대로 다음 스텝의 입력 임베딩 자리에 되먹이는(feed back) 겁니다.

평소의 생성 루프는 "hidden state → 어휘 분포 → 토큰 샘플링 → 그 토큰의 임베딩이 다음 입력"입니다. Coconut은 가운데 두 단계를 건너뜁니다. 토큰이라는 이산적인 병목을 거치지 않으니, 하나의 '연속 생각(continuous thought)' 벡터가 여러 후보 경로를 동시에 품을 수 있습니다. Coconut 논문은 이 덕분에 모델이 한 경로에 성급하게 올인하는 대신 너비 우선 탐색(BFS)처럼 추론하는 패턴이 나타난다고 보고했고, 백트래킹이 많이 필요한 논리 퍼즐에서 텍스트 CoT보다 적은 '생각 스텝'으로 더 잘 풀었습니다. 애초에 CoT 토큰의 대부분은 추론이 아니라 문장을 자연스럽게 잇는 데 쓰인다는 게 이 계보의 공통 관찰입니다.

그런데 Coconut류 순수 latent 모델은 에이전트로 쓰기 어려웠습니다. 이유는 단순합니다. 에이전트는 바깥세상과 텍스트로 만납니다. 검색 API에 보낼 쿼리, 실행할 코드, 사용자에게 줄 답 — 전부 텍스트여야 합니다. 생각 전체를 latent로 바꿔 버리면 tool을 부를 방법이 없고, 밖에서 과정을 관찰할 수도 없으며, 소규모 과제를 넘어 학습을 안정시키기도 어려웠습니다. 그래서 latent reasoning은 2년 가까이 "흥미롭지만 실험실 안의 아이디어"에 머물렀습니다.

용어 정리: 이 글에서 latent mode는 "hidden state를 되먹이며 토큰 생성 없이 추론하는 구간", text mode는 "평소처럼 토큰을 하나씩 디코딩하는 구간"을 가리킵니다. HybridAgent의 '하이브리드'는 이 두 모드를 한 번의 생성 안에서 오간다는 뜻입니다. API 요금제 이름으로 쓰이는 '하이브리드 추론 모델'(생각 on/off 전환)과는 다른 개념이니 헷갈리지 마세요.

3. HybridAgent — 한 번의 생성 안에서 두 모드를 오가기

HybridAgent의 설계 원칙은 포스터 한 줄로 요약됩니다. "Think in latent space, act through text." 계획 세우기, 중간 결과 검토, 다음 행동 고르기 같은 내부 추론은 latent mode에서 벡터 루프로 처리하고, 외부에 영향을 주는 것 — tool 호출, 최종 답변 — 만 text mode로 생성합니다. 비유하자면 이렇습니다. 지금의 에이전트는 생각을 전부 소리 내어 말해야 하는 사람입니다. HybridAgent는 속으로 생각하다가 필요한 순간에만 입을 여는 사람입니다. 말하는 속도(토큰 디코딩)가 생각의 속도를 제한하지 않게 되는 겁니다.

모드 전환은 특별한 앵커 토큰(anchor token)으로 신호합니다. 모델이 <latent> 토큰을 생성하면 latent mode로 들어가고, 이후에는 토큰 샘플링 없이 hidden state가 직접 다음 입력이 되는 루프가 돕니다. 루프에서 나올 때는 반대로, 각 latent 스텝의 상태를 어휘 임베딩에 가장 가까운 토큰으로 읽어낸 값(readout)이 복귀 마커에 해당하면 text mode로 돌아옵니다. 즉 언제 생각을 시작하고 언제 입을 열지도 모델이 스스로 결정합니다 — 이것이 뒤에서 볼 RL 학습의 핵심 목표입니다.

4. HybridLink — 10M짜리 어댑터가 하는 일

"hidden state를 입력으로 되먹인다"는 말은 간단해 보이지만, 그대로 꽂으면 문제가 생깁니다. 마지막 레이어의 hidden state와 입력 임베딩은 같은 차원이라도 분포가 다른 공간이기 때문입니다. 입력 임베딩 공간은 어휘 테이블이 만드는 비교적 좁은 영역이고, 마지막 hidden state는 다음 토큰 예측에 맞게 늘어난 전혀 다른 통계를 가집니다. 분포가 어긋난 벡터를 입력 자리에 꽂으면 모델은 학습 때 본 적 없는 입력을 받게 됩니다.

HybridAgent는 이 간극을 HybridLink라는 작은 어댑터로 메웁니다. 구조는 소박합니다 — 선형 레이어 2개 사이에 GELU를 끼우고 잔차 연결(residual connection)을 더한, 약 1,000만(10M) 파라미터짜리 모듈입니다. 역할은 "마지막 레이어의 latent 생각을 입력 임베딩 공간의 언어로 번역"하는 것뿐입니다. 백본은 Qwen3-Base 4B/8B/14B를 그대로 쓰므로, 수십억 파라미터 모델에 10M짜리 부품 하나를 더해 새로운 추론 모드를 여는 셈입니다. 생성 루프를 의사 코드로 쓰면 이렇습니다.

{{< highlight python >}} # HybridAgent 생성 루프의 개념적 의사 코드 (실제 구현은 공식 repo 참고) emb = embed(prompt_tokens) while not done: hidden = transformer(emb) # 마지막 레이어 hidden state if mode == "text": token = sample(lm_head(hidden)) # 평소처럼 토큰 디코딩 if token == LATENT_ANCHOR: # 생성 → 생각 시작 mode = "latent" emb = append(emb, embed(token)) else: # latent mode — 샘플링도, 토큰도 없다 thought = hybrid_link(hidden) # 2×Linear+GELU+residual, ~10M 파라미터 if nearest_token(thought) == EXIT_MARKER: # 복귀 신호 감지 mode = "text" # 다시 입을 연다 (tool 호출/답변) emb = append(emb, thought) # 벡터를 그대로 다음 입력으로 {{< /highlight >}}

포인트는 두 모드가 같은 백본, 같은 KV 캐시, 같은 attention을 공유한다는 겁니다. latent 생각도 시퀀스의 한 자리를 차지하고 이후 스텝이 attention으로 참조합니다. 다른 점은 단 하나, 그 자리의 입력이 "어휘 테이블에서 온 임베딩"이냐 "HybridLink가 번역한 연속 벡터"냐입니다.

5. 멀티턴의 복병 — 대화 기록(transcript)으로 복원되지 않는 상태

여기까지는 단일 생성 이야기입니다. 에이전트는 tool 결과를 받아 다음 턴을 이어가야 하는데, 이 지점에서 지금까지의 에이전트 인프라가 당연하게 기대 온 가정 하나가 깨집니다. "세션의 전체 상태는 텍스트 대화 기록으로 복원할 수 있다"는 가정입니다.

지금의 LLM 서빙은 stateless API입니다. 매 요청에 전체 메시지 배열을 다시 보내면, 서버는 텍스트를 다시 토크나이즈해 (캐시가 깨졌다면) 처음부터 다시 계산할 수 있습니다. 텍스트가 곧 상태의 완전한 직렬화이기 때문입니다. 그런데 HybridAgent의 히스토리에는 토큰이 아닌 latent 벡터가 끼어 있습니다. 이 벡터들은 텍스트로 직렬화되지 않으므로, 대화 기록만 다시 보내서는 세션 상태를 복원할 수 없습니다. 그래서 논문은 텍스트·latent 생각·tool 결과를 모두 담는 working memory를 두고, 턴이 바뀌어도 attention 캐시(KV 캐시)를 버리지 않고 이어 쓰는 방식을 택했습니다. 상태가 서버에 '살아 있어야' 하는 겁니다.

저자들도 기존 스택이 이를 지원하지 않는다고 못 박습니다 — verl(RL 학습 프레임워크)과 vLLM은 멀티턴 하이브리드 생성을 직접 지원하지 않아서, 학습·추론 스택을 직접 확장해야 했습니다. 어제 다룬 캐시 엔지니어링(AKV)이 "stateless API 뒤에 stateful 캐시"라는 같은 긴장을 다뤘다는 점이 흥미롭습니다. 방향은 달라도 결론이 겹칩니다. 에이전트가 고도화될수록, '모든 상태는 텍스트'라는 전제가 서빙 인프라의 발목을 잡기 시작했다는 겁니다.

6. 학습 — HybridSFT로 적응시키고, HybridRL로 '언제'를 가르친다

백본 모델은 latent 입력을 받아 본 적이 없으니, 두 단계의 post-training이 필요합니다.

HybridSFT는 큐레이션한 하이브리드 궤적(텍스트와 latent 구간이 섞인 풀이 과정)으로 지도학습을 합니다. 단계가 셋으로 나뉘는 게 재미있는데 — 먼저 앵커 토큰이 낀 출력 포맷에 적응시키고, HybridLink를 통과한 벡터를 입력으로 받는 데 적응시키고, 마지막으로 self-conditioned 학습, 즉 남이 만들어 준 latent가 아니라 자기 자신이 직전에 만든 latent 생각 위에서 다음 스텝을 잇는 연습을 시킵니다. 추론 시점에는 자기 출력이 곧 자기 입력이 되므로, 이 마지막 단계가 없으면 학습과 추론의 분포가 어긋납니다.

HybridRL은 그 위에 강화학습을 얹어 '언제'를 가르칩니다. 과제를 끝까지 풀어 보는 롤아웃에서 좋은 결과로 이어진 모드 전환 패턴에 보상을 주는 식입니다. latent 구간은 샘플링이 없어 재현이 까다로운데, 논문은 학습 때 롤아웃을 정확히 재현(exact rollout replay)하는 장치를 넣었습니다. 공개된 RL 데이터셋은 수학 심화 추론과 에이전트 검색 두 축입니다. README 기준 SFT는 GPU 8~16장, RL은 32장을 권장하니 개인이 재학습할 규모는 아니지만, 파이프라인 전체가 코드·데이터와 함께 공개돼 있다는 점이 중요합니다.

7. 숫자로 보는 효과 — 그리고 '생각이 안 보인다'는 논쟁

저자 보고치를 정리하면 다음과 같습니다. 평가는 수학·과학·의학·검색·에이전트 추론에 걸친 11개 벤치마크, 3개 모델 스케일에서 진행됐고, 비교 대상은 프런티어 LLM 에이전트와 텍스트·latent 기반 프레임워크들입니다.

추론 속도1.8 ~ 2.6×디코딩 스텝 수 감소
비용2.7 ~ 3.7× 절감디코딩 연산 최대 ~72.9% 절감 추정
WebWalker (14B)49.5 vs 40.5같은 크기 텍스트 전용 RL 에이전트(ARPO) 대비

에이전트 검색 벤치마크에서 같은 백본·같은 크기의 텍스트 전용 RL 에이전트를 앞선 것이 핵심입니다. "latent는 싸지만 멍청하다"는 통념과 달리, 싸면서 점수도 올랐다는 주장이니까요. 다만 모든 벤치마크에서 이긴 건 아니고(커뮤니티 분석에 따르면 GAIA의 이득이 HLE 같은 최고 난도 벤치마크에서는 재현되지 않습니다), 검증은 4B~14B 스케일에 한정됩니다. 더 큰 모델에서도 성립하는지는 열린 질문입니다.

Hacker News에서 가장 뜨거웠던 쟁점은 성능이 아니라 관측 가능성이었습니다. 생각이 벡터로 숨으면, 우리가 에이전트 관측성에서 강조했던 "추론 과정을 읽고 디버깅한다"는 안전망이 약해집니다. 논문은 각 latent 스텝을 가장 가까운 토큰 임베딩으로 투영해 유사 텍스트(pseudo-text)로 읽어낼 수 있다고 답하고, repo에는 이를 HTML 리포트로 렌더링하는 interpretable_latent_mode까지 들어 있습니다. 하지만 비판자들은 이 투영이 벡터가 품은 정보 대부분을 버리는 근사치라고 지적합니다 — 벡터 하나가 여러 경로를 중첩해 담는 게 latent의 장점인데, 그걸 토큰 하나로 읽는 순간 중첩은 사라집니다. 모니터링으로 원치 않는 행동을 잡아야 하는 안전 관점에서 퇴보라는 우려와, "어차피 CoT 텍스트도 모델의 진짜 내부 과정이라는 보장은 없었고, latent 상태를 사후에 자연어로 설명하는 연구도 진전이 있다"는 반론이 맞섰습니다. 효율과 투명성의 트레이드오프 — 이 논쟁은 이제 시작입니다.

8. 실전 — 직접 돌려보기 & 지금 가져갈 교훈

모델(8B/14B)과 데이터셋이 모두 Hugging Face에 공개돼 있어, GPU가 있다면 바로 체험할 수 있습니다.

{{< highlight bash >}} # 설치 (Python 3.11 + conda) git clone https://github.com/togethercomputer/HybridAgent.git && cd HybridAgent conda create -n hybridagent python=3.11 -y && conda activate hybridagent pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128 pip install -r requirements.txt && pip install -e . cp .env.example .env # 검색 tool용 TAVILY_API_KEY 설정 # 배치 하이브리드 추론 python -m hybrid_inference.run_batch --model togethercomputer/HybridAgent-8B-Agentic \ --input examples/questions.jsonl --output outputs/results.jsonl --num_samples 4 # latent 생각을 유사 텍스트로 들여다보기 (HTML 리포트 생성) python -m interpretable_latent_mode --model togethercomputer/HybridAgent-14B-Agentic \ --question "How many trailing zeros does 100! have?" --output report.html {{< /highlight >}}

상용 API 위에서 에이전트를 만드는 입장이라면 당장 라우터를 갈아 끼울 일은 없습니다. 그래도 가져갈 교훈은 분명합니다.

  • 생각 토큰을 비용 항목으로 따로 집계하세요. 에이전트 토큰 경제학에서 봤듯 에이전트 비용 구조는 직관과 자주 어긋납니다. reasoning 토큰이 전체 출력 토큰의 몇 %인지부터 재 보면, latent reasoning이 어디서 왜 3배 절감을 만드는지 — 그리고 우리 워크로드에서 그 절감이 의미 있을지 — 가 보입니다.
  • '생각의 양'과 '말의 양'을 분리해 설계하세요. 지금 API에서도 적용되는 원칙입니다. 추론은 reasoning/thinking 파라미터로 조절하고, 중간 결과의 장황한 재서술 같은 불필요한 가시적 출력은 프롬프트와 구조화 출력으로 눌러 두세요. HybridAgent는 이 분리를 아키텍처 수준으로 밀어붙인 극단일 뿐입니다.
  • '상태 = 텍스트 transcript' 가정에 기대는 코드를 점검하세요. 로깅, 리플레이, 세션 이관, 장애 복구가 전부 "메시지 배열만 저장하면 된다"에 기대고 있다면, latent 상태든 서버 측 캐시 상태든 텍스트 밖의 상태가 등장하는 순간 함께 깨집니다. 이 가정이 코드 어디에 박혀 있는지 알아 두는 것만으로도 준비가 됩니다.

9. 흔한 실수 · 팁

  • "latent mode = 생각 생략"으로 오해하기. 생각을 안 하는 게 아니라, 생각의 출력 포맷을 바꾼 겁니다. latent 스텝도 한 스텝에 forward pass 한 번씩 연산을 씁니다. 줄어드는 건 디코딩할 토큰 수와 그에 비례한 과금·지연이지, 사고 과정 자체가 아닙니다.
  • 아무 모델에나 hidden state를 되먹이면 될 거라 기대하기. HybridLink 없이 꽂으면 입력 분포가 어긋나고, HybridSFT 없이 쓰면 모델이 latent 입력을 해석하지 못합니다. 이 기법은 "추론 트릭"이 아니라 어댑터 + 2단계 post-training이 한 몸인 패키지입니다.
  • 유사 텍스트 readout을 '진짜 생각'으로 읽기. nearest-token 투영은 디버깅용 근사치입니다. readout이 그럴듯해 보여도 벡터에는 다른 정보가 더 실려 있을 수 있습니다. 감사(audit)나 안전성 근거로 쓰기에는 아직 부족하다는 게 공개 논쟁의 요지입니다.
  • 기존 서빙 스택에 바로 올리려 하기. vLLM 등은 멀티턴 하이브리드 생성을 직접 지원하지 않습니다(저자들도 스택을 직접 확장했습니다). working memory가 요구하는 "세션 간 KV 캐시 유지"는 로드밸런싱·축출 정책과 충돌하는, 아직 풀리는 중인 시스템 문제입니다.
  • 벤치마크 평균만 보고 올인하기. +10.4%는 평균이고, 이득의 크기는 과제 유형에 따라 다릅니다. 최고 난도 벤치마크에서는 이득이 재현되지 않았다는 분석도 있으니, 도입을 검토한다면 반드시 자기 과제 분포에서 평가부터 하세요.

10. 마무리 (TL;DR)

  • 10/13 공개된 Hybrid Reasoning Agents(arXiv:2610.18861, Stanford·UIUC·Together AI)가 HN 500점·X 바이럴로 한 주를 달궜습니다. 요지: 생각은 latent 벡터 루프로, tool 호출·답변만 텍스트로.
  • 메커니즘: <latent> 앵커 토큰으로 latent mode에 진입하고, 마지막 레이어 hidden state를 HybridLink(2×Linear+GELU+residual, 약 10M 파라미터)로 입력 임베딩 공간에 번역해 되먹입니다. 생각 구간에는 토큰이 아예 없습니다.
  • 학습은 HybridSFT(포맷·어댑터·self-conditioned 적응) → HybridRL(언제 생각하고 언제 행동할지)의 2단계. Qwen3-Base 4B/8B/14B 기준 11개 벤치마크 평균 +10.4%, 토큰 −35.5~54.7%, 속도 1.8~2.6×, 비용 2.7~3.7× 절감(저자 보고치).
  • 대가도 있습니다: latent 상태는 텍스트 transcript로 복원되지 않아 stateless 서빙 가정이 깨지고(working memory + 세션 간 KV 캐시 유지 필요), 생각이 벡터로 숨어 관측 가능성 논쟁이 붙었습니다. nearest-token readout은 근사치일 뿐입니다.
  • 코드·모델·데이터셋 전부 공개(MIT, togethercomputer/HybridAgent). 상용 API 사용자의 교훈: 생각 토큰을 따로 집계하고, 생각의 양과 말의 양을 분리해 설계하고, '상태=텍스트' 가정에 기댄 코드를 점검해 둘 것.
