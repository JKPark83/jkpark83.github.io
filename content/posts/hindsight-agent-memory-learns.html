1. 도입 — 이번 주 GitHub 1위, 왜 하필 메모리인가

이번 주 GitHub 트렌딩 1위는 신형 모델도, 새 코딩 에이전트도 아니었습니다. vectorize-io/hindsight — 에이전트 메모리 시스템입니다. 9월 25일 하루에만 스타 1,668개가 붙으며 전체 트렌딩 1위에 올랐고, 26일에도 하루 2,400개 안팎을 더하며 1위를 지켰습니다. 25일 28,000개 수준이던 스타가 이 글을 쓰는 시점엔 37,000개를 넘어섰습니다.

타이밍이 흥미롭습니다. 최근 몇 주 실무자 커뮤니티의 화두는 "코딩 에이전트의 경쟁력은 이제 어떤 모델을 부르느냐가 아니라, 세션 사이에 무엇을 기억하느냐"라는 쪽으로 기울고 있습니다. 컨텍스트 윈도우는 계속 커지는데, 매 세션 처음부터 다시 시작하는 에이전트의 건망증은 그대로이기 때문입니다.

Hindsight의 구호는 이 지점을 정확히 찌릅니다. "기억하는(remember) 메모리가 아니라 학습하는(learn) 메모리". 대화를 임베딩해 두고 필요할 때 꺼내 주는 것만으로는 부족하고, 쌓인 사실을 스스로 정리해 믿음과 지식으로 승격시켜야 한다는 주장입니다. 이 글에서는 그 주장이 아키텍처로 어떻게 구현됐는지 — 네 개의 메모리 네트워크, retain·recall·reflect 세 연산, 그리고 메모리가 스스로 문서를 쓰는 knowledge pages까지 — 하나씩 뜯어봅니다. 마지막에는 "역대 최고 정확도" 같은 벤치마크 주장을 어떻게 걸러 읽어야 하는지도 다룹니다.

이 블로그에서 에이전트 메모리를 처음 접한다면 에이전트 메모리 기초 편을, 통합(consolidation) 연구 쪽 배경이 궁금하다면 메모리 통합과 substrate 선택 편을 먼저 읽으면 이 글이 더 잘 읽힙니다. 오늘 글은 그 개념들이 실제 오픈소스 제품에서 어떤 모습으로 조립됐는지에 집중합니다.

2. 배경 — '저장하는 메모리'는 어디서 막히나

에이전트에 장기 기억을 붙이는 가장 흔한 방법은 사실상 RAG(retrieval-augmented generation) 파이프라인의 재활용입니다. 대화가 끝나면 로그(또는 로그에서 추출한 사실 문장)를 임베딩해 벡터 DB에 넣고, 다음 세션에서 질문이 오면 유사한 조각을 top-k로 검색해 프롬프트에 끼워 넣습니다. Mem0 같은 대표적인 메모리 레이어의 기본 동작이 이 계열이고, 실제로 "지난번에 말한 내 알레르기가 뭐였지?" 같은 조회형 질문에는 잘 통합니다.

문제는 메모리가 쌓일수록 드러납니다. 세 가지가 특히 아픕니다.

  • 중복이 쌓입니다. "사용자는 Python을 선호한다"는 사실이 표현만 바뀌어 수십 번 저장됩니다. 검색 결과 top-k가 같은 얘기의 변주로 가득 차면, 정작 필요한 다른 정보가 밀려납니다.
  • 모순이 방치됩니다. 3월에는 "스타트업 A에 다닌다", 9월에는 "회사 B로 이직했다"가 둘 다 저장돼 있고, 어느 쪽이 현재인지 판단하는 일은 통째로 LLM에게 떠넘겨집니다.
  • 종합이 안 됩니다. "우리 팀 에러 처리 컨벤션이 뭐지?" 같은 질문의 답은 어느 한 조각에도 없습니다. 수십 개 세션에 흩어진 결정들을 요약·일반화해야 나오는 답인데, 검색은 조각을 가져올 뿐 조각을 합쳐 주지 않습니다.

사람의 기억은 이렇게 동작하지 않습니다. 우리는 경험을 원문 그대로 쌓아 두지 않고, 자는 동안·쉬는 동안 그것을 일반화된 지식과 믿음으로 통합합니다. "저장하는 메모리"와 "학습하는 메모리"의 차이가 바로 여기에 있고, Hindsight는 이 통합 과정을 시스템의 1급 시민으로 설계한 경우입니다.

3. 네 개의 메모리 네트워크 — 사실·경험·요약·믿음을 분리하다

Hindsight는 Vectorize가 2025년 12월 16일 MIT 라이선스로 공개한 오픈소스입니다. 설계 근거는 기술 보고서 "Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects"(Virginia Tech 연구진과 공동)에 정리돼 있습니다. 핵심 아이디어는 메모리를 한 덩어리 저장소가 아니라, 성격이 다른 네 개의 논리적 네트워크로 분리하는 것입니다.

네트워크담는 것예시
World (세계)에이전트 관점과 무관한 객관적 사실"Alice는 Google의 소프트웨어 엔지니어다"
Experience (경험)에이전트 자신의 행동·상호작용, 1인칭 기록"나는 어제 배포 스크립트 버그를 고쳐 줬다"
Observation (관찰)여러 사실을 통합해 만든 개체별 종합 요약"Alice는 인프라 자동화에 관심이 많고 Python을 주로 쓴다"
Opinion (의견)확신도(confidence)와 타임스탬프가 붙은, 시간에 따라 변하는 믿음"이 프로젝트는 테스트 커버리지가 부족하다 (확신도 0.8)"

왜 굳이 나눌까요? 성격이 다른 기억은 수명과 갱신 규칙이 다르기 때문입니다. 객관적 사실은 새 증거가 오면 교체되면 되고, 경험은 시간순 기록이라 덮어쓰면 안 되고, 의견은 증거가 쌓이면 확신도가 오르내려야 합니다. 이걸 한 벡터 DB에 뭉뚱그리면 "이직했다"는 새 사실이 옛 사실을 밀어내지 못하고 나란히 공존하는, 2절의 모순 문제가 그대로 재현됩니다. 인지과학에서 말하는 의미 기억·일화 기억 구분을 공학적으로 흉내 냈다고 보면 이해가 빠릅니다.

저장소 자체는 특별하지 않습니다. PostgreSQL + pgvector 위에 네 네트워크를 올리고, 벡터·키워드·그래프(개체와 시간 링크) 인덱스를 함께 유지합니다. 그리고 모든 데이터는 bank라는 격리 단위에 속합니다. bank 하나가 사용자 한 명, 에이전트 하나, 프로젝트 하나의 "뇌"이고, bank 사이에는 데이터가 새지 않습니다.

4. 세 가지 연산 — retain, recall, reflect

네트워크가 그릇이라면, 연산은 그 그릇을 다루는 동사입니다. Hindsight의 API는 딱 세 개의 동사로 요약됩니다.

retain — 원문이 아니라 사실을 저장한다

retain에 텍스트를 넘기면 원문이 그대로 저장되는 게 아닙니다. LLM이 텍스트에서 사실, 개체(entity), 개체 간 관계, 시간 정보를 추출하고 정규화된 표현으로 바꿔 네 네트워크에 나눠 적습니다. 여기서 첫 번째 트레이드오프가 나옵니다. 쓰기 한 번마다 LLM 호출이 들어가므로, 저장형 메모리보다 쓰기 비용이 비쌉니다. 대신 읽기 시점의 품질을 미리 사 두는 구조입니다.

recall — 네 갈래 검색을 합쳐 돌려준다

recall은 빠른 조회용입니다. 한 번의 호출로 네 가지 검색이 병렬로 돕니다: 의미 검색(벡터 유사도), 키워드 검색(BM25), 그래프 검색(개체·시간 링크 추적), 시간 필터링. 결과는 RRF(reciprocal rank fusion)로 합쳐 리랭킹합니다. 하이브리드 검색 + RRF는 2단계 검색에서 다룬 그 패턴인데, 여기에 그래프·시간 축이 추가된 형태입니다. "작년 3월에 Alice가 뭐라고 했지?" 같은 질문은 벡터 유사도만으로는 잘 안 잡히기 때문입니다.

reflect — 조회가 아니라 숙고

reflect가 Hindsight의 차별점입니다. 단순 조회로 답할 수 없는 질문 — "Alice에 대해 아는 걸 정리해 줘", "이 프로젝트의 위험 요소는?" — 을 받으면, 메모리를 넓게 모아 연결 짓고 종합해 답을 생성합니다. 이때 소스를 우선순위대로 뒤집니다: mental model → observation → 원시 사실 순서입니다.

mental model은 "bank에 대한 특정 질문의 상비(standing) 답변"입니다. 자주 물을 질문을 mental model로 등록해 두면 Hindsight가 reflect를 돌려 답을 저장해 두고, 새 기억이 쌓일 때마다 배경에서 그 답을 다시 고쳐 씁니다. 질문 시점에 매번 조각을 모아 요약하는 대신, 답을 미리 만들어 두고 계속 최신으로 유지하는 것 — 이게 "학습하는 메모리"라는 구호의 실체입니다.

5. knowledge pages — 메모리 뱅크가 스스로 쓰는 위키

올여름 0.9.0(2026년 8월 7일)에서 추가된 knowledge pages는 mental model을 한 단계 밀어붙인 기능입니다. knowledge page는 "bank가 자기 자신에 대해 쓰는 살아 있는 문서"로, 위키처럼 폴더로 조직되고 검색 가능합니다. 예를 들어 "우리 서비스의 에러 처리 컨벤션"이라는 페이지를 만들어 두면, 관련된 새 지식이 통합될 때마다 Hindsight가 문서를 통째로 재생성하는 게 아니라 해당 부분만 증분 편집합니다.

공식 문서의 비유가 좋습니다. knowledge page는 DB의 뷰(view)에 가깝습니다. 테이블(원시 기억)이 아니라, 이미 추출·중복 제거·모순 조정이 끝난 기억 위에 투영된 화면이라는 뜻입니다. AGENTS.md 같은 컨텍스트 파일을 사람이 손으로 관리해 본 팀이라면 이 기능이 무엇을 자동화하려는지 바로 감이 올 겁니다. 에이전트가 일하며 배운 것이 사람이 읽을 수 있는 문서로 계속 정리되는 것이니까요. hindsight fs라는 CLI로 이 페이지들을 파일시스템처럼 다룰 수도 있습니다.

릴리스 속도도 트렌딩의 배경입니다. 0.10.0(9월 14일), 0.10.1(9월 21일)이 연달아 나오면서 bank별 검색 토글, mental model 사용량 계측 같은 운영 기능이 계속 붙고 있습니다.

6. 숫자 읽기 — 벤치마크 결과와 걸러 읽는 법

Hindsight가 내세우는 대표 숫자는 장기 대화 메모리 벤치마크 LongMemEval 결과입니다. 기술 보고서 기준으로, 오픈소스 20B 모델(gpt-oss-20b)을 백본으로 쓴 Hindsight가 전체 정확도 83.6%를 기록했습니다. 같은 20B 모델에 대화 전체를 그대로 밀어 넣은 full-context 베이스라인이 39.0%였으니 +44.6%p이고, full-context GPT-4o(60.2%)보다도 높습니다. 더 강한 백본을 쓰면 91.4%까지 올라가는데, Vectorize는 이를 "90% 선을 처음 넘은 에이전트 메모리 시스템"이라고 홍보했습니다.

또 다른 장기 대화 벤치마크 LoCoMo에서 보고된 비교는 이렇습니다(기술 보고서의 overall 수치).

인상적인 숫자지만, 에이전트 메모리 분야의 벤치마크는 액면 그대로 믿으면 안 되는 대표적 영역입니다. 걸러 읽는 기준 세 가지를 챙기세요.

  • 전부 벤더가 직접 돌린 평가입니다. 어떤 reader 모델로 답을 만들고, 어떤 judge 모델·프롬프트로 채점하고, 검색 컨텍스트를 몇 토큰 넣는지는 벤더마다 다릅니다. 실제로 Mem0과 Zep은 서로의 LoCoMo 점수 산정을 두고 공개 설전을 벌인 전력이 있고, 위 표에서 Zep이 75.14%로 나온 것도 Zep 자체 보고(더 높음)와 다릅니다. 같은 벤치마크 이름 아래 서로 다른 실험이 섞여 있는 셈입니다.
  • LoCoMo 자체가 한계에 왔습니다. 대화 전체가 요즘 모델 컨텍스트 윈도우에 그냥 들어갈 만큼 짧아서, "다 밀어 넣기"로도 점수가 꽤 나옵니다. 메모리 아키텍처의 우열을 가리는 압력이 약해졌다는 뜻입니다.
  • 정확도만 축이 아닙니다. retain마다 LLM 호출이 들어가는 구조는 쓰기 지연·비용 축에서 불리할 수 있습니다. 여러분의 워크로드(쓰기:읽기 비율, 지연 요구)에서 직접 재기 전까지는 어떤 시스템도 "최고"가 아닙니다.

7. 실전 — 10분 만에 돌려 보기

Docker 하나로 전체 스택(pgvector 포함)이 뜹니다. LLM 제공자는 OpenAI·Anthropic·Gemini·Ollama 등 25개 이상을 지원하니 로컬 모델로도 시험할 수 있습니다.

{{< highlight bash >}} export OPENAI_API_KEY=sk-... docker run -it --pull always --name hindsight \ -p 8888:8888 -p 9999:9999 \ -e HINDSIGHT_API_LLM_API_KEY=$OPENAI_API_KEY \ -v hindsight-data:/home/hindsight/.pg0 \ ghcr.io/vectorize-io/hindsight:latest {{< /highlight >}}

Python 클라이언트로 세 동사를 그대로 써 봅니다.

{{< highlight python >}} from hindsight_client import Hindsight client = Hindsight(base_url="http://localhost:8888") # retain: 원문이 아니라 LLM이 추출한 사실·개체·관계·시간이 저장된다 client.retain( bank_id="proj-alpha", # bank = 프로젝트/사용자 단위로 격리된 '뇌' content="회고에서 결정: 에러는 도메인 예외 계층으로 감싸고 sentry로 보낸다", ) client.retain( bank_id="proj-alpha", content="9월 배포 장애의 원인은 재시도 로직이 멱등하지 않았던 것", ) # recall: 4갈래(벡터·BM25·그래프·시간) 검색 + RRF — 빠른 조회 hits = client.recall(bank_id="proj-alpha", query="배포 장애 원인이 뭐였지?") # reflect: mental model → observation → 원시 사실 순으로 종합 — 숙고형 질문 answer = client.reflect( bank_id="proj-alpha", query="이 프로젝트의 에러 처리 원칙을 신규 팀원에게 설명해 줘", ) {{< /highlight >}}

서버 없이 노트북에서 실험만 해 보고 싶다면 embedded 모드도 있습니다.

{{< highlight python >}} import os from hindsight import HindsightServer, HindsightClient # 프로세스 안에서 서버를 띄우는 embedded 모드 — 실험용 with HindsightServer( llm_provider="openai", llm_model="gpt-4-mini", llm_api_key=os.environ["OPENAI_API_KEY"], ) as server: client = HindsightClient(base_url=server.url) client.retain(bank_id="scratch", content="Alice는 Google에서 일한다") {{< /highlight >}}

설계 관점의 조언 하나: bank 경계를 먼저 정하세요. 사용자별 개인화 메모리라면 bank = 사용자, 코딩 에이전트의 프로젝트 지식이라면 bank = 리포지토리가 자연스럽습니다. 경계를 넓게 잡으면(예: 전사 공용 bank) 무관한 기억이 섞여 recall 품질이 떨어지고, 사용자 데이터 격리 요구와도 충돌합니다.

8. 흔한 실수 · 팁

  • 모든 턴을 retain하지 않기. retain은 호출마다 LLM 추출이 도는 비싼 쓰기입니다. 잡담까지 전부 넣으면 비용도 늘고 통합 파이프라인에 잡음이 쌓입니다. "결정·사실·선호가 새로 생긴 순간"에만 저장하는 게 기본기입니다.
  • recall과 reflect를 구분해 쓰기. 단순 조회에 reflect를 쓰면 지연과 비용을 낭비하고, 종합이 필요한 질문에 recall만 쓰면 조각만 받아 놓고 "메모리가 멍청하다"고 오해하게 됩니다. 자주 묻는 종합형 질문은 mental model로 등록해 사전 계산으로 돌리세요.
  • 벤치마크 1등 = 우리 서비스 최적, 이 아닙니다. 6절에서 봤듯 벤더 자체 평가는 reader/judge 설정에 민감합니다. 여러분의 실제 트래픽에서 뽑은 질문 20~30개로 작은 자체 평가를 만들어 Mem0·Zep·Hindsight를 같은 조건으로 돌려 보는 편이 훨씬 믿을 만합니다.
  • 메모리에 쓰는 것도 입력 검증 대상입니다. 통합을 거친 믿음은 이후 모든 세션에 영향을 주므로, 오염된 입력이 들어가면 피해가 지속됩니다. 메모리 포이즈닝 방어 편에서 다룬 쓰기 시 검증·출처(provenance) 관리가 학습형 메모리에서는 더 중요해집니다.
  • 지운 기억이 정말 지워졌는지 확인하기. 학습형 메모리는 원시 사실이 observation과 mental model로 파생됩니다. 사용자가 삭제를 요청했을 때 원본만 지우고 파생물이 남는 설계는 규정 준수(GDPR 등) 관점에서 사고입니다. 삭제 경로가 파생물까지 닿는지 직접 테스트하세요.
  • 어린 프로젝트라는 점을 감안하기. 첫 공개가 2025년 12월입니다. 스타 상승세와 별개로 API가 아직 빠르게 변합니다(0.9→0.10에서도 토크나이저 교체 같은 변경이 있었습니다). 핵심 서비스에 넣기 전에 마이그레이션 비용을 계산에 넣으세요.

9. 마무리 (TL;DR)

  • 이번 주 GitHub 트렌딩 1위 Hindsight(MIT, Vectorize)는 "기억하는 메모리가 아니라 학습하는 메모리"를 내건 오픈소스 에이전트 메모리 시스템입니다. 9월 25~26일 이틀 연속 1위, 사흘 새 스타 28k→37k.
  • 기존 저장형 메모리(임베딩 + top-k 검색)는 중복 누적·모순 방치·종합 불가라는 세 가지 벽에 부딪힙니다. Hindsight는 기억을 World/Experience/Observation/Opinion 네 네트워크로 분리하고, 배경 통합으로 사실을 지식과 믿음으로 승격시켜 이 벽을 넘으려 합니다.
  • API는 동사 세 개: retain(LLM 추출 저장), recall(벡터·BM25·그래프·시간 4갈래 + RRF), reflect(mental model → observation → 원시 사실 순 종합). 0.9.0의 knowledge pages는 bank가 스스로 유지하는 위키 문서입니다.
  • 보고된 성적은 LongMemEval 83.6%(20B 백본, full-context 동일 백본 39.0% 대비 +44.6%p, full-context GPT-4o 60.2% 상회), LoCoMo overall 83.18~89.61%. 단, 벤더 자체 평가이고 LoCoMo는 수명이 다해 간다는 비판이 있으니 자체 평가로 검증 후 채택하세요.
  • 트레이드오프의 본질: 저장형은 읽기 시점에 비용을 내고, 학습형은 쓰기·배경 작업 시점에 비용을 냅니다. 쓰기:읽기 비율과 지연 요구에 따라 답이 달라집니다.
