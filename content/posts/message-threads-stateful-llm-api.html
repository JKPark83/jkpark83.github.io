1. 도입 — 에이전트의 숨은 반복 작업

에이전트를 처음 만들어 본 개발자가 요금 청구서 다음으로 놀라는 지점이 있습니다. 매 턴, 지금까지의 대화 전체를 다시 보내야 한다는 사실입니다. 시스템 프롬프트, 도구 정의, 읽어 온 파일, 수십 번의 도구 호출 결과까지 — 턴이 거듭될수록 요청 JSON은 수 MB로 불어나고, 모델이 첫 글자를 뱉기까지의 대기도 조금씩 길어집니다. LLM API가 무상태(stateless)로 설계돼 있기 때문에 생기는, 에이전트 루프의 기본 체질입니다.

11월 2일 Anthropic이 이 체질에 손을 댔습니다. Messages API에 공개 베타로 추가된 message threads는 대화를 잠시 서버에 보관해 두고, 이후 요청에서는 새 메시지와 직전 응답의 id만 보내게 합니다. 공식 발표에 따르면 500k~1M 토큰짜리 요청에서 첫 토큰까지의 시간(TTFT, time to first token) 중앙값이 약 35% 줄었고, Claude Code 대부분 사용자에게는 이미 기본으로 켜져 있습니다. 모르는 사이에 이번 주부터 혜택을 받고 있었을 가능성이 높다는 뜻입니다.

흥미로운 건 속도 자체보다 설계입니다. OpenAI가 Responses API에서 previous_response_id로 먼저 간 길이기도 하고, "Claude에도 비슷한 게 없냐"는 질문은 1년 반 전부터 커뮤니티에 올라오던 단골 요청이었습니다. 그런데 두 회사의 답은 닮은 듯 다릅니다. 한쪽은 대화를 저장소로, 다른 쪽은 5분짜리 캐시로 설계했습니다. 이 차이를 이해하면 stateful LLM API를 쓸 때 뭘 조심해야 하는지가 그대로 보입니다.

2. 배경 — TTFT는 어디서 새는가

"토큰은 그대로 다 읽는데 왜 빨라지지?"가 이 기능의 첫 번째 퀴즈입니다. 풀려면 TTFT를 분해해 봐야 합니다. 요청을 보내고 첫 토큰이 도착할 때까지, 시간은 크게 세 군데서 쓰입니다.

  • ① 전송과 전처리 — 수 MB 요청 본문을 업로드하고, 서버가 JSON을 검증하고, 전체를 토크나이즈하는 비용. 대화가 길수록 정직하게 커집니다.
  • ② prefill — 모델이 입력 전체를 읽어 attention 상태(KV 캐시)를 만드는 연산. 입력 길이에 비례하는 가장 큰 덩어리지만, 프롬프트 캐싱이 받아 줍니다.
  • ③ decode — 첫 토큰을 실제로 생성하는 부분. 여기는 대화 길이와 무관합니다.

지금까지 에이전트 최적화는 주로 ②를 공략했습니다. 프롬프트 캐싱을 걸면 매 턴 반복되는 앞부분의 prefill 연산을 건너뛰고 과금도 기본 입력의 10% 수준으로 떨어집니다. 그런데 ①은 캐싱이 못 건드립니다. 캐시에 적중하려면 일단 전체 대화를 보내서 "앞부분이 같다"는 걸 증명해야 하기 때문입니다. 1M 토큰 대화라면 대략 수 MB의 JSON이 턴마다 클라이언트에서 서버로 올라가고, 서버는 그걸 턴마다 다시 파싱하고 토크나이즈합니다. 긴 에이전트 세션에서 TTFT가 턴을 거듭할수록 미끄러지듯 늘어나는 이유의 상당 부분이 여기입니다.

message threads가 지우는 게 바로 이 ①입니다. 대화 본문이 이미 서버에 있으니 업로드할 것도, 다시 검증·토크나이즈할 것도 새 턴 분량뿐입니다. 모델이 읽는 토큰 수는 한 글자도 줄지 않으므로 과금과 rate limit은 그대로입니다. 요금 절감 기능이 아니라 지연 절감 기능이라는 점, 처음에 정확히 박아 두는 게 좋습니다.

3. 동작 원리 — create, continue, 그리고 replay

API 표면은 단순합니다. 기존 Messages API 요청에 thread 파라미터 하나를 얹고, 모든 요청에 beta 헤더 message-threads-2026-08-12를 붙입니다. 상태는 세 가지 동작으로 굴러갑니다.

  • create — 첫 요청은 지금처럼 대화 전체를 system, tools와 함께 보내되 "thread": {"type": "create"}를 추가합니다. API는 Claude의 응답까지 포함한 대화를 응답 id 아래 보관합니다.
  • continue — 다음 턴부터는 새 메시지만 보내고 "thread": {"type": "continue", "previous_message_id": "직전 응답 id"}를 붙입니다. system과 tools는 빼고 보냅니다(스레드가 기억하고 있고, 보내면 400 에러). 매 응답의 id가 다음 턴의 연결 고리가 됩니다.
  • replay — 스레드는 best-effort입니다. 마지막 요청 후 5분이 지나면 만료되고, 늦어도 1시간 안에 삭제됩니다. 이어 갈 수 없게 되면 continue 요청이 404(thread_not_found)를 돌려주는데, 이때는 내 쪽 사본으로 대화 전체를 새 create 요청에 담아 다시 시작하면 됩니다.
{{< highlight bash >}} # 턴 1: 대화 전체 + thread create curl -sS https://api.anthropic.com/v1/messages \ -H "x-api-key: $ANTHROPIC_API_KEY" \ -H "anthropic-version: 2026-10-21" \ -H "anthropic-beta: message-threads-2026-08-12" \ -H "content-type: application/json" \ -d '{ "model": "claude-opus-5-5", "max_tokens": 1024, "cache_control": {"type": "ephemeral"}, "system": "너는 Acme의 지원 에이전트야.", "messages": [{"role": "user", "content": "주문 관련 질문이 있어요."}], "thread": {"type": "create"} }' # 턴 2: 새 메시지만. system/tools는 빼고, 직전 응답 id만 넘긴다 curl -sS https://api.anthropic.com/v1/messages \ -H "x-api-key: $ANTHROPIC_API_KEY" \ -H "anthropic-version: 2026-10-21" \ -H "anthropic-beta: message-threads-2026-08-12" \ -H "content-type: application/json" \ -d '{ "model": "claude-opus-5-5", "max_tokens": 1024, "cache_control": {"type": "ephemeral"}, "messages": [{"role": "user", "content": "일반 배송은 보통 며칠 걸리나요?"}], "thread": {"type": "continue", "previous_message_id": "'"$message_id"'"} }' {{< /highlight >}}

여기서 설계의 핵심 전제가 나옵니다. 대화의 원본(source of truth)은 끝까지 애플리케이션이 쥐고 있어야 합니다. 서버의 스레드는 언제 사라져도 이상하지 않은 임시 사본이고, 응답만 봐서는 "이번 턴이 서버에 저장됐는지"조차 알 수 없습니다. 다음 continue가 404로 돌아와야 비로소 알게 됩니다. 그래서 threads를 쓰는 코드는 처음부터 replay 경로를 함께 설계해야 합니다 — 이건 선택이 아니라 프로토콜의 일부입니다.

append-only라는 제약. 스레드는 덧붙이기만 됩니다. 이전 턴을 수정하거나, 중간에서 분기하거나, 히스토리를 요약으로 바꿔치기(compaction)하려면 전부 "수정된 대화 전체로 새 create"입니다. 각 응답 id는 한 번만 continue할 수 있어서, 같은 id로 두 번 이으면 thread_already_continued 에러가 납니다. 항상 가장 최근 응답 id에서 이어 가세요.

4. 규칙 — 턴마다 보낼 것과 빼야 할 것

"새 메시지만 보낸다"가 전부면 좋겠지만, 필드마다 취급이 다릅니다. 공식 문서는 세 그룹으로 정리합니다.

그룹필드규칙
create 전용 system, tools create에만 보냅니다. continue에 실으면(null로도) 400 에러.
고정(fixed) model, tool_choice, thinking, context_management, output_config, 최상위 cache_control, beta 헤더 조합 등 매 턴 같은 값으로 다시 보냅니다. 값이 달라지면 400 + thread_fingerprint_mismatch, 에러 메시지가 어긋난 필드를 짚어 줍니다.
자유 max_tokens, stop_sequences, stream, metadata, service_tier 등 턴마다 바꿔도 됩니다.

직관적으로 읽으면 이렇습니다. 스레드는 대화만 기억하는 게 아니라 "이 대화가 어떤 설정으로 진행 중인가"의 지문(fingerprint)도 기억합니다. 모델이나 thinking 설정이 중간에 바뀌면 보관된 대화의 의미가 달라질 수 있으니, 바꾸고 싶으면 새 스레드를 시작하라는 겁니다. 예외도 기억해 둘 만합니다 — MCP 서버 주소나 container id는 서버가 저장하지 않으므로 쓰는 턴마다 직접 보내야 하고, MCP 인증 토큰은 턴 사이에 갱신돼도 됩니다.

5. 프롬프트 캐싱과의 관계 — 겹치지 않고 포개진다

가장 많이 나올 오해가 "threads를 켰으니 캐싱은 필요 없겠네"입니다. 반대입니다. 스레드는 아무것도 캐싱해 주지 않습니다. 전송만 생략될 뿐, 캐시 브레이크포인트를 걸지 않으면 서버는 매 턴 대화 전체의 prefill을 다시 계산하고 요금도 전액 기본 단가로 매깁니다. 2절의 그림 그대로 — threads는 ①, 캐싱은 ②를 맡는 분업입니다.

그래서 실전 조합은 "둘 다"입니다. 가장 간단한 방법은 예제에 계속 등장한 최상위 cache_control입니다. 매 요청에 "cache_control": {"type": "ephemeral"}을 실으면 API가 그 턴 메시지의 마지막 블록에 브레이크포인트를 걸어 줘서, 턴마다 "이전 대화는 캐시에서 읽고, 새 턴은 캐시에 써 두는" 흐름이 완성됩니다. 과금은 평소 캐싱 규칙 그대로입니다 — 캐시 쓰기 1.25배(5분 TTL), 읽기는 기본 입력의 0.1배(최신 모델은 더 낮음).

브레이크포인트 4개 제한. thread가 붙은 요청은 cache_control 브레이크포인트를 최대 4개까지만 가질 수 있습니다(최상위 cache_control도 1개로 계산, create 때 system·tools에 건 것은 이후 모든 continue에서도 계속 계산됨). 넘치면 400 + thread_unsupported_request. 특히 replay로 전체 대화를 다시 보낼 때, 과거 메시지에 박아 뒀던 브레이크포인트를 그대로 두면 바로 이 제한에 걸립니다. replay 전에 옛 브레이크포인트를 걷어 내고 마지막 블록에만 남기세요. SDK 헬퍼는 이걸 알아서 해 줍니다.

참고로 이 블로그에서 다뤘던 캐시 엔지니어링(AKV)까지 포개 보면 레이어가 깔끔하게 나뉩니다. threads는 전송 계층(클라이언트↔서버), 프롬프트 캐싱은 prefill 연산·과금 계층, KV 캐시 관리와 compaction은 컨텍스트 내용 계층의 문제입니다. 서로 다른 층의 도구라서 충돌 없이 함께 쓸 수 있습니다 — 단, 서버 측 compaction 기능과 context editing 대부분은 threads와 아직 호환되지 않는다는 제약은 있습니다(아래 8절).

6. OpenAI와 비교 — 서버 상태의 두 가지 철학

서버가 대화를 기억하는 API 자체는 새롭지 않습니다. OpenAI Responses API는 store: true로 응답을 서버에 저장하고 previous_response_id로 이어 가는 모델을 먼저 상용화했고, 더 긴 수명이 필요하면 Conversations API로 대화 객체를 만들 수 있습니다. 그런데 설계 철학이 다릅니다.

Claude message threadsOpenAI Responses (previous_response_id)
상태의 성격 임시 캐시 — 메모리에만 보관, 디스크 기록 없음 저장소 — 저장된 응답은 기본 30일 보존
수명 마지막 요청 후 5분 만료, 최대 1시간 내 삭제 보존 기간 내 재사용 가능, API로 개별 삭제 가능
관리 API 없음 — list/read/delete 불가 있음 — 응답 조회·삭제, Conversations 객체
원본 책임 전적으로 클라이언트 (만료 시 replay 필수) 서버에 맡기는 설계도 가능
주 목적 전송·전처리 생략 → TTFT 절감 상태 관리 위임 + 멀티턴 편의성

한 줄로 줄이면, OpenAI는 "대화를 우리한테 맡겨 두라"에 가깝고 Anthropic은 "원본은 네가 들고 있어라, 우리는 왕복만 가볍게 해 주겠다"입니다. 그래서 Claude threads에는 조회·삭제 API가 아예 없고, 보관도 암호화된 메모리에서 최대 1시간입니다. 상태 관리를 위임받지 않겠다는 의도가 수명 정책에 그대로 드러납니다. 어느 쪽이 낫다기보다, 장애 모델이 다릅니다. 서버를 저장소로 쓰면 "서버의 대화가 진실인데 유실되면?"을 걱정해야 하고, 캐시로 쓰면 "만료는 일상이니 replay를 짜 두자"가 됩니다. 후자는 귀찮은 대신 명시적입니다.

7. 실전 — 도구 호출 루프에 thread 넣기

에이전트에서 threads의 진가는 도구 호출 루프에서 나옵니다. 루프의 매 반복이 "직전 응답의 tool_use에 tool_result로 답하는 continue 요청"이 되기 때문입니다. 404 replay까지 포함한 뼈대를 Python으로 직접 짜 보면 이렇습니다.

{{< highlight python >}} import anthropic client = anthropic.Anthropic() BETA = ["message-threads-2026-08-12"] BASE = dict( model="claude-opus-5-5", max_tokens=4096, cache_control={"type": "ephemeral"}, # 매 턴 캐시 읽기+쓰기 (5절) ) SYSTEM = "너는 저장소를 분석하는 코딩 에이전트야." TOOLS = [...] # 도구 정의 history = [] # 대화 원본은 항상 내가 보관 (source of truth) prev_id = None # 직전 응답 id = 스레드 연결 고리 def call(new_messages): global prev_id history.extend(new_messages) try: if prev_id is None: raise anthropic.NotFoundError # 첫 턴은 create로 resp = client.beta.messages.create( **BASE, messages=new_messages, thread={"type": "continue", "previous_message_id": prev_id}, betas=BETA) except anthropic.NotFoundError: # 스레드 만료/유실 → 내 사본 전체로 replay (새 create) # 주의: 과거 메시지에 cache_control 브레이크포인트가 있으면 제거 resp = client.beta.messages.create( **BASE, system=SYSTEM, tools=TOOLS, messages=history, thread={"type": "create"}, betas=BETA) prev_id = resp.id history.append({"role": "assistant", "content": resp.content}) return resp resp = call([{"role": "user", "content": "이 저장소의 테스트 구조를 분석해 줘."}]) while resp.stop_reason == "tool_use": results = run_tools(resp) # tool_use 블록 실행 resp = call([{"role": "user", "content": results}]) # tool_result로 continue print(resp.content) {{< /highlight >}}

그리고 사실, 위 코드를 직접 쓸 일은 많지 않습니다. 새 SDK에 들어온 thread 헬퍼가 create/continue 전환, beta 헤더, 404 replay, refusal 후 새 스레드 시작까지 다 해 주기 때문입니다. 대화 사본도 헬퍼가 메모리에 들고 있습니다.

{{< highlight python >}} thread = client.beta.messages.thread( model="claude-opus-5-5", max_tokens=4096, cache_control={"type": "ephemeral"}, system="너는 저장소를 분석하는 코딩 에이전트야.", ) first = thread.send({"role": "user", "content": "테스트 구조를 분석해 줘."}) second = thread.send({"role": "user", "content": "커버리지가 빈 곳은?"}) # 전체 대화가 필요하면: thread.messages {{< /highlight >}}

도구 루프까지 통째로 맡기고 싶으면 thread.tool_runner()를 쓰면 되고, SDK의 beta tool runner는 기본값부터 스레드를 사용합니다. Claude Code 사용자 대부분에게 이미 켜져 있다는 것과 같은 맥락입니다 — 이 기능은 "쓰러 가는" 기능이라기보다, 에이전트 스택의 기본 전송 방식으로 스며드는 중입니다.

8. 흔한 실수 · 팁

  • 서버 스레드를 원본으로 믿기. 가장 위험한 실수입니다. 응답은 "이번 턴이 저장됐는지" 말해 주지 않고, 스레드는 5분이면 사라집니다. 대화 사본 보관과 replay 경로는 첫날부터 코드에 넣으세요. 프로세스를 넘어 살아야 하는 대화라면 SDK 헬퍼의 메모리 사본만으로도 부족합니다 — 직접 영속화해야 합니다.
  • 404 코드 안 보고 replay하기. 존재하지 않는 모델명도 404를 돌려줍니다. error.details.error_code == "thread_not_found"를 확인하고 replay하세요. 거꾸로, replay 직후에도 404가 또 나면 그 대화는 서버가 보관하기 너무 클 수 있으니 thread 없이 보내는 폴백도 준비해 두세요(헬퍼의 unsupported_request_behavior="continue_unthreaded").
  • 스트리밍 중 성급한 continue. 응답 id는 message_start에서 일찍 도착하지만, continue는 message_stop을 받은 뒤에만 보내야 합니다. 먼저 보내면 404가 날 수 있습니다. 스트림이 중간에 끊겼다면 같은 continue를 재시도하되, thread_already_continued나 thread_continue_in_flight가 오면 서버가 이미 그 턴을 처리했을 수 있다는 뜻이니 전체 replay가 안전합니다.
  • 메시지 중복 전송. continue의 새 메시지를 서버는 기존 대화와 대조하지 않습니다. 이미 보낸 메시지를 또 보내면 대화에 두 번 들어가거나 에러가 납니다. "마지막으로 어디까지 보냈나"를 느슨하게 관리하면 미묘한 품질 저하로 돌아옵니다.
  • refusal 후 continue. stop_reason: "refusal"이 나온 스레드는 이어 가지 마세요. 거부된 턴이 서버 사본에 남아 있을 수 있고 continue로는 지울 수 없습니다. 문제의 턴을 빼거나 고친 대화로 새 create를 보내는 게 정석입니다(헬퍼는 자동 처리).
  • 지원 범위 착각. Message Batches, 토큰 카운팅, compaction, 대부분의 context editing은 thread와 함께 못 씁니다. ZDR(zero data retention)·HIPAA 조직은 대상 외입니다. 조직 정책이 섞인 프로덕션이라면 thread_unsupported_request를 받았을 때 thread 없이 재시도하는 폴백이 필수입니다.
  • "요금도 줄겠지"라는 기대. 다시 한번 — 토큰 사용량, 과금, rate limit 전부 그대로입니다. 비용을 줄이는 건 여전히 프롬프트 캐싱과 컨텍스트 다이어트의 몫입니다.

9. 마무리 (TL;DR)

  • 11월 2일 Anthropic이 Messages API에 message threads 공개 베타를 추가했습니다. 첫 요청에 대화 전체를 보내 스레드를 만들고(thread: create), 이후엔 새 메시지 + 직전 응답 id만 보냅니다(continue). beta 헤더는 message-threads-2026-08-12.
  • 효과는 TTFT 절감: 대화 전체의 업로드·검증·토크나이즈가 새 턴 분량으로 줄어, 500k~1M 토큰 요청에서 중앙값 약 35% 감소. 과금·rate limit은 불변 — 모델은 여전히 전체를 읽습니다.
  • 프롬프트 캐싱의 대체재가 아니라 세트입니다. threads는 전송 계층, 캐싱은 prefill 연산·과금 계층. 최상위 cache_control을 매 턴 실어 둘 다 챙기되, 브레이크포인트 4개 제한을 기억하세요.
  • 스레드는 5분 만료의 best-effort 캐시입니다. 원본은 항상 클라이언트가 보관하고, thread_not_found(404)면 전체 대화로 새 create를 보내는 replay가 정상 흐름입니다. append-only라 수정·분기·요약은 전부 새 스레드.
  • OpenAI previous_response_id가 "대화를 서버 저장소에 위임"이라면, Claude threads는 "원본은 클라이언트, 서버는 왕복 최적화만". 장애 모델이 달라지는 설계 차이입니다.
  • SDK thread 헬퍼와 beta tool runner가 create/continue/replay를 대신 처리하고, Claude Code 대부분 사용자에겐 이미 기본 적용 — 에이전트 스택의 기본 전송 방식이 되는 중입니다.
