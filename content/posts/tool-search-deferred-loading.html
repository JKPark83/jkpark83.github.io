1. 왜 지금 '도구가 너무 많다'가 화제인가

2026년 에이전트 개발의 기본기는 MCP(Model Context Protocol) 서버를 붙여 도구를 늘리는 것입니다. GitHub, Slack, Sentry, 사내 API… 붙일수록 에이전트가 할 수 있는 일이 늘어나니 당연히 좋아 보이죠. 그런데 어느 순간부터 이상해집니다. 응답이 느려지고, 토큰 청구서가 커지고, 무엇보다 멀쩡하던 에이전트가 엉뚱한 도구를 고르기 시작합니다.

이건 개별 버그가 아니라 구조적인 문제입니다. 그래서 올 한 해 내내 "도구를 늘릴수록 에이전트가 나빠진다(more tools make your agent worse)"라는 제목의 글이 실무 커뮤니티에 반복해서 올라왔습니다. 최근에는 처방까지 표준으로 자리잡는 분위기입니다. Anthropic이 Tool Search와 지연 로딩(deferred loading)을 API·Claude Code에 정식 기능으로 올렸고, 이제는 다른 프레임워크들도 같은 기능을 따라 붙이려고 이슈를 여는 중입니다(예: Google python-genai #2185, Pydantic AI harness #40). Red Hat은 Tool RAG 라이브러리 ToolScope를 오픈소스로 냈고, 2026년 7월 28일 확정된 MCP 최신 스펙도 도구 목록을 캐시 가능하게 만드는 등 "많은 도구를 어떻게 싸게 다룰까"를 정면으로 건드립니다.

결론부터 말하면 처방은 하나로 수렴합니다. 도구를 전부 미리 올리지 말고, 필요할 때 찾아서 그때 불러오기. 검색으로 말이죠. 왜 이게 필요한지부터 차근차근 봅시다.

용어 정리. 이 글의 '도구(tool)'는 모델이 호출할 수 있는 함수 하나를 뜻합니다(예: get_weather). 'MCP'는 도구를 표준 방식으로 에이전트에 꽂아 주는 프로토콜이고요. 'Tool Search'는 도구를 미리 다 올리지 않고 검색해서 쓰는 기법, 'defer_loading(지연 로딩)'은 그걸 켜는 실제 설정값입니다.

2. 배경 — 도구 정의(tool definition)와 tool calling 복습

모델이 도구를 쓰려면, 먼저 그 도구가 무엇이고 어떻게 부르는지를 알아야 합니다. 그 설명서가 도구 정의(tool definition)입니다. 이름, 한 줄 설명, 그리고 인자 스키마(어떤 파라미터를 어떤 타입으로 받는지)로 이뤄집니다. 아래가 도구 하나의 정의입니다.

{{< highlight json >}} { "name": "get_weather", "description": "특정 위치의 현재 날씨를 조회한다", "input_schema": { "type": "object", "properties": { "location": { "type": "string" }, "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] } }, "required": ["location"] } } {{< /highlight >}}

핵심은 이겁니다. 이 정의는 매 요청마다 시스템 프롬프트 앞부분에 통째로 들어갑니다. 모델은 매번 "내가 쓸 수 있는 도구는 이것들이고, 각각 이렇게 생겼다"를 처음부터 다시 읽는 셈이죠. 대화가 이어져도 마찬가지입니다 — 도구 목록은 상태를 기억하지 않으니 요청마다 다시 실립니다.

도구가 3~5개일 땐 아무 문제가 없습니다. 정의 몇 개는 수백 토큰이면 끝이니까요. 문제는 MCP 서버를 여럿 붙여 도구가 수십~수백 개로 불어날 때 시작됩니다. 뷔페에 비유하면 이렇습니다. 요리 3개짜리 식당이면 메뉴판을 통째로 봐도 됩니다. 그런데 요리가 500개라면? 주문할 때마다 500쪽짜리 메뉴판 전체를 다시 펼쳐 드는 건 낭비이고, 그 두께 앞에서 정작 뭘 시킬지 헷갈리기 시작합니다.

3. 도구 세금의 두 얼굴: 컨텍스트 잠식 + 선택 정확도 붕괴

도구를 다 미리 올릴 때 내는 비용을 도구 세금(tool tax)이라고 부릅니다. 이 세금은 두 가지 방식으로 청구됩니다.

① 컨텍스트 예산 잠식. 도구 정의가 컨텍스트 창을 차지하는 만큼, 정작 대화·검색 결과·추론에 쓸 공간이 줄어듭니다. Anthropic 문서의 예시를 볼까요. GitHub·Slack·Sentry·Grafana·Splunk 다섯 서버를 붙이면, 모델이 일을 하기도 전에 도구 정의만으로 약 5만 5천(55k) 토큰이 소비됩니다. 심한 경우 서버 세 개(도구 40개 남짓)만으로 컨텍스트의 70% 이상을 도구 설명이 차지했다는 실무 사례도 보고됐습니다. 게다가 이 비용은 매 요청마다 반복됩니다.

② 선택 정확도 붕괴. 더 무서운 쪽입니다. 도구가 많아지면 서로 비슷한 도구가 뒤섞이고, 모델이 "이 상황엔 어떤 도구가 맞지?"를 헷갈립니다. Anthropic 문서는 도구가 30~50개를 넘어가면 올바른 도구를 고르는 정확도가 떨어지기 시작한다고 못 박습니다. 토큰만 낭비하는 게 아니라 실제로 일을 더 못하게 되는 겁니다.

실제로 Anthropic 자체 평가에서, 대규모 도구 라이브러리를 다룰 때 Tool Search를 켜자 정확도가 Opus 4는 49%→74%, Opus 4.5는 79.5%→88.1%로 올라갔습니다. 도구를 '줄여서'가 아니라 '필요한 것만 보여 줘서' 더 잘하게 된 겁니다.

4. 해법의 핵심: 미리 다 올리지 말고 필요할 때 찾아 쓴다

처방의 아이디어는 놀랄 만큼 단순합니다. 500쪽 메뉴판을 손님 테이블에 통째로 올려 두는 대신, 웨이터 한 명(검색 도구)을 둡니다. 손님이 "매운 국물 요리 뭐 있어요?"라고 물으면, 웨이터가 주방 카탈로그를 뒤져 관련 요리 서너 개만 들고 옵니다. 테이블(컨텍스트)은 깨끗하게 비어 있고, 손님은 딱 필요한 선택지만 보게 되죠.

이걸 just-in-time(필요한 순간에) 도구 로딩이라고 부릅니다. 컨텍스트에 처음 올라오는 건 '검색 도구' 하나(와 자주 쓰는 핵심 도구 몇 개)뿐입니다. 나머지 수백 개의 정의는 대기 상태로 숨겨 둡니다. 모델이 특정 도구가 필요해지면 그때 검색을 날리고, 매칭된 3~5개만 컨텍스트로 펼쳐집니다.

5. Anthropic Tool Search 뜯어보기 (defer_loading)

이제 실제 구현을 봅시다. Anthropic API에서 Tool Search를 켜는 방법은 딱 두 가지 재료로 이뤄집니다.

  • 검색 도구를 tools 배열에 추가한다. 두 종류가 있습니다.
    • tool_search_tool_regex_20251119 — 모델이 정규식(Python re.search) 패턴으로 검색(예: "github.*issue"). 패턴 최대 200자.
    • tool_search_tool_bm25_20251119 — 모델이 자연어 질의로 검색(예: "깃허브 이슈 만들기"). 최대 500자.
  • 평소에 숨길 도구엔 "defer_loading": true를 붙인다.
{{< highlight python >}} import anthropic client = anthropic.Anthropic() tools = [ # ① 검색 도구 자체는 절대 defer하지 않는다 (숨기면 아무것도 못 찾는다) {"type": "tool_search_tool_regex_20251119", "name": "tool_search"}, # ② 매 요청 쓰는 핵심 도구 3~5개는 그냥 올려 둔다 (검색 없이 바로 호출) {"name": "get_weather", "description": "특정 위치의 날씨를 조회", "input_schema": {"type": "object", "properties": {"location": {"type": "string"}}, "required": ["location"]}}, # ③ 나머지 수백 개는 defer_loading: True — 필요할 때 검색으로 불러온다 {"name": "github_create_issue", "description": "GitHub 저장소에 이슈를 생성", "input_schema": {"type": "object", "properties": {"repo": {"type": "string"}, "title": {"type": "string"}}, "required": ["repo", "title"]}, "defer_loading": True}, # ← 이 한 줄이 핵심 # ... github_*, slack_*, sentry_* 도구 수백 개 더 (전부 defer_loading: True) ] resp = client.messages.create( model="claude-opus-4-5-20251101", max_tokens=2048, messages=[{"role": "user", "content": "이 레포에 버그 이슈 하나 열어줘"}], tools=tools, ) {{< /highlight >}}

흐름은 이렇게 흘러갑니다. 처음 모델의 컨텍스트에는 검색 도구와 핵심 도구 몇 개만 보입니다. 사용자가 "이슈 열어줘"라고 하면, 모델은 github.*issue 같은 패턴으로 검색을 날립니다. API가 서버에서 카탈로그를 뒤져 매칭 도구를 tool_reference 블록으로 돌려주고(기본 최대 5개), 그걸 자동으로 전체 정의로 펼쳐 모델에게 보여 줍니다. 그제서야 모델이 github_create_issue를 실제로 호출하죠.

가장 헷갈리는 지점. defer_loading은 요청 페이로드가 아니라 모델의 컨텍스트를 제어합니다. 즉 모든 도구의 전체 정의는 매 요청마다 그대로 tools 배열에 담아 보내야 합니다(서버가 검색·확장할 때 필요하니까요). defer_loading: true가 하는 일은 "이건 모델 눈에는 검색으로 찾기 전까지 숨겨 둬"입니다. 네트워크로 보내는 양이 아니라, 모델이 읽는 양이 줄어드는 겁니다.

절감 효과는 큽니다. Anthropic 문서 기준 도구 정의 토큰을 보통 85% 이상 줄이고, 요청당 실제로 필요한 3~5개만 올라옵니다. 보도된 내부 테스트에서는 약 134k 토큰이 약 5k로 떨어진 사례도 있습니다. 중요한 건 prompt caching이 깨지지 않는다는 점입니다 — 숨긴 도구는 시스템 프롬프트 앞부분(prefix)에서 빠지고, 검색으로 찾은 도구는 대화 흐름 안쪽에 tool_reference로 덧붙기 때문에 캐시된 prefix는 그대로 유지됩니다.

MCP를 쓴다면. 도구를 MCP 서버에서 가져오는 경우엔 개별 도구마다 defer_loading을 달지 않습니다. mcp_toolset의 default_config에 한 번 걸어 서버 전체를 지연 로딩으로 돌리거나, 필요한 도구만 개별 configs로 지정합니다. 서버 단위로 켜고 끈다고 기억하세요.

6. 직접 검색 굴리기: Tool RAG(RAG-MCP)와 '결과 세금'

정규식·BM25 검색이 아쉬울 때가 있습니다. "환불 처리"라고 물었는데 도구 이름은 issue_credit_note라면, 키워드가 안 겹쳐 못 찾을 수 있죠. 이럴 땐 의미 기반 검색이 낫습니다. 도구 설명을 임베딩(embedding, 의미를 담은 벡터)으로 인덱싱해 두고, 사용자 요청과 의미가 가까운 도구를 뽑는 방식입니다. 이걸 Tool RAG라고 부릅니다 — 지식 조각 대신 도구를 검색하는 RAG인 셈이죠.

이 아이디어는 학계에서도 같은 처방으로 나왔습니다. RAG-MCP 논문(arXiv:2505.03275)은 도구 설명을 외부 인덱스에 넣어 질문마다 관련 도구만 검색해 프롬프트에 넣었더니, 프롬프트 토큰을 50% 넘게 줄이면서 도구 선택 정확도가 13.62%→43.13%로 3배 넘게 뛰었다고 보고합니다. Anthropic API에서도 이런 커스텀 검색을 꽂을 수 있습니다. 직접 만든 검색 도구가 결과로 tool_reference만 돌려주면, 나머지(전체 정의로 펼치기)는 API가 알아서 해 줍니다.

{{< highlight python >}} # Tool RAG: 검색을 정규식 대신 '임베딩 유사도'로 직접 굴린다. def my_tool_search(query: str) -> list[str]: q = embed(query) # 사용자 요청을 벡터로 hits = vector_db.search(q, top_k=5) # 도구 설명 임베딩과 유사도 검색 return [h.tool_name for h in hits] # 상위 5개 '도구 이름'만 # 모델이 내 커스텀 검색 도구를 호출하면, tool_result에 tool_reference로 응답한다. tool_result = { "type": "tool_result", "tool_use_id": call_id, "content": [ {"type": "tool_reference", "tool_name": name} # ← 전체 정의로 자동 확장 for name in my_tool_search(user_query) ], } # 주의: 참조된 도구는 top-level tools 배열에 (보통 defer_loading: True로) 반드시 존재해야 한다. {{< /highlight >}}

여기까지는 '정의 세금'(도구 스키마가 컨텍스트를 먹는 문제)을 줄이는 이야기였습니다. 그런데 세금이 하나 더 있습니다 — '결과 세금'입니다. 도구를 20번 호출하면 그 20번의 중간 결과가 전부 컨텍스트로 쏟아져 들어옵니다. 이걸 줄이는 게 programmatic tool calling입니다. 모델이 도구를 한 번씩 부르는 대신, 코드 실행 샌드박스 안에서 코드를 짜서 도구들을 프로그램처럼 호출하고, 필터링까지 끝낸 최종 결과만 컨텍스트로 돌려보냅니다. Anthropic 평가에서 웹 리서치 벤치마크(BrowseComp·DeepSearchQA) 기준 성능은 평균 11% 오르고 입력 토큰은 24% 줄었습니다. 정리하면 — Tool Search는 정의 세금을, programmatic tool calling은 결과 세금을 줄입니다. 둘은 함께 쓸 수 있습니다.

7. 언제 켜고, 언제 끄면 안 되나

좋은 기술도 상황을 가립니다. Tool Search는 도구가 많을 때 빛나고, 적을 땐 오히려 군더더기입니다.

Anthropic 문서가 제시하는 기준을 그대로 옮기면 이렇습니다. 켜라 — 도구가 10개 이상이거나, 정의가 10k 토큰을 넘거나, 도구가 늘수록 정확도가 떨어지거나, MCP 서버를 여러 개(200개 이상) 합칠 때. 끄는 게 낫다 — 도구가 10개 미만이거나, 매 요청 모든 도구를 다 쓰거나, 정의가 아주 작을 때. 참고로 defer_loading이 붙는 도구는 최대 1만 개까지 지원합니다.

8. 흔한 실수 · 팁

함정 1 — 검색 도구까지 defer해 버리기. 모든 도구에 defer_loading: true를 걸면 검색 도구마저 숨겨져, "적어도 하나는 defer가 아니어야 한다"는 400 에러가 납니다. 검색 도구는 항상 열어 두세요.

함정 2 — 검색에 안 걸리는 이름·설명. 검색은 도구의 이름·설명·인자 이름·인자 설명을 훑습니다. 이름이 do_thing_42처럼 의미가 없으면 아무 패턴에도 안 걸립니다. 서비스별로 github_, slack_처럼 일관된 접두사를 붙이고, 설명에 사용자가 쓸 법한 키워드(예: "환불", "청구")를 넣어 검색 가능성(discoverability)을 높이세요.

함정 3 — 자주 쓰는 도구까지 숨기기. 매 턴 쓰는 도구를 defer하면, 쓸 때마다 검색 왕복이 한 번씩 더 들어가 되레 느려집니다. 핵심 3~5개는 열어 두고 나머지를 숨기세요.

팁 1 — 캐시 breakpoint는 열린 도구에. defer_loading: true인 도구엔 cache_control을 같이 걸 수 없습니다(400). 캐시 지점은 defer하지 않은 도구에 두세요. 앞서 봤듯 지연 로딩 자체는 prefix를 안 건드리므로 prompt caching과 잘 어울립니다.

팁 2 — 시스템 프롬프트에 '카테고리 지도'를 주기. "Slack·GitHub·Jira 관련 도구를 검색할 수 있다"처럼 어떤 부류가 있는지 한 줄 알려 주면, 모델이 검색을 더 정확히 시작합니다. 모델이 실제로 무엇을 검색해 찾는지 로그로 지켜보며 설명을 다듬는 것도 좋습니다.

팁 3 — 매칭 0개는 에러가 아니다. 검색이 아무것도 못 찾으면 빈 결과가 돌아올 뿐(예외 아님)입니다. 이때 모델이 다른 패턴으로 다시 검색하도록 설계하고, 정말 없는 기능이면 "그 도구는 없다"고 답하게 하세요.

9. 마무리 (TL;DR)

  • 도구를 많이 붙일수록 에이전트가 나빠질 수 있다. 모델은 매 요청마다 모든 도구 정의를 통째로 읽기 때문이다 — 이게 '도구 세금'이다.
  • 세금은 두 갈래로 청구된다. ① 컨텍스트 잠식(서버 5개면 일 시작 전부터 ~55k 토큰), ② 선택 정확도 붕괴(도구 30~50개 초과 시 급락).
  • 처방은 하나로 수렴한다 — just-in-time 로딩. 전부 미리 올리지 말고, 검색 도구 하나만 두고 필요할 때 3~5개만 불러온다.
  • Anthropic Tool Search = defer_loading: true + 검색 도구(regex/BM25). 정의 토큰을 보통 85%+ 절감하고, 전체 정의는 여전히 요청에 담아 보내되 모델 눈에서만 숨긴다. prompt caching도 유지된다.
  • 키워드가 안 맞으면 Tool RAG. 임베딩으로 의미 검색해 tool_reference로 돌려주면 된다. RAG-MCP 논문은 토큰 50%↓·선택 정확도 13.62%→43.13%를 보고했다.
  • '정의 세금'과 '결과 세금'은 다르다. Tool Search는 정의를, programmatic tool calling은 도구 실행의 중간 결과를 줄인다. 함께 쓸 수 있다.
  • 다만 도구가 10개 미만이면 켜지 마라. 검색 왕복만 늘 뿐이다. 켜는 기준: 10개+, 정의 10k 토큰+, MCP 서버 다수.
