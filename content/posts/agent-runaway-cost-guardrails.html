도입 — 한 줄 프롬프트가 $78,000이 되기까지

지난주 Hacker News에서 가장 뜨거웠던 AI 글은 모델 발표가 아니라 청구서였습니다. 한 사용자가 올린 보고에 따르면, 지난 7월 10일 OpenAI Codex에 "특정 모듈의 UX/UI를 검증해 달라"는 평범한 태스크 하나를 맡겼는데, 이 태스크가 자식 에이전트 826개를 스스로 띄우고 약 $78,000어치 토큰을 태운 뒤, 무엇을 했는지에 대한 상세 기록까지 지워 버렸다는 것입니다. 결과물은 없었습니다. 이 글은 9월 26일 HN에 올라와 그 주 AI 글 중 최고 점수를 기록했습니다.

그리고 이틀 뒤인 9월 28일, NVIDIA가 Open Agent Safety Platform을 발표합니다. 요지는 "에이전트는 스스로를 단속하지 못하니, 인프라가 단속해야 한다"였고, 핵심 부품은 에이전트가 손댈 수 없는 별도 칩(DPU) 위에서 돌아가는 와치독(watchdog) Sentry였습니다. 같은 주에 터진 두 사건이 정확히 같은 방향을 가리키고 있는 셈입니다.

이번 글의 주제는 그 방향, 즉 예산 가드레일(budget guardrail) 엔지니어링입니다. 에이전트의 지출 한도는 보안 경계만큼 중요한 설계 대상인데, 대부분의 에이전트 코드에는 아예 없습니다. $78,000 사건을 해부해 실패 지점을 찾고, 루프 내부부터 하드웨어까지 4계층으로 한도를 집행하는 방법을 코드와 함께 정리합니다.

💡 이 블로그에서 다룬 에이전트 토큰 이코노믹스가 "청구서를 제대로 읽고 평상시 비용을 낮추는 법"이었다면, 이번 글은 "비정상 폭주를 구조적으로 차단하는 법"입니다. 요금 최적화와 폭주 차단은 다른 문제입니다 — 전자는 평균을, 후자는 꼬리(tail)를 다룹니다.

배경 — 에이전트 비용에는 왜 상한이 없는가

일반 웹 서비스에서 요청 하나의 비용에는 자연스러운 상한이 있습니다. 요청이 오면 정해진 코드가 돌고 응답하면 끝이죠. 반면 에이전트는 스스로 다음 일을 만들어 내는 프로그램입니다. 루프를 한 바퀴 더 돌지, 서브에이전트를 몇 개 띄울지, 어떤 모델로 띄울지를 실행 중에 결정합니다. 그래서 에이전트 한 번 실행의 비용은 대략 세 항의 곱으로 움직입니다.

비용 ≈ 턴 수 × 분기 수 × 토큰 단가

  • 턴 수 — 루프가 돌 때마다 지금까지의 히스토리를 다시 보내므로, 턴이 늘면 토큰은 대략 제곱(O(N²))으로 늘어납니다. 종료 조건이 허술하면 이 항은 무한대입니다.
  • 분기 수 — 서브에이전트 스폰(spawn)은 곱셈입니다. 부모 하나가 자식 10개를 띄우고 자식이 또 10개를 띄우면 두 단계 만에 100배입니다. 826개도 산술적으로 전혀 멀지 않습니다.
  • 토큰 단가 — 어떤 모델·어떤 추론 등급(reasoning tier)으로 실행되느냐에 따라 같은 토큰 수라도 비용이 수십 배 차이 납니다. 이 선택이 런타임에 바뀔 수 있다면 단가도 변수입니다.

이게 이론만의 이야기가 아니라는 건 측정 결과가 있습니다. 올여름 공개된 논문 When Agents Do Not Stop(arXiv:2607.01641)은 "종료 조건 없이 LLM 호출·툴 호출·에이전트 실행을 반복 유발하는 피드백 경로"를 무한 에이전트 루프(Infinite Agentic Loop, IAL)로 정의하고, 정적 분석 도구 IAL-Scan으로 실제 에이전트 저장소 6,549개를 훑었습니다. 결과는 47개 프로젝트에서 확인된 IAL 결함 68건. 흔한 버그 유형이라 부르기에 충분한 숫자입니다. 프레임워크들이 max_turns 같은 노브를 기본 탑재하는 이유이기도 합니다.

사건 해부 — 실패 지점 4가지

⚠️ 아래 수치는 당사자가 공개한 사용자 보고 기준이며, 글을 쓰는 시점까지 OpenAI의 공식 확인이나 환불 여부는 알려지지 않았습니다. 수치의 정확성과 별개로, 이 사건이 드러낸 구조적 공백은 어떤 에이전트 스택에도 그대로 존재할 수 있습니다 — 그 공백이 이번 글의 재료입니다.

보고된 내용을 타임라인으로 펼치면 이렇습니다. 루트 태스크는 GPT-5.5 / 추론 등급 Medium으로 시작했습니다. 그런데 이 태스크가 만든 자식 826개는 전부 GPT-5.6 Sol / Ultra — 사용자가 승인한 적 없는 상위 모델, 최상위 추론 등급으로 기록됐습니다. 그중 104개 자식 태스크는 루트와 똑같은 초기 메시지를 그대로 복제했고, 에이전트 역할(agent_role)이나 경로(agent_path) 기록이 없었으며, 이 부분집합의 로컬 토큰 카운터 합계만 약 1,479억(147.9B) 토큰이었습니다. 전체 실행 흔적은 메타데이터만 남은 스레드 2,550개. 상세 히스토리는 삭제된 상태였고, 지원 티켓은 2주간 사람에게 닿지 못했습니다.

엔지니어링 관점에서 이 사건은 서로 다른 네 가지 가드레일이 동시에 없었음을 보여 줍니다.

  1. 스폰 한도 부재 — 태스크 하나가 자식을 몇 개까지, 몇 단계 깊이까지 만들 수 있는지 제한이 없었습니다. 같은 초기 메시지를 복제한 104개는 fork 버그가 증폭기로 작동했을 가능성을 시사합니다. 버그는 늘 생깁니다. 문제는 버그가 "한도 없는 곱셈기"를 만났다는 것입니다.
  2. 단가 드리프트(drift) — 부모는 Medium, 자식은 전부 Ultra. 실행 주체가 모델과 추론 등급을 바꿀 수 있는데 이를 고정하거나 검증하는 장치가 없으면, "토큰 수"만 세는 예산 계산은 무의미해집니다. 실제로 이 무렵 Codex 커뮤니티에는 상위 추론 등급 위임 시 토큰 소비가 급증한다는 보고(openai/codex#41817)와 Ultra 등급의 추론 예산 트레이드오프를 다룬 실무자 분석이 이미 있었습니다.
  3. 실시간 미터링 부재 — 사용자는 폭주를 청구 단계에서야 알았습니다. 클라이언트 쪽 토큰 카운터와 서버 쪽 과금 원장(ledger)이 따로 놀면, 폭주는 "진행 중에 끊는 것"이 아니라 "끝나고 발견하는 것"이 됩니다.
  4. 감사 추적(audit trail) 부재 — 2,550개 스레드의 상세 기록이 사라져 사후 분석 자체가 불가능했습니다. 무엇이 잘못됐는지 모르면 재발 방지도 못 하고, 과금이 정당한지 다툴 근거도 없습니다.

4계층 예산 가드레일

네 가지 공백을 한 방에 메우는 단일 장치는 없습니다. 각 공백마다 집행 지점이 다르기 때문입니다. 안쪽(루프)에서 바깥쪽(하드웨어)으로, 겹겹이 쌓는 수밖에 없습니다.

L1 — 루프 내부: 공짜 노브부터 켜기

프레임워크가 주는 종료 한도는 가장 싼 보험입니다. 기본값과 초과 시 동작까지 알아 두세요.

단, 턴 한도는 깊이 방향만 막습니다. $78,000 사건의 주범인 너비 방향(스폰 폭발)은 별도 한도가 필요합니다 — "한 런에서 서브에이전트는 최대 N개, 깊이는 최대 D단계" 같은 규칙을 스폰 함수 자체에 박아야 합니다. 그리고 턴 수는 비용의 대리 지표일 뿐이라는 점도 기억하세요. 컨텍스트가 큰 턴 하나가 작은 턴 100개보다 비쌀 수 있으니, 진짜 예산은 토큰·달러로 세야 합니다.

L2 — 하네스: 모든 호출이 지나가는 요금소

핵심 아이디어는 툴 호출 컨트롤 플레인과 같습니다. 에이전트가 "모델을 부르는 길"과 "자식을 낳는 길"을 하나로 모으고, 그 길목에서 예산을 집행하는 겁니다. 여기서 할 일은 네 가지입니다.

  • 런 예산 — 실행(run) 하나에 달러 상한을 정하고, 모든 API 응답의 usage 필드를 합산해 누적 비용을 추적합니다. 상한 도달 시 즉시 중단.
  • 예산 상속 — 서브에이전트를 띄울 때 부모 예산의 일부를 떼어 줍니다. 자식이 아무리 많아져도 합계는 루트 예산을 넘지 못하게 되죠. 스폰 폭발을 "개수 제한"이 아니라 "보존 법칙"으로 막는 방법입니다.
  • 모델 allowlist — 이 런에서 쓸 수 있는 모델·추론 등급을 명시하고, 목록 밖 요청은 거부합니다. 단가 드리프트 차단.
  • 킬 스위치 + 감사 로그 — 사람이 밖에서 당길 수 있는 중단 장치, 그리고 하네스가 직접 남기는 호출 기록. 에이전트가 지울 수 없는 곳(append-only)에 씁니다.

L3 — 플랫폼: 계정 수준의 마지노선

하네스에 버그가 있어도(결국 같은 코드베이스입니다) 플랫폼 한도는 남습니다. 두 가지를 구분하는 게 중요합니다.

  • OpenAI — 지출 한도 가이드 기준으로 지출 알림(spend alert)은 통지만 할 뿐 트래픽을 막지 않고, 하드 지출 한도(hard spend limit)만 추적 지출이 설정액에 닿으면 트래픽을 차단합니다. 알림만 켜 놓고 한도를 걸었다고 착각하는 게 가장 흔한 사고 경로입니다.
  • Anthropic — 요금 한도 문서 기준으로 사용량 티어마다 월 지출 상한이 걸려 있고(Start $500 / Build $1,000 / Scale $200,000), 상한 도달 시 enforced_spend_limit_reached 코드가 붙은 429를 돌려줍니다. 그 아래로 조직이 직접 더 낮은 한도를 설정할 수 있고, 워크스페이스 단위로 지출·속도 한도를 따로 걸 수 있습니다. 에이전트 워크로드를 전용 워크스페이스로 분리하면 "에이전트가 미쳐도 프로덕션 API는 산다"는 격벽이 생깁니다. 단, 기본(default) 워크스페이스에는 한도를 못 겁니다 — 에이전트를 기본 워크스페이스에서 돌리지 마세요.

관측 쪽에는 시차가 있다는 걸 알아야 합니다. Anthropic의 Usage & Cost Admin API는 사용량을 1분 버킷까지 제공하지만 데이터 반영은 보통 요청 완료 후 5분 안팎(더 늦을 수도 있음)이고, 달러 단위 비용 리포트는 일(1d) 단위뿐입니다. 즉 "즉시 차단"은 플랫폼 한도와 클라이언트 계측의 몫이고, 플랫폼 사용량 API는 알림과 대사(reconciliation)용입니다.

L4 — 인프라: 에이전트 손이 닿지 않는 와치독

9월 28일 발표된 NVIDIA Open Agent Safety Platform은 이 계층의 모양을 보여 줍니다. 구성은 두 부품입니다. OpenShell은 오픈소스 런타임으로, 에이전트마다 샌드박스를 만들어 접근 가능한 파일·네트워크·툴·자격 증명을 운영자가 명시하고 실행 중에 검증·강제합니다. Sentry는 BlueField-4 DPU(네트워크 카드에 달린 별도 프로세서) 위에서 돌아가는 와치독으로, 호스트와 분리된 보안 도메인에서 에이전트를 감시하다가 경계를 벗어나면 밀리초 단위로 격리·중지합니다. 호스트가 통째로 오염돼도 감시는 계속된다는 게 요점입니다. 플랫폼은 Linux Foundation 산하 Open Secure AI Alliance로 거버넌스가 넘어갔고, Anthropic·Microsoft·JPMorganChase 등 120개 이상 조직이 참여를 발표했습니다.

주니어 입장에서 DPU까지 갈 일은 당분간 없겠지만, 설계 원칙은 오늘부터 쓸 수 있습니다. 집행 지점을 에이전트와 같은 프로세스에 두지 말 것. 킬 스위치 파일을 에이전트가 쓰기 권한 없는 경로에 두는 것, 예산 집행을 별도 프록시 프로세스에서 하는 것, 모두 같은 원칙의 저렴한 버전입니다.

실전 — BudgetGuard 직접 만들기

L2 하네스 계층의 최소 구현을 만들어 봅시다. 요구 사항은 네 가지입니다 — 런 예산, 예산 상속, 스폰 한도, 킬 스위치. 의도적으로 특정 프레임워크에 묶지 않은 순수 Python입니다.

{{< highlight python >}} import json, os, time, threading # 모델별 단가표 — 반드시 공식 요금 페이지에서 현재 값을 확인해 채우세요. # (단가를 코드에 박는 이유: '모를 모델 = 호출 불가' allowlist를 겸하게 하려고) PRICE_PER_MTOK = { # "model-id": {"input": X, "cache_read": Y, "output": Z}, # USD / 1M tokens } class BudgetExceeded(Exception): pass class SpawnLimitExceeded(Exception): pass class BudgetGuard: def __init__(self, budget_usd, depth=0, max_depth=2, max_children=5, kill_file="/etc/agent/KILL"): self.budget = budget_usd # 이 런(또는 서브런)에 허용된 달러 상한 self.spent = 0.0 self.depth, self.max_depth = depth, max_depth self.children, self.max_children = 0, max_children self.kill_file = kill_file # 에이전트가 쓰기 권한 없는 경로에! self._lock = threading.Lock() def _cost(self, model, usage): p = PRICE_PER_MTOK[model] # 단가표에 없는 모델이면 KeyError → 호출 차단 return (usage.input_tokens * p["input"] + usage.cache_read_input_tokens * p["cache_read"] + usage.output_tokens * p["output"]) / 1e6 def charge(self, model, usage): """모든 모델 호출 직후 반드시 호출. usage는 API 응답의 usage 필드.""" with self._lock: self.spent += self._cost(model, usage) self._audit(model, usage) # append-only 감사 로그 if os.path.exists(self.kill_file): # 사람이 밖에서 당기는 킬 스위치 raise BudgetExceeded("kill switch engaged") if self.spent >= self.budget: raise BudgetExceeded(f"${self.spent:.2f} / ${self.budget:.2f}") def spawn(self, share=0.25): """서브에이전트용 가드 생성 — 부모 예산을 떼어 주는 '보존 법칙'.""" with self._lock: if self.depth >= self.max_depth: raise SpawnLimitExceeded(f"depth {self.depth}") if self.children >= self.max_children: raise SpawnLimitExceeded(f"children {self.children}") child_budget = (self.budget - self.spent) * share self.budget -= child_budget # 부모 몫에서 차감 → 합계는 불변 self.children += 1 return BudgetGuard(child_budget, self.depth + 1, self.max_depth, self.max_children, self.kill_file) def _audit(self, model, usage): with open("/var/log/agent/usage.jsonl", "a") as f: # 에이전트 쓰기 불가 경로 f.write(json.dumps({"ts": time.time(), "model": model, "depth": self.depth, "spent": round(self.spent, 4)}) + "\n") {{< /highlight >}}

에이전트 루프에서는 모델 호출마다 guard.charge(model, resp.usage)를 부르고, 서브에이전트를 띄울 때는 guard.spawn()이 돌려준 자식 가드를 넘겨주면 됩니다. 이 구조에서 $78,000 사건의 시나리오를 대입해 보면 — 자식 826개는 max_children에서 끊기고, 설령 스폰 코드에 버그가 있어도 자식 예산의 합이 루트 예산을 넘을 수 없으며, 단가표에 없는 모델로의 드리프트는 KeyError로 차단되고, 감사 로그는 에이전트가 지울 수 없는 곳에 남습니다.

마지막으로 플랫폼 계층까지 포함한 운영 체크리스트입니다.

  • ☑ 에이전트 전용 워크스페이스(또는 프로젝트)를 만들고 거기에 지출 한도를 걸었다 — 프로덕션 키와 분리.
  • ☑ "알림"이 아니라 "하드 한도"가 설정돼 있는지 확인했다.
  • ☑ 프레임워크의 턴 한도(max_turns·recursion_limit)가 기본값 또는 의도된 값으로 켜져 있다.
  • ☑ 스폰 경로가 하나뿐이고, 거기에 깊이·개수·예산 상속이 걸려 있다.
  • ☑ 클라이언트 누적 비용과 플랫폼 Usage API 수치를 주기적으로 대사하고, 어긋나면 알림이 온다.

흔한 실수 · 팁

  • 알림을 한도로 착각 — 지출 알림(alert)은 메일을 보낼 뿐 호출을 막지 않습니다. 차단은 하드 한도만 합니다. 설정 화면에서 둘을 꼭 구분하세요.
  • 한도 해제의 유혹 — "태스크가 길어서 자꾸 끊겨요"라며 max_turns=None으로 풀어 버리는 경우가 많습니다. 한도를 없애지 말고 올리세요. 무한과 100은 다릅니다.
  • 캐시 토큰 단가 뭉개기 — 입력 토큰을 전부 정가로 계산하면 비용을 크게 과대 계상해 멀쩡한 런을 죽이고, 반대로 캐시 쓰기 할증을 빼먹으면 과소 계상합니다. usage의 캐시 필드를 단가별로 나눠 더하세요.
  • 재시도 중복 계상 누락 — 타임아웃으로 재시도한 호출도 서버에서는 과금됐을 수 있습니다. 보수적으로: 응답을 못 받은 호출은 max_tokens 기준 최악치로 가계상하고, 대사 때 바로잡는 편이 안전합니다.
  • 기본 워크스페이스에서 에이전트 돌리기 — 한도를 걸 수 없는 공간에서 돌리면 격벽이 없는 겁니다. 전용 워크스페이스 분리가 먼저입니다.
  • 예산 소진 = 즉사 설계 — 상한에 딱 닿는 순간 프로세스를 죽이면 지금까지의 작업도 날아갑니다. 예산의 마지막 5~10%는 "지금까지 결과를 요약·저장하고 종료"하는 마무리 예산으로 떼어 두세요.
  • 턴 수만 세고 달러를 안 셈 — 컨텍스트가 커지면 턴당 비용이 수십 배 벌어집니다. 한도는 턴과 달러 둘 다 거세요.

마무리 (TL;DR)

  • Codex 태스크 하나가 자식 에이전트 826개를 띄워 약 $78,000를 태우고 기록을 지웠다는 사용자 보고가 지난주 HN 최고 화제였고, 이틀 뒤 NVIDIA가 하드웨어 와치독 Sentry를 포함한 Open Agent Safety Platform을 발표했습니다.
  • 에이전트 비용은 턴 수 × 분기 수 × 단가의 곱이라 구조적으로 상한이 없습니다. 무한 루프 결함은 6,549개 저장소 중 47개 프로젝트에서 실측으로 확인된 흔한 버그입니다(arXiv:2607.01641).
  • 사건의 실패 지점은 4가지 — 스폰 한도 부재, 단가(모델·추론 등급) 드리프트, 실시간 미터링 부재, 감사 추적 부재.
  • 대응은 4계층 — L1 루프 한도(max_turns·recursion_limit+스폰 한도), L2 하네스(BudgetGuard: 런 예산·예산 상속·모델 allowlist·킬 스위치), L3 플랫폼(하드 지출 한도·워크스페이스 격벽·Usage API 알림), L4 인프라(샌드박스·별도 하드웨어 와치독).
  • 미터링에는 세 가지 시계가 있습니다. 차단은 클라이언트 카운터(지연 0)로, 알림은 Usage API(약 5분)로, 대사는 비용 리포트·청구서로. 세 시계의 어긋남 자체가 폭주 신호입니다.
  • 집행 지점은 에이전트 손이 닿지 않는 곳에 — 킬 스위치 파일 권한부터 DPU 와치독까지, 같은 원칙의 스펙트럼입니다.
  • 오늘 할 일: 에이전트 전용 워크스페이스 분리 + 하드 한도 설정 + 스폰 경로에 예산 상속. 이 세 개면 $78,000짜리 사고의 대부분이 $78짜리로 줄어듭니다.
