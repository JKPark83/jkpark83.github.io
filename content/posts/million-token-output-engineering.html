도입 — 벤치마크 말고 이 숫자를 보세요

이번 주 AI 엔지니어링 동네에서 가장 큰 사건은 의심의 여지가 없습니다. 9월 30일 Google DeepMind가 공개한 프런티어 모델 Gemini 4 Argon입니다. Hacker News 스레드는 일주일 내내 내려오지 않으며 1,700포인트·1,100개가 넘는 댓글을 쌓았고, Artificial Analysis는 "Argon이 GPT-6 Astra와 같은 인텔리전스 지수를 태스크당 60% 비용으로 달성했다"고 집계했습니다. 벤치마크 순위표가 또 한 번 뒤섞였다는 얘기죠.

그런데 순위표 경쟁은 몇 주마다 뒤집히는 소식이고, 엔지니어 입장에서 이번 발표의 진짜 구조적 변화는 다른 숫자에 있습니다. 최대 출력 토큰 1,000,000개. 직전 세대 Gemini의 64K에서 한 번에 열다섯 배 넘게 뛰었고, OpenAI와 Anthropic의 현행 플래그십이 걸어 둔 128K 한도의 약 8배입니다. 입력 컨텍스트 1M은 이미 2024년부터 익숙한 숫자였지만, 출력 1M은 업계 처음입니다.

"출력 한도가 뭐 그리 대단한가?" 싶다면, 긴 문서를 생성시키다 JSON이 중간에 뚝 끊긴 경험, "계속해 줘"를 이어 붙이다 앞뒤가 미묘하게 어긋난 경험을 떠올려 보세요. 입력 컨텍스트가 100만 토큰으로 넓어지는 동안에도 출력은 4K → 8K → 16K → 64K → 128K로 기어 왔고, 그 좁은 밸브가 우리가 아는 수많은 엔지니어링 패턴 — continue 프롬프트, 청크 생성, 심지어 에이전트 루프의 모양 자체 — 을 만들었습니다. 오늘은 Argon을 입구 삼아, 왜 출력 한도는 항상 입력보다 수십 배 작았는지, 그리고 1M 출력이 실제로 어떻게 구현됐고 무엇을 바꾸는지를 바닥부터 뜯어 봅니다. 미리 말해 두면, "1M"이라는 숫자 뒤에는 꽤 흥미로운 API 설계가 숨어 있습니다.

배경 — 입력 토큰과 출력 토큰은 같은 토큰이 아니다

가격표부터 봅시다. Argon의 정식 단가는 입력 $4, 출력 $20(백만 토큰당)입니다. Claude Opus 5.5도 $4 / $20으로 똑같은 구조입니다. 어느 프런티어 모델을 보든 출력은 입력보다 대략 5배 비쌉니다. 같은 토큰인데 왜 방향에 따라 값이 다를까요? 모델이 입력과 출력을 처리하는 방식이 근본적으로 다르기 때문입니다.

  • 입력 처리(prefill) — 프롬프트에 담긴 토큰 수만 개를 한 번에 병렬로 읽어 들입니다. GPU가 가장 잘하는 종류의 대규모 행렬 연산이라, 수십만 토큰도 수 초 안에 끝납니다.
  • 출력 생성(decode) — 토큰을 한 번에 하나씩 순차적으로 만듭니다. 다음 토큰을 만들려면 직전 토큰이 필요하니 병렬화가 안 되고, 매 토큰마다 모델 가중치와 KV 캐시(지금까지의 대화를 담은 어텐션 캐시)를 통째로 읽어야 해서 연산보다 메모리 대역폭이 병목입니다.

식당에 비유하면 prefill은 주문서 100장을 한눈에 훑는 일이고, decode는 요리를 한 접시씩 차례로 내보내는 일입니다. 주문서는 아무리 두꺼워도 금방 읽지만, 요리는 한 접시에 걸리는 시간 × 접시 수만큼 무조건 걸립니다. 그리고 요리가 나가는 내내 그 주방(GPU 슬롯과 KV 캐시 메모리)은 계속 점유됩니다. 출력이 길수록 서버 자원을 오래 붙들고 있는다는 뜻이고, 이것이 출력 단가가 비싸고 출력 한도가 짧았던 첫 번째 이유입니다. 서빙 내부가 궁금하면 예전 글 LLM 서빙 엔진 내부 구조와 prefill·decode 분리 서빙을 함께 보세요.

두 번째 이유는 더 현실적입니다. 긴 decode는 긴 HTTP 연결입니다. 10만 토큰을 생성하는 요청은 분 단위로 연결을 유지해야 하고, 그 사이 어디서든 — 로드 밸런서 타임아웃, 네트워크 끊김, 서버 재시작 — 실패하면 생성물 전체가 날아갑니다. 실패 시 날리는 돈도 출력이 길수록 커집니다. 그러니 API 제공자 입장에서 출력 한도는 과금 사고와 장애 반경을 줄이는 안전판이기도 했습니다.

마지막으로 헷갈리기 쉬운 사실 하나. 출력도 컨텍스트 윈도우 안에 삽니다. 컨텍스트 1M이라는 건 입력과 출력을 합친 작업 공간이 1M이라는 뜻이라, 입력을 90만 토큰 넣으면 출력은 아무리 한도가 커도 10만 토큰 안에서 끝나야 합니다. 그리고 요즘 모델은 추론(thinking) 토큰도 출력으로 과금하고 출력 예산에서 차감합니다. "max_tokens를 넉넉히 줬는데 답이 짧게 끊겼다"의 범인이 종종 이 추론 토큰입니다.

작은 출력 한도가 만든 엔지니어링 패턴들

출력 한도가 얼마나 느리게 자랐는지 먼저 숫자로 봅시다.

이 좁은 밸브 아래에서 개발자들이 만든 생존 패턴이 셋 있습니다. 지금 운영 중인 LLM 코드 어딘가에 분명 하나쯤 있을 겁니다.

패턴 1 — 잘림 감지. 모든 API는 생성이 왜 끝났는지 알려 줍니다. OpenAI는 finish_reason: "length", Anthropic은 stop_reason: "max_tokens", Gemini는 finishReason: "MAX_TOKENS". 이 값을 확인하지 않는 코드는 잘린 JSON을 그대로 파싱하다 터집니다. 가장 많이 나는 사고이고, 뒤의 실전 섹션에서 처리 코드를 봅니다.

패턴 2 — continue 프롬프트 체인. 한도에 걸리면 지금까지의 출력을 대화에 붙이고 "이어서 계속"을 보내는 고전적인 수법입니다. 돌긴 도는데 비용이 셋 붙습니다. 첫째, 이어 붙인 출력 전체가 다음 요청의 입력으로 재과금됩니다. 둘째, 이음새에서 사고가 납니다 — 문장 중간, 코드 블록 중간, JSON 문자열 중간에서 끊긴 걸 모델이 완벽히 이어 쓴다는 보장이 없습니다. 셋째, 이어 쓸 때마다 모델이 앞부분을 다시 요약·해석하면서 미묘하게 톤과 결정이 어긋나는, 커뮤니티에서 "의미 세금(semantic tax)"이라 부르는 품질 저하가 쌓입니다.

패턴 3 — 에이전트 루프 그 자체. 조금 과장하면, 오늘날 에이전트 루프의 모양에는 작은 출력 한도가 새겨져 있습니다. 거대한 결과물을 한 번에 출력하는 대신, 짧은 추론 → 도구 호출 → 짧은 추론을 반복하며 결과물을 파일 시스템에 쌓아 가는 구조 말입니다. 코딩 에이전트가 3,000줄짜리 파일을 통째로 출력하지 않고 edit 도구로 조각조각 고치는 것도 같은 맥락입니다. 긴 호흡의 작업을 짧은 출력 여러 번으로 쪼개는 기술은 컨텍스트 압축과 함께 에이전트 엔지니어링의 기본기가 됐습니다.

왜 Google이 이 지점을 공격했을까? Google이 Argon을 소개하며 든 사용례는 "수십만 토큰의 추론을 한 호흡(trajectory)에" — 코드베이스 통번역, 다중 문서 감사 같은 작업입니다. 모두 지금까지는 체인과 루프로 쪼개야 했던 일이죠. 쪼개는 지점마다 의미 세금과 재과금이 붙으니, "쪼개지 않아도 되는 모델"은 분명한 차별화 포인트입니다. 출시 직후 The Decoder의 평가처럼 지능 자체는 "따라잡았지만 압도하진 못한" 상황이라, 승부수를 출력 쪽 구조에 둔 셈입니다.

Argon의 1M 출력 해부 — 262K + Long Decode Continuation

그럼 Argon은 2장에서 본 물리 법칙 — 긴 decode는 긴 연결 점유, 큰 장애 반경 — 을 극복한 걸까요? 실측 데이터를 보면 답은 "극복이 아니라 우회"에 가깝고, 그 우회 방식이 이 발표에서 엔지니어링적으로 가장 흥미로운 부분입니다.

평가 기관 Vals AI가 기재한 Argon의 요청당 최대 출력은 약 262K 토큰입니다. 1M이 아닙니다. 그럼 1M은 어디서 나오느냐 — Artificial Analysis는 Long Decode Continuation이라는 새 API 기능으로 1M 출력에 도달했다고 밝혔습니다. 긴 생성을 서버가 중간에 멈췄다가, 후속 요청에서 그 지점부터 그대로 재개하는 기능입니다. 요청 타임아웃에 걸리지 않고 아주 긴 생성을 완주하기 위한 설계죠. 즉 정확히 말하면 Argon의 1M은 "한 번의 응답으로 1M"이 아니라 "하나의 생성 궤적을 여러 요청에 걸쳐 1M까지"입니다.

이 설계가 영리한 이유를 2장과 연결해 봅시다. 긴 decode의 적은 긴 연결이었습니다. Long Decode Continuation은 긴 생성을 여러 짧은 연결로 쪼개되, 생성 상태(궤적)는 서버가 쥐고 있어서 모델 입장에서는 끊긴 적이 없는 하나의 생성입니다. 수동 continue 체인의 세 가지 비용 — 재과금, 이음새 사고, 의미 세금 — 이 원리적으로 사라집니다. 우리가 애플리케이션 레벨에서 어설프게 하던 일을 서빙 레이어의 제품 기능으로 끌어내린 것, 이게 "1M 출력"의 실체입니다.

마케팅 숫자와 API 현실을 구분하세요. "출력 1M"만 보고 "요청 한 번에 1M 토큰이 나온다"고 설계하면 안 됩니다. 요청당 한도는 약 262K이고, 1M은 continuation을 전제로 한 궤적 합산입니다. 참고로 Anthropic도 비슷한 중간 단계를 밟고 있습니다 — Opus 5.5의 동기 API 한도는 128K지만, Batch API에서는 output-300k-2026-03-24 베타 헤더로 300K까지 열립니다. 타임아웃 걱정이 없는 배치에서만 더 긴 출력을 허용하는 것, 역시 "긴 decode의 적은 긴 연결"이라는 같은 물리학의 다른 해법입니다.

또 하나 짚을 것은 가용성입니다. Argon은 사이버 방어 기관을 먼저 들이는 Fairwind 프로그램부터 단계적으로 풀리고 있어서, 출시 직후에는 일반 API 키로 모델을 못 찾는(404) 사례가 보고됐습니다. 이 글의 수치는 공개 스펙과 평가 기관 실측 기준이고, 여러분 키에서 보이는 시점과 한도는 다를 수 있습니다.

실전 — 출력 한도를 안전하게 다루는 코드

Argon을 아직 못 받아도, 출력 한도를 다루는 코드는 오늘 당장 여러분의 LLM 호출부에 필요합니다. 두 가지 패턴만 제대로 깔면 대부분의 "출력 잘림" 사고를 막을 수 있습니다.

패턴 A — 잘림을 감지하고, 폴백으로 이어 쓰기. 핵심은 ① 종료 사유를 반드시 확인하고 ② 이어 쓸 때는 모델이 썼던 출력을 assistant 메시지로 그대로 돌려줘서 "네가 여기까지 썼다"를 알려 주는 겁니다.

{{< highlight python >}} # 종료 사유를 확인하고, 잘렸으면 이어 쓰는 안전 호출 래퍼 (OpenAI 호환 API 기준) # Anthropic은 resp.stop_reason == "max_tokens", Gemini는 finishReason == "MAX_TOKENS" MAX_ROUNDS = 4 # 폭주 방지: 이어 쓰기 횟수에 반드시 상한을 둔다 def generate_full(client, model, messages, max_tokens=16384): parts = [] msgs = list(messages) for _ in range(MAX_ROUNDS): resp = client.chat.completions.create( model=model, messages=msgs, max_tokens=max_tokens) choice = resp.choices[0] parts.append(choice.message.content or "") if choice.finish_reason != "length": # 정상 종료(stop) → 완성 return "".join(parts) # 잘림: 지금까지의 출력을 assistant 턴으로 되돌려 주고 이어 쓰게 한다 msgs.append({"role": "assistant", "content": "".join(parts)}) msgs.append({"role": "user", "content": "끊긴 지점부터 정확히 이어서 계속 작성해 주세요. " "앞 내용을 반복하지 마세요."}) raise RuntimeError("출력이 너무 깁니다 — 작업을 쪼개거나 출력 구조를 바꾸세요") {{< /highlight >}}

패턴 B — 스트리밍 + 증분 체크포인트. 긴 생성일수록 "다 받고 나서 저장"은 위험합니다. 90% 지점에서 연결이 끊기면 그때까지의 토큰(과 돈)이 날아가니까요. 스트리밍으로 받으면서 주기적으로 디스크에 쓰면, 실패해도 마지막 체크포인트부터 패턴 A로 이어 쓸 수 있습니다.

{{< highlight python >}} # 스트리밍으로 받으며 N자마다 디스크에 체크포인트를 남긴다 CHECKPOINT_EVERY = 20_000 # 문자 수 기준. 너무 잦으면 I/O 낭비, 너무 드물면 유실 커짐 def stream_with_checkpoint(client, model, messages, out_path): buf, since_flush = [], 0 with client.chat.completions.stream(model=model, messages=messages) as stream: for event in stream: if event.type != "content.delta": continue buf.append(event.delta) since_flush += len(event.delta) if since_flush >= CHECKPOINT_EVERY: with open(out_path, "w") as f: # 원자적 쓰기가 필요하면 tmp+rename f.write("".join(buf)) since_flush = 0 with open(out_path, "w") as f: f.write("".join(buf)) return "".join(buf) {{< /highlight >}}

마지막으로 구조적인 선택지도 기억해 두세요. 애초에 긴 출력을 피하는 설계가 이기는 경우가 많습니다. 보고서 전체를 한 번에 생성하는 대신 섹션별로 생성해 합치기, 파일 전체 재출력 대신 diff·패치 출력, 장황한 산문 대신 구조화 출력으로 필요한 필드만 뽑기. 출력 한도가 1M이 되더라도 "출력은 짧을수록 싸고 빠르고 검증하기 쉽다"는 사실은 변하지 않습니다.

1M 출력의 현실 감각 — 비용·시간·검증

그래도 1M 출력을 진짜로 쓰면 어떤 그림일까요? 숫자 몇 개로 감을 잡아 봅시다.

항목어림값근거 · 비고
비용 (출력만)프로모션 단가 $10 / 정식 단가 $20출력 $10→$20/M 공시 단가. 입력·추론 토큰은 별도
생성 시간수 시간 (가정 계산)프런티어 모델 통상 속도를 50~150 tok/s로 잡으면 1M 토큰에 약 1.9~5.5시간. Argon의 공식 속도 수치는 미공개라 어디까지나 어림입니다
분량영어 기준 단행본 7~10권1M 토큰 ≈ 영어 55만~75만 단어 (토크나이저에 따라 다름)
실패 비용90% 지점 실패 시 ~$9~18 + 수 시간체크포인트 없이 재시도하면 전액 재지불 — 5장의 패턴 B가 필수인 이유

여기에 모델 성향 변수가 하나 더 붙습니다. Artificial Analysis가 자사 인텔리전스 지수를 돌리는 데 Argon은 출력 토큰 1억 1,000만 개를 썼습니다. 평가 모델들의 중앙값은 8,200만 개, Argon의 태스크당 평균 출력은 약 6만 2,000토큰이었습니다. 즉 Argon은 꽤 수다스러운(verbose) 모델이고, 출력 단가 $20/M과 곱해지면 "지수상 태스크당 비용 60%"라는 숫자도 여러분의 워크로드에서는 달라질 수 있습니다. 추론 예산 글에서 다룬 것처럼, 요즘 모델 비용의 변수는 단가보다 모델이 얼마나 길게 말하고 생각하느냐입니다.

마지막 병목은 기술이 아니라 사람입니다. 1M 토큰짜리 출력은 누가 검증하나요? 단행본 열 권 분량의 코드 마이그레이션 결과를 사람이 리뷰할 수는 없습니다. 출력 한도가 풀릴수록 테스트 스위트, 정적 분석, 섹션별 자동 검증 같은 기계 검증 체계가 먼저 준비돼 있어야 합니다. 긴 출력을 "쓸 수 있다"와 "책임질 수 있다"는 다른 문제입니다.

흔한 실수 · 팁

  • finish_reason/stop_reason을 확인하지 않는다. 출력 잘림 사고의 9할입니다. 특히 구조화 출력(JSON)은 잘리면 항상 깨지므로, 파싱 전에 종료 사유부터 확인하세요.
  • max_tokens를 "요금 상한"으로 오해한다. 반대로 너무 작게 잡으면 멀쩡한 응답을 중간에 자릅니다. 비용 통제는 사용량 모니터링과 예산 가드레일로 하고, max_tokens는 "이 작업의 정상 출력이 절대 넘지 않을 크기 + 여유"로 잡는 게 맞습니다. 추론 토큰이 출력 예산을 먹는다는 것도 잊지 마세요.
  • 이어 쓰기 루프에 상한이 없다. 패턴 A의 MAX_ROUNDS를 빼면, 모델이 종료 조건을 못 만나는 경우 비용이 무한히 샙니다. 이어 쓰기는 항상 유한 루프로.
  • "출력이 기니까 다 넣자"로 설계가 퇴화한다. 1M 출력이 가능해져도 섹션 분할 + 개별 검증이 더 싸고 안전한 경우가 많습니다. 긴 단일 출력은 "쪼개는 비용(이음새·재과금)이 쪼개서 얻는 이득(검증 용이성)보다 클 때"만 선택하세요.
  • 컨텍스트 공식을 잊는다. 입력 + 추론 + 출력 ≤ 컨텍스트 윈도우. 입력 90만 토큰을 넣고 출력 50만 토큰을 기대할 수는 없습니다. 긴 출력 작업일수록 입력을 압축해 출력 공간을 비워 두세요.
  • 같은 프롬프트를 반복 전송하며 캐시를 안 쓴다. 이어 쓰기든 섹션 분할이든 입력 앞부분이 반복됩니다. Argon은 캐시 입력을 95% 할인하고 다른 제공자들도 비슷하니, prompt caching과 묶으면 반복 전송 비용을 크게 줄일 수 있습니다.

마무리 (TL;DR)

  • 9/30 공개된 Gemini 4 Argon의 구조적 뉴스는 벤치마크가 아니라 최대 출력 1M 토큰입니다. 직전 세대 64K, 경쟁 플래그십 128K 대비 한 자릿수가 다릅니다.
  • 출력 한도가 늘 입력보다 수십 배 작았던 이유는 물리학입니다. 입력(prefill)은 병렬 처리지만 출력(decode)은 토큰 단위 순차 생성이라 생성 내내 GPU·KV 캐시·연결을 점유하고, 그래서 단가도 ~5배 비쌉니다.
  • 작은 한도는 continue 체인, 청크 생성, 에이전트 루프라는 패턴을 만들었고, 수동 이어 쓰기에는 재과금·이음새 사고·의미 세금이 붙습니다.
  • Argon의 1M은 한 요청이 아니라 요청당 ~262K + Long Decode Continuation(서버가 생성 상태를 보존한 채 멈췄다 재개)의 궤적 합산입니다. 사실상 continue 프롬프트의 서버측 제품화입니다.
  • 당장 할 일: 종료 사유 확인 → 상한 있는 이어 쓰기 폴백 → 스트리밍 체크포인트 세 가지를 호출부에 깔아 두세요. 어떤 모델을 쓰든 유효합니다.
  • 1M 출력은 정식 단가로 $20, 생성에 수 시간(어림), 분량은 단행본 7~10권입니다. 기계 검증 체계 없이 긴 출력부터 켜는 것이 가장 위험한 순서입니다.
