1. 왜 지금 디퓨전 LLM이 화제인가

요즘 LLM 이야기는 대부분 “모델이 얼마나 똑똑하냐”에 쏠려 있습니다. 그런데 에이전트를 실제로 굴려 보면, 답의 품질만큼이나 답이 나오는 속도가 서비스의 성패를 가릅니다. 툴을 열 번 호출하는 에이전트라면, 한 번의 생성이 느린 만큼 전체가 그대로 느려집니다. 지연(latency)과 토큰 비용이 곧 돈이자 사용자 이탈입니다.

속도를 끌어올리는 방법은 여러 갈래로 연구돼 왔습니다. 더 빠른 GPU, 양자화, speculative decoding 같은 것들이죠. 그런데 이들은 대부분 “토큰을 왼쪽부터 한 개씩 뱉는다”는 오늘날 LLM의 근본 구조는 그대로 둡니다. 디퓨전 LLM(diffusion LLM, 줄여서 dLLM)은 바로 그 근본을 바꿉니다. 문장을 통째로 흐릿하게 채워 놓고, 자신 있는 칸부터 병렬로 또렷하게 만들어 나갑니다.

이게 2026년 들어 실무 talking point가 된 데는 이유가 있습니다. 아이디어 자체는 2025년에 실용성이 증명됐습니다. LLaDA가 8B 규모 디퓨전 모델로 LLaMA3 8B와 맞먹는 성능을 냈고, 스타트업 Inception이 상용 디퓨전 코드 모델 Mercury를, 구글이 Gemini Diffusion을 선보이며 초당 1,000 토큰이 넘는 생성 속도를 보여 줬습니다. 그리고 2026년, 결정적으로 서빙 인프라가 따라왔습니다. 대표 추론 엔진인 vLLM이 디퓨전 모델 DiffusionGemma를 정식 지원하기 시작했고(2026-06), 별도의 dllm-plugin까지 나왔습니다. “연구실 데모”였던 디퓨전 LLM이 “프로덕션에 올릴 수 있는 옵션”으로 넘어오는 중이라, 실무자들 사이에서 “자기회귀 독점(autoregressive monopoly)의 끝인가”라는 논의가 다시 뜨거워졌습니다.

한 줄 요약. 자기회귀 LLM은 토큰을 순서대로 한 개씩 만듭니다. 디퓨전 LLM은 문장 전체를 동시에 만들되, 여러 번 다듬어(denoising) 완성합니다. 순차 생성의 지연을 병렬로 눌러 속도를 벌고, 그 대가로 “몇 번 다듬을지”라는 품질·속도 손잡이가 새로 생깁니다.

2. 배경 — 자기회귀(AR)의 한 글자씩 문제

디퓨전을 이해하려면 우리가 매일 쓰는 방식부터 짚어야 합니다. GPT·Claude·Llama 같은 모델은 자기회귀(autoregressive, AR) 방식입니다. 이름이 어렵지만 뜻은 단순합니다. “다음 토큰 하나를 앞의 모든 토큰을 보고 예측한다”를, 문장이 끝날 때까지 반복하는 겁니다.

여기서 두 가지가 따라옵니다. 첫째, 생성은 본질적으로 순차적입니다. 3번째 토큰을 만들려면 2번째 토큰이 이미 확정돼 있어야 합니다. 그래서 300 토큰짜리 답이면 모델을 300번 순서대로 돌려야 하고(=300번의 forward pass), 답이 길수록 지연이 그대로 쌓입니다. 둘째, 각 토큰은 앞쪽만 봅니다. 이걸 causal masking(인과 마스킹)이라 부르는데, 학습·생성 모두 “미래를 미리 보지 못하게” 가리는 장치입니다.

이 구조는 튼튼하고 잘 작동하지만, 코드 편집처럼 “가운데를 채워 넣는(fill-in-the-middle)” 작업엔 어색합니다. 앞뒤 맥락을 다 보고 가운데만 고치고 싶은데, AR은 원래 왼쪽에서 오른쪽으로만 흐르기 때문입니다. 여기가 디퓨전이 파고드는 지점입니다.

3. 디퓨전 LLM은 어떻게 문장을 만드나

디퓨전(diffusion)은 원래 이미지 생성에서 유명해진 아이디어입니다. 깨끗한 이미지에 노이즈를 조금씩 끼얹어 완전한 잡음으로 만드는 과정(forward)을 배워 두고, 거꾸로 잡음에서 노이즈를 조금씩 걷어내며(reverse) 이미지를 복원하는 방식이죠. 언어에서는 “노이즈”를 [MASK](마스크, 가려진 빈칸)로 바꿉니다. 그래서 텍스트용 디퓨전을 masked diffusion(마스크 디퓨전)이라고도 부릅니다.

동작은 두 방향으로 나뉩니다.

  • 학습(forward): 정답 문장에서 토큰 일부를 무작위로 [MASK]로 가린 뒤, 모델이 그 빈칸을 한 번에 맞히도록 훈련합니다. 가리는 비율을 0%에서 100%까지 다양하게 바꿔 가며 배웁니다. AR과 달리 causal mask가 없어서, 모델은 빈칸의 앞뒤를 모두 봅니다(양방향, bidirectional).
  • 생성(reverse): 답을 만들 때는 정반대로 갑니다. 답 자리를 전부 [MASK]로 채운 흐릿한 상태에서 시작해, 여러 번의 라운드(denoising step)를 거치며 빈칸을 점점 채워 또렷하게 만듭니다.

핵심은 “한 라운드에 전부 확정하지 않는다”는 점입니다. 모델은 매 라운드마다 모든 빈칸에 대해 후보 토큰과 그 자신감(confidence)을 함께 내놓습니다. 그중 자신 있는 칸만 확정하고, 애매한 칸은 다시 [MASK]로 되돌립니다. 이걸 저신뢰 리마스킹(low-confidence remasking)이라 하고, 결과적으로 “쉬운 곳 먼저, 어려운 곳 나중에” 채우는 coarse-to-fine(거친→세밀) 흐름이 됩니다. 사람이 초안을 잡고 애매한 표현을 나중에 다듬는 것과 똑같습니다.

여기서 AR과의 결정적 차이 두 가지가 나옵니다. ① 한 라운드에 여러 칸을 동시에 확정할 수 있습니다(병렬). ② 모든 칸이 앞뒤를 다 보고 정해집니다(양방향). 그래서 “가운데만 자연스럽게 채우기”가 구조적으로 편합니다 — 코드 편집이 디퓨전의 단골 활용처인 이유입니다.

4. 왜 빠른가 — 그리고 속도·품질 손잡이

속도의 비밀은 단순합니다. AR이 N개 토큰 = N번의 순차 forward인 반면, 디퓨전은 T번의 라운드면 끝나고, 이 T가 N보다 훨씬 작을 수 있습니다. 한 라운드에 여러 칸을 병렬로 확정하기 때문입니다. GPU는 원래 “한 개씩 순서대로”보다 “여러 개를 한꺼번에”를 훨씬 잘합니다. 디퓨전은 그 특성에 딱 맞아떨어집니다.

실제 수치로도 드러납니다(각 회사 발표 기준).

하지만 공짜는 없습니다. 여기서 디퓨전만의 손잡이(knob)가 하나 생깁니다 — 몇 번 다듬을 것인가(라운드 수, denoising step). 라운드를 많이 돌리면(한 번에 한 칸씩 확정에 가깝게) 품질은 올라가지만 느려지고, 라운드를 줄여 한 번에 여러 칸을 확정하면 빨라지지만 품질이 떨어질 수 있습니다.

왜 품질이 떨어질까요? 같은 라운드에서 여러 칸을 동시에 확정한다는 건, 그 칸들이 서로 독립적이라고 가정하는 것과 같습니다. 하지만 “서울에 ___ ___”에서 두 빈칸은 사실 얽혀 있습니다. 한꺼번에 뽑으면 “서울에 부산 갔다” 같은 엇박이 날 수 있습니다. 그래서 최근 연구들은 “자신감이 충분히 높을 때만 병렬로 확정하면 순차 확정과 사실상 같아진다”는 점을 이용합니다(예: Fast-dLLM). 자신 있는 칸은 과감히 병렬로 처리해 속도를 벌고, 애매하면 라운드를 더 쓰는 식으로 손잡이를 자동 조절하는 것이죠.

5. 서빙의 진짜 걸림돌: KV 캐시와 block diffusion

디퓨전이 이론적으로 빠르다는 건 2025년에 이미 알려졌습니다. 그런데도 한동안 프로덕션에 못 올린 진짜 이유는 KV 캐시(KV cache) 때문이었습니다. 조금만 짚고 갑시다.

AR 서빙이 그나마 견딜 만한 건 KV 캐시 덕분입니다. 토큰을 왼쪽에서 오른쪽으로만 만들기 때문에, 이미 만든 토큰의 내부 계산 결과(Key·Value)를 저장해 두고 다음 토큰에서 재사용합니다. 새 토큰마다 처음부터 다시 계산하지 않아도 되죠. 그런데 순수 디퓨전은 양방향입니다. 라운드마다 빈칸이 앞뒤 전체를 다시 보므로, “앞쪽은 이미 확정됐으니 캐시해 두자”가 성립하지 않습니다. 캐시를 못 쓰면 라운드마다 문장 전체를 다시 계산해야 하고, 병렬로 번 속도를 여기서 도로 까먹습니다.

이 딜레마를 푼 열쇠가 block diffusion(블록 디퓨전), 다른 말로 semi-autoregressive(반자기회귀)입니다. 아이디어는 “두 방식의 좋은 점만 섞자”입니다.

  • 문장을 블록(block)으로 나눕니다(예: 32토큰씩).
  • 블록 사이는 AR처럼 왼쪽→오른쪽으로 순서대로 갑니다. 앞 블록은 확정된 뒤 뒤 블록에게 단방향으로만 영향을 줍니다.
  • 블록 안에서는 디퓨전처럼 여러 토큰을 병렬로 다듬습니다.

이렇게 하면 앞 블록은 다시 바뀌지 않으므로 KV 캐시를 그대로(손실 없이) 재사용할 수 있습니다(BD3-LM이 이 구조를 정리했습니다). 블록 내부 병렬성으로 속도는 벌고, 블록 간 단방향으로 캐시는 살리는, 실용적인 절충입니다. 길이도 블록 단위로 유연하게 늘릴 수 있어 “고정 길이” 제약도 완화됩니다.

2026년의 “프로덕션 진입”은 대부분 이 block diffusion 위에서 일어났습니다. vLLM은 dllm-plugin이라는 블록 기반 디퓨전 플러그인과 함께, 구글의 DiffusionGemma(Gemma4 백본, 26B급)를 정식 지원하는 첫 dLLM으로 통합했습니다(2026-06). 배치 서빙과 구조적 출력(structured output) 가드까지 얹혀, 이제 “AR 모델처럼” 올릴 수 있게 됐죠. 서빙 최적화 연구도 이어져, HERALD 같은 작업은 CPU·GPU가 KV 캐시를 나눠 들고 블록 디퓨전을 고속으로 서빙하는 방법을 다룹니다.

6. 실전 — 언제 쓰고, 어떻게 굴리나

개념을 코드로 만져 봅시다. 먼저 디퓨전 생성 루프의 뼈대입니다. 실제 라이브러리 API는 아니고, 저신뢰 리마스킹이 어떻게 도는지 감을 잡는 의사코드에 가깝습니다.

{{< highlight python >}} # 디퓨전 LLM 생성 루프의 뼈대 (개념용 의사코드) # 핵심: 전부 [MASK]에서 시작 → 라운드마다 '자신 있는 칸'만 확정 def diffusion_generate(model, length=64, steps=16): MASK = "[MASK]" seq = [MASK] * length # 1) 답 자리를 전부 마스크로 채운다 for step in range(steps): # 2) steps 번 다듬는다 (T ≪ N) logits = model.forward(seq) # 모든 위치를 '동시에' 예측 (양방향) pred, conf = logits.argmax_and_confidence() # 후보 토큰 + 자신감 # 3) 아직 마스크인 칸 중, 이번 라운드에 몇 개를 확정할지 정한다 # (뒤로 갈수록 더 많이 확정 → 초반은 신중, 후반은 과감) k = tokens_to_commit(step, steps, remaining=seq.count(MASK)) # 4) 마스크 칸을 '자신감 높은 순'으로 k개만 확정 for pos in top_k_masked_positions(seq, conf, k): seq[pos] = pred[pos] # 5) 나머지 마스크는 그대로 → 다음 라운드에서 앞뒤 맥락 보고 다시 시도 if MASK not in seq: break return seq {{< /highlight >}}

포인트는 4~5번입니다. 매 라운드 모든 칸을 예측하되, 자신 있는 칸부터 k개만 확정하고 나머지는 다음으로 미룹니다. 이 k를 크게 잡으면 빠르지만 거칠고, 작게 잡으면 느리지만 촘촘합니다 — 그림 2의 손잡이가 바로 이 k입니다.

이제 실제로 굴리는 쪽입니다. 다행히 대부분의 디퓨전 LLM은 기존 AR 모델과 똑같은 API 모양으로 감싸 제공합니다. 예를 들어 Inception의 Mercury는 OpenAI 호환 엔드포인트를 제공하므로, 클라이언트 코드는 거의 그대로 두고 base_url과 모델명만 바꾸면 됩니다.

{{< highlight python >}} from openai import OpenAI # OpenAI 호환 엔드포인트를 제공하는 디퓨전 LLM 예시 (Inception Mercury) client = OpenAI( api_key="YOUR_KEY", base_url="https://api.inceptionlabs.ai/v1", # 공급자별 엔드포인트 ) resp = client.chat.completions.create( model="mercury-coder", # 디퓨전 코드 모델 messages=[{"role": "user", "content": "이 파이썬 함수에 빈 리스트 방어 코드를 넣어 줘"}], ) print(resp.choices[0].message.content) # 호출 방식은 AR 모델과 동일 — 내부에서 '병렬 denoising'으로 만들 뿐이다 {{< /highlight >}}

오픈 모델을 직접 서빙하고 싶다면, 2026년부터는 vLLM이 디퓨전 모델을 지원합니다. 블록 기반 디퓨전 플러그인을 설치하고 DiffusionGemma를 올린 뒤, 역시 OpenAI 호환 서버로 노출하는 흐름입니다.

{{< highlight bash >}} # vLLM 블록 디퓨전 플러그인 설치 (오픈 dLLM 직접 서빙) pip install vllm dllm-plugin # DiffusionGemma를 OpenAI 호환 서버로 서빙 (실제 인자/모델명은 문서 확인) vllm serve google/diffusion-gemma --port 8000 # → http://localhost:8000/v1 로 AR 모델과 동일하게 호출 {{< /highlight >}}

그럼 언제 쓰면 좋을까요? 지금까지의 그림을 종합한 판단 기준입니다.

상황디퓨전 LLM이 유리한가이유
코드 자동완성 · 인라인 편집(fill-in-the-middle)✅ 잘 맞음양방향 맥락 + 짧은 생성 → 속도 이점이 큼(단문 생성 시 비용 50~80%↓ 보고)
저지연이 중요한 에이전트 툴 응답✅ 유리초당 1,000+ 토큰으로 왕복 지연을 줄임
구조가 정해진 출력(JSON·양식 채우기)🟡 상황에 따라빈칸 채우기와 궁합이 좋지만, 문법 보장은 서빙 측 가드에 의존
아주 긴 문서 생성 · 복잡한 장문 추론🟠 아직은 AR이 안전블록 길이·품질 안정성·생태계 성숙도에서 AR이 앞섬
실전 감각. 지금 단계의 현실적인 쓰임은 “전면 교체”가 아니라 “골라 쓰기”입니다. 지연에 민감하고 짧은 구간 — 코드 편집, 자동완성, 빠른 툴 응답 — 을 디퓨전 LLM으로 돌려 속도를 벌고, 복잡한 장문·추론은 여전히 검증된 AR 모델에 맡기는 하이브리드가 안전합니다.

7. 흔한 실수 · 팁

  • “빠르다니까 무조건 좋다”는 착각. 속도는 라운드 수를 줄여서 나온 값일 수 있습니다. 라운드를 지나치게 줄이면 서로 얽힌 토큰을 한꺼번에 뽑다가 어색한 문장이 나옵니다. 속도 수치는 항상 “어떤 품질에서?”와 함께 봐야 합니다.
  • 벤치마크 점수를 곧이곧대로 믿기. 디퓨전 모델은 채점 방식(라운드 수·디코딩 설정)에 따라 점수가 출렁입니다. 실제로 “평가 착시(evaluation illusion)”를 지적하는 연구들이 나올 만큼, 내 태스크·내 설정으로 다시 재 보는 게 안전합니다.
  • KV 캐시를 AR처럼 당연히 여기기. 순수 디퓨전엔 그 캐시가 없습니다. 서빙 성능을 논할 땐 그 구현이 block diffusion 기반인지(=캐시를 쓰는지) 먼저 확인하세요. 여기서 처리량이 몇 배씩 갈립니다.
  • 고정 길이 함정. 일부 디퓨전 구현은 생성 길이를 미리 정해 [MASK] 칸을 잡습니다. 너무 짧게 잡으면 답이 잘리고, 너무 길게 잡으면 낭비가 생깁니다. block diffusion처럼 블록 단위로 늘릴 수 있는지 확인하세요.
  • 생태계 성숙도. 도구·파인튜닝 레시피·가드레일은 AR 쪽이 훨씬 두껍습니다. 프로덕션 도입 전 구조적 출력·중단·스트리밍 같은 실무 기능이 갖춰졌는지 점검하세요(vLLM의 dLLM 지원이 이 간극을 빠르게 메우는 중입니다).

8. 마무리 (TL;DR)

  • 자기회귀(AR)는 토큰을 왼쪽부터 한 개씩 순차로 만듭니다 → 길수록 지연이 쌓입니다.
  • 디퓨전 LLM(dLLM)은 답 자리를 전부 [MASK]로 채운 뒤, 여러 라운드에 걸쳐 자신 있는 칸부터 병렬로 또렷하게 만듭니다(masked diffusion, 저신뢰 리마스킹).
  • 빠른 이유는 N번의 순차 forward가 T번의 라운드(T ≪ N)로 줄기 때문입니다. Mercury·Gemini Diffusion은 초당 1,000+ 토큰을 보고했습니다.
  • 대가는 속도·품질 손잡이(라운드 수)입니다. 자신감이 높은 칸만 병렬 확정하면 같은 품질을 더 적은 라운드로 낼 수 있습니다(Fast-dLLM).
  • 서빙의 진짜 걸림돌은 KV 캐시였고, block diffusion(블록 사이는 AR·블록 안은 디퓨전)이 이를 풀어 캐시를 살렸습니다.
  • 2026년, vLLM이 DiffusionGemma를 정식 지원하며 dLLM이 연구실을 나와 프로덕션으로 들어오고 있습니다.
  • 지금은 전면 교체가 아니라 골라 쓰기가 정답입니다. 코드 편집·저지연 툴 응답은 dLLM, 복잡한 장문·추론은 AR.
