1. 도입 — 시연은 넘치는데 연습장이 없다

이번 주 Hugging Face 데일리 페이퍼 트렌딩 1위는 Qwen 팀의 Terminal-Universe: Turning Agent Trajectories into Scalable Terminal Environments였습니다. 제목만 보면 또 하나의 데이터셋 논문 같지만, 출발점이 되는 관찰이 요즘 에이전트 엔지니어링의 급소를 정확히 찌릅니다.

Claude Code, Codex CLI 같은 터미널 에이전트가 일상 도구가 되면서, 궤적(trajectory) — 에이전트가 태스크를 푸는 동안 남긴 명령어·도구 호출·출력의 전체 기록 — 은 이미 대량으로 쌓여 있습니다. 공개된 것만 수만 편입니다. 그런데 정작 에이전트를 훈련시키려면 궤적이 아니라 환경(environment) — 에이전트가 직접 명령을 실행해 보고 결과를 확인할 수 있는, 실행 가능한 작업 공간 — 이 필요합니다. 그리고 이 환경은 여전히 사람이 손으로 만드는 희소 자원입니다.

왜 궤적으로는 부족할까요? 논문의 표현을 빌리면 궤적은 "얼어붙은 시연 한 편(a single frozen demonstration)"입니다. 남이 문제 푸는 걸 어깨너머로 한 번 구경한 기록이죠. 반면 환경은 연습장입니다. 같은 환경에 다른 질문을 몇 번이고 던질 수 있고(재질의), 내 답이 맞았는지 실행 결과로 확인할 수 있습니다(실행 피드백). 수능 공부에 비유하면 궤적은 남의 풀이 노트, 환경은 채점기 딸린 문제은행입니다. 풀이 노트만 백날 읽어서는 실력이 늘지 않는다는 걸 우리는 경험으로 압니다 — 강화학습(RL)과 rejection sampling 기반 훈련은 말할 것도 없고요.

Terminal-Universe의 답은 발상의 전환입니다. 궤적에는 그 궤적이 돌았던 환경의 구조와 내용이 새겨져 있다. 그러니 궤적을 거꾸로 재생하면 환경을 복원할 수 있다. 이 역변환으로 공개 궤적 더미에서 37,300개의 실행 가능한 환경을 만들어 냈고, 여기서 뽑은 데이터로 파인튜닝한 모델이 Terminal-Bench 2.1 점수를 11.9포인트 끌어올렸다고 보고합니다. 같은 날 arXiv에는 터미널 에이전트용 환경을 점점 어렵게 진화시키는 Environment Evolution 논문도 올라왔습니다. 올해 내내 이어져 온 "환경이 병목"이라는 흐름이, 이번 주 '환경을 어떻게 만들 것인가'라는 공정(pipeline) 문제로 또렷하게 모인 겁니다.

이 글에서 얻어 갈 것. ① 훈련·평가에서 말하는 '환경'의 정확한 구성 요소(Terminal-Bench 해부), ② 궤적→환경 역변환 파이프라인의 동작 원리, ③ 환경 하나에서 검증 가능한 태스크 여러 개를 뽑는 두 가지 축, ④ 2026년 환경 합성 연구들의 계보, ⑤ 미니 검증 태스크와 장난감 역변환을 직접 만드는 코드.

참고로 이 블로그에서 RL 환경이 왜 병목이자 해자인지는 이미 다룬 적이 있습니다. 그 글이 "환경이 왜 중요한가"였다면, 오늘은 "그 환경을 어떻게 대량 생산하는가"입니다.

2. 배경 — '환경'이란 정확히 무엇인가: Terminal-Bench 해부

막연하게 느껴지는 '환경'을 구체물로 만들어 봅시다. 이 분야의 사실상 표준 벤치마크인 Terminal-Bench(Stanford와 Laude Institute의 공동 프로젝트, GitHub 2.6k 스타)의 태스크 하나는 다섯 요소로 구성됩니다.

  • 지시(instruction) — 에이전트가 달성해야 할 목표를 적은 영어 문장.
  • Docker 이미지 — 태스크가 실행되는 컨테이너. 코드베이스, 설치된 도구, 데이터가 들어 있습니다.
  • 테스트(verifier) — 태스크 종료 후 컨테이너의 최종 상태를 검사해 성공 여부를 판정하는 스크립트.
  • 오라클 풀이(oracle solution) — 사람이 작성한 정답 풀이. 태스크가 실제로 풀리는지 보증합니다.
  • 시간 제한 — 이 안에 끝내야 합니다.

핵심은 세 번째 요소입니다. 검증기가 에이전트의 과정이 아니라 결과 상태를 기계적으로 채점하기 때문에, 사람이 개입하지 않아도 성공/실패 신호가 나옵니다. 이 신호가 있어야 RL의 보상이 되고, rejection sampling의 필터가 되고, 벤치마크의 점수가 됩니다. 그래서 이 바닥에서 환경의 가치는 "실행 가능한가"에 더해 "검증 가능한 태스크를 몇 개나 뽑아낼 수 있는가"로 매겨집니다.

그럼 사람이 열심히 만들면 되지 않을까요? Terminal-Bench 자체가 그 답을 보여 줍니다. 커뮤니티 개발자 약 100명이 참여해 만든 이 벤치마크의 2.0 버전은 겨우 89개 태스크입니다. 프런티어 모델의 점수가 50%를 넘지 않도록 어렵고 현실적인 태스크만 사람이 직접 검수해 큐레이션한 결과가 그렇습니다. 게다가 지난달 나온 2.1 버전은 그 89개 중 20개가 넘는 태스크를 수리해야 했습니다 — 벤치마크를 만든 뒤 외부 의존성이 바뀌어 정답 풀이가 깨진 태스크가 9개, 리소스 예산이 부족해 정당한 접근이 시간 안에 못 끝나던 태스크가 8개, 지시문과 테스트가 어긋난 태스크들까지. 전문가 100명이 달라붙어도 제대로 된 환경 만들기는 이렇게 어렵고, 만들어 놓아도 썩습니다. 이 비용 구조가 바로 환경 합성 연구 전체의 출발점입니다.

왜 하필 터미널인가? 웹이나 GUI 환경과 달리 터미널은 상태가 파일 시스템과 프로세스로 깔끔하게 정의되고, Docker로 통째로 포장·복제할 수 있으며, 최종 상태를 테스트 코드로 검사하기 쉽습니다. 검증 가능성이 좋으니 훈련 신호 만들기도 쉽고, 그래서 환경 합성 연구가 터미널에서 가장 먼저 폭발했습니다. 코딩 에이전트 시장이 커진 것도 물론 한몫했고요.

3. 발상의 전환 — 궤적을 거꾸로 재생하면 환경이 복원된다

Terminal-Universe의 관찰은 단순합니다. 궤적에 기록된 도구 실행 이력(tool-execution history)이 그 환경의 구조와 내용을 노출한다는 것. 생각해 보면 당연합니다. 에이전트가 ls를 치면 디렉토리 구조가, cat app.py를 치면 파일 내용이, pip install이 실패하면 의존성 상태가 전부 궤적에 찍힙니다. 에이전트가 일을 잘하려고 환경을 탐색한 흔적이, 뒤집어 보면 환경의 설계도인 셈입니다.

복원 파이프라인은 두 단계로 동작합니다.

  1. 파일 연산 리플레이(replay) — 궤적에 기록된 파일 연산을 재생하면서, 에이전트가 수정하기 전의 각 파일 상태를 복원합니다. 에이전트가 app.py를 읽고 고쳤다면, 읽었을 때의 내용이 곧 초기 상태입니다. 이렇게 하면 태스크 시작 시점의 부분 워크스페이스(partial workspace)가 나옵니다.
  2. completion agent — 궤적에 한 번도 등장하지 않은 파일과 의존성은 복원할 수 없습니다. 이 빈칸은 별도의 에이전트가 문맥에 맞게 채워 넣습니다. import 구문에 등장하는데 내용이 없는 모듈, 실행에 필요한 설정 파일 같은 것들이요.

이 접근의 영리한 점은 현실성(realism)을 공짜로 얻는다는 데 있습니다. LLM에게 "그럴듯한 코드베이스를 만들어 줘"라고 시켜서 환경을 처음부터 생성하면, 태스크가 실제 개발과 동떨어진 장난감이 되기 쉽습니다. 반면 궤적은 실제 사용자가 실제 문제를 풀려고 에이전트를 돌린 기록이므로, 복원된 환경에는 진짜 개발 현장의 지저분함 — 레거시 코드, 얽힌 의존성, 애매한 설정 — 이 그대로 담겨 있습니다. 훈련 데이터의 분포가 배포 환경의 분포와 가까워지는 거죠.

주의 — 아무 궤적이나 뒤집으면 되는 게 아닙니다. 이 파이프라인에는 전제가 둘 있습니다. 첫째, 궤적에 도구 실행의 입출력이 충분히 상세하게 기록되어 있어야 합니다(read/edit의 전후 내용). 로그를 요약하거나 잘라 저장하는 하네스라면 복원 재료 자체가 없습니다. 둘째, 궤적 속 데이터의 라이선스와 민감 정보 문제가 따라옵니다. 남의 궤적에는 남의 코드와 비밀이 들어 있을 수 있습니다. Terminal-Universe도 공개(public) 궤적을 재료로 씁니다.

4. 환경 하나 → 태스크 여러 개: breadth와 depth

환경을 복원했으면 이제 본전을 뽑을 차례입니다. 앞서 말했듯 환경의 가치는 재질의에서 나옵니다. Terminal-Universe는 복원한 워크스페이스에서 우선 원래 궤적이 풀려던 태스크를 재구성하고 — 원본 지시와 최종 상태를 알고 있으니 검증기도 만들 수 있습니다 — 거기에 더해 완전히 새로운 태스크를 두 방향으로 합성합니다.

  • breadth(가로 확장) — 서로 관련 있는 환경들 사이의 방향성 의존 관계를 채굴해, 여러 코드베이스를 넘나드는 태스크를 만듭니다. "라이브러리 A를 고치고, A를 쓰는 프로젝트 B가 여전히 동작하는지 확인하라" 같은, 실제 개발자가 일상적으로 하는 종류의 일이죠. 단일 리포지토리 안에 갇힌 기존 합성 태스크와 구별되는 지점입니다.
  • depth(세로 확장) — 한 번 묻고 끝나는 단일 턴 질의를, user agent가 사용자 역할을 연기하는 멀티 라운드 세션으로 늘립니다. 첫 요구를 이행하면 피드백과 함께 요구가 정제되어 돌아오는 — "됐고, 이제 에러 처리도 붙여 줘" — 실제 사용 패턴을 흉내 내는 겁니다.

결과 숫자는 이렇습니다. 공개 터미널 에이전트 궤적에 파이프라인을 적용해 태스크를 뽑을 수 있는 환경 37,300개를 확보했고, 약 32,000개의 궤적을 새로 합성했으며, 이 코퍼스로 Qwen3.5-27B를 SFT(지도 파인튜닝)한 결과 Terminal-Bench 2.1 단일 라운드 성능이 11.9포인트 상승했다고 보고합니다. 논문 자체 보고 수치이니 재현 결과가 나오기 전까지는 그 조건 — 해당 모델, 해당 벤치마크, SFT만 적용 — 안에서 읽는 게 안전합니다. 그래도 "손으로 만든 89개" 옆에 "궤적에서 복원한 37,300개"를 놓고 보면, 이 접근이 겨냥하는 규모의 차원이 다르다는 건 분명합니다.

5. 2026년 환경 합성 연구 지도

Terminal-Universe가 진공에서 나온 게 아닙니다. 올해 터미널 에이전트 환경 합성은 "무엇을 재료로 환경을 만드는가"를 기준으로 크게 세 계열이 경쟁해 왔습니다.

계열재료대표 연구아이디어 한 줄
리포지토리 기반GitHub 코드베이스TerminalTraj, CLI-Universe좋은 리포를 골라 Docker화하고 태스크·검증 코드를 생성. TerminalTraj는 8개 도메인에서 검증된 궤적 50,733개를 생산, CLI-Universe는 능력 분류 체계 기반으로 6천 궤적만으로 Qwen3-32B를 Terminal-Bench 2에서 33.4%까지 올렸다고 보고.
스킬 기반에이전트 스킬 정의Terminal-World, Skill Graphs스킬(무엇을·언제·어떻게)을 합성의 프리미티브로 삼아 지시·환경·교사 궤적을 한꺼번에 유도.
궤적 기반실사용 궤적CLI-Gym, Terminal-Universe실행 기록을 역변환(environment inversion)해 환경을 복원. 현실성이 공짜로 따라옴.
난이도 제어기존 환경Endless Terminals, SETA, Environment Evolution환경을 점점 어렵게 진화·확장. SETA는 검증된 환경 4,500여 개로 8B 모델 RL 훈련의 최고 성적을 보고, Environment Evolution은 대상 에이전트 성능과 무관하게(off-policy) 난이도를 끌어올리는 방법을 제안.

이 지도를 한 발 떨어져서 보면 플라이휠이 보입니다. 좋은 환경에서 에이전트를 훈련하면 → 더 나은 에이전트가 배포되고 → 더 많은 실사용 궤적이 쌓이고 → 그 궤적을 뒤집어 더 많고 더 현실적인 환경을 만들고 → 다시 훈련합니다. 지금까지 "배포에서 나온 데이터"는 대부분 로그 창고에서 잠자고 있었는데, 궤적 기반 합성은 그 창고를 훈련 인프라로 되돌리는 마지막 연결 고리인 셈입니다. Qwen 팀이 6월에 낸 Qwen-AgentWorld — 1천만 편 이상의 상호작용 궤적으로 7개 도메인의 환경 자체를 시뮬레이션하는 language world model — 까지 겹쳐 보면, "환경을 확보하는 자가 에이전트 훈련을 지배한다"는 방향으로 업계가 얼마나 진지하게 움직이는지 감이 옵니다.

6. 실전 — 미니 검증 태스크와 장난감 역변환 만들기

개념을 손에 붙이는 가장 빠른 길은 아주 작은 버전을 직접 만들어 보는 겁니다. 두 가지를 만들어 봅니다 — Terminal-Bench 스타일의 검증 가능한 태스크 하나, 그리고 파일 연산 로그를 거꾸로 재생하는 장난감 역변환.

(1) 검증 가능한 태스크의 뼈대. 핵심은 "검증기가 최종 상태만 본다"입니다. 구조는 이렇게 잡습니다.

{{< highlight text >}} count-errors/ # 태스크 하나 = 디렉토리 하나 ├── task.yaml # 지시문 + 시간 제한 ├── Dockerfile # 환경: 코드·데이터가 담긴 이미지 ├── solution.sh # 오라클 풀이 (태스크가 풀린다는 증명) └── tests/ └── test_outcome.py # 검증기: 컨테이너 최종 상태 검사 {{< /highlight >}} {{< highlight yaml >}} # task.yaml instruction: | /app/logs/ 아래의 모든 .log 파일에서 "ERROR"로 시작하는 줄 수를 세어 /app/answer.txt에 숫자 하나만 쓰세요. max_agent_timeout_sec: 300 {{< /highlight >}} {{< highlight python >}} # tests/test_outcome.py — 과정은 안 봅니다. 최종 상태만 봅니다. from pathlib import Path def expected() -> int: n = 0 for p in Path("/app/logs").glob("*.log"): n += sum(1 for line in p.read_text().splitlines() if line.startswith("ERROR")) return n def test_answer_exists_and_correct(): out = Path("/app/answer.txt") assert out.exists(), "answer.txt가 없습니다" assert out.read_text().strip() == str(expected()) {{< /highlight >}}

에이전트가 grep을 쓰든 Python을 쓰든 상관없습니다. 검증기는 /app/answer.txt의 내용이라는 결과 상태만 검사하니까요. 이 성질 덕분에 같은 환경(로그 파일 더미)에 "WARN 줄 수를 세라", "가장 에러가 많은 파일을 찾아라" 같은 다른 지시 + 다른 검증기를 얼마든지 얹을 수 있습니다. 이게 바로 "환경은 재질의할 수 있다"의 실체입니다.

(2) 장난감 역변환. 이제 Terminal-Universe의 1단계를 축소 재현해 봅니다. 에이전트 하네스가 파일 연산을 이렇게 기록했다고 합시다 — 수정 계열 연산에는 before(수정 전 내용)가 함께 찍힙니다. 실제 하네스의 edit 도구가 old/new 문자열을 받는 걸 떠올리면 자연스러운 가정입니다.

{{< highlight python >}} import json, pathlib # trajectory.jsonl — 하네스가 남긴 파일 연산 로그 (시간순) # {"op":"read", "path":"src/app.py", "content":"def main():\n pass\n"} # {"op":"write", "path":"src/app.py", "before":"def main():\n pass\n", # "after":"def main():\n run()\n"} # {"op":"create", "path":"src/new_util.py", "after":"def run(): ...\n"} # {"op":"delete", "path":"tmp/cache.pkl", "before":""} def invert(traj_path: str, workspace: str): """궤적을 역재생해 태스크 시작 시점의 워크스페이스를 복원한다.""" ops = [json.loads(l) for l in open(traj_path)] ws = pathlib.Path(workspace) for op in reversed(ops): # 최신 연산부터 거꾸로 p = ws / op["path"] p.parent.mkdir(parents=True, exist_ok=True) if op["op"] in ("write", "delete"): p.write_text(op["before"]) # 수정·삭제 전 내용으로 되돌림 elif op["op"] == "create": p.unlink(missing_ok=True) # 에이전트가 만든 파일은 원래 없었음 elif op["op"] == "read": if not p.exists(): # 읽기만 한 파일도 초기 상태의 증거 p.write_text(op["content"]) # 여기까지가 '부분 워크스페이스'. # 궤적에 안 나온 파일(예: import되지만 열어본 적 없는 모듈)은 # completion agent가 문맥을 보고 채워야 한다. {{< /highlight >}}

30줄짜리 장난감이지만 실제 파이프라인의 어려움이 어디서 오는지 그대로 보여 줍니다. read의 출력조차 초기 상태의 증거가 된다는 것(에이전트의 탐색이 곧 환경의 스냅숏), 반대로 궤적에 한 번도 등장하지 않은 파일은 원리적으로 복원 불가라는 것. 그 빈칸을 채우는 completion agent의 품질이, 복원된 환경이 실제로 "돌아가는" 환경인지 갈라놓습니다. 복원 후에 오라클 풀이를 다시 실행해 검증기가 통과하는지 확인하는 것 — 즉 환경 자체를 테스트하는 것 — 이 파이프라인의 마지막 안전장치가 되는 이유입니다.

7. 흔한 실수 · 팁

  • 검증기를 대충 만든다. 합성 환경 수천 개를 자랑해도 검증기가 약하면 훈련 신호가 전부 오염됩니다. "answer.txt가 존재하면 통과" 수준의 검증기는 에이전트에게 reward hacking을 가르치는 셈입니다. 정답을 독립적으로 재계산하는 검증기, 금지 상태까지 확인하는 검증기를 만드세요. Terminal-Bench 2.1의 수리 항목에 "reward hacking에 대한 강건성 개선"이 들어 있는 건 우연이 아닙니다.
  • 외부 의존성을 고정하지 않는다. 환경이 pip install latest-thing처럼 바깥세상에 열려 있으면, 몇 달 뒤 의존성이 바뀌면서 태스크가 조용히 깨집니다. Terminal-Bench 2.1이 수리한 태스크 중 9개가 정확히 이 문제였습니다. 이미지 빌드 시점에 버전을 박아 넣고, 가능하면 실행 중 네트워크를 끊으세요.
  • 지시문과 검증기가 어긋난다. 지시는 "로그를 정리하라"인데 검증기는 특정 파일명을 요구하면, 에이전트는 정당하게 일하고도 실패합니다. 오라클 풀이를 지시문만 보고 다시 실행해 통과하는지 확인하는 습관이 이 불일치를 잡아 줍니다.
  • 리소스 예산을 짜게 잡는다. 타임아웃·메모리가 빠듯하면 "느리지만 정당한 풀이"가 실패로 채점됩니다. Terminal-Bench 2.1에서 8개 태스크가 이 문제로 수리됐습니다. 오라클 풀이 실행 시간의 몇 배를 여유로 주세요.
  • 합성 데이터의 되먹임을 잊는다. 내 에이전트의 궤적으로 환경을 만들고 그 환경에서 다시 내 에이전트를 훈련하면, 에이전트의 습관과 편향이 데이터에 증폭되어 돌아올 수 있습니다. 궤적 출처를 다양화하고, 사람이 만든 홀드아웃 벤치마크(Terminal-Bench 같은)로만 성과를 판정하세요. 훈련에 벤치마크 유사 태스크가 섞이는 오염도 같은 맥락에서 경계해야 합니다.
  • 환경 '개수'에 취한다. 37.3k라는 숫자보다 중요한 건 그중 몇 개가 검증 가능한 태스크를 실제로 뽑아내는가, 난이도 분포가 훈련에 유용한가입니다. Environment Evolution 같은 난이도 제어 연구가 따로 있는 이유입니다. 자체 보고 벤치마크 수치는 조건(모델·벤치 버전·훈련 방식)과 함께 읽으세요.
  • 팁: 하네스의 로그 포맷을 미리 챙기세요. 궤적→환경 역변환의 재료는 결국 도구 호출의 상세한 입출력 기록입니다. 지금 에이전트를 운영하고 있다면, 파일 연산의 전후 내용을 구조화해 남기는 것만으로 미래의 훈련 자산을 적립하는 셈입니다. 요약·절단된 로그는 되돌릴 수 없습니다.

8. 마무리 (TL;DR)

  • 에이전트 post-training의 병목은 궤적이 아니라 환경입니다. 궤적은 얼어붙은 시연 한 편이고, 환경은 여러 검증 가능한 태스크로 재질의할 수 있는 데다 실행 피드백까지 주는 연습장입니다.
  • 환경 = 지시 + 실행 가능한 워크스페이스(Docker) + 최종 상태를 검사하는 검증기 (+ 오라클 풀이 + 시간 제한). 전문가 100명이 만든 Terminal-Bench 2.0이 89개에 그치고 그마저 2.1에서 대거 수리된 것이 수작업 환경 제작의 비용을 보여 줍니다.
  • 이번 주 HF 트렌딩 1위 Terminal-Universe(Qwen 팀)의 핵심: 궤적의 도구 실행 이력에는 환경의 설계도가 새겨져 있다. 파일 연산을 역재생해 수정 전 상태를 복원하고, 빈칸은 completion agent가 채워서 공개 궤적으로부터 환경 37,300개를 복원했습니다.
  • 복원한 환경에서 원래 태스크를 재구성하고, breadth(환경 간 의존 관계로 교차 워크스페이스 태스크)와 depth(user agent의 멀티 라운드 피드백)로 새 태스크를 합성합니다. Qwen3.5-27B SFT 기준 Terminal-Bench 2.1 +11.9pt(자체 보고).
  • 큰 그림은 플라이휠입니다: 환경에서 훈련 → 배포 → 실사용 궤적 축적 → 역변환으로 다시 환경. 잠자던 로그 창고가 훈련 인프라로 바뀝니다.
  • 직접 만들 때의 급소: 검증기 강도, 의존성 고정, 지시-검증 일치, 리소스 여유, 되먹임·오염 경계. 그리고 지금부터라도 하네스의 파일 연산 로그를 상세하게 남기세요 — 그게 미래의 환경입니다.
