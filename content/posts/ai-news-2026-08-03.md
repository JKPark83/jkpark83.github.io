# 📚 주목 논문

## 1. MANTA — 통신 토폴로지를 실행 중에 스스로 바꾼다

- **저자**: Mao-xun Huang, Jerry Wang, Yi-Cheng Lai, Zhengxin Zhang, Claire Cardie, Hen-Hsen Huang
- **arXiv**: [2607.28527](https://arxiv.org/abs/2607.28527) · cs.AI (2026-07-30)
- **핵심 기여**: 기존 멀티에이전트 시스템은 통신 토폴로지를 "설계 시 고정값" 또는 "오프라인 최적화 대상"으로 다뤘다. MANTA는 이를 **추론 시점에 자가진화**시킨다.
- **방법(3줄)**: ① 과거 구조 경험으로 태스크 조건부 토폴로지를 초기화. ② 협업 트레이스를 감시하다 현재 조직이 부족해지면 **경계 있는(bounded) 구조 업데이트**를 트리거. ③ 역할·통신 링크·실행 순서·정보 가시성·검증 경로를 바꾸되 태스크 인터페이스와 에이전트 예산은 보존.
- **결과(검증됨)**: 정보 탐색·툴 사용·플래닝·워크플로 실행·수리추론 5개 벤치마크에서 **평균 74.0점, 최강 베이스라인 대비 +5.8pp**, PlanCraft에서 최고 성적.
- 🛠 **에이전트 빌더 시사점**: 멀티에이전트 그래프를 하드코딩하지 말 것. "언제 역할을 추가/제거하고 통신 링크를 바꿀지"를 런타임 신호(실패·정체)에 연결하면, 같은 예산으로 더 넓은 태스크를 커버할 여지가 생긴다.
- ⚠️ **한계**: 초록 수치만으로는 업데이트 트리거의 오버헤드·안정성(진동)이 실제 프로덕션에서 어떤지 불명. 5개 벤치마크 밖 일반화도 추가 검증 필요.

![MANTA 방법 다이어그램: 초기화 → 트레이스 감시 → 토폴로지 재구성](/images/ai-news-2026-08-03/manta-topology.svg)
*MANTA 3단계 파이프라인 — 조직도를 고정이 아니라 추론 중 갱신 대상으로. 수치는 arXiv 초록에서 검증. Generated SVG.*

## 2. One Human, N Agents — 감독 예산과 "무용지물" 신뢰도

- **저자**: Cesare Zavattari, Alessandro Tommasi, Giuseppe Prencipe
- **arXiv**: [2607.28317](https://arxiv.org/abs/2607.28317) · cs.AI (2026-07-30)
- **핵심 기여**: 사람 한 명이 라운드당 `B ≪ N`번만 감사할 수 있을 때, 에이전트의 **자기보고 신뢰도(self-reported confidence)로 감사 우선순위를 매기는 게 언제 랜덤보다 나빠지는지**를 정량화. miscalibration 임계값 `δ*`를 특정한다.
- **방법(2줄)**: 2-레벨 가우시안 코퓰러 위에서 예산 제약 노이즈 검사로 모델링하고, 기록된 트레이스에 정책을 리플레이해 순서를 확인.
- **결과(검증됨)**: 두 직관이 뒤집힌다 — **예산이 작아질수록 `δ*`가 오르고**, 크로스-패밀리 상관은 낮지 않다(계보보다 "공유된 난이도"가 지배). 오픈웨이트 5종은 신뢰도가 사실상 상수라 **운영상 무용지물**, 프로프라이어터리 1종만 임계 아래로 정보력이 있었다.
- 🛠 **에이전트 빌더 시사점**: 에이전트 함대를 굴린다면 "confidence 높은 것부터 사람이 확인" 전략이 **역효과**일 수 있다. 특히 오픈웨이트 자기보고 신뢰도는 그대로 믿지 말 것. 신뢰도를 감사 배분에 쓰기 전에 **calibration부터 측정**하라.
- ⚠️ **한계**: 코퓰러 가정과 시뮬레이션/리플레이 기반이라, 실제 다양한 도메인·적대적 세팅에서의 재현은 별도 확인 필요.

# 🛠 오픈소스 스포트라이트

> ⚠️ **정직성 메모**: 이 세션은 egress 정책상 `api.github.com`의 임의 레포에 접근할 수 없었다. 그래서 오늘은 **star 수치를 싣지 않는다**(스펙상 star는 GitHub API로 검증해야 함). 아래는 오늘의 멀티에이전트 토폴로지 주제와 직결되는, 실제 존재하는 대표 프레임워크의 기능 요약이다.

- **CrewAI** — [github.com/crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) · Python. 역할(role)·목표(goal)·태스크를 선언해 **여러 에이전트가 협업하는 crew**를 구성한다. MANTA의 관점에서 보면, CrewAI의 process(`sequential`/`hierarchical`)가 곧 "통신 토폴로지"다. 매니저-워커 위계 vs 순차 파이프라인을 태스크별로 바꿔 끼우는 실험을 여기서 바로 해볼 수 있다.
- **AutoGen** — [github.com/microsoft/autogen](https://github.com/microsoft/autogen) · Python. **대화형 멀티에이전트**의 대표 프레임워크. `GroupChat`/`GroupChatManager`로 여러 에이전트가 메시지를 주고받게 하고, 발화 순서·종료 조건을 코드로 정의한다. 오늘 논문들의 "감독 예산·토폴로지"를 실험할 최소 하네스로 적합.

**써먹기**: 두 프레임워크 모두 토폴로지를 코드로 노출하므로, One Human 논문의 교훈("신뢰도로 감사 우선순위 매기지 말라")을 **매니저 에이전트의 라우팅 로직**에 그대로 적용해볼 수 있다 — 신뢰도 대신 실패 이력·검증 실패율로 사람 리뷰를 배분.

### 🟩 Codex · Review
- **카테고리**: Review
- **source**: [developers.openai.com/codex/app/review](https://developers.openai.com/codex/app/review)
- 💡 **핵심**: `/review`는 워킹트리를 **바꾸지 않고** 우선순위별 findings만 뽑아준다. 커밋/PR 전 셀프 게이트로.
- 📝 **how-to**: 세션에서 `/review`를 치고 모드를 고르거나, CLI로 직접:

```bash
# 커밋 전 로컬 변경(staged+unstaged+untracked) 리뷰
codex review --uncommitted

# 브랜치 diff를 base 대비로 리뷰 (merge-base 기준)
codex review --base main
```

- 🎯 **언제**: PR 열기 직전, 또는 큰 리팩터를 커밋으로 쪼개기 전.
- ⚠️ **caveat**: 프로젝트가 git repo 안이어야 함. 리뷰어는 승인 필요한 액션(sandbox escalation, 차단된 네트워크 등)만 평가한다는 점 유의.
- ⭐ **추천**: `codex review --base main`을 pre-push 훅/CI 게이트로 붙이면 사람 리뷰 부하가 줄어든다.

### 🟦 Claude Code · Subagent Review
- **카테고리**: Subagent / Review
- **source**: [code.claude.com/docs/en/whats-new](https://code.claude.com/docs/en/whats-new)
- 💡 **핵심**: `/code-review`가 **백그라운드 subagent**로 돌아, 리뷰 결과가 메인 대화 컨텍스트를 채우지 않는다. 긴 작업 중 리뷰를 병렬로.
- 📝 **how-to**:

```text
> /code-review        # 정확성 버그를 별도 백그라운드 세션에서 스캔
> /fork               # 현재 대화를 백그라운드 세션으로 복제, 나는 계속 작업
```

- 🎯 **언제**: 기능 구현을 이어가면서 동시에 방금 만든 diff를 검증하고 싶을 때.
- ⚠️ **caveat**: subagent가 다시 서브를 스폰하는 백그라운드 체인은 **최대 5단계**까지(Week 24). 무한 팬아웃 설계 금지.
- ⭐ **추천**: "구현 세션 1 + 리뷰 subagent 1"을 기본 페어로. MANTA식으로 말하면 "검증 경로를 토폴로지에 상시 배치".

### 🟪 공통 · 감독 예산을 설계에 넣기
- **카테고리**: Eval / Workflow
- **source**: [arXiv 2607.28317](https://arxiv.org/abs/2607.28317)
- 💡 **핵심**: 에이전트 함대에서 "자기보고 confidence 높은 것부터 사람 확인"은 **랜덤보다 나쁠 수 있다**(특히 오픈웨이트).
- 📝 **how-to**: 감사 배분 신호로 confidence 대신 **검증 가능한 대리 지표**를 써라 — 테스트 실패, 툴콜 에러율, 이전 라운드 롤백 횟수. 도입 전엔 신뢰도-정확도 calibration(reliability diagram)부터 그려볼 것.
- 🎯 **언제**: 사람 1명이 다수 에이전트/PR을 감독하는 CI·오토파이 세팅.
- ⚠️ **caveat**: 논문은 시뮬레이션/리플레이 기반. 내 파이프라인에선 소규모로 A/B(신뢰도 랭킹 vs 실패이력 랭킹) 먼저.
- ⭐ **추천**: "confidence를 오케스트레이션 신호로 쓰기 전에 calibration 측정"을 팀 룰로.
