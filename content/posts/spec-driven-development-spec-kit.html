“로그인에 이메일 인증 붙여줘.” 에이전트가 뚝딱 만들어 줍니다. 그런데 만료 시간은요? 재발송 제한은요? 이미 가입한 이메일이면요? 에이전트는 추측해서 채우고, 리뷰어인 당신은 diff 200줄을 보며 “이게 내가 원한 거였나?”를 거꾸로 되짚습니다.

— 문제는 코드가 아니라, 코드를 짜기 전에 아무도 “무엇을 만들지”를 적어 두지 않았다는 데 있습니다.

1. 왜 지금 '명세 주도 개발'이 화제인가

2026년의 코딩은 예전과 다릅니다. 이제 코드의 상당 부분을 코딩 에이전트(coding agent)가 씁니다. Claude Code, Cursor, GitHub Copilot, Codex 같은 도구에 “이런 기능 만들어줘”라고 던지면 파일을 여러 개 만들고 테스트까지 붙여 줍니다. 짧고 명확한 작업은 정말 잘합니다.

그런데 실무자들이 입을 모아 말하는 벽이 있습니다. 작업이 조금만 길고 애매해지면 에이전트가 의도를 표류시킨다는 겁니다. 처음엔 A를 만들려다 중간에 B로 흘러가고, 채워야 할 빈칸(만료 시간·에러 처리·엣지 케이스)을 제멋대로 추측합니다. 이걸 두고 흔히 바이브 코딩(vibe coding)이라 부릅니다 — 느낌으로 던지고 나오는 대로 받는 방식이죠.

여기에 대한 반작용으로 떠오른 규율이 명세 주도 개발(spec-driven development, 줄여서 SDD)입니다. 발상은 한 문장으로 요약됩니다 — “코드를 짜기 전에, 무엇을 만들지를 먼저 실행 가능한 명세(spec)로 못박는다.” 그리고 그 명세를 사람이 검토한 뒤에야 에이전트에게 코드를 맡깁니다.

왜 이번 주에도 계속 talking point일까요? 2025년 9월 GitHub이 공개한 오픈소스 툴킷 Spec Kit이 방아쇠였습니다. 2026년 8월 현재 GitHub 스타 12만 개를 넘겼고(MIT 라이선스), Copilot·Claude Code·Cursor·Gemini CLI·Codex 등 30종이 넘는 에이전트를 지원합니다. AWS Kiro, OpenSpec, BMAD 같은 경쟁 도구도 쏟아지면서, SDD는 “특정 제품”이 아니라 “에이전트가 코드를 쓰는 시대에 사람이 갖춰야 할 규율”이라는 인식이 자리 잡았습니다. 동시에 “프롬프트가 길어지고 토큰이 더 든다”는 회의론도 함께 커지며, SDD가 정말 값을 하는가가 실무 논쟁의 한복판에 있습니다.

한 줄 요약. 명세 주도 개발은 “코드 먼저”가 아니라 “명세 먼저”로 순서를 뒤집는 방법입니다. 에이전트가 코드를 쓰는 시대에, 사람이 만들 수 있는 가장 레버리지 큰 산출물은 코드가 아니라 정확한 명세라는 발상이 핵심입니다.

2. 배경 — 바이브 코딩이 무너지는 지점

바이브 코딩이 왜 길어지면 무너지는지 이해하면 SDD의 필요성이 자연스럽게 보입니다. 두 가지 성질 때문입니다.

첫째, LLM은 컨텍스트가 길어질수록 흐릿해집니다. 초반에 “JWT 만료는 15분”이라고 말해도, 대화가 수천 토큰 이어지면 그 지시가 뒤쪽 토큰에 묻혀 사실상 잊힙니다(관련 현상을 context rot이라 부릅니다). 의도가 대화 속에만 있으면, 대화가 길어질수록 의도는 옅어집니다.

둘째, 대화에 흘려보낸 의도는 재현도 리뷰도 안 됩니다. 어제 채팅으로 합의한 “재발송은 60초에 한 번”이라는 규칙은 오늘 새 세션에는 존재하지 않습니다. 팀원은 그 결정을 볼 방법이 없고, 코드 리뷰에서도 “원래 뭘 만들려고 했는지”가 없으니 diff만 보고 판단해야 합니다. 즉 의도가 버전 관리되지 않는 게 근본 문제입니다.

TDD랑 뭐가 다른가요? 닮았습니다. 테스트 주도 개발(TDD)이 “구현 전에 테스트를 먼저”라면, SDD는 “구현 전에 명세를 먼저”입니다. 다만 대상이 다릅니다. TDD의 테스트는 사람이 짜고, SDD의 코드는 에이전트가 짭니다. 그래서 SDD에서 사람의 일은 “좋은 테스트”가 아니라 “좋은 명세”를 쓰는 쪽으로 옮겨 갑니다.

3. 핵심 아이디어 — 명세를 single source of truth로

SDD를 한 단어로 요약하면 “intent-driven”, 즉 의도 주도입니다. 공식 문서의 표현을 빌리면 “무엇을(the what)을 어떻게(the how)보다 먼저 정의한다”는 것이죠. 그리고 그 “무엇을”을 머릿속이나 채팅이 아니라 버전 관리되는 파일에 적습니다.

이 발상의 힘은 두 가지입니다.

  • 명세가 single source of truth가 된다. 코드가 명세를 따르므로, 무언가 어긋나면 “코드가 틀렸나, 명세가 틀렸나”를 명확히 물을 수 있습니다. 의도가 파일로 존재하니 리뷰·토론·재현이 됩니다.
  • 한 번에 다 생성하지 않는다(multi-step refinement). 두루뭉술한 아이디어를 곧장 코드로 바꾸는 대신, 명세 → 계획 → 태스크 → 구현으로 단계를 나눠 각 단계에서 사람이 검토하고 방향을 잡습니다. 각 단계의 산출물이 다음 단계의 입력이 됩니다.

핵심 전환은 이겁니다 — 에이전트가 코드를 값싸게 대량으로 뽑아내는 세상에서, 병목이자 자산은 코드가 아니라 “정확히 무엇을 만들지”가 됩니다. 그러니 사람의 시간을 코드 타이핑이 아니라 명세를 벼리는 데 씁니다.

4. 파이프라인 해부 — constitution → implement

추상적으로 들리니 실제 도구로 내려가 봅시다. GitHub Spec Kit은 SDD를 슬래시 명령 몇 개의 파이프라인으로 구현합니다. 에이전트(예: Claude Code, Copilot) 안에서 이 명령들을 순서대로 부르면, 각 단계가 저장소에 파일 산출물을 남깁니다.

각 단계가 무슨 일을 하는지 하나씩 봅시다.

단계하는 일남기는 파일
/speckit.constitution프로젝트의 변하지 않는 원칙을 정한다. 코드 품질, 테스트 기준, 성능 요구 같은 “집안 헌법”.memory/constitution.md
/speckit.specify무엇을·왜를 쓴다. 사용자 스토리와 성공 기준. 기술 얘기는 아직 금지.specs/<이름>/spec.md
/speckit.plan어떻게를 정한다. 언어·프레임워크·아키텍처·제약을 명세에 붙인다.specs/<이름>/plan.md
/speckit.tasks계획을 검증 가능한 작은 태스크로 쪼갠다.specs/<이름>/tasks.md
/speckit.implement태스크 목록을 하나씩 실행해 코드를 생성한다.소스 코드·테스트
/speckit.converge (선택)이미 짠 코드를 명세와 대조해 남은 일을 찾아 태스크에 덧붙인다.tasks.md 갱신

포인트는 specify와 plan을 갈라놓은 것입니다. specify에서는 “무엇을”만 다루고 기술 선택은 일부러 미룹니다. 요구사항과 구현을 섞으면 “왜 이 기능이 필요한가”가 “React냐 Vue냐” 같은 논의에 파묻히기 때문입니다. 관심사를 분리(separation of concerns)하는 거죠.

5. 왜 이게 '컨텍스트 엔지니어링'인가

SDD가 단순한 문서 작성 습관이 아니라 컨텍스트 엔지니어링(context engineering)인 이유가 여기 있습니다. 컨텍스트 엔지니어링이란 “매 단계에서 에이전트의 제한된 컨텍스트 창에 어떤 토큰을 넣을지 설계하는 일”입니다. SDD의 파이프라인은 바로 그 설계를 단계별로 수행합니다.

구현 단계에서 에이전트가 실제로 받는 컨텍스트를 생각해 보세요. 바이브 코딩이라면 “로그인에 이메일 인증 붙여줘”라는 한 줄과 방대한 코드베이스가 전부입니다. 나머지는 전부 추측이죠. 반면 SDD라면 에이전트는 constitution.md(지켜야 할 원칙) + spec.md(무엇을) + plan.md(어떻게) + 지금 이 태스크 하나를 받습니다. 필요한 의도가 파일로 컨텍스트에 실려 들어오니 추측할 여지가 줄어듭니다.

같은 이유로, SDD는 AGENTS.md 같은 저장소 지시 파일과 잘 어울립니다. AGENTS.md가 “이 저장소의 상시 규칙”이라면, spec/plan은 “지금 이 기능의 일회성 의도”입니다. 상시 규칙 위에 이번 작업의 명세를 얹는 구조죠.

6. 실전 — Spec Kit으로 5단계 직접 돌리기

직접 손에 익혀 봅시다. Spec Kit은 파이썬 CLI specify-cli로 시작합니다. uv(파이썬 패키지·툴 매니저)가 있으면 한 줄로 설치됩니다. 버전은 빠르게 오르니 최신 릴리스 태그로 바꿔 쓰세요.

{{< highlight bash >}} # specify-cli 설치 — vX.Y.Z 는 최신 릴리스 태그로 교체 (예: v0.12.11) uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z # 새 프로젝트 초기화 — 사용할 에이전트를 --integration 으로 지정 (copilot, claude, cursor …) specify init my-photo-app --integration copilot cd my-photo-app {{< /highlight >}}

초기화하면 .specify/ 디렉터리와 슬래시 명령 정의가 깔립니다. 이제부터는 에이전트 안에서 명령을 부릅니다. 순서대로 따라가 봅시다.

  1. 원칙 정하기. 이 프로젝트가 항상 지킬 규칙을 헌법으로 박아 둡니다.
  2. 명세 쓰기. 무엇을·왜만 씁니다. 기술 얘기는 아직 하지 않습니다.
  3. 계획 세우기. 이제 스택·아키텍처를 정합니다.
  4. 태스크로 쪼개기. 계획을 작은 단위로 나눕니다.
  5. 구현. 태스크대로 코드를 생성하고, 사람이 리뷰합니다.

에이전트에 실제로 입력하는 명령은 이런 모양입니다(공식 예시를 각색).

{{< highlight text >}} # 1) 원칙 — 무엇을 타협하지 않을지 /speckit.constitution 코드 품질, 테스트 기준, 접근성, 성능을 중시하는 원칙을 세워줘. 모든 기능에는 테스트가 있어야 하고, 라이브러리는 최소로. # 2) 명세 — 무엇을·왜 (기술 얘기 금지) /speckit.specify 사진을 앨범별로 정리하는 웹앱을 만들고 싶어. 앨범은 날짜별 그룹으로 묶고, 드래그로 사진을 옮길 수 있어야 해. (성공 기준: 100장을 3초 안에 렌더, 앨범 간 이동은 되돌리기 지원) # 3) 계획 — 어떻게 /speckit.plan Vite 기반에 라이브러리는 최소로. 상태는 로컬 스토리지에 저장하고, 백엔드는 아직 없이 프런트만. # 4) 태스크 — 작게 쪼개기 /speckit.tasks # 5) 구현 — 태스크대로 코드 생성 /speckit.implement {{< /highlight >}}

중요한 건 명령 사이사이에 사람이 파일을 열어 읽고 고치는 것입니다. specify 뒤에는 spec.md를 열어 “아, 삭제는 어떻게 하지?” 같은 빈칸을 채우고, tasks 뒤에는 태스크가 너무 크지 않은지 봅니다. 이 검토가 SDD의 핵심 가치입니다 — 값싼 명세 단계에서 오류를 잡으면, 비싼 구현·리뷰 단계에서 잡는 것보다 훨씬 저렴합니다.

왜 파일로 남기는 게 이득일까요? spec.md·plan.md·tasks.md가 전부 저장소에 커밋되기 때문입니다. PR에 코드와 함께 명세가 올라오니, 리뷰어는 “무엇을 만들려 했는가”를 보고 “그대로 됐는가”를 판단할 수 있습니다. 나중에 요구가 바뀌면 spec.md를 고치고 다시 흘려보내면 됩니다.

7. 흔한 실수 · 팁

SDD는 만능이 아닙니다. junior가 자주 밟는 함정을 정리합니다.

함정 1 — 작은 일에도 5단계를 다 돌린다. 오타 수정이나 버튼 색 바꾸기에 constitution부터 돌리는 건 배보다 배꼽입니다. SDD는 여러 파일에 걸친, 애매하고, 오래 걸리는 기능에서 값을 합니다. 5분짜리 작업은 그냥 시키세요.

함정 2 — 명세가 곧 프롬프트가 길어진다 = 토큰이 는다. 실제로 SDD 회의론의 핵심이 이겁니다. constitution·spec·plan을 매 구현 단계에 실으면 토큰 비용과 지연이 늘어납니다. 그러니 명세는 정확하되 짧게 쓰고, 관련 없는 배경은 빼세요. 명세는 소설이 아니라 계약서입니다.

함정 3 — spec drift(명세 표류). 구현 도중 요구가 바뀌었는데 코드만 고치고 spec.md는 안 고치는 경우입니다. 그러면 명세가 거짓말이 되고, single source of truth라는 전제가 무너집니다. 규칙: 코드를 바꾸기 전에 명세를 먼저 바꾼다. Spec Kit의 /speckit.converge는 코드와 명세의 간극을 다시 맞추는 데 쓰입니다.

함정 4 — 명세를 안 읽고 승인한다. 에이전트가 뽑은 spec.md를 훑지도 않고 바로 plan으로 넘어가면, 결국 바이브 코딩과 같아집니다. 오류는 파이프라인 앞쪽에서 잡을수록 싸다는 걸 기억하세요. 명세 한 줄을 고치는 비용 < 코드 200줄을 되돌리는 비용.

팁 — 성공 기준을 숫자로. “빨라야 한다”가 아니라 “100장을 3초 안에”처럼 검증 가능한 성공 기준을 명세에 넣으세요. 에이전트가 추측할 여지가 줄고, 나중에 “됐는지”를 객관적으로 확인할 수 있습니다.

8. 마무리 (TL;DR)

  • 명세 주도 개발(SDD)은 “코드 먼저”를 “명세 먼저”로 뒤집는 규율입니다. 에이전트가 코드를 쓰는 시대에, 사람이 만들 가장 값진 산출물은 정확한 명세라는 발상이 핵심입니다.
  • 바이브 코딩은 의도를 대화에 흘려보내 표류·비재현·리뷰 불가에 빠집니다. SDD는 의도를 spec.md 같은 버전 관리되는 파일로 못박아 single source of truth로 삼습니다.
  • GitHub Spec Kit(★127k, MIT)은 이를 constitution → specify → plan → tasks → implement 파이프라인으로 구현합니다. 각 단계가 파일을 남기고, 앞 파일이 뒤 단계의 입력이 됩니다.
  • 본질은 컨텍스트 엔지니어링입니다. 구현 단계 컨텍스트에 원칙·명세·계획·현재 태스크를 실어 에이전트의 “추측” 영역을 좁힙니다.
  • 함정: 작은 일엔 오버킬, 토큰 비용 증가, spec drift, 명세 안 읽고 승인. 명세는 정확하되 짧게, 코드보다 먼저 고치고, 성공 기준은 숫자로.
