1. 왜 지금 'Apply'가 화제인가

코딩 에이전트(coding agent) 이야기는 늘 “모델이 코드를 얼마나 잘 짜느냐”에 쏠립니다. 그런데 에이전트를 직접 굴려 본 사람들은 다른 곳에서 무너집니다. 모델이 멋진 수정안을 내놨는데, 그걸 실제 파일에 반영하는 마지막 단계에서 엉뚱한 줄을 지우거나, 중괄호가 안 맞거나, 아예 파일을 깨뜨립니다. 실제로 SWE-Agent는 아주 단순한 편집 하나를 문법 오류 때문에 일곱 번 시도하다 포기한 기록이 있습니다.

이 “마지막 1cm”, 즉 생성된 수정안을 파일에 붙이는 단계를 Apply(적용)라고 부릅니다. 2026년 들어 이게 실무 talking point가 된 건 우연이 아닙니다. Cursor의 자체 편집 모델 Composer가 “빠른 에이전트 편집”에 초점을 맞춰 버전을 올렸고, Morph는 자사 Fast Apply가 초당 10,500 토큰에 도달했다는 글을 냈으며, Relace는 apply-3 모델로 초당 4,300 토큰·정확도 96%를 내세웠습니다. 8월 초 “2026 코딩 에이전트 리더보드” 논쟁이 달아오르면서, 실무자들의 결론은 한 문장으로 모였습니다 — “AI 도구가 코드를 어떻게 바꾸는지가, 어떻게 생성하는지보다 중요하다.”

한 줄 요약. 요즘 코딩 에이전트는 파일을 통째로 다시 쓰지 않습니다. 크고 똑똑한 모델이 바뀐 조각만 적고, 작고 빠른 Apply 모델이 그 조각을 원본에 병합합니다. 이 글은 왜 그렇게 나뉘었고, 어떻게 초당 1만 토큰까지 빨라지는지를 다룹니다.

2. 배경 — 에이전트가 파일을 고치는 세 가지 방식

모델이 “이 함수에 빈 리스트 방어 코드를 넣어”라는 결정을 내렸다고 합시다. 이 결정을 파일에 반영하는 방법은 크게 세 갈래입니다. 각각의 장단점을 알면 나머지 글이 훨씬 쉽게 읽힙니다.

① 통째로 다시 쓰기(whole-file rewrite). 모델에게 “고친 파일 전체를 다시 내놔”라고 시킵니다. 개념은 가장 단순하고 결과도 정확한 편입니다. 하지만 두 가지가 아픕니다. 첫째, 느리고 비쌉니다 — Relace의 계산에 따르면 1000줄 파일을 Claude 4.5 Sonnet 같은 큰 모델로 다시 쓰면 100초 넘게 걸리고 최소 0.18달러가 나갑니다. 사람 없이 수백 개 파일을 고치는 에이전트에겐 감당이 안 되죠. 둘째, 게으름(laziness)이 생깁니다. 안 바뀐 코드까지 수백 줄을 다시 뱉는 게 모델에게도 지루한 일이라, 중간을 // ... (생략) ...로 때우고 도망갑니다. 그 파일을 그대로 저장하면 코드가 통째로 사라집니다.

② search/replace 블록. Aider가 대중화한 방식입니다. “이 옛 코드를 이 새 코드로 바꿔”라고 짝을 지어 줍니다. 바뀐 부분만 오가니 토큰이 적고 빠릅니다. 함정은 옛 코드를 원본과 글자 하나까지 똑같이 옮겨야 한다는 점입니다. 공백 하나, 주석 하나만 어긋나도 “원본에서 이 블록을 못 찾음” 에러가 나고 편집이 실패합니다. Cursor 팀의 실측으로는 이런 결정론적 diff 적용이 최소 40% 확률로 실패했습니다.

③ 게으른 편집(lazy edit) + Apply 모델. 두 문제를 역할 분리로 풉니다. 큰 모델은 ②처럼 바뀐 부분만 짧게 적되, 옛 코드를 정확히 옮기라는 부담을 지지 않습니다. 대신 // ... existing code ... 같은 마커로 “여긴 그대로”라고만 표시합니다. 그리고 이 게으른 편집을 원본과 함께 작고 빠른 전용 Apply 모델에 넘겨 완성된 파일로 병합합니다. 지금부터 이 ③을 자세히 뜯어봅니다.

3. 게으른 편집(lazy edit) — 큰 모델은 조각만 적는다

“게으른 편집”이라는 이름 때문에 나쁜 것처럼 들리지만, 여기서는 의도된 게으름입니다. 큰 모델에게 “바뀌는 부분만 써라, 나머지는 마커로 남겨라”라고 명시적으로 시킵니다. 예를 들어 아래가 큰 모델이 내놓는 게으른 편집입니다.

{{< highlight python >}} // ... existing code ... def total(items): if not items: # 새로 추가: 빈 리스트 방어 return 0 return sum(i.price for i in items) // ... existing code ... {{< /highlight >}}

파일이 500줄이든 5000줄이든, 큰 모델의 출력은 이 대여섯 줄이 전부입니다. 덕분에 두 가지를 동시에 얻습니다. 비용·지연이 확 줄고(큰 모델이 짧게 말하니까), 게으름 버그도 사라집니다(원래부터 생략이 정상이니까). 큰 모델은 “무엇을 바꿀지”라는 어려운 판단에만 집중하고, “어디에 어떻게 끼워 넣을지”라는 기계적인 일은 넘겨 버립니다.

남은 문제는 하나입니다. 이 조각을 원본의 정확히 맞는 자리에 끼워 넣어야 합니다. // ... existing code ...가 각각 어느 구간을 가리키는지, 함수 안의 어느 위치에 새 줄이 들어가는지를 판단해야 하죠. 이걸 정규식이나 단순 문자열 매칭으로 하면 앞서 본 40% 실패율로 돌아갑니다. 그래서 이 병합 자체를 학습한 모델이 등장합니다.

4. Apply 모델 — 작은 7B가 큰 모델보다 잘 병합하는 이유

Apply 모델은 딱 한 가지 일만 하도록 훈련된 작은 모델입니다. 입력은 세 개 — ㉠원본 파일 전체, ㉡게으른 편집(마커 포함), ㉢(선택) 편집 지시. 출력은 하나 — 병합이 끝난 완성 파일 전체입니다. 마커를 실제 원본 코드로 채우고, 새 줄을 올바른 자리에 끼운 결과죠.

“병합쯤은 GPT-4o 같은 큰 모델에 맡기면 되지 않나?”라는 의문이 들 겁니다. 실제로는 반대입니다. Morph의 Fast Apply는 7B 모델인데, 코드 병합만 집중 학습해서 범용 대형 모델보다 100배 빠르고 이 작업에선 정확도도 더 높습니다(자체 지표 98%). Relace의 apply 모델도 “훨씬 크고 강한 모델보다 병합을 더 잘한다”고 밝히며 정확도 96%를 제시합니다. 이유는 두 가지입니다.

  • 범위가 좁아서 작아도 된다. Apply 모델은 새 알고리즘을 발명할 필요도, 세상 지식을 알 필요도 없습니다. “이 조각을 저 자리에 정확히 끼운다”만 잘하면 됩니다. 그래서 7B, 심지어 1.5B로도 충분하고, 안 쓰는 능력에 파라미터를 낭비하지 않으니 이 좁은 과제에선 더 정확합니다.
  • 에이전트에선 정확도가 복리로 무너진다. 사람이 지켜보지 않는 자율 에이전트는 편집을 수십 번 이어서 합니다. 한 번의 병합 오류가 다음 편집의 입력을 오염시키고, 오류가 복리로 쌓입니다. 그래서 “95%면 됐지”가 아니라 마지막 1~2%까지 짜내는 전용 모델이 값을 합니다.
큰 모델 vs 작은 모델, 이렇게 나뉩니다. “무엇을 바꿀까”라는 판단은 크고 똑똑한 모델(Claude·GPT 등)이, “정확히 어디에 끼울까”라는 병합은 작고 빠른 Apply 모델이 맡습니다. 강점이 다른 두 모델에 각자 잘하는 일을 시키는, 전형적인 역할 분리입니다.

5. 왜 이렇게 빠른가 — 원본이 곧 초안(speculative decoding)

Apply 모델이 초당 수천~1만 토큰을 뿜는 비결은 투기적 디코딩(speculative decoding)입니다. 원리를 한 문장으로 말하면 이렇습니다 — 병합 결과는 원본 파일과 거의 똑같으므로, 원본 파일 자체가 거의 완벽한 “초안(draft)”이 된다.

보통 LLM은 토큰을 한 개씩 순서대로 생성합니다. 느린 근본 원인이죠(이 블로그의 투기적 디코딩 글에서 자세히 다뤘습니다). 투기적 디코딩은 값싼 방법으로 여러 토큰을 미리 “찍어” 두고, 진짜 모델이 그 찍은 값을 한 번에 검증합니다. 맞은 만큼 건너뛰니 빨라집니다. 문제는 보통 초안이 잘 안 맞는다는 건데 — Apply에서는 초안이 믿기 힘들 만큼 잘 맞습니다. 함수 하나 고치는 편집에서 출력 토큰의 80~99%는 원본과 글자 그대로 같기 때문입니다.

구체적인 숫자로 보면 감이 옵니다. Cursor는 이 아이디어를 “speculative edits”라 부르며 70B 모델로 초당 약 1,000 토큰, 평범한 추론 대비 약 9배를 냈습니다. Morph는 입력·출력 유사도를 이용해 한 스텝에 64토큰씩 찍는 방식으로 초당 10,500 토큰까지 끌어올렸고, Relace는 초당 4,300 토큰으로 Claude 4 Sonnet 대비 40배, GPT-4o-mini의 예측 편집 대비 14배 빠르다고 밝힙니다.

재미있는 역설이 하나 있습니다. Cursor는 정밀한 diff를 결정론적으로 적용하는 대신 파일 전체를 다시 쓰는 쪽을 택했습니다. ②에서 diff 매칭이 40% 넘게 실패했기 때문이죠. “전체를 다시 쓰면 느리지 않나?” 싶지만, 투기적 디코딩 덕분에 안 바뀐 부분은 사실상 공짜로 지나가므로 전체 재작성이 오히려 안정적이면서 빠릅니다. 검증은 temperature=0으로 돌려 초안과 진짜 생성의 가장 긴 일치 접두사를 찾는 결정론적 방식이라, 속도를 위해 정확도를 희생하지도 않습니다.

6. 실전 — Predicted Outputs로 직접 체험하기

Morph·Relace는 상용 API지만, 이 “원본을 초안으로 쓰는” 트릭은 OpenAI Predicted Outputs로 지금 바로 체험할 수 있습니다. Chat Completions에 prediction 파라미터로 “이런 출력이 나올 것 같다”는 참조 문자열(보통 원본 파일)을 함께 주면, 내부적으로 투기적 디코딩이 걸려 재작성·편집이 3~5배 빨라집니다. GPT-4o·GPT-4o-mini·GPT-4.1 계열에서 지원합니다.

{{< highlight python >}} from openai import OpenAI client = OpenAI() original = open("cart.py").read() # 원본 파일 = 초안으로 재사용 resp = client.chat.completions.create( model="gpt-4o-mini", messages=[ {"role": "user", "content": "total() 함수에 빈 리스트면 0을 반환하는 방어 코드를 추가하고, " "파일 전체를 그대로 다시 출력해줘.\n\n" + original}, ], # 핵심 한 줄: "출력은 원본과 거의 같을 것" 이라고 미리 알려 준다 prediction={"type": "content", "content": original}, ) print(resp.choices[0].message.content) # 얼마나 건너뛰었는지 확인 — rejected가 적을수록 이득이 크다 usage = resp.usage.completion_tokens_details print("맞은 예측 토큰:", usage.accepted_prediction_tokens) print("빗나간 예측 토큰:", usage.rejected_prediction_tokens) # 이건 그대로 과금됨! {{< /highlight >}}

출력의 대부분이 original과 같으니, 모델은 바뀐 함수 근처에서만 실제로 계산하고 나머지는 예측을 받아들여 건너뜁니다. 상용 Apply 모델을 붙이기 전, “왜 이게 빠른가”를 손으로 느껴 보기에 딱 좋습니다.

전용 Apply 모델(Morph·Relace)을 쓸 때의 요청은 대개 이런 모양입니다 — 원본과 게으른 편집을 따로 넘깁니다.

{{< highlight text >}} POST /v1/apply { "initial_code": "<원본 파일 전체>", "edit_snippet": "// ... existing code ...\ndef total(items):\n if not items:\n return 0\n return sum(i.price for i in items)\n// ... existing code ...", "instruction": "빈 리스트 방어 코드 추가" } → 응답: 병합이 끝난 완성 파일 전체 (초당 수천 토큰) {{< /highlight >}}

오픈소스로 직접 만들어 보고 싶다면, Kortix의 FastApply가 Qwen2.5 Coder 1.5B·7B를 병합 과제로 파인튜닝한 공개 모델을 제공합니다. Cursor식 Instant Apply를 재현한 것으로, 게으른 편집을 원본에 병합하는 최소 파이프라인을 눈으로 확인하기 좋습니다.

7. 흔한 실수 · 팁

흔한 실수무슨 일이 벌어지나이렇게 하세요
큰 모델에 “파일 전체 다시 써”라고만 시킴 느리고 비싸며, 중간을 // ...로 생략(laziness)해 코드가 사라짐 “바뀐 부분만 마커와 함께”로 지시하고, 병합은 Apply 모델/Predicted Outputs에 위임
search/replace의 옛 코드를 대충 옮김 공백·주석 하나만 달라도 매칭 실패 → 편집 누락 정확 매칭이 부담되면 게으른 편집+Apply로 전환. 실패 시 재시도·검증 로직 필수
Predicted Outputs의 과금을 오해 빗나간 예측 토큰(rejected_prediction_tokens)도 완료 토큰 요금으로 과금됨 초안이 실제 출력과 많이 다르면 오히려 손해. 원본과 거의 같은 재작성/편집에만 사용
병합 결과를 검증 없이 저장 96~98%라도 자율 에이전트에선 오류가 복리로 누적 저장 전 파싱/린트/테스트로 검증하고, 실패하면 그 diff만 되돌리는 안전장치
마커 규칙을 프롬프트에 안 알려 줌 큰 모델이 제멋대로 생략해 Apply 모델이 자리를 못 찾음 // ... existing code ... 같은 마커 형식을 명시하고 예시를 한 개 넣기
팁 — “적용도 평가 대상”입니다. 에이전트 품질을 볼 때 보통 “정답 코드를 냈나”만 봅니다. 하지만 실전에선 낸 코드가 파일에 온전히 들어갔나가 절반입니다. 편집 성공률(적용 후 파싱·테스트 통과율)을 별도 지표로 뽑아 두면, 모델을 바꾸지 않고도 에이전트 신뢰도를 크게 끌어올릴 지점을 찾게 됩니다.

8. 마무리 (TL;DR)

  • 코딩 에이전트의 진짜 병목은 생성이 아니라 적용(apply)입니다. 멋진 수정안도 파일에 잘못 붙으면 코드를 깨뜨립니다.
  • 파일을 고치는 방식은 셋 — 통째 재작성(느리고 게을러짐), search/replace(옛 코드 매칭 실패 40%+), 게으른 편집 + Apply 모델(요즘 표준).
  • 요즘 방식은 역할을 나눕니다. 크고 똑똑한 모델이 “무엇을 바꿀지”만 조각으로 적고(마커 사용), 작고 빠른 Apply 모델이 원본에 병합합니다.
  • Apply 모델은 7B로도 큰 모델보다 잘하고 빠릅니다. 병합 한 가지만 학습해 작아도 정확하고(96~98%), 에이전트에선 이 마지막 1~2%가 오류 복리를 막습니다.
  • 초고속의 비결은 투기적 디코딩입니다. 출력이 입력과 80~99% 같으니 원본이 곧 초안 — 안 바뀐 구간은 건너뛰고 바뀐 곳만 생성해 초당 4,300(Relace)~10,500(Morph) 토큰을 냅니다.
  • 지금 손으로 체험하려면 OpenAI Predicted Outputs의 prediction 파라미터에 원본 파일을 넣어 보세요. 단, 빗나간 예측 토큰도 과금되니 “거의 같은 재작성”에만 쓰는 게 이득입니다.
