# 📚 주목 논문

## 1. ToolSpace: 환경을 "데이터에서"가 아니라 "툴에서" 만든다

- **저자**: Guanting Dong, Zhichao Sun, Xinyu Yang 외 22인 (초록에 소속 미표기)
- **arXiv**: [2611.05036](https://arxiv.org/abs/2611.05036) (cs.CL)
- **핵심 기여**: 기존 MCP 환경 합성은 DB·시나리오를 먼저 만들고 툴을 거기서 유도해, 실제 툴 인터페이스와 어긋나고 환경 하나를 넘는 과제가 드물었다. ToolSpace는 순서를 뒤집어 **실제 MCP 서비스의 실행 트레이스에서 툴 간 의존 관계(데이터·상태·재시도)를 캐낸 뒤** 환경을 조립한다.
- **방법**: 의존 관계 추출은 LLM 판단이 아닌 결정적 규칙으로. 가중 툴 조합 그래프를 클러스터링해 환경을 만들고, 상태를 바꾸는 환경만 DB를 합성한다. 상태 인지 랜덤 워크(롤백 포함)로 체인을 만들고, 초기 상태에서 재실행에 성공하는 샘플만 남긴다.
- **결과**: 같은 파이프라인으로 만든 AutomationBench·tau3-Bench Banking "Pro" 버전에서 프런티어 모델 7종이 최대 38.2점 하락. 학습 데이터로 쓰면 Qwen3.6-35B-A3B가 7개 장기 툴 사용 벤치마크 평균 23.0 → 41.0(RL 포함 43.2), GLM-5.2는 44.6 → 56.6으로 **Claude Opus 5와 동급**.
- 🛠 **에이전트 빌더 시사점**: "LLM이 심사한 합성 데이터"보다 "실행이 증명한 의존 관계"가 명확히 낫다는 ablation이 핵심이다. 사내 에이전트 평가 환경을 만들 때도 로그에서 실제 툴 호출 체인을 캐내는 쪽이 시나리오 작문보다 유리하다.
- **한계**: 실행 트레이스가 풍부한 도메인에서만 작동하고, 보고 수치는 저자 측 평가다.

## 2. Axion 1.0: 에이전트 모델, 레시피까지 전부 공개

- **저자**: Yuqi Jia, Yunjie Tian, Jiayu Zheng, Yijun Liang 외 (초록에 소속 미표기)
- **arXiv**: [2611.03233](https://arxiv.org/abs/2611.03233) (cs.AI, v2)
- **핵심 기여**: 미드트레이닝도 DPO도 증류도 없이 **SFT 2단계 + RL, 딱 3단계**로 상용 모델과 경쟁하는 에이전트 파운데이션 모델을 만들었다 — 그리고 웨이트만이 아니라 **데이터 구축·생성·필터링·검증·프롬프트·학습 코드 전체**를 공개했다.
- **방법**: 1단계 SFT는 베이스 모델이 스스로 푼 전략을 바탕으로 문제를 적대적으로 강화하는 "모델 인지" 데이터 구축으로 자립 추론을 만들고, 2단계는 실데이터와 결정적 계산에 접지된 검증 가능 과제로 툴 의존 추론을 확장, 마지막 RL이 장기 추론과 환경 상호작용을 다진다.
- **결과**: 광범위한 에이전틱 벤치마크에서 상용 선두 모델들과 여러 항목 경쟁(초록 기준, 세부 수치는 본문 참조).
- 🛠 **에이전트 빌더 시사점**: 자체 도메인 에이전트 모델을 파인튜닝할 때 참고할 수 있는, 처음부터 끝까지 재현 가능한 레퍼런스 파이프라인이다. 특히 "검증 가능한 과제 구축" 파이프라인은 ToolSpace와 정확히 같은 문제의식이다.
- **한계**: 초록만으로는 베이스 모델·규모·구체 수치가 안 보이므로 본문 확인이 필요하다.

# 🛠 오픈소스 스포트라이트

![agent-autoloop vs uncut](/images/ai-news-2026-11-05/repo-cards.svg)

*같은 날 뜬 두 하네스가 정반대 철학을 보여준다 — 오케스트레이션 최대주의 vs 루프 미니멀리즘.*

- **[KKKKhazix/agent-autoloop](https://github.com/KKKKhazix/agent-autoloop)** — TypeScript, 약 2,400★ (11/3 공개, 이틀 만에. GitHub 검색 API 기준). Claude Code·Codex 같은 CLI 에이전트를 **백그라운드 루프**로 돌리는 경량 중개 계층. 스케줄·GitHub 이슈·알림이 이벤트로 들어오면 규칙대로 에이전트에 배정하고, 에이전트는 한 턴 돌고 프로세스를 종료한다(대기 중 토큰 소모 없음). 사람 결정이 필요할 때만 Slack/Discord/飞书 카드가 날아오고, `agent-autoloop answer`로 응답하면 세션을 이어서 마무리한다. 커널은 런타임 의존성 제로, 프롬프트 받고 응답 출력하는 CLI면 한 줄로 연결. CLI 출력이 아직 중국어 중심이고 Windows 미지원(11월 둘째 주 예정)인 점은 감안. **활용**: "정기 리포트 생성·이슈 트리아지를 에이전트에 맡기되 결재만 내가" 패턴을 서버 없이 로컬 머신에서 구현할 때.
- **[Balanov/uncut](https://github.com/Balanov/uncut)** — Go, MIT, 약 600★ (11/1 공개). 정반대 극단: **컨텍스트를 절대 자르지 않는** 헤드리스 코딩 에이전트 하네스. 7MB 정적 바이너리 하나, 툴 4개, stdin/stdout, 구현 코드 837줄. 요약·압축·슬라이딩 윈도·자동 재시도 전부 없음이 기능이고, 공급자가 응답을 자르면 성공인 척하지 않고 에러로 종료한다. OpenAI 호환 엔드포인트면 로컬 서버도 붙는다. **활용**: CI 파이프라인용 미니멀 에이전트, 그리고 "컨텍스트 압축이 결과를 얼마나 바꾸는가"를 재는 대조군 하네스로 좋다.

### 🟩 Codex — AGENTS.md가 조용히 잘리고 있었는지 확인하라

- **분류**: Context / Debugging · **출처**: [commit 49f2fc2](https://github.com/openai/codex/commit/49f2fc2c1e4824b0a8eb0a15d3d7daeadc6c1523)
- 💡 Codex의 프로젝트 지침(AGENTS.md 등)에는 바이트 예산(`project_doc_max_bytes`)이 있는데, 지금까지는 예산이 바닥나면 **경고 없이** 파일이 잘리거나 통째로 스킵됐다. 이제 어떤 파일이 얼마나 잘렸는지, 어떤 환경이 스킵됐는지 경고로 알려준다.
- 📝 거대한 AGENTS.md를 쓰고 있다면 업데이트 후 경고를 확인하고, 다듬거나 예산을 올린다:

```toml
# ~/.codex/config.toml
project_doc_max_bytes = 65536  # 기본 예산이 모자라면 상향
```

  글로벌·스레드 지침도 총량에는 포함되지만 제한 자체는 프로젝트 파일에만 적용된다. 값을 바꾸면 캐시된 지침도 갱신된다.
- 🎯 모노레포처럼 디렉터리마다 AGENTS.md가 겹겹이 쌓이는 구조에서 "왜 지침을 무시하지?"의 원인 하나를 제거할 때.
- ⚠️ 예산을 무작정 올리면 매 턴 고정 컨텍스트 비용이 커진다. 경고가 뜨면 먼저 지침을 다이어트하는 게 맞다.
- ⭐ 추천도: AGENTS.md가 10KB를 넘는 팀이라면 오늘 확인 ★★★★☆.

### 🟦 Claude Code — MCP 서버, 이름 말고 URL로 차단 (v2.1.318)

- **분류**: MCP / Security · **출처**: [v2.1.318 릴리즈](https://github.com/anthropics/claude-code/releases/tag/v2.1.318)
- 💡 관리 설정의 `deniedMcpServers`에서 **URL 엔트리**가 Anthropic 제공 서버까지 포함해 업스트림 URL이 일치하는 모든 서버를 차단하게 됐다. 이름을 바꿔 단 같은 서버가 빠져나가는 구멍이 막힌 것.
- 📝 조직 관리 설정에서:

```json
{
  "deniedMcpServers": [
    { "url": "https://mcp.example.com/sse" },
    { "name": "내부-금지-서버" }
  ]
}
```

  클라우드 세션·자체 호스팅 러너의 커넥터는 커넥터 자체 URL로 매칭되고, URL이 없는 커넥터는 이름으로 거부한다.
- 🎯 보안 정책상 특정 외부 MCP 엔드포인트를 조직 전체에서 막아야 할 때. 이름 기반 차단은 우회가 너무 쉬웠다.
- ⚠️ URL 차단은 정확히 일치하는 업스트림에 적용되므로, 미러 도메인이 있는 서비스는 엔트리를 여러 개 넣어야 한다.
- ⭐ 추천도: MCP 거버넌스를 운영하는 조직 관리자라면 ★★★★★, 개인 사용자는 해당 없음.

### 🟪 공통 — 프롬프트 캐시 TTL을 "워크로드에 맞춰" 설계하라

- **분류**: Context / Workflow · **출처**: [codex commit 41cbd5b](https://github.com/openai/codex/commit/41cbd5b9b2d5369ba35957328504093ed324333c)
- 💡 어제오늘 두 에이전트 CLI가 같은 문제를 건드렸다. Codex는 턴 단위로 프롬프트 캐시 최소 수명을 **30m/12h** 중 고르는 옵션을 추가했고, Claude Code 2.1.318은 백그라운드 서브에이전트의 셸 명령을 3분이 지나면 자동으로 백그라운드로 보내 **캐시가 만료되기 전에** 턴을 이어가게 바꿨다. 공통 교훈: 긴 동기 툴 호출 하나가 캐시를 날리면, 다음 요청은 수십만 토큰을 콜드로 다시 쓴다.
- 📝 자체 에이전트 루프라면 ① TTL보다 오래 걸릴 명령은 백그라운드로 돌리고 폴링한다 ② 시스템 프롬프트·툴 정의 같은 접두사를 턴마다 바꾸지 않는다 ③ 야간 배치처럼 호출 간격이 긴 워크로드는 짧은 TTL 캐시에 기대지 말고 비용을 콜드 기준으로 잡는다.
- 🎯 1M 컨텍스트급 장기 세션, 서브에이전트 다수 운용, CI에서 주기 실행되는 에이전트 전부 해당.
- ⚠️ 긴 TTL은 보통 쓰기 비용이 더 비싸다. 호출 빈도가 TTL 안에 들어올 때만 이득이다.
- ⭐ 추천도: 에이전트 API 청구서가 커지고 있다면 가장 먼저 볼 항목 ★★★★★.
